Currently, the grammar is `none | <number>`. However, forcing authors to explicitly pick a number seems gratuitous. Why not add an `auto` value that just an alias for whatever the _aspect value_ is in the element's primary font?

## @fantasai — 2020-09-24

@litherum I think by cascading you mean inheritance. :) We can solve that by having `auto` compute to a number.

I remember @dbaron describing `font-size-adjust` as essentially "lets you pick the font size by its ex-height, but in a backwards-compatible way". The readability of a Latin font being more related to its ex-height than its cap-height. Such an `auto` value would not provide that functionality, just provide ex-heght consistency for font-family changes.

p.s. It's a little unfortunate that such a generic syntax is relevant only to European writing systems: I can imagine other writing systems needing adjustment across font families also. So maybe maybe it would be good if the keyword were a little more explicit that it's operating on the x-height...?

## @svgeesus — 2020-09-29

>  Such an auto value would not provide that functionality, just provide ex-heght consistency for font-family changes.

Why so? It is simply doing 

```js
let aspect = font_size[0] / x_height[0];
```
and then for all fonts in the list after the first one
```js
font_size[n] = x_height[n] * aspect;
```

> p.s. It's a little unfortunate that such a generic syntax is relevant only to European writing systems: 

It is, but [that proposal (by Todd Fahrner)](https://lists.w3.org/Archives/Public/www-style/1997Dec/0235.html) was made a long, long time ago. The Web was still proud of being 8859-1 instead of ASCII, and handling all (Western) European languages.

It was proposed just after [the first WD of CSS2 in 1997](https://www.w3.org/TR/WD-CSS2-971104/fonts.html) but made it into [the next one in 1998](https://www.w3.org/TR/1998/WD-css2-19980128/fonts.html#propdef-font-size-adjust):


> Property name:  'font-size-adjust'
> Value: z | none | inherit
> 
> z
>    This value refers to the ratio of em- to x-heights of the "first choice" font in decimal notation.

Notice it was automatically calculated, just as Myles is proposing.

The [1998 Proposed Rec](https://www.w3.org/TR/1998/PR-CSS2-19980324/fonts.html#propdef-font-size-adjust) had changed it to a number:

>  'font-size-adjust'
> Value:  &lt;number> | none | inherit
> Initial: | none

## @jfkthame — 2020-09-29

One reason (I guess) for `font-size-adjust` taking a number rather than an `auto` value is that this means it will behave consistently regardless of whether the author's first-choice font (from which the number would normally be derived) is actually present or not.

With `auto`, the aspect would be computed from whatever fallback happens to get used; it would then provide consistency across additional fallbacks, but might be quite different from what the author expected based on the primary font they had named.

An `auto` value would also mean, presumably, that if the primary `font-family` is a webfont, and hasn't yet finished loading, we can expect the size of any fallbacks that are being used (e.g. for content in other scripts) to change when the font-load does complete.

(I'm not necessarily *against* an `auto` value, just trying to think through its implications. The behavior it enables would be significantly different from what an explicit `<number>` provides.)

## @dbaron — 2020-09-29

So there was a previous proposal for `font-size-adjust: auto` which [I proposed in 2010](https://lists.w3.org/Archives/Public/www-style/2010Mar/0206.html) [Edit: also see [the thread following](https://lists.w3.org/Archives/Public/www-style/2010Mar/thread.html#msg206)] and that was discussed a good bit in [this August 2013 thread](https://lists.w3.org/Archives/Public/www-style/2013Aug/thread.html#msg420) and I think then removed.  I'd note that that proposal didn't use the first available font, but instead used the UA's initial font.  Such an auto basis isn't so useful when developers specify absolute font sizes, but it seems like it could be quite useful if the developer is using relative font sizes without resetting the UA's default to a length.  I was also (see my initial proposal) hoping it could be useful for replacing the `monospace` font size preference hacks.

## @DerKoun — 2021-04-21

In PDFreactor we have this functionality as a prefixed identifier value (computing to number).
However, we have decided on `from-font` instead of `auto`.
The reason was that `from-font` is more self-explanatory and also to keep `auto` free in case a more refined process is decided on later.

<!-- comment id=828300164 author=jfkthame created=2021-04-28T09:22:15Z url=https://github.com/w3c/csswg-drafts/issues/5539#issuecomment-828300164 -->
## @jfkthame — 2021-04-28

Yes, I quite like the suggestion of `from-font` here.

I'll also note that it combines nicely with the extension to have `font-size-adjust` accept a pair of values `<metric> <number>` (issue #6160). So if you're styling a headline with `text-transform: uppercase` you might also say `font-size-adjust: cap from-font`, to have any fallback fonts scaled to match their cap-heights with the first available font.
