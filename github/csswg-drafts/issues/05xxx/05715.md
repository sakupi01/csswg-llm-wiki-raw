There exist some use cases for `margin-box` sizing. Do we want to add this as a keyword to `box-sizing` and/or allow the sizing properties to take a `*-box` keyword to indicate which box to apply to? That would avoid authors having to manually "back out" their margins for e.g. image+margin = 100vh or float+margin = 50% of containing block.

<!-- comment id=5274570789 author=fantasai created=2026-08-13T00:48:12Z url=https://github.com/w3c/csswg-drafts/issues/5715#issuecomment-5274570789 -->
## @fantasai — 2026-08-13

@Loirooriol I'm not sure that we should treat margins as 0 in these cases. The idea of `stretch` is to fill the containing block. But you might set, for example, `max-height: 100vh; box-sizing: margin-box; margin: 1em` on some images. That should account for the margins you set regardless of whether the image's containing block (which might be an unstyled `<section>` or the styled `<article>` above it) has borders or padding.

So I think the definition here should keep it simple: we compute the margin, and we subtract it always, just like `padding`. Auto margins are treated as zero, and margin collapsing is not taken into account.

## @fantasai — 2026-09-01

**So here is what I propose:**

1. We add a `stretch(<length-percentage>)` function to the sizing values.
     * It resolves `<length-percentage>` exactly as they are resolved outside the function.
     * It unconditionally subtracts the margins (treating `auto` as zero, ignoring collapsing/trim) after resolving them just like `padding`.
2. We redefine `fit-content(X)` to match, making it `max(min-content, min(max-content, stretch(X))` rather than `max(min-content, min(max-content, X)`
3. We maybe also add `box-sizing: margin-box` if we believe it's useful.

Advantages of `stretch()` over `box-sizing`:
* It can be used independently in each axis.
* It can be used independently for min/max/preferred size.

Reasons to use `stretch()` in `fit-content()`:
* It matches the effective behavior of `fit-content()` in grid track sizing.
* Having both `stretch()` and `fit-content()` interpret their arguments consistently is nice.

**Regarding the margin collapsing shenanigans that Oriol is referring to:**

The spec defines `stretch` as follows:
> If this is a block axis size, and the element is in a Block Layout formatting context, and the ancestor element its percentages resolve against does not have a block-start border or padding and is not an independent formatting context, treat the element’s block-start margin as zero for the purpose of calculating this size. Do the same for the block-end margin.

*Note that this does not take into account whether the box is first, last, or in the middle of its containing block, and thus whether the margin actually collapses or not.* Its goal was to make the box fill its containing block with no extra space.

This behavior may make sense for the `stretch` keyword on its own. But it is unhelpful for the concept of asking the margin box fill a `<length-percentage>`:
* If your containing block is an unstyled DIV, which it often is, then your margins get ignored, even though they're there (just taking effect outside the containing block).
* If you're neither the first nor last child, which you often are, you're never collapsing with your container, but whether it has borders/padding will still affect whether your margins will be subtracted from the `<length-percentage>`, which is an unhelpful action-at-a-distance.

Altogether I think applying this behavior to `stretch()` will create problems for authors and their use cases, and we should not do it.
