There exist some use cases for `margin-box` sizing. Do we want to add this as a keyword to `box-sizing` and/or allow the sizing properties to take a `*-box` keyword to indicate which box to apply to? That would avoid authors having to manually "back out" their margins for e.g. image+margin = 100vh or float+margin = 50% of containing block.

<!-- comment id=725618022 author=Loirooriol created=2020-11-11T19:32:24Z url=https://github.com/w3c/csswg-drafts/issues/5715#issuecomment-725618022 -->
## @Loirooriol — 2020-11-11

I think margin collapse can make this confusing. Like if I have

```html
<div style="height: 100px; border-left: 10px solid">
  <p style="box-sizing: margin-box; height: 50%; margin: 20px 0; background: cyan"></p>
  <p style="box-sizing: margin-box; height: 50%; margin: 20px 0; background: cyan"></p>
</div>
```

then I would probably expect the content-area height of the `<p>` to be `40px`, so that `0px+40px+20px+40px+0px = 100px`. But if I have

```html
<div style="height: 100px; border-left: 10px solid">
  <div style="display: flow-root"></div>
  <p style="box-sizing: margin-box; height: 50%; margin: 20px 0; background: cyan"></p>
  <div style="display: flow-root"></div>
  <p style="box-sizing: margin-box; height: 50%; margin: 20px 0; background: cyan"></p>
  <div style="display: flow-root"></div>
</div>
```

then I would probably expect the content-area height of the `<p>` to be `10px`, so that `20px+10px+20px+20px+10px+20px = 100px`.

## @Loirooriol — 2026-08-05

We handled margin collapse for `stretch` sizes. So, I guess it's fine if we say that `stretch` is like `100%` with `box-sizing: margin-box`.

Then my examples in https://github.com/w3c/csswg-drafts/issues/5715#issuecomment-725618022 would treat the margins as 0, i.e. `box-sizing: margin-box` would behave as `border-box`.

But if the containing block had block-axis border/padding, or established an independent FC, then `margin-box` would be different.

<!-- comment id=5274570789 author=fantasai created=2026-08-13T00:48:12Z url=https://github.com/w3c/csswg-drafts/issues/5715#issuecomment-5274570789 -->
## @fantasai — 2026-08-13

@Loirooriol I'm not sure that we should treat margins as 0 in these cases. The idea of `stretch` is to fill the containing block. But you might set, for example, `max-height: 100vh; box-sizing: margin-box; margin: 1em` on some images. That should account for the margins you set regardless of whether the image's containing block (which might be an unstyled `<section>` or the styled `<article>` above it) has borders or padding.

So I think the definition here should keep it simple: we compute the margin, and we subtract it always, just like `padding`. Auto margins are treated as zero, and margin collapsing is not taken into account.

<!-- comment id=5276863416 author=Loirooriol created=2026-08-13T06:35:09Z url=https://github.com/w3c/csswg-drafts/issues/5715#issuecomment-5276863416 -->
## @Loirooriol — 2026-08-13

I think it should happen for percentages. But maybe not for lengths. But then what about `calc()` mixing both?

## @fantasai — 2026-08-13

Percentages are resolved against the containing block, and are otherwise exactly equivalent to the equivalent length. I don't think we want to change that.
