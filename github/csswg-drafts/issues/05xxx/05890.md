Can we have numeric comparisons?

e.g.
[data-balance<0] { color: red; } (common in accounting/finance, along with putting ( ) around the value)
[data-eyes>7.9] { color: black; background-colour: yellow } /* spider! */

with < <= >  >=

Noting that testing for equality is string equality so testing 06=6 fails, an alternative design might be to calc() to fetch an attribute value, and to be allowed in selectors, but that's more complex.

Maybe a new section inhttps://drafts.csswg.org/selectors/#attribute-selectors for Numeric Attribute Values?

## @bramus — 2022-09-12

_(Cross-post from #354)_

To numerically compare attribute values today, authors can work around this by:

1. Injecting all the values that the item is not equal to, using `data-*` attributes.
2. Using the CSS Attribute “Value Contains” Selector (e.g. `[attribute~=value]`) on those `data-*` attributes.

I’ve detailed this nasty and cumbersome hack back in the day over at https://www.bram.us/2016/10/13/css-attribute-value-less-than-greater-than-equals-selectors/.

## @Crissov — 2025-11-21

> A flag doesn't really add anything anyway - attribute selectors currently require the value to be an ident or a string, so numbers are invalid. Thus `[foo=5]` would already unambiguous as a numeric comparison rather than a string comparison.

Huh, I actually assumed that despite what the spec says about [tokenization](https://drafts.csswg.org/css-syntax-3/#tokenization), current browsers were lenient with [attribute value selectors](https://drafts.csswg.org/selectors/#attribute-representation) and authors would be relying on unquoted values working like string tokens, because quotation marks are often optional in HTML. A [quick test](https://codepen.io/Crissov-the-bold/pen/ByKwJVm) reveals that @tabatkins is not only correct in theory but in practice, too (at least unless the CSS token starts with a letter). That’s great. 

Numeric comparison should therefore just work, i.e. run through the usual syntax processing steps for the host language and CSS first, so `+.0` may equal `0e-00` for instance.

For any more complex value type, there would still need to be some kind of method flag or type hint. 
For some types that exist in CSS syntax, like dimensions and percentages, the use of a respective token on the right-hand side of the comparison should suffice. The left-hand side would simply need to match, or at least be compatible (like percentages and numbers). 
For others, like colors or – not available in CSS – datetimes, this fails, because they cannot always be distinguished from other types, strings or numbers/equations in particular.  
(PS: For tuples like colors or coordinates and for non-numeric types, e.g. URLs, comparison with `<` and `>` is also not intuitively applicable, although one often _could_ specify some concept of order or magnitude for them.)
