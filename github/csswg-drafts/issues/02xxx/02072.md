_From @birtles on September 8, 2017 6:43_

We currently have this rather awkward interface:

```webidl
dictionary BaseKeyframe {
    double?            offset = null;
    DOMString          easing = "linear";
    CompositeOperation composite;
};
```

To omit an offset you set it to `null`. To omit a composite operation you just leave the member off or set it to `undefined`.

I _think_ WebIDL might make these act alike for input but this difference is at least observable in the output of `getKeyframes()` (which hasn't shipped anywhere yet, fortunately).

Using nulls here probably would probably be inconsistent with the changes proposed in #148 so if there's no compatibility issue, I'd like to change the type of `offset` to `double` (not `double?`). I really need to look into WebIDL first and check if this makes a difference or not.

I tried making this change in Firefox and if you specify `offset: null` it still works so hopefully this is ok.

## @birtles — 2017-12-05

This might not be so safe as I first imagined. If there is existing code passing `offset: null` then if we change the type to `double`, [WebIDL will run](https://heycam.github.io/webidl/#es-double) [`ToNumber`](https://tc39.github.io/ecma262/#sec-tonumber) on the `null` value turning it into 0, which is obviously completely different.

## @birtles — 2017-12-05

I've been thinking about this some more and I'm somewhat inclined to just leave it as-is. In fact, it might even be worthwhile to make `composite` nullable.

I looked into WebIDL for some guidance and noticed this sample:

```webidl
dictionary PaintOptions {
  DOMString? fillPattern = "black";
  DOMString? strokePattern = null;
  Point position;
};
```

The explanation is:

> Both fillPattern and strokePattern are given default values, so if they are omitted, the definition of drawRectangle can assume that they have the given default values and not include explicit wording to handle their non-presence.

That is, they're only thinking about ease of input here. In this issue, though, I'm mostly looking at simplifying the output.

As for making `composite` nullable, there are a couple of reasons why this might be worthwhile:

1. Consistency with `offset` where for compatibility reasons amongst others, we need to keep supporting `null`.
1. Making it nullable means that when we introduce the array-form in #148, you can specify "holes" in the array by using null values.

## @birtles — 2017-12-05

Thinking about this further, I'm less sure whether removing the default value is helpful or not. It might just be simpler to think about offsets as being null and missing being converted to null as part of the WebIDL bindings.

On the other hand, having the default value means the generated keyframe objects are less readable and test files are more verbose.
