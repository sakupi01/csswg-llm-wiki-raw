In [CSS font-presentation](https://www.w3.org/TR/css-fonts-4/#propdef-font-presentation), it should be clarified what happens when `font-presentation` and the content’s BCP47 language tag (`lang`, `xml:lang`) specify a different Emoji presentation style. BCP47 extension -u- can be used to select an Emoji presentation style; see [section 4.2 “Emoji Locale Extension”](http://unicode.org/reports/tr51/#Emoji_Locale_Extension) of [UTS51](http://unicode.org/reports/tr51/).

<!-- comment id=354336226 author=SergeyMalkin created=2017-12-28T18:51:09Z url=https://github.com/w3c/csswg-drafts/issues/2138#issuecomment-354336226 -->
## @SergeyMalkin — 2017-12-28

I would expect 'text' or 'emoji' property values to have higher priority than language. Language may take part in resolving 'auto' value.

<!-- comment id=354385045 author=litherum created=2017-12-29T01:35:22Z url=https://github.com/w3c/csswg-drafts/issues/2138#issuecomment-354385045 -->
## @litherum — 2017-12-29

Does any browser currently support setting the presentation style from lang?

Given that there are already ways to specify text or emoji presentation, I’d like to propose normative text that specify lang should never be consulted when making an emoji/text presentation decision. Using lang for this purpose in HTML/XML/CSS is overloading a term and would be better specified elsewhere (variation selectors, font-presentation).

<!-- comment id=355006774 author=svgeesus created=2018-01-03T13:02:08Z url=https://github.com/w3c/csswg-drafts/issues/2138#issuecomment-355006774 -->
## @svgeesus — 2018-01-03

Unless some implementation already supports setting the auto value from `lang`, I agree with @litherum that it should be normatively barred from influencing the presentation.

<!-- comment id=355018441 author=macchiati created=2018-01-03T14:01:34Z url=https://github.com/w3c/csswg-drafts/issues/2138#issuecomment-355018441 -->
## @macchiati — 2018-01-03

I would expect the precedence to be the following:
1. if there is a variation selector (text or emoji), follow it. 
2. otherwise if there is a CSS property value of 'text' or 'emoji' (eg explicitly set and not 'auto'), then follow it.
3. otherwise if there is a BCP47 specification (eg en-u-em-emoji), then follow it.
4. otherwise use the default presentation for that character.

<!-- comment id=355102916 author=aphillips created=2018-01-03T19:25:48Z url=https://github.com/w3c/csswg-drafts/issues/2138#issuecomment-355102916 -->
## @aphillips — 2018-01-03

If you mean to exclude Unicode/CLDR's `-u-` extension from influencing the presentation of emoji characters *only*, I could see that. But it might be better to just ignore it. Obviously you do not mean to ignore BCP 47 (`lang`, `xml:lang`) values for other presentational purposes. There are lots of other things in `-u-` that CSS already ignores.

## @aphillips — 2018-01-21

The I18N WG discussed this in our [18 January](https://www.w3.org/2018/01/18-i18n-minutes.html#item05) teleconference and actioned me with this response.

We would support adding normative language forbidding the interpretation of the `-u-` emoji presentation subtags (and *only* those subtags) assuming that the fallback described by Mark (@macchiati) is not adopted. The WG members present noted that BCP 47 language tags are not a great mechanism for this kind of information--this doesn't really fit as a locale element, the way that, say, number shaping or sorting details do. While more clarity from the CLDR and emoji folks is possible, the greater complexity strikes us as unhelpful.
