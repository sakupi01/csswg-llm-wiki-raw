In #1144 I proposed a property to remove, add or override [Unicode Variation Selectors](http://unicode.org/faq/vs.html) (‘VS’, chiefly U+FE0x) from/to all applicable characters. The main use case presented was consistent presentation of possible emoji characters by enforcing either VS-15 or VS-16. The WG decided against adding an `override` keyword to the `font-presentation` property. I am now proposing `text-transform-variant` again, but limited to stripping (e.g. `ignore`, or keeping: `auto` or `none`) *all* VSs.

Variation selectors by definition do not change the semantics of the character varied. While emoji variation sequences usually come in pairs, others only document one specific variant, e.g. a slashed digit zero vs. the default design, which may depend on the font features set (OT `zero`, CSS `font-variant-numeric: slashed-zero`). Most variation sequences come in groups that are using VSs (usually VS-1 and VS-2) in a consistent way (but math symbols hardly do), e.g. Myanmar characters may be switched to a _dotted form_. This means variation sequences are close to or even crossing the border between character encoding and typography, hence design. They thus become in scope of CSS.

Changing the variant can usually be considered less consequential than changing letter case. It is also much more simple to implement because it only involves dropping certain Unicode Code points. Font selection should not be affected for non-emoji sequences, because it is always expected that only the base glyph without variation may be displayed. (Some emoji fonts only contain colorful glyphs which in many cases are only appropriate if VS-16 was present; e.g.  Symbola, on the other hand, only contains text-like characters which can also be considered inappropriate for one class of emojis.)

That is a use case and the primary one I am knowledgeable about, but there are a lot of variation sequences defined for sinograms (“Han characters”, “ideographs”) and this approach equally covers those. The feature is really different and separate from `font-presentation`.

## @myfonj — 2026-09-09

I think the unfortunate situation -- there being no "legal" way to control emoji variations from the "outside" the moment the author uses either physical variation selector -- has a rather web-platform-y solution hiding in plain sight.

## The Situation

My assumption is that these two authoring approaches are meant to be effectively equivalent:

    <span style="font-variant-emoji: emoji">&#9731;</span>
    <span                                  >&#9731;&#xFE0F;</span>

Similarly, the `text` variant:

    <span style="font-variant-emoji: text">&#9731;</span>
    <span                                 >&#9731;&#xFE0E;</span>

If this assumption is wrong, stop reading, since the rest of this note will also be wrong (but please correct me).

Indeed, it works flawlessly until there is a need to make some "override": while overriding the former is easy (a single `!important` away), overriding the latter is currently absolutely impossible. This means that while the author can produce content they themselves can control from either origin, they can also produce seemingly equivalent content that neither they (not even via `inline !important` (!)), the `user` (!!), nor the `user agent` (!!!) can affect any more:

    <span style="font-variant-emoji: text !important">&#9731;&#xFE0F;</span> FE0F still makes it colourful.

This is a very, very odd precedent in the specs, and I dare to say it is against the very nature of the Web Platform.

## Employ the Cascade

We should treat the "content" variation selector the same way we treat all other formatting signals coming from the **`author`** origin, since there is nothing semantically special about emoji variations that makes them different from, say, font weights or styles (is there?).

So the whole change would be pulling their effect from the untouchable, astral, undocumented origin sphere back to the place where they belong, into the `author` origin area. Presumably above "unimportant" inline. Simplified:

```diff
- ☛🖛🖝 THE almighty variation selector 🖜🖚☚
  user,UA !important stylesheets
  author !important inline style attribute
  author !important stylesheet
+ 👉☞🖙 well-behaved regular variation selector 🖘☜👈
  author inline style attribute
  author stylesheet
  UA,user stylesheets
```

This would preserve the functionality of the two "normal" example snippets, but fix the effect in the third one. The outcome is that the physical variation selector:
- wins over regular author styles,
- loses to all `!important` declarations,

just like a regular inline style attribute does.

I can imagine making it more special by moving it slightly higher, presumably at the very top of the `author` origin area instead, so it would win over even `!important` inline styles too, "nicely" preserving the current footgun for authors.

But I see absolutely no valid argument for putting it above all existing origins, stripping the `user` and `user agent` origins of any ability to affect this.
