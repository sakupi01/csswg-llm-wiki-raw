## @birtles — 2026-08-03

So the spec text here is wrong. I created a test here: https://birtles.blog/tests/restoring-animations.html

Chrome, Firefox, and Safari all appear to make the timeline continue running when loading the page from the bfcache—that is, they don't fiddle with the times to make the animation resume where it left off. As the issue text notes, doing that would be inconsistent with the relationship between animation times and other timing properties like `navigationStart`.

So we should either just drop this spec section altogether or make it explicit that browsers shouldn't try to restore animation position. I suggest the former. We could probably make a WPT for this too, if necessary.

@astearns Can I request an async resolution to drop section 8 "Interaction with page display" from Web Animations level 1?

## @birtles — 2026-08-19

> Do the pages get the finish events for all of the animations that finished in that time since you navigated away? If not, there's a possibility this will result in a broken page state.

Yes.

The proposal here is simply to remove special case behavior. In the absence of that, for pages restored from the bfcache it page continues as if it were always loaded so in effect there's just a really big gap between frames. Because the timing model is frame-rate independent, we'll catch up on any events that were scheduled in that gap.

Test case: https://birtles.blog/tests/animation-finish-events.html

Test in Chrome and Firefox (no access to Safari I'm afraid).
