## @diekus — 2025-11-24

During TPAC several of us agreed that the name `app-region` is not meaningful. This CSS property is used to define an area from where the user can point and drag a window in a desktop environment. The name `draggable` should be avoided to circumvent confusing with the [global draggable attribute in HTML](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Global_attributes/draggable). 

Starting to bikeshed on a new name for `app-region`:

-  `drag-area`
- `drag-point`
- `drag-behavior`

## @mhochk — 2025-12-01

Building on the earlier https://github.com/w3c/csswg-drafts/issues/7017#issuecomment-1609114145

Though not mentioned in the spec, the existing implementation (at least in Edge) extends not only the draggable nature of the titlebar to this element, but also other native titlebar behaviors like the default contents of the right-click menu. It seems like this is desirable, as the intended use is to replace the titlebar, so the user agent choosing to adopt other titlebar-like behaviors would be a good thing.

Given that, what about a CSS property like `titlebar-area`?


Alternatively (if there is strong pushback on the above direction):
* If keeping this to only dragging the window, and controllable via CSS, @emilio's `window-drag` seems like the right direction. Maybe `window-dragging`?
* If keeping this to only dragging the window, but potentially not as a CSS property, what about expanding the `draggable` HTML property to include a new `with-window` value. Similar to `contenteditable` having `true`/`false`/`plaintext-only` options.

## @mhochk — 2025-12-02

I chatted with @diekus a bit on this and now agree that CSS (not HTML) is the right place for this to live so that this can be cleanly controlled inside a CSS media query. As such, I withdraw my suggestion to extend `draggable`.

As for naming based on 'replaces the titlebar' vs 'drags the window', I still don't have a strong opinion, but now lean slightly towards 'drags the window'. Diego raised that modern apps, particularly on Mac, are using traditional-looking titlebars less. Likely because of this, the developer-facing native APIs for making a region that drags the window are moving to be less tied to the titlebar (though they are still very tied to it currently).
 
All that said, tossing out a few different ideas in case any feel particularly appropriate or inspire anyone else to come up with a perfect idea:
* `drag-behavior`: `move-window`, `normal`
* `drag-target`: `window`, `self`
* `drags: window`, `self`
* `drags-window`: `true`, `false`
* `window-dragging`: `true`, `false`
* `window-drag`: `true`, `false`

## @kyerebo — 2026-03-10

I’d like to challenge the resolution to rename app-region to window-drag and propose we add this back to the agenda for reconsideration. Historically, `app-region` is the non‑prefixed version of `-webkit-app-region`, often used with and introduced as part of the [Window Controls Overlay](https://developer.mozilla.org/en-US/docs/Web/API/Window_Controls_Overlay_API) feature that shipped ~4 years ago. Renaming at this point would effectively require deprecating both `app-region` and `-webkit-app-region`, which is a pretty significant change for something that is already shipped and documented.

Both properties have non‑trivial real‑world adoption today (`app-region` [~0.22%](https://chromestatus.com/metrics/css/timeline/popularity/702) and `-webkit-app-region` [~0.73%](https://chromestatus.com/metrics/css/timeline/popularity/412) of Chrome page loads), and deprecating them in favor of a new `window-drag` property would cause substantial developer pain and real breakage for existing sites and apps. I also discussed this proposed rename with API owners, who expressed strong dissatisfaction with the amount of churn this would introduce and did not feel the rename was necessary or worth the cost. Given the compatibility impact and existing deployment history, I think we should strongly reconsider this resolution.

## @kyerebo — 2026-03-13

Thanks for the quick response, I get the motivation to make the name more intuitive and align with the web platform design principles around naming. The hesitation isn’t really about whether `window-drag` is a better name in isolation, but about when this change is happening. Standardization (and any renaming) should have happened before unprefixing, which would have allowed us to settle on the right name without compatibility risk. In this case, the naming decision effectively happened when we unprefixed `-webkit-app-region`, and at that point developers started to adopt app-region as the unprefixed surface. From my understanding, that was the moment where a rename would have made the most sense. At this stage, it feels like reopening a decision that users have already acted on.
 
I also don’t think the existence of adoption should be discounted just because the property wasn’t standardized yet. In practice, developers see an unprefixed, shipped feature as “real,” regardless of spec status or documentation quality. A rename now primarily shifts cost onto existing implementers and developers. So, while I understand the desire to avoid spreading a confusing name further, I’m not convinced that a rename at this point actually nets out as a platform improvement given the transition and deprecation burden it introduces.
