We've already resolved how we want to handle running positions + dense-packing with a negative margin-top in https://github.com/w3c/csswg-drafts/issues/12918, but we haven't figured out how we want to handle a negative `margin-bottom` value that is greater than the height of the _following_ item.

In the spec, at the “NOTE” section after step 3 of the Masonry Layout Algorithm: [CSS Grid Layout Module Level 3](https://drafts.csswg.org/css-grid-3/#grid-lanes-layout-algorithm), it appears that a negative `margin-bottom` value should be capped at the size of the item with the negative `margin-bottom` value.  In other words, if an item has `height: 60px; margin-bottom -80px;`, the algorithm would cap `margin-bottom` to `-60px`.

To stay consistent with this, if an item has `height: 100px; margin-bottom: -80px`, and the _following_ item in the track has `height: 60px`, the _following_ item should be placed as though `margin-bottom: 60px` . In other words, the content edge of a placed item should never go above the content edge of a previous item in a track, and running position should never be placed above the content edge of the items in a track. 

If the user wishes to place an item above another visually "on top" of other items, they could place it as an OOF item.

Edit: After viewing the comments, it may actually make the most sense to follow the rule that `margin-bottom` is capped at 0 and cannot push the running position backwards, as opposed to my original idea of aligning the items at the content edge. This  feels more intuitive, as even if there was a large negative `margin-bottom`, the following items would still gather visually further and further below, instead of gathering at the content edge, like they would with my original suggestion.

Edit 2: Based on how the issue resolved, wanted to update the description to reflect this to be clear.  We are capping the EFFECT of the box with negative margins on the running position of the track, but we are NOT capping the effect of the negative margin on the location of the box.  IE, if a box is the first in a track, and has a negative margin of -20px, the box can be placed 20px higher, than the start of the track, but its location in the running position of the track will stay at 0.

## @mhochk — 2025-12-16

Based on the discussion regarding negative top margins, the justification of the resolution seems well captured by the pseudo-quote: "We are not making negative margins inconsistent with positive margins, we are only special casing negative sizes".

And the scope of the special case seems covered well by "Negative margins do affect the size of the box", "running position can only move down".

Following that line of thinking, a negative bottom-margin (or top-margin) should be treated as shrinking the size of the box until it reaches a size of 0. At that point, the negative margin may still impact the visual placement of this item, but the size will be 0 in terms of how it impacts the running position.

That all said, in example 1 above:
Running position starts at 0px
Item 1 gets placed at the running position of 0px - running position stays at 0px because its height is 0px (assuming no gaps)
Item 2 gets placed at the running position of 0px - running position increases to 60px (still assuming no gaps)
Item 3 gets placed at the running position of 60px - (mostly) covering the remaining part of Item 1

## @celestepan — 2026-01-28

@mhochk I like the example you have here; this would make running positions very simple, with each item only really accounting for itself, and it would prevent "future" items from having to worry about `margin-bottom` of the previous item in the track. 

@alisonmaher that's a good point; given that I like the proposal by @mhochk, I think it would make sense if the openings _are_ affected by any negative `margin-bottoms`, but only up until `0px`.  This might be less confusing for users too, since items would be "pushed" to the top, as opposed to gathering at the content of the opening.
