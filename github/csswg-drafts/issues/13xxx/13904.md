https://github.com/web-platform-tests/wpt/pull/58814 introduces a test that passes in chrome by minting the inheritance tree, see https://github.com/web-platform-tests/wpt/pull/58814#issuecomment-4263707301

It basically asserts that non-existing view-transition pseudo-elements should inherit from non-existing ancestor pseudo-elements rather than the originating element.

While this _can_ be implemented for _this specific view transitions case_, it's a really odd special-case (which I think was wrongly implemented in chrome, see the comment above), and is inconsistent with all other pseudo-elements.

I think it's more consistent to say that when CSSOM needs to resolve a style of a non-existent pseudo-element, you just match the rules and inherit from the originating element. That's what every other pseudo-element does.

I think there's no need to change the spec necessarily (but might be worth clarifying / being explicit).

## @vmpstr — 2026-06-30

> That's what every other pseudo-element does.

I don't know a lot of examples of nested pseudo elements. I assume that things like `::before::marker` work the way you describe? It's hard to test, since I don't think `getComputedStyle(target, "::before::marker")` is valid, or I might be holding it wrong.

The "match the rules and inherit from originating element" practice for non-existent pseudo-elements seems like it's meant to mimic the fact that a pseudo element always exists, whether or not it has a box.

For example, from CSSOM:
> In this specification the [::before](https://drafts.csswg.org/selectors-3/#sel-before) and [::after](https://drafts.csswg.org/selectors-3/#sel-after) pseudo-elements are assumed to exist for all elements even if no box is generated for them.

In this interpretation, it seems like `::before::marker` should inherit from `::before` even though `::before` might not have a box.

It was this interpretation that led us to generalize and conclude that for view transitions, where `getComputedStyle(target, "::view-transition-old(foo)")` _is_ valid even though that's nested in other pseudos, it should inherit from other non-box-generating-because-there-is-no-vt pseudos :\

## @emilio — 2026-07-01

> I assume that things like ::before::marker work the way you describe? It's hard to test, since I don't think getComputedStyle(target, "::before::marker") is valid, or I might be holding it wrong.

Yeah those are hard because we don't support the nested pseudo syntax. They're also different, because you're specifying both pseudos, and as you mentioned those are generated content, unlike view transition pseudos.

I think a better example for this would be things like `::details-content` or other element-backed pseudo-elements. If they don't exist then why should we fake the shape of them?

We just _happen_ to know that, right now, due to how view-transitions are defined, they would inherit that way. But that's the same thing as saying that we happen to know that if `::details-content` were to exist, we know it's a `<slot>` element with a particular `style` attribute, or if `::file-selector-button` were to exist it'd be a `<button>`, so it feels a bit of a slippery slope to me on how far you could take it.

## @martrapp — 2026-07-01

A bit of background from my side, as I originally filed `crbug.com/487213151`. The original issue was not about property inheritance, but about Chrome crashing when querying non existent pseudo elements.

The original bug was that Chrome would crash if `getComputedStyle(document.documentElement, "::view-transition-...(...)")` was called for a pseudo element that did not exist within an existing group. For example, `::view-transition-group(xyz)` exists, but `::view-transition-new(xyz)` or `::view-transition-group-children(xyz)` does not.

The purpose of the call was to check whether a pseudo element existed or not (for a debugger) by checking the width value. I would also have been perfectly happy if `getComputedStyle()` had thrown an exception for a non existent pseudo element that I could catch. What I could not handle was the browser crashing outright.

If fixing the bug ended up requiring a complicated solution, that was not my intention. I simply wanted a way to determine whether a pseudo element exists without causing the browser to crash.
