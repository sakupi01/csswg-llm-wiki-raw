When a mixin is applied (`@apply`), the mixins' child rules are emitted in-place. The exception is `@env` (`@local` in the https://github.com/w3c/csswg-drafts/issues/12927 proposal); it is part of the private inner workings of the mixin, and does not leak out:

```css
@mixin --m() {
  @local --color: red;
  color: var(--color);
}
#foo {
  @apply --m();
}
/* gCS(foo)['--color'] => ""               */
/* gCS(foo)[color]     => "rgb(255, 0, 0)" */
```
Had you omitted the `@local` part in the example above, you would instead mix in the `--color:red` declaration into `#foo`, i.e. `gCS(foo)['--color'] => "red"`. There's nothing wrong with that exactly, but [@kizu's post on 13113 ](https://github.com/w3c/csswg-drafts/issues/13113#issuecomment-3563069273) made me wonder if we should actually invert how this works: instead of _everything_ being mixed in by default, _nothing_ is mixed in by default, and you explicitly "return" a result using `@result`:

```css
@mixin --m() {
  --color: red; /* This is a local now. */
  @result {
    color: var(--color);
  }
}
#foo {
  @apply --m();
}
/* gCS(foo)['--color'] => ""               */
/* gCS(foo)[color]     => "rgb(255, 0, 0)" */
```

If you _want_ to mix in `--color`, then obviously you place that inside the `@result` block instead.

Sure, that means trivial mixins (without locals) are now more verbose, but I imagine mixins with even a moderate amount of internal logic would benefit from this:

```css
@mixin --m() {
  @local --a: /* stuff */;
  @local --d: /* stuff */;
  @local --c: /* stuff */;
  @local --d: /* stuff */;
  @media (magnificence > 3.1) {
    @local --d: /* stuff */;
  }
  @local --e: /* stuff */;
  @supports (accent-color:red) {
    @local --e: /* stuff */;
  }
  @local --f: /* collecting all the above stuff */;

  & {
    color: var(--f);
    accent-color: var(--f);
    &::before {
      content: "Hi";
    }
  }
}
```

Would become the following:

```css
@mixin --m() {
  --a: /* stuff */;
  --d: /* stuff */;
  --c: /* stuff */;
  --d: /* stuff */;
  @media (magnificence > 3.1) {
    --d: /* stuff */;
  }
  --e: /* stuff */;
  @supports (accent-color:red) {
    --e: /* stuff */;
  }
  --f: /* collecting all the above stuff */;

  @result {
    & {
      color: var(--f);
      accent-color: var(--f);
      &::before {
        content: "Hi";
      }
    }
  }
}
```

At least to my eyes, that looks cleaner, and it's more obvious what happens.

Benefits, as I see them:

* This mirrors custom functions well: plain `--foo:bar` declarations are also locals within `@function`, and the `result` descriptor is explicitly used to select the result. This makes it easier to learn one feature with experience from the other, which seems valuable.
* Under the `var()` model in [#12927](https://github.com/w3c/csswg-drafts/issues/12927), we automatically avoid mixing in conditional rules that only exist to make `@local`s conditional. (I.e. there is no way currently to use e.g. a `@media` rule internally in the mixin without emitting it.)
* Clearer separation between what is emitted by the mixin and what is not: the moment authors see `@result`, it should hopefully be obvious that stuff _outside_ of the `@result` rule is not part of the result. (See comments from various confused authors in [@kizu's post on 13113 ](https://github.com/w3c/csswg-drafts/issues/13113#issuecomment-3563069273).)

Drawbacks:

* Versus the `@env` model (which I'm seeking to replace with [#12927](https://github.com/w3c/csswg-drafts/issues/12927)): there is no way to interleave your internal mixin logic with the result. In other words, you can't have locals that are local to a specific rule in your result. @kizu's ideas in [#11798](https://github.com/w3c/csswg-drafts/issues/11798) could lead to a way to effectively get this anyway (but more generally).
* It makes tiny mixins more verbose. As soon as you have _one_ local, it's about the same. If we don't like this, we could make the mixin auto-wrap in `@result` if no `@result` rule is explicitly present. But I don't recommend this, since we lose clarity.

Questions:

* Is `@result` allowed multiple times? If yes, last seen rule wins wholesale?
* Is `@result` allowed inside conditionals like `@media`? I suppose it is.
  * Note that `@container` would maintain its current behavior of always evaluating to true soon-after-parsing-time. (Same as e.g. `@keyframes` are effectively unconditional inside `@container`.)
  * We would need to disallow it within `@if` as proposed by [#12909](https://github.com/w3c/csswg-drafts/issues/12909), though, since we don't have any element context at the time `@apply` happens.

Thoughts?

> you could require results to be in a nested selector, so a mixin would typically contain an & {} block and is meaningless unless it contains at least one nested selector.

We could. But it's too implicit and magical in my opinion.

> It does feel like requiring a `@result` or even nested selectors is a bit overkill for the simple cases. The whole point of a mixin is to get some styles out!

I don't think having `@result` there significantly hinders our ability to get some styles out. :-)

Like I said: we _could_ auto-wrap everything in `@result` if it's omitted.

> `@local {}` block

That would work, but an argument against this is that it sort of looks like `--a` is local to the _inside_ of the local block in `@local { --a: /* ... */; }`, when in reality all of the stuff inside `@local` is raised up to the mixin.

> Can you say more about `@container` handling? Is the idea that you could include container queries inside results, but results inside container queries wouldn't really work?

Container queries inside the `@result` block would just work.

Container queries _outside_ of the `@result` block (in a "last `@result` wins wholesale" world) would still work in the sense that the style rules inside the `@result` rule would become CQ-conditional, but the existence of the `@result` rule itself would not be conditional:

```css
@mixin --m() {
  @result { /* Always overwritten */
    color: red;
  }
  @container (/* ? */) {
    @result {
      color: green;
    }
  }
}

div {
  color: blue;
  @apply --m();
}
``` 

If the CQ evaluates to "true", the result is `green`. If it evaluates to "false", the result is `blue`. (Never `red`.)

In your proposed "`@result` rules are combined" world, however, you'd get CQ:true=>green, CQ:false=>red. I think I agree that combining seems better.

## @tabatkins — 2025-11-25

Re: combining the `@result` blocks

I did indeed miss that suggestion. Hm. I guess I'm not *against* it, but you can achieve that exact behavior already by just inverting the order and putting the conditionals inside a single `@result` block:

```css
@mixin --m() {
  @result {
    color: red;
    @container (/* ? */) {
      color: green;
    }
  }
}

div {
  color: blue;
  @apply --m();
}
```

Same result, it's `green` if the CQ is true, and `red` if not.

On the other hand, if you *don't* want combining behavior, the only way to avoid that is to use exhaustive negative checks, so only one of the conditionals is true at a time. This is different from custom functions, where you can write a generic `result` first then override it with `result` in MQs. This would be important if the positive and negative results are doing *different things* using different properties, rather than just overriding each other like in the example above.

Given how close we are to the `@function` syntax model, I lean slightly towards continuing to match it closely and sticking with the "last wins" model, like functions get with their `result`.

## @andruud — 2025-11-26

We can't just move a condition inside a `@result` block and get the same thing, no. For example:

```css
@mixin --m() {
  --param1: 0.5;
  --param2: 0.7;
  --param3: 0.11;
  --param4: 0.13;
  --processed-color: /* Complicated expression involving params */;
  @result {
    & { color: var(--processed-color); }
    &::before { content: "BEFORE"; }
  }
  @media (--actually) {
    --param1: 0.4;
    --param2: 0.6;
    --param3: 0.10;
    --param4: 0.12;
    @result {
      & { color: var(--processed-color); }
      &::after { content: "AFTER"; }
    }
  }
}
```

This either conditionally _replaces_ a "before" with an "after" (under new params), or _adds_ an "after" in addition to the existing "before" (_both_ under new params).

Either way, if you want to move that `@media` inside the `@result` without leaking the params, then you need to duplicate the `@media` outside of the result block.

   1. a single `@result {}`

   4. multiple conditional `@result () {}`.

4. Anything that is valid verbatim wherever the mixin is `@apply`ed,

   2. … except `@contents`.

## @andruud — 2026-01-21

@Crissov In this issue, there is one _main_ question I would like to resolve, and two _follow-up_ questions:

1. Main question: Do we want to mark the _result_ of a mixin explicitly instead of marking _locals_ explicitly?

In my opinion, we do, since explicitly marking locals adds a lot of "@-noise" in anything but trivial examples, it matches how CSS Functions work, and reduces the chance of unintentionally leaking locals onto elements. My proposed resolution is that the result is described by `@result { /* contents */ }`, making stuff outside of the `@result` rule local/internal mixin logic.

2. Follow-up: Does a `@result` rule replace a previous rule, or are they additive?

This depends on whether you think of `@result` as something which sets a single thing (a "result"), or whether you think of it as basically `"@public"`.

It seems reasonable to match `@function` as much as possible, and let `@result` _replace_ the previous rule.

3. Follow-up: Is `@result` implicit if omitted?

We could optionally decide that a mixin which does not contain any `@result` rules implicitly wrap their contents in a `@result` rule, to reduce the noise of smaller mixins.

I'd slightly prefer to make `@result` _required_, but I'm also OK with the alternative.

---

>  body of the @mixin {} at-rule block

_Outside_ of `@result`, you can use whatever is valid in `@function`, _minus_ the `result` descriptor, _plus_ the `@result` rule.

_Inside_ of `@result`, it's whatever we already decided goes in a mixin: anything, minus `@layer` (per resolution elsewhere), minus `@mixin`, plus `@apply`, plus `@contents`?
