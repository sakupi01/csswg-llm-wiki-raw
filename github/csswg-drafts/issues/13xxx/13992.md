The serialization of the newly added [alpha()](https://drafts.csswg.org/css-color-5/#relative-alpha) RCS function is not specified. All the other RCS color functions have serialization rules specified in https://drafts.csswg.org/css-color-5/#serial-relative-color, and alpha() needs this as well.

## @svgeesus — 2026-06-18

Now fixed, [1.3. Serializing Relative Color Functions ](https://drafts.csswg.org/css-color-5/#serial-relative-color) has

> 4. for [alpha()](https://drafts.csswg.org/css-color-5/#funcdef-alpha)

>    the string "alpha(from ", followed by the [serialization of the origin color](https://drafts.csswg.org/css-color-5/#serial-origin-color) using the rules for serializing nested origin colors, followed by a single space, followed by the canonical colorspace ("xyz-d65" for "xyz") in all-lowercase, followed by " / " and the alpha component as specified (using the same rules as the color channel arguments, but clamped) followed by ")".

## @kbhomes — 2026-06-18

I'm a little bit confused by the alpha serialization in the updated spec. In the syntax for `alpha()`, the alpha component is [optional](https://drafts.csswg.org/css-color-5/#funcdef-alpha) so a color like `alpha(from red)` is valid and [defaults to 100%](https://drafts.csswg.org/css-color-4/#typedef-color-alpha-value). Can you explain why `alpha()` doesn't follow the shortest serialization rule here and allows omission of 100% alphas like the other color functions? I can see that if the alpha component is unspecified, `alpha(from <color>)` doesn't really make sense on its own, but at least the serialization would be more consistent?

<!-- comment id=4744858827 author=emilio created=2026-06-18T18:12:37Z url=https://github.com/w3c/csswg-drafts/issues/13992#issuecomment-4744858827 -->
## @emilio — 2026-06-18

@kbhomes In general omitting the `/ 1` on relative colors doesn't round-trip, because omitted alpha defaults to the origin color's alpha, not `1`.

So while it's technically doable to realize that `red` is always opaque, it might not be with something like `currentColor`.

Might be a bit weird if `alpha(from currentcolor / 1)` had to serialize `alpha(from currentcolor / 1)` but `alpha(from red / 1)` serialized as `alpha(from red)`? Again, not _impossible_ but maybe a bit weird?

## @kbhomes — 2026-06-18

@emilio That's a good point, and I'd forgotten about the previous discussion that pointed out that the [alpha defaults to the origin color's](https://drafts.csswg.org/css-color-5/#relative-colors:~:text=If%20the%20alpha%20value%20of%20the%20relative%20color%20is%20omitted%2C%20it%20defaults%20to%20that%20of%20the%20origin%20color%20%28rather%20than%20defaulting%20to%20100%25%2C%20as%20it%20does%20in%20the%20absolute%20syntax%29%2E).

But this would then also apply to the other relative color functions which all currently say:

> followed (if the alpha component is non-unity) by " / " and the alpha component as specified (using the same rules as the color channel arguments, but clamped)

So `oklch(from rgba(255, 0, 0, 0.5) l c h / 1)` is expected to serialize as `oklch(from rgba(255, 0, 0, 0.5) l c h)` which is a different value. Maybe all of these relative color functions should remove the "non-unity" clause from alpha serialization?
