The [anchor node algorithm](https://drafts.csswg.org/css-scroll-anchoring/#anchor-node-selection) is written in terms of nodes and elements, but it seems that UAs implement in terms of layout boxes.

This is visible when style changes cause layout boxes to be destroyed and re-created; browsers don't scroll anchor if the anchor's subtree temporarily becomes `display: none`.

Test case at https://codepen.io/smfr/pen/JoRoKZQ

I think I stumbled upon an issue similar to that, with a bar that a scroll handler moves between the flow and `position: fixed`. The same call also changes its `display` between `block` and `flex`. This is the source of my issue:

https://github.com/kdeldycke/plumage/blob/f4ca11a38e870e843f4d8e3eaa24dd425a70f65e/plumage/static/js/main.js#L16-L28

After each change the handler sees `scrollY` move by about the height of the bar and changes the bar back, so the bar flips between its two states. I see it in Safari 27.0.1 and Chromium 154. With the `position` change alone, both suppress the adjustment.

This is related to #13563, which has the case of a `display` change that makes an absolutely positioned element appear.

I can try to post a minimal reproducing case if you are interested.
