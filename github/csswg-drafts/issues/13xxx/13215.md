> **Updated 2026-07-01.** This proposal has been revised to add supporting data, clarify the current state of OS-level support, and address the fingerprinting concern raised below. The original text is preserved verbatim in the collapsed section at the bottom for transparency. Nothing has been removed in substance.

## Proposal

Add a media feature that exposes a user's declared handedness preference to the web, following the established `prefers-*` pattern:

```css
@media (prefers-handedness: left) {
  /* layout tuned for a left thumb / left hand */
}

@media (prefers-handedness: right) {
  /* layout tuned for a right thumb / right hand */
}
```

Like the rest of the family, this is a **declared preference**, not an inference about the user's body. The user sets it the way they set `prefers-color-scheme`, and it defaults to off (no preference). It is also readable from JavaScript via `window.matchMedia`, so it can drive interaction, not only styling.

## Why this belongs in the `prefers-*` family

Touch is now the majority surface for the web. As of Statcounter's May 2026 figures, mobile is 50.29% of global page views and tablets add another 1.48%, so phones alone have passed desktop. On a touchscreen the hand is the interface: it is the cursor. And the affected population is not marginal: the largest meta-analysis of handedness (Papadatou-Pastou et al. 2020, 200 studies, over 2.3 million people) puts left-handedness at roughly 10%. Yet the platform exposes no signal for which hand is in play. Every other environmental and preference signal a designer needs is available (`prefers-color-scheme`, `prefers-reduced-motion`, `prefers-contrast`, `pointer`, `safe-area-inset-*`), but handedness, which directly determines reach and occlusion on a handheld device, is not.

## Current OS support: fragmented, not exposable

The original version of this issue stated that "many mobile operating systems already have handedness settings." That is misleading and worth correcting, because the real situation is a stronger argument for standardizing, not a weaker one.

What actually exists today is a scatter of partial, non-exposable signals:

- **Samsung One UI** stores a persistent, system-wide left/right *side* preference, but only as a sub-option of one-handed (screen-compression) mode. It is the closest thing to a real handedness bit that ships, yet it is trapped inside a specific mode rather than exposed as a standalone preference.
- **Stock Android / Pixel** one-handed mode (system-level since Android 12) pulls the screen *down* into reach. It has no left/right dimension at all.
- **iOS Reachability** is handedness-neutral: it pulls the top of the screen down vertically, regardless of hand.
- **Keyboard one-handed modes** (iOS long-press globe, Gboard long-press comma/enter) do shift left or right, but they are transient, per-invocation, and scoped to the keyboard. They are not a stored identity the OS could hand to a browser.
- **iPadOS palm rejection** is automatic with no hand setting, so left-handers receive no layout accommodation and routinely trigger controls placed under the resting hand.

The through-line: no mainstream OS exposes a persistent, standalone handedness preference that a browser could read. The signal exists only in fragments, and every layer that needs it (Procreate's right-hand interface, SketchUp for iPad's left-handed mode, note apps tuning palm rejection) reinvents the same toggle. That is the gap this feature fills, and it is the same reason `prefers-color-scheme` lives at the OS level instead of in a hundred separate app settings.

The honest caveat: because no OS exposes this yet, shipping the media feature depends on platforms adding the setting. That is a heavier ask than a pure CSS feature, since it needs device makers, not just browsers. But `prefers-color-scheme` and `prefers-reduced-motion` needed the same OS buy-in and got it (`prefers-color-scheme` went from nothing to shipping across every major browser by early 2020), and handedness is already a tracked property in the stylus world for palm rejection. The incentive exists where the implementation would.

## It is a UX decision, not just flipping the menu

This is not "put the menu on the left." Designers already place navigation on either side freely. Which hand holds the device changes a different thing: what belongs within easy reach versus deliberately out of reach.

- **On a phone, the constraint is reach.** A primary action belongs under the resting thumb; a destructive action is often placed out of easy reach on purpose. Without a handedness signal, that intent silently inverts for left-handers: the action you tucked away becomes the easiest to hit, and you never know it happened.
- **On a tablet, the constraint is occlusion.** The dominant hand and forearm rest over the screen, so a control on the wrong side sits under the very hand covering it.

This is not hypothetical. On Apple's own support forums, left-handed iPad users report hitting the upper-left back button and Close/Done controls constantly because their hand rests where a right-handed layout assumes empty space, and they explicitly ask for a mode that shifts those controls to the other side. That is exactly the placement problem an OS-level handedness signal resolves.

## Interaction, not only layout

Because the feature is readable from `window.matchMedia`, it reaches past static CSS:

```js
const leftHanded = window.matchMedia("(prefers-handedness: left)").matches;
```

This enables inverting a swipe or gesture direction, choosing which edge a swipe action lives on, and deciding where a context menu opens so the hand does not cover it.

## Fingerprinting

This was the first concern raised (@emilio), and it is the serious one. @linc noted in the thread that in isolation this seems no worse than light/dark mode, and was wary of slippery-slope arguments weighing against accessibility features; the scoping below is meant to make that "no worse than `prefers-color-scheme`" case concrete rather than assumed. The proposal is designed to add minimal entropy:

- **Touch-only.** Handedness is meaningless where the pointer is decoupled from grip. The query can resolve to a value only in touch contexts and carry no value on desktop, so it adds no entropy exactly where it would otherwise be useless.
- **Declared, and off by default.** Like the rest of the family, it ships as "no preference" until the user sets it. It is a single low-entropy bit the user controls, not something inferred behind their back. In isolation it is no worse than `prefers-color-scheme`.
- **First-party scoping is available.** The feature can be restricted so the top-level page can read it but embedded third-party scripts cannot, closing the cross-site correlation path without a permission prompt or opt-out checkbox.

The combination (a declared, default-off, touch-only, first-party bit) keeps the accessibility benefit while bounding the tracking surface.

## Summary

A single declared boolean, cheap to define and honor, that serves a substantial and consistently underserved share of touch users. The main cost is platform buy-in for the setting itself, which is the same cost the rest of the `prefers-*` family already paid.

<summary>Original proposal (2025-12-13), preserved verbatim</summary>

I propose adding a new media query to detect user handedness preference, similar to existing `prefers-*` queries like `prefers-reduced-motion` and `prefers-color-scheme`.

**Proposed syntax:**

```css
@media (prefers-handedness: left) {
  /* Styles for left-handed users */
}

@media (prefers-handedness: right) {
  /* Styles for right-handed users */
}
```

**Use case:**
Handedness significantly affects UI interaction, particularly on mobile devices where touch targets and navigation controls should ideally be positioned for comfortable thumb reach. Approximately 10% of the population is left-handed, yet most mobile UIs default to right-hand optimization.

**Practical applications:**

- Positioning floating action buttons and navigation controls on the appropriate side
- Mirroring toolbar layouts for thumb accessibility
- Adapting swipe gesture directions
- Optimizing one-handed mobile interface layouts

**Current situation:**
Developers currently have no way to detect handedness preferences without building custom in-app settings. This forces users to adapt to right-handed defaults or requires each app to implement individual solutions.

**Precedent:**
This follows the established pattern of existing accessibility and preference media queries (`prefers-reduced-motion`, `prefers-contrast`, `prefers-color-scheme`, etc.) that expose OS-level user preferences to web content.

**OS integration:**
Many mobile operating systems already have handedness settings (particularly for keyboard placement). This media query would expose that existing preference to web applications.

This seems like a straightforward accessibility improvement that would benefit a significant portion of users with minimal implementation burden.

</details>
