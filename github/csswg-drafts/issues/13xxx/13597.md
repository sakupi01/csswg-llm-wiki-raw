## @svgeesus — 2026-03-05

> 1. What should happen if the two headroom values are the same? Should the function be invalid?

Fair question and I don't know. I think I would prefer a defined behavior when they are the same, rather than an error or failure to parse.



> 2\. In `color-hdr(0 xyz-d65 1.2 0 0, xyz-d65 1.2 0 0)`, are they the same value?

That is invalid syntax because neither of the parameters is a color value and because the headroom follows, rather than preceding, the color to which it applies. Do you mean

```css
color-hdr(
  color(xyz-d65 1.2 0 0) 0, 
  color(xyz-d65 1.2 0 0) 0
)
```

or 

```css
color-hdr(
  color(xyz-d65 1.2 0 0) 0, 
  color(xyz-d65 1.2 0 0)
)
```
(which would be invalid)?

## @svgeesus — 2026-03-05

I just realized that identical hdr headroom values, if allowed to parse, might be a security and privacy issue. Consider:

```css
.swatch {
    background-color: red; 
}
.swatch {
    background-color: color-hdr(green 2, green 2);
}
```
Now I can tell if your hdr headroom is exactly 2 stops. Or can I, because the used value is not exposed to script?

<!-- comment id=4007734514 author=svgeesus created=2026-03-05T20:56:12Z url=https://github.com/w3c/csswg-drafts/issues/13597#issuecomment-4007734514 -->
## @svgeesus — 2026-03-05

Looking at this more, I think optional headroom values are a mis-feature: they give a very small improvement to **terseness** (3 characters typically, ie avoids typing `, 2`) at the expense of reduced **readability** and increased **spec complexity**:

-  define the default value, if one is omitted
- define what happens if _both_ headroom values are omitted (I guess that is covered by "must not be the same")

I think making them mandatory rather than optional would be an improvement. @ccameron-chromium ?
