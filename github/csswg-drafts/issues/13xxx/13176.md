In #12732 we resolved that `position-visibility: anchors-visible` used the same mechanics as `IntersectionObserver`, as if you used `IntersectionObserver` with the abspos cb as root.

That all seems fine, _however_ when trying to implement it to the letter there are a few tests that highlight somewhat diverging behavior and need more clarification.

 * Even the basic test (https://wpt.fyi/results/css/css-anchor-position/position-visibility-anchors-visible.html) would not pass with the `.isIntersecting` definition from `IntersectionObserver` because that uses edge-inclusive intersection (https://w3c.github.io/IntersectionObserver/#update-intersection-observations-algo), so when you're right at the edge you'd claim the anchor is visible. This can probably be clarified in the anchor positioning spec by additionally requiring a non-zero `intersectionArea`.

 * When both anchor and anchored are in the same containing-block (siblings) apparently `anchors-visible` is not intended to apply. [`position-visibility-anchors-visible-both-position-fixed.html`](https://wpt.fyi/results/css/css-anchor-position/position-visibility-anchors-visible-both-position-fixed.html) tests it. I'm not sure this is warranted, and I think this should probably change.

## @tabatkins — 2025-12-22

Agreed about requiring a non-zero intersection area *when* the anchor's own area is non-zero. (If you have a zero-width/height anchor, it's okay for it to be considered visible when it's on the edge.)

For the "both anchor and anchorpos have the same CB" case, yes, that's intended behavior. anchors-visible is meant to avoid the situation where your anchor scrolls away in a scroller below your CB; you don't want to hang out in space "attached" to nothing visible. If you both have the same CB, then any "scrolling away" will hide both you and the anchor equally, and there's no need to try and hide you just because your anchor has moved out of the scrollport.

## @dshin-moz — 2026-04-02

(Relating to "which rect to use" discussion that happened during above discussion)

@tabatkins FWIW, [spec](https://drafts.csswg.org/css-anchor-position-1/#clipped-by-intervening-boxes) does explicitly use ink overflow rect:

> An anchor box anchor is clipped by intervening boxes relative to a positioned box abspos relying on it if anchor’s [ink overflow rectangle](https://drafts.csswg.org/css-overflow-3/#ink-overflow-rectangle) is fully clipped by a box which is an ancestor of anchor but a descendant of abspos’s containing block.

I think this is to handle fragmented anchor boxes. IIRC we made this change along with multicol-related position-visibility changes.
