The single-variant `border-shape` uses one of the border edges to select a border color and width.
This is usually OK, but in some cases it's counterintuitive, especially given that backgrounds are not painted outside the border box.

For example, take this shape from @una:

<img width="294" height="283" alt="Image" src="https://github.com/user-attachments/assets/016534d0-c2ce-4c38-8035-0566f2639811" />

The stroke width here is `2px`, but the "border" is closer to `20px`.
To make this shape work nicely with the box model and its internal content, currently the author needs to add something like a `20px` padding for it to paint correctly. But this is not what `padding` is for - it means that, for example, positioned elements would ignore the padding and would start at the `2,2` coordinate.

Proposal:

Allow `border-shape-stroke` and `border-shape-stroke-width` properties that override the defaults for the single-shape variant of `border-shape`, with a `from-border` default.

```
border-shape-stroke-color: from-border | <<color>>;
border-shape-stroke-width: from-border | <<line-width>>;
```

## @SebastianZ — 2026-07-07

If I understand correctly, the main intent here is to decouple the border stroke width from the border box width, right?

So the example above could be expressed as:

```css
border: 20px solid;
border-shape: var(--cloudy-shape);
border-shape-stroke-color: red;
border-shape-stroke-width: 2px;
```

Meaning, when `border-shape-stroke-color` is set, it overwrites the color set by the related `border-*-color` property.
And you mixed it up a little, but I think you also want to introduce a shorthand called `border-shape-stroke`.

Are those assumptions correct?

If so, I have two alternative approaches to this:

1. Introduce a `border-area-width` or `border-box-width` property with `from-border-width | <line-width>{1,4}` as syntax that controls the border box size with `from-border-width` as initial value. The `border-*-width` properties then only define the rendering width of the border.

So the CSS for the example above would then look like this:

```css
border-area-width: 20px;
border: 2px solid red;
border-shape: var(--cloudy-shape);
```

2. Just call it `border-stroke` (and `border-stroke-width` and `border-stroke-color`, respectively) and let it also apply without the border shape. E.g. a `border: 20px solid; border-stroke: 2px red;` would create a 20px wide border box but only draw a 2px red stroke into it.

The CSS for the example above could then look like this:

```css
border: 20px solid;
border-shape: var(--cloudy-shape);
border-stroke: 2px red;
```

Sebastian

## @LeaVerou — 2026-07-08

The fact that these issues are coming up makes me question whether `border-shape` was the right primitive in the first place. This has only shipped in one engine, there is still time to completely redesign it if we want.

The issue @noamr brought up above makes me wonder if this should be about borders at all. Perhaps the right primitive is `element-shape`? OTOH there is precedent with `border-radius`. It's considered one of the mistakes in the design of the language, but at this point, there's also a consistency argument that can be made.
Another idea is `element-stroke`, but then we need to define how it interacts with borders, so maybe not.

But also, I'd question whether `padding` is actually such a bad idea for this. Think of `background-clip` and `background-origin`. What box should they follow?

The real problem is that we only have one padding "slot", and this couples the padding to the border styling, they can no longer be set independently. So what if we introduce a new property that works additively, either on the border-box or the padding box? E.g. `border-padding`, `padding-offset` etc. This can be implemented separately from `border-shape` and I can think of use cases that don't involve it (e.g. with large `border-radius`, certain `corner-shape`s, `border-image` etc)

## @tabatkins — 2026-07-08

Any solution which only addresses the area the border takes up is incomplete, I think. As I said in the call, I think *all* the stroke properties are going to end up useful here - miterlimit to control sharp corners, linecap and linejoin for strokes that aren't a continuous loop, even dasharray and dashoffset for dashed border shapes, and for techniques like the ["self-drawing SVG"](https://codyhouse.co/nuggets/self-drawing-svg-animation). This is big part of why I support just leaning on the stroke stuff, rather than trying to come up with something novel *just* for the size stuff.

-----

@LeaVerou 

Given that the use-case is definitely *replacing* the border with the specified path, I think continuing to tie the naming to `border-*` is a reasonable move. Like, in theory we could rejigger it to instead be `border-stroke` (and `border-stroke-*`), and then move the two-path version to a `border-fill` set of properties, and define a priority list for how they win over each other (presumably, `fill` > `stroke` > normal border), but that'd be the limit, I think. But I'm not sure that's needed.

## @tabatkins — 2026-07-08

> One interesting thing we could do as an alternative here is treat this stroke as the second "shape". Kind of like how ray is a special shape for offset-path.

That's possible, but it's much worse from a cascade perspective. It's hard to animate just one aspect of the stroke, for example; you'd have to respecify the entire value to change just one bit.

Tho, about "apply only in single-path" - do we want to allow for the two-path version to be stroked as well? I think that makes sense, personally; you're defining a fillable shape, just in two pieces rather than one like SVG usually does. I suspect there are reasonable effects that could be done with that. If so, then the border-shape-stroke-* properties would apply in *both* cases. We'd still be using "one path or two" in border-shape to define which model we were using (a single stroked path, or a filled/stroked shape).
