The single-variant `border-shape` uses one of the border edges to select a border color and width.
This is usually OK, but in some cases it's counterintuitive, especially given that backgrounds are not painted outside the border box.

For example, take this shape from @una:

<img width="294" height="283" alt="Image" src="https://github.com/user-attachments/assets/016534d0-c2ce-4c38-8035-0566f2639811" />

The stroke width here is `2px`, but the "border" is closer to `20px`.
To make this shape work nicely with the box model and its internal content, currently the author needs to add something like a `20px` padding for it to paint correctly. But this is not what `padding` is for - it means that, for example, positioned elements would ignore the padding and would start at the `2,2` coordinate.

Proposal:

Allow `border-shape-stroke` and `border-shape-stroke-width` properties that override the defaults for the single-shape variant of `border-shape`, with a `from-border` default.

```
border-shape-stroke-color: from-border | <<color>>;
border-shape-stroke-width: from-border | <<line-width>>;
```

## @SebastianZ — 2026-07-07

If I understand correctly, the main intent here is to decouple the border stroke width from the border box width, right?

So the example above could be expressed as:

```css
border: 20px solid;
border-shape: var(--cloudy-shape);
border-shape-stroke-color: red;
border-shape-stroke-width: 2px;
```

Meaning, when `border-shape-stroke-color` is set, it overwrites the color set by the related `border-*-color` property.
And you mixed it up a little, but I think you also want to introduce a shorthand called `border-shape-stroke`.

Are those assumptions correct?

If so, I have two alternative approaches to this:

1. Introduce a `border-area-width` or `border-box-width` property with `from-border-width | <line-width>{1,4}` as syntax that controls the border box size with `from-border-width` as initial value. The `border-*-width` properties then only define the rendering width of the border.

So the CSS for the example above would then look like this:

```css
border-area-width: 20px;
border: 2px solid red;
border-shape: var(--cloudy-shape);
```

2. Just call it `border-stroke` (and `border-stroke-width` and `border-stroke-color`, respectively) and let it also apply without the border shape. E.g. a `border: 20px solid; border-stroke: 2px red;` would create a 20px wide border box but only draw a 2px red stroke into it.

The CSS for the example above could then look like this:

```css
border: 20px solid;
border-shape: var(--cloudy-shape);
border-stroke: 2px red;
```

Sebastian

To @noamr’s point that people are responding well to this feature, I’m in full support of the feature itself! I think it's *tremendously* useful and long overdue. That’s why I think it matters to get it right. We want something that will work predictably for people's use cases, and will not be a minefield of footguns. We cannot afford another `border-image`.

One thing I think we have consensus for is that the 0 width case should still render the shape, like it does for `border-radius`. I wonder if this was a bug that was fixed because the shape does seem to render for me with `border-width: 0px`, albeit with some artifacts:

On the OP question. I’m thinking the amount of extra space **depends on `border-width`** as well, so perhaps it should be expressible relative to that rather than in absolute values only which means they need to be set together or styling breaks. Especially since `border-width` is often set externally. <img width="447" height="313" alt="Image" src="https://github.com/user-attachments/assets/ecc0dced-7ebe-4952-beae-96f752d43519" />

We don't need strokes to express the concepts these properties control. The mental model should not be "`border-shape` overrides some of the border stuff". Properties that cancel other properties increase cognitive load. That's a source of complaints for `border-image`.
Instead, the mental model should be (as much as possible) "`border-shape` defaults to `inset(0px)` but you can customize it". Then everything falls in place naturally. The properties themselves make perfect sense as `border-join`, `border-linecap`, they just apply to the default rectangle if `border-shape` has not been customized!
I'd fold `miterlimit` into the `linejoin` property. A separate property that only works when the value of another property is set to `miter` is not great design, we could instead have a `miter(<number>)` function. I don't think they ever need to cascade separately.

Alternatively, we could lean fully into strokes, with `element-shape` for the shape and `element-stroke` for the actual stroke, then define the interaction with borders. I’m not suggesting we do this, I’m saying it _might_ be the lesser of two evils if we can't figure out a coherent model for border shapes.

IMO either we should fully lean in to either borders as a mental model OR strokes. I’m worried we're creating a confused hybrid that will be internally inconsistent, and where properties that conceptually _should_ work (i.e. they have meaning), don’t for reasons that make no sense to users.

For example, this is what happens in the OP demo if I set `border-width: 1px 3px 5px 10px;  border-color: gold red blue lime;`

<img width="298" height="281" alt="Image" src="https://github.com/user-attachments/assets/c7fe45b3-2375-4059-bc3e-040a16909737" />

It took me a lot of experimentation to even understand what's happening: it’s using the min of all widths, but still reserves space around the box for the actual border box, which would explain why `border-width: 0px 3px 5px 10px;` makes the border disappear.

Similarly, setting `border-style: dashed` has no effect, but conceptually that makes no sense, at least in the stroke case that could be very well defined (in the two shape case indeed there is no reasonable expectation).

I just looked at the spec: interaction with `border-style` and `border-width` is *entirely* undefined. We should fix this 😕

Yeah, I don't think we need anything complicated linking 'border-width' and the stroke width. If they're different, you'll be setting them next to each other anyway; we don't go to great lengths to let you set margins, borders, or paddings relative to each other either. In the worst case, you can set one value in a variable and calc() it for the other, but that's likely rarely necessary.

> We don't need strokes to express the concepts these properties control. The mental model should not be "border-shape overrides some of the border stuff". Properties that cancel other properties increase cognitive load. That's a source of complaints for border-image.

I don't think *this* is the source of complaints for border-image. border-image *does* use the relevant properties that it can from 'border' (only border-width is relevant, for defining the border box size), it's just that it's *complicated* and you have to do some extra stuff to achieve all the useful cases, like visually overflowing the border box area.

The same applies here. When stroking, 'border-width' is relevant for (a) defining the size of the border box geometrically, and (b) providing the default stroke-width (half the border-width), and then 'border-color' defines the default stroke color.

'border-style' is impossible to be relevant for border-image. Only *some* values are potentially usable for a stroked border-shape (like dash), but the SVG stroking model gives us *more* power than that, and we should lean on that instead of confusingly allowing only a subset of border-styles to apply. Like border-image, none of the border-styles can apply to the two-path border-shape.

We just have several distinct ways to draw a border, and that's okay. They should align as much as *possible*, but no more. We can reuse border-width across all the variants, and border-color across most, but border-style, border-radius, and corner-shape are all very specific to the "just a rectangle" variant from CSS1.
