The current draft converts `device-cmyk()` colors to Lab, or to sRGB with the naive algorithm, before they are used in a gradient (and similar contexts):

https://github.com/w3c/csswg-drafts/blob/760f28edc52d7c2729d1b78b6f220610fe5443d4/css-color-5/Overview.bs#L2699-L2721

Interpolation then takes place in Oklab by default. The ink quantities of the endpoints are gone at that point, so a gradient between two CMYK colors cannot stay in CMYK.

For example, a gradient from C0 to C100:

```css
div {
  background: linear-gradient(device-cmyk(0 0 0 0), device-cmyk(1 0 0 0));
}
```

A straightforward reading expects this to interpolate in ink quantities, like the equivalent PDF shading:

```
5 0 obj
<< /ShadingType 2 /ColorSpace /DeviceCMYK
   /Coords [50 450 450 450] /Domain [0 1]
   /Function 6 0 R /Extend [true true] >>
endobj

6 0 obj
<< /FunctionType 2 /Domain [0 1]
   /C0 [0 0 0 0] /C1 [1 0 0 0] /N 1 >>
endobj
```

Per the current draft, without an `@color-profile device-cmyk` rule, the endpoints become `color(srgb 1 1 1)` and `color(srgb 0 1 1)`. Separating the resulting gradient back to CMYK produces non-zero M, Y, and K along the way, which is not what an author would expect from `device-cmyk(0 0 0 0)` → `device-cmyk(1 0 0 0)`. With an `@color-profile device-cmyk` rule the endpoints become `lab()` values, and the ink quantities are still gone.

In practice, Antenna House Formatter V7.5 (MR7) and Prince 17 both output a gradient with `device-cmyk()` at both ends as a linear interpolation of ink quantities (<https://github.com/w3c/csswg-drafts/issues/13934#issuecomment-6759091033>).

## Proposal

css-color-4 already has an exception to the default interpolation color space: legacy sRGB color formats interpolate in sRGB.

https://github.com/w3c/csswg-drafts/blob/760f28edc52d7c2729d1b78b6f220610fe5443d4/css-color-4/Overview.bs#L5418-L5433

I propose a similar exception for `device-cmyk()`, with the wording suggested in <https://github.com/w3c/csswg-drafts/issues/13934#issuecomment-6762782886>:

> When all the colors being interpolated are `device-cmyk()`, the user agent may interpolate in `device-cmyk()`.

Interpolating in `device-cmyk()` means linear interpolation of each of the four component values. Each interpolated color is itself a `device-cmyk()` color, and is rendered or converted as described in [Resolving `device-cmyk` Values](https://drafts.csswg.org/css-color-5/#resolving-device-cmyk-values).

An explicitly specified interpolation color space, as in `linear-gradient(in oklab, ...)`, still takes precedence, as it does over the legacy sRGB exception.

The sentence "such colors do not have a colorimetric interpretation, and thus cannot be used in gradients, compositing, blending and so on" would need to change along with this. The same comment suggests a replacement.

## @u1f992 — 2026-05-16

On reflection, `<color-interpolation-method>` as currently designed presupposes that any absolute color can be (lossily) converted into the target color space. A more fundamental framing would be a method usable only when every endpoint already shares the same color space (setting cylindrical polar spaces aside for now). For example, `in componentwise` would interpolate each component in that shared space directly. This is overkill if `device-cmyk()` is the only motivation, but I want to flag it as an alternative direction.

## @faceless2 — 2026-11-10

I would be very surprised if _any_ print formatters followed the spec text here, but it's just a draft of course.

The issue isn't that `device-cmyk` can't be used in gradients, it's that that the colorimetry at any point on the gradient may vary depending on the device. All `device-cmyk` means is "an appropriate CMYK profile". Any print formatter could pick one, use that colorimetry to interpolate in OkLab and then convert back to CMYK at the end. The good news is that none of that is incompatible with the naive linear gradient from your PDF example above.

However in practical terms there's no need to jump through those hoops when interpolating between `device-cmyk(0 0 0 0)` and `device-cmyk(0 0 0 1)`, so I think your suggestion 

>  "when all the colors being interpolated are device-cmyk(), and the output device is CMYK-capable, the user agent MAY interpolate in ink quantities"?

is a good idea - although I'd probably simplify it to "when all the colors being interpolated are device-cmyk(), the user-agent may interpolate in device-cmyk()". We already have the exception that legacy RGB colors must interpolate in sRGB, so this isn't a big leap.


The lack of colorimetry in `device-cmyk` would be an issue for blending or composition, but again, all it means is the rendering device is free to pick an arbitrary CMYK profile for colorimetric values - so it isn't really the problem it appears to be. All it means is that on a different device you might get different results.

> Typically, print-based applications will actually store the used colors as CMYK, and send them to the printer in that form.  However, such colors do not have a colorimetric interpretation,  and thus cannot be used in gradients, compositing, blending and so on.
 >
 > As such, Device CMYK colors must be converted to an equivalent color. This is not trivial, like the conversion from HSL or HWB to RGB;  the precise conversion depends on the precise characteristics of the output device.

That all feels too scary. I'd go with something like

> Typically, print-based applications will actually store the used colors as CMYK, and send them to the printer in that form. Where a colorimetric interpretation of colors is required for operations such as compositing or blending, the precise conversion depends on the characteristics of the output device.
