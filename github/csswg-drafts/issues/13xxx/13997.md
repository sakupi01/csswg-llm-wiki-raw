We frequently have bugs filed such as https://issues.chromium.org/516829766 where the rendering of a backdrop-filter or filter blur incurs a significant performance penalty. I believe css blurs are so expensive because they are calculated as a gaussian blur, https://drafts.csswg.org/filter-effects-1/#feGaussianBlurElement. In chrome, when you animate this blur we compile a new shader per blur radii visited in the animation which is why in https://issues.chromium.org/40831523 I suggested we may be able to produce imperfect intermediate frames while animating.

However, even if we can make it slightly better, I think in many use cases where developers apply blurs they do not care about the exact blur quality. I propose that we have some way for using simpler cheaper blurs both for static blurs and for animating blurs. E.g.

```css
filter-rendering: smooth | high-quality
```

The name, filter-rendering, and values smooth | high-quality, were chosen to align with [image-rendering](https://www.w3.org/TR/css-images-3/#the-image-rendering) as it has similar implications. This would allow developers to opt into making their blurs significantly less expensive to render.

E.g. a UA could choose to implement smooth filtering by using a low resolution rendering and using simple gpu scaling to smooth between those sampled pixels.

## @flackr — 2026-07-28

Backdrop-filter is a very important use case given the prevalance of glass effects. I also expect this to be used in blur extensions like the linear-blur #13285. I'm open to defining it in the function parameters instead though.

> I slopped around a bit. I'm worried about the quality and animatability of "low resolution rendering and using simple gpu scaling", but maybe I'm missing a technique.

One thing to note, is that in order to sample the outside pixels the same way that blur does you need to include them in your downsampled image. Also, in order to avoid jumps as the blur radius moves between subsequent downsamplings we would make this smooth by cross-fading between the two. I believe this is the same way that games ensure that switching between mipmapped textures doesn't result in popping. Another option is to downsample partially, and apply a blur kernel over the downsampled result to get a combination of the two methods.

That said, my hope is to get agreement that we want to pursue the ability to have cheaper blurs even if we don't agree yet on which method to use.
