We've been hacking our way around the lack of official multiple border options for years with `box-shadows`, `outline`, `drop-shadow`.  It seems like it's long past time to just allow multiple borders in a straight forward way.

problems with the current options:

- Hacking borders with `outline` on elements with focus messes up accessibility. Causing devs to need to replace that functionality. Often in reality this does not happen.
 
- Hacking borders with `box-shadow` leads to uneven "borders" on non 100% zoomed OS.

- Hacking borders with `drop-shadow` usually requires a large number of shadow because it's missing a spread option. Also has the same issue with non 100% zoomed OS.

Proposing to look something like this:

```css
border: solid #000 1px, dashed red 3px, solid #000 1px;

border: solid var(--background-color) 3px, solid #000 2px;
```

## Background on how we ended up with `stripes()`

I do agree that at first listifying seems like a better solution, but if you dig a little deeper, it causes a bunch of weird side effects. See https://github.com/w3c/csswg-drafts/issues/2532 for a discussion.

That said, I don't much like `stripes()` (even though I proposed it 😂). I think it's a very weird and overcomplex solution to the rather simple use cases it's trying to solve. It would be _much_ better if we could come up with a solution that is geared around listification of border properties.

The main problem is that we want this:

```css
border-width: 10px;
border-color: red, black, white;
```

…to specify a 10px border, not a 30px border.
But on the other hand, this:

```css
border: 10px solid red, 10px solid black, 10px solid white;
```

…should totally specify a 30px border!

There is also the issue that listification combines very oddly with the multi-side syntax:

```css
border-color: skyblue orange yellowgreen indianred, black yellow
```

![image](https://user-images.githubusercontent.com/175836/38607092-1198f110-3d78-11e8-9982-ad39e0faf6d4.png)

This is a completely nonsensical way to specify border colors. People think of all colors for a side as a group, they don't group colors by whether they are innermost or outermost.
Though different colors for each side are pretty rare, so I’m not sure this is a concern we should design the syntax around, and definitely not just cause for complicating the simple case.

## Strawman for making listification work

_(Edited substantively on Nov 22 and editorially on Dec 27)_

The gist of the idea is _"How can we design a syntax that matches author expectations in as many cases as possible?"_

For most authors (86-90% it [turns](https://x.com/LeaVerou/status/1985123158370680869) [out](https://front-end.social/@leaverou/115482600983968371)) a listified **shorthand** is very clear, e.g. `border: 1px solid white, 1px solid black` = two borders, one white and one black, each being `1px` thick. It doesn't get clearer than that. 

The problems arise when you set borders via the longhands. 
- We don't want `border-width: 1px` to result in a `3px` border because you happen to have three colors. 
- We don't want to turn `border-color` into a layout-affecting property
- We want to preserve the ability to use `border-width` to set the total border width (both because this is a common use case, and also for compat). But we also want to be able to set the individual border widths. And neither of the two should require mental math to compute it from the other.

What could be the solution?
💡 **What if we introduce a **separate** property for the relative widths?**. 
We’ll call it `border-width-relative` for now, let's bikeshed later.
**Then we can listify _that_ property, and keep `border-width` as a single value property, specifying the total width.**

The initial value of `border-width` becomes `auto` which resolves to the sum of all borders specified via `border-width-relative`. Essentially, this becomes a bit like intrinsic and extrinsic sizing: either you size individual borders and have the total width computed from them, or you specify your total border and have individual borders be computed from that total. And with `fr` units you can even define how this computation happens!

Then, a listified `border` shorthand can work as people expect: multiple borders just set `border-width-relative`.
The `border` overall shorthand sets the relative property, but setting `border-width` separately continues to work as expected. 

Another way to think about it: we separate the length and color arguments from `stripes()` into separate properties that can be set separately and cascade separately. 

Note that `border-width` is intentionally _not_ a shorthand that includes `border-width-relative`: we want setting `border-width: 1px` to work as expected as it often cascades separately, and to set the border to a `1px` border, not a _number of colors_ &times; `1px` border.

This seems to let us **have our cake and eat it too**:
- ✅ Listification on par with how other CSS properties work
- ✅ `border-width` that is backwards compatible and continues to be a guarantee for the total width
- ✅ Can set **either** total width **or** individual widths without mental math in either case
- ✅ Keeps border width, style, and color orthogonal (or at least as orthogonal as they previously were)
- ✅ Preserves `border-color` as a non-layout-affecting property.
- ✅ Actually useful for border-styles != `solid` (whereas `stripes()` just produces [extremely weird results](https://drafts.csswg.org/css-borders/images/multicolor-border-dotted.png))
- ✅ Allows widths, colors, and styles to cascade separately, even when set by different sources

Downsides:
- ❌ Not great when specifying different colors/styles/widths per side.
- That’s ...about it, I think?

### Detailed design

_(I’m going to describe the overall border properties below, but this applies to the side versions)_

All `border` properties are listified _except_ `border-width`/`border-*-width`.
```css
border-color = <color>#
border-style = <line-style>#
```

New `border-width-relative` (name TBB) property to specify absolute AND relative proportions:

- Value: `[<flex> | <line-width>]{1, 4}#`
- Initial: `medium`

`border-width` changes as follows:

- Value: `<line-width> | auto`
- Initial: `auto`

#### Border width resolution

The computed value of `border-width: auto` is computed as the sum of all `<line-width>` values (ignoring all `<flex>` values). This is resolved at computed value time, so that the change doesn't break `getComputedStyle()` reads.

The used value of `border-width-relative` is computed as follows:
- When `border-width` is `auto` all `<flex>` values compute to `0px` and all `<line-width>` values follow current resolution rules
- When `border-width` is not `auto`, widths are computed as follows: 
	- Sum all `<line-width>` values,
	- If the sum is smaller than `border-width` distribute any remaining lengths according to the `<flex>` values
	- If the sum is larger than `border-width`, scale down the values proportionally. This ensures that setting `border-width` **guarantees** certain box model dimensions.

#### Naming of the new property

Note that this needs to work well for all the `border-*-width` properties as well, not just `border-width`

- `border-width-relative` / `border-left-width-relative`
- `border-widths` / `border-left-widths`
- `border-width-separate` / `border-left-width-separate`
- ???

### Examples

#### Driving use case: white and black

The driving use case for `stripes()` (a black and a white `1px` borders) would be either of these:

```css
border: 1px solid white, 1px solid black;
```

```css
border: white, black;
border-style: solid;
border-width: 2px;
```

```css
border: white, black;
border-style: solid;
border-width-relative: 1px;
```



#### Generalization of `border-style: double` 

<img width="226" height="127" alt="Image" src="https://github.com/user-attachments/assets/17542197-d27a-41b6-be8b-370ca8e52575" />



Border that is a generalization of `double`, with a custom color between two `1px` borders

```css
border: blue, gold, blue;
border-style: solid;
border-width-relative: 1px max(2px, 1fr) 1px;
/* border-width: auto; */ 
```

Would produce a border that is of total width of `4px` (with no `border-width`, flex units would collapse to 0) that consists of two `1px` blue borders, and `2px` or more gold.

Setting `border-width: 7px` increases the gold "gap", since now `1fr` resolves to `5px`:

<img width="230" height="131" alt="Image" src="https://github.com/user-attachments/assets/d636c1b6-f6b0-40cf-be5a-a7bd33489d54" />

```css
border: blue, gold, blue;
border-style: solid;
border-width-relative: 1px max(2px, 1fr) 1px;
border-width: 7px;
```

#### Rainbow border

Nobody needs this, but since it was mentioned:

<img width="225" height="124" alt="Image" src="https://github.com/user-attachments/assets/b392dc64-d49a-4836-b559-dacf4af79aed" />

```css
border: solid; /* or border-style: solid; */
border-color: red, yellow, lime, aqua, blue, purple, fuchsia;
border-width-relative: 1px;
/* border-width: auto; */ 
```

#### Complex example: Multiple border styles

Yes, this allows multiple border styles. While this can look awful, there are also valid use cases for it, e.g. a stitched effect:

<img width="198" height="114" alt="Image" src="https://github.com/user-attachments/assets/068a25de-8ac7-442b-b7f5-be16d1325261" />

This is an **intentionally complex example** involving multiple border-styles and even different colors per side (for the 3D effect).

Current [CSS for it may](https://dabblet.com/gist/b9875187aad760afcdae73ab51edf151) look like this (and needs 2 containers):
```css
.tag {
	--background: hsl(220 20 90);
	--stitch-light: #0008;
	--stitch-dark: white;
	--border-color: hsl(220 20 30);

	display: inline-block;
	border: 1.5px dashed white;
	border-color: var(--stitch-dark);
	border-right-color: var(--stitch-light);
	border-bottom-color: var(--stitch-light);
	background: var(--background);
	box-shadow: 0 0 0 .3em var(--background), 0 0 0 calc(.3em + 1px) var(--border-color);
	border-radius: .2em;

	> div { /* Need 2 elements */
		padding: .35em .5em;
		border: inherit;
		border-color: var(--stitch-light);
		border-right-color: var(--stitch-dark);
		border-bottom-color: var(--stitch-dark);
		border-radius: .2em;
	}
}
```

With `stripes()`: **not possible at all**.

With this proposal:

```css
.tag {
	--background: hsl(220 20 90);
	--stitch-light: #0008;
	--stitch-dark: white;
	--border-color: hsl(220 20 30);

	display: inline-block;
	padding: .35em .5em;
	border: 1.5px dashed, 1.5px dashed, .3em solid,  1px solid;
	border-top-color: var(--stitch-dark), var(--stitch-light), transparent,  var(--border-color);
	border-right-color: var(--stitch-light), var(--stitch-dark), transparent,  var(--border-color);
	border-bottom-color: var(--stitch-light), var(--stitch-dark), transparent, var(--border-color);
	border-left-color: var(--stitch-dark), var(--stitch-light), transparent,  var(--border-color);
	background: var(--background);
	border-radius: .5em; /* actual value! */
}
```

Yes, there is some repetition, but it is inherent in listification. If we want to improve ergonomics further we could later introduce a `sides()` function for the shorthand which helps express author intent better not just for multiple borders, but even singular ones:

```css
.tag {
	--background: hsl(220 20 90);
	--stitch-light: #0008;
	--stitch-dark: white;
	--border-color: hsl(220 20 30);

	display: inline-block;
	padding: .35em .5em;
	border: 
		1.5px dashed sides(var(--stitch-dark), right bottom var(--stitch-light)), 
		1.5px dashed sides(var(--stitch-light), right bottom var(--stitch-dark)), .
		3em solid transparent,  
		1px solid var(--border-color);
	background: var(--background);
	border-radius: .5em; /* actual value! */
}
```

I like this a lot better than everything we've discussed so far, more consistent with the rest of the language, and avoids many pitfalls and limitations of other solutions, so I strongly believe it's the right direction overall.

## @tabatkins — 2025-11-03

I think Noam's already covered the arguments here well. We don't want multiple different border styles (multiple dots/dashes would look *horrific*, they'd be misaligned by default, and even aligned, multiple dots don't look great; groove/notch/inset/outset are just `solid` with some magic and possibly 2-color striping, and also would still just look weird to stack up). We do want multiple different border colors. We could want *either* multiple border widths *or* one big border width (with the colors being responsible for distributing themselves inside the width), but the existing tech (aka, how groove/notch work) suggests that "one big width" might be preferable. 

Further, as noted, understanding a comma-separated `border-color` that also sets different colors per side is, imo, near impossible. Two dimensions of optimal repetition is very difficult to mentally parse! Imagine manually doing `groove`, for example; it would require `gray black black gray, black gray gray black`, compared to `stripes(gray, black) stripes(black, gray) stripes(black, gray) stripes(gray, black)`, which is longer but has each side nicely grouped so it's trivial to understand what's happening on each side.

Multiple border *also* doesn't allow for gradient fades unless you go to enormous effort faking it with stacked 1px borders. That style isn't particular common these days, but the 3d border styles we used to have utilized it, and that style might return.

So that's why we settled on the design we did, and I still strongly believe it's the optimal solution, given the constraints. There are some alternatives that read better *in the simplest possible case* (all solid shape, each 'ring' the same color, which is the exact scenario you used in your poll), but fall apart the moment things get more complex.

- Simple: 2-3 solid borders, all the same width
- More complex: 2-3 solid borders, some with a different width

That’s literally it. And `stripes()` is currently suboptimal for both of these: You have to do mental gymnastics like "so I want each of my borders to be 1px wide, and I want 3 borders, so 3 * 1px = 3px". From the perspective of someone who uses CSS, I'd really just like multiple borders to be just that - multiple borders applied, in order, each one outside the previous one.

i.e., I'd like something like this:

```html
<div style="border: 1px solid red, 1px solid blue">Hello!</div>
```

to have the same appearance as this:

```html
<div style="border: 1px solid blue"><div style="border: 1px solid red">Hello!</div></div>
```

```css
.fancy-border {
  border-width: 2px, 4px;
  border-color: blue red red blue, yellow green green yellow;
}
```
Then you can see that the blue and red border is the 2px thick one, and the yellow and green border is the 4px thick one.

I don't think adding or remove a border of an existing element on a page is something which needs any special consideration. In general, people should *not* be doing that, since doing so (unless you're careful to maintain total border width) would re-layout the page. CSS authors can use custom properties to make it more ergonomic to alter colors/styles of existing borders without re-specifying the entire border set. 

A benefit of having native multiple border support is that people will be more likely to use `outline` for its intended purpose of adding a transient indication of focus/selection/attention. Additionally, if there is a reasonable "multiple border" syntax, the outline syntax could be extended in the same way to allow someone to e.g. create a black/white focus ring via outline which has high contrast over arbitrary backgrounds.

My position continues to be:
- This is the poster child of problem where the _vast_ majority of cases is very simple, but there are many niche complex cases and trying to solve for them will lead to **worse designs**. Instead of proposing solutions, we should first reach consensus about what the common cases are, and solve for them.
- I (quite strongly) believe that **the use case of separate border-styles, colors, or widths per side is niche and not worth optimizing for.** I'm fine with it having poor ergonomics if it helps us resolve on a solution that has good ergonomics for the common case and is consistent with the rest of the language. These cases should be *possible*, but they don't need to be *easy*, and should definitely not be syntax drivers! We can always introduce syntax later on that lets you group differently when using the shorthands, but anything that makes these cases easier should be a nice-to-have.
- The main things to optimize for IMO are:
  - multiple (but few) borders with the same color/style/width across all sides
  - specifying either the total width OR the individual widths without having to do manual math in either case.
  - I suspect that even within this set, 2-3 solid borders with the same width are > 50% of use cases.
- For **compat**, `border-width: 1px` **must** continue to specify the total width. This is a non-negotiable requirement, as a lot of existing content depends on a box model with certain dimensions. Same for a single border specified via the shorthands.

- Similarly for compat, **`border-style` and `border-color` should not be affecting box model dimensions**.

## @LeaVerou — 2026-01-28

After discussing this with @emilio @fantasai @frivoal last night I’m now convinced the right solution is listifying with `border-width` being the property that determines the number of borders.

- While purely from a usability/API design pov we want _both_ the ability to specify individual widths and total width, we concluded that **regardless of syntax** there is no way to enable the latter and maintain the current snapping behavior, which does point towards specifying border widths individually.
- `border-width: 1px` needs to preserve the guarantee that your border box is `1px` and `border-color` needs to remain a property that cannot affect the box model. This design satisfies both requirements.
- We don't want the indirection of needing `border-style: solid, solid, solid` to get 3 borders
- This keeps the number of new concepts to a minimum. No `border-width-relative`, no `fr` units, no weird new functions, just existing primitives.
- Perhaps we could later introduce something like `repeat()` to facilitate repetition of the same value in `border-width`, but that's definitely not MVP.

Hopefully we can get to it in this meeting and resolve for this so we can get rid of `stripes()`… (cc @astearns)

## @bradkemper — 2026-02-01

I'm pleased with the resolution, and sorry I wasn't able to be at the f2f or participate remotely (too busy at my job after coming back from PTO). 

As to some of the details:

1. In the same spirit of making the outline syntax match what we are doing with borders, I hope we can also go the other direction and have `border-offset`. 
2. For `outline-offset` and `border-offset`, there are some interesting effects that can be accomplished by allowing them to be listified too. Especially when using partially transparent colors (and/or blend modes for each border, if that was an option). I'd really like to have that. Only having `outline-offset` on the innermost outline doesn't seem useful, but being able to control the offset of each outline/border would be very useful. 
3. I agree that `border-radius` (or corner-shape) should not be listified. We called it `border-radius` because it changes the shape of the border-box (the outermost box), so it should be applied to the outermost border. Then, just as the shape of the inner edge of the border is calculated automatically, so should the shapes of the additional borders inside. To me this is very intuitive, even when borders are applied from inside to outside. 
4. Borders should be applied from inside to outside. It just feels more correct and natural to do so IMO. Adding a second border shouldn't change the first border, except that `box-sizing: border-box` squeezes it more towards the middle (as it does today with single borders).
5. The decision about `border-style: none` feels weird and inconsistent to me. If that is about ergonomics, I think writing `border: none` is a more common and simple way to remove borders anyway, and would still hide all borders by obliterating the list. I'd prefer being able to do `border-style: solid, solid, none` in order to remove a border without changing the widths set by `border-width`. Presumably we'd allow `border-width: 1px, 1px, 0px` to remove a line, so why not allow it with `border-style`, as I think most people would likely intuit? It seems like it complicates the mental model, to say the `border-width` is the thing that sets the list length, except sometimes is `border-style` when the value is `none` or `hidden`.
