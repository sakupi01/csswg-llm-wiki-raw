There appears to be a gap around Typed OM reification of computed values for properties using 1–4 side patterns, such as:
- border-image-outset
- border-image-slice
- border-image-width

Consider:

```js
document.body.attributeStyleMap.set("border-image-outset", new CSSUnitValue(0, "number"));
console.log(getComputedStyle(document.body).borderImageOutset);
console.log(document.body.computedStyleMap().get("border-image-outset"));
````

Current behavior (Chrome & Safari):
* CSSOM serialization:
  * `getComputedStyle(...).borderImageOutset` -> `"0"` or `"auto"`
* Typed OM:
  * `computedStyleMap().get(...)` -> `CSSStyleValue {}` (unsupported)

Current WPT coverage assumes these computed values are unsupported because the computed value conceptually expands to four values:
```js
// Computed value is always four values, which are not supported in
// Typed OM level 1.
```

However, CSSOM serialization collapses equal computed sides to a shorter form, for example:
```css
0 0 0 0 -> 0
1 2 1 2 -> 1 2
```

This raises the question whether Typed OM reification should follow:

* the conceptual computed value shape (always 4 values), or
* the canonical CSSOM serialization shape (collapsed representation)

Firefox's in-progress implementation will likely initially follow existing WPT coverage for compatibility (or relax WPT tests), but this behavior seems worth clarifying at the specification level.

When looking at `runUnsupportedPropertyTests` usage across these Typed OM property tests, there seems to be a pattern where values that cannot be represented as a single keyword/value (for example multi-keyword or multi-component values) are generally treated as unsupported and reified as `CSSStyleValue`. So it seems a similar approach could also make sense for these computed values.

Yes, I agree that should generally be the case. The surprising part here is that this area of the Typed OM spec appears to be significantly out of sync with existing WPT coverage and browser behavior.

> My current plan for WebKit is to match the spec and update the tests to match as well.

Could you discuss that with the spec editor and other implementors first? Firefox is currently close to matching the existing Chrome/Safari behavior for these property reification tests, and a broad WPT change here could invalidate a lot of recent implementation work.

There already seem to be many existing Typed OM WPT additions for properties that are either not listed in the spec’s Property-specific Rules section, or are listed without enough detail to define the tested behavior. For example:

* [https://github.com/web-platform-tests/wpt/commit/6ee4340a397d45ae933cd9e7c12c1686df0713cc](https://github.com/web-platform-tests/wpt/commit/6ee4340a397d45ae933cd9e7c12c1686df0713cc) (`anchor-scope` is not listed in the spec)
* [https://github.com/web-platform-tests/wpt/commit/94e6098451b2fe3e754a1058701036d8684c0715](https://github.com/web-platform-tests/wpt/commit/94e6098451b2fe3e754a1058701036d8684c0715) (`animation-duration` and `animation-iteration-count` are not listed; `gap` is listed but without a clear reification definition; `logical` not listed; `shape-margin` listed but without a definition; `stroke-dasharray` listed but without a definition)

Those changes were also added by WebKit contributors, so it seems the current ecosystem has already been evolving based on interoperable implementation behavior and WPT convergence, even in areas where the spec text is incomplete. Because of that, I think it would be good to align on the broader direction before making large compatibility-impacting WPT changes.

## @tabatkins — 2026-07-15

I agree with weinig in general. The reification behavior is very difficult to define in a general fashion, which is why the spec is written the way it currently is. This does mean it needs a lot of specification text, which is unfortunate, but the entire point of TypedOM is that the value is easily manipulatable, so there are stability concerns we want to pay attention to. That's *why* we fall back to the "uninterpreted" form; string parsing is more annoying, but it at least exists already for browsers that don't support TypedOM.

I haven't given TypedOM a lot of love the past several years, largely because it had been ignored by non-Chrome browsers so there wasn't a huge incentive to push to complete it. That's obviously been changing lately, but my bandwidth to re-pickup a big project like this is limited.

Still, I am not immediately confident that the behavior pushed forward by implementations ahead of the spec necessarily were designed with the attention to forward-compatibility that is necessary for a good design here. So, current impl behavior should ideally be considered only tentative.
