_Creating this issue as requested on mastodon._

Calling a custom function is only place in CSS where the expected/established DX of vars effectively spreading in-place doesn't happen.

```css
--rgb: 255, 0, 0;
color: rgb(var(--rgb));
```

As a CSS author, this anti-spreading behavior feels broken/unexpected.
(and is incredibly disappointing to not have access to the enormous potential of argument spreading)

It was originally planned and assumed as the rational expectation:
https://github.com/w3c/csswg-drafts/issues/11190#issuecomment-2596276757

It appears that it was implemented:
https://issues.chromium.org/issues/390205875#comment3

and then cancelled shortly after (afaik, without public discussion):
https://issues.chromium.org/issues/390205875#comment5

The `{var(--csv)}` syntax to prevent spreading makes sense from the perspective of a CSS author and is implemented / shipped.

---

The primary counter argument caters to non-CSS developers, stating that other languages don't auto spread arguments so CSS custom functions shouldn't either.

I whole heartedly disagree with the conclusion of this counter argument but so far I have stood alone in intention to question it.

Other counter arguments I've seen are situational and don't uniformly apply (like when arguments are typed, the evaluation happens anyway, etc).

---

For context, I have written dozens of complex custom functions, including working, trivial DX, --repeat() and --loop() functions, an entire bitwise suite, and am actively writing many more.

I know questioning decisions already made is not a pleasant thing to do so I apologize for that while still being incredibly hopeful that the expectation will be restored.


---

It also seems like it would be difficult to maintain erroring when too many arguments are used in the call... though I also want to say that it is confusing DX to try debugging why a function isn't working at all. (Is something cyclic? A semicolon missing? Comma missing? Something else?) Without a CSS error console, it is much much easier to debug an incorrect argument causing weird behavior than to experience when a function isn't returning anything at all.

## @tabatkins — 2026-05-19

(Jane and I have discussed this on Mastodon previously.)

> The primary counter argument caters to non-CSS developers, stating that other languages don't auto spread arguments so CSS custom functions shouldn't either.

This is one argument. It's not the primary one, and I don't think I ever characterized it as such. I do think it's a big one, though!

To elaborate, in normal CSS properties you can drop a `var()` in anywhere and it'll just spam out whatever it holds, even if that crosses what we would normally consider a "semantic boundary", then CSS parses the whole thing as a unit, with no consideration for where the var()s had appeared. For example:

```css
--foo: center, 20%;
background-position: center var(--foo) 80%;
/* expands to:
  background-position: center center, 20% 80%;
*/
```

This sort of behavior is *extremely confusing*. The custom property suggests that it's a comma-separated list of two meaningful values, when it's not - it's two halves of two `<position>`s. The `var()` suggests that it's dropping a value into a single background layer, and the surrounding values (`center` and `80%`) are doing their own thing on that layer, but it's not - it's defining *two* layers, giving the final bit of one layer, and the starting bit of a second layer.

This sort of confusing usage is unavoidable, however, because CSS grammars aren't structured enough to make "semantic units" meaningfully defineable. To allow for a lot of *reasonable* usages, we had to allow these unreasonable ones. (And this applies to CSS functions in general; while we *mimic* other language's use of comma-separated arguments, that's just a convention enforced by the function's grammar. We *avoid* commas in many cases, and in general have access to the full flexibility of CSS property values inside of functions.)

As another example where vars often *do* contain commas, take gradients. `linear-gradient(to top, var(--foo))` makes intuitive sense to us with the var() supplying the stops, as does `linear-gradient(var(--foo), red, blue)` with the var() supplying the direction/etc. But if you had `--foo: to left, white 20%; background: linear-gradient(var(--foo), red, blue);`, that could be surprising/confusing to someone else, because the `var()` is crossing the implicit semantic boundary separating the first argument from the rest. If we had a consistent story for this across CSS, it *would* be better to disallow that usage by default, and require `linear-gradient(...var(--foo), red, blue)` to make it clear you're doing something more unusual.

(But this isn't absolute! We *do* track ()[]{} pairings, and `var()` can't violate that. You can't, for example, do `background-image: url(var(--foo)); --foo: "img1"), url("img2";` and suddenly get two images. So, to the extent that semantic boundaries are easily and unambiguously detectable, we honor them.)

In custom functions, we *can't* apply arbitrarily-complex grammars inside the (), because we can't parse them unambiguously. The grammars authors *can* use for their arguments don't include commas, so commas *do* become an unambiguous semantic-unit separator. 

The only arguments that *can* take commas in their value, then, are those that are left entirely un-syntax'd, almost certainly because they're meant to take a chunk of *another property* that they'll be subbed into.  If you fill in one of these arguments manually, it's *much more obvious* that you're doing something wrong and might need to reach for `{}` to wrap the argument, but when you pass it via a `var()` or similar, that's no longer obvious.

-----------

Now that was a lot of words for something I said wasn't even the primary motivator. The other big one is consistency, as Miriam alludes to (tho from the other side, lol). *Most* of the other arbitrary-substitution functions (arbsubs) *need* to be able to tell their arguments apart immediately, to allow for useful functionality:

* `var()`, `inherit()`, and `attr()` have fallback arguments we want to leave unresolved unless needed. 
* `first-valid()` is *all* fallback arguments, so the same applies.
* `if()` wants to have the standard short-circuity behavior that if/else constructs have in almost every language, where the body of a failed test isn't resolved, and early true test will leave the later tests unresolved too.

For all of these, in order to achieve these abilities, we have to see the argument separators *before* variable substitution, so we can treat each chunk differently. If you need a var() to supply multiple of the arguments, that's what the `...var()` spread syntax is for. It signals you're doing something unusual, but you *do* lose something from it - the contents are entirely evaluated, even if they're part of fallback or unused branches.

Custom functions are also arbsubs, and it's nice to give them the same resolution behavior so there's an easier to understand rule. We shouldn't rule out, too, the possibility that we let custom functions declare some arguments to stay unresolved, so they have access to the same fallback behavior other arbsubs have. Keeping that open as a possibility *requires* us to have the same arg-splitting behavior from the start.

----------

@mirisuzanne 
> authors now need to learn two different solutions for managing spread in different contexts (that are otherwise designed to feel similar). One syntax is needed to stop spread from happening in provided functions, and another (new) syntax is needed to request spread in custom functions.

I don't see why you seem to be implying these are confusingly opposed. They're a necessary pair; you can't have one without the other (without having a really bizarre functionality hole). It's exactly identical to JS having both [] syntax for arrays holding comma-separated values, and spread syntax supplying multiple comma-separated args with a single variable. 

Neither `foo(1, [2, 3, 4], 5)` (passing three args) nor `foo(1, ...args, 3)` (passing *two or more* args) are particularly confusing in JS, and the simple case of `foo(1, args, 3)` (passing three args regardless of what `args` is) is also straightforward. In CSS these two are just spelled `--foo(1, {2, 3, 4}, 5)` and `--foo(1, ...var(--args), 3)`, and the simple case of `--foo(1, var(--args), 3)` passing exactly three args similarly straightforward.

> In other words, there is no scenario where the expectation is for it to remain as a single argument, but instead only scenarios where the expectation would be that it spreads to multiple arguments.

Not true. I mentioned the exact scenario I'm afraid of - a custom function taking a property value as an argument, where that property *can be* a comma-separated list, but doesn't *have* to be. It's easy to author the function with the assumption of a single, simple non-comma value, and then be passed a comma'd value anyway.

Note, importantly, that this isn't a problem that the function *author* can deal with. That's fairly easy to remember when you're writing the comma manually (it feels like a *different kind* of comma from the ones separating this arg from the others), but it's much less obvious that you need to do this when the argument is being provided by a `var()` or similar function.

I understand that *your* use-cases tend more towards relatively simple arguments, and var()s that can provide multiple of these arguments at once, but I'm trying to consider the full spread of cases I expect to see in the wild. I'm also trying to bias my design towards working "correctly by default" for less-advanced authors; you are emphatically *not* that. (I never want to *shut off* the ability for advanced authors to do cool stuff, but if they need to take an extra step to do something "unusual", that's more palatable.)
