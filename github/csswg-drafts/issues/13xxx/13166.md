The [`nav-…` properties for _directional focus navigation_](https://drafts.csswg.org/css-ui-4/#nav-dir) in CSS UI 4 are among a small set of properties that accept a local URL in the host document as their value. 

~~~~ ebnf
nav-up =
nav-down =
nav-right =
nav-left = auto 
         | <id> [ current | root | <target-name> ]?
~~~~

It’s simply `<id>` here, is always unquoted and starts with the usual hash sign `#`. In comparison, the [cross-reference `target-…()` functions](https://drafts.csswg.org/css-content/#cross-references) use `[<string> | <url>]` as their prime argument. There is #12590 to discuss whether or how that is a bad design decision. 

I don’t really know the full specification and implementation history of these properties – CanIUse.com, MDN etc. are rather quiet on them, but did skim over some older drafts. They were [punted to Level 4](https://drafts.csswg.org/css-ui-3/#changes-2021-03-16) after the 2017 CR of CSS UI Level 3. 

Although the [Spatial Navigation module](https://drafts.csswg.org/css-nav-1/) has been drafted in the meantime, these properties cannot _simply_ be dropped, because apparently they have been available in special-purpose TV browsers for many years since support for them is mandatory in specifications like CEA-2014-A / ANSI/CTA-2014-B (“CE-HTML”, “Web4CE”), [OIPF](https://www.oipf.tv/web-spec/volume5a.html#css-basic-user-interface) and [HbbTV 1.5](https://www.hbbtv.org/wp-content/uploads/2018/03/HbbTV-SPEC15-00001-001-specification_with_errata-integrated.pdf#page=63)/[~~2.0~~](https://www.etsi.org/deliver/etsi_ts/102700_102799/102796/01.07.01_60/ts_102796v010701p.pdf#page=138). However, they were not included in the now retired [CSS TV profile](http://www.w3.org/TR/css-tv), which also got referenced normatively in non-obsolete standards for consumer electronics products. 

((In earlier working drafts, there also used to be a numeric [`nav-index` property](https://www.w3.org/TR/2012/WD-css3-ui-20120117/#nav-index) that was intended to correspond with the [`tabindex` attribute in HTML](https://html.spec.whatwg.org/multipage/interaction.html#attr-tabindex). It was dropped in [early 2015](https://www.w3.org/TR/2015/WD-css3-ui-20150224/#changes-list) although OIPF, for instance, mandated support for it.))

Note that the `<id>` property value cannot really come from an attribute value in the host language because `attr()` is [intentionally crippled for URLs](https://github.com/w3c/csswg-drafts/issues/5079#issuecomment-3329306728). #12340 

~~~~ css
h2 {
  nav-up: #toc;
  nav-left: attr(data-prev-chapter type(<url>));
  nav-right: attr(data-next-chapter type(<url>));
}
a[href^="#"], a:local-link {
  nav-down: attr(href type(<url>));
}
~~~~

Therefore, could these four properties for spatial navigation, i.e. `nav-up`, `nav-down`, `nav-right` and `nav-left`, reuse CSS-internal [implicitly](https://drafts.csswg.org/css-anchor-position/#implicit) and [explicitly defined, named anchors](https://drafts.csswg.org/css-anchor-position/#name) as their targets, …

~~~~ css
h2 {
  nav-right: --next-chapter;
  nav-down: --chapter-start;
}
h2:focus ~ h2 {
  anchor-name: --next-chapter;
}
h2:focus + p {
  anchor-name: --chapter-start;
}
~~~~

… possibly using a new function related to existing [cross-references](https://drafts.csswg.org/css-content-3/#cross-references)?

~~~~ css
h2 {
  anchor-name: --chapter, ident("--" attr(id));
  nav-up: target(auto);
  nav-left: target(previous --chapter);
  nav-right: target(next --chapter);
  nav-down: target(next --chapter-start), target(next element);
}
h2 + p {
  anchor-name: --chapter-start;
}
~~~~
