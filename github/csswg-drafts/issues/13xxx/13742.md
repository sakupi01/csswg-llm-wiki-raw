The spec does not have any opt-out for them so seems to say "no":

> Using an attr()-tainted value as or in a `<url>` makes a declaration invalid at computed-value time.

However the current attr-security.html WPT says "yes":

```
    test_attr('--x',
              'src(attr(data-foo))',
              'https://does-not-exist.test/404.png',
              'src("https://does-not-exist.test/404.png")');
```

## @tabatkins — 2026-06-03

That test is setting `--x` (an unregistered property) to the value `src(attr(data-foo))`. Because it's unregistered, *there is no URL there*. All the CSS engine sees is the value `████attr(data-foo)████`. Substitution succeeds as normal there, resulting in `████"https://does-not-exist.test/404.png"████`, with that string attr-tainted. Totally fine.

Then when you *use* that value, parsing and interpreting the full `src("https://does-not-exist.test/404.png")`, you run into the security restrictions:

* functions that contain an [attr()-tainted](https://drafts.csswg.org/css-values-5/#attr-taint) value are themselves attr-tainted (`src()` contains an attr-tainted `<string-token>`)
* Using an [attr()-tainted](https://drafts.csswg.org/css-values-5/#attr-taint) value *as a `<url>`* makes a declaration IACVT (the tainted `src()` is indeed a `<url>`)

So the WPT is correct per spec, and matches my intention. Following your suggestion would require us to introduce new concepts to the Variables spec, where unregistered properties *partially* interpret the uninterpreted token segments of their value to determine what parts are "actually" a `<url>`.
