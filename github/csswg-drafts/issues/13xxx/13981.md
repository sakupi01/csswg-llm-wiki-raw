I'm splitting this issue out from https://github.com/w3c/csswg-drafts/issues/12437.

This issue is to discuss what the layout tree looks like when `::interest-button` is present. There have been a number of suggestions:

- "Normal" child in the layout tree
- Sibling in the layout tree
- Anonymous box created around the originating element and pseudo element (/me waves hands)
- Behavior "like [list style position outside](https://www.w3.org/TR/css-lists-3/#list-style-position-outside)" (/me waves hands)

The general issues are:
- Interaction with the [opt-in / opt-out behavior](https://github.com/w3c/csswg-drafts/issues/13980) (avoiding layout shifts).
- Ability to position the pseudo element "outside" the originating element, especially when it is a `<button>`.
- Ability to leave the pseudo element in document flow, to avoid overlapping other content or other problems.
- Playing nicely with other layout, e.g. parent `flex` or `grid`, `display:block` on the originating element, etc.

This was discussed here:
- [WHATWG/CSSWG/OpenUI task force April 30, 2026](https://github.com/w3c/csswg-drafts/issues/12437#issuecomment-4354054738)
- [WHATWG/CSSWG/OpenUI task force May 28, 2026](https://github.com/w3c/csswg-drafts/issues/12437#issuecomment-4565964710)

In particular, it was resolved on April 30 to make `::interest-button` come after `::after`, and be a **child** in the layout tree. But I think the May 28 discussion (plus the discussion on https://github.com/w3c/csswg-drafts/issues/12437) made it clear that perhaps more thought is needed.

## @mfreed7 — 2026-06-08

I am starting to think that anchor positioning might be the best way to tackle positioning for `::interest-button`. I've been playing with a prototype using this:

```css
::interest-button {
  position: absolute;
  position-anchor: auto;
  position-area: inline-end;

  margin-inline-start: 0px; /* just delete the proposed 0.25em rule in #13982 */
}
```

That looks like this (with shading added so you can see it):
<img width="88" height="61" alt="Image" src="https://github.com/user-attachments/assets/029196b1-1da9-46a6-bbad-3ea3b2f0269b" />

The pros:
- Does not cause layout shifts.
- Positions the pseudo "outside" the element.
- No need to do magic in the pseudo element tree, or deal with list marker positioning, etc.
- Plays nicely with other layout, such as `flex` or `grid`.

The cons:
- The ⓘ icon can overlap existing content.

In practice, the content overlap is only a small issue in the case that the developer didn't notice that the ⓘ showed up. It's a small icon, and text is still generally quite readable underneath it. And if the developer *did* notice it, it's also an easy fix (e.g. add `margin-inline-end:24px;` to the invoker).

E.g.

```css
[interestfor]::after {
  this-actually-is-an-interest-button: yes;
  content: '\24D8';
}
```

I like the property name, but it probably needs bikeshedding. Otherwise, the proposal would be that the above CSS generates the `::after` pseudo element, and connects clicks on that pseudo over to showing interest in the originating element (and does the same `preventDefault` behavior [previously discussed](https://github.com/w3c/csswg-drafts/issues/12437#issuecomment-3383320964)).

## @mfreed7 — 2026-09-02

So there are two issues combined here. One is the stated one: what should the layout tree be for `::interest-button`? The other is whether this should be `::interest-button` or an augmented existing pseudo like `::after` with extra behavior added. To keep this issue clean, I've split that question out into https://github.com/w3c/csswg-drafts/issues/14433.

On the original issue, I've been experimenting in Chrome and I'm starting to really like the last suggestion I [made above](https://github.com/w3c/csswg-drafts/issues/13981#issuecomment-4651351171), which is to use anchor positioning to put the button after the content:

```
::interest-button {
  position: absolute;
  position-anchor: auto;
  position-area: inline-end;
}
```

It positions the button right where most people seem to put it (after/outside the `<button>` or `<a>`), it's easy to understand and use (and therefore modify to suit), and it doesn't require heroics with the layout tree or list marker positioning. See the screenshot in the [comment above](https://github.com/w3c/csswg-drafts/issues/13981#issuecomment-4651351171). The only negative I can see is that it makes it possible for the pseudo element to overlay other neighboring content. But assuming this pseudo is opt-in, this is very easily solved when you opt-in:

```
::interest-button {
  content: '\24D8' / ''; /* opt in */
}
[interestfor] {
  margin-inline-end: 1.5em; /* adjust for the content you've added */
}
```

I suppose we could do some magic to incorporate the extra margin if this pseudo is generated, but I think that's likely not needed or even very helpful.

## @dbaron — 2026-09-03

To add to what I was starting to say in IRC as the meeting ended:

I think "sibling in the layout tree" pseudos pose some really horrible issues.  What happens when the main element is positioned or floated, or is a flex or grid item, etc.  It ends up requiring a wrapper that goes around the main element and its sibling and splitting various styles between the real element and the wrapper, and the splitting of styles never really works the way people expect.  This is similar to the problems with `<caption>` and its interaction with tables.

Ok, I got this into Chromium ([Canary 155+](https://chromiumdash.appspot.com/commit/b942aaa95ff860964c4d5cd8ec2a6bfaeb00dd74) only at this point, and with experimental web platform features enabled) and played around with it a bit. @bramus also gave it a spin. I think the tentative conclusion is "LGTM". It definitely fixes the "con" of overlapping neighboring content, since the button stays in-flow. It also removes the semi-hacky `margin-block: min(-24px, -1lh);` from the [UA stylesheet](https://github.com/w3c/csswg-drafts/issues/13982). There are some new corner cases, which were anticipated [above](https://github.com/w3c/csswg-drafts/issues/13981#issuecomment-5528437311), such as these:

- when the `<button interestfor>` or `<a interestfor>` are part of a flexbox, the `::interest-button` becomes a flex participant itself, which sometimes works and sometimes doesn't.
- when the originating elements are abs-pos or floated, they leave the `::interest-button` behind.

In practice, these seem roughly "ok" to me at least, since if this is really what you're trying to do, you can fairly easily wrap the element in a `<span>` to contain them both, or directly take control of the button positioning, e.g. via anchor pos. In the normal use case of a `<button>` or `<a>` in flow, things work very nicely.

I'd love more feedback on this approach!

## @mfreed7 — 2026-09-15

Based on my further testing, I think I really like the sibling approach. One thing that wasn't discussed above is the relative position of this pseudo to the other pseudo elements. Because it's a sibling, it obviously comes after all of the other "child" pseudo elements, so that's easy. But there are two other types of sibling pseudo elements (`::scroll-button` and `::scroll-marker-group`) that this would need to mix with. In the Chromium prototype, I put `::interest-button` *before* the scroll related pseudos. In practice I think it matters very little, since most `<button>` and `<a>` elements (the originating elements for `::interest-button`) are not scrollers, and don't use scroll pseudos. But still this seems to make sense.

I'd like to propose that we resolve this issue along the lines of [the previous resolution](https://github.com/w3c/csswg-drafts/issues/13981#issuecomment-5528407811), but without the `"Try implementing"` part. E.g.

```
Proposed resolution: `::interest-button` is positioned as a trailing adjacent sibling of the originating
element, before scroll button/marker pseudos
```

Thoughts?

I took an action item to show examples of what this (layout tree sibling) would look like in code, for flex/grid/abspos/float cases. I think the developer-side solutions are largely similar in all four cases:

### Wrapper element

Rather than a "naked" interest invoker element, use a wrapper:

```
<span>   <!--   Wrapper element -->
  <button interestfor=foo>Button with interest invoker</button>
</span>
```

That keeps the originating interest invoker together (in flex/grid) or provides a unified element that can be abspos/float positioned instead of the `<button>` itself. It does require the addition of `<span>` to the HTML, but that can be done at the time of adding `interestfor` to the HTML.


### Anchor pos (or other positioning)

Don't add a wrapper element, and use abspos and anchor pos to keep the `::interest-button` connected to the invoker:

```
<button interestfor=foo>Button with interest invoker</button>   <!-- No wrapper -->

<style>
::interest-button {
  position: absolute;
  position-anchor: auto;
  position-area: inline-end;
}
</style>
```

Both of these approaches seem reasonable, depending on what the author is trying to do with their flex/grid/abspos/float layout. I don't think either is strictly correct for all use cases - it depends on the page layout.

Another important thing is that in most cases that I've seen, e.g. [Wikipedia](https://en.wikipedia.org/wiki/Main_Page), the interest invokers are using inline layout, and not flex/grid. Certainly not usually abspos/float pos. So I think in most of the "usual" cases, the default proposed behavior of just adding an adjacent sibling in flow "just works".

I took a harder look at the "just add an anonymous wrapper layout box around it" idea, to see what might be involved. My TL;DR is that I **really** think we should avoid this approach. It doesn't seem to have a precedent in CSS, and it has *many* oddities that feel a lot worse than just adding a wrapper `<span>` to the markup. For example:

- Which of the element's properties describe the wrapper and which describe the element's own box, and is there a principle for the split or just an enumerated list? Once `position: absolute` describes the wrapper while `display: inline-block` describes the element, what should `getComputedStyle(el).position` and `.display` return, and is the element's display still blockified by a position it no longer has?
- If the wrapper exists only when `::interest-button` generates a box (which seems reasonable), then setting its `content` inside a media or container query adds and removes a box on resize. Is that acceptable, what does it mean for container-query cycles, and if not, what else determines when the wrapper exists?
- Which box is the flex or grid item? If it's the wrapper, what becomes of `align-self`, `order`, `flex`, `grid-area`, and sizing declared on the element — do they transfer to the wrapper, or is the element's style simply inert inside a flex or grid container?
- What `display` type does the wrapper have? If it's inline-level, it can end up wrapping a block-level element; if it copies the element's display, the element and the interest button end up inside a formatting context chosen for one of them.
- Several other questions. Primarily, generating two boxes from one element just opens a huge can of worms.

Based on the above, I'd like to push for *not* going this route. The sibling approach works out of the box for the usual case of in-flow elements, and the [examples above](https://github.com/w3c/csswg-drafts/issues/13981#issuecomment-5718819259) show that it's fairly trivial to make this work in flex/grid containers. And this approach [works a lot better](https://github.com/w3c/csswg-drafts/issues/13981#issuecomment-5639367454) than the prior anchor-pos approach. Given all of that, I'd like to re-propose a resolution here:

```
Proposed resolution: `::interest-button` is positioned as a trailing adjacent sibling of the originating
element, before scroll button/marker pseudos. It inherits, as usual, from the originating element.
```
