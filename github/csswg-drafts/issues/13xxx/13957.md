[css-multicol](https://www.w3.org/TR/css-multicol-1/) and [css-multicol-2](https://www.w3.org/TR/css-multicol-2/) have this example:
> EXAMPLE 31
> ```css
> article {
>   width: 60em;
>   height: auto;
>   columns: 4;
>   column-fill: balance;
> }
> ```
> In this example, an article starts with an unbreakable figure which sets the column height. Subsequent content is filled sequentially into the remaining columns:
> <img width="665" height="120" alt="Image" src="https://github.com/user-attachments/assets/67d05804-4140-4e69-9966-082ab4ced184" />

Nowhere in the definition of `column-fill: balance` or the explanation of balanced column filling does it say that columns should be filled sequentially up to some hypothetical minimum height determined up-front. The spec for `column-fill: balance` only says to "balance content equally between columns, as far as possible". A bit further up, [§8 Filling Columns](https://www.w3.org/TR/css-multicol-2/#filling-columns) tells us that this means to "minimize variations in column height". Sequential filling is called out specifically as a thing to do when columns are not balanced.
And one can achieve a more balanced distribution here, by filling all three columns that come after the figure with three lines of text each.

All browsers currently produce the example rendering from the spec when faced with a situation that would lead to it, but I cannot find any spec basis for this. How exactly am I supposed to determine 1. the column height of a balanced multicol container and 2. the expected distribution?

I am asking because I've written [an implementation](https://github.com/LadybirdBrowser/ladybird/pull/8785/changes/cb3903290e391ef5021e8bff1492b7fc26ffc0e6) for the Ladybird browser which manages to produce a more balanced layout. As it stands, this is compliant with the normative requirements, but those seem to be at odds with what everyone else is doing.

PS: Example 30 makes a similar assumption that there must be some vaguely implementation-un-defined height-establishing step up-front.

## @SelenIT — 2026-07-24

It seems that these examples try to explain the last part of that passage from the [§8 Filling Columns](https://www.w3.org/TR/css-multicol-2/#filling-columns):

> If columns are balanced, user agents should try to minimize variations in column height, while honoring forced breaks, [widows](https://www.w3.org/TR/css-break-4/#propdef-widows) and [orphans](https://www.w3.org/TR/css-break-3/#propdef-orphans), _and other properties that may affect column heights_.

I.e. _generally_ the balancing algorithm tries to minimize variations in column height _as much as possible_ (by choosing the most fitting height for all columns), but there can be things that explicitly or implicitly set the minimum column height, and in such cases the balancing algorithm can't make the height of all columns smaller than that minimum even if there is not enough content to fill the other columns. And after the column height is chosen, no other adjustment can be done, only sequential filling.

That said, I agree that the phrase "If columns are not balanced, they are filled sequentially", implying that balanced columns are filled differently, is misleading. Maybe it should be replaced by something like "After the height of the columns is determined, they are filled sequentially"?

## @mstensho — 2026-07-24

> Nowhere does the spec say that the balancing algorithm is meant to do this balancing by setting the column height to something that'll lead to a nice balance. Maybe that's where my confusion comes from, as my initial assumption was that the balancing could also be done while filling the columns, without knowing the height yet, because that can give more balanced results. (See the second image from my previous post)

The way it's implemented, `column-fill` indeed doesn't affect how columns are filled, which sure can be a source of confusion. `column-fill` doesn't affect how columns are filled. Huh? :) `column-fill` only affects the height of the columns (and the containing line). I don't think this is what the spec says.

From the spec, we know that all columns within a line have the same height.

https://drafts.csswg.org/css-multicol-2/#the-multi-column-model
> and all column boxes in a line have the same column height.

In the implementations, `column-fill:balance` will make sure that the column height is large enough (but no larger than that) to fit all fragmented content - instead of setting the height to that of the content box of the multicol container. So we're possibly violating the spec in some cases:

> In the simplest case a multicol container will contain only one line of columns, inside one multicol row, and the height of each column will be equivalent to the used height of the multi-column container’s content box.

I doesn't mention anything about balancing affecting this, meaning that:

```html
<div style="columns:2; column-fill:balance; height:1000px; line-height:42px; orphans:1; widows:1;">
  text<br>
  text<br>
</div>
```

should result in 1000px tall columns. Blink doesn't do that. (Similarly for the other engines, I guess.) Instead the column height becomes 42px - just enough for one line of text.

It gets more interesting. If we add a column rule, it *does* become 1000px tall, in all engines.

https://drafts.csswg.org/css-multicol-2/#column-gaps-and-rules
> The length of the column gaps and column rules is equal to the column height.

And that's in spite of the column height being 42px for layout purposes. In Blink we have special code that makes sure that the rules extend to the end of the multicol container (1000px), rather than just the column height (42px). Maybe the other engines do something similar.

Let's scroll to chapter 8. https://drafts.csswg.org/css-multicol-2/#filling-columns
> If columns are balanced, user agents should try to minimize variations in column height

The spec has already said that "all column boxes in a line have the same column height". There may be zero of such variation!

Maybe the rest of the spec evolved (introducing column lines and rows), whereas this part of the spec wasn't updated. It should say something about calculating column heights for balancing.

It is clear that balancing sometimes needs to affect the column height. While that necessarily wasn't the case in the previous example, where there was a fixed container height, if the container height is auto, column balancing should result in a neat column height. E.g.

```html
<!DOCTYPE html>
<div style="columns:3; orphans:1; widows:1; line-height:20px;">
  <div style="contain:size; height:100px;"></div>
  text<br>
  text<br>
  text<br>
  text<br>
</div>
```

The total height of the content (if not fragmented) is 180px (100px + 4 * 20px). We want to balance it into three columns, so 180px / 3 = 60px. However, the inner DIV is unbreakable and it is 100px, so the column height will become 100px. The height of the multicol container also becomes 100px. All engines agree on that. They all successfully calculate a suitable column height and multicol container height. What they don't do is the "minimize variations" part, apart from what we get for free by simply setting a good column height. All existing engines place all four lines in the second column, because they fit. The third column remains empty.

In summary, maybe column balancing should consist of two steps.

1. If available height is unconstrained, calculate a good column height. Blink / Gecko / WebKit do this. Otherwise column height should follow from available height (e.g. the content box of the multicol container). Blink / Gecko / WebKit all seem to calculate a "good column height" even in constrained cases, so that if there's not enough content to fill a fixed-size multicol container, the columns will be shorter than the content-box of the multicol container. This seems wrong, and we need special code to get the column rules right because of this.
2. When filling the columns, attempt to minimize variations. Blink / Gecko / WebKit don't do this.

## @mstensho — 2026-07-29

I realize now that both L1 and L2 both sort of suggest that what @Psychpsyo implemented in Ladybird is actually wrong. But maybe that's just a spec issue.

https://drafts.csswg.org/css-multicol-1/#cf

(regarding the `column-fill` property)

> In continuous contexts, this property does not have any effect when there are overflow columns.

In other words:

```html
<!DOCTYPE html>
<div style="columns:3; width:60%; height:60px; line-height:20px; orphans:1; widows:1; background:yellow;">
  line<br>
  line<br>
  line<br>
  line<br>
  <div style="contain:size; border:solid; height:100px;"></div>
  overflow<br>
</div>
```

There's an overflowing column here, and if `column-fill` shouldn't affect behavior in such cases, the four lines preceding the tall unbreakable `div` cannot be neatly balanced. One would think that if balancing is enabled, there might be two lines in the first column, and two lines in the second, but with sequential filling there will be three in the first and one in the second.

## @mstensho — 2026-07-29

L1 also has this:

> All column boxes in a line have the same column width, and all column boxes in a line have the same column height.

And this:

> If columns are balanced, user agents should try to minimize variations in column height

There can be zero variation in column height if the first piece of spec is to be honored. So maybe this latter part should rather say something about the amount of filling, rather than the column height.

Of course, as mentioned earlier, column balancing may also affect the column height (but columns on the same line should still have the exact same height), if the available space is unconstrained.
