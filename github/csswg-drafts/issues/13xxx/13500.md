How should the shorthand associated with a [coordinated value list](https://drafts.csswg.org/css-values-4/#linked-properties), such as the [`animation`](https://drafts.csswg.org/css-animations/#animation) shorthand property or the [`scroll-timeline`](https://drafts.csswg.org/scroll-animations/#scroll-timeline-shorthand) shorthand property, serialize when the [coordinating list base property](https://drafts.csswg.org/css-values-4/#coordinating-list-base-property) has fewer values than a non base property?

For example, how should the computed style (via getComputedStyle) for `scroll-timeline` serialize when the following properties have been set:

```css
 scroll-timeline-name: '--a, --b;
 scroll-timeline-axis: 'inline, inline, inline;
```

(example comes from https://wpt.fyi/results/scroll-animations/css/scroll-timeline-shorthand.html)

Should it be `--a inline, --b inline`, as the test expects, or `--a inline, --b inline, --a inline` which would be closer to what `animation` and `transition` serializations would do?

## @emilio — 2026-02-16

Yes, that's correct. Serializing shouldn't change the computed style at all (even if some of the extra values wouldn't be used due to the different lengths). Changing the length of the computed style can have other observable effects, e.g. via inheritance (consider a descendant doing `scroll-timeline-name: inherit;` or so).

## @weinig — 2026-02-17

Ok, thinking through this for some additional cases:

```
scroll-timeline-name: --a, --b, --c;
```

Here, the computed value of `scroll-timeline-name` is, `--a, --b, --c`, and the computed value of `scroll-timeline-axis` is `block` (its initial value), so the computed value of `scroll-timeline` would have to be the empty string.

I think that means the rule is that for coordinated value lists:

"If you specify more than one value for **any** of the longhands, but **not all** of the longhands, the shorthand will serialize as the empty string."

Does that sound right to you?

## @emilio — 2026-08-21

I actually realized when reviewing https://github.com/web-platform-tests/wpt/pull/62014 that the spec might not be _quite_ right I don't think. In particular, the initial value clause in [the spec](https://drafts.csswg.org/css-values-4/#linked-properties) makes:

```css
  scroll-timeline-name: --a, --b, --c;
  scroll-timeline-axis: block;
```

Serialize to:

```css
  scroll-timeline: --a, --b, --c;
```

But the later would expand to `scroll-timeline-axis: block, block, block;` which wouldn't round-trip.

@tabatkins am I missing something? Is that intentional?

Seems like Firefox currently enforces the round-tripping, but Blink and WebKit don't. I do think that special-casing the initial value like that is unfortunate / footgunny.

A test-case from @integralpilot in that WPT PR that also shows the difference with the `transition` shorthand:

```js
const element = document.createElement("div");
document.body.append(element);
element.style.transition = "all 0s ease 0s";
element.style.transitionProperty = "opacity, color";

console.log(element.style.transition);
```

Which logs `opacity, color` in Blink and WebKit but the empty string in Gecko.

## @weinig — 2026-08-26

By forward compatibility, I think @fantasai means (and its what I mean) is that if new properties are added to coordinated value group, say a hypothetical `scroll-timeline-foo` is added to the `scroll-timeline` group, existing code that assumes the shorthand would serialize would continue to serialize.

I want to make sure I totally understand the issue because I think preserving some forward compatibility makes sense and is a good goal.

For the `scroll-timeline: --a, --b, --c;` case, the issue is that this is equivalent to explicitly writing out both `scroll-timeline-name` and `scroll-timeline-axis` rules:

```
  scroll-timeline-name: --a, --b, --c;
  scroll-timeline-axis: block, block, block;
```
 
Would it be practical to re-define things such that it instead was equivalent to:

```
  scroll-timeline-name: --a, --b, --c;
  scroll-timeline-axis: block;
```

where it fills in the minimum required elements for missing components.

That would mean that something like: `scroll-timeline: --a, --b block, --c;` would be equivalent to:

```
  scroll-timeline-name: --a, --b, --c;
  scroll-timeline-axis: block, block;
```

Would there be downsides to this approach?

## @dbaron — 2026-09-02

So after a little further thought, I think I might be OK with an exception targeted to the following case:
* the longhand property is part of a coordinating list property group and is *not* the coordinating list base property
* all values of the property in the list are the same (which could be a 1-item list like `block` or a multi-item list like `block, block, block`)
* I think I'd be ok with or without a 3rd condition that that value is the initial value.

In this combination of cases I'd be ok with an exception that the length of the list doesn't matter in that case and we should be willing to serialize the shorthand even with a length mismatch.  I'm inclined to think we should apply such an exception to both specified and computed value serialization, although maybe there's a good reason to do it only for computed?

(I think this is pretty close to what was proposed above, but I didn't pick up on all these pieces when the issue was presented in today's meeting.)

I think normally such a rule, combined with the minimal serialization principle, would imply that we should always serialize the longhand as a 1-item list... though I'd be ok with not doing that because of compatibility.
