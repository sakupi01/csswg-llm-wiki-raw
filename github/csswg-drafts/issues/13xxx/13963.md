Examining a WPT test `/scroll-animations/css/scroll-timeline-in-container-query.html`, it seems that we aren't quite aligned on this.

It seems that WebKit expects the animation to have an [inactive timeline](https://searchfox.org/firefox-main/rev/8097ef6fac6522ded33f1e2d4d521c16331be5db/testing/web-platform/tests/scroll-animations/css/scroll-timeline-in-container-query.html#68-70) until the next animation frame, but [Blink](https://wpt.fyi/results/scroll-animations/css/scroll-timeline-in-container-query.html?label=master&label=experimental&aligned&q=scroll-timeline-in-container-query.html) does not.

A potentially related question is that when a scroll timeline becomes valid, what its scroll snapshot looks like until they're updated in the Resize Observer loop - is it at (0, 0), or should it try to take the scroll position, if available?

I also derived a [testcase](https://github.com/user-attachments/files/28228099/st.html) avoiding container query, just to remove interleaving as a potential source of weirdness - Seems that we still diverge.

... I don't think spec really elaborates on this, unless I'm missing something.

## @emilio — 2026-05-25

Here's my tweaked test-case:

```html
<!DOCTYPE html>
<style>
  #outer {
    height: 100px;
    width: 150px;
  }

  #scroller {
    overflow: auto;
    width: auto;
    height: 100px;

    > div {
      height: 200px;
    }
  }

  .timeline {
    scroll-timeline: --timeline;
  }

  @keyframes recolor {
    from { background-color: rgb(100, 100, 100); }
    to { background-color: rgb(200, 200, 200); }
  }

  #element {
    height: 10px;
    width: 10px;
    animation: recolor 10s linear;
    animation-timeline: --timeline;
    background-color: rgb(0, 0, 0);
  }
</style>
<div id=outer>
  <div id=scroller>
    <div></div>
    <div id=element></div>
  </div>
</div>
<span id=result></span>
<script>
function raf() {
  return new Promise(resolve => requestAnimationFrame(() => resolve()));
}
async function go() {
  element.offsetTop;
  scroller.scrollTop = (scroller.scrollHeight - scroller.clientHeight) / 2;
  await raf();
  // Unknown timeline, time held at zero.
  const unknown = getComputedStyle(element).backgroundColor;
  // This causes the timeline to be created.
  scroller.classList.add("timeline");
  // Check value with getComputedStyle immediately, which is the same
  // value since the scroll timeline is inactive before the next frame.
  const after_create = getComputedStyle(element).backgroundColor;
  const after_create2 = getComputedStyle(element).backgroundColor;
  // Also check value after one frame.
  await raf();
  const after_raf = getComputedStyle(element).backgroundColor;
  result.textContent = `${unknown} -> ${after_create} -> ${after_create2} -> ${after_raf}`;
}
go();
</script>
```

Safari (well, WebKitGTK at least) gives different results for `after_create` and `after_create2`. That seems totally busted.
