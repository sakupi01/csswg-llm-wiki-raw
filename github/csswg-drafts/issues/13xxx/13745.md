From a code-review with @DevSDK . 

The Web Animations spec spent a lot of time unifying the 3 different animation engines we had previously. See:
https://drafts.csswg.org/web-animations-1/#use-cases

The css-image-animation spec should build off these concepts rather than creating another animation engine. E.g. while initially it may be relatively orthogonal to animations, there are some related concepts creeping in, e.g. cancelling an animation if an element loses its box or similar. The timing of these should be the same as animations, rather than introducing new bespoke timing.

## @schenney-chromium — 2026-04-14

I agree that it would be good to be as consistent with CSS Animation as is feasible. To me that means:
* Rename "stopped" -> "idle"
* Does "finished" have meaning?
* Use any attach/detach behaviors that apply.

We will have to be careful to avoid situations where seek behavior is required, or reversing. The design of animated image formats and their decoders make these things inefficient.

And we have to keep in mind the existing behavior that all instances of a given animated image play the same frame at the same time. The ability to work with this existing behavior had a significant impact on the existing design.
