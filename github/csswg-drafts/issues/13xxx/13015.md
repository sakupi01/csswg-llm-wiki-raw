It's mildly annoying that you can _invoke_ a mixin without a parameter list (`@apply --m`), but _defining_ a parameter-less mixin requires an explicitly empty list (`@mixin --m()`).

It seem more civilized to either make the parameter list optional on the defining side as well, or require `()` when applying a mixin with no parameters. 

If mixins are indeed going to gain a stronger underlying connection to custom functions (https://github.com/w3c/csswg-drafts/issues/12927), then I'd slightly prefer to just always require `()`, but I'm happy enough as long as we achieve some "symmetry" between `@apply` and `@mixin`.

<!-- comment id=3444645445 author=tabatkins created=2025-10-24T19:34:03Z url=https://github.com/w3c/csswg-drafts/issues/13015#issuecomment-3444645445 -->
## @tabatkins — 2025-10-24

I made the "arg-less calling" syntax to match what Sass can do, because it seemed nice, but you're right, Sass also lets you omit the arglist from the definition if you don't *want* any arguments. (see <https://sass-lang.com/documentation/at-rules/mixin/>)

So I'm fine with allowing the arglist to be omitted at the definition site if you want.

<!-- comment id=3478132347 author=sorvell created=2025-11-02T17:33:58Z url=https://github.com/w3c/csswg-drafts/issues/13015#issuecomment-3478132347 -->
## @sorvell — 2025-11-02

I think it's valuable to be able to describe and explain mixins as [functions that operate at the style rule level](https://www.w3.org/TR/css-mixins-1/#intro). Calling and defining them similarly helps reinforce that idea. For those with coding experience the `()` can help reinforce that this is a "call that returns a result." 

For those reasons I like the idea of consistently defining and calling mixins with `()`.

<!-- comment id=4127391913 author=LeaVerou created=2026-03-25T15:12:07Z url=https://github.com/w3c/csswg-drafts/issues/13015#issuecomment-4127391913 -->
## @LeaVerou — 2026-03-25

As I said in the call:
- I more strongly believe we should be consistent between callsites and definitions than about whether to require them in both cases or omit them in both cases
- I think in those cases the parens don't add any additional information about author intent, so they just worsen signal-to-noise ratio. It's not a strong opinion, since it's only two characters, but they also don't serve a purpose so unless there is a benefit to having them (e.g. syntactically), I suggest we make them optional.
