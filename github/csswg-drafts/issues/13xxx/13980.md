I'm splitting this issue out from https://github.com/w3c/csswg-drafts/issues/12437.

The question is whether the `::interest-button` pseudo element should be:
- opt-in (`display: none`)
- opt-out (`display: inline-block`)
- enabled by media query (`display: if(media(hover:hover): none; else: inline-block)`)

Here are the places where this has been discussed before:
- [ARIA deep dive March 5, 2026](https://www.w3.org/2026/03/05-aria-dive-minutes.html)
- [WHATWG/CSSWG/OpenUI task force April 9, 2026](https://github.com/w3c/csswg-drafts/issues/12437#issuecomment-4215452595) 
- [WHATWG/CSSWG/OpenUI task force May 28, 2026](https://github.com/w3c/csswg-drafts/issues/12437#issuecomment-4565964710)

## @mfreed7 — 2026-05-28

Based on the discussion so far, here is what I've heard as the pros/cons of each option:
- opt-in (`display: none`)
    - **Pros:** Works like all other pseudo elements. Easier to understand and easier to override. Alleviates compat and unintended layout shift issues (depending on [#13981](https://github.com/w3c/csswg-drafts/issues/13981)).
    - **Cons:** Likely to stay disabled in cases where it could have helped users.
- opt-out (`display: inline-block`)
    - **Pros:** Mostly ensures that developers "notice" and think about `::interest-button`. Possibly more accessible (needs more discussion).
    - **Cons:** Will likely result in `::interest-button {display:none}` being added to reset stylesheets making overriding this harder.
- enabled by media query (`display: if(media(hover:hover): none; else: inline-block)`)
    - **Pros:** Enabled by default where it's "needed". Not enabled where it "isn't".
    - **Cons:** Likely to go unnoticed by developers, leading to possible breakage on mobile platforms (depending on [#13981](https://github.com/w3c/csswg-drafts/issues/13981)). 

Personally, I think the decision about whether it's default-on or default-off should be based, as most "default" decisions are, on what the most common usage looks like. If in most situations, developers will choose to show `::interest-button`, then it should be **on** by default. If not, then **off** by default. If it's mostly on for touchscreen and off for desktop, then *media query*. That makes the fewest people override the default behavior.

Yeah, I 100% agree that the behavior (show or don't show) can depend on the use case. I'm less certain that the markup (e.g. `popover=hint` vs. `popover=auto`, or "rich hint" vs. "tooltip") is the determining factor. I think it's actually more about what type of information is being presented, such as how central or critical it is, and also how easy it is to get that information in other ways. I can think of plain-text tooltip examples where the information is critical, and hovercard examples where it's auxiliary. I can also think of examples of both where there are other ways to get that same information (or not). This feels like a developer decision, not a browser decision.

The TAG review (https://github.com/w3ctag/design-reviews/issues/1058#issuecomment-4602914157) mentioned that their preference is for the button to show up by default on touchscreens:

> We approve of the ::interest-button proposal to give users on touchscreen platforms a perceptible way to indicate interest. We think it's important that the proponents find a way to display this button by default on such platforms, so that the feature is accessible default. **If developers have to opt into the button, we risk reproducing the status quo where a lot of developers forget to support touchscreens.**
> 
> Showing this button by default on touchscreens has a risk of creating a cluttered and possibly confusing interface, but that seems better than making users discover a context menu option.

(emphasis theirs)

## @LeaVerou — 2026-06-12

FWIW both @una and I consider enabling this **by default** (opt in is fine) actively harmful to the Web, including to users of assistive devices, to the point I’m considering formally objecting to this resolution (which I have never done in my 14 years in this WG)

Here is a mock of what this looks like on a typical app: 

<img width="660" height="1416" alt="Image" src="https://github.com/user-attachments/assets/9396adb5-c9fb-4d81-8b16-9832d673fca4" />

In conversations at CSSDay, it was clear that everyone would turn this off.

If this ships, 100% one of these two things will happen:
1. `::interest-button { display: none }` will be part of every CSS reset
2. Authors will simply not use interest invokers.

There are several problems with doing this by default:
1. Cluttering the already limited mobile real estate is likely to read to a degraded experience for not just sighted users but also non-sighted users that rely on touch to navigate.
2. It introduces a discrepancy between tooltips created via `[title]` and tooltips created via interest invokers (since presumably we won't suddenly be adding interest buttons to those too). Especially once `::tooltip` ships, these would often be indistinguishable and it makes no sense to end users why some would have ⓘ and others not. If you just need plain text, you'd reach for a plain `::tooltip`, if you need to e.g. style some text differently, you reach for interest invokers, but it's fundamentally the same use case.
3. Often the tooltips are a shorter form of the page they lead to and if you have to do anything more involved than hovering you may as well go to the page itself. They are NOT (always) alternative content that must be accessible at all times.
4. Having a tappable `::interest-button` makes a lot of assumptions about what the non-hover interaction should be, which does not work well cross-OS. Some operating systems support additional modalities to trigger hover interactions (e.g. deep press) and this would be superfluous.
5. The tooltips are so prominent that as a sighted user, I no longer know where to tap to trigger the actual action vs the tooltip, I have to wade through the clutter to actually use the UI, and the clutter is there for things that are largely auxiliary hints.
6. This gets even worse when shadow DOM comes into the picture. If a web component author has not tested on touch, there is literally no way for consumers to fix this and remove these.
7. I've heard the argument that if they are opt-out, by removing them authors are explicitly acknowledging they have provided alternative means of accessing these. Architecturally, we should not be adding things to the platform that we explicltly expect authors to remove, and if this becomes part of CSS resets removing it is no acknowledgment anyway.

Doing it as an opt-in is totally fine. We could even include additional options about how to trigger the interest tooltip.
But in general, it should be up to the UI designer to provide an affordance that a tooltip *exists* (and the right one varies by use case, e.g. a toolbar button doesn't signify it in the same way as a link with a preview) and up to the OS to define how these are triggered (e.g. hover, long press, deep press, gaze, etc).
I wonder if a middle ground solution might be an additional attribute to indicate whether this is auxiliary or essential? And then only the essential ones get the ⓘ?

## @LeaVerou — 2026-07-22

Coming here a while after to update this with two realizations I've had in the meantime.

## Realization 1: We often want to make the element _itself_ the interest button

So far we have assumed that when an element with _both_ a command invoker and an interest invoker is displayed in media with no way to express interest, we'd want to preserve the command invoker on the element and move the interest to a separate child interest-button.

However, there are cases where the **opposite** interaction is desired: the element itself becomes the interest trigger, and the command moves to a child control.

For example, suppose there is a list of options. Hovering an option shows a preview, clicking on it applies it. Typically, the desired interaction for touch screens is not "tapping on the option still applies is, tapping on some child shows the preview". If the action is destructive enough to need a preview even on touchscreens, you'd want to make that preview the main action, and move the application to a separate button so the action is very explicit. Or, if the action isn't destructive, you just skip the preview altogether because the complexity it adds to the interaction model and UI is not worth it (not in terms of implementation complexity, in terms of cognitive overhead for the end-user).

Ideally, a good API should support both models.

## Realization 2: This needs to provide a way to integrate with regular tooltips

Whatever we decide, opt in or opt out, I'm now convinced there should be a path for adding `::interest-button` for regular tooltips. It's _incredibly_ common to show a question mark icon that shows a tooltip, and it shouldn't require interest invokers and the whole idref dance to do this for plain text.
This is actually independent of `::tooltip`, though without `::tooltip` the appeal is much lower.
