https://drafts.csswg.org/css-sizing-4/#stretch-fit-sizing

> If this is a [block axis](https://drafts.csswg.org/css-writing-modes-4/#block-axis) size, and the element is in a Block Layout [formatting context](https://drafts.csswg.org/css-display-4/#formatting-context), and the parent element does not have a [block-start](https://drafts.csswg.org/css-writing-modes-4/#block-start) [border](https://drafts.csswg.org/css-borders-4/#propdef-border) or [padding](https://drafts.csswg.org/css-box-4/#propdef-padding) and is not an [independent formatting context](https://drafts.csswg.org/css-display-4/#independent-formatting-context), treat the element’s block-start margin as zero for the purpose of calculating this size. Do the same for the [block-end](https://drafts.csswg.org/css-writing-modes-4/#block-end) margin.


In #11044 we didn't consider what happens if the block is inside an inline formatting context.

```html
<!DOCTYPE html>
<style>
section { display: inline-block }
article { width: 100px; height: 100px; margin: 25px }
.border > article { border: solid; }
.outline > article { outline: solid; }
div { margin: 25px; height: stretch; background: cyan; }
</style>
<section class="border">
  <article>
    <div></div>
  </article>
  <article>
    <span>
      <div></div>
    </span>
  </article>
  <article>
    <span style="border: solid magenta">
      <div></div>
    </span>
  </article>
</section>
<script>
let section = document.querySelector("section");
let clone = section.cloneNode(true);
clone.className = "outline";
section.after(clone);
</script>
```

The Blink behavior follows from the fact that a block-level inside an inline gets wrapped inside an anonymous block. This anonymous block is then the parent and has no border nor padding, and doesn't establish a BFC.

But it seems weird to me, because the stretch size comes from the containing block.

So if the block is inside an inline, I think we should either:
 1. Check the containing block, instead of the inline or anon-block parent
 2. Check the containing block and any inline between the containing block and the element
 3. Never treat the margins as zero

Servo used to do (1), because we split the inline, so the parent was actually the containing block. Now we no longer split inlines but we don't use anon blocks like Blink, so we do (3).

## @Loirooriol — 2026-08-03

I think that always (\*) considering margins like Servo makes more sense than always (\*) treating them as 0 like Blink.
(\*): For the purpose of finding the stretch size

But I have been thinking that ideally, the 2nd row should look like the 1st one, i.e. wrapping things inside a non-styled inline box should be no-op. It's probably fine to not check these inline ancestors for borders or such, because only the fragments before and after the block-level will have them, and they are like uncles in the fragment tree. We already agreed to ignore siblings, so ignoring uncles seems fine.
