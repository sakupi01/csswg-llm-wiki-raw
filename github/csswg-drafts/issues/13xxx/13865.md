This is stated in the definition of [`fixed <number [0,1]>`](https://drafts.csswg.org/css-values-5/#valdef-random-fixed):

  > [...] the random base value is clamped to the highest representable value less than `1` [...]

This does not look like a theoretical requirement, but I cannot find when this happens, and I do not understand why this should happen.

<!-- comment id=4662023576 author=tabatkins created=2026-06-09T16:55:43Z url=https://github.com/w3c/csswg-drafts/issues/13865#issuecomment-4662023576 -->
## @tabatkins — 2026-06-09

The standard treatment of random values produces a number in the range `[0, 1)` - it includes 0 but excludes 1. This is the case with `Math.random()` in JS, for example. But CSS (purposely) can't represent open or half-open ranges in the grammar, so I have to write the range as `[0, 1]`, but then clamp to very slightly less than 1 to get the same range as what the random generator can actually produce.

As for *when*, that's unobservable. What's clamped is not the `<number>`, but the "random base value", which is a spec-internal concept. You only see the *effects* of the random base value when the function actually resolves.

## @cdoublev — 2026-06-09

More specifically, I wanted to know what the serialization of `opacity: random(fixed 1, 0, 1)` as a declared/resolved value should be (`1` or `0.999999`), and if `fixed 1` should serialize as is if min/max/step is not resolved.

<!-- comment id=4663354096 author=tabatkins created=2026-06-09T19:35:47Z url=https://github.com/w3c/csswg-drafts/issues/13865#issuecomment-4663354096 -->
## @tabatkins — 2026-06-09

The value range is `[0, 1]` and they've specified `1`, so it can continue to serialize that way.

(It just needs to be treated as 0.9999999999999999 (the shortest string that parses to the largest double less than 1) when resolving random values.)
