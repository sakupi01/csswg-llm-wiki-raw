Hey, I'm working on Firefox's implementation of the `vertical-align` shorthand (https://bugzil.la/1830771) and associated `alignment-baseline` and `baseline-shift` properties. I had a question on the expected behavior of the shorthand.

The [/css/css-text/boundary-shaping/boundary-shaping-002.html](https://wpt.fyi/results/css/css-text/boundary-shaping/boundary-shaping-002.html) WPT is testing [this line](https://www.w3.org/TR/css-text-3/#:~:text=vertical%2Dalign%20is%20not%20baseline%2E) from css-text-3's "7.3. Shaping Across Element Boundaries":

> Text shaping must be broken at inline box boundaries when [...] vertical-align is not baseline.

I think this WPT itself was probably already wrong, because it tests the shaping break using `vertical-align: 0`, which [CSS2](https://drafts.csswg.org/css2/#ref-for-value-def-length%E2%91%A1%E2%91%A5) explicitly says is the same as `baseline`. I can fix this test during my implementation.

My primary question is about how `baseline-source` fits into this. If the css-text-3 condition of `vertical-align is not baseline` is accurate, then that means any non-initial value for `baseline-source`, `alignment-baseline`, and `baseline-shift` would break shaping. The last two are clear — a different baseline or a non-zero shift _should_ break shaping. But should a non-`auto` value of `baseline-source` do that too? I would think that if changing it to `first` or `last` would have an actual effect on text shaping, then that means it would have been broken anyway.

If `baseline-source` _shouldn't_ impact shaping, then does the css-text-3 specification need to change this `vertical-align` condition to specifically `'alignment-baseline' is not 'baseline' and 'baseline-shift' is not '0'`?

## @fantasai — 2026-08-11

I think the simplest solution here is to say “If `vertical-align` is not its [=initial value=].”

`baseline-source` can't apply to inline boxes (an inline box can't have multiple line boxes), it can only affect inline-level boxes that generate an independent formatting context, so we could make an exception to not break shaping if `baseline-source` doesn't match ... but there's no use case for applying `baseline-source` to such boxes so my suggestion is to keep it simple.

We should clarify css-inline to say that `baseline-source` doesn't apply to inline boxes, though.

## @frivoal — 2026-08-13

> I'm curious about how the "applies to" change for baseline-source is implemented in practice -- does that mean that a declaration like baseline-source: first for an inline box is invalid, or that the declaration is valid but has no effect (this is my understanding)?

Valid but no effect, at least as far as effects `baseline-source` is trying to have.

> If the latter, then is 'vertical-align' is not its initial value still ambiguous, since the specified / computed value would be the non-initial value? Maybe there's something about "used values" here, I'm not sure.

It wouldn't be ambiguous. `vertical-align` is a shorthand property, so if any of its longhands (including `baseline-source`) are not at their initial value, then `vertical-align` isn't either. So in a way, `baseline-source` does have an effect on inlines, but only indirectly. 

Arguably, it'd mildly unfortunate to break shaping due to `baseline-source` when `baseline-source` itself has no effect, but then again, since it has no effect, it's unlikely to be used in this context, and so it shouldn't really matter either way.

We probably could make an exception, but if it wouldn't make a difference in practice, why bother?
