> If any non-initial value of a property would create a stacking context on the element, specifying that property in [will-change](https://drafts.csswg.org/css-will-change/#propdef-will-change) must create a stacking context on the element.


This wording is quite ambiguous and does not specify the cases where z-index is not eligible.

Chromium appears to have changed its behavior recently: https://chromium-review.googlesource.com/c/chromium/src/+/7663578

cc @bfgeek @smfr

## @bfgeek — 2026-05-28

We were basically fixing the test added in https://github.com/servo/servo/pull/35947 

We now only create a stacking context if the element is eligible, (this is specified in other specifications).

(e.g. z-index is eligible if the element is positioned (not static), or if it is a flex/grid/etc item as per https://drafts.csswg.org/css-flexbox-2/#painting ).

cc/ @Loirooriol @tabatkins

## @tabatkins — 2026-05-28

Yes, I believe the reading from the Servo devs was the intention, but I can see how the spec is a bit ambiguous there.

So,

```css
div {
 position: static;
 will-change: z-index; 
  /* does nothing, z-index doesn't apply */
}
```

and

```css
div {
  position: absolute;
  will-change: z-index; 
  /* creates a stacking context, because some non-initial values of z-index do so */
}
```

It was definitely not the intention that we do cross-property analysis like in Simon's last example tho:

```css
div {
  position: static;
  will-change: position, z-index; 
  /* does nothing: z-index doesn't currently apply, and position never creates a stacking context
     their combo is irrelevant here */
}
```

## @Loirooriol — 2026-06-23

Checking this again, `will-change: position, z-index` must establish a stacking context, because `will-change: position` alone suffices to establish a stacking context, because of https://drafts.csswg.org/css-position/#stacking:

> [Fixed](https://drafts.csswg.org/css-position/#fixed-position) and [sticky](https://drafts.csswg.org/css-position/#sticky-position) [positioned boxes](https://drafts.csswg.org/css-position/#positioned-box) nonetheless form a [stacking context](https://drafts.csswg.org/css2/#stacking-context).

## @Loirooriol — 2026-10-01

> What does will-change: transform do if you put it on a non-transformable element?

<details><summary>Testcase</summary>

```html
<!DOCTYPE html>
<style>
span {
  background-color: green;
}
span > span {
  position: relative;
  background-color: transparent;
}
span > span::before {
  content: "";
  position: absolute;
  inset: 0;
  background: red;
  z-index: -1;
}
</style>
<span><span>control-pass</span></span>
<span><span style="isolation: isolate">control-fail</span></span>
<span><span style="will-change: transform">test</span></span>
```

</details>

In Firefox and Servo, `will-change: transform` doesn't trigger a stacking context since the element is not transformable.

In Chrome and Safari, `will-change: transform` does trigger a stacking context even if the element is not transformable.

<!-- comment id=5932426054 author=Loirooriol created=2026-10-01T13:27:04Z url=https://github.com/w3c/csswg-drafts/issues/13979#issuecomment-5932426054 -->
## @Loirooriol — 2026-10-01

Thus an example with cross-dependencies is an inline box with `will-change: display, transform`, since a change in `display` would make the element transformable.

Firefox and Servo don't track this, such an element doesn't establish a stacking context.
