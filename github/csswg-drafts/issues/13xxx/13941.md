## Summary

Consider extending the `image-animation` property to accept a `<percentage>` value
that seeks the animated image to a specific point in its playback timeline
(`0%` = first frame, `100%` = last frame).

---

## Motivation

Scroll-driven image sequences are increasingly common on the web — product showcases,
explainer animations, storytelling experiences. Currently, authors implement these by
dumping hundreds of frames as individual images and swapping them on a `<canvas>` via
JavaScript. This approach is:

- Heavy on network requests or bundle size
- Complex to implement and maintain
- Not declarative or CSS-native

Modern image formats like AVIF and WebP already support multi-frame animation.
If `image-animation` accepted a `<percentage>`, authors could convert their
video/sequence to a single animated AVIF and drive it purely with CSS using
`animation-timeline` — no JavaScript, no canvas:

```css
#element {
    animation: scrub linear both;
    animation-timeline: view();
}

@keyframes scrub {
    from { image-animation: 0%; }
    to   { image-animation: 100%; }
}
```

This composes naturally with scroll-driven animations and `animation-range`,
giving authors fine-grained control over which part of the sequence plays
at which scroll position.

---

## Proposed Syntax

Extend the value definition of `image-animation` to:

````
image-animation: normal | paused | stopped | running | <percentage>
````

Where `<percentage>` seeks the image to that progress point in its animation
timeline and holds it there (similar to a paused state at a specific frame).

- `0%` → first frame
- `100%` → last frame

**Animation type** should be changed from `discrete` to `by computed value`
for `<percentage>` values, to allow smooth interpolation between keyframes —
which is what makes the scroll-driven use case work.

---

## Open Questions

- **Frame precision** — Percentages map to time, not frame count. For images
  with variable frame durations (common in GIFs), `50%` may not land on the
  visual "middle" frame. Should the spec clarify this mapping?

- **Interpolation** — Should easing (`animation-timing-function`) apply to
  the percentage value itself, or should it always map linearly to the image
  timeline regardless?

- **Interaction with `running` / `paused`** — What happens if `image-animation`
  is switched from a `<percentage>` value to `running`? Does playback resume
  from the seeked position, or reset?

---

## Accessibility Note

A `<percentage>` value implies author/user-driven scrubbing rather than autoplay,
which aligns well with `prefers-reduced-motion` goals — the animation only advances
when the user scrolls, giving them full control over playback.

## @schenney-chromium — 2026-05-25

There's a WHATWG proposal related to adding video-like controls for animated images: See https://github.com/whatwg/html/issues/11856 and https://github.com/whatwg/html/issues/12318

The proposal here is a variant in the sense that both would enable seek-like behavior. From a spec proposal the hard part is making CSS ad HTML play together sensibly. From an implementation perspective the hard part of these proposals is supporting seek behavior efficiently in image decoders.

Since it looks like https://github.com/whatwg/html/issues/11856 is more likely to happen than not, I would support at least investigating this issue.
