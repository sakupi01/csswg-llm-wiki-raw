I discovered this issue while fixing Firefox's [Bug 489100](https://bugzilla.mozilla.org/show_bug.cgi?id=489100) for positioned elements to use containing block formed by fragmented inlines. 

CSS Positioning Level 3 currently defines [containing block formed by an inline box](https://drafts.csswg.org/css-position-3/#absolute-cb) as follows:

> the containing block is formed by forming a rectangle from the start-most content edges (in both axes) of the first box fragment of the ancestor, and the end-most content edges of the end-most box fragment(s) of the ancestor in each axis.

For non-inline box, the spec defines using "padding edges" to form containing block.

In implementations, both blink and webkit use padding edges to form the containing block rect of fragmented inline. See [this testcase](https://livedomviewer.com/?%3C!DOCTYPE%20html%3E%0A%3Cstyle%3E%0A.container%20%7B%0A%20%20display%3A%20inline-block%3B%0A%20%20line-height%3A%203%3B%0A%7D%0A.rel%20%7B%0A%20%20position%3A%20relative%3B%0A%20%20outline%3A%201px%20solid%20gray%3B%0A%20%20padding%3A%2010px%3B%0A%7D%0A.abspos%20%7B%0A%20%20position%3A%20absolute%3B%0A%20%20inset%3A%200%3B%0A%20%20background%3A%20green%3B%0A%20%20opacity%3A%200.3%3B%0A%7D%0A%3C%2Fstyle%3E%0A%0A%3Cdiv%20class%3D%22container%22%3E%0A%20%20outer%0A%20%20%3Cspan%20class%3D%22rel%22%3Econtainer%20start%0A%20%20%20%20%3Cdiv%3E%3C%2Fdiv%3E%0A%20%20%20%20container%20end%0A%20%20%20%20%3Cdiv%20class%3D%22abspos%22%3E%3C%2Fdiv%3E%0A%20%20%3C%2Fspan%3E%0A%3C%2Fdiv%3E%0A).

If this is intentional, could the spec clarify why inline box use "content edges" while non-inline box use "padding edges"? Otherwise, should inline box definition use padding edges instead of content edges, for consistency with the non-inline case and existing browser behavior?
