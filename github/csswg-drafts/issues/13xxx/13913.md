In CSS Images 4, the `image()` syntax [has been changed](https://github.com/w3c/csswg-drafts/commit/d2e87713989b0c8a99714ac68616890d9f8c2cc2) to `image(<color>)`, and other values have been moved to CSS Images 5.

One of the main use cases for `image(<color>)` is to easily overlay a solid-color mask with alpha transparency on a background image.
See also: https://stackoverflow.com/questions/9182978/semi-transparent-color-layer-over-background-image

<img width="1100" height="832" alt="Image" src="https://github.com/user-attachments/assets/6a7ab73f-4eb9-4eb1-9baa-0f3a97e2bd37" />
Screenshot from: https://12daysofweb.dev/2022/css-image/#tinting-an-image by @kevin-powell

Typically, a transition animation occurs on hover, making the UX feel more natural and fluid.

So, I suggest allowing it to interpolate based on the `<color>` type, making it look just like a `background-color` transition.
At the same time, to maintain consistency, single color stop gradients `*-gradient(<color>)` should also support interpolation.
The gradient interpolation in the specification hasn’t had time to be refined yet(https://github.com/w3c/csswg-drafts/issues/6569), so tackling solid colors first is a good place to start.

> This section needs review and improvement. In particular, I believe the handling of linear-gradient() is incomplete - I think we want to specifically interpolate the "length" of the gradient line (the distance between 0% and 100%) between the starting and ending positions explicitly, so it doesn’t grow and then shrink over a single animation.
> https://drafts.csswg.org/css-images-4/#issue-f1783900

Currently, the only way to achieve this kind of interpolation is to register a CSS custom property using `@property`, which isn't very user-friendly.

```html
data:text/html;charset=UTF-8,<!DOCTYPE html>
<style>
.test {
  width: 100px;
  height: 100px;
  display: inline-block;
  --c: green;
  transition: --c .8s;
}
@property --c {
  syntax: '<color>';
  inherits: false;
  initial-value: black;
}

.t1 {
  background: linear-gradient(var(--c));
  &:hover {
    --c: blue
  }
}

.t2 {
  background: linear-gradient(green);
  &:hover {
    background: linear-gradient(blue);
  }
}
</style>
<div class="test t1"></div>
<div class="test t2"></div>
```

-----

Given that `image(<color>)` is currently being implemented in Blink and Gecko, this is a great opportunity.
- Blink: https://chromium-review.googlesource.com/c/chromium/src/+/7831826 by @CGQAQ
- Gecko: https://phabricator.services.mozilla.com/D299322 by @emilio

## @kbabbitt — 2026-05-12

Lea's comment sent me digging, and I found a link to one of the spec versions we were referencing at the time:
https://www.w3.org/TR/2011/WD-css3-images-20110217/#interpolating-gradients
tl;dr: the two gradients must have same gradient type and same number of stops.

EdgeHTML also did not support interpolating when the gradient line was specified using a box corner (e.g. `top left`). The angle to interpolate could not be determined at computed-value time since it would depend on box dimensions.

<!-- comment id=4435158824 author=tabatkins created=2026-05-12T21:58:52Z url=https://github.com/w3c/csswg-drafts/issues/13913#issuecomment-4435158824 -->
## @tabatkins — 2026-05-12

General `<image>` interpolation (using cross-fade) should ideally catch this, but browsers haven't implemented that either, unfortunately. (I suspect we'll have to switch it on with an opt-in, like interpolating size keywords.)

But interpolating `image(<color>)` directly via interpolating the color, using *color* interpolation rules, will indeed work even better.
