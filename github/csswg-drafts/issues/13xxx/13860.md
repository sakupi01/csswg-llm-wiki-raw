## The problem

`::before` and `::after` are used in a variety of use cases:
- Decorations (e.g. ribbons, speech bubble pointers, turned pages, etc)
- UI icons
- Counters
- Connectors
- Quotes (both just textual ones, e.g. for `<q>`, as well as huge decorative ones for `<blockquote>`)
- Overlays
- [Scrims](https://medium.com/@designwithkabi/ux-drill-03-what-is-a-scrim-0b37dc1e025e)
- [Fancy shadows](https://nicolasgallagher.com/css-drop-shadows-without-images/demo/)
- Separators
- List markers without the restrictions of `::marker`
- Active tab indicator that animates when the tab changes
- Partial borders
- Selected/checked item indicators
- Change indicators
- And many other things.

It is very common to need more than two on the same element, as @chriscoyier explains in https://css-tricks.com/use-cases-for-multiple-pseudo-elements/ . We keep introducing specific pseudo-elements to address specific use cases (e.g. `::marker`, `::backdrop`, view transitions), yet the pile of use cases is only increasing.

But the main problem is that this is a **composability failure**. They are effectively a shared resource that different sources of styling (components, design systems, themes, the UA, etc) need to compete for or coordinate around. Often, it's easier to give up on them altogether. 

Worse, because these are used for such vastly different effects, **a common source of breakage is when two different sources are styling the same pseudo-element**. E.g imagine the combination of code using `::before` to add a UI icon and code using `::before` to add a scrim or a shadow. 🫠

The platform suffers from this as well: we introduce new pseudo-elements that behave *exactly* like `::before`/`::after` (e.g. `::checkmark`) simply because these are off-limits for the UA because it would undesirably clash with author styles. At first, this seems harmless: there is no real difference between `::checkmark` and `::before(ua-checkmark)` and the former is shorter/nicer!
Except, from an author's pov, until they have learned a new pseudo-element, they don't know:
- Where it sits in the tree
- What properties it accepts
- What pseudo-classes can come after it
- etc

In OO concepts, a`::before(checkmark)` is an instance of a known class, a `::checkmark` is a singleton of a new class. Separate pseudos are absolutely appropriate when the answers to these questions are different than for `::before()`/`::after()`, but we should not need to introduce new vocabulary when they aren't.



Being able to create multiple `<ident>`-keyed `::before`/`::after` would not only solve both problems, it would also open up the way for implementing many things that currently need custom elements and/or shadow DOM via plain CSS, **dramatically** reducing complexity.

It would also open up these pseudos for use by components, CSS frameworks, and the UA itself, without the risk of conflicts.

## Prior art

Multiple `::before`/`::after` have been proposed many, MANY times before, dating back to the mailing list era. 
- We even have a [wiki entry](https://wiki.csswg.org/ideas/pseudo-elements) dating from …nobody knows when, discussing `::before[n]` and stackable `::before` (e.g. `::before::before`). 
- An old (c. 2003) version of GCPM had a [4.2.2. Inserting multiple '::before' and '::after' pseudo-elements](https://www.w3.org/TR/2003/WD-css3-content-20030514/#inserting0) section discussing `::before(n)` syntax. 

A few proposals I was able to dig up are:

- [De Bastiani, 2013-03 — ::before(x) proposal](https://lists.w3.org/Archives/Public/www-style/2013Apr/0074.html) — `::before(n)`
- [Adobe's `::nth-pseudo()` proposal by @astearns and @therealglazou](https://opensource.adobe.com/css-pseudo-elements/docs/css4-pseudoelements.html) which goes beyond just multiple `::before` and `::after` but also accepted `before` and `after` but also `letter`, `line`, and `column` too.
  - [Minutes of relevant discussion](https://lists.w3.org/Archives/Public/www-style/2012Aug/0771.html)
- https://github.com/w3c/csswg-drafts/issues/6169 Proposes `::trailing(n)` but also floats the idea of `<ident>`! In that, order is determined by a `pseudo-order` property that requires cascading though.
- https://github.com/w3c/csswg-drafts/issues/11670 (declares multiple named pseudos via an HTML attribute)
- [WICG Discourse #964 — Multiple ::before and ::after pseudo elements? (2015)](https://discourse.wicg.io/t/multiple-before-and-after-pseudo-elements/964/)

Nearly all proposals revolved around numerical indices. The only one I could find that touched on idents in passing was #6169.
Thus, the common arguments against them have generally been quite specific to that approach:
1. **Cascade fragility & collisions (the z-index problem):** Indices don't eliminate the shared resource problem, they multiply it. There is no way for a certain styling source to claim a certain index for itself, since integers are by definition global.
2. **Implementation cost:** Each element gets a fixed style-data slot per pseudo today. Allowing `::before(n)` for arbitrary `n` makes that unbounded.

The hope is that this proposal completely eliminates 1 and hopefully mitigates 2.

## Strawman

Taking inspiration from `@layer`, multiple `::before`/`::after` pseudos are declared as parametrized pseudos with `<ident>`, and are all siblings.

```css
.pros > ::before(marker) {
	content: "✅";
	/* ... */
}

button::before(icon) {
	content: "";
	display: inline-block;
	height: 1cap;
	aspect-ratio: 1;
	background: currentColor;
	mask: var(--icon) no-repeat;
}

.curved shadows {
	position: relative;
	
	&::before(curved-shadows-1) {
		/* ... */
	}
	&::before(curved-shadows-2) {
		/* ... */
	}
}
```

The same pseudo-element using the same `<ident>` on the same target references the same pseudo-element and cascades normally.

`::before()` and `::after()` with no arguments would be aliases to `::before` and `::after`.

**Once this is deployed widely, un-qualified `::before` and `::after` will be seen as pseudos that only final consumers should use, and the best practice would be for all tooling and libraries to use qualified ones to prevent clashes (a bit like how layers are going).**

### UA-provided `::before`/`::after`

An explicit goal is to make `::before`/`::after` machinery available to UAs, to limit the number of new pseudo-elements we need to introduce.

Whereas from an implementation pov there is no difference between a `::foo` that behaves like a `::before` and a `::before(foo)`, there is from a human factors perspective: seeing `::before(foo)` lets the author leverage their existing mental model about how this pseudo-element works. It's a new word in an existing vocabulary. Whereas `::foo` needs to be learned separately, because you can't assume upfront that it behaves like a `::before` or that it doesn't have any limitations that `::before` doesn't. Also, it means any machinery we introduce for before/after works automatically (e.g. currently you can't really place an author `::before` before a `::checkmark` in the DOM).

So to facilitate that, UAs need to have access to a separate namespace. How do we do that?
1. Authors use `<dashed-ident>`, UAs use `<ident>`. The way we've gone in other parts of the language.
2. Reserved prefix for UAs, e.g. `ua-`.

### Ordering

Most use cases are separate enough that order doesn't matter much, so we have some flexibility in the algorithm in order to make it easier to implement. Even for the use cases where order matters, it's not a precise order that's desired, the intent is usually first, last, or around the relative order of related pseudos.

A non-negotiable seems to be **immutability**: Once determined for a given element, even if the pseudo-elements get removed (by setting their `content` to `none`), the order cannot be changed.

Determining the order via a property like `pseudo-order` (#6169) doesn't seem viable for a number of reasons (being cascade-dependent etc). Even a second argument on the `::before()` seems fraught when combined with immutability.

Instead, it seems we want some reasonable deterministic default + a way to override.
What could that reasonable default be? Some examples:
1. Parse order (not accounting for conditionals etc). Would need to follow mixins.
2. Order the pseudo-elements are actually created (which would account for conditionals etc).

Open questions TBB:
- Is this internal state or can it be changed by moving rules around via the CSSOM?
- Is the order global, per tree, or per element? Ideally, it should be possible to have different orders for different elements, but it's probably not a dealbreaker if we can't.

Authors can customize the order via a similar mechanism as the empty `@layer` rule, e.g. something like `@before-order foo, bar, baz;` or `@pseudo-order ::before foo, bar, baz;` (and if there is no `::before` or `::after` it's specifying the order for both). `default` could be reserved, so that it can represent the plain version.

Like layers, any pseudos not in the sequence would be appended at the end. For example, this:

```css
@pseudo-order foo, default, bar;

div::before(foo) {}
div::before(baz) {}
div::before(bar) {}
div::before {}
```

Would produce an order of `foo`, (default), `bar`, baz`.

@tabatkins suggested also borrowing dotted idents from layers, though I can't think of any use cases that aren't just solved by namespacing.

### Balancing

@Loirooriol brought up an interesting case below: often `::before` and `::after` are used to add decorations that should be balanced (e.g. brackets etc). Should whatever we come up with for ordering allow that?

My instinct is to say that if one of the options we consider for ordering naturally allows for that, that would be a +1, but otherwise this is out of scope for now. Yes, it's useful, but it's not in the 80% MVP. Would be good to hear what others think, though.

## Out of scope (for now)

- Enabling multiples of other pseudo-elements (e.g. `::marker`) — this is strictly about `::before` and `::after`
- Nested pseudo-elements (e.g. `::before(foo)::before(bar)` to add content to an existing generated content pseudo — useful but not MVP

Would love to hear from implementors on whether this general shape might be feasible, and if not, what would make it feasible. cc @emilio @andruud @nt1m 

## Design decisions (added on Aug 4th, 2026)

Summarizing the discussion below, it seems these are the core design decisions:
1. Can authors define defaults by just doing e.g. `::before(foo) { background: yellow }` or should we have separate syntax for that so that engines can optimize?
2. Should we use `<dashed-ident>` and reserve `<ident>` for UA things, or should we use a reserved prefix for UA things (e.g. `ua-`) or do we not want to use these for UA things, even if they function identically?
3. How do we specify order?
4. What participates in this order? Just `::before()`/`::after()` or also things like `::checkmark`, `::marker` etc?
5. What is the default order?
6. Do we do anything special for balancing pairs?

## @emilio — 2026-05-08

My gut feeling is that this would tank performance linearly with the amount of identifiers you define.

If you define 3 of these "parametric pseudos" in order, you're basically forcing the engine to resolve 6 more styles per element, for all elements.

Of course, in most cases you can just throw those styles away since they're not going to be generated, but you still need to look at whether those would match and that gets fairly annoying. Plus you might want to keep them around for invalidation?

There are optimizations possible, maybe (you match all the "::before", "::before(foo)" etc rules together and then filter during the cascade or something), but still very weird and not free.

The other potential issue is that we probably wouldn't want `::before(foo)` rules to match generic `::before` rules, but given things like `*, *::before, *::after { box-sizing: border-box }` are so common, that probably means we want `::before(*)` or so as well...

## @tabatkins — 2026-07-27

(tldr note: there's an actual proposal at the end, after my commentary)

> An explicit goal is to make ::before/::after machinery available to UAs, to limit the number of new pseudo-elements we need to introduce.

I don't think this should be a goal here. There is no meaningful difference between `::before(ua-foo)` and `::ua-foo`, except the former is longer to type (and, depending on how we define the idents, might need a reserved prefix). It would also require us to make a decision on all future pseudo-elements about whether to spell them `::ua-foo` or `::before(...)`, and if we go with the latter, that's a break from existing precedent.

I think the only benefit of this might be that it's slightly more natural to use the order-defining mechanic if they're all `::before()`? But we'd want to apply it to the existing pseudos in that case anyway, so we'd need still need to include them anyway, and we can just continue to use that for *all* the UA-defined ones without needing them to be a `::before()`.

>  But do they really need to be there for all elements? Creating them lazily when they first get a non-none content value seems like a good optimization anyway.

Emilio's talking about the cost of creating the underlying object in the style system, not the box itself. In order to *receive* styles and know that you're going to generate a box, you need to already have something set up to do the receiving, and *that* probably happens on every element. We'd probably want to do something like what Emilio suggested and bucket them all together, with their names attached to the styles in some way, and then handle cascade a little more explicitly, so we'd only have to allocate one extra "thing" per element, just with some extra effort when they *do* exist.

That said, we might still want to do some contortions to avoid encouraging authors to set these styles on *every* element, so we don't *actually* have to instantiate these objects by default.

> @tabatkins suggested also borrowing dotted idents from layers, though I can't think of any use cases that aren't just solved by namespacing.

The main thing is that it lets us naturally namespace as `::before(foo.*)` and provide consistent styles to all of the names in a particular group, plus for the ordering we can naturally group everything under a `foo.*` prefix together unless you explicitly interweave things.

> Determining the order via a property like pseudo-order (#6169) doesn't seem viable for a number of reasons (being cascade-dependent etc).

I think the idea *as expressed there* (an integer-indexed propertly a la `order`, on each pseudo-element) isn't great: it requires global index management, unlike `order`; it encourages setting a property on every element's pseudo even if you only use the pseudo for real on a few elements, meaning we have to create style objects on every element; etc.

But controlling this on a per-*element* basis, with an inheriting property, seems more reasonable. Each element can negotiate what the necessary ordering is for themselves, when it's relevant, and only needs to care about conflicts when it's actually generating multiple such pseudos. An unspecified pseudo can just use some trivial default ordering, since they mostly don't matter; ASCII-betical would work to avoid having to track and remember an appearance ordering across the stylesheet when this isn't a stylesheet-level decision.

> ::before() and ::after() with no arguments would be aliases to ::before and ::after.

I don't think this is needed. We already have a way to spell plain ::before/after; we don't need a second way to do so.

----------

I think figuring out the ordering, with some semi-realistic examples of how it would work "correctly" in a mixed components system, and combined with UA-defined pseudos, is the most important thing here. Deciding on how "reversing" works between before/after is also fairly important. If we don't get these right in the beginning, I think we'll have a very hard time fixing them in the future.

So here's my proposal:

UAs keep minting new pseudo names as normal. Authors get access to a `::before(...)`/`::after(...)` set, using dashed-ident names.

We define a specific "default" order for all of the tree-abiding before/after pseudos (including ones like ::checkbox, etc); the author-defined ones all show up in one spot in ASCII-betical order by name. The "after" list is always in reverse order of the "before" list.

Authors can override the order of these lists with a `pseudo-order` property on the originating element, which takes a list of names. UA-defined pseudos can be listed by name and intermixed, like `pseudo-order: before, --foo, checkbox;`. (Issue: decide whether the "after" list is still always the reverse of the "before" list, or if it can be overridden separately.) By default, all unspecified pseudos are put after the named ones, but you can control that by providing a `*` entry instead to indicate "all the rest". Dashed-ident names in this list can be followed by a `*` (like `--foo*`) to indicate a prefix match for multiple names at once, again only matching names not explicitly specified elsewhere. (So `--foo-1, --foo*, --foo-2` would explicitly place `--foo-1` and `--foo-2`, and put any other `--foo` names between them.)

To avoid authors/libraries setting shared default styles for their pseudos on *every* element in the page and requiring us to instantiate things up on all elements, we create a new at-rule that provides the initial styles for author-defined pseudos, cascaded at UA-stylesheet level so they're trivial to override on individual elements:

```
@pseudo-style ::before(--foo), ::after(--bar) {
	color: red;
}
```

You can similarly use `--foo*` names in the list to style anything with that prefix, or just explicitly list them comma-separated. The 'content' property is considered invalid and ignored in this rule; if authors want to make a pseudo exist on all elements they have to say so on purpose. Multiple instances of `@pseudo-style` affecting the same pseudo cascade together. (Issue: does `@layer` apply? Probably.) A specific name has higher specificity than a wildcarded name, so `--foo` styles beat `--foo*` styles; wildcarded names use the length of their prefix as their specificity, so `--foo-bar*` beats `--foo*`.

(In other words, these are `*::before(--foo) {...}` style rules, but we don't have to actually process them until/unless we see an individual element receive styles for them explicitly.)

In actual style rules, only explicit names can be used (`::before(--foo)`, but not `::before(--foo*)`), because we need to know what pseudos are actaully being referred to when you tell them to exist with `content`.

Ideally, we want to come up with a good enough heuristic that authors don't have to override it all the time.
ASCIIbetical is unlikely to ever match author intent, except by coincidence.

> Authors can override the order of these lists with a `pseudo-order` property on the originating element, which takes a list of names. UA-defined pseudos can be listed by name and intermixed, like `pseudo-order: before, --foo, checkbox;`. (Issue: decide whether the "after" list is still always the reverse of the "before" list, or if it can be overridden separately.) By default, all unspecified pseudos are put after the named ones, but you can control that by providing a `*` entry instead to indicate "all the rest". Dashed-ident names in this list can be followed by a `*` (like `--foo*`) to indicate a prefix match for multiple names at once, again only matching names not explicitly specified elsewhere. (So `--foo-1, --foo*, --foo-2` would explicitly place `--foo-1` and `--foo-2`, and put any other `--foo` names between them.)

This seems exceedingly complex and I'm worried it's solving problems that not enough authors have. 

> To avoid authors/libraries setting shared default styles for their pseudos on _every_ element in the page and requiring us to instantiate things up on all elements, we create a new at-rule that provides the initial styles for author-defined pseudos, cascaded at UA-stylesheet level so they're trivial to override on individual elements:
> 
> ```
> @pseudo-style ::before(--foo), ::after(--bar) {
> 	color: red;
> }
> ```

See arguments above about this. This violates PoC and introduces new syntax for the sole purpose of implementor convenience. There doesn't seem any author-facing benefit to this over just:

```css
::before(--foo), ::after(--bar) {
 	color: red;
}
```

If the problem is that the latter needs to go through the cascade in case `getComputedStyle()` observes it, I'd be fine with just defining that a `::before(<ident>)` effectively does not exist until `content` is set on it.
Though it would be even better for the implementation to mark relevant rules and `getComputedStyle()` to pull-resolve.

> You can similarly use `--foo*` names in the list to style anything with that prefix, or just explicitly list them comma-separated. The 'content' property is considered invalid and ignored in this rule; if authors want to make a pseudo exist on all elements they have to say so on purpose. Multiple instances of `@pseudo-style` affecting the same pseudo cascade together. (Issue: does `@layer` apply? Probably.) A specific name has higher specificity than a wildcarded name, so `--foo` styles beat `--foo*` styles; wildcarded names use the length of their prefix as their specificity, so `--foo-bar*` beats `--foo*`.
> 
> (In other words, these are `*::before(--foo) {...}` style rules, but we don't have to actually process them until/unless we see an individual element receive styles for them explicitly.)
> 
> In actual style rules, only explicit names can be used (`::before(--foo)`, but not `::before(--foo*)`), because we need to know what pseudos are actaully being referred to when you tell them to exist with `content`.

I think the entire wildcarding part should be post-MVP. I'm not convinced there are enough use cases to warrant its complexity, and it can be added after with no compat risk.
