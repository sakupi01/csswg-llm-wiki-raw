The computed value serialization of the newly added [alpha()](https://drafts.csswg.org/css-color-5/#relative-alpha) RCS function seem inconsistent, and I am not sure why they are doing what they are doing.

When `currentcolor` is not involved, the tests require that legacy color serialization is maintained.

```
test_computed_value("color", "alpha(from red / 0.5)", "rgba(255, 0, 0, 0.5)");
```

But, when `currentcolor` is involved, it seems to use color() function syntax for serialization, even though the currentColor resolves to a legacy color.

```
function test_currentcolor_alpha(specified, expected, current) {
    target.style["color"] = current;
    fuzzy_test_computed_color_property("background-color", specified, expected);
}

test_currentcolor_alpha("alpha(from currentcolor / 0.5)", "color(srgb 1 0 0 / 0.5)", "red");
```

Is there a rule I am missing that specifies one vs. another?

## @svgeesus — 2026-06-18

> My preference would be that using `alpha()` always upgrades the color to its most modern form (e.g. rgb() -> color(srgb)), like we do with the other RCS functions (including the parts about maintaining hsl()/hwb() when none is used). It's not a straight analogy, since the other RCS functions do this based on the outer function, not the origin, but I think the principle still holds.

I agree with the analogy and have just made that explicit in the spec by defining the **relative color processing space** which, for the `alpha()` form, is the color space of the origin color; otherwise, it is the color space of the relative color:

> The origin color and the relative color need not use the same color function. Thus, we define a **relative color processing space**, which is the [color space](https://drafts.csswg.org/css-color-4/#color-space) within which computation of color values takes place; this also affects the serialization of the result of the relative color.

>    For the alpha-only form, the [relative color processing space](file:///C:/Users/chris/Documents/GitHub/csswg-drafts/css-color-5/Overview.html#relative-color-processing-space) is that of the origin color.

>    For the color-affecting forms, the [relative color processing space](file:///C:/Users/chris/Documents/GitHub/csswg-drafts/css-color-5/Overview.html#relative-color-processing-space) is that of the relative color function.

I then use that term consistently while describing computation, resolution, and serialization. The table in [11.3. Serializing Relative Color Functions](https://drafts.csswg.org/css-color-5/#serial-relative-color) also uses that term, and thus we end up with the modern syntax for the serialization of the result of the `alpha()` function.

> Taking the relative color `rgb(from rgba(0, 255, 0, 0.5) r g b / alpha)` as an example,
> 
>     * Chrome calculates it as **`128/255 ≈ 0.501961`**, which is: `color(srgb 0 1 0 / 0.501961)`

I don't see anything in Color 4 or 5 that requires doing 8-bit computation on alpha values. 0.5 is clearly the correct result here.

_Edit:_ Ah, actually [Serializing alpha values](https://drafts.csswg.org/css-color-4/#serializing-alpha-values) has a historical/legacy carve-out:

> If the value is internally represented as an integer between 0 and 255 inclusive (i.e. 8-bit unsigned integer), follow these steps:

So if you are storing alpha a `uint8_t` then `0.5` will be stored as `128` which, indeed, does not have a `[0,100]` integer serialization so comes back out as a float with up to six significant figures. While if you are storing alpha as, say, a half float then you store `0.5` and get back `0.5`.

This is unfortunate for interop but we are constrained by historical behavior here.

> [@weinig](https://github.com/weinig) What is the current implementation algorithm in WebKit?

When parsing colors in WebKit, we maintain maximum precision when a color is nested inside another color. In this case, the origin color, `rgba(0, 255, 0, 0.5)` is stored as a tuple of floats `(0, 1, 0, 0.5)`.  

I am pretty sure this was required by the spec at some point, though I can't pin point it now. Perhaps, though I can't be sure, I was thinking of this text:


> When relative color syntax is used, color component values, whether directly specified or arising from color space conversion, are not clamped to the reference ranges but are retained as-is. This preserves out of gamut values, if the destination color space is capable of representing them. 
(https://drafts.csswg.org/css-color-5/#rcs-intro)

I would be in favor of updating the bit requirements to apply to both color components and alpha. I don't believe that would be a problem.

I'm also in favor of going forward and mandating a minimum or 16-bit half float per component (both color and alpha) for all non-rgb() resolved colors. WebKit uses 32-bit float per component, mostly because using 16-bit half-float is sufficiently hard to do with all supported platforms, but it is not an issue in the slightest. In practice, web pages do not specify that many color values, so the internal representation used for them is pretty inconsequential. The representation really only starts to matter for things like bitmap formats, but CSS color values don't play into that.
