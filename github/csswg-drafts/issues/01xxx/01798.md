If a inline-level box contains only characters from fallback fonts, we've got two different behaviors, plus a bug:
* Edge and Safari: size the height of the inline-level box using the metrics of the fonts actually used **plus** the metrics of the primary font, even if it is not used. I.E. they take the strut into account.
* Chrome: size the height of the inline-level box using **only** the metrics of the fonts actually used. I.E. it does not take the strut into account.
* Firefox has multiple behaviors it randomly switches between. In the test linked to above, FF does the same as chrome, but if you load the Firefox Torture test linked to bellow, it will randomly exhibit multiple behaviors as you reload the page. This is clearly a bug, but does not clearly indicate what behavior is intended.

I suggest we align with Edge & Safari.

</del>

## @frivoal — 2017-09-11

There are some behavior differences when the primary font does not contain `U+0020`.

I stumbled upon this as an artifact of how I was building my test cases, specifying very limited `unicode-range` descriptors to artificially craft fonts with a limited range to activate font fallback.

In all the test related to #1796 I ran, the presence or absence of `U+0020` in the primary font made no difference to Safari and Edge.

In most cases, it made no differences to Firefox either, except that for one case, where it triggers a clear bug: compare [this](https://rawgit.com/frivoal/web-platform-tests/line-height-experiments/css/css-line-height/line-height-007.html) with [that](https://rawgit.com/frivoal/web-platform-tests/line-height-experiments/css/css-line-height/line-height-013.html). The first test is the same as the second one, except that `U+0020` is removed (via `unicode-range`) from the primary font. Firefox will randomly exhibit multiple behaviors as you reload the page. Unstable layout is undoubtedly a bug, so I'll report this to Mozilla, but we don't need to consider it from a spec point of view.

More interestingly from a spec point of view, in Chrome, the absence of `U+0020` in the primary font  triggers a different behavior in a few cases:

---
1.

| with U+0020 | without U+0020 |
|--------------|-----------------|
| [Test source](https://github.com/frivoal/web-platform-tests/blob/line-height-experiments/css/css-line-height/line-height-003.html) <br> [Live test](https://rawgit.com/frivoal/web-platform-tests/line-height-experiments/css/css-line-height/line-height-003.html) | [Test source](https://github.com/frivoal/web-platform-tests/blob/line-height-experiments/css/css-line-height/line-height-008.html) <br> [Live test](https://rawgit.com/frivoal/web-platform-tests/line-height-experiments/css/css-line-height/line-height-008.html)|

If U+0020 is missing from the primary font, the position of the baseline in a line-box with a non-normal line-height stops depending on the primary font (and continues not to depend on any fallback font either). I am not 100% sure where Chrome take its alternative value from.

---
2.

| with U+0020 | without U+0020 |
|--------------|-----------------|
| [Test source](https://github.com/frivoal/web-platform-tests/blob/line-height-experiments/css/css-line-height/line-height-004.html) <br> [Live test](https://rawgit.com/frivoal/web-platform-tests/line-height-experiments/css/css-line-height/line-height-004.html) | [Test source](https://github.com/frivoal/web-platform-tests/blob/line-height-experiments/css/css-line-height/line-height-010.html) <br> [Live test](https://rawgit.com/frivoal/web-platform-tests/line-height-experiments/css/css-line-height/line-height-010.html)|


If U+0020 is missing from the primary font, the position of the baseline within an inline level box with the line-height:normal and in a inline-level box with the line-height property manually set to the height you'd get with line-heigh:normal (assuming only the primary font is used) are no longer the same (unlike #1801). line-height:normal sizing and baseline alignment seems unaffected, which puts the two baselines out of sync due to the previous point.

----
3. 

| with U+0020 | without U+0020 |
|--------------|-----------------|
| [Test source](https://github.com/frivoal/web-platform-tests/blob/line-height-experiments/css/css-line-height/line-height-012.html) <br> [Live test](https://rawgit.com/frivoal/web-platform-tests/line-height-experiments/css/css-line-height/line-height-012.html) | [Test source](https://github.com/frivoal/web-platform-tests/blob/line-height-experiments/css/css-line-height/line-height-006.html) <br> [Live test](https://rawgit.com/frivoal/web-platform-tests/line-height-experiments/css/css-line-height/line-height-006.html)|

In Chrome, if U+0020 is missing from the primary font, size the height of the inline-level box using **only** the metrics of the fonts actually used: in other words, Chrome does not take the strut into account in that case.

---
Fonts without U+0020 are odd corner cases, more likely found in test cases than in real sites, but it seems that authors could inadvertently fall into the same case as me when trying to use `unicode-range` to select a limited subset of characters out of a font. Anyway, It would be good to harmonize all browsers.

Is there something special in fonts / open-type about U+0020 that legitimizes Chrome's behavior, or some use case that depend on it? Otherwise, I think we should consider the Chrome behavior to be merely a bug, to be fixed by looking at some other glyph than U+0020 to figure out the metrics of the font / strut.

Safari and Edge continue to use the primary font metrics. ## @kojiishi — 2017-09-12

> 1. If U+0020 is missing from the primary font, the position of the baseline in a line-box with a non-normal line-height stops depending on the primary font (and continues not to depend on any fallback font either). I am not 100% sure where Chrome take its alternative value from.

Isn't this something we just resolved in #1765? Blink doesn't use fonts whose `unicode-range` does not contain U+0020 as the first available font. Since your test doesn't contain other fonts, it's the same as no fonts found, and Blink use the users' preferred font, or last resort system font if it's missing.

> 3. Chrome does not take the strut into account in that case.

I think the question is "the strut" of which font. Since the strut should come from the first available font, and with #1765, fonts that don't have `unicode-range` U+0020 are not the first available font, we take strut from the users' preferred font or the system font.

I haven't really understood all test cases you created yet, sorry, but does this answer your question? If you have further question, or any specific case you think it's a Blink bug, please let me know.
