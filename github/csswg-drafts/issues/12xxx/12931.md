Currently the spec suggests something like `appearance: inherit !important` for pseudo-elements, should this apply to auto and none too? I get that the idea is to make it so they can't be base when parents aren't and vice versa. But if I set the parent to auto should that prevent the pseudo being none and vice versa.

<!-- comment id=3402307778 author=nt1m created=2025-10-14T15:01:37Z url=https://github.com/w3c/csswg-drafts/issues/12931#issuecomment-3402307778 -->
## @nt1m — 2025-10-14

Yes, they should. It's not a supported configuration to mix a native control with non-native parts.

E.g. an `auto` appearance range input should not have a non-native thumb or track.

<!-- comment id=3429782940 author=lukewarlow created=2025-10-21T22:22:48Z url=https://github.com/w3c/csswg-drafts/issues/12931#issuecomment-3429782940 -->
## @lukewarlow — 2025-10-21

https://jsfiddle.net/214kr3so/4/ - at least in the case of file input this kind of mix and matching is currently allowed.


It's less consistent but even for sliders you can mix auto none for the input vs the thumb and get various different combinations.

I agree it's probably not desirable but can we be sure people aren't relying on this somehow?

<!-- comment id=3437079248 author=lukewarlow created=2025-10-23T13:40:57Z url=https://github.com/w3c/csswg-drafts/issues/12931#issuecomment-3437079248 -->
## @lukewarlow — 2025-10-23

Currently, file inputs are consistently `appearance:none` because they're "not widgets" (according to https://wpt.fyi/results/css/css-ui/appearance-auto-input-non-widget-001.html) so if we force appearance inheritance, their child buttons become appearance:none.

So we'll need to resolve that somehow?
