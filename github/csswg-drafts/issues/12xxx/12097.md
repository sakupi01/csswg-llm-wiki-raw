The current `shape()` function can use length/percentage units to create a path. This allows a lot of responsive expression.
However, the responsiveness of the shape is independent of the responsiveness of the content, which might respond to layout such as CSS grid.

I wonder if there is merit in allowing a `shape()` to respond not just to length/percent, but also to coordinates determined by layout. This can allow, for example, creating a rounded hexagon that gets its edges sized according to the content it encompasses.

(Putting this here in a very raw form to invoke thought, would add more once I've thought about this more myself).

## @noamr — 2026-06-13

An example of how this whole thing work is to allow the `anchor()` function in places like shape or gradient coordinates

```css
.guide-element {
  anchor-name: --guide;
}

.arrow {
  border-shape: shape(from 0 0, ..., 50% anchor(--guide bottom), ...)
}
```

This would be a bit of a challenge to get right as this coordinate is not relative to the shape's reference box. but that's kind of what anchor positioning does anyway...

The actual trick I am using relies on 4 elements, which I make container, then use their pseudo-element (to be able to rely on cqw/cqh).

If I have the ability to use `anchor()` (and `anchor-size()`) inside `shape()` it can help me optimize the code, and maybe at the end I might need only one element for the link.

In general, being able to use `anchor()/anchor-size()` outside the inset and size properties will also be useful for various situations. 

Take the following example:

```css
--x: sign(anchor(--c1 left) - anchor(--c2 left));
--y: sign(anchor(--c1 top) - anchor(--c2 top));
```

If we suppose the variables are registered using `@property` and we can get the value of `anchor()`, I will be able, based on the sign, to identify the 4 possible positions two elements can have in relation to each other:
