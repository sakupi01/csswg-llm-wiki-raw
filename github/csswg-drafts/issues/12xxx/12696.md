It [seems](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/style/text_decoration_thickness.h;l=38;drc=c359630af74e142163b4b978854bdaa4755cad1f) Chromium does some rounding to text decoration thickness. It's not clear to me if that rounds to CSS or device pixels, I assume the later.

The spec does say to round to the nearest device pixel: https://drafts.csswg.org/css-text-decor-4/#valdef-text-decoration-thickness-length

Someone sent a patch to do something similar in [Firefox](https://bugzilla.mozilla.org/show_bug.cgi?id=840878), but that raises the following questions:

 * At a glance, this seems similar to borders, why doesn't it use the same algorithm?

 * Should this rounding be done at computed-value time rather than used-value time like borders do? I don't feel super strongly since these don't affect layout, but worth raising.

Looking at [the code](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/paint/text_decoration_info.cc;drc=3f8932533ccf9426786d1e0416d2cad13f1c991d;l=102) Chrome behavior seems to be inconsistent. Chrome also sets a min width of 1px, apparently.

All this is at used-value time. It maybe hard to do it at computed-value time due to the font interactions and need for zoom and DPI. Currently I lean toward no change.

## @loganrosen — 2025-11-24

@schenney-chromium I dug into this further, and I think I see a bigger general issue. Chrome seems to be calculating text-decoration-thickness using CSS reference pixels (rounding up to 1px CSS) and then multiplying by the DPR before rendering. In contrast, Firefox appears to calculate the value in raw device pixel units before applying the rounding/floor.

The spec says: "The UA should round the actual value to the nearest integer device pixel, and ensure it is at least one device pixel."

However, it doesn't explicitly define at which stage this rounding should occur regarding DPR scaling. Chrome seems to enforce the "at least one pixel" floor in CSS space (resulting in a minimum of 2 physical pixels on a 2x Retina display). Firefox enforces the floor in physical device space (resulting in 1 physical pixel).

If you open [this test page](https://jsfiddle.net/wxf0zd6a/) in Firefox and Chrome on a device with a 2x HiDPI display (e.g. a Retina Mac display), you'll see that the line-through decorations are rendered with exactly twice the thickness on Chrome compared to Firefox. The ratio matching the DPR confirms this is an issue of coordinate space interpretation.

It's unclear what the "correct" behavior is here, but this seems like an interoperability issue we should address.

## @jfkthame — 2025-11-25

Well, [the spec does say](https://drafts.csswg.org/css-text-decor-4/#text-decoration-thickness) that

> Some font formats (such as OpenType) can offer information about the appropriate thickness of a line decoration. The UA should use such font-based information when choosing [auto](https://drafts.csswg.org/css-text-decor-4/#valdef-text-decoration-thickness-auto) line thicknesses wherever appropriate.

which seems to imply that `auto` should behave much like `from-font`, unless the font doesn't provide a value; but it's SHOULD rather than MUST, and doesn't clarify what "wherever appropriate" actually means. So it's not actually a requirement, more of a suggestion.

If you want to try and strengthen that language to REQUIRE more consistent treatment of `auto`, I think that should be raised as a new issue; it's independent of the rounding question being discussed here.
