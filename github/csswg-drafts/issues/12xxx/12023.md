Opening this issue to split out discussion from https://github.com/w3c/csswg-drafts/issues/11243#issuecomment-2584991716 on adjustments to shorthanding:
- Any adjustments we might need to make the `grid*` shorthands accommodate masonry features.
- Possible addition of a masonry-specific shorthand.

## @alisonmaher — 2025-08-17

In Chromium, we have a prototype of a separate `masonry` shorthand: https://developer.chrome.com/blog/masonry-update#try-masonry (enabling the Masonry feature flag is required to play with it).

Given the two-dimensional nature of Grid, the `grid` shorthand ends up being fairly confusing for Masonry, given that in masonry, we only care about one direction. Having a separate shorthand that only sets the pieces needed for masonry makes it much clearer what you are setting, and I found in writing tests, leads to less opportunity for error, which I suspect will be the case for authors, as well.

## @fantasai — 2025-12-17

There seem to be two proposals here (from discussions in other issues). In both cases, they reset all the `grid` sub-properties and also set the orientation control (TBD), the `grid-template-rows/columns` property in the appropriate axis, and the `grid-template-areas` property with a syntax transformation to make it work in the appropriate axis.

**Dedicated shorthand**
```
grid-lanes: <track-listing> || <string>+ || <'grid-lanes-direction'>;
```

The `grid-lanes-direction` value indicates whether we are setting up rows or columns.

**Re-use grid shorthand**

```
grid: [ rows | columns ] <track-listing> || <string>+ || <'grid-auto-flow'>;
```

The `rows` or `columns` keyword indicates whether we are setting up rows or columns.

**Examples**

```
/* two rows, 100px and 200px */
grid-lanes: row 100px 200px;
grid: rows 100px 200px;

/* two columns, 100px named "narrow" and 200px named "wide" */
grid-lanes: 100px 200px "narrow" "wide";
grid: columns 100px 200px "narrow" "wide";

/* two columns, 100px named "narrow" and 200px named "wide", auto-placed right-to-left */
grid-lanes: fill-reverse 100px 200px;
grid: columns 100px 200px row-reverse; /* or fill-reverse, if we decide on that */
```

## @alisonmaher — 2026-01-05

I mentioned this in the call but wanted to add this point to this issue, as well, to make sure it is properly tracked.

For the proposal of `grid: [ rows | columns ] <track-listing> || <string>+ || <'grid-auto-flow'>;`, one major downside is that one part of the shorthand could override another part of the shorthand in the same declaration. I'm not sure there is precendence for this, and it seems like a fairly strange side effect.

More explicitly, if an author sets `grid: rows 100px 100px row-reverse` you'd end up with column tracks instead of rows (even though the author specified `rows` at the beginning of the statement) because `row-reverse`, per this proposal, would be a column layout. As such, `grid-auto-flow`, if specified by the author in the shorthand, always wins, no matter what `[rows | columns]` is set at the beginning.

Even though this is a separate issue from https://github.com/w3c/csswg-drafts/issues/12803, this side effect is another major reason why I believe we should be adding separate properties for grid-lanes in both issues so that we can create properties that are easier to reason about and make sense within the single axis layout model of grid lanes.

## @alisonmaher — 2026-01-06

One clarification on both of these shorthand proposals: if the directional property is set to `normal`, what happens?

For example, if we had `grid-lanes: 100px 100px normal;` I assume this will set `grid-template-columns: 100px 100px;`

But what if we had:
```
.container {
   display: grid-lanes;
   grid-template-rows: 90px;
   ...
   grid-lanes: 100px 100px normal;
}
```
Would we look at any other templating properties set before this and override rows instead of columns, or will we just assume if set on the shorthand, `normal` means columns? I presume it will always imply column, but want to double check.

## @fantasai — 2026-07-29

@alisonmaher and I discussed this topic a bit, and we would like to propose that both `grid` and any possible `grid-lanes` shorthand we add will reset all the properties currently reset by `grid` as well as any possible `grid-lanes-direction`-type properties. If we end up with two different flow-control properties, whatever the shorthand syntax ends up being, both will get set to matching values (i.e. both will create a "waterfall" layout or both will create a "brick" layout). No longhand left behind, etc. ;)
