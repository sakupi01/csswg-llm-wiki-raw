[CSS Break 3](https://www.w3.org/TR/css-break-3/) says, in [5.3. Splitting Boxes](https://www.w3.org/TR/css-break-3/#box-splitting), that when a box gets split, it's block size is effectively increased. This leads to its backgrounds and borders being painted into the remaining empty space in that fragmentainer.

This usually seems desirable, but it gets ugly when a table cell with the `rowspan` attribute gets broken due to the rows that it spans falling into different fragmentainers. In this case, the empty space that comes to exist between those rows has nothing in it, apart from the `rowspan`-cell, which I'd expect to only render next to the rows that it spans.

I think there should either be an exception for these cells, or a CSS property that can control this behavior, similar to `box-decoration-break`. Alternatively, `box-decoration-break` could be extended to accept something like `[ slice | clone ] || skip-gap` instead of just `slice | clone`. This new behavior should, in my opinion, be applied to rowspan cells by default, so this could be added to the UA stylesheet:
```css
td[rowspan], th[rowspan] {
    box-decoration-break: skip-gap;
}
```
The UA stylesheet addition would be a breaking change, though currently only Safari manages to properly break these cells at all. Both Chrome and Firefox fail to lay them out correctly in different ways. (Chrome doesn't extend the height on the rowspanned cell so it doesn't reach the end of the second row and Firefox draws the background only inside the first fragmentainer and only next to the first row.)

Yes, pretty much. Though I think "breaking the (visual) box" of something is not yet a concept that exists in the spec.
[5.3.](https://www.w3.org/TR/css-break-3/#box-splitting) says that any break causes a box to grow taller, to fill the rest of its fragmentainer. So just forcing a regular break into rowspanned cells would still result in the "Current" case from my drawing above. The sort of break inserted here would need to not stretch the box out to fill the rest of the fragmentainer.

Also, if [`box-decoration-break`](https://www.w3.org/TR/css-break-3/#propdef-box-decoration-break) is set to [`clone`](https://www.w3.org/TR/css-break-3/#valdef-box-decoration-break-clone), the break would need to be inserted above the end of the row, to leave space for the bottom padding and margins and such.

I've written up some spec text that I hope does a good job at defining behavior that can accomplish this: https://github.com/w3c/csswg-drafts/pull/12805

## @alisonmaher — 2026-06-17

> If the item has a border that will be open on the fragmented side, you'll still see it be incomplete.

Sure, although that isn't guaranteed. Also, if a table or grid is inside another container whose height relies on its items to size itself, and we break the grid or table container after row 1, (such that it doesn't continue to the end of the fragmentainer), the container will get back that shorter size as its block size, and will also end earlier in the container. This can propagate up multiple layers, and if any of those layers doesn't have a border, then that layer will look complete before it really is.

Also, I think this proposal would break the following part for the [spec](https://drafts.csswg.org/css-break/#box-splitting):

> "When a box breaks, its content box extends to fill any [remaining fragmentainer extent](https://drafts.csswg.org/css-break/#remaining-fragmentainer-extent) (leaving room for any margins/borders/padding applied by [box-decoration-break: clone](https://drafts.csswg.org/css-break/#propdef-box-decoration-break)) before the content resumes on the next [fragmentainer](https://drafts.csswg.org/css-break/#fragmentainer). (A [fragmentation break](https://drafts.csswg.org/css-break/#fragmentation-break) that pushes content to the next fragmentainer effectively increases the [block size](https://drafts.csswg.org/css-writing-modes-4/#block-size) of a box’s contents.)" 

 As well as the spec note:
> "The extra [block size](https://drafts.csswg.org/css-writing-modes-4/#block-size) contributed by fragmenting the box (i.e. the distance from the break point to the edge of the [fragmentainer](https://drafts.csswg.org/css-break/#fragmentainer)) contributes progress towards any specified limits on the box’s block size."
