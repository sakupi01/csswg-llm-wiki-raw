The current [grammar for CSS @namespace rules](https://drafts.csswg.org/css-namespaces/#syntax) is:

```
@namespace <namespace-prefix>? [ <string> | <url> ] ;
```

Since it uses the [`<url>`](https://www.w3.org/TR/css-values-4/#urls) production, that means any URL modifiers defined, such as the [request modifiers](https://drafts.csswg.org/css-values-5/#request-url-modifiers) in CSS Values 5 should also parse.

I don't think it's meaningful for `@namespace` to have request modifiers (though I may be mistaken). I propose adding some way for specifications like `@namespace` to parse only the URL itself.

(cc @noamr, @annevk, @tabatkins, @fantasai)

## @weinig — 2025-04-16

Since [<url()>](https://www.w3.org/TR/css-values-4/#funcdef-url) includes the modifiers, I think you probably want this:

```
@namespace <namespace-prefix>? [ <string> | <url-token> | url( <string> ) ] ;
```

## @tabatkins — 2025-06-30

I think the specific edits should just be `<url()>`, with accompanying prose saying that any and all arguments beyond the initial URL string make it invalid. We can't actually express a "just plain url()" in grammar, as `url()` is not parsed as a normal function, for annoying legacy reasons.

But yeah, the intention of the edit is definitely correct. XML Namespaces are terrible and we should limit our ability to make them more confusing.

Edit: Ugh, wait, right, I changed `url()` parsing years ago to make it a normal function *if* you pass a `<string>` as the first arg. So then yeah, Noam's suggested syntax works just fine, tho I'd also pair it with a note explaining why the grammar is written that way (to intentionally exclude any URL modifiers).
