There's been recent discussions surrounding `::file-selector-button` and the fact it's exposed in appearance: auto and how that's not necessarily desirable.

Should we update CSS forms to restrict all new pseudo-elements to just elements in base appearance mode?

We'd probably have to explicitly allow `::file-selector-button` and `::placeholder` to break that rule as they're pre-existing.

The spec already limits `::checkmark` and `::picker-icon` to just base appearance mode.

cc @nt1m @annevk

Ah I was mostly thinking of the appearance: auto case. Should we perhaps exclude these from matching in appearance: auto?

Though I agree the password reveal one is a case where that doesn't apply.

One downside to applying the pseudo elements in auto mode is we either have to prescribe limitations to them when in auto mode (such as not being an element backed pseudo element if that's even possible to do conditionally) or we have to specify that browsers implement auto mode in a specific way?

<!-- comment id=3385758863 author=lukewarlow created=2025-10-09T12:59:29Z url=https://github.com/w3c/csswg-drafts/issues/12365#issuecomment-3385758863 -->
## @lukewarlow — 2025-10-09

Following-up here perhaps disallowing them isn't the best approach. Perhaps we should just specify that in appearance:auto mode the browser can only expose the standard pseudo element if it matches how it behaves in base mode?

I do think you still have the issue where we might want them to be element backed which might be too prescriptive for auto mode.

I know @annevk had reservations about that.

I think given we've agreed that `::reveal-icon` is okay in auto mode perhaps we should just leave it up to browsers what they do?

<!-- comment id=3385844452 author=annevk created=2025-10-09T13:20:00Z url=https://github.com/w3c/csswg-drafts/issues/12365#issuecomment-3385844452 -->
## @annevk — 2025-10-09

In general I have strong reservations about element-backed pseudo-elements for built-in elements as it tends to expose what-should-be implementations details, such as what element type is being used for backing. Which then can result in duplicate API surface through pseudo-classes and other unfortunate side effects.

For `appearance: auto` specifically probably the ship has sailed for a number of pseudo-elements, but generally it seems better if we all aim for not letting pseudo-elements influence the final result as that is likely to interfere with native styling and could result in all kinds of subtle interoperability issues if this is handled differently across user agents.
