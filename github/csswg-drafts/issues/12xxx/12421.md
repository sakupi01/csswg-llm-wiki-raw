https://quirks.spec.whatwg.org/#the-percentage-height-calculation-quirk

> In [quirks mode](https://dom.spec.whatwg.org/#concept-document-quirks), for the purpose of calculating the [height](https://drafts.csswg.org/css-sizing-3/#propdef-height) of an element element, if [...] the specified value for the [height](https://drafts.csswg.org/css-sizing-3/#propdef-height) property of element is a [`<percentage>`](https://drafts.csswg.org/css-values-4/#percentage-value) [...] the [containing block](https://drafts.csswg.org/css-display-4/#containing-block) of element must be calculated using the following algorithm

It only mentions `<percentage>`, but this was written before CSS Sizing introduced `stretch`.

Arguably, as per https://drafts.csswg.org/css-sizing-4/#stretch-fit-sizing

> - Otherwise, if used in an axis where percentage sizes can resolve to a [definite](https://drafts.csswg.org/css-sizing-3/#definite) value
>     Behaves as 100%, except it sizes the [margin box](https://drafts.csswg.org/css-box-4/#margin-box) regardless of the value of [box-sizing](https://drafts.csswg.org/css-sizing-3/#propdef-box-sizing).

if `100%` would have the quirk, `stretch` should also have it?

Browsers don't agree: Blink and WebKit apply the quirk for `stretch` / `-webkit-fill-available`, while Firefox doesn't for `-moz-available`.

```html
<!-- quirks -->
<div style="height: -moz-available; height: -webkit-fill-available; height: stretch; background: cyan">foo</div>
```

## @bfgeek — 2025-07-01

The testcase you have isn't actually the percentage height quirk rather:
https://quirks.spec.whatwg.org/#the-body-element-fills-the-html-element-quirk

Basically the <body> element fills the ICB, and then the element stretches to that definite height.

(That quirk is as-if html & body have height:stretch by default - kinda).

A better test would be:
```
<!-- quirks -->
<div>
  <div style="height: -moz-available; height: -webkit-fill-available; height: stretch; background: cyan">foo</div>
</div>
```

And blink doesn't stretch.

## @Loirooriol — 2026-10-16

I see what you meant now. But I don't think it's comparable. For float avoidance or inset-modified CB, this available size different than the cb size can be computed locally, doesn't need extra information from ancestors. But if `stretch` and percentages resolve against different ancestors, it means that all over layout I need to pass the 2 values down to the contents, it's not enough with just the containing block. This needs to happen for intrinsic sizing, actual layout, needs to be tracked as an input for layout caching, etc. And then it will usually be useless, because modern pages using `stretch` are likely not in quirks mode. So the complexity doesn't seem worth it to me.

<!-- comment id=6220238543 author=bfgeek created=2026-10-16T16:42:20Z url=https://github.com/w3c/csswg-drafts/issues/12421#issuecomment-6220238543 -->
## @bfgeek — 2026-10-16

A few things:
1. You'll already need to support things resolving against two different ancestors, specifically for replaced elements - see https://www.software.hixie.ch/utilities/js/live-dom-viewer/?saved=14917
2. You don't actually need two different sizes, just a "does stretch resolve" boolean, and the size to resolve percentages against. I'm well aware of the information you need to pass around :) this isn't a servo specific constraint.

Finally I don't want to support this as I don't want to extend the -webkit-fill-available quirk. E.g. Blink has successfully shipped aliasing -webkit-fill-available as stretch, however WebKit hasn't for reasons that are too long to get into here. If developers find out they can get "-webkit-fill-available" everywhere just by invoking quirks mode, this will be a very bad thing IMO.
