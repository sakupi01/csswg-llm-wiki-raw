The [HTML Processing Model: Event loop section of the Scroll-driven Animations spec](https://drafts.csswg.org/scroll-animations-1/#event-loop) discusses how scroll and view timelines may become stale in the process of updating the rendering since timeline sources or subjects may change bounds during that process.

However, the spec does not reference the HTML spec with hard links and rather references sections which are by now outdated. For instance (at the time of writing this issue), the step to update animations and send events is step 11 and the current spec references step 10. As such it is not clear exactly when in the process of updating the page rendering stale timelines should be updated. Using informative notes, it appears it is after resize observers have been evaluated and styles have been recalculated and layout updated.

We should probably update the HTML spec itself to add a step that clearly references the process of updating stale timelines.

Here are related spec issues and spec change:

- [[scroll-animations] Behavior of scroll-linked animations in the first frame](https://github.com/w3c/csswg-drafts/issues/5261)
- [[scroll-animations-1] Handling changed size/position in current frame](https://github.com/w3c/csswg-drafts/issues/8694)
- [additional spec change](https://github.com/w3c/csswg-drafts/pull/8704)

Cc @flackr who made the spec change as well as @kevers-google and @andruud who reviewed it.

## @flackr — 2026-09-29

The spec attempts to have two locations where the timelines update.

1. Before updating animations so that animations can update with the correct time. Once an animation is created, in the absence of other changes to the DOM this allows scroll driven animations to update without requiring re-running style and layout. This is technically based on a stale rendering state which does not account for changes to the document. It is an optimization for the common case for when just the scroll offset is changing.

   > a [scroll progress timeline](https://drafts.csswg.org/scroll-animations-1/#scroll-progress-timelines) update their current time once during step 7.10 of the [HTML Processing Model](https://html.spec.whatwg.org/multipage/webappapis.html#processing-model-8) event loop, as step 1 of [update animations and send events](https://drafts.csswg.org/web-animations-1/#update-animations-and-send-events).

2. After layout and ResizeObserver changes as the last condition for rerunning style and layout when the recorded state no longer matches the current state. This allows animations to get the correct time for the first frame.

   > During step 7.14.1 of the [HTML Processing Model](https://html.spec.whatwg.org/multipage/webappapis.html#processing-model-8), any created [scroll progress timelines](https://drafts.csswg.org/scroll-animations-1/#scroll-progress-timelines) or [view progress timelines](https://drafts.csswg.org/scroll-animations-1/#view-progress-timelines) are collected into a stale timelines set. After step 7.14 if any timelines' [named timeline ranges](https://drafts.csswg.org/scroll-animations-1/#named-timeline-range) have changed, these timelines are added to the [stale timelines](https://drafts.csswg.org/scroll-animations-1/#stale-timelines) set. If there are any stale timelines, they now update their current time and associated ranges, the set of stale timelines is cleared and we run an additional step to recalculate styles and update layout.

We should of course update the related specs so that they aren't stale references.

## @flackr — 2026-10-01

So the issue with the failing test [scroll-timeline-invalidation.html](https://github.com/web-platform-tests/wpt/blob/master/scroll-animations/scroll-timelines/scroll-timeline-invalidation.html) is the following:

```js
promise_test(async t => {
  ...
  const animation = new Animation(
    new KeyframeEffect(
      timeline.source.firstChild,
      [{ height: '1000px', easing: 'steps(2, jump-none)'},
       { height: '2000px' }],
    ), timeline);
  ...
  await runAndWaitForFrameUpdate(() => {
    scroller.scrollTop = 0.6 * maxScroll;
  });
```

The function `runAndWaitForFrameUpdate` runs the callback function on the next requestAnimationFrame. This means the scrollTop update happens at the start of the next frame. During the post layout snapshot check we determine that the state has changed, update the time and allow it to run again. When we enter the next requestionAnimationFrame nothing is dirty anymore and thus the assertion fails:

```js
  // runAndWaitForFrameUpdate will yield after the requestAnimationFrame callbacks
  // have been serviced, which is prior to when stale timelines are updated.
  // https://github.com/w3c/csswg-drafts/issues/12120
  assert_approx_equals(timeline.currentTime.value, 60, 0.1);
  ...
}, 'If scroll animation resizes its scroll timeline scroller, ' +
   'layout reruns once per frame.');
```

This seems to be an interop issue that we should resolve on the expected behavior for. However, we could also test the core issue by swapping the initial await for a setTimeout which would result in the scroll change happening outside of a lifecycle update, i.e.

```js
  await new Promise(setTimeout);
  scroller.scrollTop = 0.6 * maxScroll;
  await waitForNextFrame();
  assert_approx_equals(timeline.currentTime.value, 60, 0.1);
```
