The [cssom-view-1](https://drafts.csswg.org/cssom-view/) spec currently specifies both scrollTo and scrollBy as if they both invoke the scroll method with the left and top set accordingly. However, I think that we should differentiate these APIs as relative directional scrolls and absolute scrolls as far as they affect several other APIs. The legacy `scrollLeft` and `scrollTop` should probably be treated as absolute scrolls as that is usually what they are used for.

Absolute scrolls:
* If interrupting an ongoing scroll, use the specified offset exactly.
* Are treated as [intended end position scrolls](https://www.w3.org/TR/css-scroll-snap-1/#intended-end-position) by scroll snap: https://www.w3.org/TR/css-scroll-snap-1/#scroll-types
* Don't set the last scroll direction for state queries #6400

Relative / directional scrolls:
* If interrupting an ongoing scroll, add their relative offset to the interrupted scroll position. E.g. `scrollBy(0, 10)` scroll always scroll 10px down rather than potentially scrolling up if there was an ongoing fling scroll.
* Are treated as [intended direction and end position](https://www.w3.org/TR/css-scroll-snap-1/#intended-direction-and-end-position) by scroll snap: https://www.w3.org/TR/css-scroll-snap-1/#scroll-types
* Change the last scroll direction for state queries #6400

Proposed resolution:
Define a consistent distinction between absolute scrolls and relative scrolls that can be implemented and shared across these affected specs.
Absolute scrolls: scrollTo, scrollLeft, scrollTop, scrollIntoView, anchor fragment scrolls, scroll anchoring, find in page scrolls, focus scroll into view, scroll thumb dragging?
Relative scrolls: scrollBy, arrow key, page up/down, spacebar, home/end?, scrollbar track clicks, scrollbar buttons

Any other ways of scrolling we need to categorize?

FYI - scroll anchoring and clamping have "relative" behavior with respect to ongoing scrolls (see [ScrollAnimator::AdjustAnimation](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/scroll/scrollable_area.cc;l=352;drc=6ef235e211f9d0e6f493d65570859fef5e9d54f0)), but they probably should _not_ set the last scroll direction for state queries. So this feels like a third category (browser-triggered scrolls?)

<!-- comment id=3137997715 author=tabatkins created=2025-07-30T22:21:13Z url=https://github.com/w3c/csswg-drafts/issues/12394#issuecomment-3137997715 -->
## @tabatkins — 2025-07-30

Yeah, "relative" isn't the term for that category; it's "directional" that you want. Scroll anchoring/clamping maybe lack both directionality and position, in the way [Scroll Snap defines those terms](https://www.w3.org/TR/css-scroll-snap-1/#scroll-types), so we could make a fourth category explicit there of scrolls that, while they adjust scroll offsets, are designed to maintain a "stasis" rather than actually do a scroll.

## @flackr — 2025-08-05

> we could make a fourth category

How did we get to fourth?

I think scroll anchoring probably is a third category of effectively non-scrolling or internal scrolling, as @tabatkins mentioned it's not really meant to be noticed by the user as a scroll. Alternately we could leave it as a special case and call out that it has elements of relative (combines with ongoing scrolls without interrupting) and absolute (doesn't infer last direction, and while it usually shouldn't change snap selection when it does we would use the absolute strategy rather than relative).

## @tabatkins — 2025-08-05

There's three categories in the spec! Directional, positional, and direction+positional. Flings are the third, as they have a direction and a desired endpoint, while arrow keys are just directional.

## @flackr — 2025-08-05

> There's three categories in the spec! Directional, positional, and direction+positional. Flings are the third, as they have a direction and a desired endpoint, while arrow keys are just directional.

Ah right. I recently refactored this code as `directional` and `directional + positional` was practically the same case, to make them the same case with a few additional args set when doing a fling or paging operation. Semantically a fling or page down operation is not an absolute position at all it is just directional with some minimum / expected displacements - but it is notably *not* an expected endpoint, it is still a relative distance from the start.

<!-- comment id=3179606268 author=flackr created=2025-08-12T14:30:43Z url=https://github.com/w3c/csswg-drafts/issues/12394#issuecomment-3179606268 -->
## @flackr — 2025-08-12

So I propose that for simplicity, we have three categories:
* Absolute target scrolls
* Directional scrolls (can have preferred displacement to handle fling / paging).
* Stationary scrolls (special case for anchor positioning, and potentially other future cases where we technically change offset but don't mean to actually visually scroll).
