Some properties require `<dashed-idents>`, for example `scroll-timeline-name`. So e.g. `scroll-timeline-name:nondash` would be invalid at parse-time. However, with the `ident()` function, we'll no longer be able to reject those values parse-time: `scroll-timeline-name:ident(var(--maybe-dashes-maybe-not) "mytimeline")`.

I guess we have two choices:

 - Allow `ident()` to bypass the dashed requirement, making `scroll-timeline-name:ident(timeline)` actually a define a timeline named `timeline`. (In order for the timeline to be reachable, the name would have to be "escaped" with `ident()` on the `animation-timeline` side as well).
 - Enforce the dashed requirement computed value time instead.

## @andruud — 2025-05-23

> Weird that it requires us to detect a troublesome custom ident and serialize it back out with an `ident()` wrapper, tho, especially since "troublesome" varies by usage site. I suspect we'd screw that up and end up generating serializations that don't round-trip.

Yeah, that's indeed an issue. We get roughly the same problem with the IACVT approach, since we need to figure out if an `ident()` produces something valid or not. I would expect the IACVT approach to be harder to do, but both should be possible.

> Stepping back, tho, your example is _already_ not parseable at parse time due to the use of `var()`; the `ident()` has nothing to do with this. A simple `scroll-timeline-name: var(--foo)` already troublesome. Are there any cases where we can trigger this "can't determine at parse time" that don't rely on an arbitrary-substitution function?

Riiight, so we could, for example, "mock"-evaluate the `ident()` at parse-time, using a placeholder value (`0`) for any integer part, and reject anything that doesn't meet the local requirements. That would make it possible to drop e.g. `scroll-timeline-name: ident(ident("myname" sibling-index()))`, since `myname0` doesn't start with dashes. `--myname:myname; scroll-timeline-name: ident(ident(var(--myname) sibling-index()))` would then automatically be IACVT by the mechanisms we already have.

This works until we spec a regular function that returns a string/ident that can't be known at parse-time: we won't be able to check that `container-name:ident(some-string())` doesn't yield `none`, for example.

## @LeaVerou — 2026-03-04

I don't think `ident()` should be privileged compered to verbatim idents, the whole idea is that it behaves identically. Implementations should not have to care where the ident came from, and whether an `ident()` was used to construct it.

First, the unknown is due to a variable, we already have established rules about how that resolves, so we should focus this issue around checking when we *don't* have a variable, such as the example where `ident(ident("myname" sibling-index()))` is used somewhere where only a `<dashed-ident>` is allowed. Conceptually, this should be always be detectable at parse time.

I think the mock eval makes sense, but it's a bit awkward and I'd rather not encode it in the spec. Perhaps the normative text could be more high-level, leaving UAs flexibility about _how_ they do the checking. Perhaps the mock-eval idea by @andruud could be a non-normative note or something.

One trickier case is if you have a non-ASF function that may or may not satisfy a `<dashed-ident>`, e.g. a `counter()` with a custom counter-style that increments by adding hyphens:

```css
@counter-style hyphens {
  system: additive;
  additive-symbols: 1 "-";
  fallback: decimal;
}
```

Then whether `ident(counter(foo) "foo")` is a `<dashed-ident>` depends on the counter value 😀

Edit: Actually counters resolve later so that's not a problem for this issue.

## @sakupi01 — 2026-06-19

Looking at @cdoublev 's point, I agree that the current "mock zero" resolution introduces some unintended side effects. Because CSS identifiers are sensitive to hyphens, treating a negative integer as "0" at parse time breaks validation logic in both false negative and false positive ways.

Regarding false positives, as @cdoublev mentioned, a valid syntax like `scroll-timeline-name: ident("-" -1);` evaluates to "-0" at parse-time and gets rejected, even though it could correctly resolve to `"--1"` at computed-time. Therefore, it is incorrectly rejected due to this parse-time resolution.

Regarding false negatives, an invalid syntax like `view-transition-type: ident("-ua" -2 "-name");` evaluates to "-ua0-name" at parse-time, which bypasses the "-ua-" prefix check. This means an author could successfully generate a restricted UA name at computed-value time, leading to IACVT. I believe this is not what developers want.

If I understand correctly, the mock algorithm treats a dynamic `<integer>` as a flat, sign-less string "0" character, ignoring the fact that CSS numbers carry operators (+ or -) that alter the syntactic structure of an identifier (e.g., injecting a hyphen that changes the prefix context or word boundaries).

To generalize, what we actually want to achieve is syntactic predictability at parse-time. 
Based on this, instead of simply concatenating with '0',

* If the first argument `A` is an `<ident>` or `<string>`:
  * It must either explicitly start with the property's required prefix (e.g., `"--"` for `<dashed-ident>`), or `A` must be exactly `"-"` while the second argument `B` is a negative integer, a math function, or any expression that could potentially yield a negative value.
* If the first argument `A` is an `<integer>`:
  * Since CSS identifiers cannot start with a digit, any `ident()` beginning with a numeric token should be treated as fundamentally invalid at parse-time for both standard identifiers and `<dashed-ident>` contexts.

Looking further ahead, as @cdoublev suggested, simply banning `<integer>` as the first argument from the start would be a great solution for syntactic predictability at parse-time.
