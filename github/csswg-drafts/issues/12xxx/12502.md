The topic of allowing authors custom selectors has come up periodically, but we have no concrete proposal yet.

For custom elements, JS can define arbitrary states that can be matched through the [`:state()` pseudo-class](https://html.spec.whatwg.org/multipage/semantics-other.html#selector-custom). I just [proposed](https://github.com/whatwg/html/issues/11466) expanding `:state()` to regular elements as well (through a similar JS API).

However, being able to assign states declaratively through CSS is strictly more powerful and feeds multiple birds with one scone.

## Custom element use cases

### Simplification of custom state management code

Currently, custom states must be applied and removed imperatively, with all the DX issues that this implies.
However, many (possibly even most) custom states are simply an abstraction over existing light and shadow DOM selectors. 

This effectively forces authors to re-implement the UA's selector invalidation, and (especially in the absence of primitives to monitor selector invalidation) invites errors.

<details><summary>Example</summary>

```js
class MyCheckbox extends HTMLElement {
	#checkbox;
	constructor() {
		super();

		this.attachShadow({mode: "open"});
		this.#checkbox = Object.assign(document.createElement("input"), {type: "checkbox", id: "checkbox"});
		this.shadowRoot.append(this.#checkbox);
		
		this.addEventListener("input", ({target}) => {
			if (target === this.#checkbox) this.#toggleState("checked", this.#checkbox.checked);
		});
		
	}
	connectedCallback () {
		this.#toggleState("checked", this.#checkbox.checked);
		this.#toggleState("disabled", this.#checkbox.disabled);
	}

	attributeChangedCallback (name, value, oldValue) {
		this.#checkbox.setAttribute(name, value);

		// Oops, did not account for being inside a disabled form/fieldset!
		if (name === "disabled") this.#toggleState("disabled", this.#checkbox.disabled);
		else if (name === "checked") this.#toggleState("disabled", this.#checkbox.checked);
	}

	#toggleState (name, force = this._internals.states.has(name)) {
		if (force) this._internals.states.add(name);
		else this._internals.states.delete(name);
	}

	get checked () { return this.#checkbox.checked }
	set checked (v) { 
		this.#checkbox.checked = v; 
		this.#toggleState("checked", this.#checkbox.checked); 
	}

	get disabled () { return this.#checkbox.disabled }
	set disabled (v) {
		this.#checkbox.checked = v; 
		this.#toggleState("disabled", this.#checkbox.disabled); 
	}
}
```

Most of this code is mapping `:checked` and `:disabled` on the shadow DOM element to `:state(checked)` and `:state(disabled)` on the host, in a buggier way than if author intent could be expressed clearly, e.g. through something like:

```css
@state checked {
	matches: :host:has(#checkbox:checked)
}

@state disabled {
	matches: :host:has(#checkbox:disabled)
}
```

Then the JS collapses down to:


```js
class MyCheckbox extends HTMLElement {
	#checkbox;
	constructor() {
		super();

		this.attachShadow({mode: "open"});
		this.#checkbox = Object.assign(document.createElement("input"), {type: "checkbox", id: "checkbox"});
		this.shadowRoot.append(this.#checkbox);
	}

	attributeChangedCallback (name, value, oldValue) {
		this.#checkbox.setAttribute(name, value);
	}

	get checked () { return this.#checkbox.checked }
	set checked (v) { 
		this.#checkbox.checked = v; 
	}

	get disabled () { return this.#checkbox.disabled }
	set disabled (v) {
		this.#checkbox.checked = v; 
	}
}
```

</details> 

### Export states and other pseudo-classes from descendants

Currently, there is no primitive for exporting states from a nested component to the outside world (akin to exporting parts). This would enable that, often with remapping (just like `exportparts`!).

### Custom state pre-rendering

Currently, to prerender (SSR) custom elements, states must be be converted to attributes, then converted back when hydrating. CSS must be written to cater to both, like so:

```css
:host(:state(foo), [ssr-state-foo]) {
	/* ... */
}
```

If consumers need to handle the state, this also becomes a leaky abstraction:

```css
my-checkbox:is(:state(checked), [ssr-state-checked]) {
	/* ... */
}
```

Declarative custom states would improve the situation tenfold: 
1. For states that can be entirely described by CSS selectors, *all* JS state management code condenses down to 2-3 lines for the mapping and works automatically when prerendering.
2. For states that still need to be serialized into an attribute, this helps contain the mapping of attribute → state in one place while everything else (component CSS, consumer CSS, etc) continues to handle the state, not only improving maintainability but also preventing the abstraction from leaking.

### It enables custom elements to add state to slotted children

Authors are often forced to create a whole new element simply to track certain types of states on slotted children or deeper descendants.

For example:
- An accordion component may want to take `<details>` as children and set a `:state(active)` and `:state(last-active)` states
- A tabs component may want to accept any container as the tab-panel but be able to set a `:state(active)`
- A [`<random-content>`](https://webawesome.com/docs/components/random-content/) component may want to set a `:state(selected)` pseudo-class to the child currently being shown
- A `<filterable-table>` component that takes a `<table>` may want to set `:state(shown)` and `:state(filtered)` to corresponding rows while filtering.
- and so on

## Non-WC use cases

Reading the above, it sounds like this should be a WC-specific feature, however there are a ton of use cases around abstracting DOM querying that have nothing to do with custom elements.

### It provides a very decent workaround for custom pseudo-classes

If you ignore the name `state` for a second, this basically allows custom pseudo-classes with practically no downsides compared to a first-class solution designed specifically for this use case.

<details><summary>Example</summary>

E.g. suppose we didn't have `:heading`, it could be implemented like:

```css
/* Now :state(heading) matches every heading */
@state heading {
	matches: h1, h2, h3, h4, h5, h6;
}
```

This could also be used as a ponyfill for `:heading`:

```css
@state heading {
	matches: :heading;
}

@supports selector(:heading) {
	@state heading {
		matches: h1, h2, h3, h4, h5, h6;
	}
}
```

Or, maybe a project wants to include `[role=heading]` to what they target. They can build a higher level abstraction _over_ `:heading`:

```css
/* Now :state(heading) matches every heading */
@state heading {
	matches: :heading, [role=heading];
}
```

</details>

Similarly, it allows component consumers to alias component states into project-specific conventions so that swapping one component for another has less of a ripple effect on the codebase.

### It allows decoupled composability

This keeps cropping up from time to time, e.g. with a quick search:
- https://github.com/w3c/csswg-drafts/issues/1855
- https://github.com/w3c/csswg-drafts/issues/10222

This would allow host environments to use `:state()` as an extension hook that third-party code (CSS libraries, frameworks, etc) can extend. E.g.:

```css
button, :state(button) {
	/* Page’s button styles */
}
```

Now a web component could opt individual buttons into the default styling by adding the corresponding part to the set of mappings:

```css
@state button {
	matches: button[part=button]
}
```

The host page doesn't need to know what elements are hooking into each state. The shadow DOM elements hooking into the state don't need to know what styling is applied, or what other elements are using it. Everything is nicely decoupled and changing the part name breaks the mapping, if that's desired.

This can go both ways. A CSS library could also provide states that the host environment then extends to apply to their own situations.
For example, the same type of styling is often used for navigation menus, as well as horizontal tab strips.

<img width="778" height="160" alt="Image" src="https://github.com/user-attachments/assets/a266b879-eca6-4e8c-ae47-7127b2fb3c10" />

A CSS library could define styles like:

```css
:state(tabstrip) {
	display: flex;
	/* ... */
}

:state(tabstrip) > *, :state(tabstrip-item) {
	flex: 1;
	/* ... */
}
```

Then, a page can apply this to its navigation menu, a tabstrip component can apply it as well etc.
Yes, mixins will also solve this, but the ergonomics are different (better or worse, depending on the use case)

The benefit of this over other approaches is the **loose coupling** it enables.
The mapping is completely separate from either side, and neither side needs to know about the other.

## Design discussion

### Multiple `.states`/`@state` rules must compose

This is a semi-hard requirement, otherwise the feature will cater to _significantly_ fewer cases.
Each `@state` rule must **extend** the set of selectors mapped to that state, not replace it. There is no primitive for declaratively *removing* a state, that should be encoded in the mapped selector (e.g. via `:not()` or scoping criteria appropriately).

Instead of `@state` rules with the same id overwriting each other, they could be composed, providing another way to satisfy some of the #10222 use cases. Yes, it would require a double handshake, but perhaps authors can reach a convention for certain states, especially if there is only one mechanism for both CSS and WCs.

As a side effect, this means that a state added via CSS cannot be removed via JS until the selector stops matching (or the rule is removed via the CSSOM). I think this is fine and how other platform primitives work where state can be set via either CSS or DOM APIs.

### Cycle detection

Since not all states are set via CSS, states must be allowed as part of the mapping. But then, how to handle cycles?

```css
@state a {
	matches: :state(b), c, d;
}

@state b {
	matches: :state(a), c, e;
}
```

What happens here?

Observations:
- The code above *is* actually meaningful, and most likely meant to match `c, d, e`.
- Ideally any cycle detection/resolution strategy should be applied separately for each complex selector in the selector list instead of dropping the entire state.

Options, in order of preference:
1. Cycle detection + bounded expansion gets us as close as possible to the user intent. Meaning, in the example above `@state a` is expanded to `matches: :state(a), c, e, c, d`, and then `:state(a)` is removed from the set.
2. Cycle detection where the entire cycle is removed from matching. in the example above, `:state(a)` still matches `c, d` and `:state(b)` still matches `c, e`. 
3. Only allow JS-originating `:state()` in `matches`. Poor long-term solution, but could be an acceptable MVP.
4. Simply disallow `:state()` in `matches` altogether. Even poorer long-term solution, but could be an acceptable MVP.

### Shadow DOM boundaries

For many of the examples above, shadow DOM CSS must be able to expose states on the host and parts that are accessible from the outside. But we cannot simply define `@state` to operate in light DOM, since it can be useful for managing shadow DOM states, though that's not a very pressing need.

Additionally, while `:host` is unambiguous, `::part()` is not. The way `::part()` was used in the examples above, it was referring to parts *within* the shadow tree, but `::part()` in shadow CSS would refer to parts of elements *inside* that shadow tree.

Perhaps the algorithm is that states are associated with the element, and anything that has access to the element, with whatever means, has access to its states. So each pair of `:host`/`foo-bar`, `[part=foo]`/`::part(foo)`, `slot[name=foo]::slotted(*)`/`[slot=foo]`  would have access to the same states.

This is probably simplest, but ideally down the line should have an escape hatch for encapsulation. Possibly a descriptor in `@state`.

### What about pseudo-elements?

Simplest for the MVP is to just ignore pseudo-elements altogether, keeping on with the model of `:is()`.

But there are many legit use cases around pseudo-elements. Obviously, `:state()` being a pseudo-class, it acts as a filter and cannot *add* elements to the matching, but it's somewhat less defensible when the base selector already applies more broadly, e.g.:

```css
@state ba {
	matches: ::before, ::after;
}

/* Does this add "test" at the start and end of every div? */
div:state(ba) {
	content: "test";
}

/* What about this? */
div::before:state(ba) {
	content: "before"
}
```

I think for both of these  it would be _very_ weird if they worked.

That said, I think there are use cases for a declarative version of `::part()` as well, which would also allow authors to export pseudo-elements like `::backdrop` or `::checkmark`, a current pain point with web components encapsulating complex native elements.

## Specificity

In L1, **specificity** would always be `0, 1, 0` or whatever the equivalent `:is()` would have been. 
In L2, a `specificity` descriptor could be used to override.

```html
<!-- CE definition that’s controlling its state -->
<script>
customElements.define("my-element", class extends HTMLElement {
  #internals = this.attachInternals();

  get open() {
    return this.#internals.states.has("open");
  }

  set open(value) {
    if (value === true) {
      this.#internals.ariaExpanded = "true";
      this.#internals.states.add("open");
    } else if (value === false) {
      this.#internals.ariaExpanded = "false";
      this.#internals.states.delete("open");
    }
  }

  constructor() {
    super();
    // Ignore the fact that there’s no ARIA role… trying to keep this focused.

    // Default expanded state is false, so `open` does not apply
    this.#internals.ariaExpanded = "false";

    this.attachShadow({ mode: "open" });

    this.shadowRoot.innerHTML = `<slot></slot><style>
      :host(:state(open)) {
        /* Open styles */
      }
    </style>`;

    this.addEventListener("click", () => {
      this.open = !this.open;
    });
  }
});
</script>
```

I get the argument you're making about having less distinct syntaxes for this sort of custom selector, but I agree with @knowler in <https://github.com/w3c/csswg-drafts/issues/12502#issuecomment-3097047503>: this conflates "information from inside a custom element" with other things, in a way that I think can be confusing.

Part of the reason we added `:state()` in the first place was to let custom elements avoid messing with the class attribute on the host element, as we wanted to leave that for the outer page to use instead. We both didn't want custom elements to accidentally clobber the page's classes thru careless mutation, and also didn't want to force a custom element to use ugly uniquified names just to avoid accidentally matching a class the outer page is using for other purposes and getting wrongly styled. Your suggestion to use :state() here would bring back that latter concern - if your page is already using `:state(heading)` as a way to select h1/etc, and you start using a new custom element that happens to use a heading state as well, you'll automatically match that custom element as well, with no way to avoid that. You'd have to either change your existing alias name across your stylesheets, or edit the component to use a different state name.

I think we should stick with just doing custom pseudo-classes a la my personal proposal. If you do want your `:--heading` pseudo to also match `:state(heading)`, you can easily do that by just adding `:state(heading)` to the selector it's defined with:

```css
@custom-selector :--heading h1, h2 h3, h4, h5, h6, [role=heading], :state(heading);
```

Or even further restrict it to just the particular custom element name you know you want. But if you don't, you can just not do that.

## @LeaVerou — 2026-07-03

I just rewrote the proposal, and added a lot of use cases that have come up meanwhile, including many *around* web components, such as pre-rendering/SSR custom states, simplifying custom state management, and many more, plus more examples.
I also fleshed out the design discussion a lot more. I'm tagging it Agenda+ F2F so it gets some broader feedback.

As for the arguments that have been brought up by @knowler and @tabatkins . 

### We should instead introduce a custom pseudo-class primitive

I agree that the name `state` is suboptimal for some of the use cases. But is naming enough to invent a whole new primitive, with its own separate JS API etc? Precedent generally says no.

Also, if we introduce a new custom pseudo-class primitive, as a web component author, I'd want to tap into that! Why expose `:state(selected)` in my API when I can expose `:--selected`?!

So what I can see happening is a weird fragmentation when component authors end up using _both_ to express the same conceptual state: one for compat and one for ergonomics.

I think it's much better to just make `:--foo` an automatic alias of `:state(foo)`. If we later introduce parameters, `:--foo(bar)` would be an alias of `:state(foo, bar)`.

### This breaks encapsulation

The outside world can already clobber everything in your web component:
- They can set attributes and override your nice ARIA
- They can apply all sorts of CSS to the host and its parts (which are usually >80% of shadow DOM elements anyway), whether a certain state applies or not and wreak havoc and you can't do anything because even their `*` has higher priority than any CSS in your shadow DOM
- They can even reach inside your shadow DOM and have a party (unless you're in the <10% of components that use closed shadow roots)

And custom states is where we draw the line?? 😅
 
IMO the goal is to prevent **accidental breakage**. 
For intentional breakage the ship was sinking before it even left the harbor. 😅
I'm not sure how that would happen with this proposal, how would someone *accidentally* assign a state to your component that would break it? And what were they _actually_ trying to do? What are they going to now do _instead_?
Even if they did that to intentionally force it to e.g. open when it otherwise would be closed, it *still* gives the component author more control than if the consumer was trying to do the same thing with CSS overrides. It's not like this pseudo-class grants them access to any additional elements they wouldn't otherwise have access to.

## @tabatkins — 2026-08-06

In <https://github.com/w3c/csswg-drafts/issues/12502#issuecomment-4878221835>, I think Lea got my concern backwards. (We talked about this in the minutes that'll be posted momentarily, but I'll write it clearly here.)

My concern is about accidental name clashing, where a component decides to use a particular name for its own purposes, and the page uses that name for unrelated purposes without realizing there is a clash. The page will accidentally select/style the component when they never intended to.

Lea pointed out in the f2f that there's always going to be some amount of potential accidental clashing; two different components can expose the same state name, so a naive `:state(foo)` selector could select more than intended. This is true! It's *less* of an issue, because the clashes here are *guaranteed* to be happening on different elements; in fact, guaranteed to be on different element *names*. So, pages can still be naive and trip themselves up, but they can also write `my-foo:state(foo)` and `my-bar:state(foo)` and get things right, regardless of what the components are doing. The page author can write their selectors a little defensively and be *guaranteed* their selectors work correctly, *regardless* of what any component is doing.

On the other hand, a custom selector and a component state can clash, and even apply to the *same element*. That is, a `@custom-selector :--foo ...;` could potentially match a `my-comp` element, which *also* exposes a "--foo" state; if this is the case, `my-comp:--foo` is *inherently ambiguous* about which pseudo class it's trying to refer to, and there's no way for the page to deal with the ambiguity. The only solution is either for the page to make sure their own names aren't used by any of the components they use, or for the components to go out of their way to uniquify their state names so they're unlikely to clash with page-defined names.

On the other hand, if the two features use a different syntax, so `@custom-selector :--foo ...;` for selector aliasing and `:state(foo)` for component custom states, we avoid this issue. Components *cannot* accidentally clash with page-defined pseudos; they can clash with *each other* but only in the way described above, where the page author can easily be defensive and safe about it.
