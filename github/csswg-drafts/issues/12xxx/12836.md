Currently chromium is having issue with when `font-variation-settings: "ital" 1` and `font-style: italic`, `font-style: oblique`, `<i>HTML element`.
See [bug](https://issues.chromium.org/issues/40681464)

According to [CSS spec](https://drafts.csswg.org/css-fonts-4/#font-style-prop) If a variable font has an Italic (ital) axis, ital axis should be activated (turned to value "1") by the CSS `font-style:italic` or `font-style:oblique` and the html `<i>`. but currently in chromium is having issues with that. 

I uploaded a CL in chromium in [here](https://chromium-review.googlesource.com/c/chromium/src/+/6965375) (passed the CQ dry run).

## @jfkthame — 2025-09-20

I think it's wrong for `font-style: oblique` to activate the `ital` axis in the font, which is what the "after fix" image seems to show for the combination of `font-style: oblique` and "Font with `ital`, 0 to 1".

If `oblique` is requested, and no actual oblique face nor `slnt` axis is available, the browser should _not_ fall back to an italic face; instead, it should apply a synthetic oblique effect. Just as it should _not_ use a distinct italic face as fallback for `oblique`, I think it should also _not_ apply the `ital` axis.

## @svgeesus — 2025-09-22

The [spec currently says](https://drafts.csswg.org/css-fonts-4/#font-style-prop) (my emphasis)

> oblique `<angle [-90deg,90deg]>`
    Controls matching against an oblique face. Positive angles represent a clockwise slant; negative angles represent a counter-clockwise slant. The lack of an [`<angle>`](https://drafts.csswg.org/css-values-4/#angle-value) represents 14deg. (Note that a font might internally provide its own mapping for "oblique", but the mapping within the font is disregarded.) Fractional and negative values are accepted; however, values less than -90deg or values greater than 90deg are [invalid](https://drafts.csswg.org/css-syntax-3/#css-invalid). If no oblique faces exist, and [font-synthesis-style](https://drafts.csswg.org/css-fonts-4/#propdef-font-synthesis-style) has the value auto, **a synthetic oblique face will be generated.**

## @hjanuschka — 2026-08-29

Trying to revive this, since it currently blocks fixing https://issues.chromium.org/issues/40681464 in Chromium (CL: https://chromium-review.googlesource.com/c/chromium/src/+/8179764).

> @jfkthame @wjhe1016 is the spec clear as-is or is clarifying wording needed?

@svgeesus I think clarifying wording is needed. The property definition already states the intent (https://drafts.csswg.org/css-fonts-4/#font-style-prop):

> For TrueType / OpenType fonts that use variations, the slnt variation is used to implement oblique values, and the ital variation with a value of 1 is used to implement the italic values.

and the axis mapping table says font-style sets "the slnt or ital axis, depending on its value". But the Font Matching Algorithm (https://drafts.csswg.org/css-fonts-4/#font-style-matching) only has explicit instantiation text for slnt in the oblique branches ("For variable fonts with a slnt axis, a match is created by setting the slnt value with the specified oblique value") and says nothing about ital in the italic branch. 


Proposed wording, mirroring the existing slnt sentence:

In the "If the value of font-style is italic" branch:

> For variable fonts with an ital axis, a match is created by setting the ital value to 1.

And, per the discussion above (jfkthame's point, which drott supported), a clarification in the oblique branches that the ital axis is not used for oblique:

> The ital axis is not used to satisfy an oblique request; if no oblique face and no slnt axis is available, a synthetic oblique face is generated per font-synthesis-style.

For fonts exposing both slnt and ital axes, the natural consequence of the above is: the italic keyword sets ital to 1 (leaving slnt at its default), and oblique sets slnt (leaving ital at its default). This matches what Gecko ships today, and what the Chromium CL implements.


Happy to turn this into a spec PR if the wording direction looks right.
