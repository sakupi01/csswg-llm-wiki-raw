The CSS Overflow Module Level 4 draft specifies inconsistent bidirectional (bidi) handling for the ellipsis generated by text-overflow versus the one generated by the line-clamp property.

1. `text-overflow: ellipsis`: The specification implies that the ellipsis is part of its paragraph for bidi purposes. Implementations typically treat it as inheriting the direction of the line it is attached to.
2. `line-clamp` (block-ellipsis): The specification for block-ellipsis states that it behaves as if it had `unicode-bidi: plaintext`.

This leads to two different implementation approaches for what is visually the same feature:
* text-overflow ellipsis inherits the parent's direction.
* line-clamp ellipsis uses plaintext logic to determine its direction.

This difference in behavior is surprising and seems unintentional. We'd like to ensure this behavior.

Context: https://chromium-review.googlesource.com/c/chromium/src/+/6817921/comment/c4178435_9956b836/

## @andreubotella — 2026-02-18

As I was working on a spec edit for this, it was not clear to me whether the resolution saying "take their bidi direction from the paragraph" matched the previous conversation. Per the log:

> &lt;TabAtkins> fantasai: making sure I understand. So it is isolated. as an isolate it behaves as a neutral char at the paragraph's embedding level. within the isolate it takes the direction of the paragraph...
> &lt;TabAtkins> florian: are you distinguishing between para or block container, or just saying para because it's easier?
> &lt;TabAtkins> fantasai: para is the bidi term. block container is what I mean

Let's say we have a block container with `direction: ltr; unicode-bidi: plaintext`, but UAX#9 P2 and P3 sets the *bidi paragraph*'s base directionality to RTL. The resolution language could imply that the ellipsis inline takes its direction from the *bidi paragraph*, so acting as if it had `unicode-bidi: isolate; direction: rtl`. Should it inherit `direction` from the block container instead?

This gets somewhat tricky when you have multiple bidi paragraphs in the same block container, because with `unicode-bidi: plaintext`, the different paragraphs could have different base directionalities.

Edit: I opened a PR assuming the directionality is inherited from the block in #13519. There are tests for bidi in `text-overflow: <string>` in `css/css-ui/text-overflow-string-{006,007}.html`, but they don't cover this issue. There are no `block-ellipsis` tests yet.

## @frivoal — 2026-03-17

Say you're in an English LTR document, and your block container is set to `unicode-bidi: plain-text`, and contains mostly LTR English text, but also one paragraph of RTL Persian, and your ellipsis string is `… (continued)`.

For English, there's no ambiguity, and you'd see:

> One upon a time… (continued)

But for Persian it could be:
> (continued) …روزی روزگاری

or
> … (continued)روزی روزگاری

The first one follow the (RTL) bidi paragraph, the second one follows the (LTR) block container.

Though admittedly usage of `unicode-bidi: plain-text` is rare, if it does occur, I think from a user point of view, going by the actual bidi paragraph seems to make more sense.
