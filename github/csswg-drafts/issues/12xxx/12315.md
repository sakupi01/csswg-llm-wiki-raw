@kizu pointed out that the following behavior is surprising:

```
@function --f(--arg <color>) {
  result: if(
    style(--arg: red): green;
    else: black;
  );
}
/* --f(#f00) => black*/
```

At the time `if()` is resolved, we are treating `--arg` as an untyped local (step 11 of [evaluate a custom function](https://drafts.csswg.org/css-mixins-1/#evaluate-a-custom-function)), which means we don't interpret the right hand side of `style(--arg: red)` as a `<color>`, and therefore `rgb(255, 0, 0)` != `red`.

Grouping parameters in with (untyped) locals seemed reasonable to me originally, but given the example, I think `--arg <color>` should act as a "local registration" within the function (also affecting any locals named `--arg`). @tabatkins, @mirisuzanne: what do you think?

## @kizu — 2025-06-11

Just adding a tiny bit of context: I noticed that when writing my [“Functional Capturing”](https://blog.kizu.dev/functional-capturing) post, and isolated the case that was a bit confusing after talking about it with @andruud here: https://codepen.io/kizu/pen/dPodpqa?editors=1100

Given in many other ways typed arguments already behave like registered custom properties, it would be nice to have this behavior for consistency as well.

Yes, I think params should keep their type. But I also think this is a more general issue for style queries of all kinds - and we may want a more general solution for on-the-fly "compare these values as `<type>`".

> Grouping parameters in with (untyped) locals seemed reasonable to me originally, but given the example, I think `--arg <color>` should act as a "local registration" within the function (also affecting any locals named `--arg`).

Agree.

> we may want a more general solution for on-the-fly "compare these values as `<type>`".

Also agree. Within a `style()` test, we could have a `foo as <type>: val` syntax. This would help in cases where a value *could* be a few different types, and you want to test it against a particular value *if* it parses to the correct type.
