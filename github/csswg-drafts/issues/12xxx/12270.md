This issue can be observed on the Cards example in the gallery: https://chrome.dev/carousel/horizontal/cards/

If the carousel is set to any marker but the first, the behavior tabbing forwards through the carousel does not match the behavior tabbing backwards.

The solution I would lean towards would be to ensure that tabbing does not reach any carousel item that is not fully in the viewport, so that tab alone can never trigger slide changes.

## @flackr — 2026-09-10

We already have a special case for arrow scrolling where if you don't have a focused element it targets the last mouse down node - this is why you can click in a scroller on a non-focusable element and still use arrow keys to scroll that scroller. This also retargets to the nearest still attached ancestor when that element is removed. I think the same should apply when the focused element is removed or becomes no longer focusable.

Similarly when the focused element is removed from the dom or becomes unfocusable I think we should set the [sequential focus navigation starting point](https://html.spec.whatwg.org/multipage/interaction.html#sequential-focus-navigation-starting-point) such that focus will start from the location that just had focus.

## @smhigley — 2026-09-11

If I've understood you correctly, that doesn't actually solve the focus issue -- the problem is that focus should never be lost while scrolling regardless of what happens with focus navigation start point. Focus loss affects screen reader cursor as well, not just keyboard operability, which is why it matters.

There are essentially three reasonable and accessible keyboard behaviors for a control like this:
1. It acts like a normal scrolling region where offscreen content is not inert or truly hidden, in which case focus remains wherever the user put it while scrolling. This works best for link behavior situations like the table of contents.
2. Arrow keys move the user's focus between slides, and slides have semantics that make this behavior predictable and understandable (not tabpanel). This would effectively make the set of slides into a composite widget (examples include arrowing between tabs in a tablist, menuitems in a menu, articles in a feed, or I'd even consider listitems in a list here even if it's not 100% kosher yet). This would need much more detailed focus management, since arrowing while focus is on the inner content of a slide shouldn't scroll and users need an easy way to get back to arrowing between slides after moving their focus into the content.
3. Slides don't scroll at all (for mouse or keyboard). The only way to change slides is to use the scroll markers or scroll buttons.

Let me know if that makes sense / if I've missed anything!

This is an author decision whether the slides are user scrollable. If they use `overflow: hidden` then the slides can only be navigated by the scroll buttons or scroll markers.

## @smhigley — 2026-09-17

Unfortunately, I don't think having focus jump anywhere on scroll is a behavior that would be predictable or expected. Either arrow keys scroll and focus doesn't move, or arrow keys move focus between elements with semantics that support that behavior (where the focus movement itself can then cause scrolling). Any other behavior would be an accessibility issue -- imagine someone using a screen reader, bumping their trackpad or mouse, and having focus randomly jump around.

This is a fundamentally different behavior from focus moving after a click-type interaction. Certain actions can prime the user to expect or at least not be surprised by a change of context, and others (scroll in this case) do not.

Everything else in my comment was me laying out more specific options and details of what those two behaviors could look like in the context of a carousel. I think you might be mixing those up a bit, and picking and choosing examples of semantics and keyboard behavior separately to try to find a basis for the current approach. Unfortunately, the semantics and behavior are interdependent, so if you want to e.g. follow the APG carousel tabpanel approach, the keyboard behavior needs to stay consistent with those semantics.

To address a couple specifics:

> The APG pattern for slides with scroll markers suggests that they are tabpanels, https://www.w3.org/WAI/ARIA/apg/patterns/carousel/examples/carousel-2-tablist/. While the APG example does not allow using the arrow keys to move between slides, many developers choose to have this behavior.

Tabpanels are fine as a semantic if you can't lose focus by scrolling between them without interacting with the tablist. Similarly, being able to move through carousel slides without interacting with the scroll markers/buttons is a common behavior devs/designers want, as you mentioned. That also isn't a problem in itself (I've made a number of these myself), but it requires different semantics and keyboard behaviors to be accessible. Allowing people to combine the two out of the box is the problem. If the browser provides the behavior of navigating between slides without interacting with the scroll markers/buttons out of the box, then it should provide semantics and keyboard behavior to match at the same time. The APG carousel + tab semantics example is no longer something that can be referenced as soon as this scrolling + offscreen inert behavior is added.

To make sure I'm not misinterpreted -- I think offscreen inert for carousel slides is a good thing, since not needing to navigate through the entire carousel before continuing is a primary UX feature. I also have made enough composite-widget-with-slide-arrowing carousels that I understand the desire to provide that feature. The only issue is combining standard scrolling with tabpanel semantics, no composite widget arrow key behavior, and focus loss.

> Being able to scroll the ancestor scroller while focus is on inner content is not new to this feature.

Similarly, scrolling is not new, but elements losing focus on scroll _is_ new, and that is the root of the problem.

> This is standard scrolling behavior. If the focused element does not preventDefault or otherwise handle the keypress, then it is allowed to scroll the nearest ancestor scroller that can scroll in this direction.

I was describing manged focus composite widgets in that section, not scrolling. The crux of what I was trying to describe is that you do _not_ allow standard keyboard scrolling within a managed focus widget like a listbox or menu. ## @smhigley — 2026-09-22

I've seen a number of unintentional scroll jumps in user studies, which would indicate that it is an issue one way or another 😅. Screen reader users can also very easily be in a different mode than they expect, and accidentally use arrow keys to scroll (i.e. in forms mode) while trying to use them to move the cursor (in virtual cursor/browse mode).

That's also not even touching on the partially sighted screen reader users who might scroll intentionally, then find themselves way back at the top of the page when focus is lost.

This is not the same as erroneously activating a button, and even buttons are required to not jump focus when clicked in certain cases (ref: [WCAG's On Input criterion](https://w3c.github.io/wcag/understanding/on-input.html))

I'm a bit surprised that this angle is getting any pushback at all -- generally I'd consider "focus shouldn't get lost on scroll" to be a basic, uncontroversial accessibility requirement. There's a good argument this also violates WCAG's On Input requirement as well, though generally I prefer not to approach accessibility issues by litigating WCAG.
