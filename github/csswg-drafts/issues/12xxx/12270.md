This issue can be observed on the Cards example in the gallery: https://chrome.dev/carousel/horizontal/cards/

If the carousel is set to any marker but the first, the behavior tabbing forwards through the carousel does not match the behavior tabbing backwards.

The solution I would lean towards would be to ensure that tabbing does not reach any carousel item that is not fully in the viewport, so that tab alone can never trigger slide changes.

I do think the behavior of offscreen slides being inert is a good one, but there would need to either be focus handling between slides when the currently-focused content goes offscreen, or the arrow-to-scroll behavior needs to be reworked.

<!-- comment id=5622724236 author=flackr created=2026-09-10T17:25:39Z url=https://github.com/w3c/csswg-drafts/issues/12270#issuecomment-5622724236 -->
## @flackr — 2026-09-10

We already have a special case for arrow scrolling where if you don't have a focused element it targets the last mouse down node - this is why you can click in a scroller on a non-focusable element and still use arrow keys to scroll that scroller. This also retargets to the nearest still attached ancestor when that element is removed. I think the same should apply when the focused element is removed or becomes no longer focusable.

Similarly when the focused element is removed from the dom or becomes unfocusable I think we should set the [sequential focus navigation starting point](https://html.spec.whatwg.org/multipage/interaction.html#sequential-focus-navigation-starting-point) such that focus will start from the location that just had focus.

## @smhigley — 2026-09-11

If I've understood you correctly, that doesn't actually solve the focus issue -- the problem is that focus should never be lost while scrolling regardless of what happens with focus navigation start point. Focus loss affects screen reader cursor as well, not just keyboard operability, which is why it matters.

There are essentially three reasonable and accessible keyboard behaviors for a control like this:
1. It acts like a normal scrolling region where offscreen content is not inert or truly hidden, in which case focus remains wherever the user put it while scrolling. This works best for link behavior situations like the table of contents.
2. Arrow keys move the user's focus between slides, and slides have semantics that make this behavior predictable and understandable (not tabpanel). This would effectively make the set of slides into a composite widget (examples include arrowing between tabs in a tablist, menuitems in a menu, articles in a feed, or I'd even consider listitems in a list here even if it's not 100% kosher yet). This would need much more detailed focus management, since arrowing while focus is on the inner content of a slide shouldn't scroll and users need an easy way to get back to arrowing between slides after moving their focus into the content.
3. Slides don't scroll at all (for mouse or keyboard). The only way to change slides is to use the scroll markers or scroll buttons.

Let me know if that makes sense / if I've missed anything!

## @flackr — 2026-09-11

> If I've understood you correctly, that doesn't actually solve the focus issue -- the problem is that focus should never be lost while scrolling regardless of what happens with focus navigation start point. Focus loss affects screen reader cursor as well, not just keyboard operability, which is why it matters.

I agree we want this to work as expected for screen readers as well. What are developers expected to do when you activate a control that removes the currently focused element (e.g. a delete button)? We could move focus to the newly active scroll marker if using tabs mode and focus was in the previous slide which might match expectations.

> There are essentially three reasonable and accessible keyboard behaviors for a control like this:
> 
> 1. It acts like a normal scrolling region where offscreen content is not inert or truly hidden, in which case focus remains wherever the user put it while scrolling. This works best for link behavior situations like the table of contents.

This is the default behavior if the author doesn't change from the links mode: https://drafts.csswg.org/css-overflow-5/#valdef-scroll-marker-group-links

> 2. Arrow keys move the user's focus between slides, and slides have semantics that make this behavior predictable and understandable (not tabpanel). This would effectively make the set of slides into a composite widget (examples include arrowing between tabs in a tablist, menuitems in a menu, articles in a feed, or I'd even consider listitems in a list here even if it's not 100% kosher yet).

The APG pattern for slides with scroll markers suggests that they are tabpanels, https://www.w3.org/WAI/ARIA/apg/patterns/carousel/examples/carousel-2-tablist/. While the APG example does not allow using the arrow keys to move between slides, many developers choose to have this behavior. As mentioned in the next point, developers can choose when they want the panels / slides to be user scrollable by whether they set `overflow: hidden` or `overflow: auto`.

>    This would need much more detailed focus management, since arrowing while focus is on the inner content of a slide shouldn't scroll and users need an easy way to get back to arrowing between slides after moving their focus into the content.

This is standard scrolling behavior. If the focused element does not preventDefault or otherwise handle the keypress, then it is allowed to scroll the nearest ancestor scroller that can scroll in this direction. if the inner content does handle the arrow key (e.g. text input, inner scroller, developer handled), then it will prevent scrolling an ancestor. Being able to scroll the ancestor scroller while focus is on inner content is not new to this feature.

> 3. Slides don't scroll at all (for mouse or keyboard). The only way to change slides is to use the scroll markers or scroll buttons.> 
> Let me know if that makes sense / if I've missed anything!

This is an author decision whether the slides are user scrollable. If they use `overflow: hidden` then the slides can only be navigated by the scroll buttons or scroll markers.
