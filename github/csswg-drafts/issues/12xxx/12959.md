There was a discussion around this in https://github.com/w3c/csswg-drafts/issues/4828, but I don't understand what the resolution actually means:

> `RESOLVED: We define this is CSSOM to match browser compat as much as it exists.`

Can we clarify this?

Assuming we can't mess with the serialization of old rules for compat reasons, we may have to accept that e.g. `@media` serializes with newlines and indents. Do we still want to go for the single line behavior for _new_ rules? If yes, does the single-line-ness carry over to any _inner_ rules that would otherwise use newlines/indents in a different context?

Example:

```
@function --f() {
  --local: 1px;
  @media (width > 200px) {
    --x: 2px;
    --y: 3px;
  }
  result: 4px;
}
```

This serializes as this nonsense in Chrome:

```
@function --f() { --local: 1px; @media (width > 200px) {
  --x: 2px; --y: 3px;
} result: 4px; }
```

That's because `@function` tries to be single-line, but `@media` wants it the old way.

It would be far more reasonable to serialize the whole thing on a single line, but @emilio notes that it could be weird that `myFunc.cssRules[0].cssText` would serialize a `@media` rule differently than what you'd get for the same rule top-level.

We could address that by having two modes: legacy mode, and single line mode. Every serialization starts in legacy mode, but as soon as you enter a "new" rule, any child constructs are also serialized in single line mode. That would allow `myFunc.cssRules[0].cssText` to serialize consistently with the top-level, while also placing everything on a single line for `myFunc.cssText`.

## @cdoublev — 2026-01-22

I thought that a common algorithm for the rule block could prevent future inconsistencies.

(sorry for the many edits, getting it right *and* concise was trickier than I thought)

  > To **serialize a rule block** from
  > an optional list of declarations `declarations`,
  > an optional list of rules `rules`,
  > and an optional `legacy` flag unset by default,
  > run the following steps:
  >
  > 1. Let `string` be the string "{", i.e., LEFT CURLY BRACKET (U+007B).
  > 2. If `declarations` is not empty,
  >    let `serializedDeclarations` be the result of performing [serialize a CSS declaration block](https://drafts.csswg.org/cssom-1/#serialize-a-css-declaration-block)
  >    on `declarations` if it is a [`CSSStyleDeclaration`](https://drafts.csswg.org/cssom-1/#cssstyledeclaration),
  >    otherwise the result of performing [serialize a CSS declaration](https://drafts.csswg.org/cssom-1/#serialize-a-css-declaration)
  >    on each declaration in `declarations`,
  >    joined with the string "; ", i.e., SEMICOLON (U+003B) followed by a single SPACE (U+0020),
  >    and followed by the string ";", i.e., SEMICOLON (U+003B).
  > 4. If `rules` is not empty:
  >    1. If `legacy` is set:
  >       1. Append a newline.
  >       2. Append `serializedDeclarations` if `declarations` is not empty.
  >       3. Append the result of performing [serialize a CSS rule](https://drafts.csswg.org/cssom-1/#serialize-a-css-rule)
  >          on each rule in `rules`,
  >          preceded with a newline followed by two SPACES (U+0020).
  >       4. Append a newline.
  >       5. Append the string "}", i.e., RIGHT CURLY BRACKET (U+007D).
  >    2. Otherwise:
  >       1. Append a single SPACE (U+0020).
  >       2. Append `serializedDeclarations` if `declarations` is not empty,
  >       3. Append the result of performing [serialize a CSS rule](https://drafts.csswg.org/cssom-1/#serialize-a-css-rule)
  >          on each rule in `rules`,
  >          joined with a single SPACE (U+0020).
  >       4. Append the string " }", i.e., a single SPACE (U+0020), followed by RIGHT CURLY BRACKET (U+007D).
  > 5. Otherwise:
  >    1. Append a single SPACE (U+0020) followed by `serializedDeclarations`.
  >    2. Append the string " }", i.e., a single SPACE (U+0020), followed by RIGHT CURLY BRACKET (U+007D).
  > 6. Return `string`.

## @tabatkins — 2026-01-23

Strong agree; the CSSOM serialization rules are *broken as hell*, and were written under the assumption that any sort of nesting didn't exist. Since it now *does* exist in many forms, it needs a dramatic rewrite that actually creates newlines and indents properly.

The only issue will be making sure some of the weird corner behaviors for non-nested cases aren't requried for compat, but I think we can deal with those as we run into them.
