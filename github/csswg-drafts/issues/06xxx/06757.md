In media queries level 5 we have the ability for authors to specify:

1. environment-blending
2. prefers-reduced-transparency
3. prefers-contrast

The use cases for these even with the documentation is _wildly unclear_. For example, let's take "@media (environment-blending: additive)" signifying that the current environment is blended. An example of this might be a smart mirror such as: https://www.youtube.com/watch?v=divCJeIMa4M. A similar example per the documentation is a HUD.

For this device. and others where an additive environment is used I'd say this implicitly represents a need for more contrast and reduced transparency. So on and so forth. It's unclear exactly when an author would want to use one of these queries over the other, some combination of them, or when _not_ to use them (whether it be via negation or exclusion entirely) as they all seem to represent some form of reduced visual complexity.

The documentation itself states it's unclear if `subtractive` is even needed in which case... I fail to see the utility of this query since in all scenarios, I personally, can think of I would simply be applying adjustments along the lines of prefers-reduced-transparency and / or prefers-contrast. Which, again, is reducing visual complexity.

A smart mirror is the most obvious use case for reduced transparency I can think of. Beyond this? I can not think of another device on which I'd wish to apply this - granted new devices are always being made and that can quickly change in the future. More importantly, are authors meant to take this to handle glassmorphism and similar trends as well for users with visual impariment? In which case.... How is this not higher contrast? If you're reducing, or even replacing, effects such as this the net effect would be a higher contrast with the foreground. Unless of course you have a glassmorphism effect the same color as your foreground.... in which case reducing the transparency would cause less contrast, but that's just bad design.

This is where the nuance for these media queries comes into play for me and precisely why it's not clear _which_ should be used as they all have some form of commonality.

For "prefers-contrast"... After _much_ digging trying to figure out how on earth I should apply this and when I should, if it all, led me to a thread discussing the usage of low contrast for people that suffer from chronic migraines etc and of course high contrast is an obvious use case for users with some form of vision impairment that may require it.

And, in these cases, it makes sense. But, per the issue, the problem is... The documentation does not reflect this. If media queries like this are added a short a11y or other discussion should accompany them to help guide authors. The latter point being specifically directed at the low contrast option. Otherwise I, and I'd imagine many others, are really just left scratching our heads trying to figure out the utility of these options.

Likewise, for prefers contrast there is conflation that has already been discussed such as the interplay with forced colors and recent update for a `custom` value I believe which is equally confusing.

I believe I saw a thread a while back discussing the merit of adding more and more querying possibilities at risk of author's being inundated with options and penultimately confused leading to either 1) not knowing how to apply them or 2) applying them inappropriately / outside their scope of intent. I'd say it's already there. 

Conversely, queries I _would_ have liked to use, representing a clear cut use case with obvious utility, was adapting to light levels. I believe that this was nixed due to overlap with high contrast? Or, was it fingerprinting? I see the notes regarding fingerprinting for `prefers-reduced-data`. So, if the implications are being working through for this media query... then why not the ambient light level as well? I and many other web authors would have loved to use this. I don't how many people reading this use google maps, but the auto switch to dark mode when going into a tunnel etc is just *_chef's kiss_*. 

As an author I prefer media queries that are extremely clear cut, such as the former were it implemented, with regards to accessibility usage rather than the amounts of conflation currently present. Even after re-reading their use cases and documentation a half dozen times I'm not at all confident I would apply them even remotely correctly. These issues aren't present within any other media query. The rest are very well defined minus a few color issues.

Getting off topic to discuss the aforementioned color issues:

It's unclear to me when authors would want to use either the video-gamut or color-gamut applications beyond their most trivial use cases. I understand the media queries signify that the device can display roughly that gamut - within some reasonable margin.  So, clearly I could define a media query such as @media (color-gamut: p3) {...} and deliver a richer experience on devices such as iPhones supporting the DCI-P3 color space.

However, my lack of knowledge in color theory, how devices actually display color with various technologies, etc means that any application of these things is done very naively. I'd imagine that's true for .... 99.999% of web devs? Literally anyone that doesn't work on specs and just goes Figma -> Web. We can certainly keep "bumping" the colors up into more expansive spaces, to my understanding srgb < p3 < rec2020 < lab etc etc, delivering better experiences and even more uniform ones for the latter (lab being device independent). I don't fully understand why one would bother themselves with this media query at all or even the new color options? It seems very akin to color-index and color never being used. I don't remember the last time I see hwb() in the wild - if ever.

If devices perform gamut mapping then why wouldn't an author just always supply their preferences, even if it may be potentially outside the devices supported gamut, if it's just going to map the color back to the best match the device can support anyways? So, if this is the case... what's the point of using "color(preferred space, fallback spaces)" and other methodologies? The only utility I see is the ability to supply a device independent color space and as lab encompasses everything the utility of others seems lacking.  Similarly, the only use case I can think of for custom color profiles etc is matching the configuration of a print setup - which is discussed per the list of FOGRAs, SWOPs, etc. and pantone.

Moreover, this is further complicated to me as an author that's been around for a bit and consumed copious amounts of web dev and design articles. I vaguely recall that one can use background images / images in general to encapsulate colors that may not otherwise be supported. 

For videos... It's a little more obvious per the discussion surrounding bi-planes and transfer curves that one can find if they dig around the docs, open issues, etc. Likewise, for images with the dynamic range media query. I could envision wanting to query these to not unnecessarily send HDR content where it's not supported for both visual and performance reasons as HDR files tend to contain more information.

But, digressing....

These are the types of nuances that are lacking to me as an author whenever I initially read and even re-read many times. I don't think the documentation should serve as an encyclopedia explaining various subfields to bring authors up to speed on being able to apply them with the utmost level of certainty and knowledge, but as the potential for design and complexity of it grows on the web - which these queries inherently represent - there should be enough there for authors to easily pinpoint what they may need or not need to brush up on - if and when a sufficient or counter example does not suffice.
