2022-09-10 Update: https://w3c.github.io/csswg-drafts/ now exists as an alternative (thanks to @tabatkins and based on @andreubotella’s system from https://github.com/andreubotella/csswg-auto-build/).

So if you can’t access a CSS spec at a particular drafts.csswg.org URL, replace `drafts.csswg.org` in the URL with `w3c.github.io/csswg-drafts` and you’ll have what you need.

> **Note**: The server sometimes becomes unresponsive under heavy load. This is a known issue and it will resolve on its own (and go away once we can do the server upgrades).

Let's please reserve this issue for when the server needs human attention. e.g.:
* You're seeing a 'No specifications in the repository' message
* You're seeing a message like 'unable to contact the database server'
* The server has been unresponsive for a long time (over an hour)

When issues like those happen, either the database server fell over, or DB connection exhaustion caused a background process to fail (requiring it to be manually restarted), or the server is under a long-term 'DDOS' attack (usually a lot of crawlers more than a genuine attack) and firewall rules need to be tweaked.

> Let's please reserve this issue for when the server needs human attention. e.g.:

I believe that from a user point of view, getting a directory listing rather than the spec content they need is an issue that needs human attention, especially if it happens repeatedly — multiple times a week or even multiple times a day.

> The server has been unresponsive for a long time (over an hour)

Users who are trying to view CSS specs don’t know how long the server has been unresponsive — nor do they have any way of knowing other than (I guess) repeatedly checking to see if they can finally actually read the spec they need.

Instead users come in trying to read a particular CSS spec but finding that they can’t. And when that happens, it stops them from solving whatever immediate information need it is that they had for wanting to read that particular spec at that moment — which stops whatever work they were trying to get done.

So when a user gets a directory listing rather than a spec, it should be completely appropriate for them to re-open this issue to record the fact that the server is broken at the point in time at which they’re trying to access what they need. It does not seem appropriate to tell users to avoid reporting an issue when something they rely on and need to use isn’t working.
