**DLM** is a new proposed color space that stands for Dynamic, Luminance, Mix.

It can represent numerous colors using just three values:
`dlm(<wavelength>, <luminance>, <mix>)`
where `<wavelength>` is the wavelength of the dynamic/tunable primary in nanometers, `<luminance>` is the Y tristimulus value when converted to CIE XYZ, and `<mix>` determines the relative contribution of the dynamic/tunable primary and the fixed 650 nm primary. 0% mix means all optical power comes from the fixed primary (650 nm), and 100% mix means all optical power comes from the dynamic primary (380-650 nm).

Given a fixed primary `(fx, fy)` and a dynamic primary `(dx, dy)`, the resulting chromaticity can be calculated with:
```
x = fx*(1-m) + dx*m
y = fy*(1-m) + dy*m
Y = l
```
where `m` is `<mix>` expressed as a number within the range 0-1 and `l` is the Y tristimulus value normalized to the range 0-1.

DLM is intended for displays capable of producing the broad range of colors that spectral primaries can represent, far more than conventional RGB gamuts. Using the area enclosed by the CIE 1931 spectral locus and the line of purples as a reference, the chromaticities that DLM can represent cover approximately 98.93% of that area.

Because DLM can represent more colors than these gamuts, there will be automatic fallbacks to RGB depending on the system's hardware and its capabilities. The fallback process is as follows:
1. Use the CIE XYZ lookup table and interpolation as well as simple weighted average math to calculate the DLM color in xyY (as shown above) and then XYZ.
2. Use an XYZ -> RGB conversion matrix depending on the widest supported gamut available.
3. Convert linear RGB into RGB with a gamma transfer function and clip values to the range 0-255, then use `rgb()` or `color()` depending on the target gamut.

To create a gradient using DLM, interpolate between the xyY values of the two endpoints, then calculate the DLM value for each interpolated point on the line.

The working demo and its source code can be found by [clicking here](https://prototypestudios.neocities.org/dlm). The demo includes an interactive CIE 1931 chromaticity diagram, RGB gamut triangles for reference, textboxes to convert between DLM and RGB, and the source code used to implement the above algorithms. Feel free to experiment with these as much as you like!

## @Scratchy2 — 2026-08-20

While `xyz-d65()` can represent colors in the CIE 1931 color space, it cannot show how to reproduce them on a display that supports it. However, `dlm()` provides that same color in a physically meaningful format. It retains information that converting to `xyz-d65()` discards.

For example, `dlm(493.11910, 100%, 59.48544%)` shows exactly how to display the D65 white point, but converting this to `color(xyz-d65 0.9505 1.0000 1.0888)` loses the information needed to consistently display it. This leads to extra calculations that `dlm()` eliminates the need for.

## @Crissov — 2026-08-20

I’m not assessing the color space itself. I’ll just note that introducing wavelengths to CSS Color, which are essentially `<length>` (just always interpreted physically), would suggest a **new unit `nm` (nanometers)** needed to be added to CSS Values and Units, because having to write `0.000650mm` or `0.65e-3mm` instead of simply `650nm` seems just wrong. 

Since millimeters `mm` are currently the smallest metric unit, this would mean a gap would be left between them where micrometers should be. It would make sense to introduce `um` (since &mu; is unavailable on the restricted character set) then as well. However, I doubt anyone might actually prefer `0.650um`.

Alas, as far as I know, browsers internally represent `<length>` in a precision that would not be suitable for also covering wavelengths, so nanometers would need to be decoupled from other absolute length units. :(

## @facelessuser — 2026-08-22

Just some final thoughts.

1. It would be good if you posted your algorithm, either in a repository or something. I didn't really dig through the source on the webpage, as the concept was straightforward (for me): draw a line from 650 nm on the locus through the color to the wavelength on the other side of the locus, then calculate m. There are likely some nuanced decisions you've made in your code, or corner cases you've handled, that aren't immediately clear from the description on the site. So, really, what I'm suggesting is a more technical write-up or a code repository.

2. The term "dominant wavelength" is used, but I guess usually that refers to the wavelength on the locus that intersects with a line drawn through the white point and the color, but here we draw one through the 650 nm primary and the color. I'm not sure this is actually what people normally think of as the "dominant wavelength", but how it is derived is similar in a way.

3. As for M exceeding 1. After evaluating things more, I think some color spaces will have this, and it is perfectly fine. Display P3 extends outside the spectral locus a little. I believe this comes from how the primaries were selected and rounded, but it will produce some colors that, floating point-wise, will be outside the spectral locus. Rec. 2020 does this too, as it rides the line near red, etc.

4. There are multiple ways to detect line intersection with the locus: use a polygon intersection algorithm, use angles, etc., but most of these will only give a rough approximation. Linear interpolation between the points (whose relationship is not really linear) leads to only about 3 - 4 decimals of precision. If more precision is needed, once the wavelengths the line falls between are identified, the results could be further refined with bisection (or some other method) to a minimum precision. I think my test implementation gets out to around 14, but it could be reduced to a level sufficient for precision and performance.

4. Obviously, this system is ideal for colors within the spectral locus and will start to break down for colors outside. This is more a general note, not a criticism. There may be weak spots inside the locus, but I haven't really done an exhaustive analysis, and I haven't really dug through your site to look through your code for potential corner cases.

So to better understand the space, here's my [impelementation](https://facelessuser.github.io/coloraide/playground/?source=https%3A%2F%2Fgist.githubusercontent.com%2Ffacelessuser%2F03fa7645c98d005fe4bad95a78300bd6%2Fraw%2Fd1d691cb7436e371b19ce98f9152e18e83eeac40%2Fdlm.py) of the approach in a live playground. The implementation is based on the loose description on the DLM site. I'm sure there may be slightly different decisions on some small edge cases, and I'm most certainly approaching the intersection of the line and the locus differently, but it generally implements the idea faithfully enough so that I could understand how the space works.

Now, is this a good fit for CSS? I don't know if I'm convinced per se. This feels a bit more niche for most people, but the idea is neat. I can see it being easier to define a color in the locus for most colors, but most people will never use such colors outside Rec. 2020. Technically, you could work within xyY, but yes, it is easier to navigate in terms of wavelengths as long as the precision of the wavelengths fits your needs.
