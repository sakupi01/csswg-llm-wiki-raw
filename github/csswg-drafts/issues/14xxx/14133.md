https://drafts.csswg.org/css-color-4/#powerless-color-component

> When performing color space conversion to a cylindrical polar color space, user agents shall treat a hue component as powerless if the chroma (or other measure of colorfulness, such as saturation in hsl) is less than the epsilon (ε) specified for that color space. For example, a gray color converted into oklch() may, due to numerical errors, have an extremely small chroma rather than precisely 0%; as a result, the hue component is powerless.

https://drafts.csswg.org/css-color-4/#specifying-oklab-oklch

> Powerless hue ε	C <= 0.000004

So `hue` is powerless when chroma is smaller than `0.000004` but chroma itself is not set to `0`.
And any missing component is treated as `0` for the actual conversion math.

So `color(from oklch(0.5 0.000004 180) display-p3 r g b)` which should have a powerless `hue` still ends up as: `color(display-p3 0.38857936 0.38856994 0.38857244)`

Converting that to `hsl` for example results in `color(srgb 0.38858148 0.38856954 0.3885725)`.

-----

Shouldn't `chroma`/`saturation` also be set to `0` when it matches the powerless `hue` condition? Otherwise the outcome is a color with whatever hue `0deg` is for a given color space. This `hue` might itself be powerless, but when converting to polar spaces it will still surface.

## @romainmenke — 2026-07-04

It isn't obvious what to do about `hwb` where powerlessness results from the combined value of `w` and `b`. 


Currently I am using:

```js
if ((Math.max(0, (Number.isNaN(out[1]) ? 0 : out[1])) + Math.max(0, (Number.isNaN(out[2]) ? 0 : out[2]))) >= 99.999) {
	out[0] = Number.NaN;

	if ((Math.max(0, (Number.isNaN(out[1]) ? 0 : out[1])) + Math.max(0, (Number.isNaN(out[2]) ? 0 : out[2]))) < 100) {
		if (!Number.isNaN(out[1]) && !Number.isNaN(out[2])) {
			out[2] = 100 - out[1];
		} else if (!Number.isNaN(out[1])) {
			out[1] = 100;
		} else if (!Number.isNaN(out[2])) {
			out[2] = 100;
		}
	}
}
```

1. if `w` + `b` is greater than `99.999`
2. if `w` + `b` is less than `100`
3. if `w` and `b` are not missing
  3.1. set `b` to `100 - w`
4. else if `w` is not missing
  4.1. set `w` to `100`
4. else if `b` is not missing
  4.1. set `b` to `100`

## @facelessuser — 2026-07-06

I would think when w + b is very close or greater than 1 (or I should say 100 in CSS), you could assume the color is achromatic (hue is powerless). At least, that is what I do in ColorAide: https://github.com/facelessuser/coloraide/blob/main/coloraide/spaces/hwb/__init__.py#L51

A value of 100 is achromatic; anything greater, I think, is beyond maximum whiteness and blackness, so achromatic as well. You can count powerlessness very close to achromatic or make 100 a hard limit. Either seems like it would work.

> Shouldn't chroma/saturation also be set to 0 when it matches the powerless hue condition? Otherwise the outcome is a color with whatever hue 0deg is for a given color space. This hue might itself be powerless, but when converting to polar spaces it will still surface.

I'm not sure the hue matters in this case, because it is...well...powerless. If chroma is very small, the actual chroma shouldn't matter as the resultant hue is powerless regardless. If you force chroma to zero, then you just get whatever random hue your floating-point noise resolves to. Is that better or worse? Some spaces may always return 0 for the hue, but some may return something else.

I've turned off achromatic hues from being normalized to undefined.

```py
>>> c = Color('lch(50% 0.0000004 230)')
>>> c.clone().convert('oklch', norm=False)
color(--oklch 0.56897 0 226.09deg / 1)
>>> c.clone().set('c', 0).convert('oklch', norm=False)
color(--oklch 0.56897 0 170.54deg / 1)
```

You just get a different hue that doesn't matter, and affects the round-trip conversion some.

The actual zero percent chroma hue is dictated by whatever noise is in your calculation:

```py
>>> Color('white').convert('lch', norm=False)
color(--lch 100 0 0deg / 1)
>>> Color('white').convert('oklch', norm=False)
color(--oklch 1 0 167.47deg / 1)
```

## @romainmenke — 2026-07-06

It is true that none of this is visually significant after a single conversion that doesn't do anything else.

But when doing calc expressions in relative color syntax you might suddenly get unexpected results when between zero and the epsilon.

I am thinking of cases where the chroma/saturation of the input color is animated slowly while there is a calc expression that amplifies the chroma/saturation of the output color.

Such a transition would go from:
1. true achromatic
2. a `hue` of `0` but with a significant chroma making that color visible
3. the actual hue of the input color

With a hard transition between 2 and 3.

While with a forced chroma of `0` it would stay a true achromatic for a bit longer and then go immediately to the expected hue. Although also with a hard transition. There is no way to avoid the discontinuity in such cases, but we can try to make it less surprising.
