Take this example:

```css
.foo {
	width: calc(1px * random(property-scoped, 1, 10, 1) * hypot(random(property-scoped, 1, 10, 1), random(property-scoped, 1, 10, 1)));
	height: calc(1px * random(property-scoped, 1, 10, 1) * --hypot(random(property-scoped, 1, 10, 1), random(property-scoped, 1, 10, 1)));
	padding: calc(1px * random(property-scoped, 1, 10, 1) * --hypot-un(random(property-scoped, 1, 10, 1), random(property-scoped, 1, 10, 1)));
}
@function --hypot(--x <number>, --y <number>) returns <number> {
  result: sqrt(pow(var(--x), 2) + pow(var(--y), 2));
}
@function --hypot-un(--x, --y) {
  result: sqrt(pow(var(--x), 2) + pow(var(--y), 2));
}
```

The question is: what's the random() behavior here? In `width` the behavior is clear - you've got three random()s, all just `property-scoped`, so they'll all gain an `<ua-random-ident>` of `ua-width` and end up spitting out the same number. There's only 10 possible results, equivalent to `1 * hypot(1, 1)`, `2 * hypot(2, 2)`, `3 * hypot(3, 3)`, etc.

In 'height', the spec has [a clear answer, too](https://drafts.csswg.org/css-mixins/#evaluate-a-custom-function) (step 8 loads up the argument values into the --x and --y custom properties, then step 9 evaluates the styles on the hypothetical element created for the function) - the first random gets a `<ua-random-ident>` of `ua-height`, while the two random()s passed to the function end up with distinct `<ua-random-ident>`s (`ua---some-fn---x` and `ua---some-fn---y`, respectively). All three spit out distinct random numbers, so there's a thousand possible results, equivalent to `1 * --hypot(2, 3)`, `9 * --hypot(8, 7)`, `2 * --hypot(10, 6)`, etc.

In 'padding' the behavior is *also* clear - neither the arguments nor the result have types, so leave their values unresolved, and spit them out unchanged, just wrapped in the sqrt(...) math. So all the randoms again get parsed as part of parsing 'padding', all sharing the same `<ua-random-ident>` of `ua-padding`, and generate the same values; back to 10 possible results.

It seems a little unfortunate that what is mostly an internal detail of the function - whether an argument is typed or not - has such a dramatic effect on random(). The same effect can be observed for other cases where there is a difference between evaluating a value on the element vs on a child; for example, `font-size: calc(1em + --some-fn(1em))` will evaluate the *first* 1em in the context of "used in `font-size`", so it'll use the parent's font-size instead, while the *second* 1em will be evaluated inside the function (assuming the argument or return type is typed as `<length>`), and will end up being cyclic (relies on `font-size` but has `font-size` in its substitution context).

The author is writing these values all at the same level, in the same "mental space", and it's a little weird if they evaluate completely differently. I think it is a big author surprise, and makes custom functions more confusing to use in general.

It turns out that Chrome has already been violating the spec here; it evaluates arguments in the outer context, as if the custom function were a normal function with its arguments grammars dropped in place. (That is, it treats `--hypot()` as if it were a CSS-defined function with grammar `--hypot(<number>, <number>)`, more or less.)  I think this is probably a better behavior for us to adopt.

Agenda+ to see if anyone has any thoughts or objections before I make edits.

## @anttijk — 2026-08-26

Seems like the right thing to do. The current model is confusing and buys nothing (the context inside function does not differ from the outside one in ways that would be useful). I don't understand why default argument evaluation would have different behavior though. That is surprising and more complex to implement. 
```
@function --foo(--len <length>: 1em) { result: var(--len); }
font-size: --foo(1em);
font-size: --foo(); // cyclic
```

Note that Chrome currently also appears to resolve locals and the result descriptor in outside context.
