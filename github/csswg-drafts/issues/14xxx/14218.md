I've seen (and raised) issues that deal with specific problems with creating interactive controls in CSS pseudos (e.g. the other css-overflow issues I raised, as well as #12163) that impact dev experience, but I think it'd be useful to have a single issue for discussion around the overall impact on developer experience, since the main justification I've seen for creating scroll markers is that they improve dev experience.

I'm adding this issue mostly for the joint discussion tomorrow, but also to have somewhere to collect the reasoning & discussion around whether scroll markers/scroll buttons should be in CSS at all. The other issues sometimes seem to get bogged down in specific details, or move towards proposals to add increasing web platform complexity without taking a higher-level look at whether that complexity is warranted.

The main issues I see around the discussion of CSS scroll pseudos' effect on dev experience are these:
1. Having the browser generate scroll markers seems like a solution looking for a problem. It feels nice to think about not needing to generate a scroll marker for every slide (or every N slides), but in practice doing so isn't particularly difficult. Wanting to be able to generate html elements based on data is also something not at all unique to carousels.
1. The dev experience benefits of auto-generated scroll markers are focused only on experience at the time of initial authoring, and more so for one-off demos and experiments. The costs are focused on the developer experience of maintenance, debugging, accessibility remediation, focus management, and overall complexity/understandability of other DOM APIs and behaviors like eventing.
1. The negative impact on developer experience is centered on accessibility -- this makes accessibility issues harder to catch, harder to debug and reason about, harder (or impossible) to fix, and harder to code for in advance. The accessibility design of CSS scroll markers is fragile by design, pushes devs into an inaccessible path by default, and prone to breaking silently.
1. The design of CSS scroll markers is designed to be extremely flexible in its visuals and potential use cases, but extremely opinionated and uncustomizable in its keyboard behavior and semantics. This means that devs will author experiences where the semantics and interactivitiy are incorrect for assistive tech users, and have no recourse to fix it without opting out of CSS scroll markers entirely.

To note -- all of these problems stem from putting focusable, semantically interactive controls in CSS pseudo-elements instead of in HTML. None of the problems here are with having a platform carousel component, or with the scroll snap behavior on its own.

Some more details for each item:

### The benefit is focused on a negligible problem

This could just by my (and my current teammates') experience, but I've built quite a lot of carousels and a few carousel components, and generating scroll markers has never been a pain point. The methods I've used in the past include:
- markers are generated in JS using the exact same loop used to generate slides based on the data passed in from the CMS / wherever the site content is coming from.
- markers are generated using handlebars/JSX/whatever templating library is used for markup logic. Also uses the same loop used for slides.
- When authoring a reusable component, the component logic handles generating the right number of markers based on how many slides there are.
- When authoring a reusable component, the component consumer is expected to use the same loop for generating both slides and slide markers.

Essentially: in every production-ready carousel I've made, there is going to be some form of templating & looping used for slides, and the same logic is trivially easy to recycle for slide markers (this goes for whether there is one slide marker per slide, or one for N slides). When I asked my teammates if this had ever been a pain point for them, the answer was universally no as well.

### The dev experience conversation has been focusing only on initial authoring

I think part of the problem with the discussion around dev benefits (and maybe the spec process as a whole), is that it's very easy to over-prioritize dev convenience that is most noticeable when creating one-off experiments and demos. Having browser-generated scroll markers is pretty cool when creating a demo, but the maintenance, accessibility, and debugging problems don't get surfaced until it's been integrated into a mature system and been lived with for a while.

From my perspective, the hit to dev experience after initial authoring is orders of magnitude larger than the benefit at authoring time. Some examples include:
- `document.activeElement` is no longer guaranteed to be focusable. A lot of focus management libraries rely on this assumption.
- `event.target` in a focus event is no longer guaranteed to be focusable, same as above.
- Focus can change without firing focus events. This means what happens when the user presses keyboard keys can change without focus or the active element appearing to have changed.
- When trying to figure out what's going on with your events, with your focus management, and with keyboard behavior, most debugging pathways involve looking at `document.activeElement`, `event.target`, and `event.relatedTarget`. Now any element in the DOM tree could have extra hidden CSS pseudos that are the real focused element. This is already an area that can be very painful to debug, this just increases the number of gotchas and edge cases.
- When trying to understand why a screen reader is saying a specific thing, it's common to look at the semantics of the focused node (among other things).
- It is impossible to alter the semantics of the scroll markers and scroll buttons. Since CSS carousels are so flexible by design, this is a mainstream need. When I did a survey of carousels on some of the biggest sites (google among them), nearly all of them diverged from the default semantics and keyboard behavior of CSS carousels. This is not to say that CSS carousels picked the wrong semantics -- there is no single set of semantics and behavior that would capture a majority of carousel usage.
- There are a number of dev best practices for accessibility (creating the accessible name by referencing visible text on the page, 
- It is not possible to alter the semantics of the scroll markers, scroll buttons, and scroll marker groups (the role, the description, the disabled state). Given the huge variation in visuals and usage, as well as the huge variation in desired carousel semantics just based on the context in which they are used (e.g. compare the Netflix app to a store's product carousel, or an image carousel inside powerpoint to an image carousel on a static homepage), altering semantics is a 90% use case.
- It is not possible to alter the keyboard behavior and tabbability of the scroll markers/buttons. A maybe-surprising number of carousels in top 100 sites have fully non-interactive presentational scroll markers, and interactivity is baked into the slides themselves and prev/next buttons. It's also quite common to remove the prev/next buttons from the tab flow & a11y tree, and have the markers do the heavy lifting. In addition to that, a single-tab-stop arrow nav region is just as common and valid as each marker having its own tab stop -- the choice would depend on the usage, the context, and the target user demographic.
- There are a number of less common but still not uncommon page-level focus management concerns that rely on the ability to control the tabindex & tabbability of any given element. CSS carousels makes that impossible, and devs are unlikely to discover this before CSS carousels are widely used enough to appear in one of these cases. An example of this is arrowing between chat messages, where only the current message's content is in the tab order. (iframes and web components have been brought up as examples of where this is already hard, but iframes are notoriously hard/impossible to manage focus around and shouldn't be an excuse for making new markup equally impossible, and web components are not base components of the web platform and devs would presumably have chosen/authored a component library and focus management system in tandem).
- This does not work with user-side translation or newer AI string extracting tools (and is easy to miss with traditional methods of finding static strings in source code). Since most scroll markers in the examples do not have visible text, the problems with internationalization will disproportionately affect screen reader users.
- User-side tools also frequently rely on tracking `document.activeElement` and focus events -- one example would be extensions that render a custom visually emphasized focus outline.
- CSS column scroll markers cannot be given an accessible name at all.

(sorry that was a lot, but also only things that I can personally thing of; I'm sure there will be a whole lot more in practice, given how many core dev tools and workflows this disrupts WRT focus, keyboard, and semantics).

In my experience, by time spent on code is much more heavily weighted towards maintenance, bugfixes, and debugging. The initial authoring time is a small fraction of the hours spent on any given piece of UI. I would not consider a feature a net developer experience win if it provides debatable authoring-time benefit at the expense of increasing the complexity of the web platform, making debugging more difficult, stymying focus management, creating extra gotchas and edge cases, and making accessibility remediation difficult to impossible.

### There is an outsized negative impact on accessibility

The biggest obstacles are centered around the inability to customize semantics, the difficulty in authoring a robust accessible name, the inability to customize keyboard behavior, and the way CSS pseudoelements merely existing on a page breaks focus management scripts. These are all accessibility-related, and easily missible by a developer making a quick demo, or only focused on the sighted pointer experience.

The response to most of this has been "use elements in those cases", but in practice accessibility work often occurs later in the dev process, often after the point where bigger DOM changes are possible, or is done by a separate company/team than the one who created the carousel component. The response I've heard to that is "maybe those companies should fix their dev process, that's not a web platform concern." However, if we're evaluating the practical impact of CSS scroll markers on dev experience, I think it's worth looking at what that experience is like in reality rather than in the ideal. The reality is a lot of accessibility relies on remediating DOM that already exists, and CSS scroll markers make that impossible.

The things that are possible (naming scroll markers and scroll buttons with CSS content) are fragile and prone to silently breaking without tripping up accessibility checkers, and the spec design makes it impossible to follow best practices (using visible text as the accName).

Even in the cases where accessibility work has been made technically possible (e.g. the `event.pseudoTarget`), it has been made more complex to understand and accomplish. Now every focus management script will have an additional thing to check for, if the author even is aware they need to check for it.

### The design is visually extremely flexible but rigid in semantics and keyboard interaction

Going by the Chrome carousel gallery and various posts / code experiments I've seen online, as well as reviewing the variety of ways carousels are implemented in practice across popular sites, I've seen common use cases for all of the following implementations of scroll markers and scroll buttons:
- a list of links, each with their own tab stop
- a tablist of tabs, as a single tab stop with arrowing between scroll markers
- entirely presentational scroll markers that are unfocusable, do nothing on click, and are not in the a11y tree
- scroll markers that render text and get their accName from content
- scroll markers that should get their accName from the main heading within the associated slide
- scroll buttons that are not in the tab order, and are a convenience for mouse users
- scroll markers + scroll buttons that are both entirely removed from the tab order, with keyboard interaction based around the slides being in a focusgroup
- disabled scroll markers (e.g. in a multistep form, for steps that aren't yet reachable)
- scroll markers that are options in a listbox (unusual, but I've seen valid use cases)

Essentially "carousel" is not a semantic pattern, but a visual convention (or even several similar visual conventions) that can be applied to a wider array of very different user flows. A home page marketing carousel is not a Netflix TV show carousel is not a store product carousel is not set of content tabs is not a table of contents. There truly is no one 90% semantic usage for carousels. I don't believe there's even a 50% usage.

All other present-day web platform features that I can think of that provide interactive controls that are not standalone HTML elements are so specific and unchangeable that it's OK to lock developers out of semantic/keyboard customizations. Some examples include: the `<input type=date>` popup, the clear button on search inputs, up/down buttons in number inputs, or the default controls in a `<video>`. None would ever need a custom dev-provided accessible name, overridden keyboard behavior, or different semantics.

In contrast, carousels have fundamentally different semantic, keyboard, and assistive tech interaction needs depending on usage and context. Since visual interaction design is a flexible and high-context language while semantics/keyboard/assistive tech interaction design is a precise and specific low-context language, this approach only works for enabling visual creation while setting up devs to fail disabled users.
