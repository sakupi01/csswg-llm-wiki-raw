There has been previous discussion about allowing users to request stronger motion reduction than `prefers-reduced-motion` provides today. `prefers-reduced-motion` is intentionally a preference exposed to authors. Authors can decide how best to respond, potentially replacing motion with another presentation rather than simply removing all animation.

Separately, I think there is value in browsers providing a stronger **“no animations”** setting that does not depend on authors honoring `prefers-reduced-motion`.

If we support such a mode, I think there are two behavioral questions we should define.

## 1. What state should an animation have when the UA suppresses it?

Simply preventing an animation from running can produce undesirable results.

For example, consider content whose animation effectively does this:

**opacity: 0 → opacity: 1**

If the UA disables the animation while leaving it in its initial state, the content may remain invisible. Similar problems can occur when authors use animation to reveal, position, or otherwise transition content into its normal resting state.

Instead, should a UA-level “no animations” mode generally cause animations and transitions to resolve immediately to their appropriate **resting/final state**?

In other words, the behavior would conceptually be:

> Don't show the animation, but do show the state the page would have reached after the animation.

I intentionally say “appropriate resting/final state” rather than “jump to the last keyframe,” because this becomes more complicated for things such as:

* infinite animations
* `alternate` / `alternate-reverse`
* `animation-fill-mode`
* CSS Transitions
* Web Animations
* View Transitions
* animations whose state is controlled programmatically

There may therefore need to be different rules for different animation mechanisms.

But as a general principle, it seems preferable for a forced no-animation mode to preserve the intended resulting presentation wherever possible rather than freezing content in its pre-animation state.

## 2. Should “no animations” imply `prefers-reduced-motion: reduce`?

I think it should.

A user requesting **no animation** is necessarily also expressing a preference for **reduced motion**, although the inverse is not true.

Conceptually:

**no animations → prefers-reduced-motion: reduce**

but not:

**prefers-reduced-motion: reduce → no animations**

This would also allow sites that already handle `prefers-reduced-motion` well to provide their intentionally designed reduced-motion experience before the UA needs to intervene.

## Questions

1. Do we agree that a UA-level “no animations” mode should generally resolve animations to an appropriate resting/final state rather than simply freezing them at their initial state?

2. Should enabling such a mode cause `prefers-reduced-motion: reduce` to match?

3. If so, should the detailed behavior be defined independently for CSS Animations, CSS Transitions, Web Animations, View Transitions, and other sources of UA-controlled motion?
