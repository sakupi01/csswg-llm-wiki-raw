The viewport `<meta>` [parsing algorithm](https://drafts.csswg.org/css-viewport/#parsing-algorithm) only describes how to split the `content` attribute into property/value pairs and how to convert a value to a number. It does not define:

- what `initial-scale`, `minimum-scale`, and `maximum-scale` mean when they are omitted,
- the allowed range for these values,
- what to do when a value is out of range, or when the three values are mutually inconsistent (`minimum-scale > maximum-scale`, or `initial-scale` outside `[minimum-scale, maximum-scale]`).

MDN [documents](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/meta/name/viewport) an allowed range of `0.0`–`10.0` and says that when `maximum-scale` is smaller than `minimum-scale`, the behavior is *undefined*. Because the spec is silent, UAs resolve these cases differently, so authors cannot rely on a consistent result. This also interacts with UA-side zoom and accessibility policies.

Related: #12710 (viewport `<meta>` element needs a definition), #9004 (how `minimum-scale` determines the layout viewport), #5016 (`user-scalable=no` clamps min/max), #4995 (absent/empty viewport meta).

## 1. Missing values

Cases to define:

1. `initial-scale` omitted; only `minimum-scale` and `maximum-scale` specified.
2. Only `initial-scale` specified.
3. `minimum-scale` omitted; `initial-scale` and `maximum-scale` specified.
4. `maximum-scale` omitted; `initial-scale` and `minimum-scale` specified.

Proposal: during parsing, the UA fills in a default for every omitted property:

| property | default |
| --- | --- |
| `initial-scale` | `1.0` |
| `minimum-scale` | `0.1` |
| `maximum-scale` | `10.0` |

The UA may still alter these values later for user settings or accessibility (e.g. ignoring `maximum-scale`, or `user-scalable=no` policies).

Questions:

- Should a missing `maximum-scale` mean "the UA's maximum" rather than the concrete value `10.0`? Turning a missing `maximum-scale` into a finite number imposes a zoom limit that the author never requested. The same question applies to a missing `minimum-scale`.
- Should these defaults be normative, or is the exact value UA-dependent (like the default `980px` layout width)?
- Does a defaulted value participate in the sanitization in §2 in the same way as an author-specified value? For example, if `minimum-scale=2` is specified and `initial-scale` is omitted, should the default `initial-scale` of `1.0` be raised to `2`, or should the specified `minimum-scale` be reset?
- How does a defaulted `initial-scale` interact with `width`/`height`? When `initial-scale` is absent, the initial scale is currently derived from the layout width; defaulting it to `1.0` may change that.

## 2. Out-of-range and inconsistent values

Cases:

- A value is negative, zero, non-finite, or very large.
- `minimum-scale > maximum-scale`.
- `initial-scale` is outside `[minimum-scale, maximum-scale]`.

Proposal:

1. Replace any value outside the allowed range with its default from §1. (Alternative: clamp it to the nearest endpoint. The group should pick one.)
2. Enforce `minimum-scale <= initial-scale <= maximum-scale`, allowing equality because `minimum-scale=1, maximum-scale=1, initial-scale=1` is a common, valid pattern:
   - If the parsed `initial-scale` is within the allowed range, keep it, and if a specified `minimum-scale` or `maximum-scale` conflicts with it, reset that property to its default.
   - If the parsed `initial-scale` is out of range but `minimum-scale` and `maximum-scale` are valid, set `initial-scale` to `1.0` if `minimum-scale < 1.0 < maximum-scale`; otherwise set it to `minimum-scale`.
3. Resolve a remaining `minimum-scale > maximum-scale` conflict.

Questions:

- For an out-of-range value, should the UA clamp to the nearest endpoint or replace it with the default? Clamping preserves more author intent.
- When `initial-scale` conflicts with a valid `minimum-scale` or `maximum-scale`, should the UA move `initial-scale` into the range, or reset the conflicting min/max property to its default? Resetting a valid `maximum-scale=2` because `initial-scale=3` seems surprising; clamping `initial-scale` to `2` seems closer to author intent. For reference, Chromium currently raises `maximum-scale` to `minimum-scale` when both are specified, then constrains `initial-scale` to the resulting range; this is one possible policy.
- Is the allowed range `[0.1, 10.0]` or `[0.0, 10.0]`? MDN documents `0.0` as allowed, but a scale of `0` is degenerate. Should `0` be treated as invalid?
- Do these sanitization steps happen at parse time or later, when the initial viewport is computed? The answer affects the preload scanner and cases where `width`/`height` participate in determining the initial scale.

## 3. Relationship to `user-scalable`

#5016 notes that Chromium clamps min/max to the computed initial scale when `user-scalable=no`. If §1 and §2 define sanitization independently of `user-scalable`, the interaction should be specified explicitly (order of operations, and whether accessibility overrides are permitted). Since `user-scalable=no` and `maximum-scale` restrictions are frequently ignored by UAs for accessibility reasons, any normative sanitization should act as a floor on user zoom rather than a ceiling.
