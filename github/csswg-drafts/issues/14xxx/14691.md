A robust fallback strategy for anchor positioning means authors are writing things like `position-try-fallbacks: flip-block, flip-inline, flip-inline flip-block`. A quick code search on GitHub shows the majority of uses of `position-try-fallbacks` specify multiple fallbacks. 

A `flip-any` value would be a reasonable default for most cases.  `flip-any` captures the intention that the user is saying "I don't care about the specifics, just make sure it fits".

## The value

### 1. Defined order

We could specify this as a defined order, such as `flip-block, flip-inline, flip-block flip-inline`. If these 3 are included, all 4 corners are covered. I don't think there's a compelling reason to have `block` before `inline` or vice versa, but the combination should be last.

### 2. A magic value 

We could come up with an algorithm that attempts to intuit a logical order from what `position-area` is used or which insets use `anchor()`. This could even be left up to the UA to determine. It could remove no-op fallbacks, such as `flip-block` when `position-area: inline-start` is set. (Although I'm not entirely sure if these are no-ops, as `inset-inline-start: 20px` would also get flipped, and modify the IMCB.)

I have a preference for a defined order- I don't think the additional complexity will lead to significantly better or different placement, but will likely be a cause of confusion.


## Other considerations

1. If a user wants to prioritize one of the options, they could set `position-try-fallbacks: flip-inline, flip-any`.
2. It can be combined with any valid options, for instance `position-try-fallbacks: --ideal, flip-any, --last-choice`.
3. This should add each of the expanded options to the `position options list`, and not add `flip-any` to the positions options list. This would count as 3 items in the positions options list, not as 1. (If capped at 5 items, the options list could be `flip-any` plus 2 additional options. This should limit potential performance implications of the value.
4. When active, it should not match `@container anchored(fallback: flip-any)`, but rather the actual applied fallback.
