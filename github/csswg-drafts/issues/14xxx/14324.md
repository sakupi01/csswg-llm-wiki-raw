One of the complaints we got about the picker styling for `<select>` was the double-border effect of the drop-down being placed immediately adjacent to the button. Because jamming the picker right up against the button looks awkward, we propose a margin (which is a commonly used effect) of 4px. This also addresses the concern @jakearchibald raised in https://github.com/w3c/csswg-drafts/issues/14172 that when a picker jams up against the viewport edge, it's hard to know if it's overflowing or not.

```
::picker(...) {
  margin-block: 4px;
}
```

Note: Especially if we do this (but maybe even if we don’t), we should consider applying [`box-sizing: margin-box`](https://github.com/w3c/csswg-drafts/issues/5715) to the picker also.

When people use no gap between a picker and button, they are often using opinionated styles that combine the two into one visual shape. For example merging background colors and removing adjacent borders. 

<img width="330" height="314" alt="Image" src="https://github.com/user-attachments/assets/b3806a32-ea5e-4faa-9d4b-f6a1af987d8f" />

This styling can be used in menus or sometimes things that are made to look like tabs, but I'd argue it is way too opinionated for a UA stylesheet and the simpler version is too prone to bugs like I've shown above. That means that the picker gap should be >2px to disconnect the two from each other and avoid the need to merge the shapes.

## @stubbornella — 2026-09-09

I did a survey of a bunch of design systems. The picker margin is a little hard to figure out from source because it can be created with a lot of different properties, but 10 design systems document a numeric gap and **7 of 10 use a 4px gap**. 

| System | Gap | Mechanism |
|---|---|---|
| Ant Design | 4px | `offset: [0, 4]` |
| Polaris | 4px | `margin-block-start: var(--p-space-100)` |
| Zendesk Garden | 4px | floating-ui `offset(theme.space.base)` |
| Wikimedia Codex | 4px | `margin-top: 4px` |
| Arco Design | 4px | `top: 4px` |
| Porsche | 4px | `top: calc(100% + 4px)` |
| Carrefour | 4px | `margin-top: 4px` *(verify)* |
| Atlassian | 8px | "Popover offset: 8px below trigger" |
| Vant | 0 | panel sits flush at the bar's measured edge |
| gov.br | −2px | `margin-top: -2px` — deliberately overlaps the trigger's bottom border |

Many of the systems that explicitly publish their gap use 4px: Ant Design, Wikimedia Codex, Zendesk Garden, and Polaris. Atlassian is the lone outlier at 8px.

Reporting on the gap depends on a system explicitly naming it, through a positioning API or a literal margin, so the data is thinner for gap. Where the spacing instead emerges from a wrapper's padding, a shadow, or a positioning library's defaults, there is no single published value to read. As a result, we have less data for gap than other properties. Also, systems that rely on the native select, like Bootstrap, have styles for the in-page trigger, but leave the position of the picker to the operating system.

The tight end of this slider is where the design problems live. At +1px, 0 and -1px the trigger's border and the picker's border land on top of each other or within a hair of it — leaving a one-pixel sliver of background that reads as an artifact rather than a gap, fusing them into a doubled 2px line, or overlapping them. At all three the two sets of rounded corners meet without aligning, notching the seam. Solving that means restyling the join itself, and only one system in the survey does: some of Airbnb's selects drop the trigger's bottom border when the panel opens so the two merge into a single shape (a white "lid"). It works, but it is a strong stylistic commitment — the kind of opinion a UA default shouldn't impose on every select.

Many design systems use JS selects that rely on underlying libraries like popper, but those libraries do not explicitly set a gap. This means the values here were most likely explicitly chosen by these designers.
