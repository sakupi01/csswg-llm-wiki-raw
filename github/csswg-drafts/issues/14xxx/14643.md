(Written with help from GPT-6 Astra Extra High.)

Chromium 151 and WebKit 26.5 return `fallback` for this:

```js
const element = document.createElement("div");
element.setAttribute("data-a", "attr(data-a)");
element.style.setProperty("--result", "attr(data-a type(*), fallback)");
document.body.append(element);

console.log(getComputedStyle(element).getPropertyValue("--result"));
```

However, step 5 of [the attr() substitution algorithm](https://drafts.csswg.org/css-values-5/#attr-substitution) returns a CSS string when the type is omitted or `raw-string`. Only step 6 introduces the attribute substitution context used for cycle detection.

That appears to require `"attr(data-a)"` here: the inner bare call returns the attribute's literal text without recursively evaluating it or entering another guarded substitution.

Existing [attr-cycle.html tests](https://github.com/web-platform-tests/wpt/blob/46175634c0210e97365ef864020ff3be6358ea41/css/css-values/attr-cycle.html#L152) agree with the browsers, including a case added by [WebKit's transitive-cycle fix](https://github.com/WebKit/WebKit/pull/61321).

Should raw reads of an active attribute be rejected before step 5, matching browsers, or is their exemption from cycle detection intentional?
