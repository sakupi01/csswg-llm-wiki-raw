Follow-up to [this discussion](https://github.com/web-platform-tests/wpt/commit/f27723cf73a143a0ffea126c01095f4a32238d17#commitcomment-166897042) about the serialization of `transparent` as a component of a declared value for `background-color`, after a commit changing it to `rgba(0, 0, 0, 0)` rather than `transparent` (the keyword in lowercase, as specified):

  > > 1. Safari returns `transparent`
  > > 2. Firefox returns `rgba(0, 0, 0, 0)`
  > > 3. Chrome returns `initial`
  > >
  > > The initial value in the spec is `transparent`.
  > >
  > > Is it the correct change?
  >
  > `initial` is definitely wrong. I don't think we should use `transparent`-the-keyword for this, given the reasons explained in the commit message. But the spec probably should be clearer?

I do not really understand the reasons explained in the commit message.

The [related WPT test](https://github.com/web-platform-tests/wpt/blob/3127c3a492e63578ed2bf76e3d4bda805183b5a3/css/css-backgrounds/parsing/background-valid.html) expects `background-color` to serialize with `transparent` in other cases.

## @svgeesus — 2026-09-29

TL;DR the declared value is `"transparent"` and the computed and used value is  `rgb(0, 0, 0, 0)`

From [6.3 The `transparent` keyword](https://drafts.csswg.org/css-color-4/#transparent-color)

> The keyword transparent specifies a [transparent black](https://drafts.csswg.org/css-color-4/#transparent-black). It is a type of [`<named-color>`](https://drafts.csswg.org/css-color-4/#typedef-named-color).

From [6.1. Named Colors](https://drafts.csswg.org/css-color-4/#named-colors)

> CSS defines a large set of named colors, so that common colors can be written and read more easily. A `<named-color>` is written as an [`<ident>`](https://drafts.csswg.org/css-values-4/#typedef-ident), accepted anywhere a [`<color>`](https://drafts.csswg.org/css-color-4/#typedef-color) is. As usual for CSS-defined `<ident>`s, all of these keywords are [ASCII case-insensitive](https://infra.spec.whatwg.org/#ascii-case-insensitive).

> **The names resolve to colors in sRGB.**

and also, from [15.5. Resolving other colors](https://drafts.csswg.org/css-color-4/#resolving-other-colors)

> **The declared value of [transparent](https://drafts.csswg.org/css-color-4/#valdef-color-transparent) is "transparent"**

>  while the computed and used value is [transparent black](https://drafts.csswg.org/css-color-4/#transparent-black).

which takes us to [4. Representing Colors: the `<color>` type](https://drafts.csswg.org/css-color-4/#color-type)

> For easy reference in other specifications, opaque black is defined as the color rgb(0 0 0 / 100%); transparent black is the same color, but fully transparent—​i.e. rgb(0 0 0 / 0%).

which is not ideal, (it is defining the color but could be read as defining a serialized form) because 

[16.2.2. CSS serialization of sRGB values](https://drafts.csswg.org/css-color-4/#css-serialization-of-srgb) says

> For compatibility, the legacy form with comma separators is used; exactly one ASCII space follows each comma. This includes the comma (not slash) used to separate the blue component of [rgba()](https://drafts.csswg.org/css-color-4/#funcdef-rgba) from the alpha value.

Easily missed. I think 15.5 could be clarified:

> while the computed and used value is [transparent black](https://drafts.csswg.org/css-color-4/#transparent-black), which, (following [16.2.2. CSS serialization of sRGB values](https://drafts.csswg.org/css-color-4/#css-serialization-of-srgb)) serializes as `rgb(0, 0, 0, 0)`
