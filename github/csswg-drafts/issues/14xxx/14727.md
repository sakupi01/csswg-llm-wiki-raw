Spec Area of Issue:
https://www.w3.org/TR/css-fonts-5/#text-scale-meta

@DanielHerr wrote in the original `<meta text-scale>` proposal:
> I can't speak for how things are on iOS, but at least on Android, the system text scale feature is already unreliable in native apps. I'd estimate maybe 5% of native apps have issues with at least some part of their UI which necessitates [the user] going to settings and setting the font scale back to default to use them. 
 _Originally posted by @DanielHerr in [#12380](https://github.com/w3c/csswg-drafts/issues/12380#issuecomment-5006081989)_

I can speak to the iOS native app implementation of Dynamic Type, and have a similar concern that adopting extra large font sizes may force users to change the font size more frequently than is reasonable.

iOS first added the font size control in iOS 5 as an accessibility-only private API feature. It shipped in iOS 7 as the public API [Dynamic Type](https://developer.apple.com/design/human-interface-guidelines/typography#Supporting-Dynamic-Type). It still took a few years before most Apple apps supported Dynamic Type at the extra large AX1–AX5 settings. Third-party developers also claimed to support Dynamic Type, but often had serious bugs supporting the largest sizes. The short term result was that users had to frequently decrease their preferred system font size in order to get one app into a readable/usable state. iOS eventually solved this problem by allowing users to set an app-specific font size. However, I worry that this CSS proposal, by not requiring site-specific settings in the implementation, is going to risk the same user problem of frequent system or containing app font size changes. 

This isn't as much of a concern for iOS Safari, which already has a size picker*, so knowledgable users can scale things back down using site-specific settings, but this may break the user experience in other mobile browsers, or other apps (mobile and desktop) that contain web views. Imagine, for example, a news reader app where the app supported large font sizes, but a site it loaded resulted in overlapping text. There's no setting where the user could get both native app text and web site text at the largest supported reading size for both.

In the inevitable event that a web site claims to address large sizes but doesn't, depending on implementation details, there may be no escape hatch for the end user. 


**Technical Note:** Re: "size picker." At TPAC last week, @davidsgrogan objected to me referring to the iOS Safari **[ a- | A+ ]** buttons as a "font size picker." Although both types of zoom change the "font size", he wanted to make the distinction between viewport or pixel ratio scaling versus what Mac Safari calls "text-only zoom"… For the sake of simplification here, I will just call it a "size picker" not a "font size picker." I acknowledge it's not the same as "text-only zoom" so my phrase "scale things back down" will not be a lossless reduction, but it remains a site-specific escape hatch for users if `<meta text-scale>` results in overlapping text on a broken web site.

## @fantasai — 2026-11-09

The CSS specs generally don't mandate the granularity of user preferences. These are generally abstracted out -- the user's preferences for the current page are the only thing under consideration per spec. We could certainly recommend that UAs allow the user to adjust the text zoom on a per site basis, though. But the UX for that is up to the UA -- it's outside the scope of the CSS specs.
