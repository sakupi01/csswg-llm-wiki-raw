When the Backdrop Root isn't fully opaque, `backdrop-filter: blur()` doesn't hide the content behind the element. The blurred copy keeps the backdrop's partial alpha, so the sharp original stays visible through it, however large the blur radius.

Let me explain why this matters, because it might seem odd at first glance. Yes, it's true on the web, the page behind is usually opaque. Tho, it does show in two places:

- A Backdrop Root that isolates content from what's behind it, which is the point of having one. Blurring text in a transparent layer without also blurring the image behind it leaves the text readable ([Mozilla bug 2073435](https://bugzilla.mozilla.org/show_bug.cgi?id=2073435)).
- Translucent windows, where the root itself isn't opaque. Electron apps ([Chromium 380416865](https://issues.chromium.org/issues/380416865)) and GTK, which implements `backdrop-filter` with the same result ([GTK #8524](https://gitlab.gnome.org/GNOME/gtk/-/work_items/8524)), both hit this.


Step 7 of the [backdrop-filter operation](https://drafts.csswg.org/filter-effects-2/#backdrop-filter-operation) reads:

> Composite the contents of T' into element B's parent, using source-over compositing.

Chromium and Firefox both follow the spec, however it doesn't say whether this outcome is intended: it never mentions a backdrop that has its own alpha, or whether the unfiltered content stays underneath the result.


[testcase.html](https://github.com/user-attachments/files/34298824/testcase.html)

Each box is a Backdrop Root with a 70% alpha background and six sharp white lines, and a child on top with `backdrop-filter: blur(16px)` and `background: rgba(255, 255, 255, 0.1)`.

| Box | Chromium 156 | Firefox 159 |
|---|---|---|
| `opacity: 0.9` | lines visible | lines visible |
| `opacity: 0.5` | lines visible | lines visible |
| `will-change: opacity` | lines visible | lines visible |
| `filter: brightness(0.99)` | lines visible | lines visible |
| `mask-image` | lines visible | lines visible |
| `mix-blend-mode: screen` | lines visible | lines visible |
| `opacity: 0.999` | lines visible | blurred, see below |
| control: no Backdrop Root, opaque page behind | blurred | blurred |
| control: opaque box with `opacity: 0.9` | blurred | blurred |

About 27% of the lines' contrast survives, against an expected `(1 - 0.7) * (1 - 0.1)`, so the show-through follows the alpha of the backdrop and of the element. Firefox's `opacity: 0.999` result isn't a difference in behaviour: Firefox treats 0.99 and above as opaque, so no Backdrop Root forms and the blur sees the opaque page.

<img width="1120" height="270" alt="Image" src="https://github.com/user-attachments/assets/10b0589e-7fea-4b7a-8970-7821415e1516" />


Is this the intended result for a Backdrop Root that isn't opaque? If it is, a note in the spec would settle it for implementers, including non-browser ones like GTK. If it isn't, step 7 needs to define what happens to the unfiltered content.

replacing the backdrop instead of compositing over it would fix these cases, but source-over is also what makes `backdrop-filter: invert(100%) opacity(40%)` crossfade with the original. A plain replace would turn that into a hole, so a fix would need to know whether each see-through pixel got that way because of the filter or because the backdrop was already see-through
