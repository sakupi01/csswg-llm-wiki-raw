https://drafts.csswg.org/css-shapes/#typedef-basic-shape-rect

```
<ellipse()> = ellipse(
  <radial-size>?
  [ at <position> ]?
)
```

https://drafts.csswg.org/css-images-3/#typedef-radial-size

```
<radial-size> = <radial-extent> | <length [0,∞]> | <length-percentage [0,∞]>{2}
<radial-extent> = closest-corner | closest-side | farthest-corner | farthest-side
```

This means the spec allows `ellipse(closest-side)` and forbids `ellipse(closest-side closest-side)`.

But browsers agree to allow `ellipse(closest-side closest-side)` and reject `ellipse(closest-side)`:

```js
[
  CSS.supports("clip-path", "ellipse(closest-side)"),              // false
  CSS.supports("clip-path", "ellipse(closest-side closest-side)"), // true
]
```

The browser behavior makes total sense for `*-side`, but `*-corner` are weirder when only used in one axis.

What Firefox seems to do, and I plan to do in Servo, is that if you have e.g. `farthest-side closest-corner`, then the vertical radius is calculated as for `closest-corner closest-corner`. But of course, due to the horizontal axis being `farthest-side`, the ellipse may not actually pass thru the closest corner at all.

Is that OK? Or should `*-corner` be restricted to be lone, affecting both axes instead of being allowed per axis?

Also note https://drafts.csswg.org/css-images-3/#valdef-radial-extent-closest-corner doesn't make much sense when the values are per axis, since a single axis value can't decide the aspect ratio:

> If the shape is an ellipse, the ending shape is given the same aspect-ratio it would have if [`closest-side`](https://drafts.csswg.org/css-images-3/#valdef-radial-extent-closest-side) were specified.

## @Loirooriol — 2026-06-05

css-images-4 makes more sense, but it's still weird for css-images-3 to require 0 or 1 when browsers require 0 or 2.

Anyways we still need to decide what to do for the corner values. 

**Option 1**: they can only be used alone, since they set the radius in both axes

**Option 2**: they can be used per axis, resolving to the radius that would result if both axes were set to that corner value. If the other axis is actually set to something different, the ellipse may not go thru the corner.

**Option 3**: they can be used per axis, with some negotiation:
 - If both axes have the same corner value, then make the ellipse pass thru that corner, using the same aspect-ratio as for the matching side value (this is what the spec already says).
   What if the side value would have a degenerate ratio?
 - If both axes have a corner value, and they are different, then typically there will be no solution that goes thru both corners, so maybe make this syntactically invalid.
 - If only one axis has a corner value, resolve the other axis first, then resolve the axis with the corner value in a way that makes it go thru the corner.
   In degenerate cases with infinite possibilities, use the same aspect-ratio as above.
   What about degenerate cases that would result in an infinite radius?
