`param(--name, green)` looks like a fallback, but is actually an assignment.

All other functions in CSS that take a similar syntax (`var()`, `attr()` etc) are actually **references**, not assignments.
CSS assignment uses `:` to separate the key from the value, so I think `param(--name: green)` would read a lot more naturally.

There was a time I'd argue against non-comma separators on the basis of more complex parsing, but the ship has sailed with `if()`, and I think the rationale is even stronger here than for the `if()` condition.

This also provides a very natural syntax for multiple params in the same function, which I filed as a separate issue: #14276

## @tabatkins — 2026-09-10

I've slightly tweaked `param()` in recent edits so that, *without* the value, they get a default value from the same-named property; that is, `param(--foo)` will take from the `--foo` property if possible. With this change, the second argument is *much closer* to `var()`'s fallback value. (The precedence is a little different, but still.)

More generally, I'm fairly opposed to introducing novel separator characters. The "ship has sailed" with `if()`, sure, but that doesn't mean the doors are wide open for every other function. I feel pretty strongly that it's better for learnability if we avoid doing that as much as possible. (`if()` had some pretty unique complexity arguments going for it, which definitely don't apply here.)
