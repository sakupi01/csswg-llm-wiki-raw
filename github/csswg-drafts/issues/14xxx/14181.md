Using scroll-driven animations in conjunction with a `sticky` positioned layout is quite common, especially in "scrolltelling". It's often desired to tie the start of a range to the scroll position when an element becomes "stuck", and tie the end of the range to the position when it becomes "unstuck".

This is why we specifically added a note in the spec:

> Note: For [sticky-positioned boxes](https://drafts.csswg.org/css-position-3/#sticky-position) the 0% and 100% progress conditions can sometimes be satisfied by a range of scroll positions rather than just one. Each range therefore indicates whether to use the earliest or latest qualifying position.

While this currently work fine, it still requires authors to manage tying layout and range offsets together.
It would be a significant improvement to the interface if authors could simply write:

```css
.animated {
  animation-range: stuck;
}
```

And have that range automatically watch the scroll range during which the timeline subject is "stuck", exactly [like we exposed for container queries scroll-state](https://drafts.csswg.org/css-conditional-5/#stuck).

This should make a lot of cases both less error-prone + allowing much better ergonomics.
