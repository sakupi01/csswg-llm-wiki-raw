The AnimationTrigger [`reset`](https://drafts.csswg.org/animation-triggers-1/#valdef-animation-action-reset) action pauses the animation and sets its currentTime to 0. This will often have the effect of transitioning the animation from its [after phase](https://www.w3.org/TR/web-animations-1/#animation-effect-after-phase) (when it has finished) to its [before](https://www.w3.org/TR/web-animations-1/#animation-effect-before-phase) or [active](https://www.w3.org/TR/web-animations-1/#animation-effect-active-phase) phase. These phase transitions are [spec](https://drafts.csswg.org/css-animations-2/#:~:text=events%20to%20dispatch%20are)'d to dispatch CSS `animationstart` and/or `animationend` events.

This behavior can be gotten using just the Web Animations API (WAAPI). As we've modelled triggers to be external controllers that behave as if these APIs were invoked, I think we generally expect trigger actions to be naturally accompanied by `animationstart` and `animationend`. However, in the `reset` case, I think it's worth giving some thought to whether these events make sense.

Here is a (vibe-coded :)) [demo](https://codepen.io/awogbemila/pen/JoEEoJo) using the animation as a timer. After the animation starts, the user has the duration of the animation (5s) to perform some action(s) that resets the timer (i.e. the animation). If the action is not performed in that time limit, the animation finishes, `animationend` fires and the page updates the DOM due to the game being over. If the reset action caused `animationend` to be dispatched, the page would incorrectly think the game was over.

My proposal is that we suppress `animationstart` and `animationend` from firing due to the `reset` action.
