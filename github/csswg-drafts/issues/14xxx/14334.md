[§9.7 Balancing Flex Items](https://drafts.csswg.org/css-flexbox-2/#balancing) appears not to account for main-axis gaps, and this creates a conflict between two of its conditions once gaps are non-zero.

## 1. "Line size" ignores gaps

The line size is defined as:

> The sum of the flex item sizes of all the flex items in the sequence (the line size) do not exceed the inner main size of the flex container

Taken literally this excludes the `(n − 1) × gap` contribution of `column-gap`/`row-gap`, both for the feasibility condition and for the squared-error objective. Presumably gaps are intended to be included (they are for ordinary greedy line breaking in [§9.3 step 5](https://drafts.csswg.org/css-flexbox-1/#algo-line-break)), but the definition should say so.

## 2. The zero-sized-item rule can contradict error minimization when gaps are non-zero

The spec lists these as parallel conditions on the chosen assignment:

> - If a flex item's size is zero, the preceding sequence was not overflowing, and it could be assigned either to the end of the preceding sequence or the beginning of the next sequence, it is assigned to the end of the preceding sequence. Otherwise, it's assigned to the beginning of the next sequence.
> - Calling the difference between the line size and the flex container's inner main size a sequence's error, the sum of the squared error across all sequences is minimized.

With `gap: 0` these never conflict: moving a zero-sized item across a line boundary changes no line size, so the zero-item rule only ever picks among equal-error assignments. With a non-zero gap, moving the zero-sized item also moves one gap, which *does* change line sizes — so the two conditions can demand different assignments.

Example: inner main size `100`, `gap: 10`, item sizes `[70, 0, 20]`, two lines:

| Assignment | Line sizes (incl. gaps) | Σ error² |
|---|---|---|
| `[70]` / `[0, 20]` | 70 / 30 | 30² + 70² = 5800 |
| `[70, 0]` / `[20]` | 80 / 20 | 20² + 80² = 6800 |

The zero-item rule requires the second assignment (the preceding line `[70, 0]` is not overflowing and either placement is possible), while error minimization requires the first. Chrome (tested with Chrome for Testing 152) chooses the first, i.e. it treats minimization as taking precedence and the zero-item rule as (at most) a tie-break among equal-error assignments.

## Questions

1. Should the line size (for both feasibility and error) include main-axis gaps? (Presumably yes.)
2. When the zero-sized-item rule and error minimization conflict, which wins? Options:
   - (a) The zero-item rule is a hard constraint on valid assignments, applied before minimization (a literal reading of the current text).
   - (b) Minimization takes precedence; the zero-item rule (like the "most items on the first line" rule) only breaks ties among equal-error assignments — matching Chrome's current behavior. Note that under (b) the rule is fully redundant with the existing lexicographic most-items-on-earlier-lines tie-break, so it could simply be deleted.
3. If (a) is intended, note the implementation consequence: the constraint on valid sequence boundaries is not interval-monotone in the line end, which interferes with the totally-monotone/Monge structure that SMAWK-style optimizations (referenced in the spec's note) rely on. It is still implementable in O(k·n·log n) by handling boundaries that precede zero-sized items separately from the monotone scan, but the spec's "nearly linear" note may deserve a caveat.
