So... in #11185 we resolved that `:hover` / `:active` broke at top layer boundaries. We decided that that wouldn't affect how `mouseenter` / `mouseleave` etc worked, which is ok I guess, but a bit weird.

I don't _hate_ that behavior, but I'm bringing this up again because that discussion didn't mention a couple things:

 * That non-custom select doesn't behave like that at all. It seems to keep `:hover` while open and hovering the picker, at least in Chrome and Firefox. In Chrome it seems to keep it even when the mouse is elsewhere.

 * That we could've maybe achieved a reasonable result with `select:not(:open):hover` in the UA stylesheet? Ok, it's not _exactly_ the same, but... given the action of clicking on the select is the same as the action of clicking anywhere else on the page, it seems ok?

Maybe the ship has sailed, but maybe we could reconsider this? Am I missing something obvious?

Note that this only affects the "there's no custom `<button>` case". I think making them not consistent with `mouseenter` / `mouseleave` etc is rather unfortunate.

Anyways, I'd be ok keeping the behavior, but it seems we maybe overcomplicated the model a bit for nothing?

> That non-custom select doesn't behave like that at all. It seems to keep :hover while open and hovering the picker, at least in Chrome and Firefox. In Chrome it seems to keep it even when the mouse is elsewhere.

I don't have a preference on whether the appearance:auto behavior is changed or not, but actually determining whether the pointer is inside the native picker sounds hard, so hopefully we can avoid that with whatever we do for appearance:auto.

> That we could've maybe achieved a reasonable result with select:not(:open):hover in the UA stylesheet? Ok, it's not exactly the same, but... given the action of clicking on the select is the same as the action of clicking anywhere else on the page, it seems ok?

I don't think it would hurt to add `:not(:open)` to the hover and active styles, but if authors put their own hover or active styles on the select then they would have to also add `:not(:open)`, which they probably wouldn't just know they need to do - the current magic helps authors out.

> but it seems we maybe overcomplicated the model a bit for nothing?

I think that the benefits of the complicated model are:
1. Authors don't have to add `:not(:open)` and are less likely to accidentally create broken experiences.
2. Other cases of nesting top layer elements inside invokers are also fixed, which also might not have an `:open` selector to use when styling. I admit that there aren't other good examples of where this happens yet for other builtin elements, but authors could already be nesting popovers inside invokers.

The implementation complexity doesn't look like that much tome: https://chromium.googlesource.com/chromium/src/+/9a341b91cb6d194a326fb947554171d7befd36d9

## @mfreed7 — 2026-07-13

> Regarding the top-layer rules, I think they're reasonable? Top layer kind of conceptually breaks out elements from their parent in various ways already, like with overflow, clipping, masking and other things. This :hover/:active logic just expands on that.

+1 to this - this was roughly why the decision was made. Since popovers (and generally top layer elements) escape most/all of their ancestors and behave as if they're the last child of `<body>`, it feels weird to propagate user action pseudo states up to the element tree they escaped. This came up for `<select>` first, but I'm not in favor of making it magic for `<select>` only. I think it generally makes sense. E.g. you have a button which opens a popover, and you've placed the popover within the button because (other than `:hover`, etc.) it just works well like that. In most use cases, you don't actually want the `:hover` to propagate up to the unrelated/escaped thing.

I do get the argument that `mouseenter` doesn't match `:hover` now, but I'm not sure what to do about that. Perhaps that's actually a feature? It lets you opt back in to the "old" behavior (via JS), in the corner case that you want that?
