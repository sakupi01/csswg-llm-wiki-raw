I wrote an article on [the ideal height for custom select](https://jakearchibald.com/2026/goldilocks-select-height/), and it boils down to this:

```css
select::picker(select) {
  /* Prevent the picker getting too small */
  min-block-size: calc-size(fit-content, min(size, 12em));
  /* Prevent the picker getting too big */
  max-block-size: calc-size(stretch, min(size, 30em));
  /* Add a margin to the viewport, so it's clear the picker isn't overflowing the viewport */
  margin-block-end: 1em;
  /* Allow the margin to flip */
  position-try-fallbacks: 
    flip-block,
    flip-inline,
    flip-block flip-inline;
}
```

Are any of these worth baking in?

[The group has already resolved to adding something like the `flip-` stuff](https://github.com/w3c/csswg-drafts/issues/13541#issuecomment-4732677022), but what about the rest?

- **Prevent the picker getting too big** - Maybe this is too opinionated, but I figured I'd throw it in for discussion.
- **Add a margin to the viewport** - Even if the gap is small, I think it's useful to be able to tell that the picker isn't overflowing the viewport.
- **Prevent the picker getting too small** - This is the one I feel strongest about. Chrome includes `min-block-size: 1lh`, which isn't in the spec, but that seems far too small. Something like `calc-size(fit-content, min(size, 5lh))` seems more useful.

I don't have strong feelings about particular length values.

## @jakearchibald — 2026-07-30

I'm requesting three resolutions here:

1: Should we add `min-block-size: calc-size(fit-content, min(size, 5lh))` to the custom select picker UA styles? This prevents the picker becoming too small when scrolling/repositioning.

2: Should we add `margin-block-end: 1lh` or similar to the custom select picker UA styles? This lifts it off the viewport edge, making it clear it isn't overflowing. Depends on [13541](https://github.com/w3c/csswg-drafts/issues/13541#issuecomment-4732677022).

3: Should we add `max-block-size: calc-size(stretch, min(size, 15lh))` or similar to the custom select picker UA styles? This prevents a loooong select picker.

The video in the OP shows the before and after.

## @fantasai — 2026-07-31

The current sizing rule for `::picker()` uses `max-block-size: stretch`. However, because stretch is calculated against the containing block, which `position-area` restricts to the area below the in-page `<select>` button, it doesn't flip when expected. This is the core problem.

We suggest using `max-block-size: calc(100svb - 8px)` instead, which allows the picker to grow along with its max-content size, flipping when it overflows the preferred `position-area`, and finally growing to fill the viewport if necessary, but no further. (8px here represents 2x a default margin of 4px; we agree there should be one, and found 4px to be a common value.)

There's no need for a minimum size if we make this change. It uses basically no "magic numbers". And, in keeping with the idea of a light touch on the author's styles, this is the most generous max-size limit we can impose while ensuring the content remains accessible on small devices.

## @fantasai — 2026-08-04

So @jakearchibald and I had a chat about this issue yesterday and we concluded that we could solve it pretty well with the following changes:

- Resolve [#14008](https://github.com/w3c/csswg-drafts/issues/14008) by saying that the default alignment safety for anchored fixedpos allows overflow in the scrollable directions, but if you say `safe` then it pulls into the original containing block.
- [Add `box-sizing: margin-box`](https://github.com/w3c/csswg-drafts/issues/5715) and apply it to `::picker()`.
- Apply `safe` alignment + `box-sizing: margin-box` + `max-block-size: 100svb` to the picker (and no minimum size).
