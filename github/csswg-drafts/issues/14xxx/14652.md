[§ 9.9.3 Flex Item Intrinsic Size Contributions](https://drafts.csswg.org/css-flexbox-1/#intrinsic-item-contributions) says:

> The main-size max-content contribution of a flex item is the larger of its outer max-content size and outer preferred size if that is not an automatic size.

The min-content contribution is defined the same way.

Browsers do not do this. When a flex item's preferred main size is not automatic, Chrome, Firefox and Safari use that preferred size as its contribution, the same way CSS Sizing 3 defines contributions for any other box. A flex itemwhose content is larger than its `width` therefore does not make its container larger.

This matters for both container algorithms in § 9.9.1, and not only for the ideal one: the [Web-compatible Algorithm](https://drafts.csswg.org/css-flexbox-1/#intrinsic-main-sizes-compat) sums the items' "max-contentcontributions" as defined in § 9.9.3. An implementation that follows the spec literally therefore still gets results that no browser produces.

### Testcase

```html
<!DOCTYPE html>
<style>
  .wrapper {
    display: inline-block;    vertical-align: top;
    margin-right: 10px;
    background: linear-gradient(to right, green 40px, red 40px);
  }
  .flex { display: flex; }
  .item { width: 40px; height: 40px; flex: 1 1 0; }
  .padded { box-sizing: border-box; padding: 0 16px; min-width: 0; }
  .content { width: 100px; height: 20px; }
</style>
<p>There should be three green squares and no red.</p>
<!-- A: padding + content (16 + 24 + 16) exceed the 40px border-box width -->
<div class="wrapper"><div class="flex"><div class="item padded"><div class="content" style="width: 24px"></div></div></div></div>
<!-- B: content is wider than the 40px width -->
<div class="wrapper"><div class="flex"><div class="item"><div class="content"></div></div></div></div>
<!-- C: like A, but sized under a min-content constraint -->
<div class="wrapper" style="width: min-content"><div class="flex"><div class="item padded"><div class="content" style="width: 24px"></div></div></div></div>
```

| Wrapper width | A | B | C |
|---|---|---|---|
| Chrome 156 | 40px | 40px | 40px |
| Firefox 158 | 40px | 40px | 40px |
| Following § 9.9.3 | 56px | 100px | 56px |

Case A is a reduction of YouTube's masthead: its voice search button is a `width: 40px; flex: 1` item with `padding: 0 16px` around a 24px icon. Following § 9.9.3 makes the button 56px wide, and this was [reported against Ladybird](https://github.com/LadybirdBrowser/ladybird/issues/12967) as a web compat bug.

The same holds for multi-line min-content sizing. Subtest 1 of [css/css-flexbox/intrinsic-size/row-wrap-001.html](https://wpt.fyi/results/css/css-flexbox/intrinsic-size/row-wrap-001.html) expects a `width: 50px` item with 100px of content to contribute 100px. Stable Chrome, Firefox and Safari all lay out the container at 50px and fail that subtest. Of the test's five subtests, all three engines pass only subtest 3.

### Proposal

Define the main-size min-content and max-content contributions of a flex item as its outer preferred size if that is not an automatic size, and its outer min-content or max-content size otherwise, clamped by its min/max main size (including the automatic minimum size). In other words, use the CSS Sizing 3 definition of a contribution and drop the "larger of".

The clauses that cap or floor the contribution by the flex base size of non-growable or non-shrinkable items probably need to be reconciled with the algorithm Chrome shipped in #8884, which handles that case at the container level using the hypothetical main size. Subtests 2, 4 and 5 of row-wrap-001.html exercise those clauses, and all three engines fail them.
