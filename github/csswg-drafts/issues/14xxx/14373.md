background-clip: text in the [spec](http://drafts.csswg.org/css-backgrounds-4/#valdef-background-clip-text) is defined as such:
```
The background is painted within (clipped to) the intersection of the border box and the geometry of the text including any decorations and emphasis marks in the element and its in-flow and floated descendants. The text color has no effect on the painting of the background.
```

The spec only says 'the border box and the geometry of the text including any decorations and emphasis marks in the element and its in-flow and floated descendants' will affect the actual effect; does the opacity count?

If opacity counts, how many other css properties should count?

For example:
Some sites like this "https://next.mvsrgroups.com/en-us/kay-core-preview", use opacity to hide the bg-clip text element, and it works on Safari but does not work on my implementation in Chrome; I think we should clarify before I fix the 'bug'

## @tabatkins — 2026-08-26

> In particular, does the specification imply that previous rendered glyphs from an animation may remain visible when the element continues to contribute to the clipping geometry?

It directly states that all text currently rendered in the element counts, for the purpose of the clip shape. If you want some text to not affect the clip, it needs to not be rendered at all, such as with `display: none`. Merely changing the opacity still causes the text to be laid out and have geometry.

> Also, has the relevant background-clip: text specification language or its interpretation changed recently? If not, would the historical behavior of earlier Chromium versions indicate that Chromium had been implementing this differently for some time, and that the M150 change was correcting a longstanding implementation difference rather than introducing a new rendering behavior?

The spec has not changed in this regard for many years; you can see it in the blame: <https://github.com/w3c/csswg-drafts/blame/main/css-backgrounds-4/Overview.bs#L1056>

The most recent change was clarifying that decorations are included and the opacity of `color` doesn't affect things; this was added last year, but based on a resolution we made back in 2017 that just didn't get applied to the spec. This isn't relevant to the problem in this issue, tho, which is about `opacity` instead.

Just to simplify things, here's a test case demonstrating the issue. Per spec, all three words should render identically, getting the full rainbow effect.

[link to test case](https://software.hixie.ch/utilities/js/live-dom-viewer/saved/14845)
```css
<!DOCTYPE html>
<p>
<span style="opacity:1"></span>
<span style="opacity:.5"></span>
<span style="opacity:0"></span>
<span style="display:none"></span>
</p>
<style>
p {
width: min-content;
font-size: 30px;
font-weight: bold;
background: linear-gradient(to right, red, yellow, blue), silver;
background-clip: text, border-box;
color: transparent;
}
span::before { content: attr(style); }
</style>
```

## @mg-support-team — 2026-08-26

Thank you for the clarification. We performed some additional testing to isolate the rendering behavior further.

We have created an interactive test page that allows different properties to be applied to the descendants participating in `background-clip: text`:

**[Interactive test page — background-clip:text property testing](https://lab.mvsrgroups.com/reproductions/css/bg-clip-test)**

> **Note:** This test link will remain available until this case is closed.

A small sample test for the `transform` behavior can be performed as follows:

1. Set **Opacity** to a value other than `0` — `0.25`, `0.5`, or `1` (`1` is recommended).
2. Set any **Transform** value other than `none`.
3. Set any visible **Text Fill** color (`red` is recommended).

The background clipping can then be compared with the transformed text. The clipping geometry appears to ignore the applied `transform`.

The **Toggle Debug** option can be used for better visibility of the positioning and geometry differences.

Tested in **Chromium 152.0.7977.54**.

As we understand the specification and the clarification in this discussion, `opacity` itself should not affect whether text contributes to the clipping geometry. However, properties that affect the actual geometry or position of the rendered text, such as `transform`, should still be reflected in that geometry. Please correct us if our understanding of how `transform` should interact with the clipping geometry is incorrect.

<img width="1238" height="359" alt="Image" src="https://github.com/user-attachments/assets/6fd4fbc0-577e-4144-928c-caced3183afd" />

The attached screenshot was taken while the test website was in **dark mode**.

In the screenshot, the original rendered elements appear in **purple/magenta**, while the background clipped through the text geometry appears in **cyan/blue**. The two are visibly misaligned in several cases:

- The colon separators have a `transform` applied. The original purple colon is positioned correctly, but the cyan clipping shape appears at a different vertical position, as though the clipping geometry is not accounting for the `transform` applied to the element.
- Similar artifacts can be seen around the `0` digits and the labels (`Days`, `Hours`, `Minutes`, and `Seconds`). A cyan border or outline is visible around the purple text, indicating that the geometry used for the background clipping does not exactly match the geometry and position of the text as it is actually rendered.

This appears to be different from the expected behavior regarding `opacity`. While `opacity` may be ignored when determining whether text contributes to the clipping geometry, the resulting clipping geometry should still correspond to the actual geometry and positioning of the participating text. The visible cyan regions suggest that some geometry- or position-affecting properties may not be applied consistently when constructing the clipping area.

Separately, our team has already found a CSS workaround for our production website. Even though we believe the behavior above is a rendering error, we can avoid the visible artifacts by removing the `background-clip: text` effect after the original elements have appeared following the color transition.

That would resolve the issue on our website for now. Please let us know whether you would prefer us to proceed with that workaround, or whether you would like us to keep the current implementation in place while this issue is investigated and closed.
