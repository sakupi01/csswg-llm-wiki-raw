Currently, [css-color-4 requires UAs to implement one of three GMAs](https://drafts.csswg.org/css-color/#gamut-mapping): MINDE, EdgeSeeker, Raytrace.

However, what we _actually_ care about is not whether UAs use a specific algorithm, but that a good output color is used that preserves lightness (primarily) and hue (secondarily) almost exactly, and does not reduce chroma more than is necessary ([as happens with naive chroma reduction](https://drafts.csswg.org/css-color/#GM-excessive-reduction)).

We could compute the maximum L and H errors for these three algorithms, and specify that UAs must instead preserve these thresholds, plus something to ensure C is not reduced more than is needed.

Or, perhaps a hybrid: either use one of these three GMAs, or feel free to use your own as long as it follows these requirements.

I’m thinking this could give UAs some freedom, while preserving the spirit of gamut mapping, and potentially making it easier for UAs to implement.

@svgeesus disagrees, so I’ll let him speak on his rationale.

If performance of the GMAs is still a concern then I think this a good idea. [OKLCh Halley](https://github.com/w3c/csswg-drafts/issues/10579#issuecomment-4952590574) is faster than Raytrace (the fastest algorithm that doesn't use a cache) so I don't see why UAs should be limited to using slower algorithms.

Even if this proposal doesn't make it into the spec I'm interested in knowing what thresholds would be acceptable as I'm working on a couple of cached and non cached algorithms that are faster than EdgeSeeker and OKLCh Halley.

## @facelessuser — 2026-09-28

Admittedly, the biggest benefit of approaches like Ray Trace, MINDE, etc., is that they are generic, and you don't have to invent a new algorithm if the current perceptual space gets replaced or the possible perceptual spaces in which you can gamut map get expanded in the future.

With that said, if Oklab is the only target, I see no reason why a more specialized, Oklab-specific approach should be denied if it performs as good or better. Clearly defining what is "as good as or better", I guess, is the challenge, but in principle, I don't see why a faster approach should be disallowed.

## @LeaVerou — 2026-09-28

A trivial way to define the thresholds is to define them as the maxΔL, maxΔH, maxΔC of all three algorithms. Hopefully there's a better way that is independent of them, but worst case, we could always fall back to that.

And yes, I agree that UAs should be able to use better algorithms if they perform at least as well.
