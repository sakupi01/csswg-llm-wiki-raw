In CSS Color 4's section on [powerless color components](https://drafts.csswg.org/css-color-4/#powerless) it states:

> When changing a powerless hue component to a missing component, the chroma (or other measure of colorfulness, such as saturation in hsl; see analogous components) is set to zero to avoid amplifying floating-point noise. Negative values are not clamped to zero, this value is only set to zero when it is larger than zero but smaller or equal to ε

However, the specific algorithms (both normative and non-normative) don't seem to perform this zeroing.

For [Converting Lab or Oklab colors to LCH or OkLCh colors](https://drafts.csswg.org/css-color-4/#lab-to-lch), the algorithm is:

> C = sqrt(a^2 + b^2)
> if (C > epsilon) H = atan2(b, a) else H is missing
> L is the same
 
To adhere to rule, it should probably be,

> C = sqrt(a^2 + b^2)
> if (C > epsilon) H = atan2(b, a) else H is missing and C = 0
> L is the same

For [Converting sRGB Colors to HSL](https://drafts.csswg.org/css-color-4/#rgb-to-hsl), the relevant part of the algorithm is:

>    if (sat <= epsilon) {
>        hue = NaN;
>    }

and should probably be

>    if (sat <= epsilon) {
>        hue = NaN;
>        sat = 0;
>    }

I will say, I don't really understand what the HWB code should be given the pseudo-code at the end of https://drafts.csswg.org/css-color-4/#powerless, but some updating https://drafts.csswg.org/css-color-4/#rgb-to-hwb with it would be very helpful.

## @romainmenke — 2026-09-28

> I will say, I don't really understand what the HWB code should be given the pseudo-code at the end of https://drafts.csswg.org/css-color-4/#powerless

In HWB it is possible to have an achromatic color (`W` + `B` equal or greater than 100) that also has a missing `W` or `B`.

So the pseudo code tries to describe how to deal with that.

If neither is missing, `W` and `B` can be normalized by setting `B` to `100 - W`.
If either is missing, set the non-missing one to `100`.

For `hwb` at least it is important to only do these steps when between the epsilon and 100 as values larger than 100 are possible.

In my implementation I also only set `s` or `c` to zero when it has a value between zero and epsilon. Negative values (if those are even possible) are preserved.

If there is a better way to describe this, please make a suggestion :)

## @Zaggy1024 — 2026-10-29

Not sure if this deserves its own issue, but it seems related to the discussion here. I'm wondering whether `rgbToHsl()` should have some epsilon when choosing whether to remove saturation:

```js
        sat = (Math.abs(light) <= epsilon || Math.abs(1 - light) < epsilon)
            ? 0
            : (max - light) / Math.min(light, 1 - light);
```

The specific case that brought this to my attention was this test case in WPT:

https://github.com/web-platform-tests/wpt/blob/ce5ca39646886a9349fc42913f843ec6e1c8a36f/css/css-color/parsing/color-computed-color-mix-function.html#L609

In Firefox, which seems to be where the test originated, 32-bit floating point precision just happens to treat this as pure white, but not because the conversion to sRGB actually produces `[1, 1, 1]`. I'm looking at bumping the intermediate precision of color conversion in Ladybird up to 64 bits, which gets us to pass every subtest in that WPT other than that single line, since rounding error in the D50->D65 adaptation, conversion to linear sRGB and gamma encoding produces values slightly under 1.

I wonder if this points to the expectation being wrong (or implementation-defined), or if this is worth defining.
