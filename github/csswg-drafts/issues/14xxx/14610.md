Opening this to seek WG direction on reintroducing a `kashida` value to `text-justify` (removed in 2013) and adding a companion `text-kashida-space` property.

Proposed spec text is available on the branch [`hjanuschka:text-justify-kashida`](https://github.com/hjanuschka/csswg-drafts/compare/w3c:main...hjanuschka:text-justify-kashida) and will be opened as a PR once the WG has signaled direction here.

## Proposal

- `text-justify: kashida` — justify by inserting cursive elongation (kashida) at a limited number of positions per word, with inter-word spacing as fallback. Insertion position selection is UA-defined.
- `text-kashida-space: <percentage>` — controls the ratio of elongation to word-separator expansion. Initial `100%`, clamped to `[0%, 100%]` at computed value.

The editor who committed the removal said during the same meeting:

> fantasai: "...and in Arabic, ideally, spaces vs. cursive elongation (Kashida)"

Three concrete objections were raised, in order:
1. jdaggett (Mozilla) — the script-categorization appendix behind the inter-ideograph / inter-cluster values was unclear and non-interoperable.
2. "can't be called Kashida (it's Latin)" — the name was objected to.
3. Bert — "not widely supported, but neither is kashida."

The implementation count was the deciding factor. That was 2013.

## Why now

Objection (3) is answerable now:

- **Blink implementation**, feature-flagged, in review: https://chromium-review.googlesource.com/c/chromium/src/+/7957320 ([crbug.com/41431127](https://issues.chromium.org/41431127)). Full WPT coverage for parsing, interpolation, priority scheme, ZWNJ/ligature/bidi edge cases, and the font-safety fallback.
- **De-facto algorithm** shared by IE, Word, LibreOffice, and DirectWrite. Khaled Hosny — author of Amiri and the implementer of LibreOffice's kashida support — has publicly confirmed the algorithmic lineage on the Chromium bug.
- **Engine-neutral reference** at [kashida-rs](https://crates.io/crates/kashida-rs) for cross-engine validation.
- **Pre-built demos** including macOS binaries and a side-by-side rendered/expected sampler at https://static.januschka.com/i-41431127/

The design hews deliberately close to fantasai's 2007 prose on the key points: UA-defined insertion positions, font-aware fallback, limited elongation.

Objection (2) is a weaker argument now than it was in 2013: `kashida` has shipped as an author-visible value in IE 5.5 through 11, has twenty years of precedent in Word's UI, and is the term used in Unicode (U+0640 ARABIC TATWEEL is colloquially "kashida"). Keeping the historical name is also the lowest-friction path for authors migrating from IE/Edge Legacy content.

Objection (1) — the ad-hoc script categorization — does not apply here: this proposal does not reintroduce `inter-ideograph` or `inter-cluster`, nor does it depend on the script-category appendix. `kashida` is defined by typographic effect, not by script taxonomy.

## Why an explicit value

Kashida is a deliberate typographic choice, not a universal default. Reasons the design keeps it author-controlled:

- **Compat.** Every page that uses `text-align: justify` on Arabic content today renders without cursive elongation. Changing that implicitly would alter the rendering of the existing Arabic web overnight, with no author opt-out short of overriding `text-justify`.
- **The companion property requires it.** `text-kashida-space` is only meaningful against an explicit mode; it has no coherent meaning for `auto`.
- **Typography is font- and context-sensitive.** Some fonts (notably Nastaliq faces such as Noto Nastaliq Urdu) do not render well with naive kashida insertion; some editorial styles (long-form prose, calligraphic headings) prefer kashida while others (code, UI chrome) prefer spacing. Kashida ratio also varies by convention: InDesign defaults to roughly 50% kashida / 50% spacing. These are author decisions, not UA defaults.
- **Consistency with the shipped lineage.** IE 5.5-11, Word, and LibreOffice all expose kashida as an explicit, author-controlled mode. There is no precedent for an opaque `auto` behavior silently elongating Arabic text, and no author expectation that it would.

## What the proposal does not define

The glyph insertion-point selection algorithm is intentionally left UA-defined, flagged with a visible `Issue` note in the spec text. This preserves the latitude fantasai's 2007 prose explicitly gave the UA ("the prioritization of kashida points is UA-dependent"). Rationale:

- Insertion rules are tightly coupled to font capabilities and language-specific conventions. Khaled Hosny's [Raqim writeup](https://aliftype.com/blog/introducing-raqim-kashida/english) argues persuasively for multiple rule sets rather than a single canonical algorithm.
- The desktop implementations (IE, Word, LibreOffice, DirectWrite) share an informally documented priority scheme that we could later capture as informative guidance, but committing to a specific normative algorithm now risks locking out future font-specific improvements.

## Questions for the WG

1. Is there appetite to reconsider `kashida` given the implementation and the archival record above?
2. `text-kashida-space`: keep as a separate property (matches IE's shipped surface), or encode as a function on `text-justify`?
3. Clamping vs parse-time rejection for the `<percentage>` value (currently specified as clamp-at-computed, matching `opacity`).
4. Should an informative appendix capture the IE/Word/LibreOffice/DirectWrite priority scheme as non-normative guidance?

Happy to iterate on the spec text in the branch, and happy to split `text-kashida-space` into a separate issue/PR if the WG prefers to consider them independently.
