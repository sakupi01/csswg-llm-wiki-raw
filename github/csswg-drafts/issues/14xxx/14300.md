So for context, this discussion comes from [this Firefox commit](https://phabricator.services.mozilla.com/D317242).

Consider this:

```css
z-index: calc(10% / 10%);
line-height: calc(10% / 10%);
opacity: calc(10% / 10%);
```

It seems to me these should all behave identically, either computing to `1` (`z-index: 1` / `line-height: 1` / `opacity: 1`), or being rejected?

That doesn't match browser behavior tho. There's some informal notes in https://drafts.csswg.org/css-values-4/#calc-simplification about how percentages generally might block simplification vs. not:

> However, "raw" percentages—​ones which do not resolve against another value, such as in [opacity](https://drafts.csswg.org/css-color-4/#propdef-opacity)—​might not block simplification.

However browsers behave differently here, and it's unclear from the spec what the right behavior is.

Similar weird example would be [this test](https://searchfox.org/firefox-main/rev/b38f633bdaaa555f64abe8095bbf7ad09ac0d80d/testing/web-platform/tests/css/css-values/typed_arithmetic.html#46), effectively `line-height: calc(10% / 1px)`, expecting it to compute to a number:

```html
<!doctype html>
<style>
 body {
   font-size: 10px;
 }
 #target {
   line-height: calc(10% / 1px);
 }
</style>
<div id=target>What's my line height?</div>
<pre><script>
  document.writeln(getComputedStyle(target).lineHeight);
  document.writeln(target.computedStyleMap().get("line-height").toString());
</script></pre>
```

I think making it compute to a number and making the percentage disappear (what Chromium does) is wrong. Because percentage line-heights generally inherit differently...

## @tabatkins — 2026-08-09

* `z-index: calc(10% / 10%);` - invalid (type resolved to `<number> with a hint of "percent"`, which *does not* match `<number>` in this context as %s aren't normally valid; see [Typed OM's "match" algo](https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-match))
* `line-height: calc(10% / 10%);` - valid, equal to 1 (it's a `<number> with a hint of "length"`, which per ["match" algo](https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-match) is okay here, as %s are normally resolved against `<length>` in this context). Simplifies at computed-value time, as %s are resolved at computed-value time against font-size.
* `opacity: calc(10% / 10%);` - valid, equal to 1 (`<number> with a hint of "percent"`, which is valid in this context per ["match" algo](https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-match)). Also simplifies at computed-value time.

## @tabatkins — 2026-08-19

I'll go dig it up, but: no, it doesn't complicate TypedOM at all. Building a calculation tree that contains percentages is just fine in all cases, assuming you use your percentages consistently; it's just when you *apply* it to a property that we check if the numeric type is okay with a percent hint existing or not.

(Like, `(10% + 10px) / (10% + 10deg)` is illegal to even construct, because the numerator's type is length with a "length" hint, and the denominator's type is angle with an "angle" hint, and when you divide we "multiply two types" which sees the inconsistent hint and fail the operation. But `10% / 10%` is always valid to construct, with a type of number with "percent" hint, and we'll check if that's actually okay when you apply it to a property and we have grammar knowledge.)

## @Loirooriol — 2026-09-01

Just to double-check I understand it correctly, https://github.com/w3c/csswg-drafts/issues/14300#issuecomment-5233307912 is actually a bit more nuanced, because

 - `line-height: calc(10% / 10%)` is only 1 if `font-size` isn't 0. Otherwise it produces NaN (behaving as 0).
 - `line-height: calc(0% / 0%)` is NaN (behaving as 0) regardless of `font-size`
 - `opacity: calc(10% / 10%)` is always 1, since the percentage does not resolve into a length.
 - `opacity: calc(0% / 0%)` is NaN (behaving as 0)

Then, for `z-index: calc(10% / 10%)`, since the property doesn't understand percentages at all, we can't know if the result should be 1 or NaN. Therefore, treating it as invalid syntax makes sense to me, @kizu.

## @tabatkins — 2026-09-02

> I think it is unfortunate that z-index: calc(10% / 10%) will not work while in other places it will. I imagine authors will stumble upon this eventually.

How do you imagine this actually happening for an author? Authors don't just write numbers randomly; percentages *mean* something, and someone would only write a percentage if they were trying to *use* what percentages meant there.

I don't think anyone would ever actually write a direct "% / %" type of expressions, that's just a number and equally easy to write by just omitting the `%`s, but if they're writing something more complex where the values are actually being added to something, the % has to fail there because it's meaningless in this context.

Allowing someone to safely use %s in a meaningless context like this, while still disallowing it in other cases where it's not safe, *is* possible to do in a consistent manner, if I overcomplicate the type system sufficiently. (So I can tell the difference between a % that *must* be consistent with a particular type due to addition with a non-% type, vs a % that's just relative to some type due to contextual rules.) I just don't think it's remotely worth it, just to allow an author to write a nonsense no-op expression where they could have instead just used numbers.

## @dbaron — 2026-09-09

So my mental model of the approach we were taking to support unit division (and general unit algebra) in `calc()` is that we can stop applying anything property-specific *inside* of the parsing of a `calc()` expression and apply the property-specific logic only to whether the toplevel type of the `calc()` matches what the property expects.  Also, the only thing that converts a «[ "percent" → 1 ]» type into a percent hint is the [add two types](https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-add-two-types) operation, which allows developers to use unit algebra (such as multiplying by a ratio of two values that are not related to the property but are the same type) in as many cases as possible.  The one possible addition would be to add a `number` value to percent hints as well -- this would improve the unit algebra for properties where percents and numbers are compatible (which definitely includes `opacity`; I'm not sure about `line-height`).

I think the reason the "percent hint" concept exists is to support this model where the property-specific logic is applied to the root of the parse tree after parsing and typing the entire expression.  I think if we want to apply property-specific syntax rules at the leaves rather than at the root of the tree, we don't need the "percent hint" concept at all.  So I'm not sure what you mean by making the percent hint per-syntax-component.

As to the original examples:
```css
z-index: calc(10% / 10%);
line-height: calc(10% / 10%);
opacity: calc(10% / 10%);
```
I'd like to see all three of them be allowed.  The individual `10%` values would all type as «[ "percent" → 1 ]».  The `10% / 10%` values would thus type as «[]» with no percent hint since no percent hint was ever created by the "add two types" operation, and the overall type of `calc(10% / 10%)` is «[]» (regardless of property), which is accepted by any property that accepts `<number>`.
