## Motivation

CSS can increasingly produce and manipulate typed numeric values declaratively. In particular, typed `attr()`, CSS math functions, and rounding functions allow values originating in HTML attributes to participate directly in CSS calculations.

However, a numeric result cannot currently be used as generated textual content.

For example, given domain data in markup:

```html
<div class="rank" data-min="37" data-max="52"></div>
```

CSS can derive a percentage and use it for presentation:

```css
.rank {
    --ratio: calc(
        attr(data-min type(<number>))
        / attr(data-max type(<number>))
    );

    background: hsl(
        calc(var(--ratio) * 120),
        100%,
        50%
    );
}
```

But the same derived value cannot be emitted as generated text:

```css
.rank::before {
    content:
        round(
            nearest,
            calc(
                attr(data-min type(<number>))
                / attr(data-max type(<number>))
                * 100
            )
        )
        "%";
}
```

Conceptually, the desired generated content is simply:

```text
71%
```

Today this requires either duplicating the derived value into markup/string data, generating an additional custom property suitable for textual use, or involving JavaScript.

This creates a composability gap: CSS can consume the source value as a number, perform arithmetic on it, round it, clamp it, and use it to derive other presentation values, but cannot serialize the resulting number as generated text.

## Current grammar

CSS Generated Content currently defines `<content-list>` approximately as:

```text
<content-list> =
    [
        <string>
      | <image>
      | <attr()>
      | contents
      | <quote>
      | <leader()>
      | <target>
      | <string()>
      | <content()>
      | <counter>
      | <symbolic-counter-style>
    ]+
```

This proposal would add `<number>` as an allowed content item.

Conceptually:

```text
<content-list> =
    [
        <string>
      | <number>
      | <image>
      | <attr()>
      | contents
      | <quote>
      | <leader()>
      | <target>
      | <string()>
      | <content()>
      | <counter>
      | <symbolic-counter-style>
    ]+
```

## Proposed behavior

When a `<number>` occurs within `<content-list>`, its computed numeric value would be serialized to its CSS textual representation (according to the appropriate CSS serialization rules) and inserted as textual generated content.

For example:

```css
.example::before {
    content: 123;
}
```

would generate:

```text
123
```

Likewise:

```css
.example::before {
    content: calc(100 / 4) "%";
}
```

would generate:

```text
25%
```

and:

```css
.example::before {
    content: round(nearest, 72.6) "%";
}
```

would generate:

```text
73%
```

The primary motivation is composition with existing typed CSS values rather than introducing any new calculation or conversion mechanism.

For example:

```html
<div data-min="37" data-max="52"></div>
```

```css
div::before {
    content:
        round(
            nearest,
            calc(
                attr(data-min type(<number>))
                / attr(data-max type(<number>))
                * 100
            )
        )
        "%";
}
```

could generate `71%` entirely from the source attributes, without requiring JavaScript or a duplicate string representation of the derived value.

## Why handle this in `content`?

I am not proposing general-purpose type coercion between CSS data types.

Instead, this proposal is narrowly concerned with a property whose purpose is already to generate content.

The `content` property already supports several non-literal-string constructs whose resolved value contributes textual generated content, including counters, quotes, and attribute values. Allowing a computed `<number>` to produce an anonymous inline box containing its serialized representation seems consistent with that role.

**Handling serialization at this sink also avoids requiring every feature that can produce a numeric value to independently provide a string-conversion mode.**

For example, a value produced by `attr()`, `calc()`, `round()`, `min()`, `max()`, `clamp()`, or a typed custom property could all participate without requiring conversion syntax specific to each producer.

## Existing workaround

An author who controls the generation of the markup can currently provide both numeric and textual representations separately, for example:

```html
<div
    data-rank="71"
    style="--rank: 71; --rank-text: '71';">
</div>
```

or generate the desired string using script.

Besides duplicating state, this moves what is fundamentally presentation derivation out of CSS.

Typed `attr()` now removes much of the need for such duplication when consuming values numerically, but generated textual output remains an exception.

## Scope

I suggest beginning with `<number>` because:

1. It directly addresses results produced by arithmetic and rounding functions.
2. Its textual representation does not require resolving an external reference value.
3. It keeps the proposal small and independently useful.
4. Other numeric CSS types could be considered separately or added if the Working Group believes they should behave consistently.

This proposal does **not** require:

- a general `string()` or type-casting function;
- automatic conversion between arbitrary CSS types;
- changes to the behavior of CSS math functions;
- changes to HTML attributes or DOM APIs.

## Possible extensions / open questions

If accepting `<number>` is desirable, should the same mechanism eventually apply to other serializable numeric CSS types such as:

```text
<integer>
<percentage>
<dimension>
```

For example:

```css
content: 50%;
content: 1.5s;
content: 30deg;
content: 12px;
```

There are additional questions for those types concerning canonical units and percentage resolution, so they need not be part of the initial proposal.

For `<number>` specifically:

1. Should serialization use the existing canonical CSS serialization rules for numeric values?
2. How should non-finite results, if they reach this stage, be represented?
3. Should a numeric item be allowed anywhere a `<string>` currently participates in the textual portion of `<content-list>`, including alternative text after `/`, or only in generated visual content initially?

## Related composability issue

This may also reduce the need for individual value-producing features to expose a special string-returning mode solely to interoperate with `content`.

The broader design principle I am proposing is:

> A property whose purpose is to emit generated textual content should be able to serialize a computed numeric scalar as that text, rather than requiring the producer of the value to have generated a string in advance.

## @sb3nder — 2026-10-06

Another existing workaround is to use `counter()`:
```css
counter-reset: int var(--number);
content: counter(int) / counter(int);
```

To show decimals:
```css
div {
  /* this doesn't show the minus sign for val>-1 */
  --value: calc(round(var(--number), 0.001));
  --int: round(to-zero, var(--value));
  --dec: mod(abs(var(--value)) * 1000, 1000);
  --dec1: round(to-zero, mod(var(--dec), 1000) / 100);
  --dec2: round(to-zero, mod(var(--dec), 100) / 10);
  --dec3: round(to-zero, mod(var(--dec), 10));

  counter-reset: int var(--int) dec1 var(--dec1) dec2 var(--dec2) dec3
    var(--dec3);

  &::after {
    content: counter(int) "." counter(dec1) counter(dec2)
      counter(dec3);
  }
}
```
