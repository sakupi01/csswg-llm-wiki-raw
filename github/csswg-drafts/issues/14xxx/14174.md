## Problem Statement
Modern web architecture relies heavily on `data-*` attributes to manage component states, variations, and design tokens. This pattern is foundational to Web Components, design systems (e.g., Radix UI, Tailwind), and state-driven UI frameworks.

As documented in **[MDN’s guidelines on Style Variants](https://developer.mozilla.org/en-US/docs/Web/HTML/How_to/Use_data_attributes#style_variants)**, using data attributes for component states introduces massive architectural advantages over traditional BEM class naming conventions (`.callout--warning`):
1. **Elimination of Invalid States:** It inherently prevents mutually exclusive state bugs (e.g., accidentally applying `.callout--note` without the base `.callout` class, or applying multiple conflicting variant classes at the same time).
2. **Static Analysis & Linting:** Isolating a variant to its own attribute (e.g., `data-variant="warning"`) allows for easier type-checking and linting of valid values.
3. **Intuitive State Toggling:** Updating an element via JavaScript’s `element.dataset.variant = 'note'` is far cleaner and more reliable than string-splitting or toggling complex class tokens.

### The Developer Experience (DX) Gap
Despite these architectural best practices, CSS forces developers to pay a "syntax tax" to use them. Standard class selectors have a lean footprint (`.note`), whereas data attribute selectors are verbose and visually disruptive:

```css
/* Current CSS Selector Syntax */
[data-variant="primary"] { ... }
[data-state="open"] { ... }

```

In complex, deeply nested stylesheets, this syntax increases cognitive load and authoring friction, driving many developers back to messy class manipulation.

Furthermore, with the rollout of the expanded `attr()` function, data attributes are increasingly used to stream dynamic variables directly to CSS values. However, writing `attr(data-value)` repeatedly feels redundant when the platform already recognizes the `data-` namespace distinctly via JS `dataset`.

## Proposed Solution: A Unified Data API

We propose a two-part, cohesive vocabulary that introduces an ergonomic shorthand for working with `data-*` attributes on both sides of a CSS rule: the **left-side selector** and the **right-side declaration value**.

### 1. The Left-Side Selector: `:data()`

We propose a new functional pseudo-class, `:data()`, which automatically implies the `data-` prefix for attribute selection. This mirrors the cleanliness of `element.dataset` directly in stylesheets.

* **Syntax:** `:data(identifier)` maps directly to `[data-identifier]`
* **With values:** `:data(identifier="value")` maps to `[data-identifier="value"]`

```css
/* Mirroring MDN's Callout Variant Example */
.callout {
  border: 2px solid black; /* Default */

  &:data(variant="note") {
    border-color: blue;
  }

  &:data(variant="warning") {
    border-color: red;
  }
}

```

### 2. Support for Advanced Substring/Token Matching

To maintain complete feature parity with standard attribute selectors, the `:data()` pseudo-class seamlessly accepts all existing attribute matching operators (`~=`, `*=`, `^=`, `$=`). This ensures developers can handle space-separated token lists or dynamic prefixes cleanly.

* **Token list match (`~=`):** `:data(features~="carousel")` => `[data-features~="carousel"]`
* **Contains substring (`*=`):** `:data(id*="card-")` => `[data-id*="card-"]`
* **Starts with (`^=`):** `:data(type^="btn-")` => `[data-type^="btn-"]`

```css
/* Selecting a specific token within a space-separated dataset list */
.component:data(features~="grid") {
  display: grid;
}

```

---

## Future Extensibility: The Right-Side Value Function `data()`

To fully realize the unified mental model, the introduction of the `:data()` selector provides a clear architectural path for a matching right-side value function: `data()`.

While the selector requires a colon to respect CSS pseudo-class grammar (`:data()`), the value function drops the colon to sit natively within declaration blocks, acting as a prefix-free alternative to `attr()`.

* **Selector (Left-Side):** `:data(theme="dark")`
* **Value (Right-Side):** `color: data(brand-color);` (Maps to `attr(data-brand-color)`)

### The Unified API in Action

By pairing these two features, developers can build robust, data-driven components that follow MDN's architectural patterns with minimal boilerplate:

```html
<!-- HTML Structure -->
<div class="card" data-theme="dark" data-padding="24">
  <h3>Unified CSS Data API</h3>
</div>

```

```css
/* Modern CSS with the Unified Data API */
.card:data(theme="dark") {
  background-color: #111;
  color: #fff;
  
  /* Automatically infers 'data-padding' and handles fallback styling */
  padding: data(padding px, 16px); 
}

```

---

## Relationship to Existing Features & Performance

* **Zero Engine Overhead:** This proposal is strictly syntactic sugar. The `:data()` pseudo-class does not require a new structural execution path; browser engines would parse this directly into the existing, highly optimized attribute selector pipeline.
* **Ergonomic Type Casting:** Unlike generic attributes which can contain any arbitrary string structure, `data-*` attributes are explicitly intended for application state and custom configuration tokens. A dedicated `data()` value function could eventually support smarter implicit type coercion or default behaviors compared to the generic `attr()` function.

---

## Compatibility & Risks

* **No Preprocessor Collisions:** Unlike symbol-based shorthands (such as using `%` or `?`), a functional pseudo-class like `:data()` adheres strictly to existing CSS grammar boundaries. It introduces absolutely zero breaking changes or compilation errors for popular legacy tools like Sass, Less, or PostCSS.
* **Web Platform Consistency:** This creates a clean, predictable, and shared vocabulary across both core languages of the front-end platform:
    * **JavaScript:** `element.dataset.foo`
    * **CSS Selector:** `:data(foo)`
    * **CSS Value:** `data(foo)`

## @tabatkins — 2026-07-13

First, this proposal has all the hallmarks of being authored by an LLM. Please write comments yourself; this proposal is far too verbose for what it contains.

Unfortunately, I'm not seeing what this proposal offers that isn't already provided, quite directly, with attribute selectors and `attr()`. `:data(foo = "bar")` is basically identical to `[data-foo = "bar"]`, and `data(foo)` is just marginally shorter than `attr(data-foo)`. All the string-matching proposed for the pseudo-class already exists for attribute selectors, and the parsing/fallback behavior proposed for the `data()` function already exists for `attr()`. This is just a very slight syntax variant, without an argument for the current syntax being onerous to the point that this very minor change is worth the cost, or any proposal for going further than the existing selector/function can.

I'm going to go ahead and close this issue. If there is new information arguing for an actual need or making a proposal for something data-* specific that would be helpful there but not for general attributes, we can reopen or open a fresh issue.
