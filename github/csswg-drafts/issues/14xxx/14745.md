We discussed [css-aam#29](https://github.com/w3c/css-aam/issues/29) at the ARIA WG (https://www.w3.org/2026/11/05-aria-minutes.html#10003), and I took an action to carry the remaining concerns over here. 

The css-aam issue is closed because the default behaviour is settled. In #12859 we resolved that `line-clamp` behaves like `overflow-y: clip`, the ARIA WG agreed that clipped content should stay in the accessibility tree. We also have tests for this (thanks @thejohnjansen).

- https://wpt.live/css/css-overflow/overflow-clip-preserves-dom-content.html
- https://wpt.live/css/css-overflow/line-clamp/line-clamp-preserves-dom-content.html

I still think there's a real gap though. Today an author has no way to say "this content is clipped because I intend it to be hidden until the user asks for it", as opposed to "this is clipped because it didn't fit". @jcsteh [summed it up well in a comment](https://github.com/w3c/csswg-drafts/issues/12859#issuecomment-4724476505): the right accessibility behaviour depends on the author's intent.

@cookiecrook also had some insights worth pointing out:

- The accessibility API can't hide something from screen readers alone. Content is either exposed to the API or it isn't, so anything we remove for screen reader users is also removed for every other AT.
- Low vision users often combine larger text with a screen reader, Zoom, or HoverText. With `line-clamp` at a large font size, the visible text can shrink to a word or two (`Lorem ipsum...`). These users currently get the full string spoken, or re-rendered large in HoverText, which is the same text read at the default size. If we trimmed the API to the rendered text, they'd be penalised for using the text size they need.
- Users not relying at all on the painted window won't (nor shouldn't) care how big their window is, but the same page could expose different content from one day to the next because of window size.
- This kind of problem has been around for a long time, and AT users have workarounds for it. We need to avoid a fix that makes things worse for one group of users while helping another.

So the current behaviour doesn't fix the following issues:

1. Screen reader users can't tell which content is visible and which is clipped, or where the clipped part ends. There isn't a reliable way to find the end of the clipped text programmatically and skip to the next item.
2. The clipped content isn't always plain text. It can contain links, buttons, or part of a button's accessible name.
3. The "show more" control is noise for AT users, since they've already heard everything. Hiding that control from AT doesn't work either, because sighted screen reader users can still see it and may want to press it.
4. Authors often clip to reduce clutter and cognitive load, and the ARIA WG feels AT users should get that benefit too.
5. Keyboard access. Unlike scrollable overflow, clipped content can't be reached by a keyboard user who isn't running AT. This might be a WCAG concern (as in; developers who make this change need to ensure conformance to WCAG criteria), but are we creating a pit of failure for developers to run into these kinds of issues?

These ideas come from the discussion and various threads:

1. An author opt-in that marks clipped content as hidden by intent, as @SebastianZ suggested in https://github.com/w3c/csswg-drafts/issues/12859#issuecomment-4724305810. Content past the clamp point would be removed from the API only when the author asks for it, and the element would be exposed as truncated or collapsed so AT can announce that there's more. The risk - as identified above with the large-text case - is if an author opts in, low vision users lose the text that the default layout would have shown them. Perhaps the hidden range could be based on the author's intended clamp rather than the rendered one, but I'm not sure that's tractable.
2. Expose both the full content and the clip boundary, also from @SebastianZ in https://github.com/w3c/csswg-drafts/issues/12859#issuecomment-4064818600. Nothing would be removed from the API. The truncation point would be exposed so that AT can announce it, offer "skip to end of truncated content", or let the user choose. This doesn't break anything for the users @cookiecrook described, but it needs AAM mapping work and AT support, and I don't know of a precedent for it in the platform APIs. Given how complex it is to land features across the entire stack this may also be untractable.
3. Keyboard reachability for clipped regions, similar to how scroll containers became focusable. This is separate from 1 and 2, but @aardrian raised it at the ARIA WG and I think it belongs in the same conversation.

I hope I captured everything that was asked for from ARIA WG folks, and kind of prodded at ways we can solve this. Ultimately I'm just the messenger - I'm sure there's some phrase about how that means I don't get harmed, right?
