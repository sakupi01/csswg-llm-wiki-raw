There is no way for a user to say "no sudden brightness above normal white" and have pages respect it. `@media (dynamic-range: high)` describes what the screen can do, and `dynamic-range-limit` lets authors cap HDR, but neither reflects what the person wants. I'd like to propose a user preference media feature for this, in the same family as `prefers-reduced-motion`.

### A real-world case

A 100 x 100 company logo in a LinkedIn job alert, viewed in Yahoo Mail in Chrome on a MacBook Pro XDR display, rendered several times brighter than the rest of the email. The JPEG embeds an Apple "Rec. ITU-R BT.2100 PQ" ICC profile (CICP 9/16/0/1), and its white sits at PQ code 255, i.e. 10,000 nits, about 49x the 203 nit graphics white in ITU-R BT.2408. It was almost certainly exported with an HDR color space by accident. Neither the sender nor the mail client chose HDR, and a screenshot shows nothing, because it is tone-mapped to SDR.

The harm is the relative jump: one element far brighter than its SDR surroundings, often while scrolling a dark UI. HDR increasingly arrives through user uploads (phone photos, avatars, logos) on pages whose authors never opted in, and authors rarely cap it. Chrome Platform Status (16 Oct 2026): `dynamic-range-limit` is used on 0.66% of page loads, versus 6.6% for `@media (dynamic-range)` and 58.3% for `prefers-reduced-motion`.

### Relation to #11790

#11790 discusses how a user-level luminance limit (such as Apple's Reduce White Point) should interact with `dynamic-range-limit` in the cascade, and @svgeesus suggested an override along the lines of "always treat `no-limit` as `constrained-high`". That override is the right way to protect rendering on every page, and it would give a concrete mechanism to the Accessibility Considerations text ("user agents should provide a mechanism to limit the maximum luminance at user option").

This issue is about the other half: **exposing that preference to authors**, so they can change design and not just brightness. For example, an SDR poster instead of an autoplaying HDR hero video, SDR brand assets, or no HDR autoplay. This is the same split as the system Reduce Motion setting plus `prefers-reduced-motion`: the system can slow animations down, but only the author can redesign them.

On the "OS-level dimming is enough" point raised there: Reduce White Point scales everything, so the HDR element stays the same ratio brighter than its surroundings while body text gets dimmer. It is also only on iOS/iPadOS; I found no equivalent on macOS, Android's control is in beta builds, and Windows has HDR on/off per display. Audio is a useful precedent: lowering the master volume never fixed loud adverts; normalizing the loud segment did (ITU-R BS.1770, EBU R128, the US CALM Act, and Spotify's user-selectable Loud / Normal / Quiet levels).

### Proposal

Two naming shapes, open for discussion:

**Levels**, mapping onto `dynamic-range-limit`:

```css
@media (prefers-dynamic-range: standard) {
  img, video { dynamic-range-limit: standard; }
  .hero-video { display: none; }
}
```

Values `standard | constrained | no-preference`. Allows a middle level (`constrained` is visibly different from `standard` in Chrome when the display has headroom). Risk: `dynamic-range: standard` and `prefers-dynamic-range: standard` differ by one word, and the wrong one fails silently.

**Binary**, matching the `prefers-reduced-*` family:

```css
@media (prefers-reduced-peak-brightness: reduce) {
  img, video { dynamic-range-limit: standard; }
}
```

Values `reduce | no-preference` (or `prefers-reduced-highlights`). Clear accessibility intent, cannot be confused with the hardware query, but no middle level.

### Open questions

1. Levels or binary, and naming.
2. Should the feature only match on HDR-capable displays, so it adds no fingerprinting surface on SDR screens?
3. Should the user-level override default to `standard` or `constrained`?

### Use cases

Groups this likely matters for: people with migraine, photophobia (including after concussion or eye surgery), and low vision users who keep screen brightness high to read text, so dimming the screen is not an option. I'm collecting first-hand reports and would welcome pointers or accounts, here or in the [explainer repo's issues](https://github.com/upadhyayprakash/hdr-brightness-a11y/issues).
