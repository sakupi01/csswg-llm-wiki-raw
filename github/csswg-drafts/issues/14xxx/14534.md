We've discussed a few times adding a bunch of `aria-*` properties, analogous to the same-named attributes, but so far have rejected that for a few reasons. (Layering, interaction with AT, etc.)

However, those objections don't, afaict, apply to pseudo-elements, while on the other hand being *able* to set these attributes on pseudo-elements seems like a useful thing.

* There's no layering issue, as you can't set the attributes in the first place. These properties would just be exactly equivalent to what setting the attributes would do, *if* it were possible to do so.
* The AT interaction is already CSS-dependent here, as the very *existence* of a pseudo-element is CSS-controlled, as is its content and accessible label (via the `content` property).
* As we add more *interactive* pseudos, like for carousel, it seems likely we'll want to make sure the exact accessibility info is specifiable.

So, I suggest we add a set of `aria-*` properties, just exactly matching the names and value spaces of all the `aria-*` attributes (with the exception of using `aria-role` as the property name corresponding to the `role` attribute). All the keyword attributes will instead take keywords with the same values; numerics will take numbers; IDREFs will take custom-idents or strings; general string attributes will take a string.

## @smhigley — 2026-10-02

Do you have more information on which interactive pseudos are being considered as use cases for something like this, aside from carousels? I'm not currently aware of any other current or proposed CSS pseudos (interactive or static) that would benefit from allowing authors to add custom ARIA, but obviously I'm not aware of every proposal. The reason I'm asking is that there have been interactive pseudo proposals floated (e.g. the interest invoker touch button) that would not benefit from author customization, so I think it'd be a mistake to conflate the possibility of interactive pseudos with a need for custom ARIA in CSS.

Do you also have any examples of where this is the case?
> The AT interaction is already CSS-dependent here

Generally content inside CSS pseudos that I'm aware of is either fully driven by the element containing the pseudo (e.g. `::checkmark` or `::before/after` on a button), or is simple static text/image content (e.g. `::before/after` on a static element). Other than carousel, I'm not aware of a proposal for a pseudo element that would have an accessible label defined via `content` -- could you give an example?

## @Crissov — 2026-10-03

For [`aria-`]`role`, most pseudo-elements – and at-rules like page margin boxes – should be `none`/`presentation` and there are only very few other values that could ever make any sense, e.g. perhaps `button` for some of the ones proposed for [css-forms](https://drafts.csswg.org/css-forms/). However, these should rather be specified in the respective CSS module, not in a stylesheet. 

Overall, it may be better to exclude roles from this proposal (and advance `:role()` instead #3596). Then, though, it needs to be more explicit about which ARIA attributes and states actually make sense to have as CSS properties for pseudo-elements.
