We've discussed a few times adding a bunch of `aria-*` properties, analogous to the same-named attributes, but so far have rejected that for a few reasons. (Layering, interaction with AT, etc.)

However, those objections don't, afaict, apply to pseudo-elements, while on the other hand being *able* to set these attributes on pseudo-elements seems like a useful thing.

* There's no layering issue, as you can't set the attributes in the first place. These properties would just be exactly equivalent to what setting the attributes would do, *if* it were possible to do so.
* The AT interaction is already CSS-dependent here, as the very *existence* of a pseudo-element is CSS-controlled, as is its content and accessible label (via the `content` property).
* As we add more *interactive* pseudos, like for carousel, it seems likely we'll want to make sure the exact accessibility info is specifiable.

So, I suggest we add a set of `aria-*` properties, just exactly matching the names and value spaces of all the `aria-*` attributes (with the exception of using `aria-role` as the property name corresponding to the `role` attribute). All the keyword attributes will instead take keywords with the same values; numerics will take numbers; IDREFs will take custom-idents or strings; general string attributes will take a string.

For [`aria-`]`role`, most pseudo-elements – and at-rules like page margin boxes – should be `none`/`presentation` and there are only very few other values that could ever make any sense, e.g. perhaps `button` for some of the ones proposed for [css-forms](https://drafts.csswg.org/css-forms/). However, these should rather be specified in the respective CSS module, not in a stylesheet. 

Overall, it may be better to exclude roles from this proposal (and advance `:role()` instead #3596). Then, though, it needs to be more explicit about which ARIA attributes and states actually make sense to have as CSS properties for pseudo-elements.

## @davidsgrogan — 2026-10-26

Some use cases we've been thinking about:

## 1.  Horizontal or responsive ::picker(select) → aria-orientation
**Scenario**: a picker laid out as a single row of swatches or icons, or one that switches between horizontal and vertical at a breakpoint.

**Today**: the picker is exposed as `listbox` or `menu`, both of which default to vertical orientation, and there's nowhere to put `aria-orientation`.

With ARIA-in-CSS:

```CSS
select:open::picker(select) {
  display: flex;
  aria-orientation: horizontal; /* proposed */
}

@media (width < 30em) {
  select:open::picker(select) {
    flex-direction: column;
    aria-orientation: vertical; /* proposed */
  }
}
```

## 2. `aria-role` on `::before`/`::after` for meaningful icons
Scenario: a meaningful glyph icon, such as a warning sign on a form error, generated with ::before.

Today: authors can set the accessible name of generated content with alt text (content: "⚠" / "Warning"), but can't set its role. The common HTML pattern for a meaningful glyph icon is `<span role="img" aria-label="Warning">⚠</span>`. (Image content with alt text already gets an image role in Chromium; text glyphs don't.)

With ARIA-in-CSS:
```CSS
.field-error::before {
  content: "⚠" / "Warning";
  aria-role: img; /* proposed */
}
```

## 3. `aria-labelledby` for generated content

Scenario: a localized page where the visible "New" label is translated in the DOM by the site's normal localization pipeline, and the badge icon should use that same string as its accName.

Today: alt text in content can set the accName of generated content (`content: url(star.svg) / "New!"`) or hide it from AT (`content: "►" / ""`). Alt text can't take the accName from visible text elsewhere in the DOM: it can only pull from attributes on the originating element, via `attr()`.

With ARIA-in-CSS:

```CSS
<span id="new-label" class="visually-hidden">Nouveau</span>
<article class="product new">…</article>

.product.new::before {
  content: url(star.svg);
  aria-labelledby: new-label; /* proposed; IDREF as custom-ident or string */
}
```

## @LeaVerou — 2026-10-26

I’m **highly** supportive of this and see [many use cases](https://github.com/webplatformco/project-css-interaction/blob/main/use-cases.md#pseudo-elements) for it.

I would propose the following changes:
- `role` instead of `aria-role`. Yes, the naming is unfortunate, but at this point consistency with the attribute is more important
- We need a more CSS-native referencing mechanism, modeled after `anchor-name` and `anchor-scope`. I’m proposing one here: https://github.com/webplatformco/project-css-interaction/blob/main/README.md#element-references-ref-scope-and-ref-name 

Challenges:
- I worry that if these are allowed _only_ on pseudo-elements, it could block the way for ever allowing them on anything else just like what happened with `content`
- Even for pseudo-elements, I can see use cases of referencing regular elements _from_ the pseudo-element. For example, an accordion panel:

```css
details {
	ref-scope: --summary;

	> summary {
		ref-name: --summary;
	}

	&::details-content {
		role: region;
		aria-labelledby: --summary;
	}
}
```

Presumably the referencing properties _could_ work everywhere, though there are cases where referencing an element affects its _own_ AT (e.g. `aria-owns`). But in most cases it doesn't, so these could be L2.

-----

That said, I think there are a lot more use cases that would benefit from ARIA in CSS on actual elements. This motivated me to resurrect [this proposal](https://github.com/webplatformco/project-css-interaction/blob/main/README.md) I had been noodling on, which is essentially a superset of this. 

As I [argue in the proposal](https://github.com/webplatformco/project-css-interaction/blob/main/README.md#why-css), I think there is tremendous value in encouraging _more_ CSS-based interactivity instead of seeing these use cases as something to mitigate.

Improving the DX of web a11y and making components lighter and more robust benefits everyone:
- Lower friction to make experiences accessible directly translates to **more accessible experiences**.
- **Semantics move up a level of abstraction.** Today the only unit that can carry ARIA once for all its uses is a JS component; a class, a CSS framework or the UA stylesheet cannot. In CSS, whoever defines a pattern specifies it once, and consumers get it automatically (e.g. by using the class).
- **Co-location resists drift.** The dominant scripted-ARIA failure is state desync; deriving semantics from the same selector that drives presentation makes them a single expression.
- **Fault tolerance.** Scripted ARIA fails whole: In JS _any_ uncaught error breaks the entire file. CSS is fault-tolerant by design. An incorrect declaration is dropped without affecting the rest of the sheet.
- **Fewer wrappers.** Built-in elements are often wrapped in components _precisely_ to encapsulate accessibility logic, which today requires JS. Handling accessibility semantics in CSS lets many of these wrappers become a CSS class on a built-in element, and the decrease in complexity compounds downstream.
Of [Web Awesome](https://github.com/shoelace-style/webawesome)'s 73 components, 39 (53%) could have been a simple CSS class if it weren't for JS syncing state to ARIA (7 of them would also need `focusgroup`); see the [component library audit](https://github.com/webplatformco/project-css-interaction/blob/main/component-libraries.md).
