In https://github.com/w3c/csswg-drafts/issues/10001#issuecomment-5204871059 we resolved to add a class prefix selector (`.foo-*`), for hyphen-separated prefixes (at least at first).

One question that came up is whether the `*` can match the empty string, i.e. whether `.foo-*` matches a `foo-` class.

Either way, there's an easy override:
- If yes, it can be overidden via `.foo-*:not(.foo-)` (opt-out)
- If no, it can be overidden via `.foo-*, .foo-` (opt-in)

Reasons for yes:
- Consistency: Wildcards represented by `*` typically match empty strings in most contexts

Reasons for no:
- Error prevention: The common case is that you _don't_ actually want to match `foo-` and matching it is a footgun

I don't have a strong opinion, but I'm weakly leaning towards no on the basis that breaking consistency for usability is often warranted https://www.w3.org/TR/design-principles/#consistency

## @tabatkins — 2026-08-10

I think we can go ahead and say no to this. Zero of the libraries I've ever seen in my entire life, using any separator character whatsoever, have ever intentionally used a trailing separator as part of their naming system. If you're using a `foo-bar, foo-baz, etc` naming scheme, having a `foo-` is either a mistake or something completely unrelated; in neither case do you really want you `.foo-*` selector matching it.

## @LeaVerou — 2026-08-12

@tabatkins they're common in BEM-style naming.

Assuming there are no other restrictions about what the `*` matches, `.foo-*` should match `foo--bar`. `.foo--*` would also match it, so you can exclude these via `.foo-*:not(.foo--*)`. 

<!-- comment id=5272956974 author=tabatkins created=2026-08-12T21:23:51Z url=https://github.com/w3c/csswg-drafts/issues/14291#issuecomment-5272956974 -->
## @tabatkins — 2026-08-12

So the mental model is that an empty dashed-segment is allowed, we just don't treat a *final* dash as defining a final empty segment.

That is:
* `foo--bar` splits into ("foo", "", "bar"), and can be matched by .foo-* (initial "foo", something following) or .foo--* (initial "foo", second "", something following). 
* `foo-` doesn't split at all, it's just a `foo-` segment and won't match any wildcards.
* `foo-bar-` splits into ("foo", "bar-"), so you can match it with `.foo-*` but not `.foo-bar-*`.
* what about `foo--`? Does that split into ("foo", "-"), so `.foo-*` matches it? Or does the entire dash sequence run afoul of "final dash isn't a segment splitter", so there's no segmenting at all and it won't match any wildcards? (I'm inclined toward the latter.)

Does this look reasonable?

<!-- comment id=5334358724 author=tabatkins created=2026-08-18T21:36:29Z url=https://github.com/w3c/csswg-drafts/issues/14291#issuecomment-5334358724 -->
## @tabatkins — 2026-08-18

@LeaVerou
> [double dashes like "foo--bar" are] common in BEM-style naming.

Ah, right. So in that context the double dash isn't indicating an empty segment, it's just a larger separator. That's the context I was looking for.

In that context, I'm actually inclined to say that `foo--bar` *does not* match `.foo-*` at all, but *only* `.foo--*`.

The model, then, is that you split the class into prefixes, with the prefix breakpoints at the *end* of each hyphen-segment with a non-hyphen following. So `foo--bar` has `foo--`, `foo-bar--baz` would have `foo-` and `foo-bar--`, while `foo--` wouldn't have any prefixes at all.

@anselmh to address your points:

> A specific class substring selector is not universal.
> It does not work for IDs and other CSS selector types easily (even though data- is stated for future extensions here)

Nothing about this feature precludes us from _also_ adding `#foo-*` and `foo-*`, and even `[foo-*]`. In fact they're also being discussed: elements in https://github.com/w3c/csswg-drafts/issues/6571, attributes in https://github.com/w3c/csswg-drafts/issues/14228.

> Using a Regular Expression Syntax for matching behaviour that is not implemented as the common > Regular Expression syntax is specified. Even in CSS * works differently than in the suggested example ([class*=" abc"]).

Yes this is not Regular Expressions. It might be confused as one because syntax could look similar, but that is a mistake for whomever makes that assumption. 

> Speaking of BEM, what about BEM prefixes? .component__sub would not be supported by this, highlighting the inflexibility of this selector syntax.

This is an acknowledged limitation that was discussed. We settled on `-` as the single viable prefix character. Nothing is stopping the community centering around a theoretical BEMv2 which uses `-`. 

> Why would `.foo-ab\/c` be matched by `.foo-*` but `.foo--` would not be matched? At least to me, this is confusing.

I think there might be an _initial_ sense of confusion from this, but I imagine developers will quickly learn. It might be better to think of `-*` as the operator, rather than `*`.

I think we simply won't ever allow arbitrary prefixes. It's too easy to match by accident on non-semantic boundaries. (The "`.foo*` matches `footer`" problem.) And the perf issues with arbitrary prefixes won't ever go away, they're quite intrinsic to the idea.

## @LeaVerou — 2026-08-26

> I think we simply won't ever allow arbitrary prefixes. It's too easy to match by accident on non-semantic boundaries. (The "`.foo*` matches `footer`" problem.) And the perf issues with arbitrary prefixes won't ever go away, they're quite intrinsic to the idea.

Even if we currently feel we won't ever do it, I've seen a lot of "we'll never do X" turn 180deg given enough time, so I'm wary of making design decisions that block such an expansion.

And even if we don't want to allow arbitrary prefixes, expanding the set of separators is very reasonable, and doesn't suffer from the foo/footer problem or the perf issues.

Also, I'd be wary of claiming that a given perf issue will never go away. That's probably the most frequently wrong prediction in Computer Science 😅 Even if the same bloom filters continue to be used in perpetuity, what today is significant storage and computation cost in 10 years might be insignificant.
