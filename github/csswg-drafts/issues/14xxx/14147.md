One issue some people are facing with (concave) corner shapes as well as with some border shapes, is that concave parts of the shape can clip the internal content, like in this example:

<img width="224" height="191" alt="Image" src="https://github.com/user-attachments/assets/6a129317-2582-41b5-8e8d-8b6a1abbbe4a" />

In some cases padding is enough, but maybe some times the designer would want to make the text follow the curve when it's at the edge.

An existing unfinished spec for this is `shape-inside` - however a huge problem with `shape-inside` is that it doesn't have a good solution for the question of "where does the overflow content go to?", and developers who ignore this question might create frustrating situations for users e.g. when content becomes bigger due to translation etc.

A possible solution to this is to allow "box-like" shapes, like the regular boxes with corners, to grow their *middle* bit in both the inline and block direction, shaping only the edges of the content based on the `border-shape` or `corner-shape`+`border-radius`.

For regular boxes this axis can be automatically derived from the border radii, and for `border-shape` we can perhaps allow some syntax to define that some of the points can use `fr` units or some such to allow them to grow by content.

## @tabatkins — 2026-07-09

I like the idea of defining *somehow* the "stretchy" parts of the shape.

The immediate idea that comes to mind is adding a command to `shape()` that is a flexible vertical or horizontal line; it would resolve to a no-op by default, but in shape-inside it could be used to grow the shape.

However, you need *two* such points, on opposite sides of the shape, so that it can actually expand. I'm not sure there's a way to automatically determine if that is the case. Since the shape is closed, it implicitly ends with a z command, so in theory it doesn't matter; after we stretch the shape along its one line, *wherever* the end point ends up, it'll connect back to the start point. But that doesn't necessarily help; it can drag down the shape definition so we don't actually gain any space.

In fact, I *suspect* that it's problematic *in general* to have the left and right growth points not be perfectly aligned vertically. If they *are* perfectly aligned, then the "top" and "bottom" of the shape cleanly separate, and any layout work that's been done in the top is still valid as you add more "middle" space, but if they're not, then your earlier work can become invalidated.

Example - line lengths determined against the right-side "wiggly" edge aren't valid after stretching puts a straight line there instead:

<img width="581" height="548" alt="Image" src="https://github.com/user-attachments/assets/dffa2808-85ec-4a7b-a4bb-8f35329dae55" />

So what I'm imagining instead is the ability to specify a vertical or horizontal stretch point in the path, as a new path command, and it *automatically* cuts the shape in the appropriate direction, making all equal-position points on the curve into stretch points as well. This should be compatible with the  SVG path model - you can arbitrarily cut beziers and elliptical curves into smaller beziers/elliptics, and insert a `v` or `h` command between the pieces. This way you always subdivide the shape into perfect vertical or horizontal "segments" and insert straight-line segments between them, preserving your previous line-layout work and making the extension work easier.

Example - The "explicit" point is a "cut" command in the `shape()` arguments, and it implicitly cuts the path on the other side, defining two vertical-growth areas

<img width="815" height="532" alt="Image" src="https://github.com/user-attachments/assets/bea27ec5-6978-465b-ba50-8f1f56cb0f17" />

I'm not sure if you should be able to create multiple such points (and distribute the needed space between them) or not. I think multiple points runs us into the "throw away previous line layout work" problem. So I suspect it needs to just be one vertical and/or horizontal cut point; probably we take the first and ignore the rest if there are multiple in the path.

(If you don't define a cut point in an axis, it just can't grow in that axis; that's fine. It's the situation we have today.)

Stretchy shapes (and I like the idea!) are somewhat orthogonal to the original issue though. Noam's first example is just with a scoop corner-shape; there, the hard part is circular dependencies between the space available for layout, and the box size; imagine trying to compute the right box size to get the text to fit inside with `border-radius: 20%`. Right, that's exactly the issue I was talking about in my comment, and why my suggestion is shaped the way it is - it avoids *most* of that problem by doing the stretch purely with straight lines at the same point on both sides.

Tho, Ian bringing up the bottom reminds me that there *is* still some thrown-away work based on the bottom half, yeah, because you don't know you're overflowing (and need to stretch) until you *hit* the bottom, yeah. I think that's intrinsic to the problem space; the lower the author can provide the stretch point, the better (ideal is at the very bottom), but any lines below the stretch point *will* need re-layout. Even trying for "simple" shapes like border-radius doesn't help us here.
