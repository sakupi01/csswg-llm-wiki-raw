https://drafts.csswg.org/css-link-params-1/#param

> A param() function usually has an element context from the way it’s used. If present, the value uses that context (and the type, if present) to fully resolve itself to a **used value** before being passed into the linked resource.

The used value of a `<color>` is pretty clear, but what's the "used value" of `accent-color: auto`? Is that also a `<color>`? Yes, [by definition](https://www.w3.org/TR/css-cascade-5/#used-value), it needs to be an absolute color but we can't very well pass that into another document, it's a privacy violation to even expose it to the web page itself!

There are a variety of places where we haven't actually pinned down what the used value is, we can't be passing it around. We should pass in the computed value (which is what inherits), with maybe some exceptions (like `<color>`) for which we need, and can define, an absolutization rule.

## @tabatkins — 2026-10-26

Big -1 on "pass the computed value" *in general*. If the computed and used values are different, it's usually because the value gets resolved in some way based on the element's context, and *that is exactly the information we need inside the image*. Whether that's an 'em' value, a % length, a color, a URL... all of them need to be the value the element actually sees, because resolving them locally on the *SVG element* is worthless.

For accent-color, so long as we can pass in *sufficient context* to resolve it the same way as we would resolve on the linking element, we can special-case that property specifically. But it is indeed a special-case, not the general case, which needs to be as resolved as possible to an absolute value. I imagine that if the value is coming from a specified color in `accent-color`, it's fine to fully resolve; if it's the auto value coming from the OS and color-scheme, we can pass it in as 'auto' but carrying sufficient context to resolve it the same way.
