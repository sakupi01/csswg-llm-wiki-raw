So when `clip-path` applies to a fragmented box, all browsers disagree on how that should work.
Gecko: Applies the `clip-path` to each fragment individually, as if each were the whole element.
WebKit: Clips all fragments, with the path being relative to a rectangle that encompasses them all.
Chromium: Clips all fragments, with a path relative to the first fragment.

None of them care about the value of `box-decoration-break`.

What's the expectation here?

Personally, I think this should listen to `box-decoration-break` and apply per-fragment if that is set to `clone` and with respect to the hypothetical unfragmented box if it's set to `slice`. That way, a circular `clip-path` would mirror `border-radius: 50%` and the author is given controls to choose whatever makes most sense for their use-case.

Out of the existing browser behaviors, I think only the Gecko one feels remotely acceptable. Chromium's leads to invisible content even if the `clip-path` is just a border-box rectangle, whereas WebKit's is completely divorced from what the fragments actually look like if they don't happen to be laid out back-to-back.

Imagine analogous questions here for `mask-image`, `clip` and `overflow`/`overflow-clip-margin`. (although I haven't looked at browser behavior for these in detail)

Also, here is my test file that I used for this:
```html
<!DOCTYPE html>
<style>
  body {
    line-height: 3em;
  }
  #broken {
    border: 2px solid black;
    background: lightgray;
    clip-path: inset(8px 8px 8px 8px);
    box-decoration-break: slice; /* or clone, doesn't matter */
    padding: 6px;
  }
</style>
<span id="broken">
  This is a box<br>
  that gets fragmented into two.
</span>
```
