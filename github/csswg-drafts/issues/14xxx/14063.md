https://drafts.csswg.org/css-link-params-1/#sec doesn't address the fact that passing a relative url via `param()` could potentially trigger a load from a different security origin, which seems unfortunate.

Do we need tainting like attr() here?

Your approach works in a way, but only addresses the param(.., attr()) case.

I was more generally concerned about things like param(.., url()) resolving against the wrong base URI and/or triggering a request from the image's origin. It doesn't seem unrealistic to have `background: env(--bg)`, and now I can send requests impersonating another origin.

## @tabatkins — 2026-09-15

Oh, that's something quite different, then. `param(--foo, url())` just doesn't resolve the url() function at all, or even know that there *is* a url() function; it's just like an untyped custom property where it's left as an unresolved token stream. On the other hand, a *typed* `param(--foo <url>, url(...))` will resolve fully against the parent document and then pass down as that resolved value, so it's probably safe.

So, hmm, I see your point about it being potentially problematic due to the ambient authority. So I guess... values passed in via link params are automatically tainted *unless* they're typed as `<url>`? (And then they also pass in taint from other sources, like using `attr()` in their value, even if they're typed correctly.)
