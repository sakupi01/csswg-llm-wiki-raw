We had discussed this earlier, but I don't see it in the spec and didn't find any other issues.

If we expect icon libraries to add `--color` params, it will be a very steep adoption curve.
We should try to support *at least* the types of customizations that are already possible from the outside without a double handshake so that once this ships, it can be used with existing icons out of the box.
Propagating `currentColor` being the top one.

cc @tabatkins

## @tabatkins — 2026-09-04

Good point. I think we can just special-case some keywords to have this behavior as `param()` args. Since we already require your actual params to be dashed-ident, this is compatible.

That is, something like `img { link-parameters: param(currentcolor); }`, which would resolve currentcolor fully then pass it down into the image, *using it as the initial value of `color`*. (And probably `env(currentcolor)` too, just for consistency? It's possible that not all values we want to give this treatment are suitable for exposing as the initial value of some existing property.)

These would have to be a special allowlist of keywords with specific behaviors, but I think it's a good idea. `accent-color` would be another one. If you have ideas on what all would be good, that would be a helpful start.

We could actually still use the "value" arg of `param()` too, to let you optionally set a specific value (rather than using the value from the element).

## @LeaVerou — 2026-09-06

Yes, setting a specific value is *definitely* a requirement. `currentColor` is a good default, but often icons are a different color than the text (e.g. less visually prominent, or accented etc). Note that it should either be `currentColor` and `accentColor` (i.e. the keywords) OR `color` and `accent-color` (i.e. the properties). Passing properties is _by_ far more understandable and more flexible, so big +1 for the latter.

In terms of other properties that could be useful, offhand:
- `fill`
- `stroke` and `stroke-*`
- `transform`

But `color` is definitely the 80% case.

`font-family` could be a huge one if we can pass resolved font-families from the outer context, since it's currently a big pain point that it's impossible to use web fonts from SVGs (e.g. excalidraw base64 encodes an entire webfont in their SVG exports…). But that's definitely a separate issue, and not worth complicating the base case for.
