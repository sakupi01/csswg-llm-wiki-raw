We had discussed this earlier, but I don't see it in the spec and didn't find any other issues.

If we expect icon libraries to add `--color` params, it will be a very steep adoption curve.
We should try to support *at least* the types of customizations that are already possible from the outside without a double handshake so that once this ships, it can be used with existing icons out of the box.
Propagating `currentColor` being the top one.

cc @tabatkins

## @tabatkins — 2026-09-04

Good point. I think we can just special-case some keywords to have this behavior as `param()` args. Since we already require your actual params to be dashed-ident, this is compatible.

That is, something like `img { link-parameters: param(currentcolor); }`, which would resolve currentcolor fully then pass it down into the image, *using it as the initial value of `color`*. (And probably `env(currentcolor)` too, just for consistency? It's possible that not all values we want to give this treatment are suitable for exposing as the initial value of some existing property.)

These would have to be a special allowlist of keywords with specific behaviors, but I think it's a good idea. `accent-color` would be another one. If you have ideas on what all would be good, that would be a helpful start.

We could actually still use the "value" arg of `param()` too, to let you optionally set a specific value (rather than using the value from the element).

## @LeaVerou — 2026-09-06

Yes, setting a specific value is *definitely* a requirement. `currentColor` is a good default, but often icons are a different color than the text (e.g. less visually prominent, or accented etc). Note that it should either be `currentColor` and `accentColor` (i.e. the keywords) OR `color` and `accent-color` (i.e. the properties). Passing properties is _by_ far more understandable and more flexible, so big +1 for the latter.

In terms of other properties that could be useful, offhand:
- `fill`
- `stroke` and `stroke-*`
- `transform`

But `color` is definitely the 80% case.

`font-family` could be a huge one if we can pass resolved font-families from the outer context, since it's currently a big pain point that it's impossible to use web fonts from SVGs (e.g. excalidraw base64 encodes an entire webfont in their SVG exports…). But that's definitely a separate issue, and not worth complicating the base case for.

## @tabatkins — 2026-09-10

Hm, how do you see fill/stroke working? They don't have dedicated keywords in SVG, they just use `currentcolor` or `transparent`, and you rarely want to actually set the fill/stroke on the root, I think. Any files not explicitly written to use a link param would either be relying on currentcolor (so we can inject it via that keyword) or setting the values explicitly (so nothing we do will help; the pages need to be rewritten slightly).

Similarly, I'm not sure what `transform` would do *at all*. Can you give an example of what an icon could even *do* with the knowledge of what its `img` element's transform is?

## @tabatkins — 2026-09-15

Lol I was just coming in to reopen this again anyway.

Two things:

1. Re: @emilio , if all we do is have it set `env(color)`/etc, that doesn't satisfy Lea's original use-case. It *does* still allow for some convenience on the *passing* side - `param(color)` is easier to write than `param(--color <color>, currentcolor)` - which I think is still quite useful. (and see #14476 where the convenience can be even larger, with one `param(font)` setting a suite of `env()`s on the linked resource)
2. Adjusting the initial value actually defeats the handshake security property that I built into the spec, where a linked resource *must* be using the param explicitly for it to have any effect at all. It probably makes sense to preserve this aspect, so I think we *do* want to just have this set `env(color)`/etc.

## @LeaVerou — 2026-09-23

Icons are black boxes to authors. They either copy them or use them from a package. They don't actually author SVG by hand, like, almost ever. Often they are even hidden behind abstractions like React components. E.g. https://www.npmjs.com/package/lucide-react is the 9th most used package by websites today. With this, this is how authors use a camera icon:

```js
import { Camera } from 'lucide-react';
// Usage
const App = () => {
  return <Camera />;
};
export default App;
```

Please explain to me how authors would do any of the things you're suggesting in this case. 

Realistically, this would mean every single icon library needs to adapt every icon to conditionally use linked parameters if they are available. So it is now up to the individual icon libraries to adopt this, rather than the individual authors, which makes the adoption curve _very_ steep (and every single icon larger…).
