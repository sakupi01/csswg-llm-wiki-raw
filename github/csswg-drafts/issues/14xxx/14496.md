Splitting out from https://github.com/w3c/csswg-drafts/issues/14254: refining color adjustments used to communicate form control states:

* **Improve Disabled Contrast**
    * Add a slight (6%) tint to the background.
    * Adjust the `:disabled` color by increasing from 50% to 55% (improve contrast).
    * Reduce the `:disabled` border-color from 50% to 25% (since we reduced the non-disabled border-color to 50%).
* **Make interaction effects more subtle:**
    * **Hover** - Use border color at 100% as the `:hover` effect, instead of using a background color. This is a more subtle effect, which fits better with a UA default stylesheet, and avoids messing with text contrast.
    * **Active** Use an 8% background as the `:active` effect, as 20% seems too strong; and apply it to `select` as well as `button` etc.
* **Communicate Invalid State** - Adopting a red border-color to indicate `:user-invalid`.

Together with #14254, the stylesheet becomes:

```
select, input, textarea {
	border: 1px solid color-mix(currentColor 50%, transparent);   /* previously 100% */
}
:is(select, input, textarea):is(:hover, :focus) {
	border-color: color-mix(currentColor 70%, transparent);       /* previously used background-color */
}
:is(select, input, textarea):active {
	background-color: color-mix(currentColor 8%, transparent);    /* previously 20% */
}
:is(select, input, textarea):user-invalid {
    border-color: light-dark(#db2a37, oklch(from #db2a37 calc(l + 0.17) c h));    /* new */
}
:is(select, input, textarea):disabled { /* Overrides all interactivity styles from above */
	color: color-mix(currentColor 55%, transparent);              /* previously 50% */
	border-color: color-mix(currentColor 25%, transparent);       /* previously 50% */
	background-color: color-mix(currentColor 6%, transparent);    /* previously transparent */
}
```

## @keithamus — 2026-09-30

Something I didn't get time to say in the meeting: if we introduce `:user-invalid` style which is _just_ border color, then sites fail [WCAG AA SC 1.4.1](https://www.w3.org/WAI/WCAG21/Understanding/use-of-color.html) _unless_ they take additional steps to add validation messages. One might reply "surely a red border is better than no border" but my interpretation of SC1.4.1 is that they are indistinguishable at best, and at worst create a false sense of security for a developer than the defaults are sufficiently WCAG compliant.

<!-- comment id=6043919728 author=stubbornella created=2026-10-07T18:09:18Z url=https://github.com/w3c/csswg-drafts/issues/14496#issuecomment-6043919728 -->
## @stubbornella — 2026-10-07

@keithamus Most design systems use red error text above or below the invalid control in addition to a border color change. One or two use an icon instead, but it is really difficult to get an icon to line up correctly in all different writing modes and languages. Instead, we should make it so `error-message="..."` attribute can actually be styled. It's not very useful as a browser styled tooltip. If we did, developers could place it wherever fits their app.

## @astearns — 2026-10-14

Summarizing a bit, I see three options for :user-invalid styling:

A. Do nothing. Add no appearance:base styles for :user-invalid (status quo, doesn’t help but also doesn’t harm)
B. Add the red outline and nothing else (helps some users, doesn’t help others. Does not meet the WCAG criterion)
C. Add the red outline and something else (meets WCAG, but each of the “something else”s we discussed have issues)

The “something else”s we have considered:

1. Error text - affects layout, localization issues
2. Icon - placement is difficult, not many design systems use them
3. Invoke browser validation bubbles somehow? (solves localization, but it adds an entirely new pattern)
4. Change border to dotted or dashed (also an entirely new pattern)
