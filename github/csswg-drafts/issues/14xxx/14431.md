This is a follow-up to a discussion with @romainmenke in #14419.

[`<media-query-list>`](https://drafts.csswg.org/mediaqueries-5/#typedef-media-query-list) is defined as accepting an empty list. Therefore, it is equivalent to `<media-query>#{0,20}` instead of `<media-query>#?`.

Regardless of this subtle distinction, the problem is that its optional nature (from the author perspective) does not show up when it is used in other value definitions ([`@media`](https://drafts.csswg.org/css-conditional-3/#at-ruledef-media), [`@import`](https://drafts.csswg.org/css-cascade-6/#at-ruledef-import), [`@custom-media`](https://drafts.csswg.org/mediaqueries-5/#at-ruledef-custom-media)). This represents a difficulty for linters to detect errors (as far as I know, `<media-query-list>` and ~[`<font-src-list>`](https://drafts.csswg.org/css-fonts-4/#typedef-font-src-list)~ [`<forgiving-selector-list>` ](https://drafts.csswg.org/selectors-4/#typedef-forgiving-selector-list)are the only two CSS productions that accept an empty input), and for authors to assimilate the syntax.

The second causes inconsistencies: `<media-query-list>` is prefixed with `?` in the value definition of `@import` in CSS Cascade [3](https://drafts.csswg.org/css-cascade-3/#at-ruledef-import)-[4](https://drafts.csswg.org/css-cascade-4/#at-ruledef-import)-[5](https://drafts.csswg.org/css-cascade-5/#at-ruledef-import), but not in CSS Cascade 6 and in the value definition of `@media`. It also causes bugs: `[ <media-query-list> | true | false ]` is ambiguous in the value definition of `@custom-media`, and should be prefixed with `!`.

One benefit of not allowing `<media-query-list>` to be empty is that it could be used in contexts that would not otherwise allow it to be empty, without using `[ <media-query-list> ]!`.

HTML defines a string as a [valid media query list](https://html.spec.whatwg.org/multipage/common-microsyntaxes.html#valid-media-query-list) if it matches `<media-query-list>`. However, nothing can *not* match `<media-query-list>`, due to its error-recovery behavior, if I am not mistaken. If `<media-query-list>` were allowed to be omitted, HTML would need to define the behavior when the string is empty (or equivalent to empty, by considering CSS comments, line breaks, etc), as well as for [*parse a media query list*](https://drafts.csswg.org/cssom-1/#parse-a-media-query-list) (for [`MediaList.appendMedium()`](https://drafts.csswg.org/cssom-1/#dom-medialist-appendmedium), [`MediaList.deleteMedium()`](https://drafts.csswg.org/cssom-1/#dom-medialist-deletemedium), the setter of [`MediaList.mediaText`](https://drafts.csswg.org/cssom-1/#dom-medialist-mediatext) - which already handles the case of an empty string - and for [`matchMedia()`](https://drafts.csswg.org/cssom-view-1/#dom-window-matchmedia)).

More generally, in my opinion, a production accepting zero or more tokens seems conceptually inappropriate. I.e. `<foo>?` and `<foo> = a` should be preferred over `<foo> = a?`.

---

So is there a reason for allowing `<media-query-list>` to be empty rather than omittable? Or is it only because defining a comma-separated list as optional (`#?`) was not possible when its (BNF) [syntax](https://drafts.csswg.org/mediaqueries-3/#syntax) was first written?

Similarly, these other uses may not want the "not all"-ification (#11289).

With some hindsight, `<media-query-list>?` does not make sense at the moment. An empty `<media-query-list>` parses (or serializes to) `all` so it cannot be omitted and `?` is irrelevant.
