I would like to suggest that there exist a feature within selectors that offers some sort of parity to what already exists within CSS values: the ability to create and interpolate a string value. 

## Problem: Specificity bloat leads to file bloat

Suppose a very real in-production selector:

```
#foo-navigation[breakpoint=desktop] .hidden-at-desktop[class][class][class],
foo-navigation[breakpoint=desktop] .hidden-at-desktop[class][class][class] {
  display:none
}
```

This is one of a series of rulesets that are unfortunately high due to specificity bloat that lives outside the domain of the stylesheet. 

But a side-effect of raising the specificity to accomplish the goal is that the selectors must requisitely become longer (lest we resort to !important or `id` selectors). 

### Solution 1: Nesting (already exists)

Nesting could be one solution to reducing redundancy, but it comes at the cost of incidental specificity sideeffects, since the most -specific selector in the list would elevate the specificity of all selectors (due to the fact that nesting uses the same mechanics as `:is()` under the hood)

So someone could write

```css
#foo-navigation[breakpoint=desktop], foo-navigation[breakpoint=desktop]) {

  .hidden-at-desktop[class][class][class] {

  }
}
```
which is functionally equivalent to `:is(#foo-navigation[breakpoint=desktop], foo-navigation[breakpoint=desktop]) .hidden-at-desktop[class][class][class] `. 


But now `foo-navigation` is given the specificity of an id, which could have un intended consequences. Not only that, the duplication is eliminated with the child elements; so the code doesn't immediately express what problem is solved with nesting. 

### Solution 2: `:where()`

It might be tempting to instead eliminate redundancy by using `:where()` since neither it nor its arguments contribute specificity:


```css
:where(#foo-navigation[breakpoint=desktop], foo-navigation[breakpoint=desktop]) .hidden-at-desktop[class][class][class]  {
display: none;
}

```
Unfortunately this creates the exact opposite problem that now all specificity is _gone_, and this may also not be a desired outcome. 

**We want to reduce duplication _without specificity side-effects_.**

### Solution 3: CSS Selector Function (proposed)
One solution could reduce redundancy, improve cognitive load, and not create specificity side-effects:

```css
@selector --<name>() {
   <valid selector string>
}
```

A real-world use-case could be as follows:

```css

@selector --foo-nav() {
  foo-navigation[breakpoint=desktop]
}

/*redundancy reduced b/c the abstracted function is shorter than the full selector */
:--foo-nav() .hidden-at-desktop[class][class][class],
#:--foo-nav() .hidden-at-desktop[class][class][class {

}
```

The custom selector function does not provide _any_ specificity because it is a pointer / container for a partial selector. 

It will behave like a CSS custom property and return the value as a string. The interior of the block will be inserted at the call site of the function. Or alternatively, the interior specificity will be computed and then added to the selector that calls the function.

This solution would also mimic the behavior of existing CSS function syntax. 


This also has the benefit of being able to **communicate the intent of selector patterns**. Having a tool for semantically labelling partial selectors will improve the developer experience:



```CSS 

@selector --spec-bump() {
  [class][class][class]
}

 #foo-navigation[breakpoint=desktop] .hidden-at-desktop:--spec-bump(),
 foo-navigation[breakpoint=desktop] .hidden-at-desktop:--spec-bump() {
  display: none;
}

```


### Problem: Interpolating CSS selectors

Currently, it is not possible to interpolate CSS selectors. 

In other words, this selector cannot be made less redundant or reusable with any selector-generating syntax

```CSS 
#foo-navigation[breakpoint=desktop] .hidden-at-desktop[class][class][class],
foo-navigation[breakpoint=desktop] .hidden-at-desktop[class][class][class] {
  display:none
}
```

*Solution: Allow string arguments passed into a selector function*

I would propose this syntax:

```css
@selector --<name>(<variable>) {
   <interpolated string>
}
```

essentially, the arguments, however many, would be inserted as-is wherever the `var` keyword is used (just like with properties). 


In this case, an application could be like so:
```CSS
@selector --foo-nav(--bp-val) {
  #foo-navigation[breakpoint=var(--bp-val)]
}



:--foo-nav(desktop) .hidden-at-desktop[class][class][class] {
  display: none;
}

:--foo-nav(mobile) .hidden-at-desktop[class][class][class] {
  display: none;
}
```

And, again, this could be further improved with semantically-named custom selectors that clearly express intent in the way that other selectors could not:

```CSS

:--foo-nav(mobile) .hidden-at-desktop:--spec-bump() {
  display: none;
}
```

With interpolation, this provides meaningful ways to reduce cognitive overload and duplication at the parts of a selector where the developer perceives there to be a need for abstraction, all while preventing raised specificity:

```CSS 

/* the --breakpoint variable is inserted at two places in the selector */
@selector --break-hide(--breakpoint) {
  [breakpoint=var(--breakpoint)] .hidden-at-var(--breakpoint)
}

@selector --spec-bump() {
  [class][class][class]
}


 #foo-navigation:--break-hide(desktop):--spec-bump(),
 foo-navigation:--break-hide(desktop):--spec-bump() {
  display: none;
}

```

## TL;DR
Proposing a selector function would allow developers to reduce duplicativity without specificity side-effects. This allows for smaller stylesheets, which means faster load times. And faster load times means better experiences for users. It also allows for reduced duplication without the risk of specificity side-effects, which means fewer bugs.

@tabatkins I want to be clear that my reason for proposing this isn't _just_ for avoiding specificity side-effects of `:is()` and `:where()`. It's **one** benefit, but not the only one. 

&lt;aside&gt;
You're right that `@layer` would be useful for managing "specificity issues", but one of the challenges that I encounter in working with content management systems (particularly their module systems), and multiple design systems, is that layers is only effective if I can layer _everything_. Unfortunately, I can't — Lots of CMS have their own complex systems for compiling CSS from multiple sources, so getting layers involved requires changes to the core parts of the CMS. 

The only CSS that I can layer is my top-most level of CSS — which isn't where my problems are! So It would be unhelpful to bump "my" CSS backwards and promote the imported / module CSS when what I need is the exact opposite.

&lt;/aside&gt;

Other benefits include:

1. Another bit of Sass functionality has an equivalent in CSS
2. The ability to be DRY at the right-most end of the selector
3. Adding a level of semantics to selectors
4. Ability to create a shorthand for attribute selectors

This is a real-world example (again, I didn't write this):

```css
rh-breadcrumb[variant='none'] > ol > li:last-child, rh-breadcrumb[variant='url(%23clip0_232_19576)'] > ol > li > a[aria-current='M2.5 14.5L0.5 12.5L5.5 7.5L0.5 2.5L2.5 0.5L9.5 7.5L2.5 14.5Z'] 
```

If _whoever_ wrote this had the option to write something like this:

```css
@selector :--aria-svg-arrow() {
  [aria-current='M2.5 14.5L0.5 12.5L5.5 7.5L0.5 2.5L2.5 0.5L9.5 7.5L2.5 14.5Z'] 
}
rh-breadcrumb[variant='none'] > ol > li:last-child, rh-breadcrumb[variant='url(%23clip0_232_19576)'] > ol > li > a:--aria-svg-arrow()
```

Then at least I have some piece of information I wouldn't have had prior about why this existed (and yes, I'm aware that CSS comments exist)

Now, with regard to my fourth point regarding "short-handing attribute selectors", Let me present another real-world example:

```css
rh-breadcrumb[variant='url(%23clip0_232_19576)']
```

Especially with the advent of web components and the ability to create all these custom props, we end up writing selectors that target these custom properties, be they `variant` or heck, `data-` attributes. 

This is where `@selector` as a function becomes very useful:

```css

@selector :--variant(--val){
  [variant="var(--val)"]
}

rh-breadcrumb:--variant(url(%23clip0_232_19576)) {
  display: none;
}

rh-breadcrumb:--variant(url(/some/very/ridiculous/path)) {
  display: regrets;
}

@selector :--state(--val) {
  [data-very-long-attribute-state="var(--val)"]
}

pf-navigation:--state(wednesday--off_only_9-am) {
  display: 😮‍💨 ;
}
```

## @khanglolol — 2026-07-21

I would like to add a comment: Why not use a `@container` style query?

If someone want something to have overpowering specificity, use `!important` in `@layer` which will override everything but `!important` inline styles (and few things that are not relevant here). Note that using !important will invert the `@layer` hierarchy, so for it to make sense, you can name your layers like `@layer strongest, stronger, strong` (free "specificity" without needing to put everything in a layer or overusing `[class]`, plus the added benefit of it being extremely easy to add upon).

Here's some rewrites:

```css
#foo-navigation, foo-navigation {
  container-name: FooNavigation;
}

@container FooNavigation style(--breakpoint: desktop) {
  .hidden-at-desktop {
    @layer strongest { display: none !important; }
  }
}
```

```css
rh-breadcrumb-container {
  container-name: RHBreadcrumb;
}

rh-breadcrumb {
  @container RHBreadcrumb style(--variant: url(%23clip0_232_19576)) {
    display: none;
  }
  @container RHBreadcrumb style(--variant: url(/some/very/ridiculous/path)) /* or var(--long-clip-path) */ {
    display: regrets;
  }
}

pf-navigation-container {
  container-name: PFNavigation;
}

pf-navigation {
  @container PFNavigation style(--state: wednesday--off_only_9-am) {
    display: 😮💨 ;
  }
}
```

In the latest spec, there should be no side effects to using `@container` style queries. Maybe it is a bit inconvenient to have to create containers, but surely using a new `@at-rule` is not that more efficient? Also, you don't need a `container-name` and the `container` elements if your team is willing to add this side effect to custom element creation: `<html style="--pf-navigation-state: wednesday--off_only_9-am">...</html>` (assuming it is not inside a Shadow DOM, which then you have to add the property to `:host`), which then allows:

```css
html { container-name: StateManager }
pf-navigation {
  @container StateManager style(--pf-navigation-state: wednesday--off_only_9-am) {
    display: 😮💨 ;
  }
}
```

I also personally decided to rewrite an egregious 50+ line declaration to this: 

```css
#pfe-navigation, pfe-navigation  {
	container-name: PFENavigation;
}

:is(
	.pfe-navigation-item__tray--container,
	.pfe-navigation__dropdown-wrapper--default-styles
) :is(
	.pfe-link-list--header,
	[role=heading][aria-heading-level],
	:is(h2, h3, h4, h5, h6),
)  {
	container-name: PFE-Header;
}

@container PFENavigation style(--state: processed) {
	@container PFE-Header {
		a:is(:hover, :focus) {
			text-decoration: none;
	    		color: #036;
	    		color: #036;
	    		color:var(--pfe-navigation__dropdown--link--Color--hover, #036);
		} /* note: specificity (0, 1, 1) but you can forget about it by using !important `@layer`*/
	}
}
```

With in `!important` in `@layer`, your team can deal with all the specificity madness very easily with understandable, declarative names. `@container` will help them DRY + manage state beautifully + reduce nesting
