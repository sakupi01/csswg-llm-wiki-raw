Hello,

I'm a little confused with some of the wording in the CSS spec, and I'm not sure if it's down to an error in the spec or my lack of understanding, so I'd like to clarify:

- As defined by the spec, a "rule" is either an at-rule, or a qualified rule [[source](https://www.w3.org/TR/css-syntax-3/#css-rule)].
- As I understand, a qualified rule has three members:

  ```
  struct QualifiedRule
  {
      ComponentValueList prelude;
      DeclarationList declarations;
      RuleList children;
  };
  ```
- As I understand, a "nested declarations rule" is defined as a style rule (so a qualified rule) [[source](https://www.w3.org/TR/css-nesting-1/#nested-declarations-rule)].

In the ["Consume a qualified rule"](https://www.w3.org/TR/css-syntax-3/#consume-qualified-rule) section, the spec says that - when consuming the block contents of a qualified rule - we should replace every list of declarations (except for the first), with a "nested declarations rule", and insert the list of declarations as the nested rule's "sole child":

> Otherwise, consume a block from input, and let child rules be the result. If the first item of child rules is a list of declarations, remove it from child rules and assign it to rule’s declarations. If any remaining items of child rules are lists of declarations, replace them with nested declarations rules containing the list as its sole child. Assign child rules to rule’s child rules.

The part that's tripping me up here is "sole child". I was under the impression that a list of declarations cannot be a child - only other rules can be considered children of a rule. So when the spec says "containing the list as its sole child", does it mean the list should be inserted into the `declarations` member of the nested `QualifiedRule`?

The ["Consume an at-rule"](https://www.w3.org/TR/css-syntax-3/#consume-at-rule) section adds to my confusion, because in that algorithm, it seems declarations lists really are treated as children of an at rule:

> Consume a block from input, and assign the result to rule’s child rules. 

The result of consuming a block is a list of rules and declaration lists. So when the spec says "assign the result to rule’s child rules" that implies that declaration lists really can be considered children to a rule.

So my question is, can declaration lists be considered children to a rule? That is, can `QualifiedRule::children` contain declaration lists as well as other rules? Is my `QualifiedRule` struct defined incorrectly? Should it have a single member that combines child rules and declarations lists, like so:

  ```
  struct QualifiedRule
  {
      ComponentValueList prelude;
      std::list<Rule, DeclarationList> children; // This can hold rules and declaration lists...
  };
  ```

And what's the deal with at rules? The spec implies that they too can contain declaration lists as children.

Apologies if I've misunderstood something obvious here.

Thanks,
Nav

## @navnavnav — 2026-10-20

Thanks for the quick response, @tabatkins! And apologies if I missed your IRC message.

That clears things up RE consuming qualified rules.

But what about at-rules? The spec defines their structure to be similar to qualified rules:

> An at-rule has a name which is a string, a prelude consisting of a list of component values. Block at-rules (ending in a {}-block) will additionally have a list of declarations and a list of child rules. (Statement at-rules, ending in a semicolon, will not.) 

So I interpreted that as:

```
struct AtRule
{
    AtKeywordToken* nameToken;
    ComponentValueList prelude;

    // These members will only be populated for block at-rules
    DeclarationList declarations;
    RuleList children;
};
```

The spec says we should insert the result of consuming a block's contents into the at-rule's children:

> Consume a block from input, and assign the result to rule’s child rules.

 Does that also need correcting? Consuming a block's contents returns a list containing both rules and multiple declaration lists. For example, consider the following CSS source:

```
@media (...) {
  color: red;
  background-color: blue;

  & {
    padding-right: 10px;
  }

  font-size: 10px;
  font-weight: bold;
}
```

When consuming the block content's of that at-rule, I believe we would produce something like:

```
{
  DeclarationList{}, // <- `color` and `background-color` properties in here...
  QualifiedRule{},
  DeclarationList{}, // <- `font-size` and `font-weight` properties in here...
}
```

What would we do with those two declaration lists? Merge them into one and put them in `AtRule::declarations`? I suspect that's incorrect, as the spec seems to require the rules in the two lists to be treated differently:

> For somewhat-technical reasons, it’s important to be able to distinguish properties that appear at the start of a style rule’s contents from those that appear interspersed with other rules.

[[source](https://www.w3.org/TR/css-nesting-1/#nested-declarations)]

That quote is specific to style (qualified) rules, but I suspect it also applied to property declarations in at rules?

And these differences appear to be handled at a later stage of parsing. So all of this leads me to believe that my definition of an `AtRule` is incorrect, and it should instead be something like:

```
struct AtRule
{
    AtKeywordToken* nameToken;
    ComponentValueList prelude;

    // This member holds both child rules and declaration lists. It's effectively identical to what's returned by the "consume a block's contents" algorithm. Also: it will be empty for statement at-rules (where there is no block contents to consume).
    std::list<std::variant<Rule, DeclarationList>> blockContents;
};
```

So which definition is correct here? The one with two separate members for declarations and child rules (`AtRule::declarations` and `AtRule::children`), or the one with a single member that holds both (`AtRule::blockContents`)? If it's the latter, perhaps we could update the ["CSS Parsing Results"](https://www.w3.org/TR/css-syntax-3/#css-tree) section to something like:

> An at-rule has a name which is a string, a prelude consisting of a list of component values. Block at-rules (ending in a {}-block) will have an additional member taking the form of a list which holds both child rules and declaration lists. (Statement at-rules, ending in a semicolon, will not.) 

Or maybe my initial understanding was correct and we can just merge all the declaration lists returned by the "consume a block's contents" algorithm into one list, and insert into `AtRule::declarations`? But I suspect this is not the case, as it would mean losing the ability to distinguish the declarations as required by the spec.

Any clarity on this would be much appreciated!

Thanks,
