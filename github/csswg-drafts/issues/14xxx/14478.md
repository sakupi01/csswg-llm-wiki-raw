Three cases in [random-serialization.tentative.html](https://searchfox.org/firefox-main/source/testing/web-platform/tests/css/css-values/random-serialize.tentative.html#12,44,92) have a property where the specified value has `random(fixed <number>, ...)` and arguments that are all absolute. But the tests currently assert that the serialization retains the random function. These should simplify directly to a value at specified-value time, right?

Chrome passes these cases, and will output the following in the console:

```js
document.body.style.width = 'random(fixed 0.5, 0px, 100px)';
document.body.style.height = 'clamp(0px, 50px, 100px)';

console.log(document.body.style.width); // random(fixed 0.5, 0px, 100px)
console.log(document.body.style.height); // calc(50px)
```

I would expect `calc(50px)` for both?

<!-- comment id=5688484970 author=tabatkins created=2026-09-15T21:41:52Z url=https://github.com/w3c/csswg-drafts/issues/14478#issuecomment-5688484970 -->
## @tabatkins — 2026-09-15

As a [math function](https://drafts.csswg.org/css-values-4/#calc-simplification), it should simplify eagerly as much as possible, all the way down to full resolution if possible.

So yes, a `fixed` key should definitely resolve at specified value time if the other arguments are resolveable. (`width: random(fixed .5, 100px, 100%);` would stay unresolved until used-value time, for example, identical to `calc(100px * .5 + 100% * .5)`.) Non-`fixed` keys should similarly resolve early if possible; in general, keys are usually resolvable at specified-value time (when you know both the element and property context). (The only reason we even *have* the `fixed` key is to handle the rare cases where the function isn't resolveable by computed-value time, so it'll inherit predictably.)

Actually, I did want to ask about the ["The random base value of a random function is generally known at specified value time, once it’s known which element the function is being applied to"](https://drafts.csswg.org/css-values-5/#ref-for-random-base-value%E2%91%A0%E2%91%A7) language in the spec. It's consistent with [value processing](https://drafts.csswg.org/css-cascade/#value-stages) but it doesn't seem to be how engines actually work, where element-dependent values are only resolved at computed value time. Like in the below:

```js
document.body.style['z-index'] = 'sibling-index()';

console.log(document.body.style['z-index']); 
// sibling-index()

console.log(getComputedStyle(document.body)['z-index']); 
// 2
```

Going by the logic of "usually resolvable at specified-value time when you know the element context", values like this `sibling-index()` would be resolved immediately, but that would behave very differently than browsers do currently. Am I misunderstanding what was meant by the "generally known at specified value time" part?
