The two shape case is adding a lot of complexity to the design of this feature, especially around interactions with other properties (e.g. it makes #14149 infinitely harder).

I think if we scope it down to one shape, at least for css-borders-4, we can end up with a much more coherent design, and likely easier to implement, increasing its likelihood of actually shipping.

And I'd argue that it would still cover >95% of use cases.

An author, I have encountered many, _many_ use cases for single-shape border-shape, but none for the two-shaped version.
All use cases in https://una.im/border-shape are about stroking a single shape. 
Same with https://www.youtube.com/shorts/qg6kzUWPsPE
Same with all real-world use cases in https://css-tricks.com/get-ready-for-the-powerful-css-border-shape-property/

The author did manage to come up with a few examples for the two-shape version, but it looks forced rather than real-world use cases (the visual version of foobar essentially) and I don't think anybody would call these borders:

## @LeaVerou — 2026-07-09

"Defer" doesn't mean "we won't do this, ever", and it doesn't mean "this is not useful". We often defer many very useful things to make it easier to define and ship features (e.g. `contrast-color()` recently became Baseline, but was completely blocked before #9166 carved out an MVP).

The feature as currently specced is **severely underspecified**, and the two shape variant will make it significantly harder to flesh out the spec.

I can see that use cases exist for the two shape variant, but I think they are a tiny fraction of the single shape variant use cases. And they are even fewer if you exclude those where what you really want is a stroke with varying thickness, like your example, which *should* be doable with a single shape (possibly with an extension to `border-width`). **Using two shapes for that is a workaround**, not a clear expression of user intent and forces you to edit two shapes to effectively modify the outline in the same way (e.g. change the min or max thickness).

Not to mention that your *exact* particular example doesn't even need `border-shape`, it’s already doable with border-radius alone, which also produces _far_ more maintainable code that is closer to the actual author intent:

```css
.two-shapes {
	width: 300px;
	height: 300px;
	border: solid green;
	border-width: 10px 30px;
	border-radius: 50%;
	padding: 10px;
	background: yellow;
	box-sizing: border-box;
	font-size: 24px;
	display: grid;
	align-content: center;
	justify-items: center;
	font-family: sans-serif;
}
```

<img width="312" height="310" alt="Image" src="https://github.com/user-attachments/assets/68a319ea-f32a-45e2-9a37-e7f065500f70" />

And it’s doable with `border-radius` thanks to @fantasai’s hard work to define that all the interactions between `border-radius` and existing `border-*` properties result in sensible results instead of just declaring that they don’t apply when `border-radius` is set.

The two shape variant makes it nearly impossible to define reasonable interactions between `border-shape` and existing border properties, because shape subtraction is not really a border.

I think this needs far more baking, whereas the single shape version is much more straightforward.

> The feature as currently specced is **severely underspecified**, and the two shape variant will make it significantly harder to flesh out the spec.

In what way is it "severely underspecified"? I think that's quite hyperbolic.
It is specified to do exactly what it does and it's a useful feature on its own.
The outer shape affects the (outset) box-shadow and outline, the inner shape affects clipping the content and inset box-shadow. The space between them is filled with the border color. The outer shape defaults to `border-box`, the inner shape defaults to `padding-box`. All of this is in the spec with a clear algorithm of how it's rendered. 

If something specific is missing please file a specific issue rather than categorically saying that something is underspecified. 

> I can see that use cases exist for the two shape variant, but I think they are a tiny fraction of the single shape variant use cases. And they are even fewer if you exclude those where what you really want is a stroke with varying thickness,

## @tabatkins — 2026-07-09

I agree with Noam. The two-path syntax doesn't seem to be meaningfully underspecified; it has some open issues, same as single-path, but in all the important ways both variants work essentially identically. Importantly, it doesn't seem to be distracting or blocking anything about the single-path version; on the contrary, I think it's *very* important that we keep it at the top of our mind when we're exploring expansions to the single-path variant, so we don't design ourselves into a corner. As Noam says, literally the only difference in the two syntaxes wrt how they interact with existing border properties is that the single-path takes its *width* from border-width, while two-path doesn't; they both take their color from border-color and both ignore all the other border-* properties. They are *incredibly* similar features, and I strongly disagree that anything about two-path necessitates it being split out from one-path.
