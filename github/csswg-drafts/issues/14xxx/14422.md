["Serialize a CSS declaration block"](https://drafts.csswg.org/cssom/#serialize-a-css-declaration-block) attempts to consolidate longhand declarations into shorthands for serialization. For example, if you write `justify-self: start; align-self: start;`, this algorithm specifies that they are serialized as `place-self: start;`.

This has two major problems:
* Creating new longhands (e.g. for `font` or `columns` or whatever) causes declaration lists that previously serialized as a shorthand to serialize as longhands (because the list no longer contains *all* the longhands for that shorthand).
* Creating new shorthands (e.g. `place-self`, [`size`](https://github.com/w3c/csswg-drafts/issues/820)) can cause declaration lists that previously serialized as longhands to serialize as shorthands.

Both of these are forwards-compat landmines for CSS. They're also a source of browser incompatibilities[^1]. We should fix this.

The only reasonable way to fix this, from what @tabatkins and @fantasai can tell, is to preserve how the author originally wrote it in the first place: shorthands serialize as shorthands, and longhands serialize as longhands. 

This also removes some significant complexity from the serialization algorithm, which has various exceptions to handle vendor-prefixes, legacy properties, reset-only subproperties, logical properties, etc.

However, it will mean that all browsers need to change their behavior. Can we do this? (Again, all browsers *already* disagree in at least some cases.)

[^1]: For example, `columns: 200px 2;` and `column-width: 200px; column-count: 2;` currently serialize in three different ways across Firefox, Chrome, and WebKit. Firefox serializes both with `columns`; WebKit serializes both with longhands (it's on a list of manual exceptions in the code), and Chrome considers the second decl block incomplete (because it also recognizes `column-height` and `column-wrap` as `columns` longhands), so the first uses `columns` and the second uses the longhands.

## @Loirooriol — 2026-09-04

"Landmine" seems an exaggeration, has this ever been an actual problem?

For example, the `top`, `right`, `bottom`, `left` properties are among the most used ones, 80-90% of pages use them. Introducing the `inset` shorthand changed the serialization, but I don't remember any breakage when I added it to Blink. I think there was just [a bug](https://issues.chromium.org/issues/41409597) that the shorthand could be used even if disabled behind a pref.

> WebKit serializes both with longhands (it's on a list of manual exceptions in the code)

Yes, WebKit has a list of exceptions, but most of them come from the time that shorthands had to be manually handled there, and people would forget. When [I made it automatic](https://github.com/WebKit/WebKit/pull/6307), I played it safe and preserved the old behavior by adding these exceptions, but several of them have been successfully removed since then.

## @tabatkins — 2026-09-04

> "Landmine" seems an exaggeration, has this ever been an actual problem?

A landmine doesn't have to have exploded *yet* to still be a problem. ^_^ The point is that it's there for us to step on in the future.

We've had other issues about style serialization from changing what properties are shorthands (see: `position`). If we've so far gotten lucky and not had a major incompatibility for the properties we've changed over time, great! Are we sure that's going to continue to be the case? Is it worth future-proofing ourselves to avoid the problem ever arising?

@kbabbitt 
> Would this proposal mean that: [...]

Naively, yeah, it would. That's probably not *strictly* necessary; I think it could be written in such a way as to serialize as `margin: 1px 1px 1px 2px; margin-left: 2px;`, at least, so we don't need to remember multiple values for a property in a single rule, just that some contiguous slice of the rule's longhands originated from a shorthand.
