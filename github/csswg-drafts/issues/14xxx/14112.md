## @bramus — 2026-06-30

There is a section in the spec that covers this: https://drafts.csswg.org/css-anchor-position-1/#scroll

In practice I have found the “remembered scroll offsets” introduced there being a PITA to work with when both using and when trying to create tooling, because a lot depends on whether you scrolled first or not. Compare these two scenarios that use the same demo:

* Scenario 1:

    1. Open https://cdpn.io/pen/debug/PwGopoQ
    2. Open DevTools (to the right, so that it doesn’t scroll)
    3. Apply `align-self: stretch` to the `.tooltip`
    4. Scroll down
  
*  Scenario 2:

    1. Open https://cdpn.io/pen/debug/PwGopoQ
    2. Open DevTools (to the right, so that it doesn’t scroll)
    3. Scroll down
    4. Apply `align-self: stretch` to the `.tooltip`

(In Chrome) In scenario 1 the `.tooltip` will shrink as you scroll. In scenario 2 the tooltip will bleed out of screen, but once it’s fully in view by scrolling the other way, it’ll start shrinking again. In both cases, it won’t grow.

I _think_ some things might be fixable by adding extra [anchor recalculation points](https://drafts.csswg.org/css-anchor-position-1/#anchor-recalculation-point) — maybe after a scroll has ended? Or when the scroll direction changes? — but OTOH I would also assume that this has a negative impact on the performance during scroll. (But that then could always be throttled, so perhaps there is a way out here.)

The Safari behavior seems like an over-invalidation issue that kicks the positioned element back into the place where it should be.

I've been working on a UI library for many years. My custom popovers are positioned in rAF + ClientRect, which as far as I know is the snappiest way to do it. However when scrolling it is a well known issue that querying client rects of anchors lags behind their actual position on screen, which is particularly obvious on slower machines/CPU throttling.

I was waiting for webkit to finally ship anchor positioning, eager to rewrite everything I have to finally get rid of that annoying problem but now that I tried it – I've stumbled upon this issue.

## @sorvell — 2026-07-14

@bramus and @jakearchibald 

The spec language there (https://drafts.csswg.org/css-anchor-position-1/#scroll) makes this sound a bit scary:

```
For performance reasons, implementations usually perform scrolling on a separate scrolling/"compositing" thread, 
which has very limited capabilities (simple movement/transforms/etc., but no layout or similar expensive operations)
```

But [this riff](https://codepen.io/editor/Steve-Orvell/pen/019f5de1-6eac-7a64-bdcf-8db35cd14093) on @bramus' example seems to show that when the `stretched` checkbox is selected:
1. all the browsers re-size the tooltip when it gets smaller but not bigger. It seems unclear how that fits the spec language.
2. when the tooltip becomes un-stretched by scrolling one direction and then the other, clicking the `twiddle styling` checkbox (which changes the tooltip border) "fixes" the size on Safari/Firefox but not Chrome.
3. when the `scrollend fix` checkbox is checked, a `scrollend` listener toggles the display of the tooltip and this causes it to resize on all the browsers (this appears to cause the anchor recalculation [described in the spec](https://drafts.csswg.org/css-anchor-position-1/#anchor-recalculation-point)).
4. Safari/Firefox seem to handle the flip-block behavior differently from Chrome.

This issue is a lot more visible when position element is size-dependent on the modified containing block. This basically seems to expose what engines to do try and optimize reflows away. e.g. In this [testcase](https://github.com/user-attachments/files/30096822/ap.html) scrolling then hovering on the positioned element changes its sized on Firefox and Safari but not Chrome.

There are existing cases for this, but in-the-wild use of anchor positioning may make it more noticeable.
