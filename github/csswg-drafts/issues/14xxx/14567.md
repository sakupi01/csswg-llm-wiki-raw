I asked on social media what feature is missing from `@scope` that build tools provide, and I got two consistent answers:

1. Naming conflicts on the scope root itself
2. Scopes that exclude a nested scope

Issue 1 is actually addressed if you use embedded `<style>@scope {}</style>` rules. But that works because there are no selectors involved. It's hard to imagine a solution for unique selectors that doesn't involve a build step. (If anyone has ideas, we can open an issue for that one)

Issue 2 is usually phrased in terms of JS framework components, such as Vue:

```vue
<script setup>
import { ref } from 'vue'
import Article from './Article.vue'

const msg = ref('Hello World!')
</script>

<template>
  <Article>
  <p>I should be red</p>
  </Article>
</template>

<style scoped>
 p {color:red;}
</style>
```

Shadow-DOM handles this use-case well. The paragraph slotted into the `Article` is still part of the outer context. But `@scope` doesn't have a good way to [express the same idea directly in CSS](https://codepen.io/editor/miriamsuzanne/pen/01a11816-90a8-748f-bbcc-e6385fba637c).

Should we consider something like `@not-scope (exclude) to (include again)` or `@scope not (exclude) to (include again)`? In practice, it would look something like this:

```css
@scope ([data-scope=outer]) {
  @scope not ([data-scope]) to ([data-scope=revert]) {
    p { background: powderBlue; }
  }
}
```

I think there may still be some practical issues here, in that it requires knowing what you want to exclude? Nesting scopes further also complicates things. But it does seem potentially useful to _exclude_ scopes from selectors like this.
