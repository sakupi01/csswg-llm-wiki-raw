### Context
We resolved to create single-axis scrollers by allowing a scrollable value in one axis and clip in the other: https://github.com/w3c/csswg-drafts/issues/12289
This allowed us to create interesting effects and we resolved that sticky, for example, tracks per axis scrollers: https://github.com/w3c/csswg-drafts/issues/865#issuecomment-4040585511
@tabatkins put together a draft PR to update a bunch of specs to recognize single-axis scrollers: https://github.com/w3c/csswg-drafts/pull/13903

### Problem & Proposal

One of the questions is whether scroll snap also tracks per-axis scrollers. I think that would be reasonable. One hiccup is that [`scroll-snap-type`](https://drafts.csswg.org/css-scroll-snap/#scroll-snap-type) includes an axis in which this scroller snaps.

So, it's pretty clear what happens in a y-only scroller with a y-only scroll-snap-type: it should only snap in y and snapping in x can happen in some ancestor scroller:

```
/* does _not_ capture x snapping, it's not a scroller in that axis and scroll-snap-type doesn't include that axis */
.scroller {
  overflow-y: scroll;
  overflow-x: clip;
  scroll-snap-type: y mandatory;
}
```

Similarly, if the scroller is a scroller in both axis, then that's just the current state: nothing propagates to ancestor scrollers

However, what happens if we have a y-only scroller with a snap that includes the x axis?

```
.scroller {
  overflow-y: scroll;
  overflow-x: clip;
  scroll-snap-type: both mandatory;
}
```
I think it's reasonable to say that because this container is a not a scroller in the x direction, then it cannot prevent some ancestor from snapping in the x direction, so the scroll-snap-type here is essentially ignored when it comes to x direction of some ancestor scroller. That seems to be similar to how we deal with sticky.

For completeness, @flackr also pointed out that if the developer doesn't want some ancestor scroller to snap in the x axis, they can always say `scroll-snap-align: center none` (in horizontal-tb)

The proposal is to clarify that scroll snap also respects single axis scrollers and "propagates" across such scrollers in the axis for which the scroller clips

## @flackr — 2026-06-05

This makes sense to me, since it's establishing the same behavior we have for non-scroll containers on these non-scrolling axes. Just to play devil's advocate, we could only propagate the other axis if the inner snap container didn't claim any snap behavior for it, but this would be inconsistent with what we do for `overflow: clip` on both axes, so i have a preference for ignoring the clip axis snap type.
