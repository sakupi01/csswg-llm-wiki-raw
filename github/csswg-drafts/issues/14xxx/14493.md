In July 2024, the Web Preferences API proposal was incorporated into the Media Queries Level 5 specification following [CSSWG issue #6517](https://github.com/w3c/csswg-drafts/issues/6517).

Since then, there have been no shipping implementations of the API. The original WICG proposal has since been retired/moved into the Media Queries specification, and the original explainer is now noted as potentially outdated.

I would like to use TPAC to establish whether there is still sufficient interest from implementers and the Working Group to continue developing this feature, or whether it should be removed from the specification.

In particular:

* Do browser vendors still see value in providing a mechanism for sites to override user preferences such as `prefers-color-scheme`, `prefers-reduced-motion`, etc.?
* Are there plans or interest in implementing the current proposal?
* If there is implementation interest, is the current design still the right approach?

If there is interest in continuing the feature, we would also like to discuss some of the outstanding design questions, including:

* Preference propagation to iframes and subresources, how an override should interact with same-origin and cross-origin iframes. [#11577](https://github.com/w3c/csswg-drafts/issues/11577)
* Retrieving the original preference value, whether and how a site should be able to distinguish its override from the underlying user-agent preference. [#11580](https://github.com/w3c/csswg-drafts/issues/11580)
* Security and privacy, including the implications of persistent, origin-scoped overrides, propagation to third parties, and potential fingerprinting or cross-site information leakage.
* Persistence and storage, how overrides should be persisted, cleared, and synchronised, and how this interacts with existing browser storage and privacy models (there was a lengthy discussion on this last time).

The desired outcome from the discussion would be to determine if we continue, revise or remove the feature completely

## @bramus — 2026-09-16

Personally I still see a lot of value in allowing users to change their preferences (such as `prefers-color-scheme` and `prefers-reduced-motion`) on a per-origin basis and in a structured manner.

The Web Preferences API would allow that, working around the issues that are detailed [in the explainer](https://github.com/WICG/web-preferences-api#introduction):

> Currently, website authors have a choice when wishing to honour a user's preference for a given setting:
> 
> They can choose to "use the platform" where the user must indicate their preference via their OS or, if lucky, they can override in the browser. This comes with a number of issues:
> 
> - Relies on the user's OS or browser offering the ability to change the setting
> - Relies on the user knowing how to change the setting in their OS or browser
> - No ability to override the setting for a specific site
> - No ability to sync preferences for a site across devices
> 
> Alternatively, sites can and do offer site-level settings, but this currently comes with a number of issues:
> 
> - No integration with CSS preference media queries
> - No integration with conditional resource loading (e.g. using `<source media="(prefers-contrast: more)">`)
> - No integration with JS APIs for retrieval of these preferences (e.g. `matchMedia`)
> - No integration with [User Preference Client Hints](https://web.dev/user-preference-media-features-headers/)
> - No integration with the `color-scheme` CSS property
> - The various client storage mechanisms that could store these preferences can be cleared in a number of scenarios
> 
> The **Web Preferences API** aims to solve this by providing a way for sites to indicate a user preference for a given pre-defined setting.

The end result for users is that the websites they visit get smaller (as authors no longer need to duplicate code) and that they can tweak the controls in one location (in the browser itself).

## @emilio — 2026-10-24

It seems like the main use case for this is `prefers-color-scheme`, and with the resolution in https://github.com/w3c/csswg-drafts/issues/13377 it seems something like this should work without requiring such massive API surface?

```html
<!doctype html>
<meta id="color-scheme" name="color-scheme" content="light dark">
<script>
  function setPreference(v, persist) {
    document.getElementById("color-scheme").content = v || "light dark";
    if (persist) {
      if (v) {
        localStorage.setItem("color-scheme", v)
      } else {
        localStorage.removeItem("color-scheme");
      }
    }
  }
  setPreference(localStorage.getItem("color-scheme"), false);
</script>
<button onclick="setPreference(null, true)">System</button>
<button onclick="setPreference('light', true)">Light</button>
<button onclick="setPreference('dark', true)">Dark</button>
```
