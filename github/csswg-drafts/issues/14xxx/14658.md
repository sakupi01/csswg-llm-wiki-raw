[Fonts 4](https://drafts.csswg.org/css-fonts-4/#serializing-at-rules) requires repeated feature blocks to be merged and repeated declarations to retain only their final value. It does not appear to specify the resulting block order or a general entry-order algorithm. Its duplicate-entry example serializes `cool` before `pretty`, illustrating last-occurrence order, but browser behavior differs from that example.

For example:

```js
const sheet = new CSSStyleSheet();
sheet.replaceSync(`@font-feature-values Example {
  @stylistic { a: 1; }
  @styleset { a: 2; }
  @swash { a: 3; }
  @ornaments { a: 4; }
  @annotation { a: 5; }
  @character-variant { a: 6 7; }
}`);
console.log(sheet.cssRules[0].cssText);
// Chromium 151 block order:
// annotation, ornaments, stylistic, swash, character-variant, styleset
// Firefox 153 and WebKit 26.5 block order:
// swash, stylistic, ornaments, annotation, character-variant, styleset
```

The duplicate-entry question can be isolated separately:

```js
sheet.replaceSync(`@font-feature-values Example {
  @styleset { a: 1; b: 2; a: 3; }
}`);
console.log(sheet.cssRules[0].cssText);
// Chromium 151, Firefox 153, WebKit 26.5: @styleset { a: 3; b: 2; }
// The last value wins, but the name retains its first insertion position.
// Fonts 4's cool/pretty example instead illustrates last-occurrence order.
```

The [existing WPT parsing test](https://github.com/web-platform-tests/wpt/blob/master/css/css-fonts/test_font_feature_values_parsing.html) assumes a particular order even in its error-recovery checks. Chromium reverses `whatchamacallit-1: 23; thingy-dingy: 3;` in one of those fixtures, unlike Firefox and WebKit. Specifying the order would let these tests assert a single expected serialization.

Related discussions do not settle this:

- [WPT #6647](https://github.com/web-platform-tests/wpt/pull/6647#issuecomment-319540222) explicitly raised the underspecified serialization and duplicate-entry position; the PR remains open.
- [CSSWG #3947](https://github.com/w3c/csswg-drafts/issues/3947) settled merging repeated blocks, rather than their serialization order.
- [CSSWG #12979](https://github.com/w3c/csswg-drafts/issues/12979) concerns selecting the winning descriptor value.
- [CSSWG #8131](https://github.com/w3c/csswg-drafts/issues/8131) concerns syntax error recovery.

Could the serialization section explicitly define both orders? A concrete proposal would be:

1. Serialize the defined block types in this order: `swash`, `stylistic`, `ornaments`, `annotation`, `character-variant`, `styleset`, omitting empty blocks. Specify the placement of any additional block types when introducing them.
1. Within each merged block, serialize names in their first-occurrence order; a later declaration of a name replaces its value without moving it.

This would require updating the current `cool`/`pretty` example to retain `pretty` first with its final value. The proposed block order matches Firefox and WebKit. All three engines match the proposed entry order in the `a: 1; b: 2; a: 3` example, but Chromium would need to change its ordering in the WPT fixture described above.
