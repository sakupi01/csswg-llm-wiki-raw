Hygienically rewritten variables are useful *on their own*, even without mixins. Even when just writing styles for a certain rule, it is incredibly common to need intermediate variables that you don't want to expose to the outside world.

Today, [this is done by convention](https://www.google.com/search?q=pseudo-private+CSS+variables): a leading underscore in the variable name indicates that this is meant to be private.

For example, a real code snippet to apply a parameterizable transparency checkerboard as a background to a color-slider component:

```css
.color-slider,
:host(color-slider) {
	--_transparency-cell-size: var(--transparency-cell-size, 0.5em);
	--_transparency-background: var(--transparency-background, transparent);
	--_transparency-darkness: var(--transparency-darkness, 5%);
	--_transparency-bg-size: calc(2 * var(--_transparency-cell-size));
	--_transparency-pattern: var(
		--transparency-pattern,
		repeating-conic-gradient(
				transparent 0 25%,
				rgb(0 0 0 / var(--_transparency-darkness)) 0 50%
			)
			0 0 / var(--_transparency-bg-size) var(--_transparency-bg-size)
			content-box border-box var(--_transparency-background)
	);

	background: var(--_transparency-pattern);
}
```

Besides holding intermediate calculations, pseudo-private variables are also used to initialize a variable while still allowing it to inherit and be trivially overridden.

Today, making these *actually* private would require a dummy, single-callsite mixin:

```css
@mixin --transparency-pattern() {
	--_transparency-cell-size: var(--transparency-cell-size, 0.5em);
	--_transparency-background: var(--transparency-background, transparent);
	--_transparency-darkness: var(--transparency-darkness, 5%);
	--_transparency-bg-size: calc(2 * var(--_transparency-cell-size));
	--_transparency-pattern: var(
		--transparency-pattern,
		repeating-conic-gradient(
				transparent 0 25%,
				rgb(0 0 0 / var(--_transparency-darkness)) 0 50%
			)
			0 0 / var(--_transparency-bg-size) var(--_transparency-bg-size)
			content-box border-box var(--_transparency-background)
	);

	background: var(--_transparency-pattern);
};

.color-slider,
:host(color-slider) {
	@apply --transparency-pattern;
}
```

This seems cheap (I just copied the existing code!) but in practice, CSS rules can be quite nested, whereas mixins need to be hoisted out, which creates an indirection that actively hinders understanding.

Imagine if I could actually apply the mixin in place, like a JS self-executing anonymous function: 

```css
.color-slider,
:host(color-slider) {
	@apply () {
		--_transparency-cell-size: var(--transparency-cell-size, 0.5em);
		--_transparency-background: var(--transparency-background, transparent);
		--_transparency-darkness: var(--transparency-darkness, 5%);
		--_transparency-bg-size: calc(2 * var(--_transparency-cell-size));
		--_transparency-pattern: var(
			--transparency-pattern,
			repeating-conic-gradient(
					transparent 0 25%,
					rgb(0 0 0 / var(--_transparency-darkness)) 0 50%
				)
				0 0 / var(--_transparency-bg-size) var(--_transparency-bg-size)
				content-box border-box var(--_transparency-background)
		);
	
		background: var(--_transparency-pattern);
	}
}
```

The UA would take care of creating a one-off mixin with a guaranteed unique name and applying it there on the fly. TBD how the CSS OM would represent this.

Alternatively, we could have an actual syntactic distinction (like JS does), which is more elegant:

```css
.color-slider,
:host(color-slider) {
	--#transparency-cell-size: var(--transparency-cell-size, 0.5em);
	--#transparency-background: var(--transparency-background, transparent);
	--#transparency-darkness: var(--transparency-darkness, 5%);
	--#transparency-bg-size: calc(2 * var(--_transparency-cell-size));
	--#transparency-pattern: var(
		--transparency-pattern,
		repeating-conic-gradient(
				transparent 0 25%,
				rgb(0 0 0 / var(--#transparency-darkness)) 0 50%
			)
			0 0 / var(--#transparency-bg-size) var(--#transparency-bg-size)
			content-box border-box var(--#transparency-background)
	);

	background: var(--#transparency-pattern);
}
```

`--#*` props are visible within their lexical `{ ... }` and inherit by default (or should they not?) but not visible from the outside (which can be implemented as hygienic rewriting). Note that visible does not mean they have a value, e.g. 

```css
.foo {
	--#foo: green;

	& + p {
		/* This would be red */
		background: var(--#foo, red);
	}
}
```

A syntactic switch is definitely a bigger lift, and probably not worth it just for this, but it may become more appealing if we could then adopt this new syntax in mixins as well. It could then help us do away with a lot of problems around hygienic rewriting and distinguishing when `--foo` means `--foo` vs `--rewritten-foo-43gh2gwlge`. It also has a nice consistency with JS.

## @kizu — 2026-06-10

I wonder if something like https://github.com/w3c/csswg-drafts/issues/11798 could help here. In https://github.com/w3c/csswg-drafts/issues/13524#issuecomment-4173368648 one of the potential names for that was `@locals` and that we could reuse it for this type of lexical scoping.

I could see it working as 

```CSS
.foo {
	@locals {
		--foo: green;

		/* This would be green */
		background: var(--foo, red);
	}

	/* This would be red */
	border: 2px solid var(--foo, red);
}
```

But that will need more thought for it to be a proper proposal: how to differentiate between locals and globals, nested locals, naming them, accessing them from other scopes, etc. (all of which could go into the 11798 eventually).

I think sugar like `--#` could also work (and could be more convenient for simpler cases), just wanted to link the bigger scoping issue here :)
