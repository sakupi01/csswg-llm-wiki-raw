Hygienically rewritten variables are useful *on their own*, even without mixins. Even when just writing styles for a certain rule, it is incredibly common to need intermediate variables that you don't want to expose to the outside world.

Today, [this is done by convention](https://www.google.com/search?q=pseudo-private+CSS+variables): a leading underscore in the variable name indicates that this is meant to be private.

For example, a real code snippet to apply a parameterizable transparency checkerboard as a background to a color-slider component:

```css
.color-slider,
:host(color-slider) {
	--_transparency-cell-size: var(--transparency-cell-size, 0.5em);
	--_transparency-background: var(--transparency-background, transparent);
	--_transparency-darkness: var(--transparency-darkness, 5%);
	--_transparency-bg-size: calc(2 * var(--_transparency-cell-size));
	--_transparency-pattern: var(
		--transparency-pattern,
		repeating-conic-gradient(
				transparent 0 25%,
				rgb(0 0 0 / var(--_transparency-darkness)) 0 50%
			)
			0 0 / var(--_transparency-bg-size) var(--_transparency-bg-size)
			content-box border-box var(--_transparency-background)
	);

	background: var(--_transparency-pattern);
}
```

Besides holding intermediate calculations, pseudo-private variables are also used to initialize a variable while still allowing it to inherit and be trivially overridden.

Today, making these *actually* private would require a dummy, single-callsite mixin:

```css
@mixin --transparency-pattern() {
	--_transparency-cell-size: var(--transparency-cell-size, 0.5em);
	--_transparency-background: var(--transparency-background, transparent);
	--_transparency-darkness: var(--transparency-darkness, 5%);
	--_transparency-bg-size: calc(2 * var(--_transparency-cell-size));
	--_transparency-pattern: var(
		--transparency-pattern,
		repeating-conic-gradient(
				transparent 0 25%,
				rgb(0 0 0 / var(--_transparency-darkness)) 0 50%
			)
			0 0 / var(--_transparency-bg-size) var(--_transparency-bg-size)
			content-box border-box var(--_transparency-background)
	);

	background: var(--_transparency-pattern);
};

.color-slider,
:host(color-slider) {
	@apply --transparency-pattern;
}
```

This seems cheap (I just copied the existing code!) but in practice, CSS rules can be quite nested, whereas mixins need to be hoisted out, which creates an indirection that actively hinders understanding.

Imagine if I could actually apply the mixin in place, like a JS self-executing anonymous function: 

```css
.color-slider,
:host(color-slider) {
	@apply () {
		--_transparency-cell-size: var(--transparency-cell-size, 0.5em);
		--_transparency-background: var(--transparency-background, transparent);
		--_transparency-darkness: var(--transparency-darkness, 5%);
		--_transparency-bg-size: calc(2 * var(--_transparency-cell-size));
		--_transparency-pattern: var(
			--transparency-pattern,
			repeating-conic-gradient(
					transparent 0 25%,
					rgb(0 0 0 / var(--_transparency-darkness)) 0 50%
				)
				0 0 / var(--_transparency-bg-size) var(--_transparency-bg-size)
				content-box border-box var(--_transparency-background)
		);
	
		background: var(--_transparency-pattern);
	}
}
```

The UA would take care of creating a one-off mixin with a guaranteed unique name and applying it there on the fly. TBD how the CSS OM would represent this.

Alternatively, we could have an actual syntactic distinction (like JS does), which is more elegant:

```css
.color-slider,
:host(color-slider) {
	--#transparency-cell-size: var(--transparency-cell-size, 0.5em);
	--#transparency-background: var(--transparency-background, transparent);
	--#transparency-darkness: var(--transparency-darkness, 5%);
	--#transparency-bg-size: calc(2 * var(--_transparency-cell-size));
	--#transparency-pattern: var(
		--transparency-pattern,
		repeating-conic-gradient(
				transparent 0 25%,
				rgb(0 0 0 / var(--#transparency-darkness)) 0 50%
			)
			0 0 / var(--#transparency-bg-size) var(--#transparency-bg-size)
			content-box border-box var(--#transparency-background)
	);

	background: var(--#transparency-pattern);
}
```

`--#*` props are visible within their lexical `{ ... }` and inherit by default (or should they not?) but not visible from the outside (which can be implemented as hygienic rewriting). Note that visible does not mean they have a value, e.g. 

```css
.foo {
	--#foo: green;

	& + p {
		/* This would be red */
		background: var(--#foo, red);
	}
}
```

A syntactic switch is definitely a bigger lift, and probably not worth it just for this, but it may become more appealing if we could then adopt this new syntax in mixins as well. It could then help us do away with a lot of problems around hygienic rewriting and distinguishing when `--foo` means `--foo` vs `--rewritten-foo-43gh2gwlge`. It also has a nice consistency with JS.

I wonder if something like https://github.com/w3c/csswg-drafts/issues/11798 could help here. In https://github.com/w3c/csswg-drafts/issues/13524#issuecomment-4173368648 one of the potential names for that was `@locals` and that we could reuse it for this type of lexical scoping.

I could see it working as 

```CSS
.foo {
	@locals {
		--foo: green;

		/* This would be green */
		background: var(--foo, red);
	}

	/* This would be red */
	border: 2px solid var(--foo, red);
}
```

But that will need more thought for it to be a proper proposal: how to differentiate between locals and globals, nested locals, naming them, accessing them from other scopes, etc. (all of which could go into the 11798 eventually).

I think sugar like `--#` could also work (and could be more convenient for simpler cases), just wanted to link the bigger scoping issue here :)

## @tabatkins — 2026-07-09

Yeah, I recognize the value of doing something like this. I've thought about doing it inline before, to simplify potentially-complex math expressions that use a lot of vars, but doing it via something like a mixin body does look better.

I don't really want a syntactic distinction in the *name* of the variable; that requires rewriting and means you have to be aware of whether a var is defined locally or coming in from the outside. I would prefer something more like what @kizu is talking about, but we *also* need a way to still set *actual* vars, not solely the local ones.

So I think my preference might be something like a `@locals` block that can *only* contain custom properties (and conditional rules), defining those as locals. These locals are then usable in the *surrounding* block, via the rewriting rules.

So given a slightly elaborated version of kizu's example:

```css
.parent
	.foo {
		@locals {
			--foo: green;

			/* This is invalid/ignored, only custom properties in @locals */
			background: var(--foo, red);
		}

		/* This would be green, it sees the @locals --foo */
		border: 2px solid var(--foo, red);
	}
	/* This is red due to fallback; the @locals --foo isn't visible and there's no "normal" --foo either.
	border: 2px solid var(--foo, red);
}
```

And yes, because it'll make Lea excited, I'd probably be okay with reverting our previous resolutions around #13138 for this. Our previous idea of requiring an `@local` prefix on *every* local variable was annoyingly verbose, but using a single wrapping rule makes it not as bad once you have 3 or more, and we'd be leaning on *general* CSS tech instead of having a mixin-specific syntax.

This resolves the drawbacks that Anders lists in that first #13138 comment; you *can* use rule-specific locals rather than only mixin-global ones, and this makes no-local mixins minimally verbose, since we wouldn't be using @result anymore. It also negates the issue we were having with mixins and macros having slightly different syntax, which was proving to be an annoyance now that we have resolutions that remove their scoping distinction. The arglist of a mixin would just define an "implicit" locals block that applies to the body of the mixin.

---------

Some remaining issues:

* This does run into the same problem that I was pushing back against in mixins, namely that the rewriting occurs syntactically based on *rule nesting*, but the value inheritance occurs dynamically based on *dom structure*, and those two don't necessarily coincide. So, just like in non-scoped mixins, you can *use* a var() reference that doesn't actually resolve to anything because its nested rule is actually applying to a sibling/ancestor/etc of the @locals-defining element. Presumably the WG is okay with this in a "well don't do that then" fashion.

* This brings the question of whether/how these scoped properties are exposed in the style model more to the front. We could somewhat paper over them when it was just mixins doing it, but if *any* rule can have locals, this becomes more troublesome. This is a bit subtle, because there's only a limited window when they *do* need to know their real name but haven't yet been substituted away - reading a style rule's `cssText` won't do the rewrite yet, and `getComputedStyle()` is post-substitution so you won't see the name there either. Inline styles (`el.style.foo`, `<el style="">`) presumably will continue to not support nested rules for now so this isn't an issue, but we should keep that in mind. I think only TypedOM is capable of exposing the specified style on an element, which would have to reflect the rewritten name; it can instead reflect it as an opaque reference that doesn't expose a name, so we don't have to worry about it being reused somewhere else where it doesn't make sense.
