While we're on the subject of making `@property` more ergonomic, what about allowing fallback values for invalid descriptors?

Today, this doesn't work:

```css
@property --color {
	syntax: "<color>";
	inherits: true;
	initial-value: green;
	initial-value: fancy-new-color;
}

body {
	background: var(--color, red);
}
```

The [testcase](https://codepen.io/leaverou/pen/EaWVvjJ?editors=1100) shows red.
WRT language semantics, there is no reason why it shouldn't. Can we make it so? 

Yes, it is possible to just include the `@property` in an `@supports` ([testcase](https://codepen.io/leaverou/pen/dPvYzXY?editors=1100)) but the ergonomics are significantly worse, and there's combinatorial explosion if you need fallbacks for more than one descriptor:

```css
@property --color {
	syntax: "<color>";
	inherits: true;
	initial-value: orange;
}

@supports (color: fancy-new-color) {
	@property --color {
		syntax: "<color>";
		inherits: true;
		initial-value: fancy-new-color;
	}
}

body {
	background: var(--color, red);
}
```

## @LeaVerou — 2026-09-01

It would, but that's not why `first-valid()` was designed. It's generally accepted that two declarations is a better fallback when it works. `first-valid()` was designed for IACVT cases where that _doesn't_ work. That's not the case here.
