In the [Processing Keyframes](https://drafts.csswg.org/css-animations-2/#keyframe-processing) algorithm, step 2.2 states:

> Group together all [`<keyframe-block>`](https://drafts.csswg.org/css-animations-1/#typedef-keyframe-block) declarations that share the same [specified](https://drafts.csswg.org/css-cascade-5/#specified-value) [`<keyframe-selector>`](https://drafts.csswg.org/css-animations-1/#typedef-keyframe-selector) (treating from as 0% and to as 100%), last declared [animation-timing-function](https://drafts.csswg.org/css-animations-1/#propdef-animation-timing-function) [computed value](https://drafts.csswg.org/css-cascade-5/#computed-value) (defaulting to default timing function if there is no such declaration), and last declared [animation-composition](https://drafts.csswg.org/css-animations-2/#propdef-animation-composition) computed value (defaulting to default composite if there is no such declaration). 

As far as I can tell, there doesn't seem to be any definition of what it means for these values to be equal. 

For instance, what does it mean for two declarations to "share the same [specified](https://drafts.csswg.org/css-cascade-5/#specified-value) [`<keyframe-selector>`](https://drafts.csswg.org/css-animations-1/#typedef-keyframe-selector)"? For trivial [`<keyframe-selector>`](https://drafts.csswg.org/css-animations-1/#typedef-keyframe-selector) like "50%" it seems clear, but what about "calc(50%)"? What about "var(--foo)"?

@tabatkins do you happen to know if equality between specified or computed values is specified or used anywhere else?

<!-- comment id=4837676110 author=tabatkins created=2026-06-29T22:09:44Z url=https://github.com/w3c/csswg-drafts/issues/14098#issuecomment-4837676110 -->
## @tabatkins — 2026-06-29

Computed values, yes, equality is relied on quite heavily for transitions purposes. It's underdefined, but we've gotten along okay so far with it. It's also used in `@container`'s style queries (implicitly relying on the same mechanics) and `if()`.

Specified values, no. We don't have equality used or even *implicitly* defined for those anywhere.

I'm pretty sure this is a leftover from the original spec, and at the time likely assumed that keyframe selectors were solely `from`, `to`, and literal `%` values.

## @weinig — 2026-06-30

Oh right, I have even recently re-written some of our transitions equality code so I totally should have remembered that :).

That leaves just the [`<keyframe-selector>`](https://drafts.csswg.org/css-animations-1/#typedef-keyframe-selector) part then, since the other two state computed value explicitly.

My, perhaps naive, proposal here would be to change the processing steps to first resolve `<keyframe-selector>` as if it were part of a property being applied to _element_, resolving any `var()` of `calc()` (or whatever else might be there) down to a percentage. 

Given that https://drafts.csswg.org/css-animations-2/#keyframe-processing has _element_ as one of its inputs, it seems like it should be possible to to treat this an an element context. 

@tabatkins is there spec text anywhere that can be invoked/linked to in cases like this to resolve CSS values against a specific element outside of the normal style property resolution path?

## @flackr — 2026-09-30

Combining keyframes that happen to compute to the same value can lead to very surprising behaviors as it changes the interpolated effect in parts of the animation that don't appear to be related keyframes.

Consider for example the following. To illustrate the issue with combining I've created a [demo](https://jsbin.com/rahisiy/edit?html,css,output) with concrete values. When the rotate duration goes to 0, you interpolate across the entire initial range towards a rotated box. IMO this is unexpected and surprising.

```css
/* Slides right, rotates, then slides down. */
@keyframes test {
  from { transform: translateX(0); }
  calc(50% - var(--rotate-duration) / 2) { transform: translate(100px, 0); }
  calc(50% + var(--rotate-duration) / 2) { transform: translate(100px, 0) rotate(90deg); }
  100% { transform: translate(100px, 100px) rotate(90deg); }
}
```

Additionally, combining would mean that when getting the keyframes from the web animations API, you would get a different number of keyframes for the same animation depending on whether the computed values combined. I think it is much less surprising and breaking if the number of those keyframes is constant.

Treating them as independent and using the specified order matches our resolution for animation-range based offsets in #8507.
