The way [random-item](https://drafts.csswg.org/css-values-5/#random-item) is currently specified, each item has an equal chance of being picked. In some situations, you'd want to increase the chance of one value to be picked over the others.

## What we have now

Something like this has an equal chance of ending up as `block` or `inline`:

```css
.elem {
  display: random-item(auto, block, inline);
}
```

 If you want display to be set randomly to `block` or `inline`, but only have a 20% chance of `block` being picked, you have to do this:

```css
.elem {
  display: random-item(auto, block, inline, inline, inline, inline);
}
```

This gives `inline` a 4/5th chance and `block` a 1/5th chance of being the eventual value.

##  Adding weighing to `random-item()`

Many CSS functions let us add a `<percentage>`  to weight between values, like `color-mix(red 80%, blue)` or `linear-gradient(to top, red, blue 10%)`. Something similar would work to enable weighted values in `random-item()`. Below would be equivalent to the 4 times repeating `inline` example above:

```css
.elem {
  display: random-item(auto, block 20%, inline);
}
```
Omitting the percentage would, just like in other color functions, set all of them to an equal value. Something like 
```
random-item(auto, 
  block 100%, 
  inline 100%, 
  inline-block 100%, 
  none 100%
);`
```

would require normalisation (total is 400%, each item is 25% of that, so each has a 1/4th chance of being selected) which also already happens for other CSS functions.

## Workaround

Currently, you can get this behavior combining `random()` and `if()` with style queries:

```css
@property --discrete-number {
  syntax: "<integer>";
  inherits: false;
  initial-value: 0;
}

span {
  --discrete-number: random(0, 10, 1);
  display: if(
    style(--discrete-number > 2): inline;
    else: block;
  );
}
```

## @Loirooriol — 2026-06-24

To avoid the syntax overlap problem, I'm thinking we could add

```
weighted-random-item( <random-key> , [ [ <percentage [0,∞]> | <flex [0,∞]> ] <declaration-value>? ]# )
```

The weight wouldn't be optional, but specifying `1fr` isn't a big deal.

`<flex>` would be resolved like in https://drafts.csswg.org/css-images-4/#valdef-stripes-flex

> A [`<flex>`](https://drafts.csswg.org/css-grid-2/#typedef-flex) is evaluated as a fraction of the total width relative to the total sum of <flex> entries in the function, after subtracting the thickness of any non-`<flex>` entries (flooring the subtraction result at zero).

Probably it should be a syntax error if:
 - the sum of `<percentage>` is more than `100%`, or
 - the sum of `<percentage>` is less than `100%` and the sum of `<flex>` values is less than `1fr`

Examples:

 - 20% `block`, otherwise `inline`

    ```css
    display: weighted-random-item(auto, 20% block, 1fr inline);
    /* Same as weighted-random-item(auto, 20% block, 80% inline-block) */
    ```

 - 20% `block`, otherwise distribute equally among `inline` and `inline-block`

    ```css
    display: weighted-random-item(auto, 20% block, 1fr inline, 1fr inline-block);
    /* Same as weighted-random-item(auto, 20% block, 40% inline, 40% inline-block) */
    ```

 - 20% `block`, otherwise distribute among `inline` and `inline-block` with ratios 3:1

    ```css
    display: weighted-random-item(auto, 20% block, 3fr inline, 1fr inline-block);
    /* Same as weighted-random-item(auto, 20% block, 60% inline, 20% inline-block) */
    ```

 - Distribute among `block`, `inline` and `inline-block` with ratios 2:2:1

    ```css
    display: weighted-random-item(auto, 2fr block, 2fr inline, 1fr inline-block);
    /* Same as weighted-random-item(auto, 40% block, 40% inline, 20% inline-block) */
    ```

## @Kilian — 2026-06-25

I would also be in favor of one function name, and one that follows existing patterns as much as possible, Browsing through the list of CSS functions on MDN, the following _all_ use `<percentage>` at the end of each declaration to add weighing between two or more values, so it's a well-established pattern.

- color-mix, 
- cross-fade 
- dynamic-range-limit-mix
- linear
- (repeating-)linear-gradient
-  (repeating-)radial-gradient

The crux is of course that they have narrow types like `<image>` and `<color>` that can't contain spaces (like `block 20%`).

Looking further, color functions like `rgb` and friends use a / syntax for the opacity. Something like that could work and like `rgb`, the weighing would be optional and normalized (so no syntax errors).

```css
elem {
  display: random-item(auto, 
    block / 10%, 
    inline / 10%, 
    inline-block / 50%, 
    none / 100%
  );
}
```

## @Kilian — 2026-06-25

I suspect the `background` shorthand is where many functions go to die. Using `{}` might work (though could give issues for the syntax around nesting), but I can't say I like the way it looks. 

Instead, looking at the `url()` function, that lets you add quotes to tell the parser what encompasses the url. These are only needed if otherwise that is impossible to determine. Similarly adding that to random-item would work and would read very naturally along existing CSS patterns:

```css
elem {
  background: random-item(auto, 
    10% / 10%, /* 10% with a weighing of 10% */
    90% / 90%  /* 90% with a weighing of 90% */
  );

 
  background: random-item(auto, 
    '10% / 10%',  /* 10% / 10% with a weighing of 50% */
    '90% / 90%'  /*  90% / 90% with a weighing of 50% */
  );
}
```

I don't know enough about the CSS syntax description but essentially the parser would interpret the `/` as where the weighing begins and not as part of a `<declaration-value>`, but a `<declaration-value>` that starts with a quote also has to end with one. 

Notably, there is already an existing pattern available for _escaping_ quotes if needed, so that's nice:

```css
elem::before {
  content: random-item(auto,
    'boosters are at 20%' / 20%,
    'boosters aren\'t at 20%' / 80%
  );
}
```

## @Kilian — 2026-06-26

I think the pattern like `if()` would work. If we make the percentage the first part, like so, then else is whatever is left up to 100% (which can be zero):

```css
random-item(
  auto,
  10%: block;
  20%: inline;
  else: none;
)
```

The `:` is a good differentiator to support both syntaxes, imo. The `;` also clearly solves some potential issues. 

With regards to the `{}` syntax: i hadn't seen that in the spec yet but I would much, much prefer quotes or even just escaping commas: `url(1.jpg) \, url(2.jpg)` as a much clearer and much more parseable syntax. The `{` is already the start of a declaration list. 

Lastly, even beyond that, any syntax could be specified to assume specific behavior (such as "commas separate items"). Behavior outside of that could be handled by custom properties as the wrapping mechanism. Shown below for the / notation I proposed: 

```css
elem {
  --backgrounds: url(1.jpg), url(2.jpg), url(3.jpg);
  background: random-item(
    auto,
    red / 30%,
    var(--backgrounds) / 70%
  );
}
```

Also works for the `if()` style if we want to keep the comma delimiter:

```css
elem {
  --backgrounds: url(1.jpg), url(2.jpg), url(3.jpg);
  background: random-item(
    auto,
    30%: red,
    70%: var(--backgrounds)
  )
}
```

I (still) think the `if()` style with percentage first reads better when we use a colon (eg:)

```css
random-item(
  auto,
  10%: block;
  20%: inline;
  else: none;
)
```
And would allow for the percentages to be omitted too:

```css
random-item(
  auto,
  block;
  20% : inline;
  none;
)
```
> inline at 20%, block and none both get 1fr out of 2fr of 80% is a 40% chance each.

The percentage at the end lets you get rid of "else", but I like the "else" because it can be a keyword and makes it very explicit that this fills up the rest and it forces visual consistency. It can work though:

```css
random-item(
  auto,
  block : 10%,
  inline : 20%,
  none
)
```
and also prevents the braces, which is a win in my book.

## @tabatkins — 2026-08-18

Okay, reviewing the discussion and the preceding comments in the issue, I think these are the four most reasonable options. We should decide between these.

# New function name

`random-weighted()` or `weighted-random-item()` or something like that. [Proposed by Oriol.](https://github.com/w3c/csswg-drafts/issues/14079#issuecomment-4788476234)

The grammar *requires* a weight to be provided, so it's unambiguous. We could require the weight at the start or at the end, whichever we think is better, but it does have to be fixed to one end or the other. (While *most* `*-mix()` functions allow the % and value in either order, the one with a fixed order, [`calc-mix()`](https://drafts.csswg.org/css-values-5/#calc-mix), takes the % second, so we can match that. This was chosen to match gradients, which also put their %s second.)

Braces are never needed to deal with the weight.

# Just add a % in either order, braces optional

We'd specify the parsing so that it would first *try* to parse as `<percentage> <decl-value>?`, falling back to `<decl-value>? <percentage>` if that fails, and finally just as `<decl-value>?` if both previous failed.

* This means `random-item(auto, 10% block, 20% inline, none)` would work fine.
* The other order, `random-item(auto, block 10%, inline 20%, none)`, would also work fine. We'd have to do non-greedy parsing (or a tiny bit of backtracking, same thing).
* If your value actually starts or ends with a % (or just *is* a %), you'd have use braces or else it'll be interpreted as a weight: `text-indent: random-item(auto, 0, {10%})`. (If you just wrote `random-item(auto, 0, 10%)`, it would interpret the second item as an *empty value* with a 10% weight.)

This will *often* be the simplest and most straightforward, doing what you want in the obvious way, but it means you'll have to pay attention to %s in your value and pull out braces, which is a novel requirement for them.


# Just add a % in either order, braces required

If you want to provide a weight, the value *must* be braced to separate it from the weight: `random-item(auto, 10% {block}, 20% {inline}, none)`.

This is simpler from a parsing and memory standpoint (no need to care about exactly what your value looks like, you just *always* brace when you use weights), but it does mean that braces are now needed in non-corner cases, which is novel as well.

# Use colon to separate weight from value

Similar to [`if()`](https://drafts.csswg.org/css-values-5/#if-notation) or [`interpolate()`](https://drafts.csswg.org/css-values-5/#mix).

* We could either define that `:` isn't excluded by the freeform-production rules (aka you *always* have to use braces if your value contains a `:`) or just let it fall out of parsing (aka you only have to use braces if your value starts with something that looks like `<percentage> :` so the parser would get confused.) I'm inclined to do the latter, as that's what `if()` and `interpolate()` do, tho in both those cases they're slightly helped by the fact that the colon is required.

In theory we could put the % and value on either side of the paren, but both parsing concerns and similarity to the `if()`/`interpolate()` structure suggest that the weight has to come first. Braces are *virtually never* needed to avoid parsing problems with the weight; it would require a *really* weird item value to run into problems.
