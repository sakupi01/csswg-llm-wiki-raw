https://www.w3.org/TR/mediaqueries-4/#media-types and https://www.w3.org/TR/mediaqueries-5/#media-types have a note that says

> It is expected that all of the media types will also be deprecated in time, as appropriate [media features](https://www.w3.org/TR/mediaqueries-4/#media-feature) are defined which capture their important differences.

I am confused by what this means and wonder in particular what it means for me as a user and developer in practice now.

- Does the note mean that I should expect that the media types `screen` and `print` will stop working in browsers and are going to match nothing then like other deprecated media types? Should I stop using them despite them not being deprecated yet, if I don't want my webpages to break in time?
- If that's the case, why don't you deprecate them now? On the other hand, what's the purpose of the note, if that isn't the case?
- Since the note points at media features as an alternative … Is there a guide which media features to use instead of the media types `screen` and `print`, if I want the exact same behavior?

Some background information:

I find the distinction between screen and print practically relevant. I am currently a student. I write all my notes and most homework assignments as webpages (using a light-weight markup language), which enables me to navigate easily through all that work. But homework assignments usually have to be submitted as PDF, so I print webpages into PDF files as well. I use different font sizes, margins and link colors in print for example. Links should stand out in the web page; they shouldn't in the printed file.

I've used the distinction between styles for print and screen so often recently that I wanted to introduce a feature in my software that automates adding the respective media-queries for convenience. But it wouldn't make sense to add a software feature that won't work in the foreseeable future anymore.

## @tabatkins — 2026-08-03

"Deprecated" doesn't mean removed; we can never remove things that are widely depended on, and there's a bunch of stuff in the web platform that's deprecated and banished to appendixes but still required to be supported. We just recommend against authors using them.

The general issue here is that "media types" try to bundle a lot of concepts together, in a way that actually didn't make very much sense in practice. What you actually wanted was to know the screen size, or whether there is a mouse pointer available that can hover something, etc., and we have media features that test for those now. Relying on the feature instead of the type means your styling will automatically work correctly on many varied devices that all share that feature, and won't misfire on, say, a tablet with a Bluetooth keyboard and mouse assuming that the user needs longpress interaction instead of hover.

"print" is the media type with the most justification to exist - it is *genuinely* different from all other output devices in important, significant ways, and most of the relevant differences *are* both unique to print and shared by essentially all printers. That's why we haven't done a lot of print-specific media features yet; it's less clear what the value is if it's still basically identical to just using the "print" media type.

This is why "print" and "screen" are still listed as non-deprecated, while all the other types are on the deprecated list. Some day we might find it worthwhile to finally capture the print-specific features with media features and finish deprecating the types, but until then, it's still fine to use the print type.
