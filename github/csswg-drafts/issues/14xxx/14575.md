CSS-content describes the `string-set` property which copies a value to a string, and a `string()` function for substituting that value into generated content.

This has been around forever and is supported in several print-focused tools to copy content to the page margins, and that's how [the example](https://drafts.csswg.org/css-content-3/#example-23e3824c) in the spec shows its use. However the `string()` function doesn't work outside the page margins, and the way it's defined it wouldn't really make sense if it did: what is the "the last value on the page" in a non-paginated context?

The [Named Strings](https://drafts.csswg.org/css-content-3/#named-strings) section starts with

> Named strings are a convenient way to pull metadata out of the document for insertion into headers and footers. In HTML, for example, META elements contained in the document HEAD can set the value of named strings. In conjunction with attribute selectors, this can be a powerful mechanism:

But it's not stated explicitly that`string()` does not work anywhere except in [Page Margin Boxes](https://drafts.csswg.org/css-page-3/#margin-boxes). It probably should.

## @faceless2 — 2026-10-09

> The second parameter doesn’t make sense outside a page context – or at least not with the currently specified keywords – but the overall function would be nice to have alongside var() and env().

We did experiment with its use in the page body, but it's awkward to use - it requires lookahead on the page then inserting a block of text, which can affect what's on the page, which may mean the value changes.

In a non-paginated context its use is effectively limited to setting the value of a string once to the first DOM element that it matches, and substituting that value later in the document - functionally this makes it a limited subset of `target-text()`. Given the very limited value, I don't think it's useful outside of page-margins.
