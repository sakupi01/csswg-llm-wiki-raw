Step 4 of the ["update the timing properties of an animation effect"](https://drafts.csswg.org/web-animations-1/#update-the-timing-properties-of-an-animation-effect) algorithm states:

> 4. If the [easing](https://drafts.csswg.org/web-animations-1/#dom-effecttiming-easing) member of input [exists](https://infra.spec.whatwg.org/#map-exists) but cannot be parsed using the [<easing-function>](https://drafts.csswg.org/css-easing-2/#typedef-easing-function) production [[CSS-EASING-1]](https://drafts.csswg.org/web-animations-1/#biblio-css-easing-1), [throw](https://webidl.spec.whatwg.org/#dfn-throw) a [TypeError](https://webidl.spec.whatwg.org/#exceptiondef-typeerror) and abort this procedure.

Like was done in https://github.com/w3c/csswg-drafts/issues/13853 for rangeStart/rangeEnd of the Animation interface, I propose we apply the same restrictions and make it parse error to use any constructions that require an element (e.g. font-relative units, var(), random(), index-sibling(), etc.), keeping things to just absolute lengths.

This is necessary for `<easing-function>` as it can include numeric values that can include calc. For example, `linear(calc(1em / 1px))`.

Like with rangeStart/rangeEnd, we can consider lifting this restriction in the future and fully specifying how/when these constructs would resolve.
