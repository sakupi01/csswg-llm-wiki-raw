https://drafts.csswg.org/css-mixins-1/#private

> Within the style rule (and any nested rules), any custom property with that name is actually a private property, and any reference to a custom property of that name (for example, with a `var()`) is a reference to the private property.

------

```css
.foo {
	@private {
		--alpha: private;
	}

	--alpha: public;

	--bar: if(
		style(--alpha: private): cyan; 
		else: orange
	);
}
```

I expect `style(--alpha: private)` to refer the private property and have a value of `private` in this style query and for `--bar` to then have a value of `cyan`.

Correct?

-----

```css
.foo {
	@private {
		--alpha: private;
	}

	--alpha: public;

	@container style(--alpha: private) {
		--bar: cyan;
	}
}
```

Here I would also expect `@container style(--alpha: private)` to reference the private property.
But the style query itself can never be true as no container can possibly have this private property.

Correct?

Although this style query would match:

```css
.foo {
	@private {
		--alpha: private;
	}

	--alpha: public;

	& .bar {
		@container style(--alpha: private) {
			--bar: cyan;
		}
	}
}
```

## @tabatkins — 2026-09-04

> I expect `style(--alpha: private)` to refer the private property and have a value of `private` in this style query and for `--bar` to then have a value of `cyan`.
> 
> Correct?

The style query *does* see the private property (this is exactly what the spec is referring to when it says "any reference to a custom property of that name"), but its value is actually `public` in your example, because your `--alpha: public;` declaration is *also* within the scope of the private property ("any custom property with that name is actually a private property,") and thus overrides the initial declaration you wrote in the `@private{}` block.

If `--alpha: public;` were defined in a different rule that applied to the same element, tho, then the style query would indeed see the `private` value. That is:

```css
.foo {
	--alpha: public;

	--baz: if(
		style(--alpha: private): green; 
		else: red;
	);
	/* --baz is red here; it's asking for the global --alpha */
}

.foo {
	@private {
		--alpha: private;
	}

	--bar: if(
		style(--alpha: private): green; 
		else: red;
	);
	/* --bar is green here, the public --alpha is shadowed by the private one */
}
```



> Here I would also expect `@container style(--alpha: private)` to reference the private property. But the style query itself can never be true as no container can possibly have this private property.
> 
> Correct?

Mostly correct. If we pretend that you've similarly fixed these two examples to make `--alpha: public;` be in the global scope, then yes,  the `@container` references the private property in both examples. In the second, it's clear that the CQ can see the `.foo` parent, but this can *also* happen in the first rule, if you have nested `.foo` elements. Both elements would be styled with the same private `--alpha`, and so the CQ on the descendant would see the value on the ancestor. (They don't need to be a direct parent/child; inheritance still works as normal, even tho the intervening elements wouldn't have any interaction with the private property.)

@sorvell 
> Agree, and I think you just have to make sure to not clobber public names you care about with your private names. That's maybe just a reasonable restriction?

Correct, that's how variables work in virtually every programming language. You can always override globals with locals within a local scope; if you don't want to shadow, you just use different names.
