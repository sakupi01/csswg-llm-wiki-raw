From: https://drafts.csswg.org/css-align-3/#auto-safety-position

> For this purpose, the overflow limit rect is the bounding rectangle of the [alignment subject’s](https://drafts.csswg.org/css-align-3/#alignment-subject) [inset-modified containing block](https://drafts.csswg.org/css-position-3/#inset-modified-containing-block) and its [original containing block](https://drafts.csswg.org/css-position-3/#original-containing-block). However, because the [scrollable overflow area](https://drafts.csswg.org/css-overflow-3/#scrollable-overflow-region) of a [scroll container](https://drafts.csswg.org/css-overflow-3/#scroll-container) can be extended to ensure the visibility of overflowing [absolutely positioned](https://drafts.csswg.org/css-position-3/#absolute-position) boxes, if the original containing block is generated by a scroll container (and is not its [fixed containing block](https://drafts.csswg.org/css-position-4/#fixed-containing-block)), the overflow limit rect is extended to infinity in any direction that does not extend into the [unreachable scrollable overflow region](https://drafts.csswg.org/css-overflow-3/#unreachable-scrollable-overflow-region).

See this testcase: https://wpt.live/css/css-anchor-position/position-area-overflow-icb-004.html
Which was added from: https://github.com/WebKit/WebKit/commit/a742f82ced72f93249bfbaad9ed6aa3585fc7373#diff-8bbe14e89217c3257d1177a8f7e00f8ee385d5f42cd7d38db98552cfe68ef2d0R444

From my reading of the spec (which explicitly omits fixpos, and doesn't reference the default anchor), this behaviour makes sense, but its specified anywhere.

WebKit seems to be allowing overflow when we have a default anchor, and are fixedpos.

Particular care needs to be applied, as we don't want this behaviour to affect position-try-fallback behaviour.

## @fantasai — 2026-08-06

Based on the discussion and resolution taken in https://github.com/w3c/csswg-drafts/issues/14172 ([see detailed minutes](https://github.com/w3c/csswg-drafts/issues/14172#issuecomment-5190247826)):
> RESOLVED: ... apply `safe` overflow alignment (with the meaning that it keeps the popover in the viewport if possible) ...

The proposal here is:
- By default, anchored fixedpos is allowed to overflow in the scrollable direction just like abspos, if scrolling would move its default anchor and thus allow it to be revealed; the overflow limit rect is otherwise constrained to max(viewport, IMCB).
- If `unsafe` is specified, it is aligned absolutely in its alignment container, with no safety adjustment. (No change.)
- If `safe` is specified, then the overflow limit rect is always constrained.

Agenda+ to confirm. CC @bfgeek
