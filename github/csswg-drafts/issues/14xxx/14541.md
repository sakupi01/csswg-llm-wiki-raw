`element.matchContainer(query)` evaluates `query` against the element's query container, i.e. its nearest eligible ancestor, not the element itself.

--- 

Regarding the naming, `matchContainer()` might suggest that you call it on the container itself rather than on a child of the container. I was also confused by that at first [and left a comment on the issue](https://github.com/w3c/csswg-drafts/issues/6205#issuecomment-4044113375), @lilles [had the same reaction](https://chromium-review.googlesource.com/c/chromium/src/+/8255022/comment/d79b78dd_23039d7c/), and @lukewarlow mentioned being a bit worried about it too.

It's clearer to me now that I've spent more time with it (the "container" is the nearest ancestor that matches the query).

Some options we could consider:
- Keep as-is (container = matching ancestor element)
- `matchContainerQuery()`
- `matchContainer(query, { target: "self" | "ancestor" })`, defaulting to `"ancestor"` so current behavior stays the same. Though I'm not sure it would actually reduce the confusion.
- `matchAncestorContainer()`
- Other suggestions welcome

I slightly lean toward keeping `matchContainer`, since it's consistent with what "container" means in `@container` (the matching ancestor). Any thoughts?

For naming prior art, @emilio [pointed out](https://github.com/w3c/csswg-drafts/pull/13551#pullrequestreview-5352514777) that Gecko has a devtools-only [`queryContainerFor(element)`](https://searchfox.org/firefox-main/rev/b333202cd8d8385cb382c42404a03995dbc126ec/dom/webidl/CSSContainerRule.webidl#24) on `CSSContainerRule`, which returns the element's container.
