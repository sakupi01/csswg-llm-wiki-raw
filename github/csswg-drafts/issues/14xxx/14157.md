# [css-borders-4] Stroke/hull direction uses the normalized (signed) half corner, but implementations require the convex half corner for concave shapes

**Spec:** CSS Borders and Box Decorations Level 4 — *To get the border-aligned corner clip-out path*

## Problem

When deriving the inset stroke/hull direction, the algorithm does:

> Let `clampedHalfCorner` be the *normalized superellipse half corner* given `clamp(curvature, -1, 1)`.
> Let `vectorFromStartToControlPoint` be `(2 · clampedHalfCorner − 0.5, 1.5 − 2 · clampedHalfCorner)`.
> Let `strokeA, strokeB` be the perpendicular of the normalized `vectorFromStartToControlPoint`.

The *normalized superellipse half corner* applies a `1 − convexHalfCorner` flip for `s < 0` (the concave shapes: scoop, notch). But both Blink and WebKit use the plain **convex** half corner here (no flip). With the spec's normalized (flipped) value, the resulting `strokeA`/`strokeB` point roughly 90° away from the correct inward direction, so **concave corners are offset the wrong way** — their inner tip is not inset.

This looks like a genuine mismatch between the spec text and shipping implementations, not just an editorial nuance.

## The divergence

Blink (`third_party/blink/renderer/platform/geometry/contoured_rect.{h,cc}`):

```cpp
// contoured_rect.h — curvature is k = 2^s
static constexpr float HalfCornerForCurvature(float curvature) {
  return std::pow(0.5, 1 / ClampCurvature(curvature));   // convex; no "1 - x" flip
}
constexpr bool IsConcave() const { return curvature_ < 1; }
constexpr Corner Inverse() const {
  return Corner({Start(), Center(), End(), Outer()}, 1 / Curvature());
}

// contoured_rect.cc — Corner::AlignedToOrigin(), the inset stroke/hull step
const float clamped_half_corner =
    Corner::HalfCornerForCurvature(ClampTo<float>(curvature, 0.5, 2));
const gfx::Vector2dF normalized_hull_vector = gfx::NormalizeVector2d(
    gfx::ScaleVector2d(
        gfx::Vector2dF(clamped_half_corner, 1 - clamped_half_corner), 2) -
    gfx::Vector2dF(.5, .5));
const gfx::Vector2dF adjusted_offset{normalized_hull_vector.x(),
                                     -normalized_hull_vector.y()};
```

Blink represents concavity as *reciprocal* curvature (`k < 1`, `IsConcave()`), handled by `Inverse()` elsewhere, so `HalfCornerForCurvature` never applies the `1 − convex` transform. Its hull vector is `(2·hc − 0.5, 2·(1 − hc) − 0.5)` with the perpendicular taken via `adjusted_offset = (x, −y)`, where `hc` is the convex half corner. WebKit does the same (`Source/WebCore/platform/graphics/CornerShapeUtilities.cpp`, in `adjustCornerForInset`):

```cpp
// The curvature is clamped to [-1, 1] (Blink clamps the equivalent 2^s to [0.5, 2])
// for the hull-direction computation only; the drawn curvature is unchanged.
double clampedCurvature = std::clamp(original.curvature, -1.0, 1.0);
double convexHalfCorner = std::pow(0.5, std::exp2(-clampedCurvature));   // convex; no "1 - x" flip
auto hullDirection = FloatSize(float(convexHalfCorner * 2.0 - 0.5), float(1.5 - convexHalfCorner * 2.0)).normalized();
strokeA = -hullDirection.height();
strokeB = hullDirection.width();
```

## Concrete example (concave clamp, `s = -1`)

The convex half corner and the spec's normalized (flipped) half corner give *perpendicular* control-point vectors:

| half corner used | `vectorFromStartToControlPoint` | perpendicular → `(strokeA, strokeB)` |
|---|---|---|
| convex `0.25` (implementations) | `(0, 1)` | `(-1, 0)` |
| spec normalized `1 − 0.25 = 0.75` | `(1, 0)` | `(0, 1)` |

With the normalized (flipped) value `(strokeA = 0, strokeB = 1)`, `offset1 = offset4 = 0`, so `adjustedCornerCenter = Center` — **the concave corner's tip is not inset at all**, and the offsets instead move toward `Outer`. The convex value `(strokeA = -1, strokeB = 0)` insets the tip correctly (via `strokeA` on both arms).

## Suggested fix

Use the **convex** half corner — `0.5 ^ (1 / 2^|s|)`, i.e. *without* the `1 − convexHalfCorner` concave flip — when deriving the stroke/hull direction, matching Blink and WebKit. Alternatively, state explicitly that the concave flip must not be applied for this step (it is still correct for the interpolation/`corner-shape` value used elsewhere).

If the current normalized half corner is intended here, it would help to explain how implementations are expected to inset concave corners with it, since as written it moves the tip in the wrong direction.


## Background

Noam Rosenthal's implementation write-up ([Implementing corner-shape](https://developer.chrome.com/blog/implementing-corner-shape), Chrome for Developers) documents this as intentional — concave shapes are computed as the *visually-symmetric reflection* of their convex counterpart:

> In terms of the specification and implementation, we are representing something visual here, so we use the symmetrical equivalents when computing concave shapes. **The rest of the math is done on convex shapes** (k>=1, or positive superellipse values).

That is precisely why the unflipped **convex** half corner is the correct input to the stroke/hull-direction step, and why the `1 − convexHalfCorner` flip should be scoped to the interpolated `corner-shape` value rather than the inset geometry — matching both Blink and WebKit above.

To recap, `normalized superellipse half corner` is broken, it can be seen in a few places:
- `-∞ Return 0.` but the formula goes to 1 for -∞.
- `∞ Return 1.` but the formula goes to 0 for ∞.
- `convert interpolation value to superellipse parameter` is not the inverse formula of  `normalized superellipse half corner`.
- etc.

https://github.com/w3c/csswg-drafts/issues/11608 says `RESOLVED: interpolate linearly across the corner diagonal and compute the parameter backwards from that`.

From a purely geometric POV, the corner diagonal x coordinate is (letting y=x):
n=2<sup>|K|</sup>
convexHalfCorner=0.5<sup>1/n</sup>
halfCornerX = K < 0 ? 1 - convexHalfCorner : convexHalfCorner

I don't know if this is the value that we want to use, for the ["hull"](https://pomax.github.io/bezierinfo/#offsetting:~:text=%22hull%22%20for%20the%20curve) vectors (In my head they are "pseudo normal" vectors, "pseudo" because they don't come from the derivate). I don't know much about bezier curves.

It seems in line with the resolution, so I guess that's fine. In #14142, I'm already doing that.

Regarding the hull vector directions, I think everything comes down to how `controlPoint` is calculated, because the start hull vectors were, and still are, calculated as perpendicular to the lines from `cornerStart` and `cornerEnd` to `controlPoint`.

Currently, in #14142, I'm doing:

> 1. Let `clampedHalfCornerX` be the [=normalized superellipse half corner=] given `clamp(K, -1, 1)`.
> 1. Let `controlPointX` be `1/(sqrt(2) - 1) ⋅ clampedHalfCornerX - 1/sqrt(2)`.

Basically, I take `clampedHalfCornerX` and apply an affine transformation so that it ranges from 0 to 1.

I have no clue whether this is correct.

For reference, the spec previously did something different that made little sense because of the bug in the half-corner formula. If I were to make that work, it would look like this:

> n = -2<sup>|clamp(K, -1, 1)|</sup>
> concaveHalfCorner = 0.5<sup>1/n</sup>
> clampedHalfCornerX = K < 0 ? concaveHalfCorner : 1 - concaveHalfCorner
> controlPointX = 2 ⋅ clampedHalfCornerX - 0.5
