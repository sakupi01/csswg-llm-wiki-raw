The default padding for `<select>`’s base appearance right now a) doesn’t adhere to good optical alignment due to the ::picker-icon and b) doesn’t provide enough spacing within the interactive elements (like option).

Proposed fixes:

```
select, input, textarea {
  padding-block: 0.5em;                     /* Currently 0.25em */
  padding-inline: 0.7em;                    /* Currently 0.5em */
}
select {
  padding-inline-start: 1em;
    /* Counter-balance ::picker-icon. */
  gap: 0.65em;                              /* Currently 0.5em */
}
select::picker-icon {
  padding-inline: 0.15em;                   /* Currently zero */
}
option {
  padding-block: 0.4em;                     /* Replaces min-block-size: max(24px, 1lh); */
  padding-inline: 0.75em 1.1em;             /* Currently 0.5em */
    /* Counter-balance ::checkmark. */
  gap: 1ch;                                 /* Currently 0.5em */
}
optgroup legend {
  padding-block: 0.6em 0.15em;              /* Replaces max-block-size: 1lh; */
  padding-inline: 0.75em;                   /* Currently 0.5em */
}
```

## @jensimmons — 2026-10-14

This is our recommendation for the inline padding & gap for the in-page select. This puts 0.7em on the left (inline-start). A gap of 0.55em + picker icon start padding of 0.15em = total of 0.7em. And a right padding (inline end) of 0.15em padding on the picker icon + 0.55em of padding-inline end = total of 0.7em on the right. 

In other words, there's 0.7em, 0.7em, and 0.7em. Which matches the padding for all other fields.

<!-- comment id=6165865584 author=JoshTumath created=2026-10-14T10:04:30Z url=https://github.com/w3c/csswg-drafts/issues/14321#issuecomment-6165865584 -->
## @JoshTumath — 2026-10-14

Ah thanks @lukewarlow, I missed this issue.

I have no strong opinion on how large the padding values should be, but my advice to authors is that - in most circumstances - they should specify `margin`, `padding` and `gap` in `px` units so that they don't scale with the text scale. However, I think we have to weigh up the arguments for and against, in this case.

The UA default stylesheet has typically specified margins and padding in `em` units, so perhaps we should try to be consistent with that? That said, there are some cases where it does use 40px or 2px for margins. For margins, I think `px` units are used for the inline axis and `em` units for the block axis. For padding, they are almost always specified in `em`.

For margins, that makes sense to me, because, when the text scales up, the spacing between blocks of text should get larger so that the separate paragraphs are distinguishable. But I do find it strange that the UA stylesheet specifies padding in `em` values - especially for things like dialog, popover - when scaled up text could squash the content on a small viewport.

So in conclusion, I think it's good if the base styles all use `px` units for padding, but if anyone wants to argue for consistency's sake that the padding should be in `em` units, I think that's fair enough.

I believe the current proposal from Jen and Nicole is this:

```
select, input, textarea {
  padding-block: 0.5rem;                     /* Currently 0.25em */
  padding-inline: 0.7rem;                    /* Currently 0.5em */
}
select {
  gap: 0.7rem;                                /* Currently 0.5em */
}

option {
  padding-block: 0.5rem;
  padding-inline: 0.7rem 1.4rem;             /* Currently 0.5em */
    /* Counter-balance ::checkmark. */
  gap: 0.5rem;                               /* Currently 0.5em */
}
```
