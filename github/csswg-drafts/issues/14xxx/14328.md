When the `line-height` is smaller than the font's ascent/descent, line boxes can have negative leading. If `text-box-trim` is applied to a block using a taller edge metric, does it remove this negative leading, thereby increasing the height of the text box? Blink and Gecko do this, but WebKit doesn't — see this [example](https://codepen.io/editor/kbhomes/pen/019ffe30-e39c-73f2-8973-252882a621c3).

Trimming negative leading seems to me like the correct behavior (and a useful one, so that you can still vertically align a block that has tight or overlapping lines within it), but it doesn't seem to be explicit in the specs and is missing from WPTs. I've filed [Bug 2063495](https://bugzilla.mozilla.org/show_bug.cgi?id=2063495) on the Firefox side to add those WPTs (conditional on this issue).

## @jakearchibald — 2026-08-14

Yeah I think the blink/gecko behaviour is correct here. `text-box` allows you to change which metric is used for the block start and end. Removing the leading is useful, even if it's negative.

Although the demo uses `line-height: 0.5`, you also (usually) get negative leading with `line-height: 1` and values in that region.

## @jakearchibald — 2026-08-17

For meeting or async discussion, here's my take:

For `margin-trim`, the use-case seems to be "I want margins to operate within this box, but I don't want them to have an effect on the box edge, or impact outside the box". Given this use-case, it seems like negative margins should be trimmed. That seems to be the intent of both the Safari and Chrome implementations.

For `text-box` one of the key use-cases is to clamp the box to a different metric than ascender/descender + half-leading, particularly for the purposes of creating a more visually equal padding. The developer isn't looking to reduce the size of the box, they're looking to use a particular metric from the font & discard leading. Therefore, trimming negative values seems correct. This is also consistent with `margin-trim`.

It is a little odd that a 'trimming' can result in something getting bigger, but I think that's a naming issue. We shouldn't define a less-useful behaviour because the name doesn't fit. If folks can't get past the naming, then we should look at renaming these properties.
