Take the example
```css
@function --f(--x) {
  result: 10px;
}

#target {
  --actual: --f();
}
```

The [spec](https://drafts.csswg.org/css-mixins/#evaluating-custom-functions) states in section 8 that `--x` should be invalid at computed time but implies that the function as a whole should resolve nonetheless, however [WPT expects](https://github.com/web-platform-tests/wpt/blob/691d45da216ab3677fa2b51daa903ec0b381ae3f/css/css-mixins/functions/dashed-function-eval.html#L867-L877) that the function resolves to the guaranteed-invalid value and [Chrome matches that behavior](https://github.com/chromium/chromium/blob/20bceedd584695c643d8815057535be965f47776/third_party/blink/renderer/core/css/resolver/style_cascade.cc#L1937).

Scratch that last comment, actually. Step 8.2 is the problematic spot. It doesn't specify what to do if the function parameter doesn't have a default value, and I don't see anything else in the spec clarifying it one way or another.

Okay, right, on reviewing, the intended behavior is indeed that if the arg doesn't have a default value, it must be passed or else the entire call is invalid. I'll fix the spec to make that clearer.
