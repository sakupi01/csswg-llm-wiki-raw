I wouldn’t be surprised if this has already been discussed, but I didn’t find anything. After seeing [this post](https://bsky.app/profile/patrickbrosset.com/post/3mqjvfzdaw22u) by @captainbrosset about replacing TailwindCSS utility classes by macros/mixins:

~~~~ html
<div class="mx-auto flex max-w-sm items-center gap-x-4 rounded-xl bg-white p-6 shadow-lg">
  <img class="size-12 shrink-0" src="…" alt="Tailwind Logo">
  <div>
    <div class="text-xl font-medium text-black">ChitChat</div>
    <p class="text-gray-500">You have a new message!</p>
  </div>
</div>
~~~~
~~~~ html
<style>
.card {
 @apply --flex;
 @apply --mx-auto;
 @apply --max-w(var(--container-sm));
 @apply --items-center;
 @apply --p(6);
 @apply --gap-x(4);
 @apply --bg-white;
 @apply --shadow-lg;
 @apply --rounded(var(--radius-xl));

 & img {
  @apply --size(12);
  @apply --shrink-0;
 }
 & .title {
  @apply --text-xl;
  @apply --text-black;
  @apply --font-medium;
 }
 & .description {
  @apply --text-gray-500;
 }
}
</style>
<div class="card">
  <img src="…" alt="Tailwind Logo">
  <div>
    <div class="title">ChitChat</div>
    <p class="description">You have a new message!</p>
  </div>
</div>
~~~~

I wondered why [`@apply`](https://drafts.csswg.org/css-mixins-1/#apply-rule) currently does not accept multiple identifiers (i.e. dashed idents or functions or both). 

~~~~ ebnf
<@apply> = @apply [ <dashed-ident> | <dashed-function> ] [ { <declaration-list> } ]?;
~~~~

I believe this should be allowed, at least if there is no curly block following, and at least for macros.

~~~~ css
.card {
 @apply --flex, --mx-auto, --max-w(var(--container-sm)), --items-center, --p(6), --gap-x(4), --bg-white, --shadow-lg, --rounded(var(--radius-xl));

 & img {
  @apply --size(12), --shrink-0;
 }
 & .title {
  @apply --text-xl, --text-black, --font-medium;
 }
 & .description {
  @apply --text-gray-500;
 }
}
~~~~

## @tabatkins — 2026-07-17

The reason it's not allowed is that it conflicts with the ability to pass a contents block, yeah.

I was gonna object on it making CSSOM complicated, but I suppose we got around that with `@layer` by generating separate classes for the two syntactic forms. We'd have a minor conflict here in that a single mixin without a contents block could be either, but we can always just declare that it parses as the rule form.
