https://drafts.csswg.org/css-mixins-1/#private

I've been working on a transpiler for `@private` and I found that this rule has some weird aspects.
I don't think we would design it this way if we weren't designing it to make mixins work without `@result`.

I also think that the use cases for `@private` go beyond mixins and that this is a feature that is often requested by authors and it is something we should get right.

If I have to pick between:
- `@result` in mixin and `@private` that works as authors expect it to
- no `@result` and `@private` mainly works in support of mixins and even then in a weird way

Then I would pick the first option.

------

`@private` is now specified and dependent on nesting for slightly more complex use cases.
For example:

```css
.foo {
  @private {
    --color-a: red;
    --color-b: green;
  }

  color: var(--color-a);
  background-color: var(--color-b);

  &:hover {
    /* flip the colors */
    color: var(--color-b);
    background-color: var(--color-a);
  }
}
```

This example can't be written without nesting while using `@private`.
This second example isn't valid by the current spec:

```css
@private {
  .foo {
    --color-a: red;
    --color-b: green;

    color: var(--color-a);
    background-color: var(--color-b);
  }

  .foo:hover {
    /* flip the colors */
    color: var(--color-b);
    background-color: var(--color-a);
  }
}
```

Where instead of being attached to the nearest style rule, custom props are attached to the nearest `@private` rule.

Because nesting is required, you run into issues with CSS that can't be written with nesting today.
Like for example referencing pseudo element selectors.

------

Any rule that can't be placed inside a style rule is also impossible to use with private props.
Like for example `@keyframes`.

Authors will want to use private properties inside `@keyframes`.

There should be a way forward for this.

```css
.foo {
  @private {
    --color: red;
  }

  animation: --foo 2s;
}

@keyframes --foo {
  to {
    color: var(--color); /* can never see private props */
  }
}
```

The same is true for `@property` and having typed private custom properties.
```css
/* this seems much better, but is invalid by the current spec */
@private {
  @property --foo {
    syntax: <color>;
  }

  .foo {
    --foo: red;
  }
}
```

Or even `@import` with `@import "foo.css" private` which auto wraps everything imported with an `@private`.

Things like that should just work but seem impossible with the current model.

------

Also see: https://github.com/w3c/csswg-drafts/issues/14407

Mixing private and non-private props doesn't have an obvious/intuitive way of working.
Authors will continuously stumble over this.

This problem exists only because of the way `@private` is specced in support of mixins.

It goes away when `@private` is a rule that encapsulate the entire set of styles wherein private things are defined and used.

----

I think that the friction/resistance I experience around the current `@private` rule can be boiled down to:
- it combines two distinct actions: value assignment and marking as private
- marking as private has to be done in a separate rule and this rule is not the lexical scope
- it favors/requires using nesting

Being able to register a private prop directly in the rule that is the lexical scope would be a much more intuitive syntax. Having a clear path to props that are private in a stylesheet is also really important.

@romainmenke 
> Because nesting is required, you run into issues with CSS that can't be written with nesting today.

This is a bug with Nesting. We shouldn't contort other features around Nesting having some issues.

That said, even if we somehow *can't* fix the Nesting pseudo issue (I think we can), I'm also still of the opinion that we should let authors write out "nested declarations rules" (the anonymous rule we wrap around decls sandwiched between rules) explicitly, probably as `@nest {...}`, and *that* would also solve your issue. You'd just use a wrapping `@nest` with a `@private` in it, then you can have multiple sibling rules that all see those privates.

> Authors will want to use private properties inside `@keyframes`.

Sure, we should figure out an answer for this. I suspect the answer will be to allow some name-defining rules to be written inside `@private`, and their names will shadow in the scope, just like custom props do. That's essentially identical to what you're suggesting.

> Can we make private a flag on custom property registration?

Now you're just reinventing `@private`, but requiring the use of `@property` even if you're not registering a syntax. ^_^ Note that this idea doesn't address *any* of the issues in your OP, because it's just a syntax transform of the existing `@private` block.

----------

@sorvell 
> in this version what happens to privates when you `@apply` in a `@private` block; in the previous version, when you `@apply` in a mixin outside a `@result`?

Invalid because `@apply` isn't allowed in that context, both then and now.

> I even wonder if we need `@mixin` at all v. just using `@function` and "returning" with result or `@result` could just distinguish them. I'm not sure having a separate namespace for functions and mixins is valuable.

It's very valuable; the two concepts are *similar* in many ways but *extremely* distinct in the details. They evaluate in different contexts and at different times, with access to different information. Notably, no preprocessor I'm aware of that has the two concepts has *ever* tried to unify them into a single construct, even tho they're *much* more similar in a preprocessor than they are in real CSS.

> That mixin introdcuces 3 different @'s (mixin, apply, private) and function just one, seems like it's asking me to know too much.

Even if we *did* merge them in this way, mixins would still be juggling three different at-rules (function, apply, result); the only reduction is that the *definition* syntaxes would use the same name, despite being distinct syntaxes in their body. That's the sort of merging that tends to cause more confusion than it removes, in my experience.

What if [Example 18](https://drafts.csswg.org/css-mixins-1/#example-c334505e)

~~~~ css
mixin --same-size(--size <length>) {
  /* @result { */
    &, & > * {
      width: calc(10 * var(--size));
    }
  /* } */
}
.parent {
  font-size: 10px;
  @apply --same-size(1em);
}
.parent > .child {
  font-size: 20px;
}
~~~~

would desugar into approximately:

~~~~ css
.parent {
  font-size: 10px;
  --size: 1em;
  width: calc(10 * var(--size));
  /* = 100px */
}
.parent > .child {
  font-size: 20px;
  --size: 1em;
  width: calc(10 * var(--size));
  /* = 200px */
}
~~~~

but if the line in the mix-in looked like this instead:

~~~~ css
      width: calc(10 * var(-same-size-size));
~~~~

where the parameter name incorporates the mix-in base name automatically, which can never be done manually on the left side of a colon or in `@property`, 
it would desugar into something more like this

~~~~ css
@property -same-size-size /* sic! */ {
  syntax: "<length>";
  inherits: true;
}
.parent {
  font-size: 10px;
  -same-size-size /* sic! */: 1em;
  width: calc(10 * var(-same-size-size));
  /* = 100px */
}
.parent > .child {
  font-size: 20px;
  width: calc(10 * var(-same-size-size));
  /* = 100px! */
}
~~~~

~~~~ css

 @contents;
  color: var(--param);
  background: var(-mi-param);
}
div {
--param: red;

   @apply --mi();
  /* red on orange */
  }
 &.b {
   @apply --mi(lime);
  /* red on lime */
  }
 &.c {
   @apply --mi(var(--param));
  /* red on red */
  }
 &.d {
   @apply --mi(var(-mi-param, pink));
  /* red on pink */
  }
 &.e {
   @apply --mi() {
    --param: olive;
    };
  /* olive on orange */
  }
~~~~

## @sorvell — 2026-09-11

I suggest the working group revisit this issue in light of https://github.com/w3c/csswg-drafts/issues/14432#issuecomment-5541608748, https://github.com/w3c/csswg-drafts/issues/14442#issuecomment-5541705648, and https://github.com/w3c/csswg-drafts/issues/14442#issuecomment-5545801594). The spec asks us to think about functions and mixins together since they are in the same module and calls them "in many ways similar." I think the difference in how they treat custom properties has the potential to create a usability and understanding cliff.

There appears to be some agreement that:
1. private properties are useful in general
2. functions/mixins should not require excessive syntax
3. to the extent they are similar, functions and mixins should be similar to create

Given (1), private properties can just be uncoupled specifically from how function/mixins work and used in them as it does or does not makes sense. This is basically the case now since they are required in mixins and not functions.

Bringing back `@result` improves (3) at the cost of (2). Another possibility that does that same thing but in a different way would be to allow and/or require `@private` inside `@function`.
