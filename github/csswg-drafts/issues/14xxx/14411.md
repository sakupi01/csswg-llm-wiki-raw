CSS 2.1 [§12.1](https://www.w3.org/TR/CSS21/generate.html#before-after-content) said:

> This specification does not fully define the interaction of `:before` and `:after` with replaced elements (such as IMG in HTML). This will be defined in more detail in a future specification.

That future specification never arrived. #1018 has been open since 2017 asking for a narrower piece of it (only when `appearance: none`). Meanwhile [css-content-3](https://drafts.csswg.org/css-content-3/#content-property) carries a note asserting the **opposite of what engines ship**:

> Note: Replaced elements do not have `::before` or `::after` pseudo-elements; the content property replaces their entire contents.

Since [css-ui-4](https://drafts.csswg.org/css-ui-4/#appearance-switching) defines a **widget** as "replaced elements that can have native appearance", that note says `button::before` must not render.
All three engines render it.
And this is only the tip of the iceberg here!

## What engines actually do

I tested Chrome 151, Firefox 153, WebKit 26.5.
- [Testcase](https://experiments.verou.me/replaced-gencontent/).
- Screenshots: [Blink](https://experiments.verou.me/replaced-gencontent/screenshots/blink.png), [Gecko](https://experiments.verou.me/replaced-gencontent/screenshots/gecko.png), [WebKit](https://experiments.verou.me/replaced-gencontent/screenshots/webkit.png).

TL;DR:

- Embedded content is interoperable in NOT supporting generated content when using a **valid source**. Some variation when source is broken or invalid, but that doesn't translate to a CSS gap (see below)
- Text fields are interoperable in NOT supporting it
- Buttons are interoperable in NOT supporting it when created through `<input>` and supporting it when created through `<button>`.
- **Everything else is a mess, and `appearance` barely explains it.** Across 46 elements measured in both `appearance` states, only 4 behave differently — the 🟠 cells below. Chrome ignores `appearance` here entirely, so #1018's framing (that `appearance: none` un-replaces a control) doesn't describe any engine's behavior.

### Embedded content

| Element | State | Chrome | Firefox | WebKit | interop? |
| --- | --- | :-: | :-: | :-: | :-- |
| `img` | loaded | — | — | — | ✅ |
| `img` | broken | ✅ | ✅ | — | ❌ |
| `picture` | | ✅ | ✅ | ✅ | ✅ |
| `video` | loaded or not | — | — | — | ✅ |
| `audio` | loaded or not | — | — | — | ✅ |
| `canvas` | | — | — | — | ✅ |
| `svg` | | — | — | — | ✅ |
| `iframe` | empty or loaded | — | — | — | ✅ |
| `embed` | loaded | — | — | — | ✅ |
| `embed` | no src | — | ✅ | — | ❌ |
| `object` | loaded | — | — | — | ✅ |
| `object` | no data | — | ✅ | — | ❌ |
| `object` | broken | ✅ | ✅ | — | ❌ |

The four ❌s are not undefined behavior: they are disagreements about *whether the element is currently replaced*, which [HTML §15.4](https://html.spec.whatwg.org/multipage/rendering.html#replaced-elements) already defines. "**Can be** replaced elements" is conditional, and spelled out per state: `iframe`, `video` and `embed` always are; an `object` not showing an image, plugin or navigable is "treated as ordinary elements in the rendering model"; a broken `img` is "a non-replaced phrasing element whose content is the text". Chrome and Firefox follow that, WebKit keeps broken `img` and `object` replaced, and Chrome keeps a data-less `object` replaced at 300×150. Conformance bugs, not a spec gap.

`picture` confirms the rule from the other side: it is embedded content but never a replaced element, so it takes generated content everywhere.

**So the entire undefined area is widgets.**

## Proposal: Widgets _SHOULD_ have `::before`/`::after`; leave placement UA-defined

It's clear that refusing to define this has created an interop mess.
It is also clear that authors find this useful where it works, so I don't think restrictiveness is the way forwards here (and probably isn't web-compatible either: In #1018 it was cited that `::before`/`::after` on `<input>` passed 1% of Chromium page loads).
E.g. until `appearance: base` it has been the standard way to style checkboxes without recreating them.

Also, for all of these use cases, **the workaround is typically worse.** Decorating a control otherwise means wrapper or sibling elements that exist purely for presentation, and have to be kept out of the a11y tree by hand.

The argument that historically blocked this was _"but if they are replaced we don't know anything about their internal structure, how could we possibly place these?"_. But do we need to?
Authors overwhelmingly want *a* box that they can style and position themselves; the default placement matters far less than whether the box exists at all.

### Concrete proposal

- Recommend that widgets _SHOULD_ generate `::before` and `::after` boxes. This allows for exceptions for valid reasons (e.g. OS-provided dropdowns) without having to resort to weirdness like overlaying the content.
- Leave the exact placement of these boxes UA-defined for `appearance` != `base`.
- Add `content` on `::before`/`::after` to the [properties that disable native appearance](https://drafts.csswg.org/css-ui-4/#appearance-switching), so a devolvable widget with generated content simply devolves. That reuses existing machinery and avoids the overlap problem that checkboxes and radios have today (see [Blink](https://experiments.verou.me/replaced-gencontent/screenshots/blink.png) screenshot).
