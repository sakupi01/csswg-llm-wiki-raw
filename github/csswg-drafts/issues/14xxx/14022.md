Rather than adding a new image function, [light-dark()](https://drafts.csswg.org/css-color-5/#light-dark), for color scheme specific image selection, could we instead extend the existing [image-set()](https://drafts.csswg.org/css-images-4/#image-set-notation) function to support light/dark options.

This would work by expanding the [`<image-set-option>`](https://drafts.csswg.org/css-images-4/#typedef-image-set-option) production to something like:

```
<image-set-option> = [ <image> | <string> ]
                     [ <resolution> || type(<string>) || [ light | dark ] ]?
```

<!-- comment id=4653349176 author=tabatkins created=2026-06-08T20:42:13Z url=https://github.com/w3c/csswg-drafts/issues/14022#issuecomment-4653349176 -->
## @tabatkins — 2026-06-08

Do you have a particular reason to prefer doing it that way, rather than the current plan?

`image-set()` has a nice tight focus right now - content negotiation by type and resolution. These two features are *somewhat* intertwined (both are, to some extent, about image size), so it makes sense to handle them together. Plus, you only really want to express type info for *some* images (the ones with less-supported types), and that's awkward to extract into a separate function.

But light/dark is a separate axis entirely. You'd never want the UA to make a decision between a light and dark image based on *other* data; so, in effect, all this would do is pre-filter the list for *just* the light or *just* the dark images (and a little unclear what you'd do with the untagged ones), and then do negotiation based on that reduced list. That's identical to just filtering the list *yourself* and doing `light-dark(image-set(...), image-set(...))`. (Or, in the odder case where you're doing art-directed images and only *some* of the options have light/dark variants, you can invert the nesting and only use `light-dark()` where needed.)

In general, my preference is that orthogonal features should be separate functions. If they're intertwined in some way, or there's a significant UX improvement we can make by mixing them, then it can make sense, but otherwise it's easier to learn and use features when they're well-defined and modular.

## @Crissov — 2026-06-10

Why does this have to be crammed into functions at all? For font selection, we have a descriptive approach using an at-rule instead. 

~~~~ css
@image --foo {
  color-scheme: dark;
  src: url(foo.dark.png);
}
@image --foo {
  color-scheme: light;
  src: url(foo.png);
}
bar {
  background-image: image(--foo);
}
~~~~

## @tabatkins — 2026-06-12

@Crissov Constructs have to pay for their weight. Fonts are larger and relatively complex, and commonly used in multiple places, and have a whole funky cascade-together behavior; giving them an at-rule and then referring to the group by name makes sense.

Images don't really share any of those properties. Inlining the choice is much lighter-weight.
