A new 5th edition of the MPEG Open Font Format that is about to become publicly available for $0 which documents both the avar v2 table (already fully covered by #10599 that ended up as https://drafts.csswg.org/css-fonts-5/#ex-avar2) as well as 3 other things first described in https://github.com/harfbuzz/boring-expansion-spec - which I believe are not yet supported by CSS `tech()`:

1. Variable Components, with a new SFNT 'VARC' table
2. More than 65,535 glyphs in the `cmap` table (and a lot of other tables that reference glyphs by glyph ID)
3. Cubic beziers in the `glyf` table, version 1 (original since 1988 is version 0, naturally)

Therefore I would like to be able to do something like this in my CSS with a font family that is build with all 3 of these new things, and then built again in the now legacy current Microsoft OpenType 1.9.x format:

```
@font-face {
  font-family: 'Noto Sans Japanese';
  src: url('NotoSansJP-VF-VARC-full-cu.woff2') format(woff2) tech(variations, variable-components, beyond-64k, cubic);
  src: url('NotoSansJP-VF.woff2') format(woff2) tech(variations);
  font-weight: 100 900;
}
```

I kinda expect that any system that supports VARC will support the other two, but I also have a strong intuition that 'beyond 64k' may be implemented in systems that still do not support variable fonts at all, so I do think probably there ought to be a tech() token for each.

I suggest assigning to @svgeesus :)

## @jfkthame — 2026-09-25

Hmm, I'm seeing a certain lack of consistency in how we're creating `tech(...)` keywords.

In [CSS Fonts 4](https://drafts.csswg.org/css-fonts-4/#font-tech-definitions), we have `color-colrv0` and `color-colrv1` to refer to versions of the `COLR` table.

(I'm a bit sad we didn't separate the table-version suffix in some way, such as `color-colr_v1`, but that ship has sailed...)

But then in [CSS Fonts 5](https://drafts.csswg.org/css-fonts-5/#font-tech-definitions), I see a bare keyword `avar2` to refer to a new variation table version. No `v` prefix for the table version, and no descriptive prefix to say what kind of tech is involved. It would seem more consistent with the existing `color-*` pattern for it to be `variations-avarv2`.

The keyword for the new `glyf` table version would then become `cubic-glyfv1`, I guess. And for variable components, maybe `variations-varc`?

For the extension beyond 16-bit glyph IDs, how about something like `glyph-id-24bit`, to be more specific about the new capability. (`beyond-64k` sounds like it could be referring to file size or something.)
