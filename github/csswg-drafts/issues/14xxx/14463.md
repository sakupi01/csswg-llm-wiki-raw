See: https://drafts.csswg.org/css-color-5/#relative-colors

> When relative color syntax is used, color component values, whether directly specified or arising from color space conversion, are not clamped to the reference ranges but are retained as-is. This preserves out of gamut values, if the destination color space is capable of representing them.

----

This issue continues from https://github.com/w3c/csswg-drafts/issues/9484
There the focus was on how to handle values that after color space conversion are outside the reference range. For example `color(xyz-d65 1 1 1)` which after conversion to `lab` (D50) has a lightness greater than 100.

The same cases in RCS however raised some extra questions.

----

In my implementation the steps are roughly:
- start parsing a relative color
- parse the origin color
- finish parsing the relative color, replacing component value keywords with their respective values

At least in my implementation the individual component value keywords indeed represent unclamped values. But the outcome goes through the same clamping steps as a non-RCS function. So you end up with clamping anyway.

I suspect that chrome is doing something similar, while firefox and safari do seem to clamp the component value keywords.

We can test this with:

`lab(from color(xyz-d65 1 1 1) calc(l / 2) a b)`

If the `l` component value keyword was erroneously clamped you would expect the outcome to have an `l` value of `50`.

Whereas both my [implementation and chrome](https://preset-env.cssdb.org/color/computed/#JTdCJTIyY2klMjIlM0ElMjJsYWIoZnJvbSUyMGNvbG9yKHh5ei1kNjUlMjAxJTIwMSUyMDEpJTIwY2FsYyhsJTIwJTJGJTIwMiklMjBhJTIwYiklMjIlN0Q=) result in: `50.058`

| implementation | `l` |
| --- | --- |
| chrome | `50.0576` |
| firefox | `50` |
| webkit | `50` |
| csstools | `50.05771898` |

---

I am not quite sure how to implement this in a way that prevents clamping.
Do we completely skip clamping in RCS?

Example 1:
[`lab(from color(xyz-d65 1 1 1) l a b)`](https://preset-env.cssdb.org/color/computed/#JTdCJTIyY2klMjIlM0ElMjJsYWIoZnJvbSUyMGNvbG9yKHh5ei1kNjUlMjAxJTIwMSUyMDEpJTIwbCUyMGElMjBiKSUyMiU3RA==)

Ideally this doesn't clamp `l` to `100` so that you can round trip.

Example 2:
[`lab(from red 120% 0 0)`](https://preset-env.cssdb.org/color/computed/#JTdCJTIyY2klMjIlM0ElMjJsYWIoZnJvbSUyMHJlZCUyMDEyMCUyNSUyMDAlMjAwKSUyMiU3RA==)

This doesn't use any of the original component values.
Does this clamp?

Example 3:
[`lab(from color(xyz-d50 1 1 1) calc(l + 2) a b)`](https://preset-env.cssdb.org/color/computed/#JTdCJTIyY2klMjIlM0ElMjJsYWIoZnJvbSUyMGNvbG9yKHh5ei1kNTAlMjAxJTIwMSUyMDEpJTIwY2FsYyhsJTIwJTJCJTIwMiklMjBhJTIwYiklMjIlN0Q=)

Here `l` is `100%` but the `calc` causes the value to go outside of the reference ranges.

----

In other words?

- do we completely forgo clamping in RCS?
- or do we mark component values if they contain a a component value keyword and only skip clamping for those?
