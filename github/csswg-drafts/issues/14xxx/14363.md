I also considered the following separate, non-blocking point.

## Avoid coupling `:animated-image` matching to a global animation setting

**Description:** The specification says that, when a user-agent setting globally disables image animations, images that could otherwise be animated are considered static and do not match `:animated-image`. In an implementation following this rule, a page could test a known animated content image and infer whether the setting is active.

**Impact:** This would expose one bit of user-agent preference state.

**Suggestions:** Consider defining selector matching independently of the global setting and letting that setting affect rendering only. If the coupling is intentional, document the exposure.

**Affected Sections:**

- https://www.w3.org/TR/2026/WD-css-image-animation-1-20260409/#animated-image-pseudo

## @frivoal — 2026-08-24

Thank you for this observation @simoneonofri. I suspect that if a global setting (if it exists) that affects image rendering were to not affect the pseudo-class, things would not be great: the expectation is that the primary use of this pseudo class is to enable authors to provide UI on to control animated images *only* on images that are actually animated.

Having images that aren't actually animated (because of a browser setting) claim to be would invite the creation of UI that does nothing, which isn't great.

Maybe the user is fine with that, because they're the one who asked for animations to be off, so they won't be confused by extra UI being made non-functional because of that, but it's not obvious that this is the case.

As far as I can tell, this has more to do with privacy than security as such, and it seems to be a tradeoff: either the pseudo class doesn't respond to the setting, in which case privacy is preserved, but there is a risk of non-functional/confusing UI, or it does, and we leak one bit of information (whether that setting exists and is on), but gain a more consistent user experience.

Unless we can find something better that preserves usability and privacy, I suggest updating the spec to make this an RFC2119 may, and explain the tradeoff?

Would that seem satisfactory?

## @simoneonofri — 2026-08-24

Thank you. I agree that this specific point is best treated as a privacy/usability trade-off. An explicit RFC2119-may, together with a short explanation in the Considerations that choosing this behavior makes the setting observable to the page, would be satisfactory to me.

For completeness, I also attempted to test this with a browser PoC, but of course it was not supported.
