# [css-borders-4] Editorial: clarify "border-aligned corner clip-out path" (pre-clip path, curve intersection, keyword shapes)

**Spec:** CSS Borders and Box Decorations Level 4 — *To get the border-aligned corner clip-out path*

This is an editorial / clarity request rather than a correctness report. The algorithm is implementable, but while implementing it in WebKit I found a few things that took some digging to work out, and I think a couple of small clarifications would help the next implementer.

## 1. It would help to say that the returned path is a *pre-clip* shape

The guidance for the clipping step is this note:

> To avoid the complexities of defining how superellipses intersect, the algorithm simplifies the process by specifying that each corner is "clipped out" of the path. The specific implementation details of this clipping operation are left to implementations.

It wasn't obvious to me from this that:

- the path the algorithm returns is a **pre-clip** shape that can **extend past the boundary where the clip actually happens**, and
- an implementation is expected to **subtract/clip** that path against the target rect to get the real contour.

Read on its own, "each corner is clipped out of the path" can be taken to mean the returned path is already the final clipped contour. For inset corners it isn't — it can overshoot — and there's no worked note pointing that out.

### On "simplifies the process"

The note reads (at least to me) as if the algorithm that follows is going to define what happens where the curves intersect. As far as I can tell it doesn't specify how two corner curves behave where they meet; it produces per-corner clip-out paths and leaves the intersection to the implementation-defined "clipping operation."

That's a reasonable choice, but "simplifies the process" undersells how much is left to the implementer. To carry out the clipping what still needs to be solved is:

- **curve–line** intersections — each corner's Bézier against the straight border/rect edges (the more tractable case);
- **curve–curve** intersections — two superellipse corners meeting (e.g. at small radii or large insets), which needs a general Bézier-intersection routine;
- **splitting/trimming** the curves at those intersection points to build the final contour.

So the complexity of "how superellipses intersect" is still present — it's effectively handled by the clipping step rather than removed. It might help to note that the clipping operation entails curve/line and curve/curve intersection plus trimming (or can be delegated to a boolean path-ops engine, as Blink does via Skia), so readers know that work is expected.

### Worked example (top-left `notch`, radius `r`, uniform inset `t`)

For `notch` (`curvature = -∞`): `clamp(-∞, -1, 1) = -1`, giving `strokeA = -1, strokeB = 0`, so `offset2 = offset3 = 0`.

```
adjustedCornerStart  = (r+t, 0)      ← lands on the OUTER top edge  (not the inset edge y = t)
adjustedCornerCenter = (r+t, r+t)    ← correct inner tip
adjustedCornerEnd    = (0, r+t)      ← lands on the OUTER left edge (not the inset edge x = t)
axisAlignedCornerStart = (r+t, t)    ← the correct inner-edge point
axisAlignedCornerEnd   = (t, r+t)    ← the correct inner-edge point
```

Resulting `-∞` path:

```
(r+t, t) → (r+t, 0) → (r+t, r+t) → (0, r+t) → (t, r+t) → (t, t) → close
  miter      overshoot    tip         overshoot    miter      clipOuter
```

The path starts at the correct clip boundary `(r+t, t)`, then goes out to the outer edge `(r+t, 0)` and back (and similarly on the other arm). It becomes correct after the implementation-defined clip subtracts it against the rect, but nothing in the prose signals the overshoot beforehand — that's the main thing I'd suggest calling out.

## 2. The general case relies on a boolean path operation

Because the returned path can overshoot, the **general** case (arbitrary `superellipse()`) comes out correct only when it's combined with a boolean path operation — subtracting/intersecting the path against the target rect. Chromium/Blink does this by building each corner's curve out to an infinite rect and using `SkOpBuilder` with `kIntersect`.

It might be worth stating this dependency directly, since a boolean subtraction/intersection is effectively what makes the general case's output meaningful.

## 3. Closed-form shapes can be handled analytically (no boolean trim)

For implementers, it could be helpful to note that the keyword shapes don't strictly require boolean path operations — they can be produced analytically by choosing stroke/offset values that place the adjusted corner directly on the inset edge, so no trim is needed. WebKit takes this route:

- **bevel**, **scoop**, **round** — closed-form adjusted corners.
- **notch** — special-cased to `strokeA = -1, strokeB = +1`. With `strokeB = 1` the arm offsets become non-zero and the endpoints land on the inset edges:

  ```
  offset2 = normalize(End − Outer)  · (t · 1) = (0, t)  → adjustedCornerStart = (r+t, t)  ✓ inner top edge
  offset3 = normalize(Center − End) · (t · 1) = (t, 0)  → adjustedCornerEnd   = (t, r+t)  ✓ inner left edge
  ```

  `adjustedCornerStart`/`End` then coincide with `axisAlignedCornerStart`/`End`, the path has no outward detour, and the notch comes out correct without a trim.

The general `superellipse()` curve is the case that benefits most from the boolean path. Calling out this distinction could let implementations avoid boolean path ops for the common keyword cases.

## Suggested clarifications

1. Note that the returned path is a **pre-clip** shape that may extend beyond the target rect, and that the "clipping operation" is a boolean subtraction/intersection of it against the target rect.
2. Note that this boolean operation is effectively needed for the general `superellipse()` case, and that the clipping step involves curve/line and curve/curve intersection plus trimming.
3. Note (non-normatively) that keyword shapes (`bevel`, `scoop`, `round`, `notch`, `square`) can be produced analytically without a boolean operation — e.g. `notch` with `strokeA = -1, strokeB = +1`.
