#10844 resolved to insert the line-clamp ellipsis at the last soft-wrap opportunity that'll fit the ellipsis.

While investigating the implementation, we discovered that on Chrome Canary, the following testcase clamps entirety of its content:

```
<!DOCTYPE html>
<meta charset="utf-8">
<style>
.line-clamp {
  font-family: monospace;
  width: 25ch;
  line-clamp: 1;
  background: peachpuff;
  white-space: pre;
}
</style>
<div class="line-clamp">We find the phrase 'פעילות הבינאום'<200e> 5 times on the page.
We find the phrase 'פעילות הבינאום'<200e> 5 times on the page.
</div>
```

This does not seem right? Spec explicitly calls out `overflow-wrap` and `text-wrap-mode: nowrap`, but not `white-space: pre`.

<!-- comment id=5546618282 author=jfkthame created=2026-09-04T21:24:40Z url=https://github.com/w3c/csswg-drafts/issues/14448#issuecomment-5546618282 -->
## @jfkthame — 2026-09-04

`white-space: pre` is shorthand for `white-space-collapse: preserve; text-wrap-mode: nowrap`, so the spec text:

> For this purpose, [soft wrap opportunities](https://drafts.csswg.org/css-text-4/#soft-wrap-opportunity) added by [overflow-wrap](https://drafts.csswg.org/css-text-4/#propdef-overflow-wrap) are ignored, as are those inhibited by [text-wrap-mode: nowrap](https://drafts.csswg.org/css-text-4/#propdef-text-wrap-mode).

applies, AFAICS. Which means there are no (non-inhibited) soft wrap opportunities, and so.... all the text gets discarded???

While that's arguably what follows from the current spec text, I think it's clearly a bad result and needs to be reconsidered.

Perhaps we should say something along the lines of "If there is no soft-wrap opportunity within the line being clamped, fall back to truncating by individual grapheme clusters, similar to the behavior of `text-overflow: ellipsis` with a single line"?

## @andreubotella — 2026-10-31

From various conversations at TPAC, it seems like the behavior we want is:
- If there are no break opportunities that would fit the ellipsis, remove characters off the end of the line as if `overflow-wrap: anywhere`. This implies that characters are removed from the end in logical order. Also that shaping is not affected.
- Unlike `overflow-wrap`, this behavior also applies when `white-space` doesn't allow wrapping.
- If the last character that allows the ellipsis to fit in the line is a space (that doesn't count as a break opportunity, e.g. because of `white-space: pre`), then we break as with `white-space-collapse: break-spaces` (i.e. we can break _after_ that space, whether or not it's at the end of a space run). The space(s) would still be rendered _before_ the ellipsis.
- If after that, we'd still end up with an overflowing line somehow, we don't displace the entire line box. Instead, we break after the first character (as `overflow-wrap: anywhere` does) and add the ellipsis after it.

(And as something maybe for the future, it might be interesting to consider if we want to allow hyphenating if `overflow-wrap: hyphenate` is set, see #616. But this is not something I'm proposing right now.)
