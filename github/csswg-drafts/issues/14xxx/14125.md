The Web App Manifest spec is adding a new discrete CSS media feature, `application-context`, and we'd like the CSSWG's review of the media feature design, naming, and syntax.

PR: https://github.com/w3c/manifest/pull/1218 (preview linked in the PR)

What it does: `application-context` reflects the application context a top-level traversable is running in. It's a discrete media feature with two values:

- `application` — the top-level traversable is an installed web application context
- `none` (default) — otherwise

```css
@media (application-context: application) {
  .install-banner { display: none; }
}
```

It's orthogonal to the existing `display-mode` media feature (also defined in Web App Manifest): `application-context` answers "what context is this running in?", while `display-mode` answers "what presentation mode is used?". Same-origin child navigables inherit the top-level value; cross-origin nested documents always evaluate to `none`.

Background: this was agreed in principle at TPAC 2025 (w3c/manifest#1092) and is aligned with Microsoft Edge's [Application Context Media Feature explainer](https://github.com/MicrosoftEdge/MSEdgeExplainers/blob/main/ApplicationContextMediaFeature/explainer.md).

We'd particularly appreciate feedback on the feature name and value names, whether the discrete media feature framing fits CSS conventions, and the forward-compatibility note about adding future values.


(Updated 2026-07-24: value names changed from `installed`/`browser` to `application`/`none` following Web App Manifest WG discussion, to avoid conflating installation lifecycle state with the current running context.)

## @benfrancis — 2026-07-30

@Crissov wrote:
> I would rather suggest a value pair like rendering-context: application | document (perhaps also resource for embedded content), 

I understand what you're getting at, but applications also have documents.

> independence: hosted | stand-alone

Installed web apps are also "hosted", `standalone` is one of several [display modes](https://w3c.github.io/manifest/#display-modes) that can be used by an installed web application and queried by the [`display-mode` media feature](https://drafts.csswg.org/mediaqueries-5/#display-modes).

> host-environment: system | browser

Installed web apps can in theory also use the `browser` display mode, which makes this naming potentially ambiguous.

> chrome: headless | standard

I'm not sure "headless" is the right term, especially for the `minimal-ui` and `browser` display modes.

@fantasai wrote:
> It seems to me that the media query should be called installed, as that's what it's about.

That actually isn't what it's about. Whether or not an app is installed on the current system is different to whether or not it is currently being rendered inside an application context (i.e. a top-level traversable with an application manifest applied). Please see https://github.com/MicrosoftEdge/MSEdgeExplainers/blob/main/ApplicationContextMediaFeature/explainer.md#alternatives-considered

@tabatkins wrote:
> (installed: application | none) sounds just fine to me, yeah. You'll usually use it in a boolean context anyway, so just (installed), which reads very straightforwardly.

Note that if an application is installed on the current system but a document inside the navigation scope of the application is loaded inside a browser tab (but not captured by the app, which is the case in most current implementations), `installed` would evaluate to `none`. As @marcoscaceres [said above](https://github.com/w3c/csswg-drafts/issues/14125#issuecomment-5064426822), using the term "installed" conflates lifecycle state with the current running context. 

For context, for privacy reasons Apple [do not want](https://github.com/w3c/manifest/issues/1092#issuecomment-1646233098) it to be possible for a document loaded inside a Safari browser tab to know whether the app it belongs to is currently installed on the OS, so the `application-context` media feature was proposed as an alternative to the (non-standard and poorly named) `navigator.standalone` property currently used on iOS. The idea is that a document can tell whether it is currently being rendered inside an application context (i.e. an app window), but a document loaded inside a normal browsing context (i.e. a browser tab) can not tell whether the app it belongs to is installed on the OS.

---

I do acknowledge that `application-context`: `application`|`none` is a bit clunky.

If the Manifest specification deprecated the `browser` display mode (which I'm not sure any vendor actually implements for installed web apps) then `context`: `application`|`browser` might be a bit more intuitive, but that may break the display mode [fallback chain](https://w3c.github.io/manifest/#dfn-fallback-chain).

Alternatively the "standalone" display mode could be renamed to something else like "headless" and then "navigator.standalone" would be a less confusing name, but I think that ship has sailed.

## @benfrancis — 2026-08-04

I think if you want to use `display-mode` for this use case (which I don't disagree with) the `fullscreen` display mode will need to be split into two separate "modes" for:
1. An application context (app window) using the fullscreen display mode from an applied application manifest
2. An ordinary browsing context (browser tab) using the full screen API

As I understand it this is basically what caused the ambiguity in the first place. Currently it is not possible for a document to reliably detect whether it is being rendered in an app window because `display-mode: fullscreen` may evaluate to true in both cases.

Whilst both display modes may look visually identical they are different in that in the app fullscreen display mode the user (or document) may not be able to exit full screen to reveal browser chrome. The user agent rendering an app window may not even implement any browser chrome.

In theory there is also an ambiguity for the `browser` display mode because it is possible for an application context to use that display mode too, but in practice I'm not sure there's any difference between the two.

For the use case of displaying an app install banner using `display-mode` will be more complicated for developers, because they will have to test for multiple display modes, but it will at least be possible (as long as other application display modes are not also reused for other purposes).
