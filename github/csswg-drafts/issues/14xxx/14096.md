How should [`animation-timing-function`](https://drafts.csswg.org/css-animations-1/#propdef-animation-timing-function) in the following be interpreted?

```css
@keyframes bounce {
  from {
    top: 100px;
    animation-timing-function: ease-out, ease-in;
  }
}
```

The grammar of [`animation-timing-function`](https://drafts.csswg.org/css-animations-1/#propdef-animation-timing-function) allows for a comma-separated list of `<easing-function>` values, and that makes sense outside of `@keyframes`, as it is part of a coordinated value list. But when used inside of `@keyframes`, the list version doesn't seem correct.

I haven't been able to find anything in the spec that restricts the grammar down to a single value inside of  `@keyframes`, and I couldn't find any WPT tests that test for this.

(The same question applies to `animation-composition`).

The issue isn't one of usefulness, it's that I can't figure out if it is specified.

I disagree with the notion that if something is not currently interop an issue it should not be specified. That puts the burden on new implementations to reverse engineer existing implementations.

At least in WebKit, the current implementation will succeed at parse time, but fail at style building time, but this is happening pretty haphazardly (and I almost broke it by switching to using the specified grammar more generally).

My preference would be for this to fail at parse time by specifying that the grammar to use inside a keyframe rule does not allow for lists.

I think it is pretty unlikely for there to be any compat issues here, so, for the time being assume there are not, a concrete proposal here would be:

- Specify that when used in a keyframe rule, the `animation-timing-function` property has the grammar `<easing-function>`.
- Specify that when used in a keyframe rule, the `animation-composition` property has the grammar `<single-animation-composition>`.

Are there any other animation properties that might need similar special casing for use in a keyframe rule?

## @tabatkins — 2026-06-29

The original spec was not well-written in this regard, but imo the behavior the spec *should* define here is that the `animation-*` properties are not allowed inside of keyframes, but some related `animation-*` *descriptors* (with different, singular syntax) are allowed, and change the behavior of the keyframe itself.
