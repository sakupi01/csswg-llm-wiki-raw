I was looking at `grid-lanes` in Gecko, and it seems the [subgridding](https://drafts.csswg.org/css-grid-3/#subgrids) stuff is a bit of a can of worms ([tests](https://wpt.fyi/results/css/css-grid/grid-lanes/subgrid/)), tying a lot the grid and grid-lanes implementation (which is maybe what you want, but maybe not).

I was wondering, are there good use cases for this?  It seems it adds a significant amount of complexity / edge cases / combinatorial explosion of features that maybe aren't worth it?

## @alisonmaher — 2026-08-26

> I was wondering, are there good use cases for this?

I don't personally have strong use cases for this, but I know Apple had felt strongly about keeping things as close as possible to Grid, and had called out use cases for subgrid in https://webkit.org/blog/15269/help-us-invent-masonry-layouts-for-css-grid-level-3/, so perhaps @fantasai could help speak more to the specific use cases they had in mind.

> It seems it adds a significant amount of complexity / edge cases / combinatorial explosion of features that maybe aren't worth it?

Subgrid is complex, and adding support in grid lanes does require testing 3 new subgridding combinations (grid lanes subgridded to grid, and grid/grid lanes subgridded to grid lanes), so given the use cases, the complexity is quite high in comparison.

Webkit did ship at least some support for subgrid in grid lanes already (although we are still trying to add a more comprehensive test suite for the various combinations at the moment as part of the Chromium implementation).

@bfgeek's [original proposal](https://github.com/w3c/csswg-drafts/issues/9041) to split the track definition for grid lanes to its own property would have allowed us to progressively add support for subgrid if we received asks from authors for it, and this approach would have been the cleanest way to diverge and allow progressive enhancement of such functionality in grid lanes had the need arisen. However, I believe the ship has unfortunately sailed on this approach.

Given that we are reusing the `grid-template*` properties in grid lanes, not supporting `subgrid` would mean that the keyword would parse but not do anything, and if we got asks to add it later, we would have an incurred compat risk that the original alternative proposal would not have had.

Also, given the name "grid lanes", it becomes a bit more difficult to explain why "subgrid" doesn't work in the grid axis for this layout type. It is a separate display from grid, so there is some flexibility, but given that subgridding is technically feasible in grid lanes, it makes it trickier to justify the divergence (especially given the resolution taken in https://github.com/w3c/csswg-drafts/issues/12022#issuecomment-3201014167).

## @bfgeek — 2026-08-26

I don't have much more to add to what @alisonmaher has written.

The complexity for the subgridding cases was part of the motivation for the original alternate proposal (and the ability progressively add these features when needed). The WebKit implementation has a fair few implementation gaps when it comes to this area showing the complexity involved.

But as we resolved to keep everything as similar as possible it'd likely be bad/confusing to omit it.
Unless @emilio you want to re-litigate the design of the feature.
