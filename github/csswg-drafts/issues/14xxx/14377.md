I'm trying to update WebKit's calc() implementation to match the latest specs around how percentages are handled, and I am a bit confused about what counts as a context.

For example, take the rule: `opacity: progress(1%, (10% - 10%), 100%)` (from [WPT](https://github.com/web-platform-tests/wpt/blob/deaaa948b1/css/css-values/progress-serialize.html)).

- The `opacity` property grammar is `<number> | <percentage>`.
- In prose it states that percentages resolve to numbers.
- The `progress` math function returns a `<number>` made consistent with the input.

In WebKit, we parse `opacity` first as a `<number>` and then, if that failed, as `<percentage>`.

When parsing as a `<number>`, the 3 arguments to `progress` have type «[ "percent" → 1 ]» with percent hint "percent", and the `progress` expression has the type «[ ]» with percent hint "percent" (due to the rule that the result of progress is number made consistent with the input). 

To determine if that type («[ ]» with percent hint "percent") matches `<number>`, we consult https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-match, which has a bunch of rules, including this one under the `<number>` section:

> If the context allows [`<percentage>`](https://drafts.csswg.org/css-values-4/#percentage-value) values, but either doesn’t resolve them against another type or resolves them against a [`<number>`](https://drafts.csswg.org/css-values-4/#number-value), then for the type to be considered [matching](https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-match) the [percent hint](https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-percent-hint) must either be null or "percent".

Is this a context that allows `<percentage>` values? It doesn't seem like it, because then something like `opacity: calc(10% + 0.1)` would be allowed, and I don't think it is.

In my mental model, the context doesn't when parsing a `<number>`, but this spec text (and the tests) make me think I am mistaken. I think my mental model is that only prescribed unioned types, like `<length-percentage>` allow percentages intermixed, and we would need some `<number-percentage>` type for that rule to ever be useful. 

So, assuming my mental model is wrong, what is the rule? Anywhere a grammar allows both `<number>` and `<percentage>` should be considered a context that allows percentages, but only in arguments to math functions that transform their type to `<number>`?

## @kbhomes — 2026-08-24

I think the model that CSS Values and Typed OM lead to is:
- The calculation values are parsed, and the calculation context dictates the hint for percentages ([ref](https://drafts.csswg.org/css-values-4/#ref-for-percentage-value%E2%91%A2%E2%91%A1))
- The calculation's type is computed according to the Typed OM algorithms
- The calculation is determined to resolve to a `<number>`, `<length>`, etc. based on whether the calculation's type matches, using the calculation context to resolve the percentage details ([ref](https://drafts.csswg.org/css-values-4/#ref-for-percentage-value%E2%91%A2%E2%91%A1:~:text=invalid%2E-,A,invalid))

I think a key point of this model is that if a property is `<number> | <percentage>`, it's not correct to think of parsing a calculation as "attempt to parse the calculation as a `<number>`, and if that didn't work, attempt to parse the calculation as a `<percentage>`". Instead, it's "parse the calculation tree, and determine if its type matches `<number> | <percentage>`". This logic works even for `<length-percentage>` which is treated as convenience syntax for `<length> | <percentage>` by both [CSS Values](https://drafts.csswg.org/css-values-4/#mixed-percentages) and [Typed OM](https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-base-type:~:text=A%20type%20matches%20%3Clength%2Dpercentage%3E%20if%20it%20matches%20%3Clength%3E%20or%20matches%20%3Cpercentage%3E%2E%20Same%20for%20%3Cangle%2Dpercentage%3E%2C%20%3Ctime%2Dpercentage%3E%2C%20etc).

To me, this makes a lot more sense. Whether percentages have a knowable value is a property of the calculation context, not the calculation tree itself. In the model where `<number>` doesn't allow parsing percentages, it seems wrong to determine how percentages are treated based on what the ultimate type of the calculation is. 

Additionally, I don't think we would say that a declaration like `opacity: calc(100vw / 1000px)` is invalid just because `<length>` doesn't appear in the syntax for `opacity`. Instead, lengths are acceptable here because we know how to use a length in a calculation. I think it's similar for `<percentage>` in `opacity`, because we know how to use percentages in a calculation — they're defined by the property to be "raw" numbers — and this doesn't change regardless of what the ultimate type of the calculation is.

## @kbhomes — 2026-08-24

> Is this a context that allows `<percentage>` values? It doesn't seem like it, because then something like `opacity: calc(10% + 0.1)` would be allowed, and I don't think it is.

There should be no issue with this, Typed OM will never allow a number and percentage to combine through the ["add two types" algorithm](https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-add-two-types). This is without even needing to consider the percentage context for determining whether the result matches `<number> | <percentage>`.

- `10%` is `«[ "percent" → 1 ]»` with hint `percent` ([per CSS Values](https://drafts.csswg.org/css-values-4/#ref-for-percentage-value%E2%91%A2%E2%91%A1))
- `0.1` is `«[ ]»`  ([per CSS Values](https://drafts.csswg.org/css-values-4/#ref-for-number-value%E2%91%A3%E2%91%A1))
- `10% + 0.1` follows the "add two types" steps:
  - Step 1: `type1` is `«[ "percent" → 1 ]»` with hint `percent` and `type2` is `«[ ]»`
  - Step 2: The percent hint is applied to `type2`, updating it to `«[ ]»` with hint `percent`
  - Step 3:
    - Are the types equivalent? The base types and exponents differ, so it doesn't return that type immediately.
    - Would the types be equivalent if percents are treated as another type? Here, `type1` contains the `percent` base type, but there is no other base type in either `type1` or `type2`, so no provisional percent hint application occurs (because they will never be equivalent).
  - Step 4: The type is returned as failure.

## @weinig — 2026-08-24

> I think a key point of this model is that if a property is `<number> | <percentage>`, it's not correct to think of parsing a calculation as "attempt to parse the calculation as a `<number>`, and if that didn't work, attempt to parse the calculation as a `<percentage>`". Instead, it's "parse the calculation tree, and determine if its type matches `<number> | <percentage>`". 

I think this definitely the core question, and what I think probably needs to be spelled out a bit more clearly.

That said, I am not clear on the utility for the user that this model ends up with. Let's tweak the example I started with by adding a multiplication:

```css
opacity: calc(3 * progress(1%, (10% - 10%), 100%))
```

It seems confusing (from a users perspective) that this works. Its mixing `<percentage>` and `<number>`, which, if not for the `progress()` function, would not be allowed. Hence my example where it is not allowed, `opacity: calc(10% + 0.1)`.

I think the only change needed to disallow the examples using `progress()` would be to tweak the `<number>` section of https://drafts.css-houdini.org/css-typed-om-1/#cssnumericvalue-match to remove the allowance of percentage (the second and third paragraphs). Are there use cases that demand those rules remain?

Making that change would kinda side-step the core question above, but I still think we should try to clarify. My opinion is that the model I defined (parse one, then the other) is preferable, but would probably require special casing or re-defining `<length-percentage>` and its ilk.
