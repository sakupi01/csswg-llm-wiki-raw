In https://github.com/w3c/csswg-drafts/issues/10001#issuecomment-5374412577 @paceaux suggested to introduce a new modifier `w` that changes the value matching to take word boundaries into account.

Taking the example from that comment, the selector

```css
[class^="foo" w]
```

allows to match all of

```html
<div class="foo-bar">
<div class="foo bar">
<div class="bar foo">
<div class="bar foo--baz">
```

Though it is not restricted to word prefixes. It could be used in any attribute selector.

So here are some more examples:

Matching suffixes is done via

```css
[data-values$="bar" w]
```

matches

```html
<div data-values="foo-bar">
<div data-values="foo-bar baz">
<div data-values="foo bar baz">
<div data-values="foobar baz">
```

Exact word matching (equivalent to `[attr~=value]`):

```css
[data-values="foo" w]
```

matches

```html
<div data-values="foo">
<div data-values="bar foo">
<div data-values="foo bar">
<div data-values="bar foo baz">
```

but not

```html
<div data-values="foobar">
<div data-values="foo-bar">
<div data-values="barfoo">
<div data-values="bar-foo">
```

Applied to `|=`:

```css
[data-values|="foo" w]
```

matches

```html
<div data-values="foo">
<div data-values="foo-bar">
<div data-values="baz foo">
<div data-values="baz foo-bar">
<div data-values="bar foo baz">
<div data-values="bar foo-baz biz">
```

but not

```html
<div data-values="foobar">
<div data-values="barfoo">
```

This can be seen as a counter-proposal to #14289 and covers more use cases than the ones outlined there.

## @paceaux — 2026-08-25

@Crissov There are a few reasons I've suggested `w` as a modifier instead of a more complex operator. I'm definitely open to being swayed, but these were my reasons:

1. `w` comes off as RegEx-ish. `i` is a flag in RegEx, and `s` is at least a false-cognate in RegEx. So the thinking is that `[class ^="foo" w]` would have the developer thinking the usage is semantically and syntactically adjacent to RegEx flags. 
2. my thinking with a third symbol was that it would be harder for a developer to understand because it leaves the question of commutativity: would `[class^~="foo"]` be different from `[class~^="foo"]`? If not, *great*, but if so…
3. Noncommutative operators means now we're introducing syntax in a relatively unlikely place. It can be very frustrating to debug selector issues in the browser,  and this isn't even a _whole_ selector! Developers may have a very difficult time tracing or debugging issues already. How much harder will it be with noncommutative operators.  
4. If `^`, `$`, `*` are allowed to blend with `~`, then why not also `|` ? And also why not with each other? I think many developers might take the implication that some or _all_ of the symbols are… combinatorial. 
5. It's already a bit confusing that `^`, `$`, and `*` are cognates in RegEx, but `~` isn't (neither is `|`, but I digress). A `w` modifier sort of lightens some of that confusion because it's explicit that it represents a word break. 



Now, having said that, I'll make some of my own counterpoints:

1. the attribute selector syntax is not RegEx, and there's risk to the developer experience if we continue with a pattern of being RegEx-ish. A complex comparison operator definitely asserts, "this is not like RegEx"
2. Going the route of complex comparison operators might set the precedent that there _could_ be more useful operations in the future, such as `[class^|=foo]` which could select `.foo-bar` and `.food-bar` classes,  or `[class$|=oo]` which selects `.foo-bar` and `.waterloo-song`. 
3. Having a `w` modifier begs the question, "what does `[class~="foo" w]` do?

## @paceaux — 2026-08-25

The real problem statement here is that there's only one CSS attribute operator that is very explicitly a partial-word match, and that's `|=` which selects on the prefix-side of a hyphen _if that item is the first item in the value_ — so it forces the developer to author the classes in a very specific way. Not every CSS author has such control over the HTML. 

A partial word match could be achieved a few different ways:

_Assuming the goal is to match class names that start with `foo`_ :

* `[class^="foo" w]`
* `[class^~="foo"]`
* `[class~=[^=foo]]`

_and assuming the goal is to match class names ending with `bar`_:

* `[class$="bar" w]`
* `[class$~="bar"]`
* `[class~=[$=bar]]`

I tend to favor the flag approach because it doesn't add new syntax and the `w` seems to intuitively represent "word". In three options I could see, the `w` feels the easiest to understand.

## @paceaux — 2026-08-25

@Crissov I would gently disagree with the assertion that `[attr="value" w]` being equivalent to  `[attr~=value]` is a _strong_ counterargument. CSS offers many redundant options for producing selectors (after all, `[class="foo"]` is an equivalent of `.foo`  and any nested selector lists are equivalents of `selector :is(selectorList)`.  A new feature that incidentally overlaps with an existing one under one circumstance I don't think discredits the value of the new feature. 

The intent with a `w` flag is that there is intuitive sub-word matching within an attribute selector `[attr^=value w]` or `[attr$=value w]` are solutions to the problem, and the fact that `[attr~=value w]` is the same as `[attr~=value]` is a "happy mistake" as Bob Ross would say.
