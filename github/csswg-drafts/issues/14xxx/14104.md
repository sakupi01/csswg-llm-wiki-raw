https://drafts.csswg.org/css-break-3/#valdef-box-decoration-break-clone

> Each box fragment is independently wrapped with the border, padding, and margin.

But all browsers agree that this doesn't happen for the fragments of an inline box that are around a block-level:

```html
<!DOCTYPE html>
<span style="border: 25px solid magenta; line-height: 100px; box-decoration-break: clone; -webkit-box-decoration-break: clone">
  a
  <div style="width: 50px; height: 50px; border: solid cyan"></div>
  b
  <div style="width: 50px; height: 50px; border: solid cyan"></div>
  c
</span>
```

Less sure whether or not that matters since there is no spec text describing exactly how this works. But if these boxes are wrapped in fragments from the line box, and those fragments aren't 0 pixels wide, then it would be important for the top and bottom borders to not show up.

 - In Gecko, any content (including collapsed whitespace, abspos & floats) suffices to clone decorations between block-levels. And the cloned decorations can then make that line become non-phantom.
 - WebKit only clones when there is some content different than collapsed whitespace (including abspos & floats). And the cloned decorations can then make that line become non-phantom.
 - Blink only clones when the line box wouldn't be phantom before cloning. Thus the cloned decorations cannot make that line become non-phantom.
 - Servo always clones decorations between block-levels. The clones decorations can't make the line become non-phantom (which I consider a bug).

## @fantasai — 2026-08-05

> I'm pretty sure decorations shouldn't be inserted around those block boxes in general, box-decoration-break or not.

Agreed. I don't think I would even consider such block boxes to be wrapped in their own fragments. 

Here's the text about block-in-inline situations from CSS2:

> When an inline box contains an in-flow block-level box, the inline box (and its inline ancestors within the same line box) are broken around the block-level box (and any block-level siblings that are consecutive or separated only by collapsible whitespace and/or out-of-flow elements), splitting the inline box into two boxes (even if either side is empty), one on each side of the block-level box(es). The line boxes before the break and after the break are enclosed in anonymous block boxes, and the block-level box becomes a sibling of those anonymous boxes. When such an inline box is affected by relative positioning, any resulting translation also affects the block-level box contained in the inline box.

I think it's pretty clear that we don't draw the inline box's margin/border/padding around block-level content.
