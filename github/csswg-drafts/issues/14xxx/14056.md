## Background

On the Chrome team, we're [considering](https://chromestatus.com/feature/5163371507875840) a new browser API and storage mechanism called [Cross-Origin Storage](https://github.com/wicg/cross-origin-storage) (COS), which would allow for resources (like huge AI models but also large Web fonts) that are identified by their hashes to be shared across origins. This proposed API is imperative (`navigator.crossOriginStorage.requestFileHandle()`), but we reckon an additional declarative way to tap into this new storage mechanism from CSS would make sense, specifically, for Google Fonts (CC: @rsheeter, @davelab6, @tomasdev; for CSS WG: @tabatkins).

## Proposal

Add a new [`<request-url-modifier>`](https://drafts.csswg.org/css-values-5/#typedef-request-url-modifier) to [`<url>`](https://drafts.csswg.org/css-values-4/#url-value):

```
cross-origin-storage() = cross-origin-storage( [ '*' | <string># ]? )
```

This new modifier would be dependent on the existing [`<integrity-modifier>`](https://drafts.csswg.org/css-values-5/#typedef-request-url-modifier-integrity-modifier). With the `<cross-origin-storage-modifier>` present, this would be the processing flow:

* If a resource matching the hash from `integrity` is found in COS and the origin is allowed, it is obtained from there.  
* Else, the resource is obtained from the network and stored in COS for the future, iff the origin limitations allow so (see the following example). If the `integrity` doesn't match the fetched resource, the browser already refuses to use it, and thus also doesn't store it in COS

## Usage examples

Restricting COS access to *same-site* origins only, by omitting the argument (mirroring the behavior of omitting `origins` in the imperative API):

```css
@font-face {
  font-family: "Same-Site Corporate Font";
  src: url(
           "same-site-corporate.woff2"
           integrity("sha256-abc123...")
           cross-origin-storage()
       );
}
```

Allowing *any origin* to pull a resource from COS, falling back to the `url()`:

```css
@font-face {
  font-family: "Popular Emoji Font";
  src: url(
           "https://example.com/popular-emoji.woff2" 
           integrity("sha256-xyz789...") 
           cross-origin-storage(*)
       );
}
```

Allowing *only specific* origins to pull a resource from COS, falling back to the `url()`:

```css
@font-face {
  font-family: "ACME Inc Corporate Font";
  src: url(
           "acme-inc-corporate.woff2" 
           integrity("sha256-abc123...") 
           cross-origin-storage("https://acme-inc.example.com", "https://acme-cdn.example.com", "https://acme-inc-marketing-site.example.com")
       );
}
```

## Origin limitation 

The origin limitation is not meant as a security feature, but as a performance opt-in. It is useful for sharing resources between a set of related origins without making the resources globally available. This option is thought for proprietary resources or resources for which global COS cache hits are not anticipated. For example, if an office suite company has two related app sites, `write.example.com` and `calculate.example.com`, that both use the same corporate font, they can store the model in COS and restrict access to just these two origins. This way, the font is not globally available to all sites that use COS, but only to the two related sites that need it. Origins not on the list can only obtain the font from the network.

I've reviewed both the general COS proposal and this `url()` extension, and they look pretty good.

Content-addressable cross-site caching has been attempted a few times in the past, and never quite succeeded. This new attempt addresses some of the issues that stopped it in the past, like timing probes, plus our general understanding of how to mitigate some of the possible attack vectors has improved over the years. Pretty happy to see this get used.

Note that if you want to comment on the general COS proposal, the place to do that is in the [the proposal's repo](https://github.com/wicg/cross-origin-storage). This issue is just about letting CSS hook into COS declaratively, to allow sharing of things like large fonts. It's obviously dependent on COS being adopted.

## @tomayac — 2026-08-09

While testing whether `cross-origin-storage()` degrades gracefully in engines that don't recognize it yet, I found that the two engines I checked disagree on how they recover from an unrecognized `<url-modifier>`, and neither behavior appears to be specified.

**Test case:** a `@font-face` `src` with two comma-separated alternatives — one `url()` carrying an unrecognized modifier function, one plain fallback:

```css
@font-face {
  font-family: "Test";
  src: url("font.woff2" totally-unknown-modifier(*)) format("woff2"),
       url("font.woff2") format("woff2");
}
```

Inspecting the parsed rule via `document.styleSheets[...].cssRules[...].style.getPropertyValue('src')`:

**Chrome 151:** keeps both comma-separated items. The unrecognized modifier function is silently dropped from within `url()`, and the rest of that `url()` (including any other, recognized modifiers alongside it) stays intact.
**Safari Technology Preview (WebKit 605.1.15, reporting Version/27.0)**: drops the entire comma-list item containing the unrecognized modifier, keeping only the plain fallback item.

Both outcomes happen to leave a usable font in this minimal test, but the mechanisms are meaningfully different, and the difference matters once a `url()` carries more than one modifier (e.g. `integrity()` alongside `cross-origin-storage()`): in Chrome's model, an engine that understands `integrity()` but not `cross-origin-storage()` would keep the SRI check and just skip COS; in Safari's model, the whole alternative (including the `integrity()` check) is discarded, falling through to whatever's next in the list (or failing to load, if there's nothing next).

I checked the formal grammar in both [CSS Values and Units Level 4](https://drafts.csswg.org/css-values-4/#urls) (`<url()> = url( <string> <url-modifier>* )`) and the [Level 5 draft](https://drafts.csswg.org/css-values-5/#request-url-modifiers) (`<request-url-modifier>`), and neither defines what a parser should do with a `<url-modifier>` it doesn't recognize. There's no prose on this one way or the other. So this isn't a bug in either engine; it's actually unspecified, and the two current implementations have independently picked different (both reasonable) answers.

Given `<url-modifier>` is explicitly designed as an open extension point — `cross-origin-storage()` is the second or third proposal to use it, after `integrity()` — it seems worth pinning down the forward-compatible parsing behavior explicitly, the same way `@font-face`'s `format()`/`tech()` hints already have documented (albeit inconsistently implemented, see the [MDN note](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@font-face/src) that some browsers still fail the whole `src` descriptor on one invalid item) per-item fallback behavior. Two possible directions:

* Mandate that an unrecognized `<url-modifier>` function is dropped in place (Chrome's current behavior), leaving the rest of the `url()` (including other, recognized modifiers) intact.
* Mandate that a `url()` containing an unrecognized modifier is invalid as a whole, relying on `<font-src>`-style comma-list fallback (Safari's current behavior) for graceful degradation.
 
Either would give authors and future modifier proposals (including this one) a guaranteed cross-engine story instead of accidentally-compatible behavior. 

For the time being, the "falling through to whatever's next in the list" behavior can act as progressive enhancement, see [2. CSS integration](https://web-ai-community.github.io/cross-origin-storage-extension/progressive-enhancement-demo.html).
