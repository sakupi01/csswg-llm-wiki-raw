The icons we use for ::checkmark and ::picker-icon are not particularly useful to read aloud. The status of the control is already exposed to AT independently, so we propose using empty alt text for these glyphs:

```
::checkmark {
  content: "\2713" / "";
}
::picker-icon {
  content: ... / "";
}
```

## @matatk — 2026-09-23

We looked at this in a recent Accessible Platform Architectures WG call - thanks for flagging it @fantasai.

We appreciate the intent behind this change, however, after discussing it, we think it may be better to take a different approach.

Right now, this change is effectively a no-op, because any alt text (accessible name) being provided to the glyph will be overridden by the accessible name provided to the button that contains it.

However, in future, it is possible that users and ATs may wish to delve inside the button, to inspect it in more detail. In this case, overriding the glyph to have no name actually _removes_ information.

Whilst no AT does this yet, it would be nice to not preclude it as an option in future, and it's possible that the richer info gleaned from the choice of glyph could be of interest or assistance.

As CSSWG resolved, we too are keen to hear ARIA WG's view on this.

## @smhigley — 2026-10-01

@matatk I think re: whether the glyph would be overridden, my concern is that the glyph would contribute to the accName if exposed (or value, in the case of select and `::picker-icon`). Specifically in these cases:
- `::picker-icon` on a `<select>` -- since the value text is computed from the content of the select's trigger button, the glyph would presumably contribute to the value text.
- `::checkmark` on options -- similarly, in practice nearly all options get their accName from content, and the glyph would be text content. Unless the author added `aria-label` or `aria-labelledby`, I assume the accName of a selected option would become something like "\2713 orange" if the glyph isn't hidden.

Browser vendors can feel free to correct me if I'm wrong though :D
