## Title
Proposal: Overflow-aware pseudo-classes (`:overflowing-inline`, `:overflowing-block`)

---

## Problem Description

CSS currently provides mechanisms to *control* overflow (e.g., `overflow: hidden`, `scroll`, `clip`) but does not provide any way to *detect* when an element’s content overflows its container.

As a result, authors cannot conditionally adapt styles when clipping occurs, leading to:

- Reliance on JavaScript for overflow detection
- Visually broken UI when elements become partially clipped
- Inability to express responsive fallback behaviors purely in CSS

This is particularly problematic for modern UI patterns such as:

- Dynamic dashboards with constrained tiles
- Icon or badge containers with unpredictable content
- Tooltips/popovers near viewport edges
- Responsive cards with mixed content

---

## Proposed Solution

Introduce pseudo-classes that match elements whose content overflows in a given axis:

```css
:overflowing-inline
:overflowing-block
```

### Behavior

- `:overflowing-inline`  
  Matches elements whose inline-axis content exceeds their content box.

- `:overflowing-block`  
  Matches elements whose block-axis content exceeds their content box.

These pseudo-classes allow authors to react declaratively to overflow conditions.

---

## Example Use Cases

### 1. Hide partially clipped elements

```css
.card:overflowing-inline {
  display: none;
}
```

---

### 2. Scale down content to fit

```css
.icon:overflowing-inline {
  transform: scale(0.85);
}
```

---

### 3. Switch layout strategy

```css
.container:overflowing-block {
  flex-wrap: wrap;
}
```

---

### 4. Tooltip fallback behavior (paired with anchor positioning)

```css
.tooltip:overflowing-inline {
  position-try: left, right;
}
```

---

## Prior Art / Related Features

- `overflow` (CSS Overflow Module) — controls clipping but does not expose state
- `text-overflow` — handles inline overflow for text only
- `object-fit` / `background-size` — address content fitting but not detection
- Container Queries — allow size-based adaptation but not overflow detection
- Anchor Positioning — introduces collision-aware placement but not general overflow state

---

## Why This Is Needed

There is currently no declarative way to express:

> "Apply these styles only if this element is being clipped."

This forces authors into JavaScript-based solutions such as:

```js
element.scrollWidth > element.clientWidth
```

which:
- Adds runtime cost
- Increases complexity
- Breaks separation of concerns between layout and behavior

---

## Design Considerations

### 1. Axis-specific matching

Separating inline and block axes:
- Aligns with existing logical properties (`inline-size`, `block-size`)
- Avoids ambiguity across writing modes

---

### 2. Performance considerations

This proposal introduces a post-layout condition. Potential mitigations:

- Restrict matching to final layout phase
- Avoid recursive layout invalidation
- Define behavior similar to container query evaluation

---

### 3. Interaction with `overflow`

Pseudo-classes should reflect actual layout overflow regardless of:
```css
overflow: hidden | clip | scroll | auto;
```

---

## Possible Extensions (Non-blocking)

These are exploratory ideas that build on the same concept:

### A. Conditional masking

```css
clip-mask: fade;
clip-mask-trigger: overflowing-inline;
```

Apply a mask only when overflow occurs to soften clipping edges.

---

### B. Declarative overflow responses

```css
clipped-response: shrink | hide | wrap;
```

A higher-level abstraction for common adaptive behaviors.

---

These extensions are less critical but demonstrate the broader design space enabled by exposing overflow state.

---

## Open Questions

- How should overflow be defined for fragmented layouts?
- Should scrollbars affect matching conditions?
- How should this interact with `contain` and layout isolation?
- Can this integrate with container query evaluation models?

---

## Summary

This proposal introduces a minimal, composable primitive:

✅ A way to detect overflow  
✅ Compatible with existing CSS architecture  
✅ Unlocks new responsive and adaptive layout patterns  
✅ Reduces reliance on JavaScript for common UI scenarios  

---

Looking forward to feedback and discussion from the Working Group.
