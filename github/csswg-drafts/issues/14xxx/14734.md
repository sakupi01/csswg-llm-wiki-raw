## Background

Spec: https://drafts.css-houdini.org/css-properties-values-api-1/#at-property-rule

Lazily loading CSS with HTML and JS is common, and generally good for performance. However, lazy-loading CSS with a `@property` rule causes a full-dom restyle, which is not good for performance.

Example: you have an aside on your page that isn't important for the first load, and therefore can be loaded lazily. And you need an `@property` rule because you want to use a CSS Custom Property in, say, an animation.

```html
<p>...the main content, rendered first...</p>
<aside><?start name="aside-content">Loading...<?end></aside>

<!-- loaded later -->

<template for="aside-content">
	<style>
		@property --turn {
			syntax: "<angle>";
			initial-value: 0deg;
			inherits: true;
		}

		@keyframes rotate {
			to {
				--turn: 360deg;
			}
		}

		#spinny {
			transform-origin: left center;
			animation: rotate 2.5s cubic-bezier(1, 0, 0, 1) normal infinite;
			transform: rotate(var(--turn));
		}
	</style>
	<div id="spinny">I'll try spinning!</div>
</template>
```

Because the `@property` registration is global, the moment it gets loaded, every element in the document gets restyled. In a large document, that has huge performance implications.

The workaround is to register every property the application might use in the initial document or stylesheet. The downside is that every page carries the registrations of every lazily loaded feature, and those features can't ship their types with their own CSS.

## Proposal

A non-global `@property` rule registers a CSS Custom Property for the elements its parent selector matches (and their descendants), and nothing else changes about how CSS Custom Properties work.

```css
#spinny {
	@property --turn {
		syntax: "<angle>";
		initial-value: 0deg;
		inherits: true;
	}
}
```

If it is lazily loaded, the whole document does not need to restyle because of the late registration; only `#spinny` and its descendants do.

(While you _could_ say that this is "scoped", I'm deliberately avoiding the term "scoped" right now because there is a lot of historical context -- linked below -- of what "scoped" means; and it is much more than what this proposal is asking for. e.g. This is not the shadow-root-scoped registration discussed in https://github.com/w3c/css-houdini-drafts/issues/939.)

This proposal is asking for the property to largely behave exactly like it did before:

1. The CSS Custom Property inherits like it did before. It behaves the same through shadow DOM, slotted children, `::part()`, animations, transitions, `getComputedStyle()`, etc. The only difference is that it may find a nearer `@property` definition between it and the document root.
2. If a Custom Property has one syntax above the at-rule (e.g., `"<percentage>"`) and the non-global at-rule uses another (e.g., `"<color>"`), then everything under the non-global rule gets a `<color>`-enforced value, and everything above it gets a `<percentage>`-enforced value.
3. To force a value reset, follow the non-global at-rule with an `initial` declaration.

```css
#spinny {
	@property --turn {
		syntax: "<angle>";
		initial-value: 0deg;
		inherits: true;
	}
	/* force a reset to `0deg` */
	--turn: initial;
}
```

A rule from elsewhere in the application could write `#spinny { --turn: 10px }` with a `<length>` in mind, and the non-global `<angle>` registration makes it invalid at computed-value time. The spec already accepts this kind of conflict for global registration:

> If the outer page is using a custom property of the same name for different purposes, that is already a conflict that needs to be resolved, and the registration behavior does not make it worse.

## Questions

1. Can browsers optimize the current behavior without this proposal, and restyle only the elements that use the property instead of the whole document? That would render half of this proposal moot (but not the half about teams owning and shipping their own `@property` rules).
2. I wonder if _setting_ the value would require a DOM walk up the tree to check for a non-global `@property`, and if so, would that hurt performance? Could this be done efficiently, without a full walk?
3. Would this affect the timing around when custom property values are computed? (https://jakearchibald.com/2026/css-custom-property-compute-time/)

## @romainmenke — 2026-11-08

This isn't implemented anywhere yet but we have very recently [resolved to add `@property` support in `@private`](https://github.com/w3c/csswg-drafts/issues/14442).

This allows you to write:

```css
#spinny {
	@private {
		@property --turn {
			syntax: "<angle>";
			initial-value: 0deg;
			inherits: true;
		}
	}
}
```

This would be lexically scoped to the `#spinny` style rule.
Nothing outside the `#spinny` style rule would be able to use this registration.

So this isn't exactly what you are asking for, but might be worth looking into.

## @tabatkins — 2026-11-09

Well, it *does* cascade, it's just more restrictive than that.

`@private` creates a *lexically-scoped* variable - it's a normal custom property that gets defined on an element and inherits down the tree, but it *also* is only visible within its parent rule and any nested rules. Rules elsewhere in the stylesheet can't see it, and can't collide with its name either. (That is, a normal --turn custom property can exist on an element at the same time as a --turn private property; they're separate properties and don't interact.)

In general, I think this should be what you actually want with a scoped custom property. If the property isn't global, then you intend it for a private use and want to avoid clashing with other usages. If it's still a *normal* custom property, tho, then it *can* still clash accidentally, with one library expecting their --turn to work on an element that happens to also have *your* --turn defined on it. With private properties that can't happen - your --turn and their --turn are completely different properties that can coexist and neither of you needs to know the other exists.

(The downside is that, for now, `@keyframes` can't interact with private properties, since `@keyframes` rules are also global and can't be defined in a nested rule. There's plans to fix that, but one step at a time.)
