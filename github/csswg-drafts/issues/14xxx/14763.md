Tooltips are ubiquitous in terms of user experience, but are severely broken on the Web. `title` is discouraged because of accessibility issues, and tooltips produced through it are not stylable, which makes authors not want to use them. 

`::tooltip` was [proposed](https://github.com/w3c/csswg-drafts/issues/8930) to help with the styling issues and [accepted](https://github.com/w3c/csswg-drafts/issues/8930#issuecomment-1644333441) by the CSS WG, but hasn't moved forwards yet.

[Interest invokers](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API/Using_interest_invokers) are supposed to fix the a11y issues, but are clunky to use for the common case as they require a separate element and id references.

Compare this:

```html
<button interestfor="foo">Tooltip trigger</button>
<div popover="hint" id="foo">Tooltip content</div>
```

With this:

```html
<button title="Tooltip content">Tooltip trigger</button>
```

A simple tooltip should not require all this plumbing. Imagine the amount of extra DOM elements and markup for a whole toolbar! Interest invokers are great for making [complex things possible](https://lea.verou.me/blog/2025/user-effort/), but not the right tool for making [simple things easy](https://lea.verou.me/blog/2025/user-effort/). `title`, on the other hand, is perfect for this (and SVG's `<title>` model is even better, since as an element it is more i18nclusive), but authors are discouraged from using `title` due to its accessibility issues.

Both have [a11y issues that need to be sorted out](https://github.com/openui/open-ui/issues/1534), but it seems that interest invokers will be a little easier to figure out. So what if `::tooltip` can piggyback on them so that when we solve the issues for interest invokers, we have a way forwards for `title` as well?

## Proposal

Styling a `::tooltip` automatically creates an **implicit interest invoker** from the originating element. We can also define the tooltip itself as a hint popover with predefined UA styling that authors can override, à la `appearance: base` (what that would be is TBD). This also means proper tooltips can be created from CSS, via `content`.

## Open questions

- Is it feasible to make _any_ styling work for this, or do we need some kind of `appearance: base-tooltip`? The `::picker()` precedent points towards the latter, though from an HCI perspective, it's a double opt-in, which is unfortunate, but not the end of the world.
- Does that require widening the set of triggers that can hold interest invokers? If so, how, and is this a problem?
- Currently, the [recommended ARIA](https://developer.chrome.com/docs/modern-web-guidance/guides/ui-behaviors/interest-triggered-tooltips#accessibility) differs between toggletips (whose sole purpose is showing the tooltip) and regular triggers (who do something else when activated). Do we need to be able to specify both? If so, #14534 can help here. Presumably, the default would be the latter, which is safer.

Yup!
We could even define that _any_ `content` on `::tooltip` suppresses the native tooltip, so that other attributes can be used.

> > * Is it feasible to make _any_ styling work for this, or do we need some kind of `appearance: base-tooltip`?
> 
> I doubt you want to trigger this switch on just "any" styling of the pseudo element. This could be triggered with an HTML attribute also, like `<a title="cool link" bettertooltips>`.

A property to turn it on is fine (and I agree makes sense), but I would be _strongly_ opposed to requiring HTML to turn this on. There is no reason for the switch to not be in CSS, and it complicates a lot of use cases (now aggregation requires JS).

But I'm also thinking, **perhaps `content` can be the switch**. Instead of `content: attr(title)` living in the UA stylesheet and then requiring a separate property for the opt-in, `content` _becomes_ the opt-in, à la gencontent pseudos.

> > Does that require widening the set of triggers that can hold interest invokers? If so, how, and is this a problem?
> 
> At first, I'd advocate (strongly?) for only allowing this on the things that already support interest invokers (buttons and links), since those were chosen to avoid the a11y issues of putting this on non-focusable elements.

For regular HTML elements, yes. But this forces the question of what _pseudo-elements_ are valid interest invoker triggers.
E.g.
- Would `::part()` work? Would it depend on what type of element it encapsulates? And if so, isn't that an encapsulation leak?
- Same question for `::slotted()` though at least there there's no encapsulation leak to consider
- `::scroll-button()` and `::file-selector-button` should probably allow it?

If the answer to these is "yes", note that this would make `::tooltip` the _only_ way to attach an interest invoker to these. We may later want to explore how to make it possible to attach an actual element for the interest popover to them, if use cases emerge.
