Currently, `border-shape` does not affect either, I believe. The [only quote in the spec is about `shape-inside`](https://drafts.csswg.org/css-borders-4/#border-shape-layout-interaction):

> An author can use [border-shape](https://drafts.csswg.org/css-borders-4/#propdef-border-shape) in tandem with [shape-inside](https://drafts.csswg.org/css-shapes-2/#propdef-shape-inside) to create effects that both decorate the box and control its text flow.

This seems to me like a footgun. The common case is that you *do* want `border-shape` to affect these. Setting them to something else is the exception.

Can we define that the initial value of `shape-outside` is the computed value of `border-shape-outside` and the initial value of `shape-inside` is the computed value of `border-shape-inside` if these are set? (I know these longhands don't exist, but you get the idea 😁 )

Then, authors can still override them, but their initial value follows the principle of least surprise.

We could even be smarter than using the shape wholesale and fix the problems in #13506 by computing a suitable default shape automatically. But that’s harder.

## @tabatkins — 2026-07-10

I'm lightly against the shape-* properties acting meaningfully different for border-shape than they do for the existing borders+border-radius. The current ways we have of shaping the border do *not* automatically transfer to the shape-* properties. If you have a big floating border-radius circle, text lines both within and outside it will continue to treat it as square.

I think it would be reasonable to add a keyword to the shape-* directing it to take the shape from the border, though, once we solve the #14147 issues.

But not always! Sometimes (often?) you just need extra padding. 

So something like ’shape-inside: border-inset’ or some such is the way to go IMO.
