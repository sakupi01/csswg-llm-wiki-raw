**Problem**
Scroll positions, and now [pointer positions](https://drafts.csswg.org/pointer-animations-1/), can drive animation progress without script. Pointer-driven animations extend the Web Animations model with pointer progress timelines, derived from the concepts of Scroll-driven Animations. Because the UA owns these inputs, it can update compositor-friendly properties off the main thread. 

Other inputs have no such path. Device sensors, gamepads, eye or hand tracking, and values computed by on-device ML in a worker must all go through main-thread script (requestAnimationFrame → style → layout). Any main-thread work then adds directly to input-to-photon latency.

**Motivating case**
a robot face whose on-screen eyes follow a person’s gaze. Beyond roughly 100 ms, the eyes read as “not looking at me” rather than “slow”. The latency budget looks like this:

```
Camera capture         33 ms       (30 fps)
Gaze inference         10–50 ms    (WebNN/WebGPU, in a worker)
Event loop             0–16 ms
Style / layout         variable    ← main-thread bottleneck
Composite / scan-out   16–33 ms
```

Inference can be made faster on-device, and scan-out is fixed by hardware. The event loop and style stages come from the platform architecture. Animating only transform/opacity doesn’t help if the input value still has to pass through the main thread.

**Other use cases**
* Eye-gaze and head-tracking input for accessibility (gaze cursors, dwell indicators)
* UI that reacts to WebXR hand tracking
* Device-tilt and gamepad-driven effects

**Proposal**
Generalize the progress-timeline model of scroll-animations-1 and pointer-animations-1 to arbitrary input sources. An InputTimeline’s progress is a linear mapping of an input value onto 0–100%.
```javascript
// Main thread
const gazeX = new InputTimeline({ range: [-1, 1] });
pupil.animate(
  { transform: ['translateX(-20px)', 'translateX(20px)'] },
  { timeline: gazeX }
);
worker.postMessage({ input: gazeX.source }, [gazeX.source]); // transferable

// Worker: push each inference result
input.update(x); // x in [-1, 1]
```

**Key semantics**
* Non-monotonic progress, as with pointer timelines. Values outside range are clamped, and animation-range-center sets the rest position.
* Worker-to-compositor path. The source is transferable to a worker (similar to OffscreenCanvas), so values reach the compositor without a main-thread round trip. UA-owned sources such as device orientation or gamepad axes could be wired directly, the way scroll offsets are.
* No main-thread work for compositor-only effects. When the animated properties are compositor-friendly, updates should not require main-thread style or layout.
* Optional time-based smoothing to absorb sensor jitter.

**Relationship to existing work**
* [pointer-animations-1](https://drafts.csswg.org/pointer-animations-1/) defines PointerTimeline and animation-range-center, which sets the point of 50% progress to a specific point instead of the default center of the attachment range. This proposal applies the same model to non-pointer inputs.
* #2493 (Generalized Time Values) proposed an AnimationInput abstraction, with scroll and pointer inputs, for worklet animations. This proposal is narrower: a declarative value-to-progress mapping, with no author script on the compositor. 
[github](https://github.com/w3c/csswg-drafts/issues/2493)
* #7059: time-based smoothing (“lerp”) was suggested for scroll-driven animations but deferred to level 2. It matters even more for noisy sensor input. 
[github](https://github.com/w3c/csswg-drafts/issues/10574)

**Open questions**
* Should this be a new InputTimeline interface, or a pluggable source on AnimationTimeline?
* How should CSS reference script-defined input timelines (e.g., animation-timeline: --gaze-x)?
* One timeline per axis, as with scroll and pointer timelines, or a 2D timeline?
* When a source stalls, should the timeline hold its last value or become inactive?
* Privacy: UA-owned sensor sources should keep the permission requirements of the underlying API, and currentTime must not expose data the page couldn’t otherwise read.

## @ydaniv — 2026-10-31

Hey @anawhj, thanks for proposing.
I agree this is an area worth solving, but I'm still missing key features in your proposal, mainly:

1. How do you connect a timeline to a source?
2. How do you define an axis on such timeline/source for the progress to track?

I think once you defined those you can plug that progress as an input to any animation, and by that to an effect.
But before you solved these 2 questions we're still at the starting point.

Also note the [proposal of Custom Effects](#6861), might be relevant to what you're trying to achieve.
I also suspect you'll have to solve privacy and security constraints in some cases for some of the inputs you mentioned, but not necessarily.

Another small comment, regarding the `range` property you passed in your example to the timeline, you probably want to keep the timeline as `[0, 1]` range to be fully standard and reusable, and have the ranges apply on a property/effect basis.
