## Problem
css-color-4 specifies [gamut mapping](https://drafts.csswg.org/css-color-4/#css-gamut-mapping) and three different methods for doing so. Currently, no browsers have shipped gamut mapping. But if/when they do, feature detection through conventional means is likely to be limited or impossible.

## Suggestion
This seems like a good candidate for a css-conditional-5 [named feature](https://drafts.csswg.org/css-conditional-5/#support-definition-named-features) for the `@supports` at-rule, which would overtly expose the capability for gamut mapping. This could be one named feature (e.g., `gamut-mapping`) or one for each method (`ray-trace-gamut-mapping`), though I'll defer to others' judgment on whether that level of detail should be exposed to web developers.

## Motivation
For web developers, it would be helpful to be able to detect whether gamut mapping is in use (possibly by which method) and use workarounds if required.

For people like me who document the web platform, it would also be helpful to have a reliable method to determine when a browser supports gamut mapping, without resorting to manual, visual tests. This would aid data accuracy on MDN and caniuse (by way of [mdn/browser-compat-data](https://github.com/mdn/browser-compat-data)) and [gamut mapping's Baseline status](https://web-platform-dx.github.io/web-features-explorer/features/gamut-mapping/) (by way of [web-features](https://github.com/web-platform-dx/web-features/)).

I agree about evaluating implementations.

The [gamut mapping to canvas WPT](https://wpt.fyi/results/css/css-color?label=master&label=experimental&aligned&q=mapping) use a set of carefully selected colors and, for each, a calculated error threshold such that any of the three methods are **within** it, and the result of clipping is **well outside** it.

I could see some value in more finely-grained feature support but the **major win** is being able do detect whether it is **available or not**.
