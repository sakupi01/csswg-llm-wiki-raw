Related issues: #12317, #7523

In a function/mixin, the *arguments* establish new custom properties inside the body, unrelated to anything of the same name that might exist outside of the function/mixin. You can give this property a type, inline, with the syntax `--foo <color>: red`, which we're reusing for the "shorthand" version of `@property`: `@property --foo <color>: red;`.

This leaves us with a hole, tho, about local/private variables. They're just as separate from the outer page, and thus don't see any outside registrations, but don't have a way to provide an inline declaration like arguments do, either.

One proposal in #12317 is that we just allow `@property` inside these contexts, giving a registration for those private vars. With the shorthand, that's not too bad:

```css
@mixin --foo(--color <color>: red) {
	@private {
		@property --length <length>: 1em;
	}
	box-shadow: var(--color) var(--length);
}

@function --foo(--color <color>: red) {
	@property --length <length>: 1em;
	result: var(--color) var(--length);
}
```

----------

Another idea is to just copy the argument syntax more directly, and allow the type directly in the declaration, like:

```css
@mixin --foo(--color <color>: red) {
	@private {
		--length <length>: 1em;
	}
	box-shadow: var(--color) var(--length);
}

@function --foo(--color <color>: red) {
	--length <length>: 1em;
	result: var(--color) var(--length);
}
```

This is even shorter, and makes the local vars exactly as powerful and easy as the args. It would require some Syntax work to allow it in the parser, but I think I can make it work reasonably. (It would slightly expand the space of "selectors you can't write in nested rules because they look like a custom property", but not in any interesting way.)

--------

In either case, if you declare the type multiple times in the block, I think we'd just take the last, as normal for repeated `@property`.

---------

Also: what's the exact context this would be allowed in? I propose it's only valid in `@private` and the body of `@function`, both places where you're defining a lexically scoped property. This would be invalid in normal style rules, as those contexts are *using* a global custom property which is (often implicitly) defined at the global level instead.

---------

This also implies that the value you provide in the `@private`/`@function` block is in fact the *initial value*, as it's implicitly creating a registration, so later uses of the property can use `initial` to refer to it. This makes sense to me, any contrary thoughts?

## @tabatkins — 2026-09-04

@romainmenke 
> Makes sense, but can we then still get a guaranteed invalid value?

That comes for free if we use `@property`, as you'd just write `@property --foo <length>;` and that would give you the default initial value, which is the GIV. This is indeed another argument leaning toward just using `@property` for this, instead of shoving *even more* syntax into declarations that can conflict with nested rules.

@bramus 
At least in mixins, I don't think there's a strong argument for that - if you want to use the same property as the outside world, you can just *do so*, if you don't shadow it with an arg or private.

In `@function`, at least in this author's example I don't think they're *really* asking to match the outer world's `@property`, they just want *some* way to type a local var, and they were reaching for `@property` as the only way they could think of. With this thread's proposal, we'd just write their example as:

```css
@function contrast(--c <color>) {
	@property --cc <color>: contrast-color(var(--c));
	result: if(style(-cc: black): black; else white);
}
```

@sorvell 
That distinction was indeed exactly my fear originally, and why I started from and defended using `@result`. But switching to the new model of `@private` has some significant benefits as well, notably that it's now leaning on a more generic bit of useful functionality that people can start using across their stylesheets.

Basically, tho, you can pretend that the body of an `@function` *is* an `@private` rule; they have identical parsing restrictions limiting them to only containing custom properties (save for the magic `result` property). This concordance would continue here, as `@function` and `@private` bodies would both allow inline `@property`, which otherwise isn't allowed in style rules.

It *is* slightly unfortunate that you have to spell them a little differently, because `@function` *implies* the `@private` wrapper while `@mixin` doesn't, but you've gotta write extra stuff in `@mixin` one way or another to distinguish private properties from "normal" custom properties that get written out into the style rule. This is a spot where there are tradeoffs both ways; the WG decided on this direction for the conflict, and I think it's reasonable overall.

I’m interpreting their request the other way: they have an `@property`-registered there in their code (globally) to be `<color>`, yet the local property inside the `@function` does not get treated as such. Without any prior knowledge about how functions work, authors would expect that the local variable inside `@function` also computes to a `<color>`.

```css
@property --c {
	syntax: "<color>";
	inherits: true;
	initial-value: #123456; /* Some brand-specific color */
}

@function --bg() {
	--c: blue; /* Does not compute to a color */
	result: if(
		style(--c: #f00): hotpink;
		style(--c: #00f): hotpink;
		else: lime;
	);
}

html {
	--c: red; /* Computes to a color */
	background-color: --bg(); /* This is lime instead of hotpink */
}
```

While it is part of educating authors about how things work here to get them to understand why this happens — i.e. you _really_ don’t want outer registrations to clash with the inner workings of a function — I think it would be handy if folks could, inside the function, just say: _“inherit the definition from outside”_ when using a local `--c`.

```css
@property --c {
	syntax: "<color>";
	inherits: true;
	initial-value: #123456; /* Some brand-specific color */
}

@function --bg() {
        @property --c <inherit>: blue; /* 👈 This local --c now uses the same registration info as the outer --c … so this computes to a <color> now */
	result: if(
		style(--c: #f00): hotpink;
		style(--c: #00f): hotpink;
		else: lime;
	);
}

html {
	background-color: --bg(); /* This is hotpink, yay! */
}
```

(And yes, they probably could just type `@property --c <color>: blue; ` inside the function, but would not give them the `initial-value` or `inherits` aspects of the outer registration)

## @tabatkins — 2026-09-10

> I’m interpreting their request the other way: they have an `@property`-registered there in their code (globally) to be `<color>`, yet the local property inside the `@function` does not get treated as such. Without any prior knowledge about how functions work, authors would expect that the local variable inside `@function` also computes to a `<color>`.

I disagree. Variables defined in functions are generally new, scoped instances of the variable, shadowing whatever might exist in the outer context.  This happens *automatically* in Python, for example (you have to explicitly indicate when you're referring to a non-local, with `global` or `nonlocal` on the first assignment of that variable in the function). It is a little different in JS (you have to use var/let/const or else your assignment implicitly goes to the outer-scope variable), tho some bits, like function arguments, automatically define new args rather than assigning to non-locals.

Like, that certainly *could* be the author's expectation, but it's not a *universal* expectation, and common programming languages go multiple ways, so there's no obvious answer. This is something people will have to learn one way or another, and the fact that the function's body *cannot* assign to the outside-visible custom prop in any way leans it somewhat toward being an independent variable imo.

> (And yes, they probably could just type `@property --c <color>: blue; ` inside the function, but would not give them the `initial-value` or `inherits` aspects of the outer registration)

Luckily those two aren't relevant here: they're explicitly assigning the property, so the initial value doesn't matter; and there's no child elements here so the inheritance doesn't matter. ^_^

------

re:`using`, we repurposed that syntax for a bunch of things over time, but yeah, "automatically inherit this custom property from the calling context" was one of them.

I recommend that we wait and see how much desire there really is for this sort of "make my function locals use the same registration as my page's custom properties", vs how much people appreciate not having to think about whether a local name is already used. If we do end up wanting it, there's plenty of syntax space to handle it.
