Chromium currently has a gap in its scoped view-transition implementation: some otherwise eligible elements cannot render the view-transition pseudo-element tree because their layout restricts ordinary child boxes. My interpretation is that these restrictions should not prevent an eligible scope from hosting and styling its view-transition pseudo-elements.

These layout restrictions occur across several categories of elements. The following cases are relevant wherever the element meets the existing requirements for a transition scope:

| Category | Elements and cases |
|---|---|
| Images and embedded content | `<img>`, `<canvas>`, `<iframe>`, `<embed>`, `<object>` |
| Media | `<video>`, `<audio>` |
| Form controls | `<input>` across its rendered types, `<textarea>`, `<select>` in dropdown and listbox modes, `<button>` |
| SVG | SVG roots and `<foreignObject>` |
| MathML | `<math>` and eligible descendants, including `<mrow>`, `<mfrac>`, `<msqrt>`, `<mroot>`, `<mpadded>`, `<mspace>`, token elements (`<mi>`, `<mn>`, `<mo>`, `<mtext>`), script/limit elements such as `<msub>`, `<msubsup>`, `<mover>`, and table cells (`<mtd>`) |
| Specialized HTML layout | `<fieldset>`, `<table>` and eligible table parts, and legacy `<frameset>` |

These cases have different implementation constraints: some reject ordinary child boxes, some restrict the types of children they accept, and others use anonymous content wrappers.

## Expected behavior

The scope hosts the normal view-transition pseudo-element hierarchy. Authors can style and animate it using scope-qualified selectors, for example:

```css
#scope {
  view-transition-name: image;
}

#scope::view-transition-old(*) {
  animation: slide-out 1s both;
}

#scope::view-transition-new(*) {
  animation: slide-in 1s both;
}

@keyframes slide-out {
  to { transform: translateX(-100%); opacity: 0; }
}

@keyframes slide-in {
  from { transform: translateX(100%); opacity: 0; }
}
```

This should work when `#scope` is an eligible element from the categories above, not just an ordinary container.

I haven’t found a restriction in the [view-transition pseudo-element definitions](https://drafts.csswg.org/css-view-transitions-2/#view-transition-pseudos) that excludes these elements.

## Proposed clarification

Any element that meets the existing requirements for a transition scope can host the view-transition pseudo-element tree, regardless of restrictions on its ordinary layout children.

I’d like feedback on whether this interpretation matches the intended model and whether any of the listed cases need special consideration.
