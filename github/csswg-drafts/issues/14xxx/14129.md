Currently the spec for values allowed as [`<event-trigger-event>`](https://drafts.csswg.org/animation-triggers-1/#typedef-event-trigger-event) is practically placeholder:

> [`<event-trigger-event>`](https://drafts.csswg.org/animation-triggers-1/#typedef-event-trigger-event) = activate | interest | click | touch | dblclick | keypress(`<string>`) |  ...

We should formalize the values for this type.

## Options to consider:

1. Start with all events? Or start with a limited list and expand as we go?
2. Some events could benefit from a functional form with modifier args, as already implied in the spec, such as `key` for keyboard , and `button` for mouse/pointer, etc. Should we allow functional? Allow both functional and keyword? Only functional?
3. If we do allow functional form, which args for each event?
4. It's already suggested to add `activate` and `interest` (which IMO is great), but do we need `activatein`/`activateout`/`interest`/`loseinterest`? Or do we leave these to be automatically decided based on usage, i.e. `event-trigger: --t interest / interest` automatically becomes `interest / loseinterest`. Or perhaps `interest(in|out)`?

## Proposal

1. Start with a limited list and expand. Probably after there's a first prototype deployed in the wild. I think starting with keyboard/mouse/pointer/`interest`/`activate` as suggested is a good start.
2. I think both are good (if it's not a problem).
3. I guess starting with the suggested `key` for keyboard events is fine as a starting point. Probably as a space delimited list? And if so, probably needs a special case for `" "` to be handled as `Space`.
4. I think starting with just `interest`/`loseintereset`, and `activate` being decided automatically based on usage should be a good start.

## @flackr — 2026-08-05

My rough understanding is that click is already meant to be synonymous with activation. Per [the MDN page](https://developer.mozilla.org/en-US/docs/Web/API/Element/click_event):

> The event is a device-independent event — meaning it can be activated by touch, keyboard, mouse, and any other mechanism provided by assistive technology.

I'd prefer we use this rather than have the activate term here which doesn't directly correspond to any event. I.e. in general, my hope is that for every event trigger there is a simple corresponding trigger a developer could listen for with an event listener in JS. This should make it easy for the triggered css effect and corresponding functional changes to occur for the same trigger conditions.

If the activate we're defining here means something different than click, then we should add a dom event. There was DOMActivate, but the spec for https://w3c.github.io/uievents/#event-type-DOMActivate advocates for authors to use click as an accessible alternative.

If your trigger condition doesn't match the event, then there are risks that we'll activate effects when the corresponding action is not initiated.

## @SebastianZ — 2026-08-05

I'm some leaning towards keeping event names synchronized with them from DOM, for consistency as well as huge flexibility. E.g. you not only get `keypress` but also `keyup` and `keydown`. Not only could we have `click` but potentially also all the `mouse*` and `pointer*` events. We might potentially react to _any_ DOM event, maybe even custom ones.
I also imagine that to make it possible for implementations to re-use the code paths they have.

BUT this also brings a bunch of issues:

* If we stricly stick to the DOM names, we carry over any naming mistakes made for those DOM events.
* Mapping them is complicated, especially in regard of parameters.
* Keywords in JS and CSS don't always match and some mechanics don't line up (thinking of `interest` / `hover` vs. `mouseover` / `mousemove`)

-----

If we can't agree on aligning both, I suggest to go with CSS-specific keywords / functions and possibly additionally introduce a `dom-event()` function that covers the above.

Sebastian
