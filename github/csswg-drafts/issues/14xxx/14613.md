# [Read the full explainer](https://github.com/MicrosoftEdge/MSEdgeExplainers/blob/main/highlight-v2/explainer.md)

Many Web experiences apply visual effects to text. AI chat interfaces and online presentation tools have made text entry and exit effects especially prominent, while read-along experiences and editing tools use changing highlights to convey playback or analysis state.

Existing Web primitives can be inefficient for text-level animation effects because they require backing elements. For a per-word animation with a lot of text, hundreds of extra elements might be created for no reason other than to support such an effect.

One suggestion I got in response to [previous](https://github.com/w3c/csswg-drafts/issues/13689) [explorations](https://github.com/w3c/csswg-drafts/issues/3208#issuecomment-5087558171) was to investigate the Custom Highlight API, which already lets authors identify arbitrary text ranges without changing the document structure. However, highlight styling has limitations that make it an incomplete replacement for element-level effects. This issue proposes three additions to close those gaps.

## CSS Animations and Transitions

We propose allowing the CSS animation and transition properties to apply to custom highlight pseudo-elements. For example:

```css
@keyframes emphasize {
  from { background-color: transparent; }
  to { background-color: gold; }
}
::highlight(new-annotation) {
  color: blue;
  transition: color 150ms;
  animation: emphasize 300ms ease-out;
}
```

Effects are per (Highlight registry entry, range, originating element) tuple. A `Highlight` may be registered under different names that match different `::highlight()` rules and therefore produce different effects. Each range may have its own per-range style, as described in the next section. Each originating element can also resolve different property values, which may influence transition endpoints.

Adding a range to or removing it from a registered `Highlight` can transition between the computed highlight style and a not-highlighted endpoint. Animation and transition events on `Highlight` and integrating highlight effects with the Web Animations API are also included in the proposal.

Moving a range boundary can create new effect targets if an element boundary is crossed, but it does not initiate new effects. This is consistent with the behavior that occurs when adding a new text node to an element.

## Per-Range Styling

A staggered text fade requires each successive word to start its animation slightly later than the preceding word. This is technically achievable with custom highlights today, but in ways that are poorly suited to the scenario: either driving the progression through a JavaScript loop or having a distinct `::highlight()` rule for each animation offset.

We propose a new `Highlight.getRangeStyle()` method, which returns a mutable declaration block for a range's membership in a `Highlight`. This is analogous to an element's inline style, while allowing the same range to have different styles in different `Highlight` objects.

```js
const ranges = splitElementTextIntoRanges(someElement);
const highlight = new Highlight(...ranges);
const staggerInterval = 6 /* milliseconds */;
for (const [index, range] of ranges.entries()) {
  highlight.getRangeStyle(range).animationDelay = `${index * staggerInterval}ms`;
}
```

## Opacity

Entry and exit effects commonly use the `opacity` property to fade content smoothly. However, `opacity` is not among the properties supported by highlights.

Adding it is not simply a matter of supporting one more property. Non-default opacity on an element creates a stacking context, which affects paint order. [Highlight painting](https://drafts.csswg.org/css-pseudo-4/#highlight-painting) does not paint overlapping highlights one on top of another. Instead, all highlight backgrounds are painted, followed by shadows, underlines, overlines, text in the winning color, and finally line-throughs.

We propose a winning-value model: where highlights overlap, the highest active highlight that specifies opacity supplies the value for the entire stack. The highlighted region is painted using the existing highlight paint order, after which that value is applied once to its combined ink, including contributions from all active highlights, the highlighted foreground, and associated effects from the originating element. Opacity on the originating element or its ancestors composes separately and continues to apply to the result.

## @flackr — 2026-10-30

> For color specifically, if there’s overlapping higlights, we pick a single color

The painted color could be the result of compositing the colors in highlight order on top of the underlying color. These colors could each by partially translucent in order to apply subtle effects, e.g. black + highlight color rgba(255, 0, 0, 0.5) + highlight color rgba(0, 0, 255, 0.5) would result in rgb(64, 0, 127). This would allow them to not suddenly override colors mixing over time. The main thing you can't do with this is make it more transparent, which you could do with the opacity property.

I wonder if instead of per range styles you could think of the effect as a sort of animated gradient over the entire range instead. ## @kbabbitt — 2026-11-03

Thanks for all the engagement on this! I've updated the explainer based on feedback I got at TPAC:

* Capture the conceptual distinction between "different highlights" and "different ranges within a highlight."
* Delete the data-driven range styling example. Editing highlights from different users are semantically different highlights and thus not a fitting application for varying styles per-range within a given highlight.
* Add range-index() as an alternative to getRangeStyle().
* Add auto value for opacity to distinguish non-specified opacity from explicit opacity:1.
