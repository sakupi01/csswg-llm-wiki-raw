Currently there is a footgun where if authors need to remember to use `:open` if they want to set a different `display` value on a customizable select, otherwise the select is always open, just laid out badly ([testcase](https://codepen.io/leaverou/pen/RNojvPZ))

Are there any use cases for having a `display` value other than `none` on pickers of closed selects? Now that we can animate from `display: none`, I can't think of any.

If not, I propose adding this to the UA stylesheet:

```css
select:not(:open)::picker(select) {
	display: none !important;
}
```

This does not appear to negatively affect listbox selects, since they have no picker.

## @keithamus — 2026-06-17

This is also true for popovers, if you want a flex popover for example the author needs to write `[popover]:not(:popover-open) { display: flex }`.

If we fix one, all the reasons apply for fixing the other. If there are legitimate use cases for displaying a `[popover]` as block, I'd suggest those same legitimate use cases also exist for `::picker(select)`.

> 
> If we fix one, all the reasons apply for fixing the other. If there are legitimate use cases for displaying a `[popover]` as block, I'd suggest those same legitimate use cases also exist for `::picker(select)`.

I'm less sure about that one (and also, changing that is likely to have web compat implications). There are many use cases where the same component switches from a regular static layout to popover mode depending on screen real estate. Many such use cases can be observed in https://vitepress.dev/guide/what-is-vitepress by resizing the viewport:
- Sidebar becomes a drawer in smaller viewports
- "On this page" becomes a popup menu in smaller viewports
- Top-level navigation becomes an overlay in smaller viewports
- Version picker is a popup menu on large viewports, but a disclosure widget on smaller ones (since it becomes part of the navigation overlay)

This requires being able to override `display`. Are there similar use cases for `select`?
