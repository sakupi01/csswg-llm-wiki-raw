See: https://drafts.csswg.org/css-color-4/#lch-to-lab

> If H is missing, a = b = 0

I didn't implement this step and it seems that neither did [colorjs](https://apps.colorjs.io/convert/?color=lch(20%2020%20none)&precision=4), nor chrome

This was called out by @weinig in https://github.com/web-platform-tests/interop/issues/1494

-----

This seems inconsistent with `hsl` to `srgb` conversion where the result is a chromatic color.

```
rgb(from hsl(none 50 50) r g b)
```

becomes:

```
color(srgb 0.75 0.25 0.25)
```

---

It also means that the value doesn't round trip as nicely if you convert it back and forth between color spaces.

----

This also makes some interpolation impossible.

For example:

```
color-mix(in oklch, lch(80 30 270), lch(30 30 none))
```

Here an author might reasonably expect to have saturation that is consistent with `30` in lch.

e.g. `oklch(0.61909628 0.08689075 264.1562336)`

While instead it will be half that: `oklch(0.61410188 0.04104694 264.1562336)`

-----

## @romainmenke — 2026-09-30

Or maybe make this only apply when displaying a color, same as gamut mapping?
In principle it makes sense that a color with a `none` hue displays as achromatic instead of whatever color happens to be `0deg`.

Making this a function of display means that interpolation, relative color, ... all still work as expected and preserve `c`.

On my end the `none` hue was already converted to `0` at this point as my implementation didn't record the missing hue beforehand.

So `cos(0)` and `sin(0)`.

----

Aside: these cases with `none` and conversions from polar to rectangular and back always have a sharp edge somewhere. Really tricky to pick the right trade-offs :)

## @svgeesus — 2026-09-30

Okay so `oklch(60% 0.2 none)` [becomes `oklab(60% 0.2 0)`](https://apps.colorjs.io/convert/?color=oklch(60%25%200.2%20none)&precision=4) with all the chroma shoved into the `a` axis, giving a deep magenta.

Which then round-trips to `oklch(60% 0.2 0)`, preserving the chroma value it had before.
