# [css-scroll-anchoring] Declarative anchoring to a scroll container's start or end edge

## Summary

Authors need a declarative way to keep a scroll container attached to either its logical block-start or block-end edge while its contents change, provided the user was already within a specified distance of that edge.

This is common in chat logs, terminals, consoles, live feeds, timelines, and other streaming interfaces. JavaScript can approximate the behavior, but it cannot reliably perform the necessary measurement and adjustment between layout and paint. Under streaming updates, the workaround can expose intermediate scroll offsets, visibly jump, or fight user scrolling.

This issue proposes an opt-in, container-scoped scroll anchoring policy with:

- a logical edge: `block-start` or `block-end`; and
- a threshold: the maximum distance from that edge at which a subsequent layout change reattaches the scroll container to it.

The names and grammar below are tentative. The primary proposal is the behavior.

## Use cases

### Follow the end of a chat or terminal

When a user is at, or near, the end of a chat log, streamed text and appended messages should keep the latest content visible. If the user scrolls farther away to read history, new content should not pull the viewport back.

```css
.chat-log {
  overflow-y: auto;
  overflow-anchor-edge: block-end 120px;
}
```

### Follow the start of a reverse chronological feed

Some feeds place the newest material at the logical start. When the user is near that edge, inserted or expanding content should keep that edge visible. If the user has moved farther into the feed, their reading position should remain undisturbed.

```css
.live-feed {
  overflow-y: auto;
  overflow-anchor-edge: block-start 80px;
}
```

### Streaming content that changes size repeatedly

An assistant response, build log entry, caption, or status item may grow several times per second. The scroll adjustment needs to use the final layout for each rendered frame, without painting an intermediate offset.

## The platform gap

A typical JavaScript implementation does approximately this:

1. Read `scrollHeight`, `clientHeight`, and `scrollTop`.
2. Decide whether the viewport is close enough to the desired edge.
3. Mutate the DOM.
4. Wait for layout.
5. Read the new dimensions.
6. Set `scrollTop`.

There is no author-facing hook that runs after the relevant layout has stabilized but before that layout is painted. Framework updates may also span multiple DOM mutations or commits. Streaming text, fonts, images, nested layout changes, and virtualization make the measured scroll range provisional.

Consequently, script implementations can:

- paint one frame at the old offset before correcting it;
- briefly move in both directions as intermediate layouts are produced;
- force synchronous layout through measurement;
- generate scroll events that are difficult to distinguish from user input;
- compete with native scroll anchoring or smooth scrolling; and
- lose the anchored state during rapid updates.

Scroll anchoring already operates at the layout stage where the user agent knows both the previous and new scrollable overflow. This behavior therefore seems to belong in [CSS Scroll Anchoring](https://drafts.csswg.org/css-scroll-anchoring-1/), rather than in an author script or scroll snap.

## Tentative syntax

One possible property is:

```css
overflow-anchor-edge: none | [ block-start | block-end ] <length-percentage>?;
```

Tentative definition:

| Field | Value |
| --- | --- |
| Name | `overflow-anchor-edge` |
| Value | `none \| [ block-start \| block-end ] <length-percentage>?` |
| Initial | `none` |
| Applies to | Scroll containers |
| Inherited | No |
| Percentages | Relative to the scrollport size in the block axis |
| Animation type | Discrete |

Examples:

```css
/* Reattach to the exact end when the old position was within 120px. */
.chat-log {
  overflow-anchor-edge: block-end 120px;
}

/* Reattach to the exact start when the old position was within 10%. */
.reverse-feed {
  overflow-anchor-edge: block-start 10%;
}
```

An omitted threshold could mean zero, or it could mean a user-agent selected `auto` threshold. It may be clearer to require an explicit threshold in the first version.

Another possible design uses separate longhands:

```css
overflow-anchor-edge: none | block-start | block-end;
overflow-anchor-threshold: auto | <length-percentage>;
```

A third option is two properties such as `overflow-anchor-start` and `overflow-anchor-end`. A single edge selector avoids a conflict when both edges qualify and makes it explicit that a container follows at most one edge at a time.

This probably should not be added as a length value to the existing `overflow-anchor` property. `overflow-anchor` currently controls whether an element and its descendants participate in anchor-node selection, while this proposal defines policy on the scroll container itself.

## Proposed behavior

For a scroll container with this feature enabled, the user agent maintains the configured logical edge as a synthetic anchor candidate.

At a layout opportunity that changes the size or position of the scrollable overflow:

1. Before applying the layout change, determine the scroll container's distance from the configured logical edge in the block axis.
2. If the distance is less than or equal to the computed threshold, mark the synthetic edge anchor as active for that layout opportunity.
3. Complete layout and determine the new scrollable overflow.
4. If the synthetic edge anchor is active, adjust the scroll offset so the configured edge of the scrolling area coincides with the corresponding edge of the scrollport.
5. Apply the adjustment before painting the resulting layout.
6. If the pre-layout distance exceeded the threshold, do not perform this edge adjustment. Normal scroll anchoring may still apply according to its existing rules.

In pseudocode:

```text
old_distance = distance_from_configured_logical_edge(scroller)
should_attach = old_distance <= threshold

perform_layout()

if should_attach:
    scroll_to_configured_logical_edge(scroller)
```

The threshold is evaluated against the position before the relevant content or layout change. It is not evaluated after the scrollable overflow has already changed.

The resulting adjustment is instant unless existing CSS scrolling rules determine otherwise. Whether `scroll-behavior: smooth` should affect layout-driven anchoring adjustments is an open question; existing scroll anchoring adjustments are not normally exposed as animated author scrolls.

## User scrolling and reattachment

The distance threshold provides the basic user interaction rule:

- A user-initiated scroll that moves beyond the threshold prevents subsequent layout changes from reattaching to the edge.
- Scrolling back within the threshold makes the next relevant layout change eligible to reattach.
- Programmatic scrolling within the threshold should likewise make the next relevant layout change eligible, unless existing scroll anchoring suppression rules say otherwise.
- A layout-driven adjustment produced by this property must not itself be treated as user intent to leave the anchored state.

This design does not require a permanently stored `stuck` boolean. Eligibility can be derived from the pre-layout distance at every adjustment opportunity. Implementations might still keep equivalent internal state as an optimization.

## Logical directions

`block-start` and `block-end` refer to the scroll container's own writing mode. They must not be aliases for physical `top` and `bottom`.

Logical edges allow the same declaration to work in horizontal and vertical writing modes. Restricting the initial proposal to the block axis also matches the primary streaming-content use cases. Inline start and end anchoring could be considered separately if there is sufficient demand.

Reverse flex and grid flows need explicit treatment. The selected edge should be a logical edge of the scrolling area and scrollport, independent of DOM order. Tests should cover `flex-direction: column-reverse`, vertical writing modes, and RTL combinations.

## Relationship to existing scroll anchoring

This feature would be an opt-in specialization of scroll anchoring:

- It reacts to layout changes that affect scrollable overflow.
- It adjusts the scroll offset before paint.
- It uses a synthetic scroll-container edge instead of selecting a descendant anchor node.
- When active for a layout opportunity, the synthetic edge anchor should take precedence over ordinary anchor-node selection for that scroll container.
- When inactive because the distance exceeds the threshold, existing anchor-node selection can operate normally.
- Existing suppression windows and suppression triggers should apply unless the Working Group identifies a reason for different behavior.

The interaction with `overflow-anchor: none` needs a decision. Plausible options are:

1. `overflow-anchor: none` disables all anchoring, including this edge policy.
2. The new property is independent because it is an explicit container opt-in, while `overflow-anchor` controls descendant candidate selection.

The second option may better reflect author intent, but it would need careful naming and specification language.

## Relationship to scroll snap

This proposal reacts to content and layout changes. Scroll snap primarily selects a resting position for scrolling operations. They solve different triggers.

The existing Scroll Anchoring specification limits anchoring adjustments when a scroll container is snapped. The same precedence rule could apply: an edge-anchor adjustment must not move the container to a position that re-snapping would disallow. The exact interaction should reuse existing scroll anchoring and scroll snap rules rather than introduce an independent priority system.

## What counts as a relevant change?

The simplest predictable rule is any completed layout that changes the scrollable overflow size or the configured edge's position, including changes caused by:

- inserted or removed DOM content;
- streamed text updates;
- font loading;
- image or embedded-content intrinsic size changes;
- generated content;
- container resizing; and
- style changes that affect layout.

Restricting the trigger to literal DOM insertion would miss common cases in which an existing streaming message grows or an asynchronously loaded resource changes size.

The adjustment should use the final layout represented by the frame being painted. If additional mutations invalidate that layout before presentation, the stale adjustment should not be exposed as an intermediate frame.

## Accessibility and user control

Automatic movement must not override a user's attempt to inspect earlier or later content. Moving beyond the threshold disables the edge adjustment naturally.

The Working Group should also decide whether anchoring must be suppressed when:

- keyboard focus is inside the scroll container but away from the configured edge;
- a selection is active inside the container;
- find-in-page has selected a match;
- assistive technology has established a reading position; or
- reduced-motion preferences are active and an implementation would otherwise animate the adjustment.

Existing scroll anchoring priority candidates and suppression behavior may already cover part of this, but an explicit edge policy could otherwise override them.

## Initial positioning

This proposal governs adjustments caused by layout changes. It does not necessarily define where a newly created scroll container initially starts.

For a chat log rendered with existing history, authors may also want initial attachment to `block-end`. Possible approaches include:

- define initial layout as an eligible adjustment opportunity;
- add a separate keyword controlling initial attachment; or
- leave initial positioning to script and keep this proposal focused on subsequent layout changes.

This should be decided explicitly because requiring one initial scripted scroll would preserve a common source of timing bugs.

## Implementation experience

We implemented the proposed block-end behavior in a small retained-mode CSS renderer as a utility equivalent to:

```css
overflow-anchor-edge: block-end 120px;
```

The implementation records the old distance from the block end, performs layout, computes the new scrollable overflow, and updates the retained scroll offset before painting. Doing the adjustment during layout eliminated the need for application-level scroll listeners and post-render `scrollTop` writes.

Streaming content exposed an additional requirement: a frame based on stale content layout must not be presented after a newer layout mutation. Filtering stale layout frames removed the remaining small backward jumps while allowing user scroll offset changes to remain immediate. This supports treating the feature as part of the rendering and scroll anchoring pipeline rather than as a DOM library behavior.

This is implementation experience from a non-browser renderer, not evidence of multi-browser implementability. A browser prototype and Web Platform Tests would still be needed.

## Suggested tests

Tests should cover both `block-start` and `block-end` with:

1. Content appended at the configured edge while exactly at the edge.
2. Content inserted at the opposite edge while exactly at the configured edge.
3. Existing content growing through repeated text changes.
4. A position inside the threshold.
5. A position one CSS pixel beyond the threshold.
6. User scrolling away and back.
7. Programmatic scrolling away and back.
8. Content shrinking as well as growing.
9. Scroll container resizing.
10. Late font and image sizing.
11. Nested scroll containers.
12. `overflow-anchor: none` on the container and descendants.
13. Scroll snap interaction.
14. `scroll-behavior: smooth` interaction.
15. Horizontal and vertical writing modes.
16. RTL and reversed flex flows.
17. Focus, selection, and find-in-page priority candidates.
18. Several mutations occurring before a single rendered frame.

## Alternatives considered

### JavaScript scroll listeners and observers

These lack a reliable after-layout-before-paint hook and can force layout, expose intermediate offsets, or conflict with user-generated scrolling.

### An end-marker element using existing `overflow-anchor`

An explicit marker can sometimes produce end-following behavior, but it depends on anchor selection heuristics, marker geometry, prior scrolling, and DOM structure. It does not directly express an author-selected distance threshold or start/end container policy.

### Scroll snap

Scroll snap is centered on the resting positions of scrolling operations. This proposal reacts to layout-driven changes in scrollable overflow, which is the trigger already handled by scroll anchoring.

### Reversed layout

Authors sometimes reverse DOM or flex order so the desired edge maps to the scroll origin. This changes ordering and accessibility semantics, complicates virtualization, and does not address all streaming-growth cases.

## Open questions

1. Does CSS Scroll Anchoring own this behavior, or should it live in CSS Overflow?
2. What should the property be called?
3. Should one property select both edge and threshold, or should they be separate longhands?
4. Should the first version accept percentages, or only lengths?
5. Should an omitted threshold mean zero or `auto`?
6. Should initial layout attach to the configured edge?
7. Should `overflow-anchor: none` disable an explicitly configured edge anchor?
8. Which existing suppression triggers and priority candidates apply?
9. How should focus, selection, find-in-page, and assistive-technology reading positions suppress the behavior?
10. Does `scroll-behavior` affect the adjustment?
11. Should scroll events be fired for these adjustments, consistent with existing scroll anchoring?
12. How should reversed layout modes define the logical scrolling-area edges?
13. Should inline-axis edges be included now or deferred?
14. Does this belong in Scroll Anchoring Level 1 or a future level?
