## Context

The spec currently defines 2 types of triggers:

> [timeline triggers](https://drafts.csswg.org/animation-triggers-1/#timeline-trigger), managed by the [timeline-trigger](https://drafts.csswg.org/animation-triggers-1/#propdef-timeline-trigger) properties, which allow animations to be triggered by entering or leaving certain timeline ranges. (Usually, [view progress timelines](https://drafts.csswg.org/scroll-animations-1/#view-progress-timelines), so an animation can be started when an element comes on-screen.)
>
> [event triggers](https://drafts.csswg.org/animation-triggers-1/#event-trigger), managed by the [event-trigger](https://drafts.csswg.org/animation-triggers-1/#propdef-event-trigger) properties, which allow animations to be triggered by certain user-interaction events, such as clicking an element or pressing certain keys.

We also resolved in [13710](https://github.com/w3c/csswg-drafts/issues/13710#issuecomment-4128044742) to:

> Allow event triggers with the same name to combine into a single named trigger.

And we resolved in [13643](https://github.com/w3c/csswg-drafts/issues/13643#issuecomment-4613983278) that:

> play, play-f, play-b do not auto-rewind at the end; we add play-always which does; we remove play-once since that's now 'play' behavior.

So essentially it follows that:

1. Multiple event trigger declarations with the same name bind to a single state source using that name in same given scope
2. The state of triggered animation is controlled by the current state of the animation (whether paused/finished/playing/etc). The specified trigger only controls the action to be used when trigger activates/deactivates.

## Problem

Timeline triggers are still exempt from the "merging" behavior of names, so a timeline trigger declared with same name as an event trigger will still clash.

## Proposed solution

Make timeline triggers work the same with same name declarations behavior of merging to a single source, so that both event and timeline triggers, with the same name, will merge to the same hoisted shared state.

So that entering/exiting an active range of a timeline trigger will just propagate activation/deactivation state changes to the shared state. And depending on the action and the animation's state it will behave accordingly. Note that this is no different from the current behavior of event triggers that may emit activation to an already activated trigger.

The state of the timeline ranges on the trigger doesn't necessarily need to match the state of the trigger they're associated with. They just need to emit changes.
