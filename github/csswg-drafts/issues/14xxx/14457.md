[CSS Values §6.1.2.1](https://drafts.csswg.org/css-values-4/#viewport-variants) says that the large and small viewport-percentage units are fixed unless the viewport itself is resized.

Consider a mobile browser that changes the set of top or bottom user agent (UA) interfaces while a document remains loaded. Two representative scenarios are:

**Scenario 1: Adding or removing an interface**

The UA adds a persistent media, reader, status, or feature-control bar. The interface occupies space previously allocated to the document, so the UA reduces the web-content area and relays out the document. The reverse happens when the interface is removed.

**Scenario 2: Replacing one interface configuration with another**

In the normal browsing state, the UA displays multiple non-overlay bars with a combined height of (H_1).

When the user enters another browser mode - for example, Find in Page - the UA hides those bars and replaces them with a single non-overlay bar of height (H_2), where (H_2 < H_1).

The web-content area consequently grows by (H_1 - H_2), and the document is laid out into the newly available space. When the user exits the mode, the original set of bars returns and the web-content area becomes smaller again.

In both scenarios:

- the document remains loaded;
- the physical display and outer browser window do not change;
- the relevant UA-interface configuration remains in effect until the feature or mode is exited;
- the interfaces occupy space rather than overlaying the document; and
- this is not ordinary scroll-driven expansion, retraction, or translation of an existing toolbar.

The specification says that an interface change may:
- (A) change all viewport-percentage sizes and the initial containing block simultaneously;
- (B) contribute to the difference between the large and small viewport sizes; or
overlay the content without affecting viewport-percentage sizes.

It also says that sufficiently steady-state interface changes, for which relaying out the document into the adjusted space is beneficial, must be categorized as (A).

**Questions:**
1. Does a change in the space allocated to web content in either scenario constitute resizing “the viewport itself,” even though the physical display and outer application window have not changed?
2. Does a UA-interface configuration that remains active until the user exits the corresponding browser mode qualify as a “sufficiently steady state” change that must be categorized as (A), or may a conforming UA categorize it as (B)?
3. In the replacement scenario, should categorization be based on the resulting overall UA-interface configuration and web-content area, rather than treating the removal and addition of the individual bars independently?
4. If the change is category (A), should the large, small, and dynamic viewport sizes - and therefore lvh, svh, dvh, and vh - all be recalculated by the change in available space?
5. Is this behavior expected to be symmetrical? In other words, should the viewport units increase when a shorter interface configuration replaces a taller one, and decrease again when the taller configuration returns?
6. Is it conforming for such a steady-state interface reconfiguration to update only the small or dynamic viewport size while leaving the large viewport size unchanged?
