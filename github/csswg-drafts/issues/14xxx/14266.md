Relatives URLs in CSS are defined to be resolved based on the stylesheet's URL.
However, this is not very useful/obvious for navigation locations (`@location`, `url-pattern()`), as those refer to the changes in document's URL and not to specific resources.

Exposing the document URL as is to 3rd party contexts is likely a no-go, but perhaps it's OK when the stylesheet is origin-clean (same-origin or CORS).

Note that allowing matches based on navigation URL is not the same as exposing it, as the author has to "guess" URL patterns and match them during navigations (which CSS cannot initiate).

See https://drafts.csswg.org/css-navigation-1/#issue-d82d9a59

## @noamr — 2026-08-10

Cross-posting from discussion with @emilio and @zcorpan at https://github.com/mozilla/standards-positions/issues/1440:

Thinking to use the stylesheet's referrer as a base URL rather than the document's origin.
By default it would be either the document's URL or the document's origin, and this can change based on the `referrerpolicy` attribute on the `link` element, or the `referrer-policy` modifier when importing.

Note that this still exposed new information to theh cross-origin stylesheet, but as mentioned before the stylesheet can only access this information by guessing all the possible locations and hoping that the user navigates to them, which doesn't differ from styling with on attribute selectors.

## @noamr — 2026-08-25

Having discussed this with our internal security team, the problem is actually not with base URL itself but with the fact that URL patterns can sniff the arbitrary parts of the document URL with prefixes/RegEx, exfiltrating things like tokens.

Referrer-policy with `unsafe-url` can probably mitigate this, but might make it so that people overuse that option for CSS, which perhaps doesn't seem like a good trade-off.

Alternatives:
1. Use a subset of URL patterns without prefixes/suffixes/RegEx, e.g. only full parts of the path/query.
2. Add an explicit opt-in for `<link>` and `<style>` to allow document URLs in routes (or in other places?). It can be an "allow"-style boolean or something that can also pass an explicit base URL for routes
3. Control the URLPatterns from JS, like in custom highlights, e.g. `CSS.locations.add("--movie", "/movie/:id")`
4. Make the case for using referrer policy for this

From an initial look, (1) seems like an overkill and (3) seems like a step backwards in terms of being declarative.
Perhaps (2) is worth pursuing?

## @noamr — 2026-10-14

@fantasai @LeaVerou @bramus where I struggle with what we got to is as follows.

Let's say we use one of these strawman options or something similar:
```html
<script type=locationmap src="locations.json"></script>

<!-- locations.json: -->
{ "home" : "/" }
```

or

```html
<link rel=locationmap href="locations.css">

<!-- locations.css: -->
@location --home { pathname: "/" }
```

we would still need CSSOM access to this *anyway*. So why not start with that?

```html
<script src="locations.js"></script>

<!-- locations.js: -->
CSS.locations.add("--home", new URLPatern("/"));
```

and we can implement one of the other options if it adds value on top of that in practice?

Note that having script doesn't mean that it needs to be copy-pasted... The same `js` file can be referenced from all documents.
