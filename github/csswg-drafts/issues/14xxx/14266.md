Relatives URLs in CSS are defined to be resolved based on the stylesheet's URL.
However, this is not very useful/obvious for navigation locations (`@location`, `url-pattern()`), as those refer to the changes in document's URL and not to specific resources.

Exposing the document URL as is to 3rd party contexts is likely a no-go, but perhaps it's OK when the stylesheet is origin-clean (same-origin or CORS).

Note that allowing matches based on navigation URL is not the same as exposing it, as the author has to "guess" URL patterns and match them during navigations (which CSS cannot initiate).

See https://drafts.csswg.org/css-navigation-1/#issue-d82d9a59

Cross-posting from discussion with @emilio and @zcorpan at https://github.com/mozilla/standards-positions/issues/1440:

Thinking to use the stylesheet's referrer as a base URL rather than the document's origin.
By default it would be either the document's URL or the document's origin, and this can change based on the `referrerpolicy` attribute on the `link` element, or the `referrer-policy` modifier when importing.

Note that this still exposed new information to theh cross-origin stylesheet, but as mentioned before the stylesheet can only access this information by guessing all the possible locations and hoping that the user navigates to them, which doesn't differ from styling with on attribute selectors.
