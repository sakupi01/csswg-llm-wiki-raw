Splitting this out of #10001 so that #10001 can be scoped more tightly to classes, which are a little easier.

Use cases:
- Many libraries, frameworks etc augment existing elements with hyphen-separated namespaced attributes. For example `v-` (VueJS), `hx-` (htmx), `x-` (Alpine.js). These may or may not be combined with `data-`. This would allow these libraries to find elements using attributes they own without needing to list them all.
- Sometimes the attribute name contains part of the data, e.g. Vue's `js-attr-foo="bar"` syntax, in which case there is no set of attributes to match.

I think use cases, especially beyond simple attribute presence, are less prominent than classes. Many of the use cases expressed would actually require capturing the wildcard-matched part and using it in declarations which I agree could be useful, but is a much bigger feature.

I have personally never come across use cases for this beyond simple attribute presence, but perhaps others have.

One caveat compared to other wildcard expansion cases is that we'd need to disambiguate `[foo-*=bar]`: is it a `foo-` prefixed attribute with the value of `bar` or a `foo-` attribute that contains `bar`?

Whitespace can help disambiguate, with the wildcard version being `[foo-* = bar]` _and_ make the selector easier to read. There is precedent for mandatory whitespace: that's how we distinguish minus from idents with dashes in `calc()`.
Alternatively, we could support optional quoting that becomes mandatory when the attribute name is not a simple ident.

Or, we can sidestep all of these issues by only supporting it for attribute presence, which seems to be the 80-20 use case.
