## Introduction

Presented, for discussion, are some ideas about customizing `innerText` behavior and, more generally, content transformations with style.

## Example

What if one wanted to omit the `<a>` elements' contents from the results of `document.getElementById('p1').innerText`, in the following example?

```html
<p id="p1">
  This is a first sentence. <a class="cite" href="#ref1">[1]</a>
  This is a second sentence. <a class="cite" href="#ref2">[2]</a>
</p>
```

Generalizing from this example, one can use hypertext to add a wide variety of useful features for end-users, but the resultant hypertext can complicate extracting and using plain-text versions of such content.

## Use Cases

One might desire for the results of `document.getElementById('p1').innerText` or more general-purpose content transformations to be readily useable with:

1. [`Intl.Segmenter`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter) sentence-splitting,
2. text-to-speech functionalities,
3. clipboard and drag-and-drop scenarios,
4. accessibility scenarios.

## Considered Styling Alternatives

### Style Properties

Perhaps one could style elements to describe their behavior with respect to a content transformation into plain text?

```css
a.cite { inner-text: none; }
```

### Pseudo-elements

Perhaps one could use a pseudo-element to provide elements' contents with respect to a content transformation into plain text?

```css
a.cite::inner-text {
  content: none;
}
```

### Pseudo-classes

Perhaps one could use a pseudo-class to style elements for content transformations as they were occurring?

```css
a.cite:transformation-target(text) {
  display: none;
}
```

## Related Document Object Model Ideas

### A New Property

If these ideas are of any interest to the community, should a DOM property for obtaining style-customizable transformations to plain text be the original `innerText` DOM property or, instead, should a new read-only DOM property, e.g., `innerTextStyled`, be provided in addition to the original one?

```js
document.getElementById('p1').innerText;
```
```js
document.getElementById('p1').innerTextStyled;
```

### A New Method

If these ideas are of any interest to the community, brainstorming, perhaps a new DOM method: `transformTo(mimeType, options)` would be useful. The MIME type of `text/plain` could be used to indicate that a content transformation to plain text was desired. Using the `options` parameter, one could indicate: the transformation scenario (from a controlled vocabulary), whether the transformation was, for some MIME types, of a mode of `inner` or `outer` with respect to the element, and, topically, whether to enable customizing the content transformation via styling.

As considered, the `options` argument would be optional. The default value of its `scenario` property could be `serialization`.

```js
document.getElementById('p1').transformTo('text/html', { scenario: 'serialization', mode: 'outer', styling: false });
```
```js
document.getElementById('p1').transformTo('text/plain', { scenario: 'sentence-splitting', mode: 'inner', styling: true });
```
```js
document.getElementById('p1').transformTo('text/markdown', { scenario: 'clipboard-copy' });
```
```js
document.getElementById('p1').transformTo('application/ssml+xml', { scenario: 'speech-synthesis' });
```

How might one use style to be able to customize content transformations for multiple MIME types for multiple scenarios? For discussion, perhaps in a manner resembling:

```
a.cite:transformation-target('text/plain'):transformation-scenario('sentence-splitting') {
  display: none;
}
```

## Conclusion

What do you think about any of these ideas? Thank you.

(see note at the end of https://tc39.es/ecma402/#sec-findboundary ) Maybe if a non-breaking space is used they could segment parentheticals to the preceeding sentence instead of the following one...
2 is (CSS-wise) covered by the [speak](https://www.w3.org/TR/css-speech-1/#speaking-props-speak) property. Anything that wants to read out arbitrary HTML should probably also respect at least [speak-as](https://www.w3.org/TR/css-speech-1/#speaking-props-speak-as) and ideally all the other properties from [css-speech](https://www.w3.org/TR/css-speech-1) if applicable / possible
3 sounds like it might want to be synonymous with [user-select](https://drafts.csswg.org/css-ui/#propdef-user-select)?
4 is, once again, covered by [css-speech](https://www.w3.org/TR/css-speech-1), I think? Did you have any specific accessibility scenarios in mind?

Also, in your example with the references, I'd argue that those should not generally be stripped from plaintext representations of the content. Afterall, documents with nothing but plaintext use references like that to direct the reader towards footnotes. So this would only really be desirable if you're taking an excerpt from the content that doesn't include the footnote at all. The [CSS Generated Content for Paged Media Module](https://www.w3.org/TR/css-gcpm-3/) has [some stuff regarding footnotes](https://www.w3.org/TR/css-gcpm-3/#creating-footnotes) that might be applicable here in some way.

## @AdamSobieski — 2026-10-22

Thank you @Psychpsyo. The [`speak`](https://www.w3.org/TR/css-speech-1/#speaking-props-speak) property covers points 2 and 4 and [`user-select`](https://drafts.csswg.org/css-ui/#propdef-user-select) covers point 3.

I see your point about inline citations, footnotes, endnotes, and bibliographic entries &ndash; there are scenarios where one would want inline citations in resultant text content but others not. Extracting plain text from hypertext appears to have scenario-dependent aspects. Beyond this, you suggest that it can have content-specific, element-specific, or selection-specific aspects: does the content, element, or selection in question also provide those footnotes, endnotes, or bibliographic entries that any inline citations point to?

AI interoperability with documents in Web browsers is of interest to me. I'm thinking about software tools assisting the analysis and evaluation of hypertext documents to, for example, be able to separate out sentences for processing (perhaps alongside their containing paragraphs) and to be able to put wavy or squiggly lines under sentences, without authors having to use `<span class="sentence">`.

If we, those interested, could devise some best practices with respect to getting at only the natural-language plain-text contents of hypertext elements, for example those contents of `<p>` elements, understanding that, for some scenarios, some nested hypertext elements are extraneous, then, maybe, down the road, one could propose techniques for selecting individual sentences (or even individual words) from within hypertext content (including by means of using [`Intl.Segmenter`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter))?

Tying it back to the original post, an idea is that documents could use style to indicate which elements were extraneous with respect to the extraction of plain text from selections of hypertext.

Meanwhile, the Web Annotation Data Model provides [CSS selectors functionalities](https://www.w3.org/TR/annotation-model/#css-selector) while also providing means to [refine selections](https://www.w3.org/TR/annotation-model/#refinement-of-selection). So, one could use a [`TextQuote`](https://www.w3.org/TR/annotation-model/#text-quote-selector) or [`TextPosition`](https://www.w3.org/TR/annotation-model/#text-position-selector) selector to refine a CSS selection resulting in a document's paragraph element.
