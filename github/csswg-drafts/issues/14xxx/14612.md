## Introduction

Presented, for discussion, are some ideas about customizing `innerText` behavior and, more generally, serializations of elements to text, and related content transformations with style.

## Example

One can use hypertext to add a wide variety of useful features for end-users, but the resultant markup can complicate extracting and utilizing text versions of such content. What if, for example, one wanted to omit some `<a>` elements from the `innerText` of a paragraph, or from some other technique for serializing the paragraph to text?

```html
<p id="p1">
  This is a first sentence. <a class="cite" href="#ref1">[1]</a>
  This is a second sentence. <a class="cite" href="#ref2">[2]</a>
</p>
```

## Use Cases

One might desire for the results of a text serialization or content transformation to be readily useable with:

1. [`Intl.Segmenter`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter) sentence-splitting,
2. text-to-speech functionalities,
3. clipboard and drag-and-drop scenarios,
4. accessibility scenarios.

## Considered Styling Alternatives

### Style Properties

Perhaps one could style elements to describe their behavior with respect to a content transformation into plain text?

```css
a.cite { inner-text: none; }
```

### Pseudo-elements

Perhaps one could use a pseudo-element to provide elements' contents with respect to a content transformation into plain text?

```css
a.cite::inner-text {
  content: none;
}
```

### Pseudo-classes

Perhaps one could use a pseudo-class to style elements for content transformations as they were occurring?

```css
a.cite:transformation-target(text-plain) {
  display: none;
}
```

Perhaps one could use pseudo-classes to style elements for content transformations to specified content types and for specified scenarios?

```css
a.cite:transformation-target(text-plain):transformation-scenario(sentence-splitting) {
  display: none;
}
```

## Related Document Object Model Ideas

### A New Property

If these ideas are of any interest to the community, should a DOM property for obtaining style-customizable transformations to plain text be the original `innerText` DOM property or, instead, should a new read-only DOM property, e.g., `innerTextStyled`, be provided in addition to the original one?

```js
document.getElementById('p1').innerText;
```
```js
document.getElementById('p1').innerTextStyled;
```

### A New Method

If these ideas are of any interest to the community, brainstorming, perhaps a new DOM method: `transformTo(mimeType, options)` would be useful. The MIME type of `text/plain` could be used to indicate that a content transformation to plain text was desired. Using the `options` parameter, one could indicate: the transformation scenario (from a controlled vocabulary), whether the transformation was, for some MIME types, of a mode of `inner` or `outer` with respect to the element, and, topically, whether to enable customizing the content transformation via styling.

As considered, the `options` argument would be optional. The default value of its `scenario` property could be `serialization`.

```js
document.getElementById('p1').transformTo('text/html', { scenario: 'serialization', mode: 'outer', styling: false });
```
```js
document.getElementById('p1').transformTo('text/plain', { scenario: 'sentence-splitting', mode: 'inner', styling: true });
```
```js
document.getElementById('p1').transformTo('text/markdown', { scenario: 'clipboard-copy' });
```
```js
document.getElementById('p1').transformTo('application/ssml+xml', { scenario: 'speech-synthesis' });
```

### A New Interface

Drawing inspiration from [`XMLSerializer`](https://html.spec.whatwg.org/multipage/dynamic-markup-insertion.html#xmlserializer), one could provide Web developers with a new interface to utilize to serialize elements, e.g., to text, with these components' algorithms being customizable with style.

This new interface could be called `HTMLSerializer`:

```webidl
[Exposed=Window]
interface HTMLSerializer {
  constructor();

  DOMString serializeToString(Node root, optional object options = {});
};
```
```js
const p1 = document.getElementById('p1');
const serializer = new HTMLSerializer();
const txt = serializer.serializeToString(p1, { type: 'text/plain', scenario: 'sentence-splitting', styling: true });
```

Beyond this, you suggest that it can have content-specific, element-specific, or selection-specific aspects: does the content, element, or selection in question also provide those footnotes, endnotes, or bibliographic entries that any inline citations point to?

AI interoperability with documents in Web browsers is of interest to me. I'm thinking about software tools assisting the analysis and evaluation of hypertext documents to, for example, be able to separate out sentences for processing (perhaps alongside their containing paragraphs) and to be able to put wavy or squiggly lines under sentences, without authors having to use `<span class="sentence">`.

If we, those interested, could devise some best practices with respect to getting at only the natural-language plain-text contents of hypertext elements, for example those contents of `<p>` elements, understanding that, for some scenarios, some nested hypertext elements are extraneous, then, maybe, down the road, one could propose techniques for selecting individual sentences (or even individual words) from within hypertext content (including by means of using [`Intl.Segmenter`](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter))?

Tying it back to the original post, an idea is that documents could use style to indicate which elements were extraneous with respect to the extraction of plain text from selections of hypertext.

Meanwhile, the Web Annotation Data Model provides [CSS selectors functionalities](https://www.w3.org/TR/annotation-model/#css-selector) while also providing means to [refine selections](https://www.w3.org/TR/annotation-model/#refinement-of-selection). So, one could use a [`TextQuote`](https://www.w3.org/TR/annotation-model/#text-quote-selector) or [`TextPosition`](https://www.w3.org/TR/annotation-model/#text-position-selector) selector to refine a CSS selection resulting in a document's paragraph element.

> I don't think I suggested any of this?

I was referring to your argument:

> Also, in your example with the references, I'd argue that those should not generally be stripped from plaintext representations of the content. Afterall, documents with nothing but plaintext use references like that to direct the reader towards footnotes. So this would only really be desirable if you're taking an excerpt from the content that doesn't include the footnote at all.

To your question:

> Precisely what content is extraneous in what scenarios?

The idea here is that content authors could provide this information to algorithms using style.

Beyond tags like `<script>` and `<style>`, for which one could use style to broadly exclude them from parent elements' `innerText`, and beyond `<a>` tags which are sometimes to be included and other times to be excluded, there are also HTML custom elements to consider. HTML custom elements may or may not be extraneous to the sought `innerText` content of their parent elements, at all or for a scenario.

> Why are sentences/words specifically of interest here and why is important to be able to index them programmatically?

Sentences, more than words, as units of language and expression, are important for AI-enhanced document analysis and evaluation. Grammar-checking, for instance, operates at the granularity of sentences.

While LLMs can handle entire articles, sections, and paragraphs, it can be useful to be able to discuss individual sentences occurring in paragraphs.

Is this sentence the topic sentence of its paragraph? Is this sentence factual or fact-bearing? If so, is this sentence factually correct according to some repository of facts? Is this sentence a claim? If so, is this claim supported by other statements?

These kinds of questions, operating at the granularity of sentences, would make use of the capability to separate out, select, and reason about individual sentences. To communicate any findings from such tools with end-users, e.g., with wavy or squiggly lines, it would also be useful to be able to style individual sentences.
