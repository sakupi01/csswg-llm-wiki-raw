In Blink we've been working with a prototype of the "shrink to fit" feature as described in: https://github.com/w3c/csswg-drafts/issues/191

I've split this issue out separately just for clarity.

Our prototype changes how `max-content` is calculated for a subtree.

As a refresher:
`max-content` is calculated by not taking any soft-wraps, a.k.a what is the size of the content if given infinite available space.
`min-content` is calculated by taking every soft-wrap, a.k.a. what is the size of the content if given zero available space.

We've introduced a new property `max-content-sizing: shrink-to-fit` (likely needs to be bikeshedded a little). This property *changes* how `max-content` is calculated. Instead of giving it an infinite available space, we give it a definite one determined by the `min-width`/`max-width` of the ancestors.

As basic example:

https://github.com/user-attachments/assets/9759e53d-a203-4fc9-9038-bf0144573062

<details>
  <summary>Code</summary>

```
<!DOCTYPE html>
<style>
#target {
  box-sizing: border-box;
  max-content-sizing: shrink-to-fit;
  width: fit-content;
  max-width: 100px;
  border: solid 2px;
}
</style>
<input id="range" type="range" min="0" max="200" style="width: 200px" />

<div id="target">
  The quick brown fox jumped over the lazy dog.
</div>

<script>
range.addEventListener("input", (evt) => {
  target.style.maxWidth = `${evt.target.value}px`;
});
</script>
```

</details>

There is an alternate solution where we introduce a new keyword for this value e.g. `width: shrink-content` is similar, but the approach of changing how `max-content` has some advantages.

Primarily things which have `width: fit-content`, shrink-to-fit within the subtree "just work". E.g. their own max-content becomes shrink-to-fit, and so far things work as you'd expect. Additionally this is somewhat simpler for implementations as there is less information to store (only need `min-content`/`max-content`, and not a 3rd `max-shrink-content` or similar. 

N.B. For implementors caching becomes interesting but relatively straight forward. For a given `tentative_inline_size` you can reuse a min/max sizes result if its between a cached `tentative_inline_size` and the produced `max_content`.

I'll open sub-issues for how to distribute this size to children with examples for various layout modes including:
 - flex
 - grid
 - muli-column
 - table
 - atomic-inline

These issues are somewhat orthogonal to the exact syntax/method decided upon.

## @bfgeek — 2026-10-07

Yeah the explainer needs to be updated.

Effectively when computing the max-content size for a layout-node you pass in an additional parameter: the `tentative_inline_size`[1].

We typically thing of the min/max sizes pass as not depending on anything from the parent (except for the tentative block-size). This proposal (in a shrink-to-fit subtree) allows the parent to pass some tentative inline-size.

This `tentative_inline_size` is computed as:
 - The available-size if definite.
 - Otherwise the `tentative_inline_size` from the parent with the parents min-inline-size/max-inline-size applied if resolvable.

In code form if it helps:

```
BlockLayout::CalculateMinMaxSizes(parent_tentative_inline_size) {
   child_tentative_inline_size = parent_tentative_inline_size;
   child_tentative_inline_size = std::min(max_inline_size, child_tentative_inline_size);
   child_tentative_inline_size = std::max(min_inline_size, child_tentative_inline_size);

  result;
  for (child : children) {
    result.Encompass(child.CalculateMinMaxSizes(child_tentative_inline_size));
  }

  return result;
}

BlockLayout::Layout() {
    // for calculating the size of a child:
    child.CalculateMinMaxSizes(available_inline_size);
}
```

[1] Better terminology suggestions appreciated.
