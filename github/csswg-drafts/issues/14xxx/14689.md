The [15 August 2024 Conditional Rules 3 CRD, §3](https://www.w3.org/TR/2024/CRD-css-conditional-3-20240815/#typedef-supports-in-parens) links `<general-enclosed>` to `https://drafts.csswg.org/css-values-4/#typedef-general-enclosed`, both in the grammar and in the evaluation prose. The linked Values 4 Editor’s Draft no longer defines that anchor. This is a missing fragment/definition, not an HTTP failure.

Evidence from locally content-pinned HTML (SHA-256):

- Conditional 3, fetched from `https://www.w3.org/TR/css-conditional-3/`, identifies itself as the 2024-08-15 CRD: `672eb79c78c53b9c92a460ffcfd8718af3c1e38ecf317566d955ffa1df470b35`. HTML line 1333 contains the Values 4 ED href above; lines 1492–1494 repeat it and state “The result is false.”
- The linked Values 4 ED: `26dac2780d37795863209f71d101aec95f3628d6e9affdce1bcb8f5b92ff8315` (HTML revision `700ba7b5e6ea39623b68a2a0575c2bb89c640d54`). No `general-enclosed` text or anchor occurs in these bytes.
- The [13 January 2022 Conditional 3 CR, same grammar anchor](https://www.w3.org/TR/2022/CR-css-conditional-3-20220113/#typedef-supports-in-parens), SHA-256 `83661f96d78a01e99c1bfc94fb870f7e21c9fdba63a4867a6701ab4dcaaa8eb8`, instead links `https://www.w3.org/TR/mediaqueries-5/#typedef-general-enclosed` at HTML line 630.
- That [Media Queries 5 anchor](https://www.w3.org/TR/mediaqueries-5/#typedef-general-enclosed) exists in the pinned 2026-02-19 WD, SHA-256 `9e761f96f6a9935591264b470bdf5e4c1b5b15874c376b9de70e670171671c95`, line 2156: `<general-enclosed> = [ <function-token> <any-value>? ) ] | [ ( <any-value>? ) ]`.

Related issue #10465 records the removal of the duplicate Values 4 definition; it does not appear to track this remaining published Conditional 3 reference. I searched existing issues for `general-enclosed`, `general-enclosed link`, and `css-conditional broken` before filing.

Could the published Conditional 3 reference (or an erratum) point to the maintained definition, as the 2022 CR did? This is only a cross-reference correction request: Conditional 3 already explicitly assigns false to this fallback, and the MQ5 evaluation rule should not replace that prose. It is not a request to add selector feature queries or change evaluation behavior. Evidence above is document inspection, not browser/compiler test output.
