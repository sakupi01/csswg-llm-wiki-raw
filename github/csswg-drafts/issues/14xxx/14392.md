## Summary

CSS currently has no declarative way to select flex items based on the generated flex line they belong to.

For a wrapping flex container, I would like CSS to expose two related pieces of layout information:

1. **Which flex line an item belongs to**
2. **The item's position within that flex line**

For example, conceptually:

```css
/* Position within each generated line */
.item:first-in-flex-line {}
.item:last-in-flex-line {}
.item:nth-in-flex-line(2) {}
.item:nth-last-in-flex-line(2) {}

/* Which generated line the item belongs to */
.item:first-flex-line {}
.item:last-flex-line {}
.item:nth-flex-line(2) {}
.item:nth-last-flex-line(2) {}
.item:nth-flex-line(2n) {}
```

The exact syntax is only illustrative. The important requirement is exposing generated flex-line membership and position declaratively.

## Concrete use case

My immediate use case is a wrapping group of flex items that should visually form rounded rows.

For example:

```html
<div class="group">
    <button>One</button>
    <button>Two</button>
    <button>Three</button>
    <button>Four</button>
    <button>Five</button>
    <button>Six</button>
    <button>Seven</button>
</div>
```

```css
.group {
    display: flex;
    flex-wrap: wrap;
}
```

Depending on the available width, layout might generate:

```text
One   Two   Three
Four  Five  Six
Seven
```

The DOM only tells us that `One` is `:first-child` and `Seven` is `:last-child`.

What I actually need to identify is:

```text
first in line: One, Four, Seven
last in line:  Three, Six, Seven
```

Then styling could simply be:

```css
.group > :first-in-flex-line {
    border-start-start-radius: 8px;
    border-end-start-radius: 8px;
}

.group > :last-in-flex-line {
    border-start-end-radius: 8px;
    border-end-end-radius: 8px;
}
```

This is purely presentational. `border-radius` does not affect flex sizing or line formation, so there is no layout/style cycle in this use case.

## Current workaround

Currently I have to reproduce information that the flex layout algorithm already knows.

In JavaScript I need to:

1. Detect the generated flex lines from element geometry.
2. Mark the first and last item of every line.
3. Recompute this when the container resizes.
4. Recompute this when children are added, removed, or changed.
5. Maintain the generated classes/state separately from CSS.

In practice this requires both `ResizeObserver` and `MutationObserver`.

A typical implementation also has to read item geometry such as `getBoundingClientRect()` or offsets, group items by their cross-axis position, and then add/remove classes.

This is a considerable amount of imperative infrastructure for information that already exists internally during flex layout.

## Position within a flex line

The smallest useful feature would be first/last item selection:

```css
.item:first-in-flex-line {}
.item:last-in-flex-line {}
```

However, a general `An+B` form would make the feature substantially more useful and consistent with existing structural selectors:

```css
.item:nth-in-flex-line(1) {}
.item:nth-in-flex-line(2) {}
.item:nth-in-flex-line(odd) {}

.item:nth-last-in-flex-line(1) {}
.item:nth-last-in-flex-line(2) {}
```

Possible aliases could be:

```text
:first-in-flex-line == :nth-in-flex-line(1)
:last-in-flex-line  == :nth-last-in-flex-line(1)
```

This would support use cases such as:

* first/last item styling
* separators between items except at line boundaries
* special treatment of the second or penultimate item
* repeating patterns within each generated line
* line-local striping or grouping

## Selecting the flex line itself

There is also a separate useful dimension: selecting items according to **which generated flex line they belong to**.

For example:

```css
.item:nth-flex-line(1) {}
.item:nth-flex-line(2) {}
.item:nth-flex-line(2n) {}

.item:nth-last-flex-line(1) {}
.item:nth-last-flex-line(2) {}
```

Possible aliases:

```text
:first-flex-line == :nth-flex-line(1)
:last-flex-line  == :nth-last-flex-line(1)
```

This would make it possible to style:

```css
/* Every item in the first generated flex line */
.item:first-flex-line {}

/* Every item in the last generated flex line */
.item:last-flex-line {}

/* Every item in even generated lines */
.item:nth-flex-line(2n) {}
```

Useful cases include:

* different styling for the first or last visual line
* top/bottom borders for a wrapped group
* alternating generated-line styling
* visual separators between generated lines
* different spacing or decoration for edge lines
* identifying the four outer corners of the complete wrapped group

The two dimensions could compose naturally:

```css
/* First item of the first flex line */
.item:first-flex-line:first-in-flex-line {}

/* Last item of the first flex line */
.item:first-flex-line:last-in-flex-line {}

/* First item of the last flex line */
.item:last-flex-line:first-in-flex-line {}

/* Last item of the last flex line */
.item:last-flex-line:last-in-flex-line {}
```

That provides direct access to the four layout-generated corners of a wrapped flex group.

## Alternative: expose flex lines as pseudo-elements

An alternative design is to expose generated flex lines themselves, conceptually:

```css
.container::flex-line {}
.container::flex-line:nth-child(2n) {}
.container::flex-line:first-child {}
.container::flex-line:last-child {}
```

and potentially allow selecting items through them:

```css
.container::flex-line > :first-child {}
.container::flex-line > :last-child {}
```

This closely matches the conceptual model in Flexbox, where a flex line is a generated grouping created by the layout algorithm rather than a DOM element.

I do not have a strong preference for whether the eventual API should be:

* pseudo-classes directly on flex items
* a `::flex-line` pseudo-element
* both
* another layout-query mechanism

Pseudo-classes on items seem particularly convenient for the common first/last-item case.

## Previous proposal

This is not a new use case.

In 2015 Kenneth Moore proposed a `::flex-line` pseudo-element on the www-style mailing list. The proposal specifically mentioned:

```css
.flex-container::flex-line > .flex-item:first-child
.flex-container::flex-line > .flex-item:last-child
```

as well as selecting even flex lines.

The motivating example was also essentially the same: borders and `border-radius` on wrapping flex groups where DOM `:first-child` and `:last-child` cannot represent generated line boundaries.

That discussion did not result in a standardized feature, so the underlying author problem remains unresolved.

## Layout dependency and cycles

I understand the primary difficulty with this class of feature: flex-line membership is determined by layout, while CSS selected through that membership might itself affect layout.

For example, something like:

```css
.item:last-in-flex-line {
    width: 80%;
}
```

could change wrapping, which could change which item is `:last-in-flex-line`.

However, this does not apply to many important uses of the feature:

```css
.item:last-in-flex-line {
    border-radius: 8px;
}
```

Properties such as `border-radius`, color, background, outline, box-shadow, etc. do not change flex-line membership.

Therefore I don't think the existence of potentially cyclic declarations should make all non-cyclic flex-line-dependent styling impossible.

There has also been broader CSSWG discussion of layout-dependent selectors in #5979.

Possible ways to define cyclic cases could include, for example:

* detect a style/layout dependency cycle and stop reevaluating that dependency for the current update
* retain the previous stable match set when reevaluation would create a cycle
* define snapshot semantics for layout-dependent matching
* ignore only declarations participating in a detected cycle
* restrict some layout-affecting properties if the feature is represented through a special pseudo-element
* use another explicit dependency/containment mechanism

I am not proposing a specific cycle-breaking algorithm here. My point is that cyclic and non-cyclic uses are distinguishable in practice, and browsers already have mechanisms for detecting and terminating other layout-related feedback loops.

The existence of pathological cases such as changing `width` should not necessarily require ordinary cycle-free cases such as `border-radius` to remain dependent on JavaScript.

## Generated order semantics

There are several semantic details that would need specification.

### `order`

Position within a line should presumably correspond to the flex layout's order-modified sequence rather than raw DOM sibling position, since that is the sequence from which flex lines are formed.

### `flex-direction`

`first-in-flex-line` and `last-in-flex-line` should probably refer to the first and last item according to the flex main-axis ordering rather than physical left/right positions.

This would make the selectors work naturally with:

```css
flex-direction: row;
flex-direction: row-reverse;
flex-direction: column;
flex-direction: column-reverse;
```

### `flex-wrap: wrap-reverse`

Similarly, the definition of:

```css
:nth-flex-line()
:nth-last-flex-line()
```

needs to specify whether numbering follows line generation order, cross-start/cross-end order, or physical visual order.

My expectation would be that this should follow Flexbox's logical layout ordering rather than physical top/bottom or left/right coordinates.

### Single generated line

For a single-line result, its items would naturally match both:

```css
:first-flex-line
:last-flex-line
```

Likewise, a flex line containing one item would make that item match both:

```css
:first-in-flex-line
:last-in-flex-line
```

This allows useful composition without introducing additional `:only-*` selectors.

## Why expose both dimensions?

Flex layout already computes a two-dimensional structure:

```text
line 1: item 1, item 2, item 3
line 2: item 4, item 5, item 6
line 3: item 7
```

Authors currently have selectors for neither coordinate:

```text
line index
position within line
```

Exposing both gives a complete and composable model:

```css
:nth-flex-line(An+B)
:nth-last-flex-line(An+B)

:nth-in-flex-line(An+B)
:nth-last-in-flex-line(An+B)
```

Instead of adding isolated selectors for only one special case, this would make the generated flex-line structure generally addressable.

## Related current Flexbox work

Flex lines are still an area of active development. For example, #13414 discusses exposing/control related to flex-line count in connection with balanced wrapping.

If CSS is gaining more control over generated flex lines, it may also be worth considering whether authors should be able to query their generated structure for styling purposes.

## Main request

Could CSS expose generated flex-line structure declaratively, including:

```text
1. first/last item in each flex line
2. nth item in each flex line
3. first/last generated flex line
4. nth generated flex line
```

with appropriate semantics for cyclic layout-dependent cases?

Even only the first/last-in-line capability would eliminate a common category of JavaScript layout observation, while the generalized forms would provide a consistent selector model for flex-line-aware styling.

## @Crissov — 2026-08-28

Would it solve the use cases if the position within a flex (or possibly also grid, table, …) layout was not available as selectors but as **variables** instead (as the local result of a global function), which could be used in `if()` conditions etc.?

Example using the first scenario from the OP:
~~~~ css
.group > button {
  border-radius: 8px;
  border-radius: if(
    style(nth-slot(flex-line) = 1): 8px 0 8px 0;
    style(nth-slot(flex-line) = slot-count(flex-line)): 0 8px 0 8px;
    else: 0;
  );
}
~~~~

PS: Using the shorthand does not cover the case where an item is both the first and the last within a flex line, but you get the idea. 
PPS: How authors can calculate those values – at least for grids with equal-width columns – themselves, is explained in [this article](https://css-tip.com/grid-information/), for instance, which shows it is feasible.
