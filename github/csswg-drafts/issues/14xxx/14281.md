Per the step 3.4 (Generate Initial and Final Frames) in [[css-animations-2]](https://drafts.csswg.org/css-animations-2/#keyframe-processing):
> Repeat for final keyframe, using an offset of 100%, considering keyframes positioned later in the [used keyframe order](https://drafts.csswg.org/css-animations-2/#used-keyframe-order), and appending to keyframes.

If there are multiple matched keyframes at 100%, we consider the later one. However, the spec doesn't mention 0%, so should we use the same rule or we have to choose the first one instead?
For example, if the specified keyframes looks like:
```
@keyframes anim {
  50% {width: 100px;}
  100% {}
  cover 100% {}
  exit 100% {}
  0% {}
  0% {animation-timing-function: linear;}
  cover 0% {}
}
#target {
  width: 50px;
  animation-name: anim;
  animation-timeline: --active-view-timeline; // Assume this is a valid and an active view timeline.
}
```
When filling the missing properties, which 0% and 100% keyframes should have the `width:50px` when calling getKeyframes()?

In Chromium, `getKeyframes()` returns:
```
0: {offset: 0, easing: 'ease', composite: 'auto', computedOffset: 0}
1: {offset: 0, easing: 'linear', composite: 'auto', computedOffset: 0}
2: {offset: 0.5, easing: 'ease', composite: 'auto', width: '100px', computedOffset: 0.5}
3: {offset: 1, easing: 'ease', composite: 'auto', computedOffset: 1}
4: {offset: {"cover", "0%"}, easing: 'ease', composite: 'auto', width: '50px', computedOffset: 0} // Chromium fills the width:50px in the last 0%
5: {offset: {"cover", "100%"}, easing: 'ease', composite: 'auto', width: '50px', computedOffset: 1} // Chromium fills the width:50px in the first range-based 100%?
6: {offset: {"exit", "100%"}, easing: 'ease', composite: 'auto', computedOffset: 1}
```

In WebKit, `getKeyframes()` returns:
```
0: {composite: "auto", easing: "ease", offset: 0, computedOffset: 0, width: "50px"} // WebKit fills the width:50px in the first 0%
1: {composite: "auto", easing: "linear", offset: 0, computedOffset: 0}
2: {composite: "auto", easing: "ease", offset: 0.5, computedOffset: 0.5, width: "100px"}
3: {composite: "auto", easing: "ease", offset: 1, computedOffset: 1, width: "50px"} / WebKit fills the width:50px in the first 100%
4: {composite: "auto", easing: "ease", offset: {"cover", "0%"}, computedOffset: 0}
5: {composite: "auto", easing: "ease", offset: {"cover", "100%"}, computedOffset: 1}
6: {composite: "auto", easing: "ease", offset: {"exit", "100%"}, computedOffset: 1}
```

So it seems Chromium chooses the later one for 0% and 100%. However, if there are multiple range-based keyframes, it chooses the first range-based keyframe. This doesn't match the spec.
WebKit always chooses the first one (i.e. the percentage-based keyframe). So this seems incorrect either (at least for 100%).

This is unclear to me.
In Gecko, I intend to always put the properties into the last matched keyframes:
```
0: { composite: "auto", easing: "ease", offset: 0, … }
1: { composite: "auto", easing: "linear", offset: 0, … }
2: { composite: "auto", easing: "ease", offset: 0.5, width: 100px, … }
3: { composite: "auto", easing: "ease", offset: 1, … }
4: { composite: "auto", easing: "ease", computedOffset: 0, offset: {"cover", "0%"} ,width: 50px, … } // last 0%
5: { composite: "auto", easing: "ease", computedOffset: 1, offset: {"cover", "100%"}, … }
6: { composite: "auto", easing: "ease", computedOffset: 1, offset: {"exit", "100%"}, width: 50px, … } // last 100%
```
This matches the spec words for 100%, but it is still unclear to me about 0% (so I assume we should put it in the last one as well).
