### Context

Currently, the segment endpoint algorithm creates "internal" endpoints at a gap junction, which according to the spec:

> A gap junction is a region where one or more gaps abut or overlap the gap.

This makes no distinction between layout models (Grid, multicol, flex, grid-lanes). However, after some discussions we think that there should be somewhat of a distinction, which is described below.

### Layout models

#### Multicol

The gutters and column rules separate whole column boxes.  The content within the column boxes becomes irrelevant and doesn't affect or create any segment endpoints. 

Each column rule runs from top to bottom, even with `rule-break: intersection`.

<img width="466" height="402" alt="Image" src="https://github.com/user-attachments/assets/575a1601-cb71-4b32-82eb-ac91e029364f" />

#### Grid

Grid has tracks in both axes. The gutters separete these tracks, and therefore row and column gutters cross. Thus the track structure creates "internal" endpoints.

<img width="466" height="402" alt="Image" src="https://github.com/user-attachments/assets/0e3c624b-b111-4ef1-a687-a05c78b8eedb" />

#### Flex

Flex has no tracks, but gutters are defined as existing between items and flex lines, and these abut so we end up with "internal" endpoints as so:

<img width="466" height="402" alt="Image" src="https://github.com/user-attachments/assets/0e603f39-a4ac-4be9-84a2-cd7e5e10bd3c" />

#### Grid lanes

Grid lanes has tracks only in the grid axis. Stacking-axis gutters are then technically local to between items inside each track.

<img width="466" height="402" alt="Image" src="https://github.com/user-attachments/assets/473dff9b-d9c9-4eeb-b6e3-af3a7d88d7b5" />

### Problem

As currently in the spec, the generic endpoint  behavior creates endpoints in a grid-axis gap whenever a stacking-axis gutter abuts it.

In many cases this ends up creating many staggered endpoints and splits the grid-axis decoration endpoints based on the contents of each track.

With `rule-break: intersection`, the result is:

<img width="466" height="402" alt="Image" src="https://github.com/user-attachments/assets/57ebe6ea-6bb8-4621-9e86-061e94f74336" />

This seems inconsistent with how we treat multicol and grid, since in those cases we treat the decorations as a separator between tracks with the content within those tracks not really affecting the decoration geometry.

### Proposed model

For a grid-axis gap in a grid lanes container:

- We treat stacking-axis gutters as confined within their tracks, BUT as not abutting grid axis gutters. **This has no impact on how we are currently treating the stacking-axis gutters and decorations.**
- Items spanning across the grid-axis gap still create endpoints at their boundaries, preserving the current `normal` behavior.
- The only exception becomes when items span across the grid axis gap, which effectively extends the gutter for that item beyond the track(s) it might be in.

This gives the following result for `rule-break: intersection`:

<img width="466" height="402" alt="Image" src="https://github.com/user-attachments/assets/c3f50144-c318-41d0-ad01-73e34ca09b0f" />

Thus, `intersection` and `normal` have the same effect on grid-lanes' gap decorations, in both axis (which is what happens in a multicol with no column wrap):

- `none` remains continuous, including behind spanning items.
- `normal` breaks at spanning items.
- `intersection` also breaks only at spanning items.

Related:
- https://github.com/w3c/csswg-drafts/issues/14489 (this proposal would make resolution for this trivial).
- https://drafts.csswg.org/css-gaps-1/#segment-endpoints

## @alisonmaher — 2026-09-18

In grid lanes, the decorations in one-dimension separate tracks, and the decorations in the other dimension separate items, so I agree that these should be treated as independent and not create intersecting points used for `rule-break: intersection` (similar to what we get in multicol).

> Should we change the flex behavior to align with this proposal as well?

Unlike grid lanes, the decorations in both dimensions separate the same thing (items) so I could see the argument for these two to diverge, but I would be ok simplifying flexbox, as well, since the behavior can end up looking quite strange.
