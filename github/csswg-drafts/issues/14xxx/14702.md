**Where:** CSS Shadow Module Level 1 (formerly CSS Scoping), Editor's Draft 28 April 2026, §5.3 Forwarding a Shadow Element: the exportparts attribute (#exportparts-attr), against §5.6.1 Rules for parsing part mappings (#parsing-mapping) and §5.6.2 Rules for parsing a list of part mappings (#parsing-mapping-list).

**Text.** §5.3 lists this mapping form:

> ::ident : outerIdent

> If ::ident is the name of a fully styleable pseudo-element, adds ::ident / outerIdent to el’s forward part name list. Otherwise, does nothing.

and example #example-b11a0a88 uses it:

```html
<template id=custom-element-template>
  <p exportparts="::before : preceding-text, ::after : following-text">
    Main text.
</template>
```

§5.6.1:

> A valid part mapping is a tuple of tokens separated by a U+003A COLON character and any number of space characters before or after the U+003A COLON The tokens must not contain U+003A COLON or U+002C COMMA characters.

> Collect a sequence of code points that are not space characters or U+003A COLON characters, and let first token be the result.

> If first token is empty then return error.

§5.6.2:

> If mapping is an error then continue to the next iteration of the loop. This allows clients to skip over new syntax that is not understood.

**What is wrong.** Parse `::before : preceding-text` with §5.6.1. After skipping leading spaces, the first code point is U+003A COLON, so the first token is empty and the algorithm returns error. §5.6.2 then drops the mapping. The same happens to `::after : following-text`. So the `::ident : outerIdent` form defined in §5.3 can never be produced by the parser, and the example forwards nothing. No cascade step is involved; the mapping is lost before matching.


Background: #10083 (closed) resolved that the exportparts attribute "will gain a syntax for exporting part-like pseudos, details TBD". The §5.3 form looks like that addition; §5.6.1 was not updated with it. #5504 (closed, invalid) is about a different, older mismatch in this section.

Found during an AI-assisted review of the cascade specs.

**Request:** could §5.6.1 be aligned with §5.3 so that the `::ident : outerIdent` form parses, for example: "If the next two code points are U+003A COLON U+003A COLON, consume them and let first token start with them. Then collect a sequence of code points that are not space characters or U+003A COLON characters, and append them to first token."
