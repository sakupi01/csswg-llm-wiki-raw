Right now `object-view-box` does nothing on an inline `<svg>` in any browser, and the spec isn't clear on what it should do. There's even an inline issue in the text saying "Make sure behavior is properly consistent for SVG". This came up again in w3c/fxtf-drafts#7, where @vmpstr asked whether that proposal is just `object-view-box`. I think it is, if we define it properly for SVG. I've been working on the Chromium implementation and I'd like to get the spec side settled so I'm not inventing behavior.

The use case I care most about is the one people have been asking for since #128 in 2016: an inline SVG with a `viewBox` and no `width`/`height` attributes, sized by CSS, that you can pan and zoom by animating a property. That's how most inline SVG gets written today, because dropping the width and height is what makes it responsive. Any definition that requires those attributes back is a non-starter for that audience.

### Issues with the current text
The spec says the property has no effect "if the element does not have both a natural width and a natural height". For an inline svg, natural width and height come from the `width`/`height` attributes only. A viewBox-only svg has a natural aspect ratio but no natural size, so by the letter of the spec the property is a no-op for exactly the case people want.

The intro says it "maps to the `<svg viewBox>` attribute", which reads as user units, but the normative text resolves the shape against the natural size in CSS px. Those two things disagree as soon as the viewBox and the natural size differ.
The spec doesn't say which viewport the svg's contents get laid out into, or whether hit testing and geometry APIs see the view box.

And `Percentages: n/a` is just wrong, `inset()`/`xywh()`/`rect()` take percentages.

### Proposed text
**Reference box.** Resolve the view box against a reference box, picked like this:
1. If the element's contents have their own coordinate system with a size (for `svg`, the `viewBox`), use that, in that coordinate system. The origin is the viewBox's min-x/min-y. This applies even if the svg also has width/height attributes.
2. Otherwise, if the element has a natural width and height, use that. This is the current rule and nothing changes for `img`, `video`, `canvas`.
3. Otherwise there's no reference box and the property has no effect.

The reason for "even if it has width/height attributes": an svg author already thinks in user units for everything else (`getBBox()`, `transform`, `createSVGPoint()`). Having the units of `object-view-box` silently switch from user units to CSS px depending on whether someone added `width="100"` is the kind of thing that generates bug reports forever. `<img src="x.svg">` is a different situation because the img can't see inside the image; natural size is all it has.

**Natural size.** If the element had a natural width and height, treat it as having the view box's size, as today. If it didn't, it still doesn't. Either way, if it had a natural aspect ratio, it now has the view box's ratio. The point is that a responsive svg stays responsive. Adding or animating `object-view-box` never changes how big the box is, only what's shown in it (unless you're relying on `height: auto` and the ratio changes, which is the same as for an img).

**Layout viewport for the content.** The svg's contents are laid out into a viewport that's the natural size if there is one, otherwise the viewBox size (one user unit per CSS px). Not the CSS content box. viewBox and `preserveAspectRatio` apply to that viewport like normal. If there is a natural size, the user-unit view box gets mapped to the natural size through that same transform. Then the result is scaled and positioned into the box by `object-fit` and `object-position`, same as an image.

For the viewBox-only case this means nothing inside the svg changes when you add the property: percentages, stroke widths, all of it resolves exactly as before. That's also the real difference from a property that overrides `viewBox` directly. Content doesn't reflow while you pan, which is what you want.

One thing people might want to discuss: once `object-view-box` applies, `object-fit` is what fits the content into the box, not `preserveAspectRatio`. The default `object-fit: fill` stretches, so if you were relying on the default `xMidYMid meet` letterboxing you'd add `object-fit: contain`. I think that's correct (the `object-*` properties should work together) but the spec should say it.

**Hit testing and geometry.** The scale and translation apply to hit testing and to anything that reports the geometry of the contents (`getBoundingClientRect()` on descendants, `getScreenCTM()`), as if it were part of the content's transform. The svg element's own box isn't affected.

**Scope.** This applies to replaced elements in the document they're laid out in. It doesn't apply to the root `svg` of a standalone svg document or of an svg image; their viewport comes from the embedding context. Same as the other `object-*` properties, and it avoids applying a view box twice (`<img style="object-view-box">` showing an svg whose root also sets it).

**Zero area.** I think we'd treat it as `none`. That closes the open issue in the spec and matches what shipped for `img`, and has less compat issues, though in practice it might surprise people to see it snap.

### Examples

```html
<svg viewBox="0 0 1000 1000" style="width: 100%; object-view-box: xywh(250 250 500 500)">
```
Shows the middle quarter, scaled to fill. The box is still `width: 100%` with a 1:1 ratio. Animate `object-view-box` to pan around.
```html
<svg width="100" height="100" viewBox="0 0 200 200" style="object-view-box: inset(50px)">
```

`inset(50px)` is in user units, so this selects user units 50 to 150 (the middle 50 CSS px of the natural size), scaled 2x into the 100x100 box.

### Implementation
Chromium, behind a flag: https://chromium-review.googlesource.com/c/chromium/src/+/8603348 (started by @vmpstr). Tentative WPTs are in `css/css-images/object-view-box-inline-svg*.html` and cover viewBox-only, viewBox with a non-zero origin, viewBox differing from the natural size, preserveAspectRatio letterboxing, width attribute only, percentages, object-fit, hit testing, zoom, and document-root exclusion.

### Asks
1. A resolution that `object-view-box` applies to inline `svg` as described above.
2. Editorial: fix `Percentages: n/a`, and change "It maps to the `<svg viewBox>` attribute" to something like "It is analogous to the `viewBox` attribute of SVG", plus the examples.

## @tabatkins — 2026-10-20

This bit of spec text was definitely just a rough sketch (can you tell??) that I subsequently forgot about, so I'm happy to see it get attention. ^_^

Note that, despite the spec *saying* "maps to the `<svg viewbox>` attribute", that's wrong. It's a lie. Later, the definition *explicitly* says it doesn't interact with `viewBox`. As currently defined, the property is *solely* about replaced elements, like `object-fit`/`object-position` are. So, let's talk about the types of things we *could* define it to affect.

First, here's the order of operations for the various properties today:

1. Query the element for its natural sizes.
2. Use natural sizes + CSS layout to size the element.
3. Use the sizing algo to combine natural sizes, specified sizes, and default sizes into a concrete size. (`object-fit` applies here, affecting how we determine the concrete size.)
4. Ask the image to render into the concrete-size rectangle.
5. Use `object-position` to position this drawn rectangle into the element.

As currently defined, 'object-view-box' has an effect on step 1 (where it can change the natural sizes) and in a step 4.5 (where it scales/translates the rendered result).

We've also got several situations where 'object-view-box' could potentially apply:

1. Raster image in `img`. (Has all natural sizes, simple rendering.)
2. SVG image in `img`, on the `img`. (Can have 0-3 natural sizes, complex rendering.)
3. Inline `svg` in HTML.
4. SVG image in `img`, on the `svg`.
5. Other elements that take `viewBox`, like `marker`.

1-3 are what the property is *currently* defined to affect, parallel with `object-fit` and `object-position`. 3-5 are the "has `viewBox` attribute" cases, which (ignoring the lie in the spec) aren't yet touched by this property. We need to make sure that these two cases, which I think are rather separate, play nicely together, particular in the overlap case (3).

I think Case 1 is pretty straightforward and intuitive. 'object-view-box' defines a viewport over the image, and we size the `img` according to the viewbox's dimensions. Simple.

A wrinkle is that, currently, the spec says that we use the view box's dimensions as the new natural dimensions; if you have a 200x100 image and use `object-view-box: xywh(0 0 100px 100px);`, you'll get a square 100x100 image instead. This is different from your proposal, and how `viewBox` works, where it just provides a (weak) aspect-ratio. I believe my thought at the time was that this was useful to cut out a fragment of an image, and should behave as if it was just that fragment, but I think I was wrong, and you're right here: the "pan and zoom" use-case for view-box manipulation/animation is much better served if the width/height doesn't change (except indirectly via an `auto` size that uses the aspect ratio). This means that `object-view-box` would *not* have an effect on step 1, above, and instead should use the concrete object size as its reference box. This'll mean that `inset(0 0 0 0)` is a no-op view box, which I think is reasonable/intuitive.

Case 2 is part of what you're interested in. This should behave essentially the same as case 1; the format of the image shouldn't have an effect on the rendering. This implies that `object-view-box` *stacks with* whatever the SVG's own `viewBox` is doing; they don't interact with each other. (This also means that you don't need to worry about what the image might be doing with its `viewBox`, which I think is important; when linking to an external SVG, those are irrelevant details.)

However, as currently defined this only works when the SVG has `width` and `height` attributes on the root. Consistent with above, I think we should indeed change this, to just impose an aspect-ratio, and to use the concrete object size as the reference box, so it applies at all times.

Case 3 is the other part that you're interested in, and it's more interesting, I think. First, despite their definitions, `object-fit` and `object-position` don't actually apply to an inline SVG. See, for example, [this testcase](https://software.hixie.ch/utilities/js/live-dom-viewer/):

```html
<!DOCTYPE html>
<svg viewBox="-1 -1 2 2" preserveAspectRatio=none><circle fill=orange r=1 /></svg>
<img src="https://tabatkins.com/circle">
<style>
body > * {
 border: thick dotted;
 width: 200px; height: 100px;
 object-fit: none;
 object-position: top left;
}
</style>
```

I wonder how intentional this is, and if we want to change that? There's three possibilities, I think:

1. The `preserveAspectRatio` attribute maps to a subset of the `object-fit`/`object-position` functionality, and *could* be made into a presentation attribute that expands to those two properties. It would certainly be easier to use than the SVG attribute values, I think! (`object-fit: cover; object-position: center bottom;` versus `preserveAspectRatio="xMidYMaX slice"`)
2. `object-fit`/`-position` apply exactly the same as they do in `img`, *on top of* whatever the SVG is doing. This way, inline `<svg>` and `<img>` would render identically.
3. `object-fit`/`-position` don't apply to inline SVG, only `img` and related elements.

Then `object-view-box` should, hopefully, just follow along and do the same thing: either `viewBox` becomes a presentation attribute for `object-view-box`, or `object-view-box` applies just like it does on `img`, or `object-view-box` doesn't apply at all to inline SVG.

Behavior 1 makes cases 3-5 all act similar, while Behavior 2 makes cases 1-3 all act similar. Behavior 3 is the current behavior, and makes the question moot. I lean toward Behavior 1, personally.

Case 4 and 5 should be the same as each other, and should follow along with Case 3: either `viewBox` is a presentation attribute for `object-view-box` on the elements, or `object-view-box` has no effect.

---------------

Your proposal is for a slightly different Case 3 behavior: rather than `object-view-box` (/`-fit`/`-position`) applying *on top* of the rendered SVG, like Case 2, or being *CSS equivalents* for `viewBox`/`preserveAspectRatio`, they apply *inside of* the SVG's `viewBox`. The default behavior (`object-fit: fill`) means you stretch the `viewBox`/`preserveAspectRatio`-defined rectangle to fill the `<svg>` element's bounds, but you can do other stuff with it.

I think I'm mildly opposed to this, just because it's *doing the same thing* as what those properties are already doing. You'd be sizing/positioning one rectangle, and then sizing/positioning a second rectangle inside of it in the exact same way. That seems somewhat unnecessary and potentially confusing to me, at least in the inline-SVG case. (In `<img>`, this is fine, as you aren't directly exposed to the `viewBox`/`preserveAspectRatio` set on the SVG.)

It also means that `object-view-box` uses quite different coordinate systems for `<img>` and for `<svg>`, which I think is potentially confusing.

-----------------

So, proposals to discuss:

1. Should we change `object-view-box` on to just provide a (weak) aspect-ratio (only if it doesn't already have one), like `viewBox` does? It will no longer adjust the natural width/height of an image, and only affect the size of an `img` *at all* if it's an SVG without a natural width/height, and `height: auto`. This means that, outside of that one mentioned case, animating `object-view-box` will just perform a zoom/pan of the content, and will not change the dimensions.
2. How should `object-view-box`/`-position`/`-fit` apply to inline SVG? Same as for `<img>`? Turning `viewBox` and `preserveAspectRatio` into presentation attributes for those properties? Not apply at all? (I propose presentation attributes, tho we'll need compat data.)
3. Should external `<svg>` roots and other `viewBox` using elements (nested `<svg>`, `<marker>`, etc.) act the same as question 2, or ignore these properties entirely? (I propose same.)
