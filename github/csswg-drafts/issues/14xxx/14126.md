### Summary

Title basically.

When a point lies over a replaced element (e.g. `<img>`) that a custom highlight covers and paints over, should `highlightsFromPoint()` return that highlight? And, symmetrically, should a point over a **non-replaced, non-text** element that merely occupies layout space (nothing painted there) return no highlights?

In short: **is the set of boxes `highlightsFromPoint()` hits defined to be the same set that highlights paint over?**

### What the spec says today

[css-highlight-api-1 6 Interacting with Custom Highlights][interactions] defines `highlightsFromPoint(x, y, options)` as returning the highlights/ranges "hit at a given x, y coordinate", ordered by priority, but it does not spell out which kinds of boxes/nodes count as a hit (e.g. text vs replaced content vs an empty non-replaced box that just takes up space).

The set of boxes a highlight **paints** over is governed by [css-pseudo-4 3.4 Area of a Highlight][bounds] ("text or replaced content"), which is the subject of a separate issue: https://github.com/w3c/csswg-drafts/issues/14108.

### The question

1. Should `highlightsFromPoint()` return a highlight when the hit point is inside a replaced element that the highlight covers and paints over (e.g. clicking a highlighted `<img>`)?
2. Should it return nothing for a non-replaced, non-text element that merely occupies layout space?
3. Most importantly: should the spec define the hit-testable set to **equal** the painted set? Keeping the two in sync avoids the surprising case where a highlight visibly tints a box but `highlightsFromPoint()` doesn't report it there (or vice versa).

### Motivation

Because the spec doesn't specify which kinds of boxes count as a hit, a UA could reasonably implement `highlightsFromPoint()` to consider only text, in which case a point over a highlighted replaced element returns nothing even though the highlight visibly tints it, so the painted set and the hit-testable set would diverge. Defining the two to match in the spec avoids that inconsistency and keeps implementations interoperable.

### Proposal

Define the `highlightsFromPoint()` hit set to equal the painted set from css-pseudo-4 3.4: text plus the replaced boxes UAs paint `::selection` over.

Feedback welcome.

## @schenney-chromium — 2026-07-06

One model would be caretPositionFromPoint, but that explicitly says "where text insertion could occur". In Chromium, from memory, you can get a position right before or after an inline image in some circumstances.

My immediate reaction is that highlightsFromPoint should return the highlights that are painted regardless of what's under the point. I think a user or developer would be surprised if there was no way to identify a highlights painted over a replaced element or something else. Presumably you're trying to identify the highlight to remove it or otherwise take some action, so making the highlight effectively invisible seems wrong.
