The spec for the `block-ellipsis` property (which is part of `line-clamp`) says the ellipsis isn't counted for `min/max-content`:

> It also has no effect on the intrinsic size of the box: its [min-content](https://drafts.csswg.org/css-sizing-3/#min-content) and [max-content](https://drafts.csswg.org/css-sizing-3/#max-content) sizes are calculated exactly as if [block-ellipsis](https://drafts.csswg.org/css-overflow-4/#propdef-block-ellipsis) were [no-ellipsis](https://drafts.csswg.org/css-overflow-4/#valdef-block-ellipsis-no-ellipsis).

For `width: {min,max}-content`, in most cases it seems like this would be okay; but if the clamp point happens to be on the longest line, then the box would be sized according to that, and _after that_ the ellipsis would reduce the width of the line (and in the case of `min-content` displace it entirely by the ellipsis), leaving the width no longer minimal:

<img width="278" height="166" alt="Image" src="https://github.com/user-attachments/assets/b6e5b792-c3d8-4d67-8bdb-7a1723e8e99f" />
<img width="278" height="166" alt="Image" src="https://github.com/user-attachments/assets/60f0ce1c-523d-4419-a0ff-af6297ba7728" />

Is this what we want?

For the record, there are a few WPT that fail in our implementation in Chromium because of this. They're all related to baselines, and are basically written to the same mold and trigger this issue in the same way. In these tests, since all of the lines only contain an atomic inline of the same size which is taller than the strut, when the ellipsis is added to the last line, the atomic inline gets displaced, and that line becomes shorter, which can be observed through the baselines:
