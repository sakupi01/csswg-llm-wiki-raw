In §6.3 (ICtCp), the first example gives sRGB `lime` as `ictcp(0.5393 -0.2643 -0.0625)`. The spec's own sample code (`XYZ_to_ICtCp`, Yw = 203) gives a different value:

| | I | Ct | Cp |
|---|---|---|---|
| printed | 0.5393 | -0.2643 | -0.0625 |
| computed from `lime` | 0.5398 | -0.2812 | -0.0495 |

The printed value decodes to about `color(srgb -0.339 1.010 0.188)`: close in lightness, 4° off in OKLCh hue, and outside sRGB.

The other ICtCp values in the draft agree with the sample code: `red` as `ictcp(42.8% -0.116 0.279)` in the ΔE ITP example, and diffuse white as `ictcp(0.58069 0 0)` right below this one.

I could not find one change that reproduces the printed triple. A 100 cd/m² white gives Ct -0.2642, but then I is 0.4689 and Cp -0.0474.

Suggested fix: `ictcp(0.5398 -0.2812 -0.0495)`.

Computed with the sample code of the 26 October 2026 draft and with colorjs.io 0.7.1; the color-space npm library, which I maintain, agrees.

## @svgeesus — 2026-11-10

Thanks for the report. I agree the current spec value is not correct (possibly it was, at some earlier point, with the code I was then using).

I agree that your suggested fix (which is the default value when the color.js convert utility is started) is better, although [that value converts back](https://apps.colorjs.io/convert/?color=ictcp(53.98%25%20-0.2812%20-0.0495)&precision=4) to `rgb(-0.0981% 100% 0.1002%)` which is out of gamut. Limited precision is the culprit here

[Converting `lime` with 7 digits](https://apps.colorjs.io/convert/?color=lime&precision=7) gives `ictcp(53.97603% -0.2812479 -0.0494845)` which when [converted back](https://apps.colorjs.io/convert/?color=ictcp(53.97603%25%20-0.2812479%20-0.0494845)&precision=7) gives `rgb(0.0000984% 100% 0.0000325%)` - still not exact, but much closer and not out of gamut.
