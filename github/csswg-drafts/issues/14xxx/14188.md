I'd like to clarify how the [`zoom`](https://drafts.csswg.org/css-viewport/#zoom-property) property should work with [`animation-range-start`](https://drafts.csswg.org/scroll-animations/#propdef-animation-range-start) and [`animation-range-end`](https://drafts.csswg.org/scroll-animations/#propdef-animation-range-end).

My expectation is that when using [`animation-range-start`](https://drafts.csswg.org/scroll-animations/#propdef-animation-range-start) and [`animation-range-end`](https://drafts.csswg.org/scroll-animations/#propdef-animation-range-end) from CSS, pixel lengths are scaled using the effective zoom of the same element's style just like all other properties.

Similarly, the pixel values returned from an [Animation](https://drafts.csswg.org/web-animations-2/#the-animation-interface) object's (when used with a style backed animation that has not overridden anything) [rangeStart](https://drafts.csswg.org/web-animations-2/#dom-animation-rangestart) and [rangeEnd](https://drafts.csswg.org/web-animations-2/#dom-animation-rangeend) attributes should be unscaled values due to the viewport spec [stating](https://drafts.csswg.org/css-viewport/#zoom-om) "All other APIs related to element geometries must return unscaled lengths (except as detailed below)". (Though, is this relative to "element geometries"? Kinda?).

Where I am not sure is when setting pixel values on the programatic interfaces.

For example, if you have a style backed [Animation](https://drafts.csswg.org/web-animations-2/#the-animation-interface) object, and the style that defined it was something like:

```css
.animation-element {
    animation: go 1ms linear;
    animation-range-start: 100px;
    animation-range-end: 200px;
    zoom: 2;
}
```

and you override it in script with something like:

```javascript
animation.rangeEnd = "20px";
```

Should the [`zoom`](https://drafts.csswg.org/css-viewport/#zoom-property) of the backing animation element's style (in this case with value `2`) affect that? In this case meaning the used value would be `40px`?

One argument in favor of having [`zoom`](https://drafts.csswg.org/css-viewport/#zoom-property) apply to overridden values is that it round trips. Reading the value and then setting it back keeps the value the same.

In the case of non-style backed [Animation](https://drafts.csswg.org/web-animations-2/#the-animation-interface) objects, there is no style to get the [`zoom`](https://drafts.csswg.org/css-viewport/#zoom-property) property from, so my assumption is pixel lengths are unscaled throughout in that case.

## @ydaniv — 2026-07-17

An important thing to note about `animation-range-*` properties is that they are set on the animation effect's target, but are actually [calculated against the animation's associated timeline](https://drafts.csswg.org/scroll-animations/#view-progress-timelines).
So zooming the target doesn't zoom the timeline.
But zooming the timeline - the `source` of a specified `scroll-timeline` or the nearest scroll-container of a specified `view-timeline` - should probably apply the behavior you describe.

As far as I can tell, the [`zoom`](https://drafts.csswg.org/css-viewport/#zoom-property) property doesn't take anything like that into account. It only cares about the value of [`zoom`](https://drafts.csswg.org/css-viewport/#zoom-property) for the element the `<length>` it is is scaling was defined on.

> As far as I can tell, the [zoom](https://drafts.csswg.org/css-viewport/#zoom-property) property doesn't take anything like that into account. It only cares about the value of [zoom](https://drafts.csswg.org/css-viewport/#zoom-property) for the element the <length> it is is scaling was defined on.

Sure, what this means is that `zoom` on the animation target - the element `animation-range` is specified on - shouldn't affect the lengths specified in `animation-range`, but `zoom` specified on the timeline source - the element matched by the view-timeline specified in `animation-timeline` - should affect these lengths.

## @emilio — 2026-07-23

So the CSS case should be uncontroversial, it should be resolved like every other length. You can make the same argument with `position: absolute; top: 10px;` or so being relative to the containing block rather than the element you're styling, but that doesn't change the `zoom` behavior.

The JS case is... funnier. If there's no element there's clearly no zoom, so that seems ok.

> One argument in favor of having [zoom](https://drafts.csswg.org/css-viewport/#zoom-property) apply to overridden values is that it round trips. Reading the value and then setting it back keeps the value the same.

Yeah, I think that'd be a decent argument for applying it to JS... On the flip side zoom is kind of a legacy thing so if it makes things all that much more complicated I could live with not doing so.

There's the same question as usual (at which point do we track it, at the point of setting? Or at used value time?). I guess since zoom usually works at least as-if it was used-value time, it seems fine to do it like that (but needs to be defined of course).

## @weinig — 2026-07-23

In the WebKit implementation, I opted to ignore zoom for any value set using the JS API regardless of whether it is a style originated Animation or not because it was slightly simpler and avoided a bunch of questions. I think this is the least objectionable behavior despite my argument against it and would be my proposal.

The one bit I am still not totally sure on is if zoom should be applied or not when reading a style originated value from the JS API. Having the zoom not applied would match the behavior of things in the CSSOM like clientTop and serialized computed style lengths, but this isn't the CSSOM so I am not sure if that is an appropriate analog.
