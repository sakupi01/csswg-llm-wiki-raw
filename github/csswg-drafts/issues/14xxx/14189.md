In Gecko, we're trying to make incremental progress towards unprefixed `line-clamp`. However, that proves to be a bit tricky because, naively, it means that we should make `-webkit-line-clamp` _either_ a shorthand or a longhand at runtime, which tricky to implement right.

I took a look at how Chromium implements it and it involves multiple internal properties with different names like `-alternative-webkit-line-clamp-shorthand`, `-alternative-webkit-line-clamp-longhand`, `-alternative-line-clamp-shorthand` ([code](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/css/css_properties.json5;l=7465-7565;drc=2328614277cbba0afae40d04aa4f88deb4f529f0)) to get the (close to) the right behavior. Even so, it's [tricky to implement](https://issues.chromium.org/issues/535213605), given all the CSSOM implications of being a longhand vs shorthand.

It's _fine_, I suppose, it doesn't block progress, but incremental progress would be a lot easier if we shipped unprefixed `line-clamp` restricted to the `-webkit-legacy` syntax. I guess you do get to the same issue eventually when trying to make `line-clamp` a shorthand but that doesn't necessarily expand the syntax space which simplifies things a bit.

Seemed worth running by folks at least :)

## @andreubotella — 2026-07-15

For what's worth, in Chromium we're planning to ship `line-clamp` as a longhand (which `-webkit-line-clamp` would be a legacy shorthand of), but with the entire syntax space of it as a shorthand except for the ellipsis string (which we're planning to add in a later version, together with `text-overflow: <string>`).

The difference is of course that in Chromium we have essentially the whole of the property implemented, except for minor things that can be added after shipping and don't affect syntax (again, other than the ellipsis string). The only reason we're shipping `line-clamp` as a shorthand is that the division of the syntax space among the longhands is still not fully clear (https://github.com/w3c/csswg-drafts/issues/13670#issuecomment-4461184054).

I think shipping `-webkit-legacy` only might be fine, especially if it lets you advance more easily; but I'd want to be careful about the devrel aspect of this. Ideally we wouldn't want developers using `-webkit-legacy`: they'd instead use `line-clamp` only where they want it to have some effect.

But I wonder if it'd be possible to ship `line-clamp: <number> -webkit-legacy?` instead, removing the need for `display: -webkit-box` when it ships, and then over time moving its behavior closer to the spec? But that's probably creating too much of a compat risk.
