## @svgeesus — 2026-06-19

From CSS Color 4,  all colors were absolute and thus [Serializing alpha values](https://drafts.csswg.org/css-color-4/#serializing-alpha-values) says:

> If, after clamping to the range [0, 1] the alpha is 1, it is omitted from the serialization; an implicit value of 1 (fully opaque) is the default.

> If the alpha is any other value than 1, it is explicitly included in the serialization as described below.

However, in CSS Color 5, [Processing Model for Relative Colors](https://drafts.csswg.org/css-color-5/#rcs-intro) it says:

> If the alpha value of the relative color is omitted, it defaults to that of the [origin color](https://drafts.csswg.org/css-color-5/#origin-color) (rather than defaulting to 100%, as it does in the absolute syntax).

Which means that the declared value serialization of relative colors, which currently says that unitary alpha is omitted, is **wrong**. Omitted alpha means the alpha of the origin color, not 1.

**Proposed resolution:** when serializing the declared value of relative colors, remove the "non unity" clause and always serialize the alpha value.

## @tabatkins — 2026-07-29

I think omitting the alpha component from the alpha() function is fairly nonsensical. I *understand* the argument that this is just yet another relative-color-syntax function and following along with the behavior the rest have is good, but it only has *one controllable component*, and omitting it makes the function a no-op.

It seems to make a lot more sense (and avoid the extra questions in this thread) if `alpha()` is recognized as just a slightly unique function in this regard, which *cannot* have the alpha component omitted.
