[#11211](https://github.com/w3c/csswg-drafts/issues/11211#issuecomment-2842523956) resolved on fixing up [`linear()` ](https://drafts.csswg.org/css-easing-2/#funcdef-linear)control points at used value time, like [gradient color stops](https://drafts.csswg.org/css-images-3/#color-stop-fixup). This blocks the simplification of [`calc-interpolate()`](https://drafts.csswg.org/css-values-5/#funcdef-calc-interpolate) at parse time, even when the `linear()` control points are all declared with absolute values (i.e. `<number>`s and `<percentage>`s resolving to a `<number>`).

The simplification of `calc-interpolate()` at parse time is also not possible with other subtypes of [`<easing-function>`](https://drafts.csswg.org/css-easing-2/#typedef-easing-function) (`cubic()` and `steps()`) when they take a numeric function resolving at computed value time or later, like `sibling-index()` or `calc(1em / 20px)`.

Therefore I would like the conditions for simplifying `calc-interpolate()` at parse time to be clarified:

  1. if it takes no `<easing-function>`
  2. if it takes no `<easing-function>` that is `linear()` or that takes a numeric function resolved at computed value time or later
  3. if it takes no `<easing-function>` that takes a numeric function resolved at computed value time or later
  4. if it takes no `<easing-function>` applying to `<progress-value>` or the interpolation progress of the segment containing `<progress-value>`

(3) implies fixing up `linear()` at parse time.

<sup>(edit) Added a 4th, more granular option.</sup>
