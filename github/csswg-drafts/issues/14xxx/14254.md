We are using mixes of `currentColor` and `transparent` to indicate various form control states. However, the coloration is based on using `border-color: currentColor` as the default state, whereas our survey of design systems showed that common authoring practices tend to use more muted shades of gray rather than black or undiluted currentColor.

To bring the [default style sheet](https://drafts.csswg.org/css-forms-1/#basic-appearance-stylesheet) in line with existing practices, we suggest the following adjustments:

* **Lighten Borders -** Make the default border color on inputs 50% instead of 100% (opaque), to avoid competing with the text for attention. _(This issue.)_
* **Improve Disabled Contrast** _(See [#14496](#14496).)_
    * Adjust the `:disabled` color by increasing from 50% to 55% (improve contrast).
    * And adjust the corresponding `:disabled` border-color (currently 50%) to 25%, matching default reduction to 50%.
* **Make interaction effects more subtle:** _(See [#14496](#14496).)_
    * **Hover** - Use border color at 100% as the `:hover` effect, instead of using a background color. This is a more subtle effect, which fits better with a UA default stylesheet, and avoids messing with text contrast.
    * **Active** Use an 8% background as the `:active` effect, as 20% seems too strong; and apply it to `select` as well as `button` etc.
    * **Communicate Invalid State** - We also suggest adopting a red border-color to indicate `:user-invalid`.
* **Better hint at interactiveness in Dark Mode** - Adopt a subtle bit of background shading in dark modes, to make the inputs look more input-y. _(See [#14461](https://github.com/w3c/csswg-drafts/issues/14461).)_

We're open to other tunings or suggestions, but this is what we came up by merging findings from a survey of design systems with the existing decisions about UA styles.

```
select, input, textarea {
	border: 1px solid color-mix(currentColor 50%, transparent);   /* previously 100% */
}
:is(select, input, textarea):hover {
	border-color: color-mix(currentColor 70%, transparent);       /* previously used background-color */
}
:is(select, input, textarea):active {
	background-color: color-mix(currentColor 8%, transparent);    /* previously 20% */
}
:is(select, input, textarea):user-invalid {
    border-color: light-dark(#db2a37, oklch(from #db2a37 calc(l + 0.17) c h));    /* new */
}
:is(select, input, textarea):disabled { /* Overrides all interactivity styles from above */
	color: color-mix(currentColor 55%, transparent);              /* previously 50% */
	border-color: color-mix(currentColor 25%, transparent);       /* previously 50% */
	background-color: color-mix(currentColor 6%, transparent);    /* previously transparent */
}
```

Note: High/low/custom contrast modes are handled in https://github.com/w3c/csswg-drafts/issues/14318.

## @fantasai — 2026-08-12

@Psychpsyo If the author sets the border color to _literally anything_, it'll override this effect. This is because author rules absolutely override UA rules, regardless of specificity.

(Note this also means that if the author sets any border/background/color rules, they'll have to set their own :focus/:active/:disabled colors, too, because they've now blown those UA rules away also.)

Having these rules in the UA stylesheet just makes it work nicely by default.

## @stubbornella — 2026-09-09

I did a survey of design systems to see how they treat border colors relative to their text colors. 

Only one system (gov.uk) uses the same color for text and borders. They manage to make really dark borders work on forms by having very short forms with one question per page so the user isn't looking at a long list of very loud form controls. All other systems lighten the border compared to the text, most by a lot. 

**Mean ΔL 0.516, median 0.584** so the proposed values are right in that range.

## @lukewarlow — 2026-09-24

To clarify something that some people seemed a bit confused by, author styles don't necessarily clobber in forced colors mode because of how forced colors mode works. They unfortunately would clobber for increased contrast mode but that's probably fine, just a matter of documenting better.

> media (forced-colors: none) and (prefers-contrast: no-preference)
> maybe we should specify the original style as currentcolor and then have prefers-contrast: less

Also fwiw prefers-contrast:less is essentially meaningless outside of very specific Contrast Themes on Windows (which enable forced colors mode anyway). It's not offered as a standalone preference anywhere today.

I think I'm okay with this resolution (though a value higher than 50% would make me feel more comfortable). I think seeing it prototyped will make it easier to evaluate all these styles together. I'm worried that the loss of contrast is going to be problematic. Already people commented on socials regarding lower contrast for optgroup titles in the Select styles than were shared.

## @lukewarlow — 2026-09-24

It's worth being aware that while bumping contrast for the users that have declared a preference for increased contrast is good. Not all users have that ability, it was only quite recently (maybe even Android 16?) that Android actually added an explicit contrast preference.

Some Linux distros have a setting, some don't.

Windows also doesn't have the ability to signal a preference for increased contrast as a standalone option, your only real choice are contrast themes which set forced colors mode which are quite heavy handed.

iOS and macOS thankfully do offer settings for this.

On top of the mixed bag of OS settings, to my knowledge no browser offers a browser level override for this setting.

So there will be users who benefit from increased contrast who might simply not be able to signal it.
