[Style features](https://drafts.csswg.org/css-conditional-5/#typedef-style-feature-plain) use a `<declaration-value>` after the colon. Read literally, the [free-form function-argument rules](https://drafts.csswg.org/css-values-5/#free-form-productions) appear to apply to that value inside `style()`, restricting top-level commas and removing an initial brace wrapper. I cannot find an explicit exception for style queries.

However, the [style-feature prose](https://drafts.csswg.org/css-conditional-5/#style-container) also describes the syntax as that of a valid declaration. That suggests preserving commas and braces as part of the declaration value, which is what browsers do:

```html
<style>
  #container { --x: {a,b}; }
  #target { color: blue; }
  @container style(--x: {a,b}) {
    #target { color: red; }
  }
</style>
<div id="container"><div id="target">Example</div></div>
```

Chromium, Firefox, and WebKit match this query and produce red. They also match `a,b` against `a,b`, and `{a}` against `{a}`, but do not match `a` against `{a}`. Braces are part of the value, not merely argument framing.

Please clarify this conflict by explicitly exempting plain style-query declaration values from the comma restriction and brace stripping, while retaining the ordinary grammar of nested functions. Merely making the value a non-strict free-form production would still strip its braces.
