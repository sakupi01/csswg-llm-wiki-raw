The Env spec now defines [custom environment variables](https://drafts.csswg.org/css-env/#custom-environment-variable), denoting something that authors can set and expose via `env(--foo)`. This is currently used solely by [Linked Parameters](https://drafts.csswg.org/css-link-params/) - the passed-in params are exposed to the embedded document as custom envs.

However, I don't have any details in the Env spec about how those values are *processed*. I think there's only one possible option: they're treated like untyped custom properties and left completely unresolved, except that we look for arbitrary-substitution functions and force them to fail substitution.[^1]

[^1]: This isn't something that can happen with the CSS ways to pass in a param, as they'll substitute on the element passing in the parameters already, but passing a link-param in the URL can, as will any future ability to set envs in JS. If CSS can't do it, we shouldn't let these other channels smuggle in some functionality.

Other rejected possibilities:
* resolving against the root element: obviously unworkable, as env() is meant to be globally usable, but this would allow values to be cyclic.
* resolving against a "global" context, like MQs: can only resolve a few types of values, and generally needs to know what *type* the value is beforehand. Also, removes some potentially useful ability to pass in relative values that are *intended* to resolve against the actual usage site, like colors or ems.

Just double-checking that there's no secret fourth option I'm missing, before I add this behavior to the spec.

## @tabatkins — 2026-09-10

Okay, I've defined a behavior in [Link Params](https://drafts.csswg.org/css-link-params-1/#param) - if the param() has an element context (which it does in 'link-parameters', in 'url()', and in a URL if it's in a URL attribute on an element), it fully resolves the value *before* passing it into the linked resource. The env() then just substitutes as what it got.

If you *don't* have an element context (such as if you navigated straight to the image's URL in the address bar), those param()s don't define a link parameter, and are ignored. No env() exists in this case (unless the author supplied a fallback by repeating the param() with a different value). It's okay to use param()s that don't *need* an element context to resolve; they'll work in all cases.

I think this suffices to address the issue. If/when we define a JS interface for custom env(), we'll do the same thing - you *can* supply an element context to resolve the value at the time of registration, and if not it'll just be an invalid registration if it needs an element context.
