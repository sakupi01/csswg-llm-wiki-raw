## @hiikezoe — 2026-11-11

So in a background tab, Firefox will lose rendering opportunity in about 10 or 20 minus, and IIUC Chrome will lose the opportunity soon after the document gets in a background tab. 

While the UA doesn't have the rendering opportunity, the UA has no chance to dispatch queued animation events since dispatching the queued animation is basically done as a rendering task source which is processed only if there's a rendering opportunity.

In the meantime, animation events can be enqueued, from [4.5.12. Updating the finished state](https://drafts.csswg.org/web-animations-1/#updating-the-finished-state):

> 7. If animation has a [document for timing](https://drafts.csswg.org/web-animations-1/#animation-document-for-timing), then append finishEvent to its document for timing’s [pending animation event queue](https://drafts.csswg.org/web-animations-1/#pending-animation-event-queue) along with its target, animation. For the [scheduled event time](https://drafts.csswg.org/web-animations-1/#scheduled-event-time), use the result of [converting](https://drafts.csswg.org/web-animations-1/#animation-time-to-origin-relative-time) animation’s [associated effect end](https://drafts.csswg.org/web-animations-1/#associated-effect-end) to an origin-relative time.
>
> Otherwise, [queue a task](https://html.spec.whatwg.org/multipage/webappapis.html#queue-a-task) to [dispatch](https://dom.spec.whatwg.org/#concept-event-dispatch) finishEvent at animation. The task source for this task is the [DOM manipulation task source](https://html.spec.whatwg.org/multipage/webappapis.html#dom-manipulation-task-source).

So even if there's no rendering opportunity, if there's a document for timing, animation events are appended to the pending animation event queue, which will never be dispatched until a new rendering opportunity comes.

What I can propose is that, even if the animation has a document for timing but if the document is hidden state, then use the DOM manipulation task source as if there's no document for timing, since as least on Firefox once after the document has lost the rendering opportunity in a background tab, the document timeline is never advanced until the document gets active in a foreground tab.
