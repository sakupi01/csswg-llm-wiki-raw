The new requestResize() API causes a synchronous layout instead of allowing the browser's normal rendering pipeline to report the changes which is bad for performance. Unrelated components will call the API causing multiple repeated layouts, and it's likely the value will be wrong if any mutations happen afterwards. 

The API should instead be using the ResizeObserver timing to report the values to the parent document. That will have the same effect but means repeated calls to requestResize() don't cause forced layouts. 

Note: I'm not suggesting using an actual RO, just that the method should be marking the frame for an update not causing it synchronously.

## @kojiishi — 2026-10-28

Thanks @esprehn, that makes sense.

Discussing with @bfgeek, we think we should do this not only for `requestResize()` but also for event-based resizing as well.

The [ICB locking] makes it a little complicated though.

If the current ICB size is different from the locked ICB size, doing it after layout (RO timing) makes the layout 3 times; the normal one, locked ICB to measure the natural size, and then after ICB size is restored. If we do before style/layout, it can be done by two layouts; one for locked ICB and one standard. It's a bit different from RO timing though.

Does this make sense?

[ICB locking]: https://drafts.csswg.org/css-sizing-4/#locked-embedded-icb-size

## @esprehn — 2026-10-30

I'm not sure I understand the reason for the ICB locking here, but I do think adding new offsetTop like APIs instead of either rAF (frame start) or RO timing (frame end) is a mistake. 

Any side effects inside RO or rAF callbacks can change the size which would invalidate the values reported from requestResize(). I'm not sure I understand the use cass you picture but in a web app using frameworks I think the only correct time to call requestResize() is very late in the pipeline probably after rAF has run when user code has finished modifying the document. In those cases people are going to call requestResize() repeatedly to correctly flush the size which means many more layouts than what you're describing. 3 passes is better than 10 which is what I see happening with APIs like this. 

If you had to though I suppose you could do the flush at the start of the frame before rAF instead of RO timing to avoid that extra pass you're talking about, but that has the same error issue with rAF based mutations in user code. 

I think the only correct time to do this is after rAF when user code has finished modifying the DOM.
