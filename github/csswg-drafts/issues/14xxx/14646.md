The new requestResize() API causes a synchronous layout instead of allowing the browser's normal rendering pipeline to report the changes which is bad for performance. Unrelated components will call the API causing multiple repeated layouts, and it's likely the value will be wrong if any mutations happen afterwards. 

The API should instead be using the ResizeObserver timing to report the values to the parent document. That will have the same effect but means repeated calls to requestResize() don't cause forced layouts. 

Note: I'm not suggesting using an actual RO, just that the method should be marking the frame for an update not causing it synchronously.

## @kojiishi — 2026-10-28

Thanks @esprehn, that makes sense.

The [ICB locking] makes it a little complicated though. If the current ICB size is the same as locked ICB size, we can avoid synchronous layout by deferring it after layout clean.

If the current ICB size is different from the locked ICB size, doing it after layout makes the layout 3 times; the normal one, locked ICB to measure the natural size, and then after ICB size is restored. If we do before style/layout, it can be done by two layouts; one synchronous for locked ICB and one normal.

Does this make sense?

[ICB locking]: https://drafts.csswg.org/css-sizing-4/#locked-embedded-icb-size
