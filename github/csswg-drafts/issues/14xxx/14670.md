The [locked embedded ICB size](https://drafts.csswg.org/css-sizing-4/#locked-embedded-icb-size) was introduced to reduce the chance of layout loops, as described in the following NOTE of the spec:

> This freezing of the ICB reduces the chance of layout loops (an iframe document sizing to slightly larger than its ICB, then the parent iframe changing size to match, and the next layout again making it slightly larger than the ICB, etc to infinity).

We've received feedback that this locked ICB leads to unexpected behavior when an iframe is externally resized: https://issues.chromium.org/issues/565383556

To solve this, we propose locking only the responsive axis. This allows iframes to be externally resized on one axis while allowing the content to be automatically sized on the responsive axis, without introducing any new chances for layout loops.

For example:

```css
iframe.target {
  frame-sizing: content-height;
}
```

and let's say:
1. The ICB of the iframe content's initial layout was 300x150.
2. The iframe content is laid out to 300x400, and the iframe is resized to fit.
3. The parent doc resizes the iframe to 600x400.

Currently, the iframe content computes its natural size by using 300x150 ICB size. Since the width isn't the responsive axis in this case, this proposal changes it to using 600x150.

## @bramus — 2026-11-03

+1 to this change, as this solves the main feedback we have received from authors about this. See this demo by @jakearchibald for example: https://random-stuff.jakearchibald.com/responsive-iframe/ _([video](https://bsky.app/profile/jakearchibald.com/post/3mxyst7mvx22s))_

With this proposed fix _(available in Chrome 158.0.8126.0 or newer)_, the demo now works as expected: when resizing the browser horizontall _(and thereby also resizing the iframe’s `width` in response)_, the iframe’s “responsive height” now gets computed with respect to the new ICB width as that axis did not get locked.
