The original, and primary, purpose of `word-break: keep-all` was to provide Korean with word-based breaking at spaces. However the spec prose is overly specific, indicating that the only difference with `normal` is that Hangul is treated like Latin. This doesn't correctly handle combinations with punctuation, for example the following break unnaturally in Gecko and Blink:

| Text | Disallowed break | UAX14 pair |
|---|---|---|
| `표(일반석)는` | `표 ❌ (일반석) ❌ 는` | H ÷ OP, CP ÷ H |
| `“안녕하세요”라고` | `“안녕하세요” ❌ 라고` | Pf ÷ H (LB19a, East Asian context) |
| `『토지』를` / `《경향신문》에` | `『토지』 ❌ 를` / `《경향신문》 ❌ 에` | CL ÷ H |
| `50%가` | `50% ❌ 가` | PO ÷ H |
| `글쎄…라고` | `글쎄… ❌ 라고` | IN ÷ H |
| `서울/부산행` | `서울/ ❌ 부산행` | SY ÷ H |

We need to do something more comprehensive than what we've specified so far. At minimum, it seems we need to:

- Reclassify ID and Hangul as AL generally, not only in combination with other alphanumerics.
- Treat wide brackets and quotations the same as narrow ones.
- Disallow breaks at slashes, and likely some other characters.
- Continue allowing breaks at wide comma, period, colon, semicolon?

WebKit has had a dumb implementation of only breaking at spaces (until some recent changes broken things anyway), so we should have some room to maneuver here, Web-compat-wise.

## @xfq — 2026-10-21

Indeed, Korean is an agglutinative language. Particles are often attached directly to the nouns that precede them. Even when the preceding term includes quotation marks, parentheses, or a percent sign, the attached particle remains grammatically inseparable from that term, so they are a single, indivisible unit, and the line should not be broken. I agree with @fantasai.

<!-- comment id=6415664943 author=fantasai created=2026-10-26T12:10:47Z url=https://github.com/w3c/csswg-drafts/issues/14627#issuecomment-6415664943 -->
## @fantasai — 2026-10-26

I think two of the tailorings we need to accommodate Korean are:
- Tailor Hangul to AL.
- Tailor either all of [CL](https://util.unicode.org/UnicodeJsps/list-unicodeset.jsp?a=%5B%3Aline_break%3DCL%3A%5D&g=&i=), or only the [Pe](https://util.unicode.org/UnicodeJsps/list-unicodeset.jsp?a=%5B%3Ageneral_category%3DPe%3A%5D&g=&i=) (closing punctuation) [subset](https://util.unicode.org/UnicodeJsps/list-unicodeset.jsp?a=%5B%3Aline_break%3DCL%3A%5D%26%5B%3Ageneral_category%3DPe%3A%5D&g=&i= of CL, to CP.

But I think we also need to consider whether `keep-all` should admit _any_ breaks other than at word separator characters (like spaces). For example, should it allow breaks at [ideographic commas](https://util.unicode.org/UnicodeJsps/character.jsp?a=3001) or sentence-ending punctuation?

## @xfq — 2026-10-28

[LB30](https://www.unicode.org/reports/tr14/#LB30) explicitly excludes East Asian width opening and closing punctuation from its ordinary alphabetic-parenthesis no-break behavior:

```
(AL | HL | NU) × [OP-$EastAsian]
[CP-$EastAsian] × (AL | HL | NU)
```

So changing a fullwidth closing bracket from CL to CP would not, by itself, guarantee that `『토지』를` stays together.

So maybe we should specify the desired Korean line-breaking behavior, rather than just do a few Unicode class substitutions.

About whether `keep-all` should allow breaks at punctuation, I'd like to hear more thoughts from Korean typography experts.
