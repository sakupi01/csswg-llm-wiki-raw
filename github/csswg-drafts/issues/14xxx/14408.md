https://drafts.csswg.org/css-mixins-1/#private

> Applying a mixin with `@apply` effectively substitutes the mixin in-place, so a mixin sees any private properties visible to the style rule it’s substituted into (if it doesn’t override them with its own mixin parameters or private properties).

This seems weird to me. It kinda breaks the entire premise of `@private` making things private.
I can easily imagine cases where authors use both `@private` and `@mixin` but not in a coordinated fashion and expect custom props to be isolated from each other.

What is the motivation for the current spec?

## @sorvell — 2026-09-02

This also initially struck me as really weird and wrong, but I think I'm coming around to it maybe being ok [1].

If you are not using a param or private var, then all bets are off, the value could be unset, a global, an enclosing private.

I do think it's problematic if a `@private` overrides the calling scope via an `@apply`. I think maybe the spec handles that via this but it's not clear to me:

> Two [private properties](https://drafts.csswg.org/css-mixins-1/#private-property) with the same name are considered the same property if and only if they have the same nearest [style rule](https://drafts.csswg.org/css-syntax-3/#style-rule) ancestor that has their name in its [private property names](https://drafts.csswg.org/css-mixins-1/#private-property-names).

But clearly (?) the following must be avoided:

```css
@mixin --a() {
  @private { --foo: 10px; }
  padding: var(--foo);
}

div { 
  @private { --foo: 2px; }
  @apply --a();
  margin: var(--foo); /* this must be 2px, not 10px */
}
```

Note, I think the previous model with `@result` also had this kind of "spooky action at a distance" behavior. For example:

```css
@mixin --sub() {
  @result {
    background: var(--bg);
    color: var(--color);
  }
}
@mixin --mix(--bg: blue) {
  --color: var(--bg);
  @result {
    @apply --sub();
  }
}
div { @apply --mix(); /* background: blue; color: blue */
```

[1] Note, it's a little hard to follow the evolution of this feature so I hope this feedback isn't off.

## @romainmenke — 2026-09-02

I might also be coming around to it :)
At least if mixins apply as if they are in their own style rule.

So 

```css
div { 
  @apply --a();
}
```

acts somewhat similar to

```css
div { 
  & { @apply --a() }
}
```

This would make private properties visible to the mixin without allowing the mixin to bleed into the private properties of the rule it is being substituted in.

I agree that this example should result in a margin of `2px`

```css
@mixin --a() {
  @private { --foo: 10px; }
  padding: var(--foo);
}

div { 
  @private { --foo: 2px; }
  @apply --a();
  margin: var(--foo); /* this must be 2px, not 10px */
}
```

I think this is fine:

```css
@mixin --a() {
  padding: var(--foo); /* padding is 2px */
}

div { 
  @private { --foo: 2px; }
  @apply --a();
}
```
