After considering sequential navigation with the _tab key_, the [introduction to the Spatial Navigation module](https://drafts.csswg.org/css-spatial-nav-1/#intro) claims:

> While arrow keys are naturally suited to control spatial navigation, no previous specification describes how that should work, or how it may be controlled. 

Actually, the [`nav-…` properties for _directional focus navigation_](https://drafts.csswg.org/css-ui-4/#nav-dir) in CSS UI add *explicit targets* to d-pad buttons or arrow keys. CSS Spatial Navigation should reference those!

These properties traditionally accept `<id>`, i.e. a local URL in the host document, as their value (and an optional target frame name); I have proposed to let them use CSS-defined anchors instead. #13166

~~~~ ebnf
nav-[up|down|right|left]: auto 
   | <id> [ current | root | <target-name> ]?
~~~~

It may be helpful to **add a `nav-tab` property** – I’m proposing many additional ones in #14414 –, **`nav`** and `nav-arrows` or `nav-directions` **shorthand** properties, and keyword values to select between `physical` = **`visual`** (i.e. the default for existing properties) and **`sequential`** (default for tabbing) navigation.

It absolutely makes sense to add more author control over `nav-…: auto` behavior, and that is what [css-spatial-nav](https://drafts.csswg.org/css-spatial-nav/#declarative) does with its three properties:

~~~~ ebnf
spatial-navigation-contain: auto | contain;
spatial-navigation-action: auto | focus | scroll;
spatial-navigation-function: normal | grid;
~~~~

There is no **`spatial-navigation` shorthand** yet, perhaps there should be. Alas, all of these declarative means to control spatial navigation in CSS are marked at risk for Level 1, except for `…-action: auto | focus`.

Apparently, `…-function` has a similar purpose to the `visual` / `sequential` distinction I suggested for `nav-*` above, but the former changes the spatial navigation behavior of an *element / box / container* and the latter changes the behavior of a *key / button / gesture* when the selected element has navigation focus (without the need for `:focus`). 

To make this more obvious and to prepare for the properties proposed in #14414, the **keyword `spatial`** would select automatically between `sequential` and `visual`. Furthermore, the latter would compute to **`upward`, `downward`, `rightward` and `leftward`** for the properties `nav-up`, `nav-down`, `nav-right` and `nav-left`, respectively, and to **`forward`** for `nav-tab` (implying **`backward`** for \*`nav-tab-shift` or so).

If `sequential` was set for one of the four directional `nav-` properties or their new collective shorthand, they would probably compute to `forward` for both `nav-down` and `nav-right`, and to `backward` for both `nav-up` and `nav-left`, at least in a top-to-bottom, left-to-right environment. 

Another useful `nav` behavior would be **`logical`**, which would differ from `sequential` in that `nav-up` computes to **`outward`** and `nav-down` to **`inward`**, whereas yet another keyword `hierarchical` could use this as well but also make `nav-left` switch to a *higher level* and `nav-right` to a *deeper* one. 

Likewise, as special cases of `visual`, additional values **`vertical`** and **`horizontal`** would also unify left with up, and right with down keys.

To reiterate, only the keys and buttons whose respective `nav-…` properties compute to `upward`, `downward`, `leftward` or `rightward` would be available for _spatial_ navigation and were therefore affected by the `spatial-navigation-…` properties. 

Importantly, the tab key would not be affected by them either, because it defaults to `sequential` navigation, but it can be set explicitly to `spatial` navigation when needed. It then computes to `rightward` in LTR contexts and to `leftward` in RTL contexts, unless set to a specific value.

Whether it would be smart to revive the `nav-index` property, matching the `tabindex` attribute or not, for sequential navigation would be the topic of another issue.
