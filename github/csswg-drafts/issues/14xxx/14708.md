The prose of [3.2](https://drafts.csswg.org/css-anchor-position-1/#anchor-pos) allows `anchor()` "as a value in its [inset properties](https://drafts.csswg.org/css-logical-1/#inset-properties)", and that term covers `top`/`left`/`bottom`/`right`, their flow-relative longhands `inset-block-start`, `inset-block-end`, `inset-inline-start`, `inset-inline-end`, and the `inset-block`, `inset-inline` and `inset` shorthands. The property table right below it extends only the four physical ones:

> Name: top, left, right, bottom
> New values: `<anchor()>`

The same holds for `anchor-size()` in [5.1](https://drafts.csswg.org/css-anchor-position-1/#anchor-size-fn): the prose allows it in the [accepted @position-try properties](https://drafts.csswg.org/css-anchor-position-1/#accepted-position-try-properties), which include all the inset properties, but the table's Name row lists `top, left, right, bottom` and no flow-relative inset.

The logical margins don't have this problem, since `margin-inline-start` is defined as `<'margin-top'>` and picks up `anchor-size()` through it. The logical insets are defined in css-position-3 as `auto | <length-percentage>` on their own, so nothing in the tables reaches them.

Tooling that reads the tables gets a grammar where the shorthand accepts `anchor()` and its own longhand doesn't. I hit this generating parsers from `@webref/css`, which extracts the tables as written.

### Steps to reproduce

1. Open https://drafts.csswg.org/css-anchor-position-1/#anchor-pos and read the property table under the first paragraph, then the one in https://drafts.csswg.org/css-anchor-position-1/#anchor-size-fn.
2. Follow the "inset properties" link in the first paragraph of 3.2 to https://drafts.csswg.org/css-logical-1/#inset-properties.
3. To see what a consumer of the extracted data reads, run the gist https://gist.github.com/YevheniiKotyrlo/f2c7e8c353b3f8f4ef387567ab11bd7f, which prints both tables' Name rows from the live draft and the extracted syntax of four inset properties:

```
git clone https://gist.github.com/f2c7e8c353b3f8f4ef387567ab11bd7f.git anchor-logical-insets
cd anchor-logical-insets
npm install
node check.mjs
```

**Expected:** both tables name every inset property, so `inset-inline-start` gets the same value grammar as `top`: `auto | <length-percentage> | <anchor()> | <anchor-size()>`.

**Actual:** both tables name only the physical insets, and the extracted grammar follows them:

```
css-anchor-position-1 Editor's Draft, revision 2cc20d2a6468b710f240c26288bec8465748107e
  #anchor-pos table, Name: top, left, right, bottom
  #anchor-size-fn table, Name: block-size, inline-size, width, height, min-block-size, min-inline-size, min-width, min-height, max-block-size, max-inline-size, max-width, max-height, top, left, right, bottom, margin-top, margin-left, margin-right, margin-bottom

@webref/css 8.7.8
  top                 auto | <length-percentage> | <anchor()> | <anchor-size()>
  inset-inline        <'top'>{1,2}
  inset-inline-start  auto | <length-percentage>
  inset-block-start   auto | <length-percentage>
```

Implementations and WPT already follow the prose. [anchor-parse-valid.html](https://github.com/web-platform-tests/wpt/blob/master/css/css-anchor-position/anchor-parse-valid.html) and [anchor-size-parse-valid.html](https://github.com/web-platform-tests/wpt/blob/master/css/css-anchor-position/anchor-size-parse-valid.html) test the flow-relative longhands, and `CSS.supports('inset-inline-start', 'anchor(--a start)')` and `CSS.supports('inset-inline-start', 'anchor-size(--a width)')` both return `true` in Chromium 156, Firefox 157 and WebKit 27.2 (Playwright builds, Windows 11).

### Suggested fix

Add `inset-block-start, inset-block-end, inset-inline-start, inset-inline-end` to the Name row of both tables.
