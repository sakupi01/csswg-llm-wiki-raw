## Summary

The current behavior of `scrollbar-gutter: stable` does not match the intuitive meaning of "stable" from a web layout perspective.

When the operating system dynamically switches between classic scrollbars and overlay scrollbars, the layout viewport width changes even though `scrollbar-gutter: stable` remains applied.

This can cause unexpected layout shifts during normal user interaction, for example when connecting or disconnecting a mouse on macOS.

## Steps to reproduce

1. Use macOS with the default scrollbar behavior:

   * "Show scroll bars: Automatically based on mouse or trackpad"

2. Create a page with:

```css
html {
    scrollbar-gutter: stable;
}
```

3. Observe the viewport dimensions:

```js
console.log({
    innerWidth,
    clientWidth: document.documentElement.clientWidth,
    scrollbarWidth: innerWidth - document.documentElement.clientWidth
});
```

4. With an external mouse connected:

```
innerWidth: 1680
clientWidth: 1665
scrollbarWidth: 15
```

5. Disconnect the mouse and use only the trackpad.

The viewport is recalculated:

```
innerWidth: 1680
clientWidth: 1680
scrollbarWidth: 0
```

The layout expands by the scrollbar width.

This behavior is reproducible in:

* Safari
* Chrome
* Firefox

## Expected behavior

`scrollbar-gutter: stable` should provide a stable layout area regardless of whether the platform uses classic or overlay scrollbars.

In particular, once a page opts into `scrollbar-gutter: stable`, authors should be able to rely on the layout not changing when the OS changes scrollbar presentation.

The current behavior makes it impossible to prevent layout shifts caused by OS-level scrollbar mode changes.

## Actual behavior

The gutter is only reserved while the platform exposes classic scrollbars.

When macOS switches to overlay scrollbars:

* the gutter disappears;
* `document.documentElement.clientWidth` changes;
* all layout depending on viewport width changes.

The computed style remains:

```js
getComputedStyle(document.documentElement).scrollbarGutter
// "stable"
```

but the visual/layout behavior is no longer stable.

## Why this is problematic

The name `stable` suggests that the layout geometry is stable, not merely stable while a specific scrollbar implementation is active.

This creates several issues:

* Responsive layouts can unexpectedly shift when users connect/disconnect input devices.
* Centered layouts can move horizontally.
* Aligning icons between scrollable and non-scrollable sections is also tricky 
* Elements sized relative to the viewport (`vw`, viewport-based calculations, etc.) can change size.
* Applications cannot opt into a consistent layout behavior.

This is especially noticeable on macOS where scrollbar style can change dynamically depending on whether a mouse or trackpad is used.

## Possible resolutions

A few possible directions:

1. Clarify that `stable` only guarantees stability for classic scrollbars and rename/document this behavior more explicitly.

2. **Better**: Introduce a way for authors to request a persistent gutter even when overlay scrollbars are used.

For example, a potential new value could behave like:

```css
scrollbar-gutter: always;
```

meaning:

> Always reserve scrollbar gutter space, regardless of the platform scrollbar mode.

3. Alternatively, consider whether `scrollbar-gutter: stable` should reserve space based on the maximum possible scrollbar width instead of depending on the current platform scrollbar mode.

## Additional information

The issue is not browser-specific:

* Safari
* Chrome
* Firefox

all exhibit the same behavior on macOS.

The issue appears to be related to how the specification defines "stable" in relation to classic vs overlay scrollbars.
