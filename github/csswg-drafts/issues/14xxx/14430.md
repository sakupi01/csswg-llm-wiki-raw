The "evaluate container queries and report changes" step is anchored "after style and layout have been updated and post-layout state has been snapshotted". whatwg/html#11613 places those snapshot steps inside the ResizeObserver loop, and Chromium implemented it that way, so the step runs after each layout pass within one rendering update.

With that, [Element.matchContainer()](https://github.com/w3c/csswg-drafts/pull/13551) has a potential infinite-loop problem.

If we modify the container in the handler, it can create an infinite loop and hang the renderer.

For example:
```html
<div id="container" style="container-type: inline-size; width: 200px">
  <div id="target"></div>
</div>
<script>
  const list = target.matchContainer("(width > 100px)");
  list.onchange = () => container.style.width = list.matches ? "50px" : "200px";

  requestAnimationFrame(() =>
      requestAnimationFrame(() => container.style.width = "50px"));
</script>
```

ResizeObserver had the same issue, which was resolved by [introducing depth-limit algorithm](https://github.com/WICG/resize-observer/issues/7).

Should matchContainer adopt the same algorithm?

Since a container query always evaluates from an ancestor of the querying element, the depth-limit approach seems like a good fit. 

For now, Chromium implementation part [limits these step to at most once per lifecycle update](https://chromium-review.googlesource.com/c/chromium/src/+/8260311/16/third_party/blink/renderer/core/frame/local_frame_view.cc#2616).  I'll update it once this is decided.
