Consider this:
`a::link::selection { color: red; }`

Should both the unvisited and visited selection color be red? Currently there is a WPT testing that the `::visited` selection color is the default is this case, and only the `::unvisited` color is red. Chromium browsers pass this test. The other browsers seem to make other choices about what to do for these tests, and nobody agrees.

https://wpt.fyi/results/css/css-pseudo/selection-link-001.html?label=master&label=experimental&aligned
https://wpt.fyi/results/css/css-pseudo/selection-link-002.html?label=master&label=experimental&aligned
https://wpt.fyi/results/css/css-pseudo/selection-link-003.html?label=master&label=experimental&aligned

Chrome security AI thinks this is a problem because the visited behavior can be detected, which is a bit if the stretch. However, personally I feel that if `::visited` and `::unvisited` are not explicitly provided, the ::link::selection style should apply to both visited and unvisited. We can fix compat too.

I would expect `::visited::selection` to style only visited and take precedence for visited.
Same with `::unvisited::selection` styling only unvisited and take precedence for unvisited.
Either falls back to `::link` if available.
Then falls back to UA default.

Any objections? Maybe we can async resolve this one.

As an aside, why do we have ::link at all?

## @schenney-chromium — 2026-09-02

The timing attack is a concern now that I think about it some more, because Chrome at least takes a different, more expensive rendering path for `::selection` rendering particularly if it has underlines or something like that.

My concrete proposal is that we do not support `::visited::selection` or `::unvisited::selection` and `::link::selection` uses the same style regardless of visited status, which eliminates the timing attacks for detecting visited status.
