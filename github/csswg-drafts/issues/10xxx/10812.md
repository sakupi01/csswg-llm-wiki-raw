https://drafts.csswg.org/css-images-3/#typedef-radial-size

```
<radial-size> = <radial-extent> | <length [0,∞]> | <length-percentage [0,∞]>{2}
```

This syntax does not allow this:

```css
clip-path: ellipse(closest-side closest-side at 5rem 6rem);
```

Despite that being the implemented feature: https://codepen.io/romainmenke/pen/PordyZx


I think this was a regression in https://github.com/w3c/csswg-drafts/pull/9723

Grouping it seems to resolve the issue:

```
<radial-size> = [ <radial-extent> | <length [0,∞]> | <length-percentage [0,∞]> ]{2}
```

But I am not that familiar with the feature, so my suggestion might be incorrect.

## @cdoublev — 2024-09-03

I closed #9730 in favor of this issue, to rephrase my questions about the `<radial-size>` extension in CSS Images 4.

As noted in the comments above, it would be great if the restriction to a single component value for `circle()` and a `circle` gradient shape could be hardcoded into the syntax.

Before this extension:

  - `circle()` could be specified with one `<radial-extent>` (restricted to `*-side`) or `<length-percentage>`
  - a `circle` gradient shape could be specified with one `<radial-extent>` or `<length>`
  - `ellipse()` could be specified with two `<radial-extent>`s (restricted to `*-side`) or `<length-percentage>`s
  - a `ellipse` gradient shape could be specified with one `<radial-extent>` or two `<length-percentage>`s

Now:

  - `circle()` and `circle` gradient shape can be specified with one `<radial-extent>` or `<length-percentage>`
  - `ellipse()` and `ellipse` gradient shape can be specified with one or two `<radial-extent>`s or `<lenth-percentage>`s (possibly mixed, cf. #9729)

Now for `ellipse()` and `ellipse` gradient shape, reading #824, it is not clear whether accepting a single component value was intentional, what the default value (if any) of the second component value and the shortest serialization should be when omitted.

I suspect it should default to the first component value, except when the first is `*-corner`.

Since a single `<length>` (or `<percentage>`, presumably) indicates a `circle` gradient shape, how would you serialize `ellipse 1px` or `ellipse 1px 1px`:

  1. `ellipse 1px`
  2. `1px 1px`

Or maybe it is fine to serialize `1px`? Would it mean that `ellipse(1px)` should serialize as `circle(1px)`?

Hi @romainmenke @cdoublev, the main question was how to handle two independent <radial-extent> keywords in ellipse(), like:

[clip-path: ellipse(farthest-corner closest-corner at 175px 100px);](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/web_tests/external/wpt/css/css-masking/clip-path/clip-path-ellipse-closest-farthest-corner.html;l=19)

Chromium and WebKit parsers accept <shape-radius>{2}, where each radius resolves independently to the euclidean corner distance - no aspect ratio preservation. The above WPT test also uses this form.

My [CL](https://chromium-review.googlesource.com/c/chromium/src/+/7754379) implemented this based on the current parser behavior to make the WPT test pass, so I hadn't thought deeply about the spec's intent. But looking at the resulting ellipse, to me the current behavior doesn't seem to have a clear geometric meaning - the ellipse doesn't pass through any corner.

If we want an ellipse that passes through the specified corner and fits the box shape naturally, I feel updating the parser and the WPT test to match the spec could be a reasonable direction.

## @tabatkins — 2026-09-17

All right, I was asked to provide explictly what the suggested grammar changes would be. I think, first, a bit of history would be helpful, as Images and Shapes have been historically tangled together in this regard and the current state of both specs and impls is confusing if you don't know the order things happened in.

1. Images defined `radial-gradient()` first. Circles could use a single side/corner keyword, or a single length (no %, as it wasn't clear what to resolve it against). Ellipses could use a single side/corner keyword (aspect ratio taken from the reference box), or two length-percentages (resolving %s against width/height).
2. Shapes then defined `circle()` and `ellipse()`, *mostly* copying Images but still doing something unique. `circle()` could take a single *side* keyword (not corner!), or a single length-percentage (%s resolved against `hypot(width, height)`). `ellipse()` took a pair of values, each either a side keyword or a length-percentage. (No way to use the reference box's aspect ratio.)
3. Images 4 then took some lessons from Shapes, relaxing `radial-gradient()` somewhat. Circles could take a length-percentage (%s resolved against `hypot(width, height)`). Ellipse could take two keywords (but deferred the meaning of that to Shapes, meaning two corner keywords was undefined...)
4. Shapes then changed to just lean on Images, switching the grammars to just take `<radial-size>` identical to `radial-gradient()`. This left Images relying on now-missing text from Shapes, and left Shapes missing the additional prose limiting circle() and ellipse() to just the circle/ellipse halves of the grammar.

-------

So, the proposal is that we allow the meaningful union of what these two gramamrs intended to do:

1. Circles can take a single side/corner keyword, or a length-percentage, with %s resolved against `hypot(width, height)`.
2. Ellipses can take 2 side keywords or length-percentages, with %s resolved against width or height. Specifying just one of them is the same as duplicating it. They can alternately specify a single corner keyword, which takes the aspect ratio from the reference box.

Specifically:

```
<circle-size> = closest-side | farthest-side | closest-corner | farthest-corner | <length-percentage>
<ellipse-size> = closest-corner | farthest-corner | [ closest-side | farthest-side | <length-percentage> ]{1, 2}
```

`radial-gradient()` will then pair `<circle-size>` and `<ellipse-size>` with the `circle` and `ellipse` keywords, and define that if the shape keyword is omitted, it's a circle if it matches `<circle-size>` and an ellipse otherwise. `circle()` and `ellipse()` will just use the correct size non-terminal to begin with.

## @tabatkins — 2026-09-18

I'm *weakly* against including the corner keywords in the two-keyword ellipse form, just because the behavior seems nonsensical to me. You'll only actually hit corners by accident, whereas the side keywords always hit the sides exactly. It makes sense as a "well the spec says so, I guess I can implement something" sort of behavior, but is not something we'd ever design on purpose, I think.

Yeah, looking at the test you've linked, that's definitely just nonsense behavior. The ellipse doesn't touch any of the four corners of the container, because both times it's calculating the radius that would make a *circle* (using the 1:1 aspect ratio of the container) hit the closest or furthest corner, and when you make an ellipse with those axises it fails at both tasks.

So, no, I think we should stick with the proposal above, and only allow side keywords in the two-value ellipse syntax, reserving corner keywords for the single-value syntax where it makes sense.
