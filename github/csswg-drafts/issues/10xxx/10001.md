## Pain point

It is very very common to use classes with a shared prefix as to specify key-value pairs. For example:

- [The HTML spec recommends using this pattern, to specify the language of `<code>` elements](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-code-element) (and it has been a huge pain to handle in Prism).
- [Tailwind](https://tailwindcss.com/), [Bootstrap](https://getbootstrap.com/) and other frameworks use classes like `pt-6` or `space-y-4` to specify their styles
- Icon families like [FontAwesome](https://fontawesome.com/) and [Bootstrap Icons](https://icons.getbootstrap.com/) use utility classes like `fa-*` / `bi-*` respectively to specify their icons (in this case the prefix does double duty: it serves as both the key and a namespace).
- Authors often create such utility classes of their own.

These utility classes have commonalities shared across all instances, as well as declarations that are specific to the value used. Usually, these are implemented in one of three ways:
1. Enumeration of all the possibilities in the CSS, when they are finite. Manually (and painfully) when they are few, with build tools when they are dozens. This includes both CSS rules for the specific values of each utility class, as well as exceedingly long selector lists for the commonalities among them.
2. Pushing the friction to authors by asking them to use one class for the commonalities and one for the specific values. E.g. to use a Bootstrap Icons icon, authors need to use *both* a `bi` class and a `bi-iconname` class. 
3. This is not an option for libraries, but authors (who have more control of their markup) may do things like `[class^="prefix-"], [class*=" prefix-"]`

None of these are ideal. It seems pretty straightforward to provide the capability these use cases *really* need, so this seems like a a quick win.

While the vast majority of use cases are around class names, I could see something like this being useful for all attributes that take a space-separated list of values.

## Potential solutions

I see two options:
1. Extending class selectors to support wildcards. It appears that `.foo-*` is actually *not* currently valid, so it seems like a natural choice, especially as it extends nicely to other types of wildcard selectors such as element names, attribute names, ids, etc.
2. Introducing a new attribute selector, that is basically a combination of `~=` and `^=`. Options for the operator could be `~^=`, `^~=`, or even `^~` if we want to keep it to a max of 2 characters. This is quicker to implement, but very specific to attribute selectors, and far less intuitive.

For what it’s worth, I believe utility classes for atomic design tokens – i.e. usually with a name that roughly matches its single style rule like `.font-sm {font-size: 0.8rem}` – are very much an anti-pattern for production-level CSS.
~~~~ css
$fg-green {color: var(--my-green);}
$bg-white {background: white;}
~~~~

~~~~ html
<a style="@include $fg-green $bg-white">dev</a>
~~~~

~~~~ css
.pattern {@include $fg-green $bg-white;}
~~~~
and the HTML could become more readable and semantic again. 
~~~~ html
<a class="pattern">prod</a>
~~~~

~~~~ css

  --icon: url(icons.svg#name);
~~~~

## @LeaVerou — 2024-03-19

Lots of conjecture about what is hard for beginners being thrown around 🙃

From a usability pov, **it's not the density of symbols that hinders understanding, it's the recognizability**.
ASCII symbols in programming languages are analogous to icons in GUIs. When an icon has a widely understood meaning, it facilitates understanding, because the circuit in our brains that recognizes pictures is *much* faster than the neural pathway that processes written language. However, when an icon is used that has no widely understood meaning, this benefit is moot, and instead it simply adds friction to the interaction, as we have to hover over it to figure out what it does from the tooltip. If we stick to the interface, we eventually learn what the icon means, and then it goes through the faster pathway, but that can take a while and I can't remember if it ever becomes 100% as fast as it is for a widely recognized symbol. Depending on the constraints of the use case, sometimes that may be an acceptable tradeoff, but usually it isn't. A happy medium is UIs that have both, so you can fall back to the text if image recognition fails, but not every UI can afford that kind of real estate.

The same applies to programming languages: ASCII characters are *their* "icons". That’s why `width < 500px` makes more sense than `max-width: 500px` but `Boolean(foo)` is more readable than `!!foo`. In programming languages instead of hovering over a button to see its tooltip we try to google it, but the principle is the same: symbols that are widely understood improve understanding, and symbols that are not hinder it (at least for a while).

Often this is intuitively understood by language designers, but the specifics of *what* exactly is widely recognized by the target audience is the source of many a debates (e.g. for my previous example, I'm sure many would argue `!!foo` is perfectly fine because it's widely understood as a JS convention).

On to this particular case, I would argue using a wildcard to mean "any string of symbols" is a *very* widespread convention. It extends beyond programming languages as well, as it's a common convention in many searching GUIs. On the contrary, strings of symbols like `^~=` are far more esoteric. Sure, you'd be able to tell that `[class^~="foo"]` has to do with classes, but beyond that, you'd be stuck. And once we need to come up with a selectors for element types or attribute names, we have to invent two _other_ conventions, whereas using wildcards across the board to mean "this part is variable" means authors only need to learn a single concept that they can then apply to multiple places, which tends to be a characteristic of good UI design (few flexible concepts that can be combined in many different ways, rather than many rigid ones that have to be learned separately).

Also, whether beginners can understand the difference between `.foo-*` and `.foo- *` is a pretty easily testable hypothesis. 😄

@AtkinsSJ The question mark `?` is another frequent choice to represent a wildcard; in contrast to the asterisk `*`, it usually stands for single characters (or digits as in CSS’s [peculiar codepoint notation](https://drafts.csswg.org/css-syntax-3/#consume-unicode-range-token)), which is a vague concept and mostly irrelevant in Selectors. In regular expressions, the dot or period `.` is used instead, which already has meaning in this context that would lead to other ambiguous situations – probably even if it was doubled `..` or tripled `...` to mimic a horizontal ellipsis `…`, which is used in (English) prose for similar purposes.

Besides the question mark, the least bad one remaining from the US-ASCII repertoire is perhaps the percent sign `%`.

## @vrugtehagel — 2026-08-20

I read [Bramus' post](brm.us/class-prefix-selector) on this earlier today, and I have some reservations about this feature that I'd like to voice.

In the original post, Lea mentions that one of the current solutions is

> Pushing the friction to authors by asking them to use one class for the commonalities and one for the specific values. E.g. to use a Bootstrap Icons icon, authors need to use both a `bi` class and a `bi-iconname` class.

I feel this is the correct thing to do, at least with CSS's current semantics. A certain category (class) of elements has a class name in common. This proposal is, in a way, about having "classes of classes" or "subclasses", but it's bolting semantics onto what currently is only a convention, and only sometimes. For example, I agree it makes total sense to interpret `.button-large` as a `-large` subclass of `.button`, but when I write `.fine-print`, I assume most would agree it is incorrect to interpret this as a `-print` subclass of `.fine`.

I also think authors have created slightly different meanings around the use of hyphens for themselves. For example, I might create a cookie banner including a `.cookie-banner-backdrop` and a `.cookie-banner--dark` class. In this case I would say `.cookie-*` doesn't make much sense, and as author I would intuitively think `.cookie-banner-*` would match only `.cookie-banner-backdrop` and not `.cookie-banner--dark`. However, from what I understand from this thread and the [related issue](https://github.com/w3c/csswg-drafts/issues/14291), this is not the case. And I'm sure there are circumstances where the opposite behavior is expected.

What I'm trying to say here, is that creating new syntax for a category of identifiers that currently have no well-defined semantic meaning in CSS seems inappropriate. I do understand that this is a reasonable small-enough step to reach something useful, but I feel a more robust "subclassing" system would be better for CSS overall. What if we instead add similar semantics to something like `class="foo/bar/baz"` (currently presumably rare)? Then we can select things like `.foo/*`, which makes it much more obvious that `/` is a "subclass separator" and that writing `.foo*` doesn't make much sense. This would also create some potential flexibility around the separate parts, for example, we can later decide to extend this to follow shell expansion-esque syntax with `.foo/*/baz/qux`, `.foo/**/qux`, etcetera.

As a footnote, I do think the `part` attribute should be considered as part of this proposal (alongside `exportparts`). This is a very class-like attribute, being a space-separated token list. But to match them, we need `::part()`. Is the idea to extend that to allow e.g. `::part(foo-* bar-*)`?

* It has unintuitive side effects (e.g. should `.region-*` select `.region-sidebar` and `.region-name`)
* Enforces specific semantics that don't work well for common naming conventions
* Is overly specific in that it focuses on classes and one of the many popular naming conventions

> Introducing a new attribute selector, that is basically a combination of `~=` and `^=`. Options for the operator could be `~^=`, `^~=`, or even `^~` if we want to keep it to a max of 2 characters. This is quicker to implement, but very specific to attribute selectors, **and far less intuitive.**

* more flexible
* doesn't assume naming/semantics of classes
* easier to implement (per Lea, I wouldn't know)

That feels much more spec worthy than class prefix, which has baggage that feels more appropriate for an _optional_ Sass extension.

Fixing the core concern here seems like "nice to have", which implies a higher level of scrutiny.

* Having `<div class="foo foo-bar"></div>` is _fine_ for the vast majority of sites
* This could be solved on the CSS side by having a declaration block that styles all variations e.g.:
  ```css

  .foo-bar,
  .foo-baz {}
  ```
  (which you can use CSS pre/post-processors to get to a lot easier in large projects)
* There are plenty of frameworks that minify/combine CSS selectors and update the markup and styles

## @romainmenke — 2026-08-23

> It was my impression that the `.foo-bar--baz` naming scheme was a workaround for CSS lacking ways to **group and namespace style rules, and isolate them from each other**.

That isn't what this proposal is trying to do.
Naming schemes like BEM typically focus on naming parts of the DOM tree.
For example two separate components having distinct image styles.
In such a case you can't just use `.image` as a classname as it would clash.

With BEM this would look like:
- `.foo__image {}`
- `.bar__image {}`

Where `__` separates distinct DOM elements.

And exactly this problem is also what `@scope` is designed to help with:
- `@scope (.foo) { .image {} }`
- `@scope (.bar) { .image {} }`

Nesting could also be used but is a slightly weaker tool than `@scope` as it doesn't take DOM proximity into account.

A class prefix selector could however help with the modifier part of BE**M** (same element, but different style).
- `.foo--green`
- `.foo--blue`

I don't think this is meaningfully better:

```css
.foo-* {
  width: 200px;
}

.foo--green {
  color: green;
}
```

```html
<div class="foo--green">
```

vs.

```css
.foo {
  width: 200px;
}

.foo--green {
  color: green;
}
```

```html
<div class="foo foo--green">
```

But then I also don't think either is good and prefer:

```css
.foo {
  width: 200px;
}

.foo[data-color=green] {
  color: green;
}
```

```html
<div class="foo" data-color="green">
```

This might seem similar to the example I gave earlier but the scale if very different. 2-3 variants vs. hundreds of icons. Internal use vs. a library. It makes sense that libraries try to provide a clean and simple way to use their features.

Bootstrap already tries to allow their users to write a single class instead of two:

https://cdn.jsdelivr.net/npm/bootstrap-icons@1.13.1/font/bootstrap-icons.css

```css
.bi::before,
[class^="bi-"]::before,
[class*=" bi-"]::before {

}
```

It makes sense to provide a better API for this.
And this proposal does exactly that.

Personally I think that attributes are better suited (e.g. `<i bi="alarm-fill">` or `<i data-bi="alarm-fill">`), but authors clearly prefer to use classes.

Obviously fine that when this exists that it is also used for other things, but I don't see any issues there. Those who don't consider it a good fit for their project simply don't use it.

There might be false positives when matching elements but I think this will be rare in practice. It would surprise me if authors suddenly (ab)use prefix selectors for everything. Much more likely that this will be a well considered choice to use it for a specific problem.

> My point with the "region" example is - what is stopping the author from using `class="region"` in both scenarios?

Nothing, they could, but if they have decided that a certain type of element belongs to the `.region` class, they would not also apply it to `.region-name` elements if they do not belong to that same category. Regardless, the `.region-name` class, while unique, still receives the `.region-*` styles no matter what.

> They equally have to keep in mind the two unrelated uses of the word in that scenario; this is not special to the class prefix selector.

Yes, you're right, but I think the distinction in syntax should be relevant. I find "this whole token defines a class" to be a much simpler thing to intuitively do right than "this whole token or any part from the start to a hyphen could define a class".

Bootstrap's "hacky" `[class]`-based selectors are a perfect example of where this could go wrong. If I introduce a `.bi-directional` class, it gets icon styles, even though that class is uniquely identifying a whole different group of elements. Bootstrap's selector is unsemantic usage of classes, and the attribute-based syntax used at the very least gives off a hint that might break certain expectations.

I feel that, to bind an element to a class, I must assign it the unique name identifying this class of elements. In my opinion, Bootstrap's approach shouldn't be encouraged with new syntax; instead a more robust solution is to require a `.bi` class. Writing `class="bi bi-foo"` is not much of a burden for authors anyway, nor does it significantly impact transfer sizes assuming basic text compression. All while making things much easier to understand. The `.bi` class is for Bootstrap icons. Don't use it for anything else. I don't think I would even consider the `.bi-*` prefix at all when assigning the `.bi-directional` class.

## @LeaVerou — 2026-08-25

I agree with @AtkinsSJ. 

BEM (and similar naming conventions) emerged as a means to work around CSS limitations, most notably the lack of scoping, the brittleness of the cascade, and the lack of fine-grained control over specificity. To work around these limitations, it encouraged developers to sidestep CSS selectors entirely, manage their selection logic themselves, and encode structure into verbose class names following a naming convention that had to be kept up to date manually or via JS. 

Modern CSS, however, provides first-class primitives for these concerns: cascade layers, `:where()`, `@scope`, nesting, etc reduce the need to manually encode structure in class names. In fact, when I [proposed](https://github.com/w3c/csswg-drafts/issues/1170) `:where()` back in 2017, it was _exactly_ to address the CSS limitations that BEM was designed to work around. 

Although BEM is still in widespread use, it is a convention the industry is slowly moving away from (note the wording in recent online discussions about it: “[Do you _still_ use BEM?](https://www.reddit.com/r/css/comments/1odv2q6/do_you_still_use_bem_naming_convention_at_work/)”). 
Even if there are some valid reasons to use BEM today, it is a polarizing issue among developers (example discussions: [1](https://www.reddit.com/r/css/comments/1odv2q6/do_you_still_use_bem_naming_convention_at_work/) [2](https://hashnode.com/forums/thread/css-methodology-to-bem-or-not)).

We should definitely not be designing CSS features around it.

Besides BEM, pushback centers around these arguments:

## @vrugtehagel — 2026-08-25

> "It's not right to privilege -!" CSS already privileges -.

It's not about privilege, it's about semantics. I don't think it's right to create syntax that invokes the meaning of "namespacing" where there was no meaning before.

But counterarguments aside, I find this feature unnecessary. I see no compelling argument for using `class="foo-bar"` with `.foo-*` over `class="foo foo-bar"` with `.foo`. The latter is a bit longer to write, sure, but is also more robust, because the former "claims" the whole `foo-` namespace whereas the latter only has to "claim" a single `foo` class. I think this is a risky feature because it might be encouraging developers to write more brittle code (as I have attempted to demonstrate in previous comments).

In fact, I struggle to really grasp the problems that the original post tries to bring up. It mentions the HTML spec suggesting using `language-` classes to denote their language. The spec however doesn't say that you shouldn't be adding an additional `highlighted` class to mark them for bulk highlighting, nor does it mention CSS at all (in fact, a `data-language` attribute seems most appropriate for scripting, so I'm guessing this part of the spec was written before data attributes existed). Frameworks use classes like `.pt-6`, but I don't see how `.pt-*` is going to significantly improve DX in this case. For libraries like Bootstrap or Font Awesome, using `class="bi bi-foo"` and similar is an existing, stable solution. And yes, authors create utility classes, but I struggle to see a case where this feature would be of significant benefit beyond the other cases.

As for the original post's mention of the current solutions, I would say enumeration is a "code smell" of sorts; if you have `.button-red`, `.button-green`, etcetera, and you want to assign styles to all colors at the same time, then the appropriate solution is to add a shared, overarching class. They're all buttons, give them a `.button` class! No enumaration necessary. The third point about doing `[class^="prefix-"], [class*=" prefix-"]` just shows that if this is _really_ needed, authors can already do it.

Since the three bullet points are followed up with 

> None of these are ideal.

I want to bring attention back to what I believe to be the correct solution, also brought up in the original post:

> Pushing the friction to authors by asking them to use one class for the commonalities and one for the specific values. E.g. to use a Bootstrap Icons icon, authors need to use both a `bi` class and a `bi-`iconname class.

Specifically I find it surprising to hear that "use one class for the commonalities" is considered "not ideal". This is what classes are, and have been for decades! And really, how much friction are we talking about? The difference between `class="bi bi-foo"` and `class="bi-foo"` is extremely minimal, especially with IDEs of today. It also doesn't add significant bloat to file sizes, assuming basic text compression, so overall I remain confused about the problem we're really solving here. I get that it shortens things in some scenarios, but I find it excessive to introduce this new syntax (which comes with its costs in terms of the language) purely for the keystrokes saved.
