Currently, `@scope` only accepts _rules_ in its body. If you want to apply something to the scoping root itself, you need to use a `:scope` rule:

```
@scope (div) {
  :scope {
    color: green;
  }
}
```

However, ever since [relaxed nesting](https://github.com/w3c/csswg-drafts/issues/7961) was introduced (where we first try to parse something as a declaration, and otherwise try it as a nested rule), we should be unblocked if we wanted to support direct declarations in the rule.

## @mirisuzanne — 2024-06-09

I think the main source of confusion here would be determining the specificity. Currently these have different specificities:

```css
@scope (#foo) {
  p { /* 0,0,1 */ }
  :scope p { /* 0,1,1 */ }
  & p { /* 1,0,1 */ }
}
```

That's already somewhat confusing, since `:scope p` and `p` have identical behavior. When you remove the nested `p` and consider `:scope` vs bare declarations (with implied-`:scope`), it should likely have the same specificity implications? `0,1,0` vs `0,0,0`?

I don't know if that causes round-trip issues when captured in CSSOM.

## @andruud — 2024-06-12

> This would be 0,0,1 - a bit less surprising to me.

No, keep in mind that the `<scope-start>` selector [acts as the parent rule](https://drafts.csswg.org/css-nesting-1/#nesting-at-scope) for `&`here. So per spec this is 1,0,1. (Warning: not what Blink actually does).

<!-- comment id=2162909845 author=mirisuzanne created=2024-06-12T12:41:20Z url=https://github.com/w3c/csswg-drafts/issues/10389#issuecomment-2162909845 -->
## @mirisuzanne — 2024-06-12

Sorry, some confusion here in the back-and-forth. I think we've landed on an answer in the attached issue. The implicit prefix when nesting in `@scope` is similar to `:where(:scope)` - so the resulting specificity is:

```css
div { /* the div is merged into <scope-start> as though `& #foo` */
  @scope (#foo) {
    color: blue; /* 0,0,0 */

    p { /* 0,0,1 */ }
    :scope p { /* 0,1,1 */ }
    & p { /* 1,0,1 */ }
  }
}
