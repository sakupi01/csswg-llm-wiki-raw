Currently to give an element a keyframe animation, the author has to declare the `@keyframes` rule in one place, give them a name, and then assign the keyframes to an `animation-name`.
This is unnecessarily tedious in some cases where the keyframes have a 1:1 relationship with an element or selector, and also restrict their use in inline styles.

Asking that we find a syntax to "shortcut" the keyframes directly into `animation-name`. Perhaps:

```css
animation-name: @keyframes { ... }
```

## @noamr — 2026-08-27

Some idea, what if `keyframes()` was a per attribute function?

So instead of:
```css
@keyframes anim {
  from { opacity: 0.3; translate: 100px; }
  50% { opacity: 0.5; translate: 200px; }
  to { opacity: 1; translate: 1000px }
}

.me { animation-name: anim }
```

you can do something equivalent to `if`

```css
.me {
  animation-name: auto;
  opacity: keyframes(from: 0.3; 50%: 0.5; to:1; }
  translate: keyframes(from: 100px; 50%: 200px; to: 1000px; }
}
```

Perhaps with an "else" like semantic for the base value.
This would naturally work in inline styles.

The actual pain point is that you need to create a global (tree-scoped) identifier every time you want an animation.
That doesn't need a parallel syntax, it just needs scoped names!
What if we could nest a `@keyframes` rule in another rule and use hygienically rewritten names? Then you need to put significantly less thought in picking a name that won't clash.
That would also allow mixins to provide animations, which is a common need.

While we're at it, a pain point that web component authors brought up to us recently is that WC consumers cannot pass animations to replace default ones due to the current scoping rules. I wonder if we could feed two birds with one scone here. 🤔

> Perhaps with an "else" like semantic for the base value. This would naturally work in inline styles.

You haven't specified the timing, easing, fill modes, repeat, timelines, ranges, etc of those animations. Would it all go in the keyframes function?

Using the animation property would also work in inline styles and would provide a more model where multiple properties are animating in the same animation. If you have a keyframes function per property then it would be hard to coordinate associated property changes.

My main concern is the complexity of animation parsing and matching. Parsing is pretty self evident, but there is also the issue that whenever the animation-name property (the property where these keyframes would slot in) changes, we evaluate whether the animation name changed from what it was before. If instead of a name we have a whole description of the animation that comparison is going to be more expensive. It's certainly doable, just something to keep in mind, e.g.

```js
elem.style.animation = `
    @keyframes { 0% { opacity: 0; transform: translateY(-2rem); } } 5s,
    @keyframes { 0% { color: red; } 100% { color: green; } } 2s;`;
// Some time passes
elem.style.animation = `
    @keyframes { 0% { opacity: 0; transform: translateY(-1.5rem); } } 5s,
    @keyframes { 0% { color: red; } 100% { color: green; } } 2s;`;
```

This needs to detect that the second animation is the same in both, but the first animation changed so it is treated as a brand new animation starting over from the beginning.
