WebKit-ancestral browsers (including Blink) at one point implemented a non-standard `overlay` value for scrolling.This was never standardized (see [here](https://github.com/w3c/csswg-drafts/issues/7421) for a discussion of why it shouldn't be).

Subsequently, WebKit made `overlay` a synonym for `auto` .Gecko treats it as an invalid keyword. Blink still retains the original implementation (but the change to match Webkit is tracked in [this bug](https://bugs.chromium.org/p/chromium/issues/detail?id=1271942)).

This also came up as a [compat problem in Interop 2023 discussions](https://github.com/web-platform-tests/interop/issues/187).

I propose to put the current WebKit behavior (`overlay` is an alias to `auto`) into the spec as a web compat compromise, because making it invalid would likely break too many sites.

## @Loirooriol — 2022-11-11

I think it would be quite confusing to accept `overlay` but then use classic scrollbars. It could also be a problem for webpages that are using `CSS.supports("overflow", "overlay")` to decide whether to polyfill overlay scrollbars or try to use a native approach.
Would the breakage of removing `overlay` be that bad, given that Gecko doesn't support it?

That polyfill test would already fail in WebKit, per Chris's comment about their behavior.

Firefox doesn't really get away with this; it's a pretty significant webcompat issue, which is why we're keen to get something fixed here; see https://bugzilla.mozilla.org/show_bug.cgi?id=1521631 for details (all the See Also links are site breakage).

## @Loirooriol — 2022-11-16

AFAIK the problem with `overflow: overlay` is that for now there is no implementation interest to have a feature to allow authors to choose overlay scrollbars. If this changes in the future, but now we define `overflow: overlay` as `auto`, then authors won't be able to use `@supports` to check whether they can choose overlay.
