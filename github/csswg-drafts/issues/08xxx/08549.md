We've had requests from developers (e.g. [airbnb](https://bugs.chromium.org/p/chromium/issues/detail?id=1189696#c3), [google search](https://bugs.chromium.org/p/chromium/issues/detail?id=1420772)) to customize the fling curve of snap point scrolls. A common cause or desire is to align behavior, which itself seems partially motivated from the way that browsers haven't given special treatment to scrolling physics for certain snap use cases in the same way that the experiences being emulating have given them different physics.

`scroll-snap-stop` is often used as a simple form of control over the physics (forcing a stop at each item), but even when the typical interaction is to scroll one item at a time developers often want to still allow flings to cross multiple items.

I think expectations may vary based on the size of snap items and lengths of documents, e.g.:
* For long articles with headers that may want to snap, having snap behave similar to normal scrolling likely matches expectations
* For lists with snap points on each item, there is often an expectation that a standard length flick will move about a page of items. The experiment in [crbug.com/1189696](https://bugs.chromium.org/p/chromium/issues/detail?id=1189696) shows that for such use cases it may be as simple as adjusting fling distances to meet expectations here. A paginated book would likely have similar expectations.
* Scrolling within a large snap point should probably match document scrolling but may want to prefer seeing the end of the current snap point rather than jumping to the next snap point.

While some cases the browser may be able to "just do the right thing", I think there are cases that would be helpful if the developer could give the browser a hint what kind of category things fall into.

Some possible ideas:
* Add a `scroll-snap-distance: item | page | document` which hints whether the UA should treat a typical fling as traversing the distance of one item, one page, or a document scroll (the current behavior). Alternately, it could take a length.
* Add a `scroll-snap-friction: #` which applies some amount of friction to getting to scrolling past each subsequent snap point.
* Something else?

I'm not sure what the exact right solution is here but there seems to be a common developer need to apply different physics to different scenarios.

See concrete proposal in https://github.com/w3c/csswg-drafts/issues/8549#issuecomment-4623142600

## @flackr — 2026-06-04

I have worked up a concrete proposal here, including more recent requests I've heard for resistance to leaving snap areas and difficulties I encountered with building pull to refresh with scroll snap ([demo](https://flackr.github.io/web-demos/css-scroll-snap/email/)). See motivating use cases for a rough representative set of things that are difficult to replicate today.

## Proposal
I think that we can address all of the motivating use cases that have been raised (see examples below) with a couple additional values and an additional property:
1. Resistance to bypassing snap points in flings - while flinging, the snap point will actively resist passing it (i.e. it will slow down your scroll).

```css
scroll-snap-stop: normal | always | <length> | before
```

`before`: No fling strength will reach this snap point, the user must drag at least as far as the point at which this snap point is preferred.
`<length>`: Some amount of fling strength will be "consumed" by bypassing this snap point. Always is effectively like specifying an infinite length.

2. Strength and magnetism to the snap point. If attract, applies magnetic / gravitational attraction to the scroll while actively dragging (e.g. notification dismissing behavior on android).

```css
scroll-snap-strength: [auto | <length>] || [attract | no-attract]
```

<length> is used to determine the relative attraction of this scroll snap area compared to snapping to a different snap point. If the lengths overlap, the inflection point where you switch from one to the other is determined by the average position between the maximum strengths of each group of aligned points, capped to the snap points themselves. If the scroll container has scroll-snap-type mandatory, then the midpoint between any remaining gap in lengths is used as the point at which you select one or the other.

If attract is specified, the scroll will resist scrolling away or accelerate to scrolling to the next point with attract specified. Once you exceed this length the UA may catch the scroll up, but I don't think this needs to be mandatory.

Note that we could consider having a small set of keywords instead of the `<length>` options if we think that arbitrary lengths may be too permissive. E.g. `strong`.

## Motivating use cases

### Pull to refresh
A snap point that you have to scroll all the way to, and cannot fling to.
```css
.main { scroll-snap-align: top; }
.ptr { scroll-snap-align: top; scroll-snap-stop: before; scroll-snap-strength: 0; }
```

### Dismissable areas (e.g. bottom sheet)
A snap point that resists actively scrolling it away.
```css
.sheet {
  scroll-snap-strength: 3rem attract;
}
```

### Galleries or carousels
Increased resistance to flinging past many entries - like a weaker scroll-snap-stop.
```css
.item {
  scroll-snap-align: center;
  scroll-snap-stop: 30vw;
}
```

## @nickcoury — 2026-06-24

I love the intent of this, but don't love the API or concrete proposal. I agree with the first comment in the thread that half the reason it's a problem is that the behavior on mobile doesn't match the underlying native platform that users develop a lot of muscle memory for. The mechanisms here seem to be providing configuration for yet another physics system that doesn't match the native platforms.

In particular, Flutter has useful prior art when they tried to make a unified API and received significant pushback on both Android and iOS for feeling non-native which led them to completely change their scroll snapping logic to more closely resemble native platforms:

https://github.com/flutter/flutter/issues/119875
https://github.com/flutter/flutter/issues/149221
https://github.com/flutter/flutter/issues/120338

I think this API makes a bit more sense for use cases that aren't heavily scrolling based, like pull to refresh. But will be problematic for heavy scrolling cases like carousels. I'm not even sure how I'd tune this for a good experience. It would be trial and error and very inconsistent for users across sites.


I’ve been digging into other implementations (Android, iOS, Flutter, etc) to see if that suggests a better balance between platform-specific behavior and customization, and it hints at some other possible designs. In particular, there seem to be two conceptual phases:

Phase 1 - Fling (Momentum Decay). The OS uses standard, unmodified platform friction to let the swipe coast and mathematically project a theoretical resting coordinate. Modifying friction here is what feels uncanny valley.

Phase 2 - Settle (Snap). Once a snap point is determined, the OS abandons the friction decay and transitions to a spring curve using the active velocity as an input.

Here are some APIs that might map to that. Please forgive any errors in use of native APIs, I don't have deep enough experience with them and this was based on quick research.

### 1. scroll-snap-limit
Give web authors a mechanism to cap how far the fling can go, but still let the OS control the fling.

```css
.carousel {
  /* Flings as far as native momentum permits */
  scroll-snap-limit: none;
  
  /* Fling traverses a maximum of 1 item */
  scroll-snap-limit: 1;
  
  /* Fling traverses a maximum of 1 visible viewport */
  scroll-snap-limit: 100vw;
}
```

Both Android and iOS use this concept:

iOS
```Swift
ScrollView { ... }
  .scrollTargetBehavior(.viewAligned(limitBehavior: .alwaysByOne))
```
Android
```Kotlin
val flingBehavior = PagerDefaults.flingBehavior(
    pagerSnapDistance = PagerSnapDistance.atMost(1)
)
```

### 2. scroll-fling-decay
I'm not as confident on this one, and I'm more in favor of skipping it. But if modifying fling friction is required, there's a bit of prior art on the native side.

```css
.carousel {
  /* Uses standard OS momentum */
  scroll-fling-decay: auto; 
  
  /* Maps directly to steeper native OS deceleration */
  scroll-fling-decay: fast; 
}
```

Native equivalents:

iOS
```Swift
// Note this is in UIKit which is legacy, and there's not an equivalent option in SwiftUI
scrollView.decelerationRate = .fast 
```
Android
```Kotlin 
val decay = exponentialDecay(frictionMultiplier = 2.0f)
```

### 3. scroll-snap-animation
For the second phase snap, developers may want to modify how fast it snaps which gives most of the feel that's worth customizing anyways.

Most systems now use spring physics which feel intuitive and natural, and can readily take the current velocity as an input. While this means spring() would likely need to be finalized as part of this, that may be a desirable thing anyways. There's an option here to use one or both of:
1. Presets that map to the OS or are tuned by the UA to feel natural.
2. expose a more raw spring() configuration object that uses the velocity. The values likely need to be clamped to avoid situations like infinite overbouncing.

```css
.carousel {
  /* Semantic OS defaults */
  scroll-snap-animation: auto | fast | smooth | bouncy; 
  
  /* Customize */
  scroll-snap-animation: spring(<mass> <stiffness> <damping>);
}
```

Native equivalents:

Android
```Kotlin
val flingBehavior = snapFlingBehavior(
    snapAnimationSpec = spring(
        stiffness = Spring.StiffnessLow, 
        dampingRatio = Spring.DampingRatioMediumBouncy
    ) 
)
```

iOS doesn't actually have an equivalent here, except maybe a custom scroll implementation in UIKit that isn't in SwiftUI. It sounds like they don't allow this kind of scroll snap customization on native scrollers. Programmatic scrolls can be customized, and that's still done with springs.
```Swift
ScrollView { ... }
```
