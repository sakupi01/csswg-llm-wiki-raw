Transitions tend to happen in the opposite direction on 'back' navigations.

With SPA, we recommend looking at state in the navigation API, and setting a class name on the root.

For MPA, it feels like we should have something higher-level:

```css
@media (vt-nav-type: back) {
  /* … */
}
```

We should also look at ways to add that behaviour for SPAs:

```js
document.startViewTransition({
  isBackNavigation: true,
  update: callback,
});
```

Or we could look at a tighter integration with the navigation API.

## @noamr — 2023-05-30

Note that this is possible to achieve with a bit of JS even for MPA. Though of course a declarative solution would be much preferable.

For example, this PoC would slide from the top when going forward, from the bottom when going backwards, and fade in when reloading:
```js

	switch (performance.getEntriesByType("navigation")[0].type) {
		case "reload":
			document.documentElement.dataset.navDirection = "reload";
			break;
		case "back_forward": {
			const prev = sessionStorage.getItem("prev-url");
			console.log(prev, document.referrer)
			document.documentElement.dataset.navDirection = document.referrer === prev ? "forward" : "back";
			break;
		}
		default:
			document.documentElement.dataset.navDirection = "forward";
	}

	sessionStorage.setItem("prev-url", location.href)
```

```css
@keyframes slide-in {
  from { transform: translateY(-100%) }
  to { transform: none}
}

@keyframes slide-out {
  from { transform: translateY(100%) }
  to { transform: none}
}

@keyframes fade-in {
  from { opacity: 0 }
  to { opacity: 1 }
}

::view-transition-group(root) {
  animation-name: slide-in;
  animation-duration: 1s;
}

html[data-nav-direction="back"]::view-transition-group(root) {
  animation-name: slide-out;
  animation-duration: 1s;
}

html[data-nav-direction="reload"]::view-transition-group(root) {
  animation-name: fade-in;
  animation-duration: 1s;
}
```

## @dbaron — 2025-11-21

In [last week's discussion](https://github.com/w3c/csswg-drafts/issues/12594#issuecomment-3530564088) of CSS navigation / route matching, @jakearchibald raised the issue of being able to query whether a navigation was back or forward, which was also discussed before in this issue.

I *think* @jakearchibald's use case relates to the idea that a developer wants a design where the UI has some sort of "physical" (in animation) representation of the browser's session history, most likely through side-to-side movement.  (@jakearchibald, is that correct?)  I think this is different from the use cases we were initially focusing on, where the motion of an animation from a list of items to the details of one item, or the animation from details to list, depends on the "from" and "to" of the navigation in order to represent the movement of the single item between being the focus of the UI to being a single item within a list, and that motion doesn't depend on the type of navigation.  But maybe there are also other use cases for knowing this -- which may or may not differ in which exact distinctions they want to make.  (In particular, I'd like to understand when a developer wants the animations to be a function of where in the browser session history the pages are *rather* than what the particular pages are and how they are connected within the logical structure of the site/app.)  It would be useful to raise additional use cases here.

Then there's the question of what we want to query.  The space of possibilities is a bit larger than just back/forward.  I think a good high-level summary of the cases is the [`NavigationType`](https://html.spec.whatwg.org/multipage/nav-history-apis.html#navigationtype) enum in the HTML spec, which has `push`, `replace`, `reload`, and `traverse`.  Note that back and forward *both* fall into the "traverse" category (where typical browser [back](https://html.spec.whatwg.org/multipage/nav-history-apis.html#dom-history-back) and [forward](https://html.spec.whatwg.org/multipage/nav-history-apis.html#dom-history-forward) buttons correspond to a delta of -1 or +1, though they often provide additional drop-down UI for deltas further from 0).

Then the question is, which things do we need to distinguish?
* It seems like exposing the 4-way distinction in the `NavigationType` enum above is probably a good baseline.
* I think @jakearchibald's use case wants to know (for the `traverse`) case whether the delta is positive or negative -- and maybe even exactly what it is?
* Do the `push` and `replace` cases need to distinguish between navigation and `history.pushState()`/`history.replaceState()`?
* Do we need more in addition to that?  Or less?

For now, what would you think about adding the following to `@navigation`:
* `(type: traverse)` for when the active naviation has [`NavigationType`](https://html.spec.whatwg.org/multipage/nav-history-apis.html#navigationtype) of `"traverse"`
* `(type: back)` for when the active naviation has [`NavigationType`](https://html.spec.whatwg.org/multipage/nav-history-apis.html#navigationtype) of `"traverse"` and the delta is negative
* `(type: forward)` for when the active naviation has [`NavigationType`](https://html.spec.whatwg.org/multipage/nav-history-apis.html#navigationtype) of `"traverse"` and the delta is positive
* `(type: reload)` for when the active naviation has [`NavigationType`](https://html.spec.whatwg.org/multipage/nav-history-apis.html#navigationtype) of `"reload"`

It's not clear to me what distinctions we'd want to expose for `push` and `replace` navigation types (between or within them), but the above four seem like a coherent set that exposes useful functionality.  (By "coherent set", I mean that, for example, exposing "back" without exposing "forward" just seems visibly incomplete in a way that's unnecessary.)

Happy to see that there are ideas to reduce the need for JavaScript on directional view transition.

When doing tooling to set view transitions types for different kinds of navigation, I found the following useful for cross-document view transitions:

Directional types for backward/same/forward as described [here](https://vtbag.dev/tools/turn-signal/#directions-script) 
 - based on Navigation API (use "backward" for backward history traversal, optional "same" for any navigation to the same page, "forward" for everything else) 
 - based on a ordered list of URLs (see [turn signal](https://vtbag.dev/signal-demo/bag/) demo and the previous / next links in the footer of vtbag.dev.   
 - specified forward type (and optional types for same page and history backward traversal) in an data-attribute of a link (see [image viewer](https://vtbag.dev/viewer-demo/) & multiple direction [fish pond](https://vtbag.dev/link-demo/) demos) 

Never saw myself the need to distinguish between push and replace, but that could be because I seldom replace.

What I found useful was to set additional types "old" / "new" during capture of old and new images to guide view transition naming.
