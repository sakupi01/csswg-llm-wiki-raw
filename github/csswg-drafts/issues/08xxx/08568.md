I am sorry I did not comment on #4431 and #6083, but I did not know about them until today.

I think [`box-shadow-offset`](https://drafts.csswg.org/css-backgrounds-4/#propdef-box-shadow-offset) could be defined with `none | <length>{1,2}#` instead of `none | <length>{2}#`.

[`<spread-shadow>`](https://drafts.csswg.org/css-backgrounds-4/#typedef-spread-shadow) would have to be defined with `<'box-shadow-color'>? && [none <length>{0,2} | <length>{2,4}] && <'box-shadow-position'>?` with a prose saying that the first two `<length>`s are for `box-shadow-offset`, etc, and that it always serialize with two explicit `<length>`s in `box-shadow`, when other `<length>`s are not omitted.

## @SebastianZ — 2023-03-14

As noted in #8581, we could also introduce a new future-proof syntax that avoids ambiguities (while keeping the existing one for legacy reasons, of course).

The syntax suggested in the other issue uses slashes to distinguish the values:

```ebnf
<spread-shadow> = <modern-spread-shadow-syntax> | <legacy-spread-shadow-syntax>
<modern-spread-shadow-syntax> = <'box-shadow-color'>? && [ <'box-shadow-offset'> [ / <'box-shadow-blur'> [ / <'box-shadow-spread'> ]? ]? ] && <'box-shadow-position'>?
<legacy-spread-shadow-syntax> = <'box-shadow-color'>? && [ <'box-shadow-offset'> [ <'box-shadow-blur'> <'box-shadow-spread'>? ]? ] && <'box-shadow-position'>?
```

Sebastian

<!-- comment id=1468923358 author=SebastianZ created=2023-03-14T22:26:24Z url=https://github.com/w3c/csswg-drafts/issues/8568#issuecomment-1468923358 -->
## @SebastianZ — 2023-03-14

And just to avoid that the notes from the other issue get missed, I mention them here as well.

Given that we also [want to allow different values for the horizontal and vertical spread radius](https://drafts.csswg.org/css-backgrounds-4/#level-changes) (and possibly for the blur radius as well), I suggest we rather introduce a new syntax and treat the current one as legacy syntax.

This is also similar to #6946.

And for a precedent where a new syntax was introduced, see the [color functions in CSS Color 4](https://drafts.csswg.org/css-color-4/#funcdef-rgb). 

Sebastian

## @LeaVerou — 2023-08-22

I think allowing a single value in `box-shadow-offset` is a nice enhancement and I'd be in support.
I don't think the benefit is worth the drawbacks of moving to a different slash-based syntax however, and having to support both forever. I'm also unconvinced about the prevalence of use cases with 45deg offsets, though we can easily find out about that via an HTTPArchive query.

Furthermore, slashes are problematic, because there is no established precedence of operators (spaces, commas, slashes) across CSS, different properties use different precedences. E.g. in `background` slashes have a higher precedence than commas, whereas in `font` commas have a lower precedence than slashes.

@SebastianZ, can you please tell me in which cases *"legacy reasons"* apply to preserve optional values specified with their default value?

  > Note: The rules described here outline the general principles of serialization. For legacy reasons, some properties serialize in a different manner, which is intentionally undefined here due to lack of resources. Please consult that property’s specification and/or your local reverse-engineer for details.

https://drafts.csswg.org/cssom-1/#serializing-css-values

If a property `foo` accepts a value `a` and later followed by a value `b?` defaulting to `0`, omitting `0` specified for `b` is obviously expected. 

But should it be omitted in the reverse situation where `b?` *becomes* optional, like the second `<length>` of `box-shadow-offset`?
