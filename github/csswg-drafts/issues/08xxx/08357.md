`:target-within` and `:focus-within` were added to the language during an era when we thought we could never do `:has()`. They are special cases of `:has()`, namely to `:has(:target)` and `:has(:focus)`. Now that we have `:has()`, there's no reason to have them in the language. `:target-within` has no implementation, so we could just drop it. `:focus-within` is widely used (~[8% of websites](https://docs.google.com/spreadsheets/d/1OU8ahxC5oYU8VRryQs9BzHToaXcOntVlh6KUHjm15G4/edit#gid=370286500)) but it may make sense to deprecate so we could drop it one day, if usage drops.

## @Loirooriol — 2023-01-26

Just pointing out that

 - `:focus-within` includes the element itself, so it may be convenient to avoid `:is(:focus, :has(:focus))`
 - `:focus-within` includes descendants in the flat tree, unlike `:has(:focus)`
 - It's likely that `:focus-within` has better performance

## @dbaron — 2023-06-14

I think the other value of these selectors is that they are much faster than `:has()` (though they require the browser to do a little bit of extra up-front work to get that benefit).  I'm still quite concerned that `:has()` is going to create selector performance problems that will require things like lints to forbid `:has()` and developers to know to avoid it.

While in theory we could detect and optimize some very specific cases of `:has()` such as `:has(:target)`, that seems like it would create more confusion around what the performance characteristics of CSS selectors are.  There's value in creating a platform that is understandable to the developers that use it -- and this does apply to its performance characteristics.

<!-- comment id=1591205797 author=dbaron created=2023-06-14T13:24:45Z url=https://github.com/w3c/csswg-drafts/issues/8357#issuecomment-1591205797 -->
## @dbaron — 2023-06-14

I believe the performance of `:has()` is significant in some cases, although that belief is based on conversations with implementers rather than measurement.  In particular, I see occasional suggestions for things like implementing a dark theme checkbox using `:root:has(#dark-theme-control:checked) ...` selectors, and my understanding is that a significant number of `:root:has(...)` selectors on a large page would add up to a measurable performance problem.

<!-- comment id=1591324038 author=LeaVerou created=2023-06-14T14:24:03Z url=https://github.com/w3c/csswg-drafts/issues/8357#issuecomment-1591324038 -->
## @LeaVerou — 2023-06-14

I suspect once such usage of `:has()` becomes more widespread, there will be further optimizations for common patterns. We should not be designing CSS syntax around transient performance issues. Especially since such messaging takes a very long time to go away — there are devs even today who hesitate to use descendant selectors because of 2010 era guidance around selector performance.
