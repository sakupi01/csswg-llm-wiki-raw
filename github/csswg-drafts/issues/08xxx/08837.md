- [my article with the experiments](https://kizu.dev/anchor-positioning-experiments/)

While thinking of various use-cases for the anchor positioning, I was thinking: could we want to have multiple effects based on it applied to the same element? If so, for this, we could want to have multiple different anchor names assigned to the same element, so different positioned elements could be attached to the same item declaratively, without the need for them to know the exact name of this element.

For example, we could want to have a tooltip attached to an element, but also to cross-reference it with some other element, and/or have a footnote for it.

Without an ability to have multiple names to the same elements, we could only work around this in the following ways:

- Assign a unique id for the name, and then somehow communicate it to the “recipients”.
- Use multiple wrappers/added pseudo-elements just for the sake of having multiple names available.

Both of these are not ideal.

What if the `anchor-name` could be a `<dashed-ident>+` instead of just a `<dashed-ident>`? There are other precedents like [`container-name`](https://drafts.csswg.org/css-contain-3/#container-name) which is defined as `<custom-ident>+`, so having the anchor-name follow the same logic would be consistent?

Are there reasons not to do this?

(On a related note — given that there would be cases where the anchor would get an implicit name, like when using the Popover API, what if those names could be always used via something like an implicit `list-item` counter, basically we could have a built-in ident just for those implicit cases, allowing an element that has a popover to still have other anchors attached to it etc).

Was reading the recent [exploration](https://fantasai.inkedblade.net/style/specs/css-anchor-exploration/#anchor-lookup) by @fantasai, @jensimmons and @mirisuzanne and noticed that it also defined the `anchor-name` as `<dashed-ident>`, and not as `<dashed-ident>+`. Was there a reason for that as well?

Also, cc @tabatkins and @xiaochengh — allowing defining multiple names for a single element seems like an easy win unless there are caveats I'm not aware of. The need for this came up a lot in my experiments.

## @xiaochengh — 2023-07-26

I don't see any issue with `<dashed-ident>+`. We should change it so if that's useful.

<!-- comment id=1654757077 author=tabatkins created=2023-07-27T23:34:32Z url=https://github.com/w3c/csswg-drafts/issues/8837#issuecomment-1654757077 -->
## @tabatkins — 2023-07-27

Yeah there's no particular reason to limit it to one name, except simplicity. If it's useful to allow multiple that's fine, it doesn't change anything about the spec.

<!-- comment id=1687438989 author=fantasai created=2023-08-22T05:10:49Z url=https://github.com/w3c/csswg-drafts/issues/8837#issuecomment-1687438989 -->

+1 to @tabatkins and @xiaochengh. I think we should aim to be consistent with scroll-animations syntax, though, so that would be `<dashed-ident>#`.
