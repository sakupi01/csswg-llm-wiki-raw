It is currently *impossible* to detect elements with a shadow root without direct traversal and checking `element.shadowRoot` for every single element, which is costly.

Use cases:
- DOM traversal across the flattened tree, to identify which elements they to do extra work on. For example fetching elements of a particular type across the entire flattened tree (e.g. for an HTML polyfill)
- Cloning a subtree properly that may contain declarative shadow roots (they disappear with `cloneNode(true)`).
- In general, handling declarative shadow roots properly and shadow roots ad hoc attached to elements without a CE (e.g. to fix [this Vue bug](https://github.com/vuejs/core/issues/12813))
- Handling CEs have been defined but not yet properly initialized (`:defined:not(:has-shadow)`) 
- Targeting SSR-rendered CEs (`:has-shadow:not(:defined)`)

It’s probably pretty easy to add a pseudo-class for this that matches if the element has an open shadow root. 

Design decisions:
- Should this also match **closed** shadow roots? They are already detectable by calling `attachShadow()` on the host (the error even mentions that a shadow root already exists), so this wouldn't be leaking any private state.

Related: 
- #11001
- https://github.com/whatwg/dom/issues/1422
- https://github.com/whatwg/dom/issues/1475
- https://github.com/whatwg/dom/issues/1287

## @hiroya-uga — 2026-04-16

Hi! I'd like to share a use case.

I use a third-party widget that requires domain registration before it initializes. The host structure looks like this:

```html
<li>
  <div id="widget">
    <script src="..."></script>
    <script src="..."></script>
  </div>
</li>
```

Until my domain is approved, no shadow root is attached and the `<li>` renders as an empty placeholder. Once registered, an open shadow root is created and the widget renders.

I want to hide the `<li>` with CSS until the shadow root appears:

```css
li:not(:has-shadowroot) {
  display: none;
}
```

or

```css
li:not(:has(::shadow-root)) {
  display: none;
}
```

This may be a niche case, but it represents a pure CSS styling use case — distinct from the JS/DOM traversal use cases already discussed here and in #2908.   
So I decided to leave a comment.

Personally, I prefer the `:has-shadowroot` syntax. Since this feature is intended for DOM traversal only, I think directly styling `:host` from outside should remain impossible — for both open and closed shadow roots — in order to preserve encapsulation.

I hope this helps the discussion.

## @LeaVerou — 2026-06-23

> It probably makes sense that this would not match closed shadowRoots? If it did, it would leak that detail, which might be unacceptable. It'd also match built-ins with shadowRoot which is likely undesirable.

That detail is already available — trying to attach a shadow root to an element with an existing closed shadow root throws with:

```
VM25:1 Uncaught NotSupportedError: Failed to execute 'attachShadow' on 'Element': Shadow root cannot be created on a host which already hosts a shadow tree.
    at <anonymous>:1:10
```

So I now think `:has-shadowroot` should match both, with a parenthetical form for the type of shadow root (`:has-shadowroot(open)` vs `:has-shadowroot(closed)`)

## @sorvell — 2026-08-05

I think this should likely match closed shadowroots. It's not important to hide the fact that an element has a (closed) shadowroot; it's only important to prevent it easily from being modified.

One can basically "detect" a closed shadowroot in JS already ([example](https://codepen.io/editor/Steve-Orvell/pen/019fd229-173a-7753-817a-021578253471)).
