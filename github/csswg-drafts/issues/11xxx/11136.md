There are currently three `<whole-value>` substitution functions: [`first-valid()`](https://drafts.csswg.org/css-values-5/#first-valid), [`interpolate()`](https://drafts.csswg.org/css-values-5/#funcdef-interpolate), `toggle()`. All are resolved at computed value time or later.

Using them as a shorthand value is specified for `toggle()`, but not for the other two: should they expand like [arbitrary substitutions](https://drafts.csswg.org/css-values-5/#substitution-in-shorthands), with a pending-substitution value?

## @tabatkins — 2024-11-01

> But I think first-valid() is resolved at parse time?

No, it's not. If you're solely providing literal arguments, then yes, it *could* be, but then you could just write them as separate declarations for the same effect.  The point of first-valid() is to take var()s in their arguments, so in practice it's always resolved at computed value time, during substitution. For consistency, we just make it *always* resolve then, like the other arbitrary-substitution functions.

## @tabatkins — 2025-01-31

Ah, I can see how my #5055 comment can be taken like that, but no. `first-valid()` is resolved "at parse time", but "at parse time" gets delayed when there's an arbitrary-substitution function involved. My point in that comment is that there's no special complexity involved here; you just do necessary substitution, then check parse-validity of the arguments.

But *if* you're not using a substitution function, then first-valid() is indeed resolved at *normal* parse time. For example, `display: first-supported(foo, bar);` from your example is indeed invalid at parse time, throwing out the declaration, because neither `foo` nor `bar` are valid `display` values.
