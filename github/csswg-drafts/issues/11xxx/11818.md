The new `attr()` behavior is inconsistent with the old one when attribute does not exist, new `attr()` will be IACVT and the old one would produce an empty string.

This is consistent with behavior of substitution functions in general, but since it's a breaking change, our users see this as a [regression](https://crbug.com/396334721). Example:
```
<style> 
  div::after { content: attr(data-text); }
</style>
<div>Test</div>
```
While with old `attr()` behavior the pseudo element `::after` with empty content will be created, with the new one the `attr() ` would be IACVT and hence the pseudo element would not be created.

Proposing the following spec changes to [7.7.1. Attribute Value Substitution](https://drafts.csswg.org/css-values-5/#attr-substitution):

> If there is no attribute named _attr name_ on _el_ and the _fallback_ is omitted, return an empty string.

Ah dang, that makes sense.

I propose that we limit this behavior to specifically the *omitted* type value, as this is a legacy compat issue. Having IACVT is useful otherwise, because you can key off of the failure and do something else.

Oops, I'm really sorry, seems like [spec already says that](https://drafts.csswg.org/css-values-5/#attr-notation:~:text=If%20the%20%3Csyntax%3E%20argument%20is%20omitted%2C%20the%20fallback%20defaults%20to%20the%20empty%20string%20if%20omitted%3B%20otherwise%2C%20it%20defaults%20to%20the%20guaranteed%2Dinvalid%20value%20if%20omitted.):

> If the [<syntax>](https://drafts.csswg.org/css-values-5/#typedef-syntax) argument is omitted, the fallback defaults to the empty string if omitted; otherwise, it defaults to the [guaranteed-invalid value](https://www.w3.org/TR/css-variables-1/#guaranteed-invalid-value) if omitted.

Ah, while the spec did say that in the argument descriptions, the attr() substitution algo didn't; it handled the omitted fallback explicitly, and didn't take an omitted syntax into account. That's fixed now.
