## @ccameron-chromium — 2025-02-20

Scattered thoughts:

My inclination is that this shouldn't make things that weren't HDR become HDR. It should clamp colors to wherever they were clamped before.

But what happens if this is applied to already-HDR content, or a mix of HDR content?

This API is not a good one for enabling HDR, because it works in absolute headroom (and we don't want to expose that, either for privacy or for performance reasons).

<!-- comment id=2672413543 author=svgeesus created=2025-02-20T19:01:00Z url=https://github.com/w3c/csswg-drafts/issues/11752#issuecomment-2672413543 -->
## @svgeesus — 2025-02-20

CSS filters are, as currently specified and implemented, restricted to `sRGB` and clamped to the `[0, 1]` range. Even extending them to SDR P3 is problematic

<!-- comment id=3055884748 author=aaronth07 created=2025-07-10T06:52:02Z url=https://github.com/w3c/csswg-drafts/issues/11752#issuecomment-3055884748 -->
## @aaronth07 — 2025-07-10

This is a little old, but why not give the option? Clamp by default, but if somebody sets the dynamic range to higher than SDR, then allow the filters to move into HDR color and luminance ranges. Artificially clamping the output would look wrong on HDR displays with mixed content sources.

However, similar to what svgeesus was implying, the filter(s) would need to be rewritten to utilize HDR output.
