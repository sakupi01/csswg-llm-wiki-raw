This is more-so related to the associated event for `content-visibility: auto` (i.e. `contentvisibilityautostatechange`). I noticed that in Chrome (131) this bubbles, while in Safari (18.1) and Firefox (133) it does not. I was planning on making a WPT for this, but I don’t really know what the behaviour should be, so I figured I’d ask here. [The relevant section in the spec](https://drafts.csswg.org/css-contain/#content-visibility-auto-state-change) mentions nothing about bubbling.

I made [a demo highlighting the bubbling problem](https://knowler.dev/demos/WA2d_f9).

Thank you for the spec reference, although I still fail to see any description of bubbles being false, other than in IDL function signatures. The rest of the spec references things like "set `bubbles` to _bubbles_" but doesn't really specify what is the value of _bubbles_ if it isn't explicitly stated. Anyway, that's a bit besides the point, it was just a curiosity.

> And that use case... just use a capturing event listener in such perhaps a bit unusual case.

I disagree that the case here is unusual. This is the intended use of the `contentvisibilityautostatechange` event, as outlined in the explainer. Toggling work for some subtree is frequently a more involved process than adding `content-visibility: auto` to some children of an element, so forcing the developer to necessarily add an event listener to each element affected by `content-visibility: auto` is awkward. Hence the case of observing such changes in some ancestor, I would argue, is the common use case for the event.

I would also push back on just using a capturing event listener. Yes, that can work, but bubbling the event also works. I think bubbling is a bit more flexible in that it allows multiple levels of ancestors to react in an appropriate way to the event. 

Is there a positive argument for not bubbling?

## @LeaVerou — 2026-07-30

> This isn't one of these events. Are there other principles that cause us to prefer non bubbling?

I suggested one earlier: 
> _would bubbling prevent more bugs than it would cause?_

bugs that it would cause = unintentionally listening to events from descendants when you didn't intend to (think of the old `mouseover`/`mouseout` bugs which led to `mouseenter`/`mouseleave`)

I think a better formulation might be are there more cases that need to listen to descendants or more cases where that would cause bugs? 

`capture: true` is essentially an explicit opt-in to event delegation. I can't think of any downside to it except that it's less common. So I think even 50-50 isn't enough, there would need to be _significantly_ more cases that need delegation than cases where that's a bug.
