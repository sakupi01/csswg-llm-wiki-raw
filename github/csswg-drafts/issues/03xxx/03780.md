I've been trying to figure out how to have different styles on left-hand and right-hand pages of paged media. It seems that css-page only defines margins and gutter and crop marks and such, and while it supports page numbering, it doesn't seem to affect page formatting.  Left-hand and right-hand pages want to be different because of the way books are bound. Floats are the first issue that came to my attention in this regard, although there may be others.  I applaud the extension of floating to the vertical as well as horizontal direction, but the horizontal direction still doesn't seem to have the ability to put float a block left if it is on a left-hand page and right if it is on a right-hand page, or vice-versa. Many printed books use such a style, but as far as I can tell, in the latest drafts there is not yet a method to implement such a style.

## @fantasai — 2019-04-17

There were proposals to handle this in early drafts of css-regions and css-scoping, see https://www.w3.org/TR/2014/WD-css-scoping-1-20140403/#fragment-scoping ... however, this is really hard! See the issues against ::first-line style resolution as an idea.  It gets even worse with layout-affecting things like floats and margins, basically tossing in a large chunk of the layout complexity of overflow fragments https://www.w3.org/TR/css-overflow-4/#fragment-overflow or regions..

Bottom line, we'd like to do it, but it's super complicated, so it's not happening in the near future! But it **is** on the to-do list?

Fwiw, pathway to getting there is

1. Fix ::first-line style resolution to be precise, understandable, interoperable, and usable -- we will reuse this model for per-fragment style inheritance within a styled container.
3. Get overflow fragments specced and implemented, including variable-width fragmentation (see https://www.w3.org/TR/css-break-3/ ) -- this gets us per-fragment box layout.
4. Define and implement region-scoped selectors -- this gets us per-fragment style resolution within a container.
5. Relax restrictions on what can be scoped per-page now that we can do per-fragment inheritance, style resolution, and layout!

Unfortunately, each of these steps is a major project, implementation-wise. And not particularly easy to spec, either. I guess, follow along with ::first-letter fixes, each one is one step closer to per-page styling? :)

## @cmahnke — 2025-11-23

I came accross this issue a few days ago, initially since I suspected it to be not working to be a bug in [Prince](https://www.princexml.com/).

The full context is on the forum:
https://www.princexml.com/forum/topic/5193/different-flex-orders-for-spreads

Just so that not everyone has to read the full thread. My assumption was that the following will work:
```css
@page :left {
  margin-left: 1cm;
  margin-right: 1.5cm;
  
  @bottom-left {
    content: counter(page);
    vertical-align: bottom;
  }
  
  article.entry .page .text {
    order: 2;
    text-align: right;
  }
  
  article.entry .page .image {
    order: 1;
  }
}

@page :right {
  margin-left: 1.5cm;
  margin-right: 1cm;
  
  @bottom-right {
    content: counter(page);
    vertical-align: bottom;
  }
  
  article.entry .page .text {
    order: 1;
    text-align: left;
  }
  
  article.entry .page .image {
    order: 2;
  }
}
```

The funny part is that [Paged.js](https://pagedjs.org/) supports this, but as we've concluded in the linked thread, that might be by accident- maybe even to be considered a bug.

My standpoint is that this is a quite common use case for printed (and bound) material like books, brochures and magazines. So it should be specified within the next iteration of the Paged Media module. Given the fact that implementing a updated specification will likely take some time (small number of years), I would consider it urgend. I have to admit that I'm a bit disappointed in the folks who try to sell one CSS as way to do modern printing (which a certainly not the people who read here), for not pushing this issue - currently some claims (in the form that CSS is already a possible replacement for XSL-FO) fell just dishonest (or at least uninformed).

Mark Brown mentioned in the thread the [CSS containment module](https://www.w3.org/TR/css-contain-3/) ant though I get how this can help in this specific use case, I wouldn't call it a straight forward solution, since in introduces another (not yet widely used) concept: container queries.  Being either able to define selectors within `@page :right` or having the possibility to do a media query (see below) for the spread side would have the benefit that existing knowledge on how to use @-rules or media queries to solve the problem.

I'm well aware of the fact that having a simple solution can cause more issues with (page) overflows down the road, but having a well known syntax will certainly outweight the potential backdraws.

Anyways: In thread I was raising the question why we couldn't have solved this by something like a media query, since from my perspective the binding edge (which is for my requirements the defining feature for a left or right spread) is comparable with detection of screen width or orientation on a display device `screen`.

It would also be nice to have a example for this within the next specification.

As for this issue: I'm not sure (as @rachelandrew already implied) that the prefix of this issue (`[css-page-floats]`) is right, maybe someone can move it into the Paged Media namespace (by editing the title)?
