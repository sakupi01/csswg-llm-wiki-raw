https://drafts.csswg.org/selectors-3/#lang-pseudo

The draft says

> The pseudo-class :lang(C) represents an element that is in language C. Whether an element is represented by a :lang() selector is based solely on the element's language value (normalized to BCP 47 syntax if necessary) being equal to the identifier C, or beginning with the identifier C immediately followed by "-" (U+002D). The matching of C against the element's language value is performed case-insensitively within the ASCII range. The identifier C does not have to be a valid language name.

The "normalized to BCP 47 syntax if necessary" opens a can of worms. It implies that the user agent should take locale strings such as "en_US" or "it_IT.utf8" and normalize them to BCP 47's syntax if necessary (which would be "en-US" and "it-IT"). Please do not suggest that an element's language can be set with xml:lang="en_US" or lang="it_IT.utf8" and the user agent will "normalize" it to a BCP 47 language tag.

## @AmeliaBR — 2018-08-16

I suspect part of the vagueness is because the CSS pseudoclass is designed to work with many different document types, which may have their own syntaxes for specifying the element language.

CSS uses BCP 47 in the `:lang()` selector. If a document type uses a different syntax, the user agent needs to convert it to  BCP 47 in order to test equality.

The allowed values for the [`lang` attribute in HTML](https://html.spec.whatwg.org/multipage/dom.html#the-lang-and-xml:lang-attributes) and the [`xml:lang` attribute in XML](https://www.w3.org/TR/2006/REC-xml11-20060816/#sec-lang-tag) are defined in those specifications. HTML specifies BCP 47, XML references rfc 3066. I'm not an expert on the differences between those two, but I'm pretty sure "en_US" isn't valid for either.

While the offending text in this issue has been resolved, other changes to the text may have brought in language tag conversion through the back door. Specifically:

> The element’s [content language](https://drafts.csswg.org/css-text-4/#content-language) matches a [language range](https://drafts.csswg.org/selectors-4/#language-range) if its content language, as represented in BCP 47 syntax, matches the given language range in an extended filtering operation per [[RFC4647]](https://drafts.csswg.org/selectors-4/#biblio-rfc4647) Matching of Language Tags (section 3.3.2). Both the content language and the language range must be canonicalized and converted to extlang form as per section 4.5 of [[RFC5646]](https://drafts.csswg.org/selectors-4/#biblio-rfc5646) prior to the extended filtering operation. The matching is performed [ASCII case-insensitively](https://infra.spec.whatwg.org/#ascii-case-insensitive).

This requires the "content language" to be canonicalized and converted to extlang form using BCP47's rules. While garden variety strings like `en_US` or `it-IT.utf-8` or `English` can be "canonicalized" and potentially put into extlang form (before not matching very well). Should there be an explicit note about this?

## @GLRoylance — 2026-05-28

:lang() should take only IETF langtag syntax.

If the langtag syntax fails, then there is no match. Matching should only be done between IETF langtags.

Strings such as it_IT.utf-8 are typically locale strings and are intended to be opaque. There is a typical format (typically of the form language[_territory][.codeset][@modifier]), but a locale string may be opaque. (See, for example, https://man7.org/linux/man-pages/man3/setlocale.3.html stating that setlocale may return an opaque string.) The contents of such strings may change. Avoid the can of worms.

Wikimedia opened the can of worms for SVG's systemLanguage attribute, and it is still an unresolved mess. Wikimedia takes a langtag, tries to convert it to a corresponding Unix locale string, feeds that locale string to the operating system, and then hopes a library converts the locale string to the original langtag. It works for simple cases such as de but fails for de-DE and zh-Hans. The de-DE langtag is turned into a de_DE locale string, and that locale string is turned into Accept-Language de-DE, de. Yes, a better library could do a better job, but what if there is no locale string that corresponds to zh-Hans?

Keep things simple. If you want complicated matching to work, then work in a domain where the strings and operations are well defined.

If some document wants to use CSS :lang() selectors, then it should use the IETF langtag format.

## @aphillips — 2026-05-28

@GLRoylance noted:
> If some document wants to use CSS :lang() selectors, then it should use the IETF langtag format.

I agree with your comment in general and agree with this sentiment. I don't want to encourage POSIX locale-like strings under any circumstances, but they aren't probably the high-runner case for bad tagging??

My suggested texts are the way they are because I was reluctant to completely forbid non-valid language tags. For one thing, "valid" means having a copy of the LSTR and having it be up to date. Match behavior could vary over time as a result of that. Having non-valid tags canonicalize as themselves permits very specific matching, e.g. `lang=English` == `:lang(english)` without permitting garbage such as `lang=en_AQ@UTF-8` from matching `:lang(en)`. 

We *can* forbid non-valid tags/ranges from ever matching. The text for that might be:

> The element’s [content language](https://drafts.csswg.org/css-text-4/#content-language) matches a [language range](https://drafts.csswg.org/selectors-4/#language-range) if its content language, as represented in BCP 47 syntax, matches the given language range in an extended filtering operation per [[RFC4647]](https://drafts.csswg.org/selectors-4/#biblio-rfc4647) Matching of Language Tags (section 3.3.2). The content language and the language range must be canonicalized and converted to extlang form as per section 4.5 of [[RFC5646]](https://drafts.csswg.org/selectors-4/#biblio-rfc5646) prior to the extended filtering operation; language tags or ranges that are not [valid](https://www.w3.org/TR/i18n-glossary/#dfn-valid) do not match anything. The matching is performed [ASCII case-insensitively](https://infra.spec.whatwg.org/#ascii-case-insensitive).
