## Level 6 `contrast-color()`

A summary of the current situation is as follows:

- **Biggest roadblock:** There is currently no problem-free contrast algorithm we could use as a default.
	- WCAG 2.1 algorithm, despite very wide usage, is severely flawed, even for only grayscale colors, or only picking between black and white. [False positives/negatives up to 40% (!)](https://www.cedc.tools/article.html).
	- APCA which has been advertised as a successor has issues too, including [a patent disclosure](https://www.w3.org/2004/01/pp-impl/patents/174?fbclid=IwAR3UBZB1WlBDpuelNWqukpPDmGBpXju7O94OEM2Bs2m3HBbz2nSp6A9_V2g) (not an exclusion), which makes baking it in CSS tricky.
	- There are [other contrast algorithms](https://colorjs.io/docs/contrast.html) (Weber, Michelson etc) but do not generally produce good results.
	- Relevant issues:
		- #7356 
		- #7361
		- #7357

## @danielcamposramos — 2026-11-02

An implementation report on `contrast-color()`, from two renderers outside the browsers.

CSS Color 5 §8 advises UAs "to not simply use the WCAG 2.1 section 1.4.3 Contrast (Minimum) contrast ratio algorithm", and #7361 resolved that the default is "the best available to the UA, which gets updated".
Today the three engines resolve it by the WCAG 2.1 ratio alone:
- WebKit, [CSSContrastColorResolver.cpp L37-L44](https://github.com/WebKit/WebKit/blob/0f12ab8938f6d250560003ba3e43215aae7c0934/Source/WebCore/css/values/color/CSSContrastColorResolver.cpp#L37-L44), with a FIXME for a non-naive resolution; its `>` returns black on a tie, where §8 says white.
- Gecko, [computed/color.rs L113-L128](https://github.com/mozilla-firefox/firefox/blob/cd3dab7712655521bb111039c077b2a2a8f98b5a/servo/components/style/values/computed/color.rs#L113-L128), with a TODO pointing at APCA.
- Blink, [style_color.cc L198-L209](https://github.com/chromium/chromium/blob/fe2f822bfb5513271c8c884dc520337ed982cad4/third_party/blink/renderer/core/css/style_color.cc#L198-L209).

Qt SVG ([change 785347](https://codereview.qt-project.org/c/qt/qtsvg/+/785347), in review) and librsvg (a proposal to follow) are gaining `contrast-color()` now, and we use both checks, in order:
1. Readability first: black when the background's Oklab lightness is above 0.7, white otherwise, from [Lea Verou's measurements](https://lea.verou.me/blog/2024/contrast-color/) (between 68.7% and 71.6% neither black nor white text fails APCA).
2. Then WCAG 2.1 as the floor §8 requires: if that choice is below 3:1, the other colour, which always reaches at least 4.58:1.

On `#3498db`, for example, the WCAG ratio alone gives black and this rule gives white.
Lea's post now also gives 0.623 where WCAG compliance is required; the 3:1 step above keeps §8's requirement either way.

Would the group consider naming a recommended default of this shape, so that browsers and the renderers outside them give the same text colour for the same document?
