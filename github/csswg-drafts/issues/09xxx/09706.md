The `:checked` and `:indeterminate` pseudo-classes can apply to `<input type=checkbox>`:
https://drafts.csswg.org/selectors/#checked
https://drafts.csswg.org/selectors/#indeterminate

These are also defined in the HTML spec here:
https://html.spec.whatwg.org/#selector-checked
https://html.spec.whatwg.org/#selector-indeterminate

WebKit recently implemented support for matching both of these selectors at the same time since the "checked" and "indeterminate" states exist independently and don't force each other on or off when modifying via javascript: https://github.com/WebKit/WebKit/pull/21157

I was going to implement the same behavior in chromium to pass the WPT, but it was pointed out that the idea of matching both at the same time was never discussed here. Can we formally decide to allow this and perhaps add a note to the spec saying that both can match at the same time?

I'm curious if the fact that the CSS selector spec *used* to say this but now doesn't was an intentional or unintentional change to the selector spec.

From a usage perspective this change seems weird -- I think conceptually `:indeterminate` was intended to act like a third state that is distinct from `:checked` and unchecked.  Even though it wasn't defined that way in the DOM, that doesn't mean it's desirable to expose the DOM weirdness about it in *more* places.

## @tabatkins — 2026-05-21

Pulling out my point from the minutes:

A lot of argument *for* preserving the independence of these two is that HTML can express a checked indeterminate *or* unchecked indeterminate, and clicking the checkbox will un-indeterminate it *and* either check or uncheck it as normal. So there are two *very similar* states in HTML - mixed-but-will-check-everything and mixed-but-will-uncheck-everything.

My point in the call is that, in my experience, I have *never* seen that presents a "mixed" checkbox actually represent those two states distinctly. For example, in Gmail, the select-all/unselect-all checkbox has a mixed state when you manually select some email, but when you click the checkbox, it *always* reverts to unchecked. Other, less well-designed, UIs sometimes just make the "everything checks or unchecks" decision up to however the checkbox state happened to be before it became mixed, so the user might have to click the box twice to get to the state they want.

I've just never, myself, ever seen a UI that actually presents two different mixed states based on whether clicking it will go to all-checked or none-checked. And nobody in the call could produce an example off the top of their head - attempts to, instead, resulted in describing scenarios with a single mixed state instead. There might very well be such a case in existence, but is it something we really need to cater to in CSS?

I submit that it's better for CSS to reflect the (as fas as I can tell) practical UI pattern of a 3-state toggle, which also matches the ARIA model. The fact that HTML *technically* has two distinct mixed states just isn't relevant as a UI concern.

-----------

There was a further concern in the call that people might want to use selector matching to tell what checkboxes are checked or unchecked (to know whether they'll submit or not) regardless of whether they're indeterminate or not. I suspect that's just not a real issue in practice - on a *single* checkbox it's easier to do `el.checked` than `el.matches(":checked")`.  For multiple elements, `document.querySelectorAll(":checked")` is a little easier than `document.querySelectorAll("input").filter(x=>x.checked)`, but not by much.

## @AutoSponge — 2026-05-22

> The fact that HTML technically has two distinct mixed states just isn't relevant as a UI concern.

I disagree which is why I needed to make the example below. Which also shows that the browsers don't agree, yet.

I made a [test page](https://codepen.io/editor/AutoSponge/pen/019e51b3-9061-7b65-8745-64c7a16a4836) and tested safari, chrome, edge, and firefox. Native CSS selectors are inconsistent across browsers for the case of indeterminate checked (intent uncheck all). This can be achieved using aria checkboxes, through some other stateful property hack, but the intent is not currently conveyed to AT without an additional description.

Here are a few paths forward for consideration:

* **Option 1: Align CSS & ARIA with WHATWG State Machine**
  * **Behavior:** Safari and Firefox are treated as correct for reflecting the WHATWG state machine with CSS pseudo-selectors (which would mean correcting CSS Selectors Level 4 §12.2). Chrome and Edge update for consistency.
  * **A11y Impact:** ARIA and `html-aam` receive proposals for mappings to `mixed-true` and `mixed-false` (or equivalent) states in future versions. AT vendors can then provide better native contextual hints for checkboxes in intermediate states.
  * **Outcome:** AT users receive native, automated support without authors needing to append redundant descriptive text.

* **Option 2: Maintain CSS Spec Rigidity, Update ARIA Mappings**
  * **Behavior:** Chrome and Edge are treated as correct by strictly adhering to §12.2. This means the use case cannot be achieved natively with CSS alone; Safari and Firefox must update to reflect §12.2 exclusivity.
  * **A11y Impact:** ARIA and `html-aam` get proposals to align closer with native HTML so the intent-action of native HTML can be better conveyed through AT.
  * **Outcome:** AT vendors update descriptions, but CSS cannot be relied upon for this UI state—only ARIA will work for AT users.

* **Option 3: Maintain CSS Rigidity, No ARIA Changes (Status Quo)**
  * **Behavior:** Chrome and Edge are correct per §12.2. HTML is either deemed incorrect, or the platform accepts that HTML state is not intended to be fully reflected in CSS. Safari and Firefox alter their engines to match.
  * **A11y Impact:** ARIA, `html-aam`, and AT behaviors remain entirely unchanged.
  * **Outcome:** CSS cannot be used to distinguish these states; ARIA is the sole fallback mechanism for AT users, and the invisible state variance remains unaddressed.

* **Option 4: Decouple Selection/Action Selectors entirely (The "Intent" Pseudo-class)**
  * **Behavior:** CSS Selectors Level 4 remains strict or exclusive for `:checked` and `:indeterminate` as states, but the CSSWG introduces a *new* functional pseudo-class or modifier (e.g., `:stale`, `:reverting`, or an action-intent pseudo) specifically designed to expose what the *next* state will be upon activation. (Safari and Firefox alter their engines to match Chrome/Edge).
  * **A11y Impact:** HTML-AAM can cleanly map this new selector's logic to AT without conflicting with the classic tri-state checkbox paradigm.
  * **Outcome:** Solves the "invisible state variance" problem TabAtkins mentioned by providing authors with an explicit tool to style the difference between an indeterminate box that will *clear* all versus one that will *select* all, without overloading the definition of `:checked`.

I'm not sure when that line was added to Selectors, but ever since `:checked` and `:indeterminate` matching has been defined by HTML they were not exclusive. ## @tantek — 2026-07-15

&gt; Also cc tantek who I think was (at least partly) responsible for creating indeterminate.

Yes, I introduced the concept of :indeterminate for consideration in:
* [https://www.w3.org/TR/1999/WD-css3-userint-19990916#issues](https://www.w3.org/TR/1999/WD-css3-userint-19990916#issues) (issue 8)

And then formally wrote it up in:
* [https://www.w3.org/TR/2000/WD-css3-userint-20000216#pseudo-indeterminate](https://www.w3.org/TR/2000/WD-css3-userint-20000216#pseudo-indeterminate)

Will note explicitly from that link:
&gt; Radio and checkbox elements can be toggled by the user, but are sometimes in an indeterminate state, neither checked nor unchecked.

This was based on (now decades of) experience and practice of actual human computer interfaces with tri-state checkboxes/radiobuttons.

This was before it was ever written up in HTML.

I don’t know why HTML failed to adopt this semantic. It’s unfortunate we didn’t notice this bug in HTML for so long. Perhaps because it was possible to have contradictory DOM attributes and the HTML spec tried to retcon that into meaning something when it should have fixed it.

We should do “the right thing” here, which is define the feature (in Selectors, and HTML) to reflect actual developer need and usage, not some (likely) accidental bug introduced the HTML spec.

I am reminded of the similar stubbornly-precise but disconnected from real-world developer needs specification of :valid / :invalid which eventually forced the addition of :user-valid and :user-invalid.

Let’s avoid similarly introducing a :user-indeterminate because the HTML spec made a mistake.
