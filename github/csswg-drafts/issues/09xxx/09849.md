I believe the spec should be explicit about which, if any, ASCII control characters should be potential targets of highlight pseudos. For reference, the CSS Text Decorations spec says "Characters belonging to the Unicode classes for control codes and unassigned characters (Cc, Cf, Cn) are skipped...". That includes tabs.

However, chromium does paint tabs for selection, and has a bug (or feature) that it will draw underlines and highlights for tab characters when used in ::selection.

I see 2 possible resolutions:
- Adopt the Text Decoration behavior for highlights and make ::selection that uses such features follow the same rules.
- Special case the tab character as a control character that text decorations and highlights do apply to.

I don't think the behavior for text decorations and highlight should be different, given that text decorations can be used as highlights.

The spec about Highlight Overlays says this:
https://www.w3.org/TR/2022/WD-css-pseudo-4-20221230/#highlight-overlay
"Spacing between two characters may also be part of the overlay area ..."

To me, "Spacing" lumps together anything that makes space and I expect the behavior to be consistent across all kinds of spaces.

## @schenney-chromium — 2026-08-04

Updated links:

The Highlight Overlay area description: https://www.w3.org/TR/css-pseudo-4/#highlight-text "For text, the corresponding overlay must cover at least the entire em box and may extend further above/below the em box to the line box edges. Spacing between two characters may also be part of the overlay area, in which case it belongs to the innermost element that contains both characters and is selected when both characters are selected."

Emphasis skips control characters, which makes a lot of sense: https://www.w3.org/TR/css-text-decor-4/#text-emphasis-style-property

Text Decoration has [text-decoration-skip-spaces](https://www.w3.org/TR/css-text-decor-4/#text-decoration-skip-spaces-property) which implies the default is to underline the spaces assuming "none", so I suppose highlights should follow this behavior.

I propose we explicitly add information about which spaces are included in the overlay, using the terminology from the Text Decorations spec. Optionally, we could consider adding some way to control highlighting background area of spaces similar to text-decoration-skip-spaces.
