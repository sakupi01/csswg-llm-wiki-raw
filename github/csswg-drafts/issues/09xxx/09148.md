When using `text-box-trim: both; text-box-edge: text`, outcomes vary greatly depending on the font's metrics. Many fonts set line gap metrics to 0 and instead distribute that space among their ascenders and descenders to ensure appropriate default spacing, as explained in this [documentation](https://silnrsi.github.io/FDBP/en-US/Line_Metrics.html) and in the [Google Vertical Metrics Specification](https://googlefonts.github.io/gf-guide/metrics.html#8-linegap-values-must-be-0).

As a result, trimming to `text-box-edge: text` might not give the expected result. 

![ascent-and-decent-including-line-gap](https://github.com/w3c/csswg-drafts/assets/175195/5de32df0-427b-49ac-9c52-a1278892a64b)

### Proposal:

For better customization, it would be beneficial to extend the `text-box-edge` property to support the [em-over](https://drafts.csswg.org/css-inline-3/#em-over-baseline) and [em-under](https://drafts.csswg.org/css-inline-3/#em-under-baseline) baselines. Moreover, an author-defined baseline would further enhance this flexibility, especially when predefined font baselines fall short.

Support `text-box-edge: em` or a more flexible `text-box-edge: <number>` or `text-box-edge: <length>`

### Use case:
Consider trimming the first or last line of text to align with em-based decorations:

<img width="540" alt="image" src="https://github.com/w3c/csswg-drafts/assets/175195/6ee36eab-1656-40c5-a38c-e6cdd5c8645b">

In the above blockquote, the intent is to trim the leading from both the first and last lines. The blockquote features corporate identity shapes, with the circle sized at 1em. Post-trimming, the text should align with this circle.

Given that the font integrates an additional 0.2em space between its ascender and descender metrics:

- `text-box-edge: text` would leave 0.1em half-leading above the text due to the font metrics, misaligning it with the shapes.
- `text-box-edge: cap alphabetic` eliminates all half-leading, aligning the text with the circle's top, not its center.

Current workarounds involve adding extra elements and using negative margins.

Allowing a user defined text-edge would provide more flexibility for use cases like this:
`text-box-edge: em` or `text-box-edge: 1em`

## @johannesodland — 2025-04-16

Glyphs have more information about the different vertical metrics strategies in use: 
https://glyphsapp.com/learn/vertical-metrics

The "Google strategy" not only distributes leading to the ascender and descender metrics, but adjusts the descender metric so that capital letters are vertically centered in the box defined by the ascender and descender metrics.

With these strategies, there seems to be no way to trim to the actual ascenders and descenders.

## @fantasai — 2025-10-15

As @jfkthame and others note in the call, there's no good way for the UA to guess at the intended metrics. For some fonts such as a basic sans-serif, some heuristics could be usable, but this isn't generally true. And the em metrics are also a heuristic that isn't particularly reliable if we consider the wide variety of font styles and writing systems that need to be accommodated.

The best way to solve for wrong metrics is probably to use the override descriptors in `@font-face`. https://www.w3.org/TR/css-fonts-5/#font-metrics-override-desc

I think [`@font-face`](https://developer.mozilla.org/en-US/docs/Web/CSS/@font-face) could be used like this:

```
@font-face {
 /* ... description of font */
 ascent-override: 80%; /* this is just an example; it'd actually be deduced from what you want to remove the undesired spacing */
 descent-override: 90%; /* this is just an example; it'd actually be deduced from what you want to remove the undesired spacing */
}
```
