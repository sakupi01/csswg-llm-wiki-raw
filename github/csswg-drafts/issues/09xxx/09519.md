In the [css-scroll-snap-1 spec section 4.1.1](https://drafts.csswg.org/css-scroll-snap-1/#snap-axis) it states that for the scroll-snap-axis both:
> The [scroll container](https://drafts.csswg.org/css-overflow-3/#scroll-container) [snaps](https://drafts.csswg.org/css-scroll-snap-1/#scroll-snap) to [snap positions](https://drafts.csswg.org/css-scroll-snap-1/#scroll-snap-position) in both of its axes independently (potentially snapping to different elements in each axis).

What's the use case for this? I would expect the common case is that the author would expects the UA to snap to both axes of that element if it snaps to that element. If an author wants to snap independently on different axes (e.g. for rows and columns of a table) they can specify snap alignment in a single axis.

Use cases where you'd for sure want alignment in both axes are any sort of 2d selection UI, e.g. a 2d panning map with multiple POI that snaps to a particular POI.

This in particular makes using the snapchanged / snapchanging apis in css-scroll-snap-2 more complicated if you do want to know which element is aligned in both axes.

## @flackr — 2026-06-01

> Some prior discussion on this

Forgive me, i'm having a hard time finding the actual discussion of when you want to snap to a different `scroll-snap-align: both` elements in the vertical and horizontal axes. The closest I see is https://lists.w3.org/Archives/Public/www-style/2014Jan/0591.html where it was discussed that you want to be able to make a scroller snap in one axis but not both.

Can we discuss this? I think it would be really helpful for some common use cases.

If we can't remove independent scroll snapping, could we add a keyword to opt into it? Maybe scroll-snap-type: [**element** | x | y | inline | block | both] [proximity | mandatory] where element snaps to a single element at a time (implied that it's in both axes).

Or alternately, if we think we can change the default but still want to support explicit independent alignment to `scroll-snap-align: both` we could add explicitly specifying both axes as meaning snap independently, i.e. `scroll-snap-align: both mandatory;` selects a single element where `scroll-snap-align: x y mandatory` snaps to different targets on each axis.

I believe the relevant discussion is in one of fantasai's links, <https://lists.w3.org/Archives/Public/www-style/2015Jun/0170.html>:

> The “partial grid” behavior is interesting, but problematic when scrolling: a vertical scroll could yank you sideways to go to nearby snap point. So I’m not sure we want to do this.

This was in support of independent axis snapping, rather than tied-together axis snapping to a single element. We ended up deferring the "cities on a map" snapping behavior that would tie them together, but we didn't rule out adding it back in.

## @flackr — 2026-07-29

So the syntax space where we have `both` is `scroll-snap-type`, which is a property of the scroll container. If this is indeed the property where we are adding the `pair` keyword, there is a question of what to do with elements which only have one `scroll-snap-align` axis, e.g.

```css
.scroller {
  scroll-snap-type: pair mandatory;
}
.block-and-inline {
  scroll-snap-align: center;
}
.block {
  scroll-snap-align: center none;
}
.inline {
  scroll-snap-align: none center;
}
```

Do we..
1. Only consider `.block-and-inline` elements and ignore the others, or
2. Allow snapping to both axes of a `.block-and-inline` element or snapping to a `.block` and a `.inline` element?
3. Something else?

IMO, I think (2) provides a valuable meaning to the `.block` and `.inline` in the same way that it works for `scroll-snap-type: both`, but (1) is simpler to reason about and I'm not sure if there are concrete use cases for for (2).
