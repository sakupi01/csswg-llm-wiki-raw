## @annevk — 2022-10-27

I chatted with @rniwa about this and I think he has a good point that this is a bit odd. For the HTML parser we're essentially using `<template shadow...>` as a macro to instantiate shadow trees and we preserve some of that state for serialization. But making it affect normal DOM operations as well turns it into a strange API whereby it's no longer just a parser macro. I tend to agree that if we want to support such cases we should offer a specialized API that would maybe also work if you put shadow trees in `template`'s contents yourself. (That specialized API can also be a future entry point for templating, where we also ran into needing something like that for the `template` element.)

<!-- comment id=1297725542 author=rniwa created=2022-10-31T21:46:53Z url=https://github.com/whatwg/html/pull/5465#issuecomment-1297725542 -->
## @rniwa — 2022-10-31

> For the HTML parser we're essentially using `<template shadow...>` as a macro to instantiate shadow trees and we preserve some of that state for serialization. But making it affect normal DOM operations as well turns it into a strange API whereby it's no longer just a parser macro.

I think the weirdness comes from the fact regular shadow trees are not cloned when you call importNode or cloneNode but declarative shadow trees are.

One way to rectify this weirdness might be to add an independent flag like "cloneable" as an argument to attachShadow. Declarative shadow DOM will implicitly set this flag to true by default (or maybe it could be explicit?).

Alternatively, we could introduce a new option dictionary like {includeShadowRoots: true} to allow cloning of shadow trees, and authors would have to use that API to clone shadow trees. This isn't so ideal because the author / maintainer of a component doesn't get a choice on whether cloning is allowed or not. So maybe we'd need cloneable flag in this case as well.
