This PR updates the content model for the `<select>`, `<option>`, and `<optgroup>` elements in support of customizable `<select>`.

The major additions are:
- `<select>` and `<optgroup>` can contain `<div>` elements.
- `<option>` elements can contain `<div>` and non-interactive phrasing content.
- `<optgroup>` can have a child `<legend>` to represent its label.

Fixes https://github.com/whatwg/html/issues/10317

Is the idea to allow `<select><div><h1><option>` and such? Or only `<select><div><div><option>`?

If the former, you need to change the definition of phrasing content to include "`option` (if it is a descendant of a `select` element), `optgroup` (if it is a descendant of a `select` element)".

## @scottaohara — 2024-10-22

we need to update the optgroup element with it's allowance of the `legend` element.

similar to option where someone can either use text, or label/value attributes - the optgroup should either have a label for the group rendered by the use of the `label` attribute OR by someone using a `legend` element.  

If both are defined (label attribute and legend element) one should win out over the other, like what happens with option and the current select > option.  


```
<select>
  <optgroup label=one>
      <legend>two</legend>
       ...
  </optgroup>
   <option label=A>B</option>
</select>
```

based on the way the current select works, for the option the visible label would be "A".
If optgroup were to follow suit, then arguably the legend should be ignored / have a UA style of display none.  personally though, i would rather the label attribute be ignored, and the legend is what is what gets visually rendered / names the optgroup.

## @scottaohara — 2024-10-30

This PR removes some important(?) context about option use within / outside of a datalist. 
for instance, without mention of datalist, the second condition in the option content model doesn't make sense / doesn't appear to do anything with the text inside of the option:
>If the element has a [label](https://whatpr.org/html/10586/form-elements.html#attr-option-label) attribute but no [value](https://whatpr.org/html/10586/form-elements.html#attr-option-value) attribute: [Text](https://whatpr.org/html/10586/dom.html#text-content).

per the above, if i have `<option label=foo>test</option>` with the current select, all browsers use "foo" as the visible text. But, per the current spec, this makes more sense because other conditions are for use of option as not a child of a datalist.  If the option is a child of a datalist, that example renders "test" as the primary label, and "foo" as a sort of sub-text (if rendered at all)... and at least chromium browsers expose that subtext as part of the option...

but again, that only works within a datalist, which would be good to point out (unless we want to do similar for options within a select - which could be useful.....)

Additionally, testing with the current chromium canary build, following the first content model condition results in no visible label for an option
>If the element has a [label](https://whatpr.org/html/10586/form-elements.html#attr-option-label) attribute and a [value](https://whatpr.org/html/10586/form-elements.html#attr-option-value) attribute: [Nothing](https://whatpr.org/html/10586/dom.html#concept-content-nothing).

so `<option value=foo label=test>` renders as an empty option with the customizable select, but renders "foo" as a visible label with the current select.

if the label attribute is not being used in the customizable select, i think this needs to be clearly stated.  (checking/rechecking the definition for option and the label attribute, i don't see this called out?)

but just as importantly, it should also be clear whether new content model allowances are only allowed within options of a styleable select, or if they are allowed for options in a datalist.  the current PR reads as if this is a change for everywhere, and i'm not sure if that's really the intent at this point?
