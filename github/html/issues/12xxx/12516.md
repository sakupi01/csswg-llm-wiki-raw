### What is the issue with the HTML Standard?

`<select>` in `appearance:base` has `counter(fake-counter-name, disclosure-open)`; https://html.spec.whatwg.org/#:~:text=fake%2Dcounter%2Dname.

This is really odd for a few reasons:

 - It looks really strange (like a hack or mistake). What even is `fake-counter-name`? It's not otherwise defined (I understand it is a type of `<counter-name>` but it has no relationship to the element and no other mention of it resides in the spec). Why are we using a counter at all, when it doesn't increment?
 - It's hard to explain to developers why this even exists in the way it does. I believe it mostly exists due to accidental complexity of e.g. `content` and the desire to use `disclosure-open`.

I think we can do one of two things here:

1. **Specify `content: "\25be"`.**:
   - Pros:
     1. This completely eradicates the `counter(fake-counter-name`
     2. Everyone is using `\25be` for the `disclosure-open` sigil anyway, so this is just less-roundabout.
     3. 
     4. `disclosure-open` is implementation defined, which means it's potentially a source of discrepancy in an otherwise standardised appearance. This would remove that discrepancy.
     5. Easy to ship right now - 1LOCSS change.
   - Cons:
     1. Doesn't align quite so nicely with `<details>`.
     2. Arguably `"\25be"` is more opaque or confusing compared with `disclosure-open` (even with the surrounding junk).

2. **Specify `content: <list-style-type>` within CSS, and specify `content: disclosure-open;`**:
   - Pros: 
     1. This completely eradicates the `counter(fake-counter-name`
     2. Retains the implementation defined `disclosure-open` name.
     3. Arguably clearer than `"\25be"`.
     4. Self explanatory to a developer, moreso than `counter()`
     5. Has a nice benefit of developers being able to simplify some css which uses a similar technique, e.g. `content: square` as opposed to `content: counter(fake, square)`. ([an attempt at finding examples](https://github.com/search?q=language%3Acss+%2Fcontent%3A%5Cs*counter%5C%28%28dummy%5B%5E%2C%5D*%7Cfake%5B%5E%2C%5D*%7Ctest%5B%5E%2C%5D*%7C%5BA-Z%5D%29%2C%5Cs*%28disc%7Csquare%29%2F+AND+NOT+%22fake-counter-name%2C+disclosure-%22&type=code))
   - Cons:
     1. Requires changes to `content` syntax, could get complex.

## @dbaron — 2026-06-09

Indeed, a big reason to use `disclosure-open` is that it changes appropriately for `writing-mode`.  It also has the advantage (over Unicode characters) that we're not at the mercy of font availability and variation, or needing to ship an appropriate font with the browser.  (So far I think our experiences of using Unicode in this sort of context is quite limited although I think not quite zero.)  In Chrome at least, `disclosure-open` has [custom drawing code](https://source.chromium.org/chromium/chromium/src/+/main:third_party/blink/renderer/core/paint/text_fragment_painter.cc;l=226-273;drc=001b5bdc78051d96a1646c791c5baac2a1b86734).  (Gecko's code is [at least writing-mode-aware](https://searchfox.org/firefox-main/rev/13c921de977264c9684ce23b0bfc46578babda18/layout/style/CounterStyleManager.cpp#832-853) though I'm not sure if there's custom drawing code; there used to be custom drawing code used only when used as a list item but not as a counter that was [removed](https://phabricator.services.mozilla.com/D111692); I don't immediately see any replacement that covers the counter case (which is now the only case).)

I presume the suggestion for `content: <list-style-type>` is a suggestion to add a new CSS feature to support this?

Is the sole use-case for this making it look slightly less hacky to reuse the disclosure counters? Are there any other counters that are meaningfully usable here? 

The counter-style system *in general* is a little weird to invoke here. We only have a handful of builtin styles that are totally static and don't care about the counter value. I wouldn't try to be generic here, honestly. If we want a more straightforward "use the same glyph" syntax, we could just add the specific keywords for those built-ins to 'content' (rather than allowing any counter-style name): disc, circle, square, disclosure-open, disclosure-closed.

But my larger question is indeed still just - can this just be solved by using a slightly more obvious counter name and a comment in the source, rather than inventing a new syntax? Or is it worth adding this syntax to solve an author issue outside of the HTML stylesheet itself?

## @dbaron — 2026-06-09

My understanding is that a use of a counter name in generated content doesn't cause any changes to the scoping or numbering of that named counter.  (I admit it's been [over 2 decades](https://bugzilla.mozilla.org/show_bug.cgi?id=3247#c100) since I really worked closely on counters, though.)  So use of a counter name should be side-effect-free, with the possible exception of performance.  And even for performance, implementations probably ought to optimize `counter()` (though not `counters()`!) functions whose list style type is one of the [5 simple symbolic counter styles](https://drafts.csswg.org/css-counter-styles-3/#simple-symbolic) to avoid having any interaction with counter numbering at all.

So I think the use of the name in this context doesn't actually expose that name in any way with the possible exception of performance effects that *ought* to be optimized away.  Or is that not the case for some reason I've forgotten?
