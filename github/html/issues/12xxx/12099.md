### What is the issue with the HTML Standard?

```html
<!doctype html>
<select>
  <option>One</option>
  <option>Two</option>
  <option>Three</option>
</select>
<select id="s2">
  <option>One</option>
  <option>Two</option>
  <option>Three</option>
</select>
<select id="s3">
  <option>One</option>
  <option>Two</option>
  <option>Three</option>
</select>
<style>
  #s2, #s3 {
    appearance: base-select;
  }
  #s3::picker(select) {
    appearance: base-select;
  }
</style>
<div id="p" popover="" style="inset: 40px; margin: 0; width: 200px"></div>
<script>
  document.addEventListener("click", () => {
    setTimeout(() => p.showPopover(), 500);
  }, true);
  p.showPopover();
</script>

```

There are three different selects:

 - Select 1 is auto appearance.
 - Select 2 is base-select but the picker is auto
 - Select 3 is base-select with a base-select picker.

When the page opens the popover is open. Try three different steps:

1. Click select 1.
2. Observe popover remains open, picker opens.

1. Click select 2. 
2. Observe popover remains open, picker opens.

1. Click select 3.
2. Observe popover closes, picker opens. Observe that after 500ms the picker closes as the popover re-opens.

The inconsistency between all means this is not simply progressive enhancement. This seems to be a meaningful semantic change based on styling. So I'd suggest we have a few options:

1. Make select's base-select a manual popover so that it does participate in the hide popover steps.
2. Make select's auto appearance picker respect the hide popover algorithm steps and hide, perhaps by making it a auto popover.

## @josepharhar — 2026-01-22

I'd think of this more as an enhancement that leverages new technology than an inconsistency, but if there's a strong desire to change that then I guess we can try.

> Make select's base-select a manual popover so that it does participate in the hide popover steps.

The way that the existing auto popover interconnects with the existing light dismiss and other popover algorithms feels desirable to me and might be difficult to make it behave as auto in some cases and manual in others. We should still make it behave like auto when running light dismiss, and it sounds like it should behave as manual when opening another popover in the page. There are probably other cases to be considered whether it should be like auto or manual, but maybe making it manual and just adding something in light dismiss could work? Although I don't know how complicated the logic added to light dismiss would be. Should the select popover be included in the auto popover stack or not? Do interactions with hint popovers need any consideration?

Maybe this is simpler than I'm making it sound and we would just need to add one step to the light dismiss algorithm, but I can't be certain given the complexity of the popover algorithms.

> Make select's auto appearance picker respect the hide popover algorithm steps and hide, perhaps by making it a auto popover.

The auto appearance picker is a native OS picker or something else, so I don't see how we can just make it a popover. I imagine that we would just have to make it so that opening any auto popover in the page would close any native select picker. It looks like in chromium, script already has the ability to close the native select picker by disconnecting the select element from the document, so it wouldn't introduce new capabilities for script to control native pickers.

## @mfreed7 — 2026-01-23

I tend to agree (strongly) with Joey on this. There are very definite differences between `appearance:base-select` and `appearance:auto`, **on purpose**. The new one fixes the many problems of the old one, which is a good thing. And one of those things is that the old one doesn't play nicely with other popovers. Thankfully, we fixed it, by making the `appearance:base-select` picker a normal `popover=auto`, so it plays nicely with other popovers. I suppose we could work to "fix" the `appearance:auto` popup picker in some way, but I'd be not very excited to do that. Generally, I'm not a fan of trying to bring all of the good stuff from `appearance:base-select` back to `appearance:auto`, because then what was the point? We added an `appearance` opt-in, so that developers could choose the new, good behaviors, or keep the old existing behaviors.
