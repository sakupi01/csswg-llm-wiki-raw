### What problem are you trying to solve?

A common use case for select-like components on the web is the ability to filter the rendered options by typing into a text field. For example, the "Labels" picker here on github has a listbox of labels with a text field above it to filter the labels.


### What solutions exist today?

To build this today, you would need to build your own input and listbox components, set up the ARIA so that the text field can control the listbox, and build a lot of keyboard and focus behavior which allows the user to type into the listbox while simultaneously using the arrow keys to choose options from the listbox.


### How would you solve it?

We have been discussing this use case for a while in OpenUI here: https://github.com/openui/open-ui/issues/847
Some potential solutions discussed in that issue include:
1. Allow authors to put an input element inside the select element which performs filtering.
    1. Pro: minimal markup for authors
    2. Pro: authors can still fully access the input element to customize behavior
    3. Con: The parser doesn't currently allow for input elements inside the select element due to site compat issues, where sites omit the select end tag and rely on the input tag implicitly closing the select tag.
    4. Con: The input element needs to exist outside of the listbox in order to control it for a11y and keyboard purposes. However, if we just allow authors to put it in the select somewhere, it would become difficult or impossible to make the browser wrap all of the options in a container that doesn't exist in the DOM. The fact that the input could exist anywhere in the select makes this harder - I imagine that we would have to traverse the entire subtree of the select element, look for input elements and options, decide if they are positioned correctly (input before all options), then decide where to build a secret listbox that we can put all the options in which is controlled by the text input, and make the popup a dialog instead of a listbox.
    5. Con: Doesn't accommodate for complex pickers like the Labels picker on github, which also has an "Edit labels" button after the listbox.
2. Add an HTML or CSS opt-in to display a filter input automatically
    1. Pro: minimal markup for authors
    2. Con: doesn't allow authors to directly access the input element, so we would have to add a lot of APIs to the select element to let authors control it, such as an IDL to see the value typed into the input element and events which fire when the user types a character into it.
    3. Con: Doesn't accommodate for complex pickers like the Labels picker on github, which also has an "Edit labels" button after the listbox.
3. Add markup to allow authors to connect an input element to a listbox select element, which an author could put in their own picker
    1. Pro: This is a simple building block which authors can use to build their own pickers with additional interactive elements like the Labels picker on github or something that exists outside of a picker entirely.
    2. Pro: authors have full access to the select element to customize behavior
    3. Con: Additional markup required for authors to build their own picker since they have to declare an element to be the picker and use attributes to connect the pieces

I think option 3 of adding markup is the best because it is relatively simple and enables significantly more use cases.

### Anything else?

There is also an OpenUI discussion about javascript APIs to modify how filtering works which would support use cases such as fetching results from a server and could also be applied to the input with datalist pattern: https://github.com/openui/open-ui/issues/931#issuecomment-3470754770

Solution 1, Allow authors to put an input element inside the select element which performs filtering:
```html
<select>
  <input>
  <option>one</option>
  ...
</select>
```

Solution 2, Add an HTML or CSS opt-in to display a filter input automatically:
```html
<select filter>
  <option>one</option>
  ...
</select>
```

Solution 3, Add markup to allow authors to connect an input element to a listbox select element, which an author could put in their own picker:

```html
<input filter=select>
<select id=select size=4>
  <option>one</option>
  ...
</select>
```

## @josepharhar — 2026-04-01

Based on @annevk's feedback [here](https://github.com/whatwg/html/issues/12227#issuecomment-4010837016), I'm guessing that solution 1 with less markup would be preferred, although I still think that solution 3 is ideal at the moment.

I thought some more about the cons I wrote about solution 1, and I have some ideas of how to work around them.

> Con: The parser doesn't currently allow for input elements inside the select element due to site compat issues, where sites omit the select end tag and rely on the input tag implicitly closing the select tag.

We could add logic to the parser to carefully consider whether an opening input tag should close its ancestor select tag or not. The idea is that if there are options already added to the select element, then the input should close the select, otherwise it should keep the select open. We could implement with logic like this when an input is added:

1. If the input tag has a direct parent select element/tag:
    1. If the parent select element has no elements inserted, or only has one button element inserted, then keep the select open.
    2. Otherwise, close the parent select tag.
2. Otherwise, close any ancestor select tag if present.

This could help to address the compat risk, but I'm not completely certain yet.

> Con: The input element needs to exist outside of the listbox in order to control it for a11y and keyboard purposes. However, if we just allow authors to put it in the select somewhere, it would become difficult or impossible to make the browser wrap all of the options in a container that doesn't exist in the DOM. The fact that the input could exist anywhere in the select makes this harder - I imagine that we would have to traverse the entire subtree of the select element, look for input elements and options, decide if they are positioned correctly (input before all options), then decide where to build a secret listbox that we can put all the options in which is controlled by the text input, and make the popup a dialog instead of a listbox.

If we require that the author's input element comes as a direct child of the select element, and that it must come before any child element in the select except for the button, then we will be in a better place to fixup the UA shadowroot of the select element to make sure that all of the option elements are correctly wrapped in an element which can act as a listbox. This could work in unison with the strict parser rules about getting an input tag inside of a select.

> Con: Doesn't accommodate for complex pickers like the Labels picker on github, which also has an "Edit labels" button after the listbox.

If we also allow an input inside of a listbox select, like this, then this proposal could still be used to build the "Labels" picker on github or other pickers which have other interactive elements, like this:

```html
<select size=4>
  <input>
  <option>one</option>
  ...
</select>
```

Looking forward to hearing more feedback on this proposal!

## @josepharhar — 2026-04-02

We had [a discussion about this in OpenUI](https://github.com/openui/open-ui/issues/847#issuecomment-4179758599), and some of the ways I [addressed the issues with solution 3](https://github.com/whatwg/html/issues/12050#issuecomment-4170811822) are not perfect.

In order to make it easy for the select element to know whether it should slot its children in the listbox or in the slot for the input element which comes before the listbox in the picker, and for the select element to update its shadowroot accordingly, I said that we should make the input element be the first child element, or after the author provided button element. However, I got feedback at OpenUI that authors may want to put an svg before the input element, and wrap the input and svg in a div for layout purposes. This makes sense as a use case, as we can see the Labels picker in github has a magnifying glass icon to the left of the search input. So now we have author HTML that looks like this:
```html
<select>
  <div id=input-wrapper>
    <svg>...</svg>
    <input>
  </div>
  <option>one</option>
  ...
</select>
```
The div in the above example should be slotted outside of the listbox in the select's shadowroot, which could look like this:
```html
<select>
  #shadow-root
    <slot id=button-slot></slot>
    <div popover=auto pseudo="::picker(select)" role=dialog>
      <slot id=input-slot></slot>
      <div role=listbox>
        <slot id=options-slot></slot>
      </div>
    </div>
```
In the author example above, `<div id=input-wrapper>` should be slotted into `input-slot`. However, in order to know that, we would have to traverse the subtree of the select element during slot assignment, and invalidate slot assignment when descendants of `<div id=input-wrapper>` are modified. In addition, we would have to require that authors don't mix input elements and option elements within the same child wrapper div of the select element - they need to be in separate children of the select element in order to be slotted into different spots.

There may be good ways to get around this issue, but it definitely makes option 3 more appealing since it doesn't have this complexity.

## @lukewarlow — 2026-05-13

I've been thinking on this some more and I don't think solution 1 fits with the existing design decisions around enhanced select. In my mind the *main* deciding factor behind sticking with the `<select>` element, rather than creating something new was the graceful degredation in older / unsupporting browsers.

You can write all manner of fancy markup for `appearance: base-select` pickers, but it all fallsback seamlessly. Solution 1 breaks this fundamental premise.

```html
<select>
  <input>
  <option>one</option>
  ...
</select>
```

If we take this in its simplest form, in browsers today you get, an empty select, an input and then an orphaned option element (essentially a span with a text node). See https://software.hixie.ch/utilities/js/live-dom-viewer/?%3Cselect%3E%0A%20%20%3Cinput%3E%0A%20%20%3Coption%3Eone%3C%2Foption%3E%0A%20%20...%0A%3C%2Fselect%3E

<img width="241" height="85" alt="Image" src="https://github.com/user-attachments/assets/f9a40ae4-8482-43ff-bf0b-dc90ee3284db" />

Now if we pushed authors to put the input as the last child rather than first, you still end up with a trailing input in older browsers, and then the author or the browser has to find a way to get the input to the top of the listbox (be that in-page or in picker).

```html
<select>
  <option>one</option>
  ...
  <input>
</select>
```

See https://software.hixie.ch/utilities/js/live-dom-viewer/?%3Cselect%3E%0A%20%20%3Coption%3Eone%3C%2Foption%3E%0A%20%20...%0A%20%20%3Cinput%3E%0A%3C%2Fselect%3E

Neither of these solutions seem great. Nor tbh does further changes the select parser as that has compat risk and so will take time and that means Firefox and/or WebKit will probably want to ship before that decision can be made.

## @josepharhar — 2026-06-03

After the last discussions about filterable select, I feel that there are too many issues with nesting `<input>` in `<select>` compared to the solution of having `<input>` as a sibling to a listbox select element:

- Difficult to manage scrollable area inside the picker and make it controllable by authors: https://github.com/openui/open-ui/issues/1441
- The DOM structure of the select element's shadow root and the slotting algorithm have to depend on whether each select child has descendant option or input elements, which is complex to implement and difficult to make performant
- Authors have to make sure that each child node of the select element only has either an input element or option elements, not both because each child has to either be slotted into the listbox or the slot for inputs
- Since HTML parsers in browsers currently make `<input>` automatically close the ancestor `<select>` tag, graceful degradation won't work because all of the `<option>`s following the `<input>` will be moved outside of the `<select>`, making the select element unusable. The last parser change we made for the select element did not have this issue.
- nesting `<input>` in `<select>` can make simpler cases have a little less markup, but it forces a specific structure. all examples ive seen of this pattern are not simple and would not benefit from nesting, such as the github labels picker (which puts selected options as chips after the invoker button rather than inside of it) or pickers that could be a modal dialog instead of a popover (like the select picker on android). if supporting simpler cases still proves to be needed later, shipping the sibling input and listbox pattern does not preclude shipping more patterns.
- supporting `<input>` in `<select>` for appearance:auto could be tricky since I don't think that ios or macos support having a search box inside their native popup pickers. Supporting appearance:auto filtering for the sibling input and listbox select case on the other hand is easy, I already prototyped this in chromium.

## @josepharhar — 2026-08-03

An update on different options we have for the api shape:

nesting `<input>` in `<select>`
- would require html parser changes:
    - we could allow `<input>` before any `<option>`s, which is [probably web compatible](https://chromestatus.com/metrics/feature/timeline/popularity/5894) but doesn't allow for progressive enhancement at all
    - we could allow `<input>` anywhere in `<select>`, which would allow for progressive enhancement by putting `<input>` at the end of the `<select>` but would  break [many websites](https://chromestatus.com/metrics/feature/timeline/popularity/5546)
- parser changes and lack of progressive enhancement may make it unusable for many years. feedback on this from developers [1](https://x.com/JosephArhar/status/2077060267192799277) [2](https://bsky.app/profile/josepharhar.bsky.social/post/3mqmlaapxts26) and [the last meeting](https://github.com/whatwg/html/issues/12050#issuecomment-4682432311) has been negative.
- various [other minor issues](https://github.com/whatwg/html/issues/12050#issuecomment-4617644547) including implementation complexity and figuring out scrollable areas

sibling `<input>` with listbox `<select>`
- requires author to do more things:
    - build their own button and picker
    - ensure elements have correct accessibility roles
    - potentially add missing behaviors like auto-closing picker when choosing an option
- would also need to make `<selectedcontent>` work outside of `<select>`
- more polyfillable than other solutions

"filterable" attribute on `<select>`
- we could add a filtering input to the shadowroot of the select element when an attribute is set on the select element. this was suggested by someone in an aria meeting about filterable select. I created an OpenUI issue here: https://github.com/openui/open-ui/issues/1491
- we would have to expose all the IDLs of the input that developers would want on the select element
- has same minor [scrollable area issue](https://github.com/openui/open-ui/issues/1441) as nesting `<input>` in `<select>`

nesting a new element like `<input>` in `<select>`
- we could create a new element which is functionally identical to `<input>` to avoid parser and progressive enhancement issues
- goes against [apple principle about redundant form control elements](https://github.com/whatwg/html/issues/9799#issuecomment-1770254871)

## @emilio — 2026-08-27

I think the input approach would be the most flexible, but it seems doable to start with a `filterable` attribute in the `<select>` element, designing it in a way that would be forward-compatible with slotting your own `<input>` would be doable? It would also allow the filtering to work on `appearance: auto` select and so on.

E.g. something like:

 * Give the select's shadow tree a `<slot name="filter"><input type="search" id="filter"></slot>` or so. The UA must not display the slot at all if there's no `filterable` attribute.

 * We define a `filter` event (name TBD) on `<select>`. The `<select>` fires this event from the filter's `input` event (or so?). If that event is `preventDefault()`ed, then the UA does nothing, otherwise the UA performs the filtering somehow (maybe toggling the `hidden` attribute on the non-matching options?).

Eventually, that `<slot>` could host the nested `<input>` (just like the existing slot deals with `<button>`).

Would something along those lines work?
