### What is the issue with the HTML Standard?

The only hint the specification gives at the moment is that it's called a "select popover". There's no normative requirements related to this.

Originally spotted here: https://github.com/whatwg/html/issues/11729#issuecomment-4069314178.

This also reminds me that I ran into some default style sheet conflicts between `[popover]` and `::picker(select)` as we used the `popover` attribute to implement it. We needed various workarounds, such as:

```css
[popover]:not(:popover-open):not(dialog[open]):not(:-internal-select-popover) {
    display: none;
}

[popover]:not(:-internal-select-popover) {
    inset: 0;
    margin: auto;
    border: solid;
    padding: 0.25em;
    color: CanvasText;
    background-color: Canvas;
}
```

(`:-internal-select-popover` being equivalent to `::picker(select)`.) I think these are real conflicts as the specificity of `[popover]` is too high. Of course, depending on how we specify this we might not run into this as we could delegate to some internal mechanism instead without using the attribute.

Based on what I'm seeing, no special casing of the `[popover] { display:none }` rule is actually needed for customizable select, because the only other thing setting it to display block is just `div { display:block }`, which has lower specificity than `[popover]`, right...? Our `[popover]:where(:not(:popover-open))` rule looks a little funny, but it at least doesn't have anything that specifically targets the select element's base appearance picker. In case I'm glossing over something - the picker should be display:none when closed in order to make sure that top layer animations work normally, which I explained how I implemented in chromium [here](https://gist.github.com/josepharhar/9c359f5b8b6fa4c31065bd1fbeab40dd#computed-style-for-pickerselect).

As for the other rules like `inset:0`, the [rendering section specifies](https://html.spec.whatwg.org/multipage/rendering.html#:~:text=%3A%3Apicker(select)%20%7B%0A%20%20box,span%2Dinline%2Dstart%3B%0A%7D) that this element should have `inset:auto`. You can see in the screenshots that in chromium we are setting the desired `inset:auto` in a `select:not(:-internal-list-box)::picker` selector, and that `inset:0` is being set in a `[popover]` selector. We also didn't need a pseudo-class specifically for the select element's picker in this case or account for it in the `[popover] { inset: 0; }` selector.

Do we need to explicitly say in the rendering section that these rules take precedence over other UA style rules?

This is a different thing which makes menu elements behave as popovers without the element actually having the popover attribute. In this case, the picker element really does have the popover=auto attribute.

> I'm not sure why we're doing `[popover]:where(:not(:popover-open))`, but I don't think that its for customizable select.

It's mentioned in the comment there, but it's so these two rules don't fight, in the case of `<dialog popover>` which is open as a modal dialog. Without `:where()`, the dialog would stay `display:none` because the top rule would have higher specificity:

```
dialog:not([open]), [popover]:where(:not(:popover-open)) {
    display: none;
}
dialog[open], [popover]:popover-open {
    display: block;
}
```
