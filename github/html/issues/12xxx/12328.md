Browsers are currently implementing the customizable `<select>` element, which expands `<option>` elements to allow rich content.

While the spec already disallows interactive content inside the <option> element, it currently provides no guidance on how user agents should handle violations of this rule. In current nightly builds across multiple engines, authors can insert interactive elements, including links and buttons, inside an `<option>`, and these elements remain at least partially functional.

This creates accessibility challenges because it's not clear how such content should be reachable via the keyboard or via AT.

I think the specification should explicitly define the error-handling and rendering behavior when interactive content is encountered inside an `<option>`.

Potential solutions might include:
- Stripping the interactive elements during parsing, or ignoring the subtree.
- Rendering the elements visually, but forcing them to be inert.

## @josepharhar — 2026-04-06

In chromium, we have added features to devtools to let authors know they did something wrong in this case in addition to others when the content model is not followed.

I think that adding buttons with secondary actions inside options was a followup plan at some point, although I haven't seen any discussions about this in a while.

> Stripping the interactive elements during parsing

When we changed the html parser to stop dropping tags inside the select element, it was a very big breaking change and I'd prefer not to make additional parser changes. This also won't help with authors who use frameworks like react to create their DOM because that doesn't necessarily use the HTML parser.

> Rendering the elements visually, but forcing them to be inert.

I suppose that we could force all child nodes of option elements to be inert by using the controversial interactivity property like this:
```css
option > * {
  interactivity: inert !important;
}
```
I imagine this would have the effect of pushing authors away from using customizable select, since hopefully our devtools signaling is enough to already let them know that they are going to run into a11y issues and they should reconsider what they're doing. If we ever figure out how to make secondary actions work, this could also preclude us from making it polyfillable.

If we did something like this to option elements, should we do the same thing to every other interactive element in the browser, like button elements?

## @lukewarlow — 2026-04-09

Fwiw I don't think we should enforce this at the parser level, if we in future come up with ways to fix "nested interactives" then we'd have to make yet another parser change. In fact a world where aria-actions exists might mean that this is a legitimate pattern (I'm not an expert I could be completely misunderstanding that).

We should already be handling this in the content model, but we discussed this during the long road of incubating and I think there was largely consensus to *not* block authors from doing this sort of thing.
