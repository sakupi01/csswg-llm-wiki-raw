### What is the issue with the HTML Standard?

The only requirement I see for `optgroup` is

> An [optgroup](https://html.spec.whatwg.org/multipage/form-elements.html#the-optgroup-element) element is [expected](https://html.spec.whatwg.org/multipage/rendering.html#expected) to be rendered by displaying the element's [label](https://html.spec.whatwg.org/multipage/form-elements.html#attr-optgroup-label) attribute.

which seems insufficient for what the tests expect.

The `option` element also has a rather curious sentence that I don't quite understand:

> indented under its [optgroup](https://html.spec.whatwg.org/multipage/form-elements.html#the-optgroup-element) element if it has one

Shouldn't that be defined through CSS, if there's any indentation to be done at all? Also, if you render `option` like suggested in the surrounding sentence, you might well end up with a rendering that doesn't support pseudo-elements, so something is missing there as well.

## @annevk — 2026-03-04

I wanted to briefly reflect on our options (harhar) here. For the `option` element we need to either display the `label` attribute or its contents. The conditions for what to show are:
- Does it have a `label` attribute whose value is not empty? (This is what the `label` getter uses as condition.)
- Does it have a `select` element owner? It would seem somewhat natural to me if outside of a `select` element the element behaves like a `span` element as neither `base` nor `auto` appearance of the `select` element would be applicable.

We could do this either as a `div` element (contains `label` attribute value)  and a `slot` element as siblings which are conditionally shown based on those conditions. Or we could have a single `slot` element (contains `label` attribute value) that we force to show its fallback based on the conditions (you make no nothing match if the conditions match, essentially). I think these are identical, but I prefer the latter as it makes best use of the shadow tree primitives. If we ever give more access through pseudo-elements, these would no longer be identical and the distinctions would become more relevant.

---

For the `optgroup` element we need to either display the `label` attribute or a `legend` element child, followed by the contents. The conditions are roughly the same, but now also depend on whether there is a `legend` element child as well.

This could again be done as a `div` element (contains `label` attribute value) and a `slot` element as siblings which are conditionally shown. This is fairly clean in a way and can be made to not have an impact when there is no `select` element owner. (In contrast to the `option` element the `div` element would also have some `padding` applied to it.)

More in line with shadow roots would probably be two `slot` elements with the first `slot` element having a `div` element containing the `label` attribute value as fallback. (This `div` element would also have some light padding applied to it.) A first element child if it is a `legend` element would be slotted into it, if any. (This is different from the initial prototype/proposal which allows for any `legend` element child to suppress the `label` attribute. But it would match more closely with how we only slot the first element child if it is a `button` element in a `select` element.)

I suppose we could still make it so that outside of `select` elements the first `slot` element would not be shown and not match any element, but it would feel a bit less natural (to me, anyway).

## @lukewarlow — 2026-03-04

I've just come across a behaviour for which I've raised a WebKit [bug](https://bugs.webkit.org/show_bug.cgi?id=309161) but I figure I should check what is actually expected here.

`data:text/html,<select size="4"><optgroup label="Animals"><legend>Foobar</legend><option>Lion</option></optgroup></select>`

In Chromium this will render with the legend content NOT the label, in WebKit (using latest main where it will work in base appearance with size=1) this renders with the label.

Given we're in auto appearance mode perhaps WebKit is correct, BUT this is for listbox select where the security issues of allowing rich content don't apply. So essential, should the legend only be rendered when in base appearance mode?

Worth noting Chromium won't use rich content from the options only the optgroup which seems odd but perhaps thats for compat reasons.
