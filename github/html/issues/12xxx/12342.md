### What problem are you trying to solve?

Right now, the `<selectedcontent>` element does not clone option elements when it is in a `<select multiple>`. With base appearance `<select multiple size=1>`, the `<selectedcontent>` element would be useful if the author wants to display the currently selected options inside the button.

Here's an example of a multi-select library which shows each option in the button, rather than text which just says "2 selected" or "3 selected": https://primereact.org/multiselect/

### What solutions exist today?

Use script to manually change the contents of the button element every time the select is changed.

### How would you solve it?

Clone each selected option element into the selectedcontent element, one after another. Based on an openui discussion, we should also automatically create separator elements for each cloned option: https://github.com/openui/open-ui/issues/1355#issuecomment-3928467441

Here is what the resulting DOM would look like after the selectedcontent element updates itself:
```html
<select multiple size=1>
  <selectedcontent>
    <div>one</div>
    <div>two</div>
  </selectedcontent>
  <option selected>one</option>
  <option selected>two</option>
  <option>three</option>
</select>
```

### Anything else?

_No response_

## @fantasai — 2026-05-28

Several of us were discussing some interesting (single-value) `<select>` sizing behavior yesterday: [testcase](https://software.hixie.ch/utilities/js/live-dom-viewer/?%3C!DOCTYPE%20html%3E%0A%3Cselect%3E%0A%3Coption%3EShort%3C%2Foption%3E%0A%3Coption%3ELooooooooooooooooooooong%3C%2Foption%3E%0A%3C%2Fselect)

This isn't currently implementable in CSS, because the content is taken out of flow. To do it, we would need the button to contain all the values always, and just [collapse](https://www.w3.org/TR/css-flexbox/#visibility-collapse) the ones that aren't selected so that they are invisible, but still in-flow and contributing to the size of the button. (Notably, we don't want to take the size of the popover, we want to take the size of the content as it would be represented if it were selected.)

Bringing that up here because it's also potentially about representing multiple items in `<selectedcontent>`.

I think that this is worth a separate issue and in my opinion doesn't need to block selectedcontent in select multiple. If we only include the dom of the selected option(s), then the obvious way to do selectedcontent in select multiple is to include the dom of each selected option element, like my current proposal does. If we end up changing the selectedcontent element to always include the dom of each option element, then we would be making the same change for single select and multi select selectedcontent elements.
