### What is the issue with the HTML Standard?

As part of implementing the `selectedcontent` element in WebKit we believe we encountered an issue. Namely that the removing steps itself end up itself removing nodes, which can result in the `pagehide` event, whose listeners would now have access to the DOM during an inconsistent state.

I think at least for that case we need something akin to post-removing steps perhaps or maybe custom element reaction timing?

(See also this older issue discussing some of the issues with these events: #4611.)

## @josepharhar — 2026-01-21

Thanks for bringing this up. The reason that the removal steps run cloning is because it may change which selectedcontent becomes the primary one, and we want to keep the primary one up to date. This didn't matter in the original implementation which always updated all selectedcontent elements, but we changed it to only track one "primary" selectedcontent element:
- https://github.com/whatwg/html/pull/10633#discussion_r1834376985
- https://chromium.googlesource.com/chromium/src/+/f8190777fa80312a588f06a7b6ba2cf3bd9897a7

In my opinion, keeping the newly primary selectedcontent element up to date in the case that the primary selectedcontent element is removed is not a use case we should guard against because there is no use case to append multiple selectedcontent elements to a select and then remove the first one, which would be another way to justify removing the selectedcontent element removal steps.

So I think we have two options to address this issue:
1. Clone the selected option into every selectedcontent element descendant of the select element instead of the first one in tree order.
2. Drop the selectedcontent removal steps without any other changes because it guards against a case that isn't important.

## @dbaron — 2026-01-21

The cloning would be a change to https://html.spec.whatwg.org/multipage/form-elements.html#update-a-select's-selectedcontent so that it iterates a list of `selectedcontent` rather than just updating one of them as it does today.  (The removing steps and parts of the post-connection steps are there to handle the case of insertions/removals changing *which* `<selectedcontent>` is the one that gets updated, and if we update all of them we can avoid dealing with insertions/removals changing the state of a *different* `<selectedcontent>`.)

## @annevk — 2026-02-09

We currently manage `selectedcontent` disabled state as part of the post-connection steps. This means that if you insert multiple `selectedcontent` elements the first will calculate its disabled state and then trigger the `select` element to find `selectedcontent` element descendants to update. This will end up updating all `selectedcontent` elements descendants, even if they later end up being disabled.

So we probably need a new strategy for that too, even if it is an error condition.
