Spun off from [HTML modules discussion](https://github.com/w3c/webcomponents/issues/645)

There are certain amount of interest that including HTML snippet into an HTML document, without using JavaScript. That would be similar to `<iframe>`, but more lightweight and merged into the same document.

It would work as a naive way to have your header and footer sections defined in one place.

## @TakayoshiKochi — 2017-06-27

HTML Imports load a HTML document, via `<link rel="import" href=...>` and its contents are never rendered without DOM manipulation via script. The document is stored in `$(link).import` property. HTML Imports have more, like `<script>` is executed etc.

This idea is about inserting HTML snippet in HTML document. e.g.

main document
```html
<include src="header.html"></include>
Awesome contents
<include src="footer.html"></include>
```
header.html
```html
<h1>Welcome!</h1>
```
footer.html
```html
<footer>Copyright 2017 by me</footer>
```

will result in
```html
<h1>Welcome!</h1>
Awesome contents
<footer>Copyright 2017 by me</footer>
```

```javascript
var included = document.querySelector('#my-include');

  // included_ === included
  // and this promise is ready once the HTML code
  // from included.src has been fetched and appended to the DOM
```

- loaded promise
- currentInclude (or a better name)

I think it would be quite useful for any cases where we want DRY html authoring but not the burden of running code server side or requiring JS. It's actually what I naively expected html imports to do at first. 

The use cases may be relegated primarily to the realm of small, static-only websites but I think it's a _huge_ advancement for those cases. Simple static-only sites are a large number of websites, or sites that probably should be purely static but cannot be for reasons such as requiring server side rendering to DRY shared fragments such as header/footer, etc. I'm thinking of all the shared web hosting site builder tools and a large number of wordpress sites (a security/maintenance nightmare for typical site owners in my experience) and things along those lines. These kinds of sites are typically owned/maintained by the least tech-savvy operators and are therefore likely under-represented in these kinds of platform-advancement discussions. I'm aware that dynamic rendering or static build tools can get the job done, but those are inaccessible tools to a majority of simple website owners (again, in my personal experience).

The JS-free aspect gets back into the philosophy of progressive enhancement including "site basically works without scripting enabled" and I think that's still important, personally, particularly when we have Brave browser picking up steam with JS disabled by default for security/privacy purposes.

I may try to take a stab at faking this using a custom element backed by fetch, but it wouldn't fill the same gap IMHO and would merely be a demonstration for illustrating the convenience it can provide to the page authoring experience once it's all set up.

## @AshleyScirra — 2017-06-29

Further to @brandondees' point, I think I'd point out that offline-first PWAs using Service Worker very much encourage a client-side approach. For example in our PWA (editor.construct.net), despite it being a large and complex web app, we generate virtually nothing on the server side. So I think there are actually some significant use cases where you might want to process an include client-side, and "just do it on the server" doesn't cover everything.

The algoritm was as simple as follows. Also works with nested dependencies due to custom elements lifecycle reactions:

```javascript

  Element `import-html`

  (class extends HTMLElement {

    onconnect () {
      this.innerHTML = 'Content Loading...'
      this.context.location = this.getAttribute `src`

      let headers = new Headers({'Accept': 'text/html'})

      fetch (this.context.location, {mode: 'no-cors', headers: hdrs})
        .then (response => response.text ())
        .then (content => this.parse (content))
        .catch (err => console.warn(err))
    }

    parse (string) {
      let
        root = (new DOMParser)
          .parseFromString (string, 'text/html')
          .documentElement

      , html = document.importNode (root, true)

      , head = html.querySelector
          `head`.childNodes

      , body = html.querySelector
          `body`.childNodes

      this.innerHTML = ''
      this.append ( ... [ ... head, ... body ] )
    }
})
```

## @maherbo — 2017-11-05

I'm the author of issue #3200 that has just been closed by @domenic and referenced here.

The primary objective of includes is the ability to cache your views client-side, reducing web traffic and server load.  You cannot do that with server-side scripting language (except by putting your HTML inside a JS file, which is basically a hack and, well, requires JS enable).

The goal is not to include 3rd-party software, so the question of linking style and JS is irrelevant; You can do that in your 'main' document.  The idea is just to split your 'main' document into document fragments (which are NOT documents, but merely just static content, a text file) such that you can reuse them on other pages.

Nobody expects PHP includes to be independent (although they can be with namespaces and such), they are simply pasted into the calling document.  It is up to the programmer to make sure both the calling document and the included document are compatible.

Please read issue #3200 for more details on my thoughts about the problem.  I don't even think a new element is needed, just extending the definition of an already existing attribute.

1. load the `<script>` source file;
2. compile the script;
3. run the script;
4. modify the HTML document;

With IFrame, you have to:
1. load the `<IFrame>` source file;
2. load (i.e. build) the IFrame document;
3. copy the IFrame document content (with JS);
4. modify the main document by replacing the IFRAME with the copied IFrame content (with JS);

On the browser point of view, a document fragment should work like a [constant](https://en.wikipedia.org/wiki/Constant_(computer_programming)) in computer programming (emphasis mine):

> Many high-level programming languages, and many assemblers, offer a macro facility where the programmer can define, generally at the beginning of a source file or in a separate definition file, names for different values. A preprocessor then replaces these names with the appropriate values **before compiling**, resulting in something functionally identical to using literals, with the speed advantages of immediate mode. Because it can be difficult to maintain code where all values are written literally, if a value is used in any repetitive or non-obvious way, it is often done as a macro.

By doing so, a browser would identify the document fragments in a document BEFORE doing anything else, replace them by their content and then parse the document to build it.  This would give the best UX and make server admins and developers happy.

## @LeaVerou — 2018-05-13

Thanks @domenic for pointing to this. This was my post:

Currently, even the simplest templating, such as headers and footers across multiple pages of a static website, require server-side code or build tools, both of which which are complicated for non-developers and take time for everyone. JS solutions exist, but this reduces indexability and makes essential parts of the website content very fragile.

This proposal is for an HTML element that accepts an `src` attribute, asynchronously fetches the content (following usual CORS rules) and embeds it in the page's DOM tree, executing any `<script>` elements. Since `<template>` is taken, one potential name (for the sake of discussion) could be `<include>`. Alternatively, `<link rel="html">`, so that it can be used in the `<head>` too without the issues a new element would introduce.

# Not another `<iframe seamless>`!

This element *transcludes* the content of the linked HTML document. This means better performance (no multiple documents and window contexts), and simpler CSS. This essentially mimics how sever-side includes work.

# Why not use a custom element or JS?

See comment re:JS solutions above. Several indexers and server-side renderers do not process JavaScript. Also, JS is inherently fragile, and this is needed for essential parts of a website's content.

Furthermore, a declarative solution has some accessibility benefits, since browsers could expose UI to skip certain templates (e.g. a website header with no "skip to content" link).

# Questions that need to be answered

Several things need to be ironed out for this to happen, but I firstly wanted to gauge interest and see if there are any major implementation obstacles I'm missing (since this seems like very low-hanging fruit, so there must be a reason it doesn't exist).

## Does the `<include>` element stay in the DOM?

Regarding how the transclusion happens, I see three possibilities, each with its own pros and cons:
- The `<include>` element remains in the DOM and the fetched HTML is added as a child
- The `<include>` element remains in the DOM and the fetched HTML is added after it (akin to `document.write()` in `<script>`)
- The `<include>` element is replaced by the fetched HTML.

## Does `DOMContentLoaded` wait for the content to load? What about the `load` event?

It seems reasonable that the answer is no and yes respectively, but probably another thing to discuss.

There seems to be two kinds of behaviour discussed in this thread, and some proposals are a combination of both in a way that doesn't make sense.

# Injecting into the parser.

The browser would parse until it gets to `<include src>`, then it stops feeding the parser data from the navigation response, and instead makes a new request to the `src`, and feeds the parser bytes from that response before continuing to use the navigation response.

This seems like the closest to what folks want in the thread, but it could be bringing along all the problems of `document.write()` but with an extra network request into the mix.

`<include src>` would not interrupt the parser. Instead, the browser would make a request to the `src` and feed elements into the include element in parallel to parsing the main document.

1. If the content of the `header` resource ends `<!--`, will "Content" be within an HTML comment?
1. Module scripts execute after dom ready. If the includes take a long time to load, will they delay the module script from executing?

The content of an include source should be a valid [document fragment](https://developer.mozilla.org/en-US/docs/Web/API/DocumentFragment).  This makes sure you have correct HTML (i.e. no opening tag without a closing tag, etc.).

When the parser encounters an include, it should build the document fragment and insert it into the calling document.  If there is an include in the document fragment, it should be executed once inserted into the document.

- **default:**  Stop parsing the document, load and insert document fragment, continue parsing;
- **async:**  Load document fragment while continuing parsing the document and insert document fragment when ready;
- **defer:**  Parse entire document, then load and insert document fragment.

Process modeled after a stylesheet's `@imort`:
1. A root document is retrieved and the DOM parser comes across a `<fragment>` element inline a parent document and asynchronously fetches the content. 
2. Upon completion of the fetch, this document-fragment is added to the end of the queue to be parsed sometime in the future.
3. Once the DOM parser has completed the parent document the next src is pulled from the queue. 
4, The parser looks at the <fragment> element changing it's working source path to be the `basename` of the calling documents 'document.location' path-resolved against the `basename` of the src file in the `<fragment>` element's src attribute. 
5. The DOM parser continues parsing the fragment and upon parsing an `<img>` element resolves the src attribute against the DOM parser's current working path, fetching the img at that resultant URI.

The point is, just as we do with a current working directory in shell scripts, the path is always relative to the parent. Only the parser is required to keep track of it's working path during the expansion of the HTML Document parts into the final DOM. In the same way, `document.location` shouldn't ever change, because the root document is not moving around, it is simply sourcing material to flesh out the content.

> The user experience is much better if such inclusion is done server-side ahead of time, instead of at runtime.

Most web pages already include numerous resources such as style sheets, scripts, and images, which are fetched after the main document loaded. Caching these shared static resources gives much better performance than loading all resources again for each page. This is one reason that we prefer to use external scripts and stylesheets, not inline script and stylesheets.

Consider a blog or news site. Each page has similar header, footer, menus, etc. Only the article content and images are different. The header, footers, menus and other shared components do not change often, and can be cached for day or weeks, or until they change.

If I am reading a number of articles on the same blog or news site, over the course of a month, my data transfer will be less and my user experience will be better if the shared HTML resources are cached rather than fetched anew for each article I read.

If we also fetch article body text separately, it makes it easy to have both single-article pages and aggregate pages (with many articles, or all articles on a single topic), without duplicating any resources, and without resorting to scripting.

With a little effort, we could have an HTML include with slots and attributes, which would enable to cache the entire page structure as a single resource, and just update the article inside it. This would also help with theming, where the client can choose to view the article in a different page structure, and without having to reload the article itself. An HTML include with slots and attributes is equivalent to an HTML macro, and it might approach the capabilities of web components, without need for scripting or special DOM hacks.

If we are worried about repeated round-trips to the server to fetch resources, we can solve that using HTTP server push: "HTTP/2 Server push allows you to send site assets to the user before they've even asked for them." The server should not re-send cached assets. Ideally, this single feature could be backported to textual HTTP, as I'm not a fan of binary protocols.

Even without HTTP push, I would still prefer to use a site that loads a little slower on the first request, then runs like a rocket thereafter because everything that can be cached is cached. I would prefer that we have this client-side include capability built into HTML, without need for scripting, so that the search engines can handle it better (SEO), and because it is a fundamental feature that was somehow missed. Client-side includes would also greatly reduce the amount of data that search engines need to fetch. There are some caching bugs in Chrome and other browsers that we need to fix, to reach the ideal user and developer experience with includes.

Another reason to support client-side includes, is that the server-side environment is very diverse, and there is no single standard way to do server-side includes. Here is [a large list of different ways to do includes](https://css-tricks.com/the-simplest-ways-to-handle-html-includes/). We have apache SSI, PHP includes, pages created from components by running `make`, and a million other hacky ways to put pages together. Instead of all that crud, we could have a single standard client-side include feature in HTML, and what's more if you really want to implement includes on the server, the server could pre-process the HTML, look for the single standard include syntax, and include the resources that it can before sending the page. If we want to get really clever, perhaps the client could cache the resources that the server included separately. This could help to eliminate the slow first page problem.

## HTML: Client Side Include

I think we have to put aside Javascript for a moment. While it may be impacted by decisions in this thread, the reality is we're talking about functions built into the DOM and how the model is generated by the client.

#### Current state

1. HTML is a modeling language. It's core function should be to ease creation of an interface (view) of a model to be rendered by a client, and be easily consumed by the controller (Javscript/ES).  
2. HTML is currently tightly coupled with Javascript in order to perform some of it's most basic functions.
3. HTML has some tags which are gifted the ability to store their content as a remote resource, while others are not.
4. HTML contains effectively three types of elements.
    - element complexes (`document`, `ol`, `ul`, `table`, `form`)
    - pre-styled elements (`p`, `div`, `em`, `strong`, `pre`, `li`, `input`, `button`, `select`, `textarea`, `label`, `br`, etc.
    - non-html external content-type elements (`img`, `script`, `style`, `video/audio`, `iframe`, `object/embed`)

Regardless of implementation details, the HTML specific use-case missing:

Constructs within HTML should permit the combination of two or more HTML documents into a single resulting document by allowing external references to be resolved, fetched, and combined into the user-requested HTML document. Just as an anchor can provide a reference that when acted upon by the client's consumer tells the client which document to fetch and render next, the HTML document itself should be able to retrieve portions of it's DOM form external resources. This is already done for non-HTML resources, such as when including images via the `img` tag, stylesheets via the `style` tag, javascript source via the `script` tag, svg documents via the `svg` tag as well as content-types not called out here.

While I personally am partial to allowing any element which could potentially be a container of HTML Elements to be a remote resource, it seems more pertinent to have a solution that the majority can agree upon. I can appreciate a more prudent approach by scoping this functionality to specific tags which, by design, only contain HTML tags and *NOT* inline-text content. Creating a dedicated tag permitting HTML Documents or Fragments would also be sufficient.

The key requirement here from my perspective is that it *should* be possible to merge an HTML DOM sourced from remote URI with the active DOM without the necessity of Javascript. Whatever it takes to get us there, I am on board.

Edit: Also, I want to be clear. I don't have anything against Javascript. I simply think that this function should be built into HTML as a built-in function, as it could then be more tightly coupled to the creation and resolution of the DOM tree, and more loosely-coupled to the Javscript event-loop.

I think this <include> tag should have the following properties:

1. It´s `inner HTML` should be used as a replacement for loading status `<include href="url">loading...</include>`
2. If it is used as a void element or if no `inner HTML` is provided, it should display nothing during load stage
3. It should be a block level element
4. Is should be stylable while the contents are still loading
5. The `outer HTML` of the tag should be replaced by the response
6. It should allow nested includes
7. `href` property should be absolute or relative to the page being currently rendered, irrespective of how many nested includes are there
8. It should allow importing content from other domains
9. It must not execute scripts for security reasons
10. It should trigger a `loaded` event with a reference to the `include` tag, so as to execute scripts when needed, thus providing a way to define scripts only from the requester side
11. It should be cacheable
12. Included css should be treated as regular css present in any other place of the final DOM (global)
13. It should be non blocking (rendering does not wait until contents are fetched via GET)
14. Upon errors when failing to fetch contents, it should display an error only in the place the content should be present (404 - Not found, Timeout, etc, as plain text)
15. If the response of the requested resource contains a completely formed HTML document, it only pastes the contents of the `<body>` tag
16. If the response of the requested resource is not presentable as HTML or any other text based format (json, xml, etc), it should display an error
17. if the response of the requested resource is a textual format, but not HTML or XML like, it should paste the raw response

The main use case I can think of is in static web sites, allowing users without knowledge of a backend language to create static web sites without the hurdle of needing to maintain a backend. Also, it would be excelent for PWA's as mentioned previously.

## @DavidJCobb — 2022-12-15

Template stamping (#6417) has been brought up a few times, but I'm surprised to see that in most of the five years this issue has existed, it wasn't brought up specifically as something that alleviates concerns about network requests and blocking the parser. Right now, SVG has several places where you can refer to other files (`href(url)`) or to previously defined elements in the same file (`#id`); I see no reason why template stamping couldn't be made to work the same way, which would unify #6417 and this request.

Here are my own thoughts on some of the other topics brought up in here, along with some edge cases I've thought of, all from the perspective of having a single feature handle both template stamping and the use of external HTML resources. I'll be using the term "substitution" to refer to what the feature does, in contrast to "importing" (name of a deprecated spec) or "including," but I don't really care what the feature is called, in the end.

* Substitution must be usable without any JavaScript whatsoever. It's worthless otherwise; it would offer nothing new, and would arguably be redundant with [other proposals](https://github.com/WICG/webcomponents/blob/gh-pages/proposals/Template-Instantiation.md).

* Substitution should be akin to copying and pasting the full content of the specified `template` element or external file. That means that concerns about relative paths, unscoped styles, etc., in the included file are completely irrelevant. (In particular, if the included content needs to contain scoped styles, then [a more general mechanism for CSS scoping](https://github.com/w3c/csswg-drafts/issues/3547) should be standardized and then used within the included content.) Use the base URL of the substituting document; allow style tags in the substituted document to affect rendering of the substituted document; et cetera. *At most* the only special behavior should be to refuse to execute `script` tags in the substituted-in content (maybe unless they're same-origin?).
  
  There are other proposals and suggestions for far more advanced and powerful "HTML module" ideas [elsewhere](https://github.com/WICG/webcomponents/issues/645), and IMO those ideas would be the place to tackle any behaviors beyond an automated copy and paste.

* Substitutions should block rendering and interaction unless they're marked with a `async` attribute. When using substitutions for large chunks of a page's layout, blocking rendering and interaction also be needed to ensure a consistent user experience (no FOUC or massive layout shifts; no race conditions in keyboard navigation or screen reader navigation; etc.). Another user [commented](https://github.com/whatwg/html/issues/2791#issuecomment-783397770) that using substitutions for large chunks of a site's layout is a desirable use case that could reduce bandwidth usage when browsing around; I agree with this view.
  
  In any case, whether substitutions block or are async should be the page author's choice: as [others here have suggested](https://github.com/whatwg/html/issues/2791#issuecomment-317133397), give people tools like `async`, and let them use or forgo those tools based on their page's unique needs.

* Asynchronous substitutions introduce an edge-case: consider a page which substitutes in *A* and, later in the document, *B*; *A* contains a `template` element *C*; and *B* substitutes in the content of *C*. If *B* loads and is substituted in before *A*, then *B* may fail to find and substitute in *C*. There are two ways to handle this.

  **a)** If a substitution *S* specifies an element ID that does not match any `template` currently in the DOM, then suspend the substitution until parsing is complete and all other substitutions are either completed, failed, or suspended. After any other substitution completes, check whether the ID requested by *S* now corresponds to a valid `template` element; if so, perform *S* immediately. Once all substitutions are either completed, failed, or suspended, all suspended substitutions should become failed.

  **b)** Do not allow nested substitutions.

  The former approach is, in my opinion, the better of the two. I personally don't like the complexity here for what ought to be just an automated copy-and-paste, but it's necessary as long as [blocking the parser is prohibited](https://w3ctag.github.io/design-principles/#avoid-html-parser-blocking) or an `async` option is considered desirable.

* We should be allowed to perform substitution anywhere in the substituting file i.e. the `head` or the `body`.

* The token (element or attribute) that triggers HTML substitution should not be left behind after substitution, to avoid breaking CSS [as mentioned previously](https://github.com/whatwg/html/issues/2791#issuecomment-461037608).

* If substitution is triggered by a special element, e.g. `<paste id="template"/>` or `<paste src="file.html"/>`, then creating this element via `document.createElement` or via setting the value of `innerHTML` should have no effect. It's tempting to allow it to work in `innerHTML` and similar, but if it refers to an external file, then that means that the `innerHTML` setter has to block on a network request.

* If substitution is triggered by a special attribute, e.g. `paste="#template"` or `paste="file.html"`, then setting this attribute on an existing element via JavaScript should have no effect. This attribute should also have no effect when present in a string passed to `innerHTML` and similar, as with the previous bullet point.
  
  If an attribute is used for substitution and an element with that attribute has other children already, I am unsure whether those children should be replaced, appended to, or moved into any substituted-in template slot(s). Replaced content could function as fallback content for older UAs, but only if elements using the substitution attribute are `display:none` by default in supporting UAs.

* I lean toward having substitution use an element, and toward having that element not be void. Child elements, if present, could be used as fallback content. Alternatively, if implementors are interested in expanding the feature, one way to do that would be having children of the substitution element replace [slot elements](https://developer.mozilla.org/en-US/docs/Web/Web_Components/Using_templates_and_slots#adding_flexibility_with_slots) in the substituted-in content. That would allow for a relatively small and controllable amount of dynamism when making substitutions, though it moves beyond the use case of "automated copy and paste," which is valuable on its own.

- The first writable is put into an errored state, meaning the second writable 'takes over'.

## @trusktr — 2025-05-01

> Synchronous fetching is a big no-no. That's not happening.

@annevk Sync fetching would be very bad indeed. That's not what I meant, and not what we want.

Let me rephrase:

### The need

Fetching should be async, but for sanity the default execution model should be that the *execution* is "down the page" linearly, the same as with existing non-module `<script>`s, inlined `<style>`s, and `<link>`ed styles. Perhaps "linear execution" is a much better term (similar to `await` in JS offering linear execution of a function's logic).

Without a linear execution model by default, content will pop into the page in a random order, introducing unwanted FOUC by default, and would require JavaScript for handling the situation appropriately. 

Using JavaScript would defeat the purpose of the proposal.

### How

The parser can continue parsing forward and fetching files in parallel (async), while the execution catches up. While fetching external files, further includes (or non-module scripts and linked styles) can be also fetched in parallel.

The end goal for default behavior is that externalizing a piece of HTML would essentially behave the same as if it were written inline. The only difference would be slightly more time for the page to execute due to network requests. To the user, the only "difference", before and after assuming the same exact network speed, would be as if the connection to the website got slower by some amount (depending on the number of externalized pieces of HTML and hence the number of additional network requests).

### Optimization 

The above model is *very easy* to optimize in a way that does not require much thought: a bundler would simply inline the content (recursively, in case of includes inside includes, or other non-module scripts and linked styles), without there being a difference in the final behavior of the page apart from speed differences (no random popping/FOUC of content before optimization/bundling, same visible behavior after but faster).

# Reference Implementation & Edge Case Handling in Userland

I've been exploring userland primitives for declarative HTML partial inclusion and created a zero-dependency Web Component, `<html-include>`, that addresses the primary architectural objections traditionally raised against client-side inclusions.

* **Live Demo:** https://alokrathava.github.io/html-include/
* **Repository:** https://github.com/alokrathava/html-include

## Key Edge Cases Addressed

### 1. CLS & FOUC Prevention

The component pre-injects its base block-level styles and allows authors to reserve layout geometry before the included content loads.

The `min-height` and `aspect-ratio` attributes help prevent Cumulative Layout Shift (CLS) and Flash of Unstyled Content (FOUC).

```html
<html-include
  src="partials/header.html"
  min-height="116px"
>
  <div class="skeleton">Loading navigation...</div>
</html-include>
```

### 2. Table Contexts & Parser Eviction

HTML elements placed directly inside restricted parsing contexts such as `<table>`, `<ul>`, or `<select>` may be moved or removed by the browser's HTML parser through foster parenting and parser correction rules.

To handle these cases, the implementation supports an attribute-based fallback using `data-include` on valid host elements.

```html
<table>
  <tbody data-include="partials/table-rows.html"></tbody>
</table>
```

This allows partial content to be loaded into elements that are valid within their surrounding HTML context.

### 3. Recursion Safeguards

The implementation detects circular and excessively deep inclusion chains before initiating additional network requests.

It traverses both regular DOM ancestors and Shadow DOM boundaries using `ancestorChain()` to:

* Detect direct and indirect circular dependencies
* Prevent infinite recursive inclusions
* Enforce a configurable maximum nesting depth
* Stop invalid requests before they reach the network layer

### 4. Script Execution & Content Security Policy

For security, `<script>` elements are stripped from included content by default.

Trusted first-party content can explicitly enable script execution using the `allow-scripts` attribute.

```html
<html-include
  src="partials/dashboard.html"
  allow-scripts
></html-include>
```

When script execution is enabled, scripts are recreated and executed sequentially to preserve document order.

The implementation also supports Content Security Policy requirements by propagating valid CSP nonces when scripts are recreated.

### 5. Race Condition Prevention

The component uses `AbortController` to manage pending network requests.

When the `src` attribute changes dynamically, the previous request is cancelled before a new request begins.

```javascript
const include = document.querySelector("html-include");

include.src = "partials/profile.html";
include.src = "partials/settings.html";
```

Without cancellation, a slower response from `profile.html` could arrive after `settings.html` and overwrite the newer content.

By aborting stale requests, the implementation ensures that only the latest requested partial is rendered.
