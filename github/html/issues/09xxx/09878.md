### What is the issue with the HTML Standard?

Given a form containing both native elements (`<input>`s) and Form Associated Custom Elements, there are several ways to trigger the browser to show any validation messages:

- `form.requestSubmit()`
- `form.reportValidity()`
- `input.reportValidity()`

Calling this when the input is `:invalid` or after calling `setCustomValidity(message)` on it, this will trigger a native "popover" with the built-in or custom validation message. 
![CleanShot 2023-10-24 at 17 58 17@2x](https://github.com/whatwg/html/assets/3968/7fa591c7-8764-4f23-820c-43ad141b817c)

Each vendor has its own styling for these "popovers". So I'm trying provide my own styling which is the same across vendors. The easy part is to call `event.preventDefault()` on the `invalid` event. That event is dispatched when calling `checkValidity()` or `reportValidity()`. By doing that, all vendors no longer show the native popover.

The problem starts after that: there is no way to detect when a Form Associated Custom Element (or a web component wrapping an `<input>` for that matter) should display a validation message. The only event dispatched when calling `reportValidity()` is `invalid`, but since that is also dispatched when calling `checkValidity()`, it cannot be used for that. Also, the event has no additional info to distinguish between `checkValidity()` or `reportValidity()`.

Is there a reason such a "reportValidity() hook" is missing from the standard? What's the idea behind `checkValidity()` triggering an `invalid` event? (if it didn't, then we could just use the `invalid` event for this)

In https://github.com/whatwg/html/issues/5016#issuecomment-624004959 this was also mentioned and acknowledged that this is not possible.

I think the core issue here is that there does not appear to be a way to know when the browser will [interactively validate the constraints](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#interactively-validate-the-constraints) of a form element. ## @jpzwarte — 2023-10-25

Here's a proposal: in https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#interactively-validate-the-constraints, insert the following steps between 2 and 3:

1. [Statically validate the constraints](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#statically-validate-the-constraints) of form, and let unhandled invalid controls be the list of elements returned if the result was negative.
2. If the result was positive, then return that result.
3. Let unhandled reportable controls be an initially empty list of elements.
4. For each element field in invalid controls, if any, in [tree order](https://dom.spec.whatwg.org/#concept-tree-order):
  4.1. Let notCanceled be the result of [firing an event](https://dom.spec.whatwg.org/#concept-event-fire) named [report] at field, with the [cancelable](https://dom.spec.whatwg.org/#dom-event-cancelable) attribute initialized to true.
  4.2. If notCanceled is true, then add field to unhandled reportable controls.
5. (was step 3) Report the problems with the constraints of at least one of the elements given in unhandled reportable controls to the user.
  etc.

That way a control can cancel the `report` event which will prevent the user agent from displaying the native popover. This is also backwards compatible with the current way client validation works (`invalid` event remains exactly the way it is).
When a control receives the `report` event, it knows it is time to display the validation message.

## @jpzwarte — 2023-10-26

Not quite; there are 2 parts to client-side validation: 
1. https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#statically-validate-the-constraints
2. https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#interactively-validate-the-constraints

The first step is the `checkValidity()` method. The second one is the `reportValidity()` method. When you call `reportValidity()`, then `checkValidity()` is run as well (behind the scenes probably). The spec describes that as part of the first step, the `invalid` event is dispatched. This problem is that the second step does not fire any type of event. This issue aims to solve that by firing a `report` event just before the element reports the invalid validity. 

Once the `report` event has been received, then the recipient could enter a "report state" and directly show any new constraint violations. It would not have to wait for a new `report` event (but this behavior is up to you as component author). For example: say a component has a `required` and `minlength` constraint. If you enter nothing and you try to submit the form, then it would show the `required` validation message. Once you start typing, the `required` constraint would be satisfied and it would display the `minlength` validation message. Until you've satisfied that constraint, and then the component would just be valid.

## @ITenthusiasm — 2025-09-14

I wanted to introduce a different approach here. I'm actually not certain if developers _want_/_need_ to know when the browser wants to report an error. Rather, developers want to _drive_ when errors are reported _in response to user interactions_. Browsers already report error messages when the user attempts to submit a form. This is correct and simply needs to be expanded such that: 1&rpar; Validation occurs during other interactions (like `input`) and 2&rpar; Errors are styled and placed appropriately.

For those wanting that capability today, I wanted to mention a JS library that I believe solves these issues, then _pull ideas from it_ which I think could be used in the spec so that JS is no longer needed.

## An Existing JS Solution

I created the [`FormValidityObserver`](https://github.com/enthusiastic-js/form-observer/tree/main/docs/form-validity-observer) to solve this exact problem: A delegated Event Listener watches all of a form's fields for _user interactions_. When those _user interactions_ occur, the validity state is checked to see if any new error messages need to be rendered/displayed. If no errors exist, any visually-displayed error messages are removed; otherwise, the most-relevant error message is displayed to the user. Error messages can be rendered directly to the DOM, or into other environments in the case of JS frameworks. And errors can be customized using JS.

Since accessible form controls _must_ point to elements via `aria-describedby` (or `aria-errormessage`) when displaying error messages, the library automatically knows where it should render errors -- even if some controls live _outside_ the rendered `<form>` element.

I think this is the approach that should be taken when trying to address the error reporting issue. That is, the error messaging should be:

1) Displayed in the proper place/styling _based on markup/attributes_
2) Driven by _user interactions_

There are other things the library can do (like custom validation), but they're irrelevant to the discussion because I can't imagine them ever being doable without JS; so I won't dive into them here. If you need a solution today, you can see if the library does what you need.

Onto the abstracted ideas. I'll take one step at a time here.

## Possible Future Spec Solutions

### Customizing the Error Messages

If we want to support robust error messaging in contexts that don't require JavaScript, then we need a declarative HTML solution. (CSS Pseudo-Elements aren't a practical solution because they don't take into account internationalized SSR applications. Typically, developers are not -- and probably should not -- be generating CSS on the fly server-side.) Ultimately, this means we'll need a solution that leverages attributes...

```html
<input 
  requirederror="Supply something" 
  patternerror="Numbers only plz"
/>
```

or that leverages new/augmented elements...

```html
<input>
<requirederror>Supply something</requirederror>
<patternerror>Numbers only plz</patternerror>
```

The latter example comes from https://github.com/openui/open-ui/issues/802. There, `@scottaohara` mentioned the possibility of using `<output>` instead of creating new error elements. That could potentially work too.

Although these approaches are verbose, there isn't really an alternative option if we want something that works without JS. (If we want something that works _with_ JS, we already have `setCustomValidity`, the `FormValidityObserver`, and other solutions.

### Customizing the UI

Although the above are approaches to providing custom error messages, they don't address the problem of _how_ the messages are displayed or _when_ they are displayed. For error messages that are displayed simultaneously, popovers can get too distracting. (For example, a password field might have a longer error message that blocks other fields if a popover is used.) So we'd want something inline.

How would the the browser know _where_ to render the error messages? If the goal is to give developers full control over the error messages displayed to users, then the best thing that we can do is point one element to another element with attributes.

```html
<input
  requirederror="Supply something" 
  patternerror="Numbers only plz"
  errortarget="my-display"
/>
<div errorcontainer id="my-display"></div>
```

or

```html
<input id="my-field">
<requirederror validationtarget="my-field">Supply something</requirederror>
<patternerror validationtarget="my-field">Numbers only plz</patternerror>
```

As you can see, I'm borrowing ideas from the Popover API with this solution. (The OP of the issue I mentioned also does this.) Similar to Popovers, these "error containers" would be hidden by default. However, when the browser reports the validity of the form fields (e.g., through `control.reportValidity()` or `form.reportValidity()`), it can reveal these error messages until the user resolves them. (And the errors would be revealed for _all_ form controls, not just one.) I imagine focusing the first erroneous field is still desirable.

If no error container is present, the browser will render the error message in its typical, inaccessible bubble. Otherwise, the error message will be rendered to the specified container. For those who feel they _must_ use popovers, perhaps the Popover API could be expanded such that these error message elements appear in the Top Layer when they are revealed if they're given a popover attribute.

Proper ARIA attributes would still be required unless `validationtarget`/`errorcontainer` would be used to imply `aria-errormessage`/`aria-describedby`.

### Complex Error Messages

One last thing we need to consider when it comes to how to display error messages is what to do with more complex error messages. For example, a Password field might display error messages in a `ul > li*N` so that the user can see all of the password requirements upfront.

The element-based approach can handle this rather easily

```html
<patternerror validationtarget="my-field">
  <ul>
    <li>Need Numbers</li>
    <!-- ... -->
  </ul>
</patternerror>
```

The attribute-based approach makes this kind of impossible... unless we shoehorn in other approaches like using templates.

```html
<input
  requirederror="Supply something" 
  patternerror="#password-errors"
  errortarget="my-display"
/>
<div errorcontainer id="my-display"></div>

<template id="password-errors">
  <ul>
    <li>Need Numbers</li>
    <!-- ... -->
  </ul>
</template>
```

Notice the preceding `#`. A preceding `#` would imply pointing to a template, whereas anything else is a "pure string". Of course, the limitation here is that developers would be unable to start their IDs for errors with a `#`. (I'm not sure why anyone would want to do that, though.)

### _When_ to Show Error Messages

This is one of the most important parts. The OP mentions concerns about needing greater clarity on when to display error messages. I don't think this information comes from `reportValidity()`/`invalid` events or the like. I believe it comes from user interactions. In fact, browsers already understand this, because they only call for validity reports when the _user_ clicks the `submit` button.

What's missing here is the ability to display errors `oninput` and `onblur`/`onfocusout`. (_Maybe_ some people might like `onchange` too.) Today, `novalidate` exists so that developers can suppress the native error bubbles and supply their own robust, accessible messages. But developers would have more power if they could specify the scenarios in which reporting should happen in the form instead.

```html
<form reporton="change" rereporton="input" skipinvalidfocus></form>
```

`reporton` would enable developers to show error messages when a user performs a certain kind of interaction. (Validation should always occur `onsubmit` unless `novalidate` is present.) The `skipinvalidfocus` would prevent the first invalid field from getting focused when the form is submitted. (I don't know if that's a good idea, but it's an option.)

The `rereporton` attribute is optional. Today, at least in Chrome, if a user 1&rpar; submits an invalid form, 2&rpar; gets directed to the invalid form field, and then 3&rpar; starts interacting with it, then the browser will automatically update the error message in the popover as the user types. There are obvious reasons why the distracting popover has to disappear in a few seconds in today's behavior. But if the error message is being rendered to the DOM via attributes/elements, then the browser doesn't have to hide the error in N seconds. Instead, it can keep displaying errors until the user resolves _all_ of them. In that case, we have 3 options:

1) After a field is first "reported on", it will _always_ show/hide its error messages whenever its validity state changes. Browsers should be able to handle this automatically, just like they do for native popovers; so devs would not need to observe an event for this change. In this case, `rereporton` isn't needed.
2) After a field is first "reported on", the error message will continue to be updated by user interactions specified by `reporton`, but it will _also_ be updated when interactions specified by `rereporton` occur.
3) After a field is first "reported on", the error message will not go away until another form submission occurs. The `rereporton` attribute would be useless in this case. This is likely an undesirable UX, though it matches what happens in SSR apps today that have more accessible error messaging (if JS is disabled).

### Additional Thoughts

@jimmyfrasche mentioned the idea of showing a list of _all_ broken validation constraints simultaneously. In this case, a `validitystatechange` event could be helpful. However, if the element-based approach was found desirable (instead of the attribute-based approach), then this would open the door for two options:

- Only show 1 error at a time
- Show all errors at once

This could perhaps be configured at a control/`<form>` level with another attribute like `showallerrors`

```html
<input id="my-field" showallerrors>
<requirederror validationtarget="my-field">Supply something</requirederror>
<patternerror validationtarget="my-field">Numbers only plz</patternerror>
```

This way, everything could be handled declaratively, and no JS would be needed (though perhaps the event could still be useful to have).

This idea travels in a very different direction from the OP, so I'd especially be interested in hearing @jpzwarte's thoughts. But I think this direction gives more power/flexibility to developers.
