One unfortunate coupling of concepts in the web platform is the way it is decided whether a `<select>` should be rendered as a listbox or a dropdown. Currently:
- If `size` is specified and is > 1, it is a dropdown
- If `multiple` is specified, it is rendered as a listbox, regardless of the value of `size`

This has several unfortunate consequences:
- It is impossible to create a multi-select dropdown, a very common author need. As a result, this is one of the elements most commonly recreated by authors.
- It is impossible to use `size` to set the height of the dropdown picker, since it makes the control a listbox.

However, **the core problem is that there is no way to control the listbox vs dropdown variable directly**. If there were, these just become sensible (?) defaults that can be overridden.

While we [resolved](https://github.com/w3c/csswg-drafts/issues/12468#issuecomment-3079365750) in the CSS WG that `appearance: base-select` should apply to listboxes as well, it doesn't seem like it will be possible to switch between the two modes in CSS, as the a11y tree is vastly different.

If we were designing `<select>` today, we'd probably make the choice explicit via an attribute, e.g. `type`, which would default to the dropdown rendering.
However, that ship has sailed. What we _could_ do is define an attribute for selecting one of the two modes (names TBB, let's use `type="dropdown | list"` for the sake of this), whose default value is `auto`, which resolves to `list` if either `multiple` or `size` is specified and `dropdown` otherwise (the current behavior). This allows adding more types down the line, e.g. `button-group` or even a value that renders a radio/checkbox group, solving another common web platform pain point.

Another idea that @josepharhar had was to special case `<select multiple size="1">` to render as a dropdown, web compat permitting. I think that’s less elegant because `size` fundamentally has a different purpose, but that's a weak objection.
