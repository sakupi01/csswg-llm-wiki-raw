Currently, `<selectedcontent>` is defined as this strange element that auto-clones the selected option, with unpredictable [timing](https://github.com/whatwg/html/issues/10520), which has no precedent in the web platform. Beyond the practical concern that cloning could lose valuable state, this raises several architectural concerns:
- When using the web platform's declarative languages things just work reactively, and timing or order of operations are not author concerns, by design. 
- `<selectcontent>` seems [overfitted](https://github.com/w3ctag/design-principles/issues/450) to `<select>` use cases, when the core use case is broader.

It seems that what is really needed here is **mirroring** rather than cloning. And the web platform _does_ have precedent for this: it is exactly how [SVG's `<use>`](https://www.w3.org/TR/SVG2/struct.html#UseElement) [works](https://codepen.io/leaverou/pen/gbaadYK)!
Additionally, the need for mirroring is not specific to selects, but comes up incredibly frequently:
- Practically all use cases for `element()`
- Responsive tables (displaying column titles above content)
- Responsive widgets (e.g. switching from static content to a popover or dialog)
- Certain templating use cases (e.g. navigation menus present in both header and footer)
- Editing the same form element in multiple places (e.g. a filter)
- A web component needing to repeat a slotted element multiple times (e.g. a rating widget may accept a slotted icon, and then needs to repeat it)
- Summary content: e.g. thumbnails of slides, tables of content
- Some more here: https://bsky.app/profile/did:plc:eagnfcoqnbtzpkglrtej6ayg/post/3lu6rjcilg22i

I wonder, what if instead of defining it using `cloneNode()` we define `<use>` for HTML content and feed multiple birds with one scone?
To properly replace `<selectedcontent>` with it, we would also need some way to pull in content via a CSS selector, so we can do `option:checked` without requiring ids. Some good discussion on this in https://github.com/whatwg/html/issues/10143 but since this is not about retrofitting an existing idref, I think it's an easier problem.

## Concrete proposal

- An HTML `<use>` element, loosely modeled after SVG's.
- Unlike SVG, `href` would only allow local links (`#hash`). This may be relaxed later (and would obviously be better if we could include that earlier, but the complexity of including URLs is not needed for these cases.
- Unlike SVG, there are no `x`, `y`, `width`, `height` attributes.
- A `select` attribute that takes a CSS selector. When `select` is specified, `href` is ignored (since it can be useful for fallback).
	- Or should it be combined somehow? E.g. specify the root of the matching?
- A `selectscope` attribute that defines the scope of the selector (nearest ancestor wins). If omitted, the scope is the entire document (or should it be the parent of the `<use>` element?).
- The `<use>` element has `display: contents` by default, but can be styled, just like `<slot>`.
- If the selector matches multiple elements, are they all mirrored, as if they were in source order. This unlocks a lot more use cases, and is needed to replace `<selectedcontent>`, so I really hope it's implementable!
- Mirrored elements can be styled differently though the exact mechanism is TBD (a combinator? Simply treating them as descendants? Something else? That part of SVG is a mess, so not something to emulate…)

Putting all these pieces together, we can replace `<selectedcontent>` with `<use select="option:checked" selectscope="select">` or `<use select="option:checked" selectscope=":host">` when used in the select's shadow DOM. Plus, this way, when authors use it, they can customize the matching and exclude certain options.

### TBD

- How to avoid cycles? We can exclude `<use>` elements from the matching but `<use>` elements **inside** referenced elements should be fair game, which can still create cycles, so we need additional constraints. TODO: Study what SVG does.
- Backport `select` and `selectscope` to SVG `<use>` as well?
- a11y / focus management. `<use>` mirrors *everything*, including focus state. How is that exposed to the AT? Is that desirable?

## @justinfagnani — 2026-06-04

I would really like to see this approach used instead of cloning for customizable select, even removing cloning before customizable select ships cross-browser.

Cloning just doesn't work in general. It doesn't support non-markup state (JS properties, input value, select selected item, etc.) and it can massively interfere with code that introspects the DOM on startup, like SSR hydration (see https://github.com/lit/lit/issues/5349), which will process the cloned contents of `<selectionoption>` as if they were server-rendered.

Mirroring fixes these problems, even if it does have complexities like mentioned in https://github.com/w3c/csswg-drafts/issues/9284
