### What problem are you trying to solve?

When building a web component, it isn’t currently possible to use a select element inside the shadow root and let the web component user provide option elements to be slotted into the select. Here’s an example:
```html
<my-custom-select>
  <template shadowrootmode=open>
    <select>
      <slot></slot>
    </select>
  </template>
  <option>one</option>
  <option>two</option>
</my-custom-select>
```

### What solutions exist today?

If I wanted to build this today, I'd create a MutationObserver to detect changes to the custom element's subtree and clone the options into the shadow root. I'm not sure how I'd deal with copying the styles from the options.

### How would you solve it?

I would solve this by changing the select element to look for options in its flat tree.

## @josepharhar — 2025-08-05

Some spec changes which I think will be needed to support this use case based on my prototyping so far:
- The select’s [list of options](https://html.spec.whatwg.org/multipage/form-elements.html#concept-select-option-list) needs to do a flat tree traversal to look for option elements instead of a regular DOM traversal.
- The option HTML element insertion steps and HTML element removal steps need to do a flat tree ancestor traversal instead of a regular DOM ancestor traversal.
  - This runs the [selectedness setting algorithm](https://html.spec.whatwg.org/multipage/form-elements.html#selectedness-setting-algorithm), which needs to be run every time an option is added or removed from a select.
- When slot assignment is recalculated and a [slot change is signaled](https://dom.spec.whatwg.org/#signal-a-slot-change), any ancestor select element of the slot element should run its selectedness setting algorithm to account for options which may have been added or removed.

## @chrisdholt — 2025-08-05

IMO, this is a necessary change and while I understand we are in "feature" land at this point due to this requiring spec changes, this was clearly a "miss" in the spec process itself. It's incredibly common for design systems to be built nowadays using Web Components. As it stands with the current implementation, usage within the shadow DOM is not feasible at all, meaning that this improvement to the platform cannot be used with the platform's actual component model. We do not have a method of extending this element as a built-in, nor do we have a way to attach a shadow. Without this improvement, custom element authors who wish to provide a declarative "select" that benefits from Web Components as a technology must rebuild everything, using heavy-handed JS, custom DOM and templating, and provide their own a11y support. That's been par for the course, but it is exactly the reason that myself and others who have authored custom element libraries were active early on in Open UI. We'd like to stop rebuilding this and we'd like to be able to use web-native technologies rather than large JS frameworks to do so 😄.

Please consider prioritizing the changes to the spec so that we can make use of this improvement to the platform!

## @josepharhar — 2026-02-10

> It seems to make sense that if we allow this for `<select>` we should allow this for `<datalist>`.

Yes, if people are asking for it like they are for select, which I could imagine happening after we implement customizable combobox.

> Does that get messy? 

I don't see any reason that doing this for datalist would be any harder than doing it for select.

> What about `<fieldset disabled>`, should that mark slotted elements disabled?

I haven't seen this asked for before. I wonder if custom element authors are using fieldset in their shadowroot and slotting in form-associated elements.

> What about `<form>` itself (see [#10220](https://github.com/whatwg/html/issues/10220))? I imagine `<form>` would be the riskiest in terms of web compatibility (especially concerning would be FACE, I guess?).

Making a custom element behave like a form seems like a good solution there, just like form-associated custom elements solves a similar problem without needing to make the browser track stuff in the flat tree.

Form-associated custom elements enable custom elements to have form-associated elements in their shadowroot and pass through their state to an ancestor form element, but this case doesn't involve slotting:
```html
<form>
  <x-input>
    #shadow-root
      <input>
```
Solving this issue with select in a way that doesn't involve slotting would be nice, but I'm struggling to find an appealing way to do it. Maybe we could make custom elements that behave like select elements and option elements, but that just sounds like custom builtins. How else can we associate the select element and option elements in an example like this?
```html
<x-select>
  #shadow-root
    <select>
      <slot>
  <x-option>
    #shadow-root
      <option>
```
Maybe custom builtins aren't powerful enough for this use case since they don't have a shadowroot available for the custom element to put whatever it wants in there, but this is what I'd imagine it looks like:
```html
<select is=x-select>
  <option is=x-option>
```

In general, I'm interested in making the select element support slotted option elements because multiple authors are asking for it and because other cases like forms and FACE have different types of solutions that work well.
