### What problem are you trying to solve?

See [explainer](https://github.com/w3c/csswg-drafts/blob/main/css-view-transitions-2/two-phase-transition-explainer.md).

When switching between pages, the navigation experience can be both abrupt and laggy when not instant.
It waits until commit before displaying any response, and then freezes (either the old frame or blank) until rendering is unblocked.

We want to allow authors to provide a better experience there, both reducing the "frozen" time and providing an exit/preview indication during exit (e.g. a skeleton);

### What solutions exist today?

The developer can intercept the navigation (e.g. `navigateEvent.intercept({precommitHandler})`, and start a new navigation when they're ready.

However, this would create a slow end result as the cross-document navigation initiation is delayed.

Also developers can already show an animation when leaving the page, but it would be aborted mid-way in an abrupt way depending on commit timing.

### How would you solve it?

1. Expose something along the lines of `navigateEvent.deferCommit(promise)` which would allow the old page to run whatever exit UI they want.

2. Expose something like `navigateEvent.nextPageReadyToRender` which is true on prerender/BFCache restore when the next page is not render-blocking. This would allow the old page to selectively decide whether to defer or let the presumably instant navigaiton continue. 

### Anything else?

1. This is different from https://github.com/whatwg/html/issues/10997, where the "unload" actions are also valid for cross-origin navigations (e.g. an IndexedDB transaction). This is specific for in-app (same-origin) navigation customization.

2. In parallel, will pursue a way to do this declaratively in CSS, e.g. by allowing a CSS animation to declare that it is preferred for it to run until completion. This would allow this experience to be achieved declaratively, without having to manually clean up the state e.g. in the case of the navigation being aborted.

## @nickcoury — 2025-10-22

Are there any signals available that would indicate when the next page is ready? Use cases that are coming to mind:

1. Showing infinite skeleton loaders until the next page is ready. This is kind of possible today by just playing an animation on the outgoing page, but the animation will freeze when the document is unloaded and before the next page is ready which is visually jarring. If this proposal is implemented in a way that the animation plays until the next page is ready to transition (using render blocking + cross-doc VTs) then that would allow an instant visual response to the navigation click and also a seamless transition.

2. "Catching" an animation in-flight. Imagine the outgoing page plays a 350ms animation but the new page is ready in 50ms. If this can be detected, it would be ideal for the site to resolve the promise and swap to an animation that includes the new page content faster, similar to native mobile apps rendering skeleton loaders that are replaced with new content during a transition. Though this already feels a bit challenging to coordinate writing down the idea. I wonder if there's a different cross-doc VT mode that could be played on the exiting document but using the new page as the live root pseudo. This would also need more thought if the new root pseudo starts as skeleton loaders but is replaced dynamically with the new page content. Perhaps it could utilize render blocking and a convention that the new content overlays any other content in the new pseudo upon render.

The main benefits of the heuristic approach would be simplicity, and the potential for the browser to optimize certain cases like cached content to avoid unnecessary latency. 

This might benefit from some kind of timeout as a safeguard. I don't think there's a vulnerability for same-origin given the user could always intercept and stop the navigation, though there might be if this was cross-origin. A timeout could prevent a footgun if the website doesn't properly resolve the promise.

## @noamr — 2025-10-23

@nickcoury agreed, there are some advantages to keeping this as an animation-based heuristic:
- it's easier to reason about letting the browser abort and force the commit
- it's more difficult to abuse
- #10997 already deals with non-UI use-cases, which are usually not limited to same-origin navigations
- it's easier to connect with browser heuristics that have to do with the next page, e.g. waiting for render-blocking resources if the next page is prerenedered.

## @noamr — 2025-10-23

If we do want to go with the explicit/generic/non-heurisic route, perhaps a direction would be to better align this with prerendering.

Something along the line of this:
```js
// Initializes prerendering if that hasn't started yet, and returns a promise that resolves when all the render-blocking resources of the new document are loaded
navigateEvent.prerender();

// This doesn't intercept, but allows deferring the commit without waiting for `pageswap` to do so.
navigateEvent.defer(promise);

// Then you can do something like:
navigateEvent.defer(Promise.race([
  navigateEvent.prerender(),
  new Promise(resolve => setTimeout(resolve, 1000),
  document.startViewTransition(() => preview_transition()).finished
]);
```

I still think there is value in making this declarative and giving the browser a bit more control; But perhaps both options are viable.

## @noamr — 2025-12-09

Current API design from draft PR:
Happy to get feedback for it!

```js
// It's called "deferPageSwap" rather than "deferCommit"
// because it does "commit" a same-document navigation.
navigateEvent.deferPageSwap({
  // This means that the history is swapped immediately, like a `pushState`,
  // and the navigation becomes a `replace`.
  historyChange: "immediate",
  async handler(controller) {
     const transition = document.startViewTransition(show_skeleton);

     // The restore callback will be called if the navigation is aborted, or if this document is restored from BFCache.
     controller.addRestoreCallback(() => hide_skeleton());
     return transition.finished;
  }
});
```

The main addition since past conversation is the addition of `historyChange` - by default, deferring commit/page-swap would change the history immediately and then "replace" when swapping documents. This is to avoid confusion when pressing the back button etc in the middle of preview. This behavior is customizable via the `historyChange` option.

## @noamr — 2026-08-25

Coming back to this after fleshing out the declarative alternative. See discussion in https://github.com/w3c/csswg-drafts/issues/12829#issuecomment-5345261399

Some insights:
- Doing all of this entirely in CSS has some trade offs that are not all positive. The main negative tradeoff is that style is not the only thing to modify during preview - the author might want to set up a11y as well (think `aria-busy` for example), and perform other imperative operations
- In general, this is an advanced feature, at least to begin with. It feels very low level when embedding it into CSS
- `addRestoreCallback` is not that bad. It's a foot-gun but we can document it in a way that people understand. It's similar to existing patterns like having to clean up after `useEffect`.

My conclusion is that this (`deferPageSwap` as part of the navigation API) is probably a better first step than CSS, and that we should look again at declarative solutions once people use this low-level and extensible enabler and patterns emerge.
