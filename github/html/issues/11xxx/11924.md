### What is the issue with the HTML Standard?

Based on PR #11721, the disabled algorithm for option has received significant changes.

However, the algorithm may not be entirely clear:

> The **disabled** attribute is a [boolean attribute](https://html.spec.whatwg.org/multipage/common-microsyntaxes.html#boolean-attribute). An [option](https://html.spec.whatwg.org/multipage/form-elements.html#the-option-element) element option is disabled if the following steps return true:
> 
> 1. If option's [disabled](https://html.spec.whatwg.org/multipage/form-elements.html#attr-option-disabled) attribute is present, then return true.
> 2. For each ancestor of option's [ancestors](https://dom.spec.whatwg.org/#concept-tree-ancestor) in reverse [tree order](https://dom.spec.whatwg.org/#concept-tree-order):
>    1. If ancestor is a [select](https://html.spec.whatwg.org/multipage/form-elements.html#the-select-element), [hr](https://html.spec.whatwg.org/multipage/grouping-content.html#the-hr-element), [datalist](https://html.spec.whatwg.org/multipage/form-elements.html#the-datalist-element), or [option](https://html.spec.whatwg.org/multipage/form-elements.html#the-option-element) element, then return false.
>    2. If ancestor is an [optgroup](https://html.spec.whatwg.org/multipage/form-elements.html#the-optgroup-element) element, then return true if ancestor's [disabled](https://html.spec.whatwg.org/multipage/form-elements.html#attr-optgroup-disabled) attribute is present; otherwise false.
> 3. Return false.

Step 2.1 may end the ancestor search early, but why is the list of elements like this: [select](https://html.spec.whatwg.org/multipage/form-elements.html#the-select-element), [hr](https://html.spec.whatwg.org/multipage/grouping-content.html#the-hr-element), [datalist](https://html.spec.whatwg.org/multipage/form-elements.html#the-datalist-element), or [option](https://html.spec.whatwg.org/multipage/form-elements.html#the-option-element)? For a web developer, I think this will not be obvious. Could you explain this list? It would also be a good idea to add a note to this step that would explain why these particular elements were chosen.

## @josepharhar — 2025-11-21

Some more historical context on this is:
1. I/we chose not to support nested optgroups, at least for now, and not including descendants of nested optgroups follows that decision.
2. I/we wanted to unify some tree traversals in chromium which do things like collect option elements for select.options, collect "list items" to be rendered in native pickers, and calculate disabledness like this algorithm. Figuring out how to represent an option element inside another option or inside an hr element in a native picker is challenging, and excluding them seemed like a logical decision.

(I say I/we since its hard at this point to remember off the top of my head whether each detail was decided in code/spec I originally wrote or code review feedback or spec review feedback)

## @cdoublev — 2026-02-12

In current versions of Chrome and Firefox ESR, `:disabled` matches `<option>` nested in `<optgroup>` nested in `<select>` nested in `<fieldset>` when either `<select>` or `<fieldset>` has the `fieldset` attribute specified. It does not match when only `<optgroup>` has the `disabled` attribute specified.

This is not compatible with the current definition of this algorithm in all cases.

<details>
<summary>Example</summary>
<br>

```html
<style>
  option:disabled {
    outline: 2px solid red;
  }
</style>
<form>

  <fieldset disabled>
    <select>
      <optgroup>
        <option></option> <!-- red outline -->
      </optgroup>
    </select>
  </fieldset>

  <fieldset>
    <select disabled>
      <optgroup>
        <option></option> <!-- red outline -->
      </optgroup>
    </select>
  </fieldset>

  <fieldset>
    <select>
      <optgroup disabled>
        <option></option> <!-- no red outline -->
      </optgroup>
    </select>
  </fieldset>

  <fieldset disabled>
    <select>
      <optgroup disabled>
        <option></option> <!-- red outline -->
      </optgroup>
    </select>
  </fieldset>
  
</form>
```

</details>

Should this algorithm find `<datalist>` or `<form>` before it can return anything?

WPT has a [test](https://github.com/web-platform-tests/wpt/blob/c12c26e12df02a81af21545b625f658c971c3e20/html/semantics/selectors/pseudo-classes/disabled.html#L23-L26) that all browsers pass and that expect `:disabled` to match `<option disabled>` nested in `<optgroup disabled>` nested in `<select disabled>`. There should be 3 separate test cases defining the `disabled` option on only one of them imo.

## @josepharhar — 2026-02-12

Thanks for the example.

Making options become disabled when they are inside a disabled optgroup makes sense, but I have a few concerns:
- Unforeseen compat issues with how this has worked for decades
- We would have to tweak lots of UA styles for base and auto appearance modes in order to prevent rendering changes. The UA styles for disabled options would start applying, and when combined with existing styles for disabled optgroups I think we might end up with double transparency/opacity or other issues.
- Activation behavior would probably still work as expected, but would need double checking.
