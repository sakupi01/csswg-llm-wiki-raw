### What is the issue with the HTML Standard?

While playing around a bit with the enhanced `select` element semantics I realized that for the `option` element we'd need to observe changes to descendant elements to correctly handle this case:
```html
<p><select id=select>
 <div>
  <option>2<div id=evil>3</div></option>
 </div>
 <div>
  <option>1</option>
 </div>
</select>

<p><button onclick=evil.textContent='4'>Click</button>
```
When you hit "Click" the select is supposed to show 24, not 23. This might not be script-observable if you do everything lazily, but it's UI and reference-test observable and as such it probably needs to be defined.

I'm not sure how we would go about defining this however as thus far we've avoided making the web platform itself rely on mutation observers (and it's unclear if that's what we want timing-wise). (I asked around and for WebKit using mutation observers for this is not something we're interested in.)

Also, to be sure, is this the only case with the enhanced `select` element that needs something like this?

## @josepharhar — 2025-10-08

Chromium has been using a mutation observer to implement this since 2020 due to sites using script to manually insert elements with text inside options which would have been thrown away by the parser: https://chromium-review.googlesource.com/c/chromium/src/+/2235227

I've briefly looked into making it one mutation observer per select element instead of one per option element which could theoretically be more performant, but I haven't gotten anything working yet. I'm open to alternate ideas.

> Also, to be sure, is this the only case with the enhanced select element that needs something like this?

- appearance:auto rendering of select elements need this to update their copy of its text content used for rendering in the document, including a drop-down select's button or a listbox select's options.
- appearance:base-select rendering of the select element itself without an author provided button element needs this in order to update its button text content, but only for the currently selected option.
- appearance:base-select rendering of option elements inside the picker don't need this because the option just slots its child nodes in.
- datalist doesn't render anything in the document right now so that shouldn't be needed.
- depending on how options are rendered outside of a select or datalist, you might want this, but the last time I checked, all browsers render something different for this.

## @annevk — 2025-10-08

Okay, I noticed Chromium has a mutation observer for `select` elements as well, but it did seem like that was only for metrics.

It's weird that Chromium added this before the `select` element was enhanced as I'm pretty sure no other browser has logic for descendants. Though maybe it's because that test forces a layout of some kind to happen that makes other browsers recalculate lazily?

One way we could tackle this is by introducing "descendant change steps" in DOM with some kind of accompanying disclaimer that you should really design your thing to not need it if it can be avoided. Then whenever we run children changed steps we also run that for the entire ancestor chain. And perhaps we assert that you can't have both to keep it straightforward.

I do think it might be observable for `datalist` as when those options are shown to the user in theory they could be mutated through a timer or some such. Not a great experience though.

That last bit also makes me question a bit whether we truly want to require this as while it's reftest-observable, it's also UI. But I suspect dynamic updates are already supported for children and in that case it should be consistent with descendants.
