### What problem are you trying to solve?

Running script when a select element's picker is opened or closed

### What solutions exist today?

For opening the picker you could add event listeners to the select element itself to detect clicks or keyboard inputs which might open the picker. This would require incorporating platform differences and looking at the event's patch to see whether the event originated in the picker or not.

For closing the picker you could add click and keyboard event listeners to the whole document or document.body, and guess whether they will close the picker or not. The same challenges for opening still apply, but it would likely be even harder to figure out whether the event will close the picker.

### How would you solve it?

Add toggle and beforetoggle events to the select element which get fired when the picker is toggled open or closed.

This would have been possible for customizable select with an earlier propsed design which allowed the author to provide their own popover element as a datalist element, but since we removed that capability it is no longer possible to listen to toggle and beforetoggle events directly on the popover since it is in a user-agent shadowroot.

This was raised in OpenUI here: https://github.com/openui/open-ui/issues/1228

- Don't fire beforetoggle/toggle for `<select multiple size=1>`, even when it is rendered as a drop-down box.
- Don't fire beforetoggle/toggle for `appearance:auto`, since the drop-down box or listbox should be consistent in base appearance.

## @teetotum — 2026-02-26

I'm very much in favour of finally having events that allow us to observe when a `<select>` opens or closes its dropdown.
But I want to challenge the idea that it needs to be the [toggle](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/toggle_event) and [beforetoggle](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/beforetoggle_event) events.
I believe a better solution would be to have a new and distinct event type for the `<select>` element; either as a pair: `selectopen` and `selectclose` or a combined event `selectpickertoggle` (with oldState / newState properties).

This would have the following advantages over reusing the existing `toggle` event:
- The question whether `apperance:auto` or `apperance:base` has any influence on the event vanishes because now the new event is no longer tied to the implementation detail whether the picker is in the top-layer or not.
- The question whether there needs to be a cancelable `beforetoggle` to avoid inconsistencies vanishes; there would be no need for it and no inconsistencies would result.
- It would leave room for a potential future improvement of the customizability:
  > [...] earlier proposed design which allowed the author to provide their own popover element as a datalist element
  
  This path would still be open, and such a popover would emit regular `toggle` events without clashing with the select's _native_ events
- The `toggle` event as it exists today already creates problems by lumping together a bunch of unrelated HTML element types that can potentially emit this event type (see explanation below) and I would not want to exacerbate the situation by adding yet another element type as a potential emitter.

## a problem with the toggle event as it is today

A toggle event with newState `open` currently can mean:
- a `<details>` element is expanded
- a `<dialog>`  was opened with `.show()` or with `.showModal()`
- a popover was opened with `.showPopover()` or with `.togglePopover()` or declaratively

But correctly distinguishing these cases in an event listener is not straightforward; a `<dialog popover="manual">` could be used as a popover, but it could also be shown with `.showModal()`, a `<details>` element could have a popover attribute that is never used. How would an event listener then decide "this opened as a popover" and "that opened as modal dialog" and "and that expanded as a reveal"?

Therefore the following code is subtly wrong:
```
document.addEventListener('toggle', (e) => {
  const element = e.target;
  if (element.tagName === 'DIALOG') {
    handleDialog(e);
  } else if (element.hasAttribute('popover')) {
    handlePopover(e);
  } else if (element.tagName === 'DETAILS') {
    handleDetails(e);
  }
}, { capture: true });
```
and we are forced to perform additional checks on the elements like `element.matches(':popover-open')` or `element.matches(':modal')`
