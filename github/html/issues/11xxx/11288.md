## What problem are you trying to solve?

Filtering `<select>` menus is a common UI/UX pattern on the web today and has become an expectation both for users and developers, especially for lists that contain dozens or hundreds of options. Users often want to quickly type and narrow down results. While many JavaScript libraries provide this behavior, often by building custom “combobox” components that simulate a text input tied to a dropdown, these solutions typically require replacing the native `<select>` element entirely.

There’s currently no built-in or semantic way in HTML to connect a plain `<input>` to a `<select>` for filtering purposes. For many use cases, developers don’t want to fully re-implement a combobox; they want a lightweight, accessible way to make native `<select>` elements searchable, without sacrificing built-in keyboard support, form integration, or semantics.

## What solutions exist today?

There are many JavaScript-based solutions that simulate filterable selects, but they come with tradeoffs. Most of them:

* Replace the native `<select>` entirely with a custom component
* Lose built-in accessibility and keyboard support
* Add a significant amount of complexity for a relatively small feature
* Require developers to write or copy filtering logic even when they just want something simple

There is no native HTML mechanism to declaratively link a text input to a select for filtering purposes.

## How would you solve it?

I propose two complementary enhancements to HTML that would allow web-native, accessible filtering of `<select>` elements using `<input>` elements:
1. Using `for` to associate an external `<input>` with a `<select>`
2. Allowing an `<input>` inside a `<select>` to act as a built-in filter

Both could be implemented and supported simultaneously:

### Option 1: Using `for` to associate an external `<input>` with a `<select>`

Allow `<input>` elements to use the `for` attribute to link to one or more `<select>` elements for the purpose of filtering options by text.

**Example:**

```html
<input type="text" for="fruit-select" placeholder="Type to filter">
<select id="fruit-select">
  <option>Apple</option>
  <option>Banana</option>
  <option>Cherry</option>
  <option>Date</option>
</select>
```

When the user types in the input, only options in the associated select that match the input text would remain visible. The filter could match case-insensitively by default and support substring matching. The unfiltered options would still remain in the DOM but be hidden visually.

This would preserve keyboard accessibility and native `<select>` behavior while giving developers a way to enhance long dropdowns in a declarative way.

The `for` attribute already exists to associate form controls, and it fits well here as a mechanism to link an input to the select it controls. This could be extended to support multiple selects using space-separated IDs.

### Option 2: Allowing an `<input>` inside a `<select>` to act as a built-in filter

In addition to the above, placing an `<input>` element directly inside a `<select>` could indicate that the input should act as a native filter for that select’s options.

**Example:**

```html
<select>
  <input placeholder="Filter options...">
  <option>Apple</option>
  <option>Banana</option>
  <option>Cherry</option>
  <option>Date</option>
</select>
```

When the input is typed into, the select options would be filtered based on the input text using the same behavior as described above. This approach would be useful in self-contained patterns, where the filtering UI and the list are tightly coupled within a single component structure.

Both of these enhancements would work in parallel and give developers flexible ways to enable native filtering with minimal effort, while still preserving semantics and accessibility.

## Anything else?

* Filtering behavior could be customizable later (e.g. with attributes like `filtermode="starts-with inclusive"`)
* It would be important to ensure accessibility, especially for screen reader users and keyboard navigation
* Filtering could work without JavaScript, making it more robust in progressive enhancement scenarios
* This could be a small but meaningful quality-of-life improvement for forms with large or dynamic selects

## @LeaVerou — 2025-07-15

This proposal seems to couple many different things and tries to solve many different problems at once. Let's try to disentagle them.

## Combobox vs autocomplete

A combobox is fundamentally different from a searachable select, even though both are dropdowns with a searchable list of options. One constrains the user choice within the available options and the other aids the user by suggesting common inputs, but does not constrain them in any way. A `<datalist>` + `<input>` affords the combobox pattern, not the searchable select pattern.

Additionally, `<datalist>` as currently implemented is imperfect for combobox patterns, because it provides no way to make the internal value invisible, in the way a `<select>` does. There is no way to follow the `<select>` pattern of having separate user-friendly labels and separate machine-readable values. You _can_ have options with separate values and labels, but when selected, the `value` is entered in the input, not the label. Since inputs do not support separate labels and values, it's unclear how else that could possibly work. Having a separate presentational value and a separate submitted value could be useful functionality in general, e.g. for date formatting, number formatting and so on, so perhaps there is a separate proposal there.

## Customizing how the filtering works

Customizing how the filtering happens is something that is not only useful here, but also for `<datalist>` and it seems should be solved together for both, but I see it as separate from adding filtering functionality to selects. Just like `<datalist>` shipped with UA-defined filtering, so can this.

For `<datalist>` one question is whether that is behavior that should be specified on the `<datalist>` itself, or the `<input>`, which can only be answered via use cases. Usually they are 1-1 so this doesn't matter, but often they are not. I can't think of use cases where it needs to be different for the same set of data, so I'm leaning towards making it part of the `<datalist>`, but more research is needed.

Additionally, whatever declarative solution we come up for making common cases easy, ideally there should also be a JS API for  making complex cases possible (fuzzy search, AI search, remote loaded options etc). Otherwise, authors will still resort to reimplementing these controls.

## Ease of use vs power curve

Authors should not have to code filtering by themselves just to style the filtering input. If they don't care about styling the filtering input or customizing its behavior, they should not need to provide one. I can't remember what was decided about native elements using slots, but IMO it's a great mechanism for this type of progressive customization with sensible defaults.

From a UX point of view, **any select with more than a certain number of options _should_ be searchable**. There is certainly a gray area, but I have trouble thinking of use cases where searchability is not desirable in a select with several dozen options (such as a country selector). Most OSes afford some basic searchability through typing, but this is an undiscoverable power user feature, since the typed characters are not visible.

So, I would even argue that at least for unstyled selects in the dropdown state with more than N options, the filtering should be there **by default**. 

## Putting it together

I'd propose:
- An attribute to enable/disable filtering, with the default being `auto`, which enables filtering when in the dropdown state and there are more than N options (which could even be UA-dependent). 
	- The attribute can be later expanded with values to declaratively customize how the filtering works.
	- Potential names: `filterable`, `searachable`
	- A way to define a function to customize how the filtering works (not MVP). 
		- Perhaps `HTMLOptionElement.matchesFilter(text)` (though then it would need to be set on every `<option>` and these are often dynamically added/removed)
		- Alternatively, `HTMLSelectElement.matchesFilter(text, option)` (with a corresponding `HTMLDataListElement` attribute)
- By default, the filter is a shadow DOM `<input>` which can be accessed through a pseudo-element (e.g. `::select-filter`). For more customizability, authors can slot in their own `<input>`.
