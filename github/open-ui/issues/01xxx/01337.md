While dual-handle usage (min/max price filters) is the most common use case, the foundation of the <rangegroup> API supports adding more than two handles. 

Community feedback provides specific, validated use cases where 3 or more handles are necessary, which confirms the design choice to support N handles, the use cases are however, limited.

## A few Justifications for 3+ Handles:

- **4 Handles:** Opening Hours Selector to manage separate open and close times (e.g., AM shift and PM shift), which is demonstrated in the prototype and mentioned by developers.
- **3+ Handles**: Data visualization tasks, such as setting bin sizes across a histogram, or complex category allocation in budget tracking.
- **N Handles:** Used in Color gradient selectors.

There is, however, a caveat here. Most people I talk to tell me that they haven't used more than two handles, mostly because a library didn't support it, and then another way was easier (this also resulted in the form, a lot of examples with two thumbs, barely any with more). 

However, many are excited that if it were possible, there might be new ways to visualize ranges.

So, I'd love to ask confirmation here. Based on the (currently) limited use cases. Do we want to continue with this idea for an API. 
I feel that this API opens up possibilities that weren't there yet and can be made accessible in a clean way. 

The other way would be a lot of attribute additions, which I feel could get bloated really fast.

The community is positive of the idea to have N-thumbs, but once again use cases are limited.

My main question here is: Is there actually a case **against** the capability of making it more than 2 thumbs based on the current API design?
Should there be a limit (also from an engineering standpoint)? Or is the author's responsibility?

## @TheJaredWilcurt — 2025-12-15

This could help with scheduling events, such as auditions, performances, live concerts, conference talks, etc.

```
   5:30     6:00     6:30     7:00     7:30     8:00              9:00     9:30    10:00
<---|--------|--------|--------|--------|--------|-----------------|--------|--------|----->
  Staff    Band     Setup/   Venue   Opening  Concert           Set Ends  Audience  Venue
 Arrives  Arrives Sound Test Opens     Act     starts                      Leaves   Closes
```

Though a table or bulleted list would be better for communicating this information to attendees, when creating the event, it may be more natural to use a timeline, instead of a stacked series of input fields for times:

```
|  5:30 📆 | Staff Arrives
|  6:00 📆 | Band Arrives
|  6:30 📆 | Setup/Sound Test
|  7:00 📆 | Venue Opens
|  7:30 📆 | Opening Act
|  8:00 📆 | Concert Starts
|  9:00 📆 | Set Ends
|  9:30 📆 | Audience Leaves
| 10:00 📆 | Venue Closes
```

If each time picker was an input, you'd need to add in extra logic to ensure they are sorted in the correct order, etc. Each form would have interconnected logic and validation, which is more complex than just one form that handles all of that more naturally. The range version also visually conveys the distance between events.

* * *

Another usage could be in draggable timelines. Think video or audio editing. Having multiple segments on the same timeline, each with a start/end timestamp that cannot overlap. This would allow trimming a portion of a clip, or moving those clips closer/further apart on a timeline. Or even overlapping to create a new segment with a cross fade between the other two.

Being able to define the nodes on the range with ID's and connect them would be nice natively (A+B move together, C+D move together), but could also be handled with JS.
