I've been looking in to how the Interest Invokers work from an accessibility perspective, and have a number of potential concerns mainly relating to the way that semantics seem to work in demos, and the way that the explainer says that they should work. *As a heads up*: this is my first time contributing to any of this work, so if I'm way off, or should log issues elsewhere, I'd appreciate you letting me know! 😅 

In the [InterestInvoker example using the interestfor attribute](https://mdn.github.io/dom-examples/interest-invokers/popover-examples/) that I've reviewed, as well as an example using the [interestfor polyfill](https://www.npmjs.com/package/interestfor), screen readers don't seem to consistently be announcing the popover content when the relevant controls receive focus.

In the InterestInvoker example using the `interestfor` attribute, we found JAWS and Narrator don't announce the tooltip's content when focusing on the button with `Tab`, `Shift` + `Tab`, or any screen reader navigation command. NVDA doesn't speak it when using `Tab`, or any screen reader navigation command, but it does speak it when using `Shift` + `Tab`. When using the polyfill, the content is announced as if using `aria-describedby`, but when reading through the content as a whole using a screen reader (not focusing on the elements), there are no announcements to convey that the interactive elements have related tooltips/popovers, nor how these would be accessed.

While displaying tooltips on hover or focus is a fairly standard way for developers to implement tooltips, as things currently stand, I think this may resemble more of an anti-pattern (based on semantics currently available to us). It establishes that a single control should be responsible for multiple interactions, and I'm not sure that we have the semantics to clearly communicate this type of behaviour. I can't think of a way to flag that an individual control will display additional content when focused, when a screen reader is reading through the content. As a result, I think this functionality may inadvertently result in people using screen readers missing information.

The explainer also documents that there may be "rich hints" - tooltips that contain additional content, for which `aria-expanded` would be set on the trigger element:

> [Rich hints (aka hovercards or other)](https://open-ui.org/components/interest-invokers.explainer/#rich-hints-aka-hovercards-or-other)
> Since rich hints have additional content that might want to be explored directly, additional connections need to be made here:
> The rich hint popover gets a minimum role of “tooltip”…
> The interest invoker gets `aria-expanded=true` when the rich hint popover is open, and aria-expanded=false when it is not, unless the interest invoker is inside the popover.

I'm not sure if I've understood this right, but this also has me a little concerned. The use case that comes to mind is if a button already has a distinctive purpose, such as to open a dialog, when focused, according to the spec `aria-expanded="true"` would be set on the button and a screen reader would announce that the control is expanded. The issue is that `aria-expanded="true"` is an attribute that we might reach for to convey that a dialog has opened. In the circumstances that I've explained, if I've understood correctly, this announcement on the popover being triggered would then obfuscate the primary purpose of the control. It would become quite difficult to understand whether the button's dialog has been triggered or whether there's a popover present, without being able to see the screen.

I understand that there's the suggestion of the `has-interest-for` attribute to help communicate this state, but I'm not sure how this would work if the dialog is open, and `aria-expanded` has been set by the author, but then the popover is also present, for which `aria-expanded` should be set by this new functionality, along with the state being communicated to platform accessibility APIs?

I've tried to do quite a bit of due diligence in reading through related OpenUI issues here in this repo, as well as a number of issues linked out to from the explainer. However, I still have a feeling that I'm missing something, so I'm really sorry if these concerns have already been discussed and I'm re-treading old ground.

tl;dr: I'm unsure about whether there are ways of communicating that elements have associated interest invoked popovers for people using screen readers, and as a result, may lead to people missing information.

> In the InterestInvoker example using the `interestfor` attribute, we found JAWS and Narrator don't announce the tooltip's content when focusing on the button with `Tab`, `Shift` + `Tab`, or any screen reader navigation command.

So I looked into this one a bit more in Chrome, and found that the issue is because a "plain hint" (as [defined in Chromium](https://source.chromium.org/chromium/chromium/src/+/main:ui/accessibility/ax_role_properties.cc;l=1181;drc=5775fdf3e4c6a1fc988fba5cf5914207e0444a0e)) includes `kInlineTextBox`, `kLineBreak`, `kStaticText`, `kCanvas`, `kDocCover`, `kGraphicsSymbol`, `kImage`, `kSvgRoot`, `kGenericContainer`, `kNone`, and `kGroup`. However, in the [linked example page](https://mdn.github.io/dom-examples/interest-invokers/popover-examples/), the popover contains this:

```
<div id="button-tooltip" popover="auto">
  <p>This button does absolutely nothing.</p>
</div>
```

The `<p>` there gives it `role=paragraph`.

==> Should we consider `paragraph` roles to be "plain hints"? It seems like yes, but I'm not the expert.

By the way, for both of these issues, based on the conversation on https://github.com/GoogleChrome/modern-web-guidance-src/pull/3357, I've [landed changes to Chromium](https://crrev.com/c/8769804):


1. Elements that invoke a popover via popovertarget or commandfor (with a popover command) now take their expanded state and details relation only from the popover they invoke, never from interestfor. Previously, the expanded state already came from the popover in most cases, but the details relation was taken from the rich hint first, so e.g. <button popovertarget=closed interestfor=open-rich-hint> was collapsed but had details pointing at the rich hint. Also, a popover invoker inside its own popover (which exposes no expanded state or details from the popover) would pick up the rich hint's state instead.

2. Links no longer expose an expanded/collapsed state from a rich hint, since activating a link navigates rather than expanding anything. Links still get the details relation to an open rich hint, and still expose an authored aria-expanded, which was previously overridden by the rich hint state.
