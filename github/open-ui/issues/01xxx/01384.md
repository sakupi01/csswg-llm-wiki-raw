It's been [suggested](https://github.com/openui/open-ui/issues/1372#issuecomment-3899987045) that some use cases for [overscroll actions](https://open-ui.org/components/overscroll-actions.explainer/) might require the overscroll area to become modal when opened. It was also raised that if there's a `::backdrop` pseudo element for overscroll areas, and it is darkened/blurred to obscure the background, then that should be a modal interaction pattern.

I'm a bit unclear on the concrete example use cases for this, so I'm hoping the community can help me enumerate these. It'd help (me at least) to be able to think about the interaction pattern in some specific cases.

Assuming there are use cases that require modal, the second question is how should that be achieved in the HTML. One [suggestion](https://github.com/openui/open-ui/issues/1372#issuecomment-3929508361) is to just use a `<dialog>` element as the target overscroll element, which would then automatically become open in modal mode. That might be a little weird, given it would also be in the top layer, but perhaps we add a new special dialog "open in overscroll mode" mode, or something? E.g.

```
<div overscrollcontainer>
    <dialog id="modal">Modal contents</dialog>
    ...Regular content...
</div>

<button commandfor="modal" command="toggle-overscroll">
  Toggle Modal Dialog Menu
</button>
```

Are there other ideas?

<!-- comment id=4006976345 author=flackr created=2026-03-05T18:46:17Z url=https://github.com/openui/open-ui/issues/1384#issuecomment-4006976345 -->
## @flackr — 2026-03-05

A classic example is that mobile side menus often cover or otherwise prevent access to the main document while open. Another primary use case for this of showing a bottom sheet also prevents access to the underlying content while open. See mocked demos https://flackr.github.io/web-demos/css-scroll-snap/menu2/index.html and https://flackr.github.io/web-demos/css-scroll-snap/bottom-sheet/index.html

<!-- comment id=4006990914 author=flackr created=2026-03-05T18:49:15Z url=https://github.com/openui/open-ui/issues/1384#issuecomment-4006990914 -->
## @flackr — 2026-03-05

Relatedly, if you had multiple areas, only one of which was an overscroll container, there's no reason having one open should block access to the other. I think that dialogs also need this kind of component modality concept.

## @css-meeting-bot — 2026-03-05

The Open UI Community Group just discussed `Should it be possible to open overscroll areas "modally", and if so, how?`, and agreed to the following:

* `RESOLVED: the behavior and role of the overscroll area should be determined by the target element. E.g. a <menubar> or a <dialog>. Most of the special behaviors (e.g. focus) should come from the element chosen. Don't limit which elements are allowed in terms of behavior, but perhaps limit in the content model.`
