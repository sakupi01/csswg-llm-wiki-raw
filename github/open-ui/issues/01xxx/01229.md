## Proposal

the ability to set directionality for the arrow key/tab navigation of select options:

Syntax is very strawman, but I wold like the ability to decide if the direction should be block, inline, or both.

```css
::picker(select) {
  tab-direction: block || inline || block inline || both; /* alternatively both = block inline */
  tab-start: start || end;
}
```

### "tab-direction"

- `tab-direction: block` = also the default (current behavior), arrow keys up and down move through options in one direction
- `tab-direction: inline` = arrow keys left and right move through options in one direction
- `tab-direction: block inline` = left arrow behavior, and bottom arrow = right arrow behavior move through options in one direction
- `tab-direction: both` =  arrow keys up/left/down/right move in multiple directions (I'm not sure how this would be implemented to be honest, but it would be neat!)

** horizontal and vertical may be better than inline and block*

### "tab-start"

- `tab-start: start` = navigation starts at first item (current default)
- `tab-start: end` = navigation starts at last item, and moves to first

In this example, I can visually move through the list, snapping the items into place using the left and right arrow keys. I can tab through the items using the up and down arrows, but visually the items don't snap into place.

## @dizhang168 — 2025-06-05

As currently designed, CSS `reading-flow` is meant for tab navigation. Since navigating between options in select uses arrow keys, the feature is not helpful (yet). We are looking at improving it to handle arrow key navigations (https://github.com/openui/open-ui/issues/1201). There is a lot of complexity though since arrow keys is used everywhere in form controls.

<!-- comment id=2957192879 author=josepharhar created=2025-06-09T22:36:10Z url=https://github.com/openui/open-ui/issues/1229#issuecomment-2957192879 -->
## @josepharhar — 2025-06-09

Thanks for opening this!

We could just make arrow right act the same as arrow down and make arrow left act the same as arrow up by default in order to achieve the `tab-direction: block inline` behavior (i think). Arrow right and left don't currently do anything.

Making the arrow keys follow the grid layout in the airbnb demo sounds more challenging and interesting. I wonder if arrow up and down should be able to iterate every option, which we could probably still do if we wanted in this case. I also wonder if we could make arrow keys follow the grid layout without the need for an opt in.

<!-- comment id=3184885234 author=smhigley created=2025-08-13T17:49:40Z url=https://github.com/openui/open-ui/issues/1229#issuecomment-3184885234 -->
## @smhigley — 2025-08-13

Looks like this could map to `aria-orientation` reasonably cleanly as Luke mentioned.

The one caveat is that having grid-like up/down/left/right navigation also needs grid semantics and a more rigid structure (i.e. it doesn't reflow and change the number of columns) to work well with screen readers.

<!-- comment id=3189187976 author=josepharhar created=2025-08-14T16:57:36Z url=https://github.com/openui/open-ui/issues/1229#issuecomment-3189187976 -->
## @josepharhar — 2025-08-14

The HTML spec currently says that for customizable select, there is UA defined behavior with keys which may focus another option: https://html.spec.whatwg.org/multipage/form-elements.html#focus-another-option

This means that we are free to implement whatever we want for the up/down/left/right arrows. I'm still not sure exacty how this should work, but I don't think that we should add a CSS or HTML feature specifically to control the arrow keys. Something more generic like direction or automatically detecting a grid layout seems more ideal to me.
