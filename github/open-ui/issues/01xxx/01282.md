The switch explainer has a long standing open question regarding markup. Initially, the explainer was proposing adding a new `<switch>` element but an [switch attribute proposal](https://github.com/whatwg/html/pull/9546) using `<input type="checkbox" switch>` was submitted to WHATWG in July 2023 shortly before the explainer was published.

Should the explainer be rewritten to use the `switch` attribute?

See also: 
- [Interop issue for web platform tests](https://github.com/web-platform-tests/interop/issues/1063)
- [Comparison between the two approaches](https://open-ui.org/components/switch.explainer/#comparison-switch-attribute-vs-switch-element)

## @o-t-w — 2025-10-04

I think it should be rewritten or moved to non-active. The PR to add it to the HTML spec has not been merged after several years and the [Mozilla standards position](https://github.com/mozilla/standards-positions/issues/990) is still open... but the stable version of Safari shipped the `switch` attribute in March 2024 and judging from the comments of Apple developers I doubt they'll be keen on also implementing an alternative. The [CSS Form Control Styling Level 1 spec](https://www.w3.org/TR/css-forms-1/#slider-pseudos) has several mentions of `<input type=checkbox switch>`. I have [tried out](https://codepen.io/cssgrid/pen/azdBrJV) the `::track` and `::thumb` in Safari Technology Preview (currently behind a feature flag). Once they can be used together with `appearance: base` I think that will be a good approach. 

In the Open-UI [comparison](https://open-ui.org/components/switch.explainer/#comparison-switch-attribute-vs-switch-element) between the two approaches, one of the points in favour of the `<switch>` element approach is that inline SVG can be used, which can be styled with `currentColor`. While it is not implemented anywhere yet, at some point we may get [CSS link parameters](https://drafts.csswg.org/css-link-params/) to change the color of non-inline SVG.

From looking at [great many examples](https://component.gallery/components/toggle/) in the wild, the vast majority of custom switch components are fairly simple/minimal, so the verbose markup approach felt like overkill imo.

## @lukewarlow — 2025-10-06

I'm in two minds about this because the switch attribute isn't standardised, and I don't think the switch attribute was necessarily the best design.

The form participation behaviour is unfortunate (check boxes behave equally weird). The fallback to a checkbox is semantically questionable also, due to the immediate action aspect.

I'd be curious on how well used it is (aka how hard to change it is). Though either way it has shipped in Safari, and it's not fatally flawed. The pragmatic approach is to probably accept that design.

We can update css-forms to use any selector for a switch, just happened to have used the one shipped in Safari for now.

## @josepharhar — 2026-02-17

> In the Open-UI [comparison](https://open-ui.org/components/switch.explainer/#comparison-switch-attribute-vs-switch-element) between the two approaches, one of the points in favour of the `<switch>` element approach is that inline SVG can be used, which can be styled with `currentColor`. 

This is also an issue with `<input type=checkbox>`, and sites work around it by rendering a separate element on top of the checkbox in a way where the input element receives the hit testing. I imagine that doing the same thing for a switch would be much harder since the thumb moves around.

> While it is not implemented anywhere yet, at some point we may get [CSS link parameters](https://drafts.csswg.org/css-link-params/) to change the color of non-inline SVG.

This sounds like it could be a great solution for checkboxes and switches!
