https://open-ui.org/components/combobox.explainer/#the-search-attribute says:

> Typing “a” will display “Apple”, “Apricot”, and “Banana”. definition [here](https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype.includes).

However, `"Apple".includes("a")` evaluates to `false`.

If the intent of to have more complicated processing, such as case folding, the more complicated processing should be explicit.

If case folding is to be performed, the case folding should probably be aware of Turkish and Azerbaijani being special, and a definition of where the language information is taken from would be necessary.

It seems that JavaScript doesn't have a public `toLocaleFoldCase` operation, but browsers have it available internally.

## @hsivonen — 2026-01-28

> Perhaps another relevant question here is whether typing "av" should include Ávila. 

The Web does not have a language-aware way (in the sense that ö should not match o diacritic-insensitively in Estonian, Finnish, Icelandic, Swedish, Turkish, etc.) of doing diacritic-insensitive _substring_ matching. (`Intl.Collator` provides full-string matching, but I think providing it is a misfeature.) As a collator implementor, I very much don't want the Web platform to require collators to be able to perform substring search over the 64-bit collation units and be able to correlate the result back to the input characters.

It would make sense to define a language-aware character to character mapping that removes diacritics, though. I have a perma-TODO to write this up for the Unicode Consortium. Perhaps I should actually get around to writing it.

<!-- comment id=3813493264 author=hsivonen created=2026-01-28T19:42:20Z url=https://github.com/openui/open-ui/issues/1366#issuecomment-3813493264 -->
## @hsivonen — 2026-01-28

On second thought, collator-based "starts with" and "includes" would be very easy to implement. They would just be very inefficient compared to a character-level folding away diacritics like fold case does case-insensitivity on the character level.

Also, implementing a collator-based "starts with" API is an invitation to the API users to build a very inefficient "indexOf" on top, which would then be a slipperly slope towards demand for optimizing that to a slightly less inefficient collator-based "indexOf" API, which is the part that I particularly want to avoid.
