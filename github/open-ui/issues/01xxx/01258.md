Here's a new idea (thanks @chrishtr!) to meet the same use case as `::interest-hint` (see [explainer](https://open-ui.org/components/interest-invokers.explainer/#option-35---add-an-opt-in-info-button-pseudo-element) and [CSSWG issue](https://github.com/w3c/csswg-drafts/issues/12437)):

```html
<a href=# interestfor=popover id=link>Some link with a hovercard</a>
<button id=interest-hint commandfor=link command="toggle-interest"> (i) </button>
<div popover id=popover>The hovercard</div>
```

Essentially, add a `command` called `"toggle-interest"` which (when targeted at an element with `interestfor`) shows interest in that target element when the button is activated (and loses interest if the popover is already showing). This achieves roughly the same developer experience and capabilities as the `::interest-hint` [proposal](https://open-ui.org/components/interest-invokers.explainer/#option-35---add-an-opt-in-info-button-pseudo-element), and side-steps a lot of [questions](https://github.com/w3c/csswg-drafts/issues/12437#issue-3197162064) such as accessibility (buttons inside buttons), focusability, arbitrary content, etc.

Because one of the use cases is to only show this extra button on touchscreen devices, here's how that would be done, in a very similar way to `::interest-hint`:

```css
#interest-hint {
  display:none;
}
@media (any-pointer: coarse) {
  /* On touch devices, show the extra button */
  #interest-hint {
    display:inline-block;
  }
}
```

One question is about the name: I chose "toggle-interest" here because I think tapping the button twice should lose interest. We could call it "show-interest" but it might be a little less clear that this will actually toggle. Or I guess you could *only* show interest, and use other things like tapping elsewhere on the page to lose interest. But it feels nice to have the button toggle, right?

Thoughts? Things you can't do with this version?

## @mfreed7 — 2025-08-07

As I'm implementing this, I think I want to go back to `command="show-interest"`. For the core popover use case, clicking on the command invoker button a second time (after the first click shows interest and shows the popover) will light dismiss the popover, which will automatically lose interest in the interest invoker. And *then* the command invoker logic will kick in and run, finding an interest invoker without interest, and will show interest again. So practically, there's no need for `toggle` behavior, since popovers already nicely handle that. 

Plus, `command="show-interest"` is a lot easier to read and understand, I think.

## @brechtDR — 2025-08-07

The reason why I would like a pseudo-element is that it could be enforced to be visible by default. The reason I mention this because I still have some concerns about touch device accessibility as described in [the explainer](https://open-ui.org/components/interest-invokers.explainer/#touchscreen)

With the pseudo-element, we could (potentially) enforce it to be visible by default and thus be the main trigger for touch devices, which is one of those solutions in the explainer. 

Then, if an author were to get rid of it (e.g, display: none), it would be an author choice (there might also be more incentive to just re-style the thing), but at least by default, the content is accessible on all devices.

Even though this does not exclude this idea, I'd rather see this as an extra possibility to replace the pseudo-element if the author wants to, instead of a default replacement of the pseudo-element idea if the latter would be the "touch-device alternative".

So +1 on the idea as a capability/enhancement here, but not as a base touch-device solution.

## @mfreed7 — 2025-08-07

Alright, we had a good long discussion of this proposal. Here's what I heard:

- We really want a non-focusable, non-actual-button for this `(i)` icon thing. The actual interest invoker is already accessible (via AT, keyboard, mouse) and this is primarily (perhaps only?) useful for touchscreen users.
- So the ideal situation is that the `(i)` button isn't really a button, and instead it acts like `<span onclick=showInterest()>`. It just looks like a button to sighted users.
- It shouldn't be in the a11y tree. It shouldn't be focusable (on its own).
- We shouldn't/can't include the media query in the UA stylesheet, because that confuses developers. So this (still) needs to be a developer opt-in.
- There was talk of a new HTML element for this purpose, something like `<interesthintbutton>`, which would presumably be (only?) placed as a child of the element with `interestfor`. So something like this I guess: `<button interestfor=foo>Button text goes here <interesthintbutton><svg>some logo</svg></interesthintbutton></button>`. And then that would only get rendered (I guess?) on touchscreens? And it wouldn't really be a button, but would just be a pointer-clickable thing that looks like a button. I.e. not keyboard focusable and not in the a11y tree. I'm wary of the complexity of this solution for what seems like a smaller problem. And I'm guessing a huge pushback will be: what happens if you put that outside an interest invoker, on its own?

My tentative conclusion is that perhaps the `::interest-hint` [pseudo element](https://github.com/w3c/csswg-drafts/issues/12437) really might have been the better solution. This discussion cleared up a bunch of the questions, e.g. how to make it focusable. One downside that was discussed today is that it isn't fully stylable, since it can't contain arbitrary content. But perhaps it covers the 80% use case, and we can invent something to cover the other 20% later, once we learn what's in the 20%?

Thoughts?

For the pseudo element, these are the (still) open questions:
- it needs a good name (always). Current ideas are `::interest-hint` and `::interest-button`.
- is there a more general feature here, that works for things other than interest invokers? I'm not sure what that would be, but it was brought up in the CSSWG discussion.
- Where does it live in the layout tree, relative to e.g. ::after and others? Feels like it belongs just **before** the `::after` pseudo element.
