This is a rough proposal for a content model for the menubar/menulist proposal ([explainer](https://open-ui.org/components/menu.explainer/)).

In response to a content model violation, we are cribbing from https://github.com/openui/open-ui/issues/1099 and [customizable select behavior](https://gist.github.com/josepharhar/9c359f5b8b6fa4c31065bd1fbeab40dd#breaking-the-content-model):
* We'll still render the violating elements
* We'll emit devtools console messages warning the author
* If the content model is violated inside a `menubar`, we will give the `menubar` the `???` aria role
* If the content model is violated inside a `menulist`, we will give the `menulist` the `dialog` aria role

## Content Model

### `<menubar>`

`<menubar>` represents an *in-page* group of `<menuitem>` elements.

- **Allowed Descendants:**  
  - `<menuitem>`  
- **Forbidden:** *Any* other element

### `<menulist>`

`<menulist>` represents a native *popover* containing a list of `<menuitem>` elements.

- **Allowed Descendants:**  
  - `<menuitem>`  
  - `<fieldset>` (used for grouping checkable items)  
  - `<hr>` (used as a separator)  
- **Forbidden:** *Any* other element

### `<menuitem>`

The `<menuitem>` element represents an individual command or submenu trigger.

- **Allowed Descendants**  
  - `<div>`  
  - phrasing content (e.g., text, `<span>`, `<img>`), provided it is not in the exclusion list below.  
- **Exclusion List**  
  - `<datalist>`  
  - `<object>`  
  - [interactive content](https://html.spec.whatwg.org/multipage/dom.html#interactive-content) (e.g., `<a>`, `<button>`, `<input>`, `<textarea>`, `<select>`).  
  - Any element with a `tabindex` attribute specified  
  - Any element that is `contenteditable`  
- **Forbidden:** *Any* other element

## (Some) open questions:
1. What aria role do we use for a `menubar` with prohibited descendants?
2. Should we allow `div`s inside `menubar` and `menulist` to wrap `menuitem`s?

We've started to write this content model at https://whatpr.org/html/12011/interactive-elements.html#the-menubar-element

## @davidsgrogan — 2026-09-09

My minutes from the ARIA deep dive on 2026-05-14, the part where we talked about the content model:

dgrogan: When an author violates the content model, like put a link or a video or some weird thing in a menu, we are going to do a few things
…one is we're going to red-squiggly underline the element in devtools to say you violated the content model here
…second, cribbing from Joey's customizable select, we are going to change the role from menu to dialog and hope that screen readers handle that okay
… third, switch keyboard behavior to tabbing through each child
… But what do we need to make sure about when we switch the role to dialog? What do screen reader users expect that we need to make sure still works in a dialog role, but with this markup?
Matt: make sure that the dialog contains tab and that escape works to close the dialog
… possibly add a visual affordance so sighted users know that escape closes it?
… screen reader users often just know when they hear dialog to press escape to close it
Scott: some screen readers don't even announce that you are directly interacting with menu items
…The primary announcement is that you've entered a menu, so that's the only way you know that you are navigating menu items
…So if we switch to a dialog announcement to let SR users know that there's non-menuitems inside this menu, is there anything else that we need to account for in how that information is exposed to people?
…changing the role like we did for customizable select makes sense to signal to someone that there's things beyond just what they might expect in here, as an author repair.
Matt: making a dialog seems sufficient to enable reading cursors to work in menus, at least in JAWS and NVDA.
…: But are we making everything inside the dialog reachable by TAB?
Joey: Yes. For valid menus, in non-dialog mode, TAB closes all the menus and submenus you're in and goes to the next thing after the menubar or the button that invokes this menu
… in dialog-mode, when there's interactive content in the menu, TAB does NOT close the menu, it just focuses the next thing inside the menu
… if TAB should actually move you between menu items is an open question
dbaron: what parts are changing to dialog?
Scott: the container element
dgrogan: Are we changing internal elements' roles?
Scott: menuitems and menuitemcheckboxes could make sense
 … but that would be weird because menuitem radiobuttons focus is different, selection follows focus in normal radio buttons, but not in menu items
Adrian: there's risk with any standard control changing its role because of the interaction pattern that's conveyed vs what the page actually supports
Matt: I was thinking, in this repair experience, the menulist becomes a dialog
… Every item in the menulist becomes an element in the tab order in the dialog
… what the roles of those elements would be is TBD
… It'd be kind of weird if they stayed as menuitems
… selection following focus isn't that big a concern because you're TABBING to them anyway, not arrowing to them
dgrogan: we are making every menu item reachable by TAB, right?
Joey: yes. In customizable select, you can reach options by arrows or everything by TAB
Matt: maybe we should disable arrow keys in dialog mode
… this is confusing to SR users and if arrow keys still work, they might not know that they are missing stuff in the menus
