While working on https://github.com/whatwg/html/pull/11006 a question has come up for me. When a button (or `a` or `area`) has full interest and target is showing, it's possible for a number of things to break or change the link between the invoker and the target element:

- `interestfor` attribute changes so that either there is no target, or a new target
- Similarly, the element with `interestfor` is moved or removed
- The `id` attribute of the target changes so that either there is no target or another element (with the old ID but later in tree order) is the target
- Similarly, the target is moved or removed

This is all similar to removing the `open` attribute from an open `<dialog>` element or removing a current fullscreen element, in that the change is immediate and one simply has to handle it synchronously as well as possible.

Testing https://codepen.io/foolip/pen/VYLJoje in Chrome Canary, this is the current behavior:

- Removing the `interestfor` attribute makes both `:has-interest` and `:target-of-interest` stop matching, but leaves the popover open.
- Removing the `id` attribute leaves `:has-interest` still matching, `:target-of-interest` not matching, and the popover open.

I think the behavior should be consistent and make none of the selectors match, but my main question is about the popover. Should it be left open, or should it be closed?

cc @mfreed7

## @mfreed7 — 2025-07-07

> I think the behavior should be consistent and make none of the selectors match, but my main question is about the popover. Should it be left open, or should it be closed?

Thanks for raising this issue. My view is that in all of these cases, the target popover (if it's a popover) should be left alone and not force-closed. The issue is that closing a popover has side-effects, including synchronous events getting fired. And in some of the situations you have listed (e.g. removing elements from the DOM), you can't do that. My mental model is that once you've done any of these things, you've broken the link between the invoker and the popover, and the popover can be left.

Having said that, the pseudo classes should all immediately stop matching, in my opinion. Gaps in that behavior are bugs in Chromium. For example, the `id` attribute is definitely not tracked properly right now - thanks for raising it.

One situation you didn't list: what happens if the interest invoker currently has interest, and is also currently focused/hovered, and then you break the link? In that case, I'd expect the "interest lost" timer to start on the target, because you're no longer maintaining interest via focus/hover on the invoker. I bet that behavior is currently broken also in Chromium.

> One situation you didn't list: what happens if the interest invoker currently has interest, and is also currently focused/hovered, and then you break the link? In that case, I'd expect the "interest lost" timer to start on the target, because you're no longer maintaining interest via focus/hover on the invoker. In https://github.com/whatwg/html/pull/11006 this would call "reset interest state" so that any pseudos stop matching and leave any popover open. The only thing that can start the interest lost timer is a user interaction. But we could do it differently if you think that doesn't make sense.

## @foolip — 2025-07-09

> The only thing that can start the interest lost timer is a user interaction

The nuance here is whether the trigger is the user interaction that might trigger a change in focus/hover state, or if the change in focus/hover state itself is the trigger. I wrote it so that it would be the user interaction, not the resulting events or other web-observable state changes.
