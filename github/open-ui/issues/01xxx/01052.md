We've discussed this before but I don't think there's a dedicated issue to talk about what could constitute interest on a touch device (e.g. phone, tablet, certain laptops).

We should also discuss what potential issues there are with this and potential work arounds.

## @lukewarlow — 2024-05-03

So far I think we've been talking about a long press as a touch input interest mechanism.

Pros:
- This isn't a complete new behaviour, touch devices already use long press for some secondary actions (e.g. text selection, copy, paste, and showing tooltips in the case of Android)

Potential issues to overcome:
- Potentially overloaded because it's already used for other things 
- Might interfere with text selection 
- Might not be possible to trigger for users with certain conditions
- Might need to handle focus differently on touch so it doesn't count as a trigger
- Hard to polyfil due to lack of "long press" event.

## @mfreed7 — 2024-05-09

It might be controversial to say this, but I think it might be necessary to leave some parts of the concept of "interest" to user agents to define. For example, in a Vision Pro like platform, with eye-tracking and a distinctly non-keyboard, non-mouse user interface, it likely needs to be up to the platform to decide when a user is "interested" in an element. I don't think we should (or need to) write down exactly how this works. In contrast, keyboard users and mouse users have fairly standard ways to indicate "interest", namely focusing or hovering the element. These, I feel, should be standardized so they behave in the same way across browsers and platforms. Somewhere in the middle is touch. Perhaps touch is standardized enough that we can specify it, but perhaps not? What's important, to me at least, is that the standard says, normatively, that the user **must** have **a way** to "indicate interest" in an element, no matter their input modality.

Stepping back off the soap-box, per your questions about touch:

> Potentially overloaded because it's already used for other things

In chromium at least, I could see just adding an item to the existing context menu.

> Might interfere with text selection

I agree this might be an issue, but I would see it as an implementation issue maybe? It must be possible for the user to do both, **somehow**.

> Might not be possible to trigger for users with certain conditions

I might need more context on this one. But again, the UA should provide an accessible way to indicate interest.

> Might need to handle focus differently on touch so it doesn't count as a trigger

Agree completely.

> Hard to polyfill due to lack of "long press" event.

Agree. But it's not a requirement that new features be polyfillable. Definitely nice to have though.

## @mfreed7 — 2024-08-26

Here's a new idea for touch, from an internal discussion (credit to @b1tr0t):

On touch platforms (or potentially any platform where the UA determines that there's no mouse/keyboard?) the UA adds a pseudo-element button (such as ℹ️) next to the `interesttarget` source element. That button can then be invoked in the normal way to indicate interest in the source element. And the pseudo element should be available for custom styling via CSS. Perhaps the button can be a `popover=manual` anchor-positioned to the source element? Just to avoid layout shift on touch platforms.

This idea gets around the problems of using long-touch, and is actually a cow-path paved by several design systems.

Agenda+ to discuss.

## @mfreed7 — 2024-08-29

Great discussion just now, thanks all. So I'm coming down to a more concrete proposal:

```html
<button interesttarget=foo>Button</button>
<span interesttarget=bar>some text</span>
```

The idea would be that both of those elements (the button and span) would generate pseudo elements that could be targeted like:

```css
[interesttarget]::interest-target-icon {
  content: "?";
  background-color: linen;
  border: 0;
}
```

which would be presented as:

![Screenshot 2024-08-29 at 11 47 38 AM](https://github.com/user-attachments/assets/8b98a43b-c702-45e0-b2e6-ae70194e5ded)

Clicking those `?` buttons would trigger the interesttarget target element. The buttons could be made fully accessible, they would be part of the sequential focus navigation, etc.

To address the concerns raised in the meeting:
1. The `::interest-target-icon` pseudo element would *always* be generated for any element that has an `interesttarget` attribute. This would not be dependent on pointer event precision, etc.
2. The pseudo element could be used to disable or control the visibility of the icons, as well as style them to fit the page.
3. The pseudo element would come after the element with `interesttarget`, but would be styled (by default) as `position:static` so that no content would be obscured. However, developers could change that to `position:fixed` and anchor-position them, if desired.
4. Hovering (with a mouse) the originating element (e.g. the button and span in the example) would also trigger interest.
5. Focusing (with a keyboard) the originating element would **not** trigger interest, since the preferred way to do that would be tabbing to the `?` icon and activating it. This also removes the need to make `<span interesttarget>` keyboard focusable.
6. We should (strongly?) recommend that UA's have a user setting that allows three things: **1)** the default behavior, **2)** **always** show the `::interest-target-icon` (even when developers have hidden it), and **3)**  **never** show those.

## @nmn — 2024-10-04

Hi! I'm very interested in this topic and I was travelling when a lot of this was discussed so, sorry about jumping in late.


## 1. Responding to a few comments

> Ah, I thought long-press wasn't a thing on iOS.

It became thing just before they killed "force touch".

> If folks are convinced that the lack of control over long-press is the blocker here, it's probably better to solve that before creating a higher level feature that solves some of the long-press issues in a particular way. [taps the sign]

The big blocker here isn't *just* the ability to detect a long press, (shouldn't `onContextMenu` be enough for this?), but the ability to render custom UI *alongside* the context menu, so it's not quite an easy thing to add.

Having a super reliable way to detect long press alone wouldn't solve anything.

## 2. My stake in this

- I work on the Components (design system) team at Meta and my team and I have been trying to make Hovercards fully accessible for years now. 
- Although Hovercards are *optional* for our design, removing them causes noticeable regressions to our core metrics.
- Almost *all* hovercards are bound to links. Removing the ability to navigate by tapping/clicking just once on the link is *even worse* for our metrics that removing Hovercards.

## 3. Establishing my views

1. I strongly favour showing the "hovercard" for mouse, keyboard and touch with Hover, Focus and long-press respectively.
   - The mouse interaction is well understood, I'll elaborate on what I think would be good approaches for keyboard and touch below.
2. On iOS I want the ability to render custom UI instead of the link preview "callout" that iOS renders. Hovercards usually server the same purpose anyway, with the addition of interactive elements. (Hovercards are "mini" views into the destination of the link)
3. On any platform that has no mechanism or space to render UI alongside the context menu, an extra context menu option to "show preview" would be OK.
4. Not having hovercards on touchscreens would be preferable to adding buttons next to every trigger.

## 4. A prototype of what I'm currently experimenting with:

I have been trying to use what's available today to come up with a Hovercard that is accessible and work with mouse and keyboard for now.

https://codepen.io/naman34/pen/rNEwVYY

It doesn't have the correct `role`s or `aria-` attributes, so it's (probably) still broken for screenreader users, but it *should* work for both mouse and keyboard users.

Here's the overall idea I used:

1. The main idea is to show a somewhat inert "preview" of the Hovercard on *both* hover and focus. This preview is to communicate to the user that there is something there.
2. From there, a mouse user can mouse over the hovercard preview which "activates" the hovercard. 
3. For keyboard users, when the link is focused, simply pressing the "down" arrow "activates" the hovercard.
4. When the hovercard "activates", the focus jumps from the link to the first accessible element within the Hovercard. Since I couldn't find an accessible pattern for popovers with the type of content we need, I made the Hovercard behave like a modal dialog when "activated".
5. Mousing *out* from the hovercard *or* pressing escape *or* a click on the backdrop dismisses the Hovercard and the focus returns to the link.

#### "down" arrow discoverability

In order to make the "down" arrow discoverable, I've tried to use a "role" around the trigger link that is supposed to have a "focusgroup". In my example, I've chosen `role="menu"`. I've added *two* links within this "menu" so that a screenreader can announce that the "trigger" link is "one of two" items within. The second link is a visually hidden dummy link.

This should indicate to the user that they can use arrow keys to cycle between the items.

#### Functionality & a11y

I think the functionality of this prototype is very close to the idea we would want. I don't know if it is properly accessible in its current state, but I think it's pretty close considering the lack of relevant `role`s for such a use-case.

## 5. So how should this work on a touchscreen

I agree with @keithamus on this. The most obvious way to trigger a Hovercard on a touchscreen is with a longpress. But we *don't* want to lose the context menu either.

On iOS this means showing the hovercard in place of the "preview callout". Just like the native apps do. In order to make this work, I propose that the user agent is allowed to render the "Hovercard"/"Interest Target" within any "box" in the top-layer. It should be possible to query the size of this "box" with `@container` queries.

<img width="664" alt="Screenshot 2024-10-04 at 2 22 16 am" src="https://github.com/user-attachments/assets/83ef198f-c647-4850-bedc-fbd135f4d7cd">

On iOS, this can be the largest possible box that can be rendered for the Hovercard. On Desktop, it can the Viewport itself. 

On Android, there is a small preview of the link above the context menu as well. This preview could be expanded to fill the available space of a phone screen and the extra space can be made available to the "interest target" content.

Each user agent should be allow to respect Anchor positioning on Hovercard or not. E.g., on Desktop and tablets, anchor positioning should likely be respected. But on iOS, the pattern is to use a "grow animation" show the callout coming *from* the target and that is OK for that user agent.

This "box" concept gives user agents to some freedom too. For example, on visionOS, context menus are rendered in 3D space *above* the UI with a gap in the Z-axis. The Hovercards in visionOS could similarly be rendered in a box that is "lifted" off the UI in the z-axis.


## 6. Miscellaneous Conclusions

- Hovercards should be declared statically in the HTML, just like popovers. This should enable user agents to render and compute their sizes pre-emptively and use it to position context menu and frame around the content.
- It would be *OK* to make it impossible to *show* or *hide* the Hovercard imperatively. Relying on the User Agent to show it when applicable would provide certain guarantees that might be desirable for User Agents. (I think `datalist` works like this today)
  - When showing Hovercard content imperitively, it can just be treated like a "popover" with all of the control that brings.
- Developers should be able to make the Hovercard content itself responsive based on the size of the "BOX" within which it is rendered.

Ok, so @eriinly and @yhux worked on some UX concepts for `interesttarget` on touch screen interfaces. See the large image below, which contains several interaction pattern mockups. All assume that `interesttarget` is placed on a link (`<a href=foo interesttarget=bar>`), since that's the most interesting example. Later we can consider other things like buttons, which should be similar.

These mockups contain three activation modes:

1. **Single-tap activation with action overlay**. One tap on the link opens the hovercard, rather than navigating to the link directly. The UA provides an additional button/link as an overlay over the top of the content area. That link lets the user actually navigate to the link, as a second tap. In this case, the context menu is opened as it is today - via long-press on the original link.

2. **Single-tap activation with integrated inert preview**. Again, one tap on the link opens the hovercard, but in this case, the hovercard is rendered as an *inert* preview provided by the browser. Because in this case, the browser has control over the placement and size of the hovercard, it can provide non-overlapping buttons/links to allow the user to navigate to the link. I.e. this gets around the problem that the additional button/link in case <span>#</span>1 might overlap the content. It adds the problem that the hovercard must be inert: there can be no nested hovercards or activatable buttons.

3. **Long-press activation**. Long-press opens the existing context menu, augmented with an inert preview of the hovercard alongside. Again here, the hovercard is not interactive or nestable. But in this case, no additional taps are required to either navigate the link directly (single-tap) or access the context menu (long-press).

1. Follow the mockup provided in https://github.com/openui/open-ui/issues/1052#issuecomment-2467616677, which will be shown when the user long-presses the element with `interesttarget`.
2. There are two regions in that mockup, the top "hovercard" part, and the lower "UA provided menu" part.
    a. The site will continue to be rendered, importantly *unblurred*, underneath the UA provided menu.
    b. The UA will place the UA-provided menu somewhere on-screen, attempting to leave as much of the physical screen area un-obscured. For example, toward the bottom of the screen, leaving the top available.
    c. These will allow a hovercard to be positioned safely within the still-visible space left on screen, so that both the hovercard and UA menu can co-exist.
3. Taps on the menu will perform the selected menu item. Taps outside the menu will "fall through" to the rendered page, and will also close the UA menu. I.e. interactive elements rendered on the hovercard can still be tapped, which will simultaneously activate the tapped element and close the UA-provided menu (without performing any menu actions).

With the above system, the mockup should be able to look just like https://github.com/openui/open-ui/issues/1052#issuecomment-2467616677, but that will require more work on the part of the developer, to be sure to position the hovercard appropriately, and likely blur the rest of the screen to avoid visual clutter?  - Are the developer ergonomics easy enough to make this work cleanly on touch and also on desktop? I.e. what's the "hook" to determine if the hovercard should render using `context-menu-inset-top`, etc?
