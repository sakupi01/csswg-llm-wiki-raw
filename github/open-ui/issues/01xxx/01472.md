Rich web apps are built from major regions — a ribbon, a navigation pane, a document canvas, a chat list, a composer, an assistant sidebar — much like native apps. Users want to jump between these regions from the keyboard without Tab-ing through every control in between. This is one of the most common accessibility and productivity requests for web apps, yet the web has no primitive for it.

Today the paradigm is missing:

* Sequential navigation (Tab) spans the whole page but visits every control — exactly what users want to skip here.
* Directional navigation (focusgroup) moves within one widget.
* Landmark navigation — moving between regions — has no declarative equivalent.

Native platforms do this routinely (e.g. F6 / Shift+F6 on Windows), and browsers already use it for their own chrome, but it stops at the edge of web content. So every app that wants it hand-rolls a solution: picking a key that may clash with the browser or nested apps, maintaining an ordered region list and a "current region" pointer, deciding where focus lands in each region, and re-implementing all of it across iframes. The result is inconsistent or absent behavior across sites, and no shared model between browser UI and page content.

Because this problem is common across web apps, it seems worth solving at the platform level so behavior, default accessibility, and interoperability come from the browser rather than per-site script.

I've drafted an explainer proposing a declarative HTML primitive, inspired by [ARIA landmark role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/landmark_role) and [focusgroup](https://open-ui.org/components/scoped-focusgroup.explainer/)  (placeholder name focuslandmark) for this: https://github.com/MicrosoftEdge/MSEdgeExplainers/blob/main/Accessibility/FocusLandmark/explainer.md.

This is an issue with an obvious fix on Windows (tying it to the OS-wide feature landmark navigation key F6), and it looks like some people at Apple are also looking into solving this problem: https://bsky.app/profile/marinaaisa.com/post/3moiffbnotc23.

I'd like your thoughts. Is this a problem others agree on? What ideas do you have to solve it?

## @benbeaudry — 2026-07-14

@tombrunet If I understand your point correctly, you're saying that's an extra key and it's even more things to remember for the user. I agree with you, and would like to clarify three things that are worth pointing out, imo:

1. As both a macOS and Windows user, I got used to this macOS-specific behavior of having to press the Fn key to reach any function key. It makes sense; it's OS-wide, and I'm used to it.
2. This proposal doesn't suggest making F6 (or any function key) the standardized key; instead, it leaves it up to the UA and the platform to define their own key. On Windows, because this is a well-defined feature already implemented across apps (but the web platform), I suggest reusing the same shortcut to the web platform as it feels like a natural extension of the same OS-level feature. As far as I know, macOS doesn't have this keyboard-first landmark navigation feature natively across apps (I believe they support it with VoiceOver, though), but if they were to implement it
   1. the web platform would be have everything ready for it to "just work" with this proposal (with the key of their choosing), and
   2. browsers like Microsoft Edge, Chrome, and Firefox could implement a UA-only feature with the key binding of choosing without being blocked by the OS. The key would be left to the UA to determine, and expose it to the user
   3. Personally would love to see macOS adopt such a highly requested feature at the OS-level, but this is out-of-scope to this web platform specific problem we're trying to solve.
3. To play devil's advocate for the Fn+F6/Fn+Shift+F6 on macOS (again, not recommending using this specific shortcut for this proposed feature), it would still be an improvement if all websites had this feature exposed with this specific key combo instead of having many websites not support the feature at all or, worse, support it with different shortcuts for every domain (like is the case today).

>There are a bunch of shortcuts for moving directly to different parts of the browser, so perhaps it's not an issue. I'd be curious what folks (maybe especially screen reader users) who currently rely on F6 navigation a lot would think.

I spoke to 4 different screen reader users at Microsoft who use F6 already in the browser and in other apps. The feedback I got was positive and in favor of this proposal. They all independently mentioned that it would change their habit of using F6 in certain cases, that'd they have to go through a bit of an adjustment if this ships, but that they wouldn't mind it because it would be easy to adapt and the benefits of having one shortcut across all websites, and have it be the same one as the OS one and the browser one, would make it worth it.

That being said, the 4 persons I interviewed are Microsoft employees and all identified as power users. I looked into it a bit more and later this year we could be able to run a real user study with a larger, less-biased groups of screen reader users. I'll report back on those findings as well.

Next steps are to bring this up to the ARIA WG to get their thoughts as well, uploading the explainer to OpenUI, and starting discussions in the WHATWG.
