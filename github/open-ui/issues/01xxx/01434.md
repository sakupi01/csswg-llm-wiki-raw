For [example](https://codepen.io/sb3nder/pen/WbGOpgJ):
```html
<button>fries</button>
<div focusgroup="tablist">
	<button>cake</button>
	<button tabindex="-1">ice cream</button>
	<button focusgroupstart>bread</button>
</div>
<button>rice</button>
```
For normal FG items, if you focus "cake", then press Tab, focus goes to "rice".

For `tabindex=-1` elements, if you focus "ice cream", then press Tab, focus goes to "bread",
and if you focus "ice cream", then press Shift+Tab, focus goes to "fries".

I understand why it behaves like this from reading the HTML PR, as it says that `tabindex="-1"` elements are not *"focus group items"* and if I follow the algorithm, yada yada... 

What I don't know is ***why*** they behave like this, and consequently, then I guess why they aren't "focus group items."
Do you have any examples? Or do you know of an ARIA APG where this is clear?

~~(For context: I'm asking because `tabindex="-1"` is the only way to work around segments; I wouldn't have asked otherwise.)~~

## @sb3nder — 2026-04-17

One strange thing is that `tabindex="-1"` elements aren’t "focusgroup items," yet to disable directional navigation, you use `focusgroup="none"`.
`<button tabindex="-1" focusgroup="none">cake</button>`

EDIT: Strange in terms of naming.

## @janewman — 2026-04-24

Sorry for my late reply, this [chromium behavior](https://chromium-review.googlesource.com/c/chromium/src/+/7486357) came out of the other issue you raised: https://github.com/openui/open-ui/issues/1358 and subsequent discussions.

Focusgroup doesn't consider elements with a negative tabindex as participating, and this keeps the internal logic of "only elements with a positive tabindex are keyboard focusable" paradigm, unless the element already has focus (via mouse or programatic). When focused, we temporarily treat the element as if it is a focusgroup, allowing directional input to move focus to its neighbors within the focusgroup and sequantial navigation (tab/shift+tab) to move focus following focusgroup item rules.

That all said, one part of your example seems like a bug to me: Hitting tab when the focus is on "ice cream" be equivalent to the behavior you would get if it was a focusgroup item, and should move focus to "rice" instead. (or fries when moving backwards, regardless of the location of focusgroupstart or if focusgroupstart is present.)

## @sb3nder — 2026-04-24

I would also expect that the example is a bug, because in #1358, we haven't discussed any special segment behavior or memory interaction for `tabindex=-1`. However, I would not rule out refining its behavior if needed.

The possible behaviors I thought of are:

1. **Behave as a focus group item**: Arrow out, no boundary, Tab/Shift+Tab go outside.
2. **Current behavior**: Arrow out, no boundary, Tab/Shift+Tab go to the first next focusable element, including the focus group starts (even implicit ones).
3. **Behave as an opted-out element with the possibility to arrow out**: Arrow out, same as `focusgroup=none`.
4. **Behave as a conflict element**: Arrow out, Tab behaves the same as arrow keys or go outside.

I don't feel strongly about any of these options. Personally, I think prototyping a `nosegment` modifier for the entire focus group could help separate some issues and guide us toward the right choice. However, feel free to tell me why `nosegment` might be a bad idea.

## @janewman — 2026-08-04

The original issue was agreed to be an implementation bug, fixed with https://chromium-review.googlesource.com/c/chromium/src/+/7789656
The behavior in the explainer and the chromium implementation is to allow arrowing out of, but not into such elements.
