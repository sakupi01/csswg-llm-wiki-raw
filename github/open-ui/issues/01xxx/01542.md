The explainer says a `<rangegroup>` contains real range inputs but doesn't define the tree relationship that makes an input a participant.

A DOM-descendant model can be expressed as:

```text
input is a participant when:
  it is input[type=range], and
  its nearest DOM ancestor rangegroup is this rangegroup
```

This supports ordinary labels and wrappers and excludes nested `<rangegroup>`s. It doesn't support a custom element whose shadow tree contains a native `<rangegroup>` and a `<slot>` for consumer-provided handles:

```html
<x-range>
  <label>Minimum <input type="range"></label>
  <label>Maximum <input type="range"></label>
</x-range>
```

```html
<!-- x-range shadow tree -->
<rangegroup><slot></slot></rangegroup>
```

Customizable select is exploring flat-tree option discovery for the analogous composition problem:

- https://open-ui.org/components/select.slotted.option/
- https://github.com/whatwg/html/issues/11535

### Options to consider

1. DOM descendants only.
2. All flat-tree descendants.
3. DOM descendants plus inputs explicitly assigned through `<rangegroup>` slots, without traversing unrelated descendant shadow roots.
4. DOM descendants plus a future explicit (and separate) association mechanism.

### Questions to resolve

- Should a light-DOM input slotted into a `<rangegroup>` participate?
- Should slot forwarding through multiple custom elements work?
- Should a range input inside a descendant custom element's shadow root participate automatically?
- Is participant order DOM order, flat-tree order, or slot-assignment order?
- Can a slotted `<legend>` name the group, or must the legend be a DOM child?
- Do form ownership, labels, disabledness, and events remain those of the real input when it crosses a shadow boundary through slotting?
