In [this article](https://microsoftedge.github.io/Demos/focusgroup/toolbar.html), showing demos of the implementation in Chromium it is noted the following :
> Set aria-orientation="vertical" on the container so assistive technologies know the toolbar is oriented vertically.

If one wants to make a vertical toolbar, 2 attributes need to be changed, even though (to my knowledge) one would suffice. Knowing the general state of things when it comes to accessibility on the web (lots of tools but very little attention from the dev community at large), would it not be better that the attribute that defines the behavior also describes it to the user ?

connexe question : is there a case where `focusgroup="toolbar block"` and `aria-orientation="horizontal"` (using different axis) makes sense on the same element ?

## @janewman — 2026-03-09

This has come up before, but as of yet, I still think that these should remain decoupled, here's my reasoning:

* Focusgroup’s inline/block tokens control keyboard behavior (which arrow keys work)
* aria-orientation conveys semantic structure to assistive technologies
* These are related but distinct concerns: keyboard axis restrictions may be used to avoid key conflicts rather than to indicate the orientation of the content.
* Aria-orientation is already handled in default cases, when focusgroup applies a [minimum role](https://open-ui.org/components/scoped-focusgroup.explainer/#supported-behaviors), that role’s default aria-orientation applies unless explicitly overridden.
* Aria-orientation has no concept of "all inputs work", e.g. `focusgroup="toolbar inline block"`, or `focusgroup=listbox"
[Section on explainer](https://open-ui.org/components/scoped-focusgroup.explainer/#aria-orientation)

Please let me know if you disagree with any/all of these points, or if you have an idea on how reconcile these. I agree the frustrations and potential for issues you are highlighting here are important.
