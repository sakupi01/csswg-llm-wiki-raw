During the [8 October 2026 telecon discussion on #1524](https://github.com/openui/open-ui/issues/1524#issuecomment-6066630772), it was resolved that `::slider-thumb(n)` follows the DOM order of the child `<input type="range">` elements.
During that discussion, @keithamus raised that thumbs should reflect their backing input's state:

> keithamus: thumbs should match input state, :disabled should match. I think you should make a separate issue for that.*

This issue is split out to investigate how state styling should work across the group-to-thumb pseudo-element boundary.

On `<rangegroup>`, the parent element owns the composite track rendering and coordinates the handles. Consequently, thumbs are addressed as pseudo-elements of the group:

```css
rangegroup::slider-thumb(*) { background: #0070f3; }
rangegroup::slider-thumb(1) { background: #e00; }
```
However, user interaction and DOM state live on the child `<input type="range">` elements:

- An individual input can be independently disabled (<input disabled>), or disabled via an enclosing <fieldset>.
- An input receives :focus and :focus-visible when tabbed to.
- An input receives :hover or :active during interaction.
- Today, styling a disabled or focused thumb through the group pseudo-element requires awkward and brittle :has() queries:

```
/* Example styling thumb 1 when its backing input is disabled */
rangegroup:has(input:nth-of-type(1):disabled)::slider-thumb(1) {
  opacity: 0.4;
  cursor: not-allowed;
}
```

This approach:

- Does not scale when thumbs are added or removed dynamically.
- Cannot easily express "style any thumb that is currently disabled or focused" without writing separate rules for every index.
- Becomes very complex for interaction states like :active or :focus-visible.

A few things to get the discussion going:

- Should ::slider-thumb reflect the child input's state pseudo-classes directly? Could authors target state directly on the pseudo-element:

```
/* Style any thumb whose backing input is disabled */
rangegroup::slider-thumb(*):disabled {
  opacity: 0.5;
}
/* Focus ring on the active handle */
rangegroup::slider-thumb(*):focus-visible {
  outline: 2px solid blue;
}
```

Alternatively, should thumb styling originate from the child <input>? Even though <rangegroup> coordinates the layout, could an author style the thumb from the input itself:

```
rangegroup input[type="range"]:disabled::slider-thumb {
  opacity: 0.5;
}
```

(Note: This relates to whether <input type="range">::slider-thumb remains a valid selector within <rangegroup>, or if the group exclusively owns ::slider-thumb.)

Interaction with group-level disabling: When <rangegroup disabled> is present, all thumbs are disabled. Does rangegroup:disabled::slider-thumb suffice, and does each thumb also match `:disabled`?

CSS Selectors precedent: What precedent exists for pseudo-elements reflecting host or associated light-DOM element states (e.g. `::file-selector-button:disabled` or `::slotted(:disabled))`?

I'd like to get some ideas here first, if possible, before we set this on the agenda, to at least steer the discussion a bit better.
