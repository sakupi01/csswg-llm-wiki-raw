## Introduction

This proposal introduces a styling API for HTML range inputs, allowing developers to customize the appearance of both single and dual-range inputs. This enhancement aims to provide greater design flexibility while maintaining the benefits of native form controls.


## Use Cases



* Creating range inputs that match a site's design system
* Implementing custom visualizations for range selection
* Enhancing the usability of range inputs with visual feedback

## Proposed Solution

We propose introducing a new CSS appearance value and a set of pseudo-elements to enable detailed customization of range inputs.


## CSS API

To opt-in to the new styling capabilities:


```
input[type="range"] {
  appearance: base-range;
}
```


Pseudo-elements:



* `::range-handle`: Represents the draggable handle(s)
* For dual ranges, use values `low` and `high` to target individual handles
* `::track`: Represents the track along which the handle(s) move
* `::selected-range`: Represents the portion of the track between handles (in dual range) or from start to handle (in single range)
* `::ticks`: Represents tick marks along the track

Example Usage


```
input[type="range"] {
  appearance: base-range;
}

input[type="range"]::range-handle {
  width: 20px;
  height: 20px;
  background-color: blue;
  border-radius: 50%;
}

input[type="range"]::track {
  height: 5px;
  background-color: #ddd;
}

input[type="range"]::selected-range {
  background-color: #4CAF50;
}

/* Think  of scroll-marker capabilities */
input[type="range"]::ticks {
  content: "";
  background:... ;
}
```



## Styling Dual Ranges

For dual range inputs, individual handles can be styled (based on proposal [issue 1164](https://github.com/openui/open-ui/issues/1164)):


```
input[type="range"][dual]::range-handle(low) {
  background-color: red;
}

input[type="range"][dual]::range-handle(high) {
  background-color: blue;
}
```

This could also become handy for reading attributes:

```
input[type="range"][dual]::range-handle(high) {
  content: attr(data-highnumber type(<number>), 0);
  background-color: blue;
}
```



## Backwards Compatibility

This styling API is designed to be backwards compatible. Browsers that don't support `appearance: base-range` will fall back to their default range input styles.

## Open questions

* Should we provide more granular pseudo-elements (e.g., `::tick-label`)?
* How should we handle vertical range inputs in terms of styling?
* These proposals provide a framework for both extending the functionality of range inputs with dual handles and enhancing the styling capabilities of all range inputs. They aim to balance new features with backwards compatibility and progressive enhancement.
* Is there some way we could add scroll-marker capabilities into this equation?

## @thebabydino — 2025-02-26

I really don't have the energy for this right now, but here are [a dozen very detailed comments](https://github.com/w3c/csswg-drafts/issues/4410#issuecomment-1087244943) going into the problems I've hit with the current range input and which this proposal isn't addressing.

Also this is [a case study showing problems I'm hitting](https://gist.github.com/thebabydino/68901fd1d93cf1dc88dbb1174fc29ba2) with the current range input when trying to style a very simple one consistently.

As for the solution proposed here.

I don't see the point in moving away from `::thumb` to `::range-handle`. And I'm not a fan of the `dual` attribute - sometimes I want more than two thumbs. I think allowing the `value` attribute to take more values and the number of values being the number of thumbs, then referenced as `::thumb(1)`, `::thumb(2)`. I'm not a fan of `high` and `low` because it implies we can only have two thumbs and that one is always associated with the smaller value, while the other is always associated with the bigger one. I've found it useful when the thumbs can cross - if the first value is the bigger one, then the range interval goes in the negative direction, which gives me a sign I can use in subsequent computations.

I don't know how I feel about `::selected-range`, though I agree the current Firefox `::-moz-progress` doesn't really illustrate what we want, so we need another name. Perhaps `::fill` and two of them (selected/ unselected, though somehow those don't feel like the right words to describe it), like IE/ pre-Chromium Edge used?

The `::ticks` proposal is very limited compared to what we currently get using `datalist`. Though I have wondered whether it's not better to integrate a ruler with a value display into the actual range `input` (like IE/ pre-Chromium Edge did) given people don't know about `datalist` and [don't use it](https://gist.github.com/thebabydino/6a2bc57754132128b9077108ae03a803)? I think this also answers yes to the first open question.

As for vertical sliders, we can currently get them from the CSS in both Chrome and Firefox by simply setting the `writing-mode` to vertical. Seems like a valid solution that requires no further future effort. This can be seen in action in [this demo](https://codepen.io/thebabydino/pen/oNOrXQj).
