For `<rangegroup>` the following questions was asked:

What could be done to enable segment dragging? At the moment, according to the explainer, a click on the track will move the nearest thumb.

The example given was the [iOS alarm clock](https://support.apple.com/en-mz/guide/iphone/iphf2a780f81/ios).

The behavior is that you can select two times and drag the whole segment, moving the two thumbs together.
It might be a thing we could do with a JS api. I'm not sure it should be the default. I also wonder about accessibility implications for this. I'd like us to at least think about the possibility

This feedback was gathered at CSS Cafe 13/06/2026

## @brechtDR — 2026-08-28

No resolution. Two clusters of use cases:

1. **Endpoints matter** (price min/max): click/drag on the track should move the nearest thumb; people do **not** want the whole range to jump.
2. **The interval matters** (calendar block, video in/out, traces): users expect to **translate** the selected range. Clicking outside may move the block rather than only one end.

Concerns: click-to-move-nearest-thumb vs drag-the-segment fight if both are default; 3+ thumbs make a single “the segment” unclear; shaky-pointer / accidental drags.

**Direction to investigate (not specced):** an author-selectable **mode** (name TBD — not `draggable`) so the control is either thumb/endpoint-oriented or range-oriented. Default should follow **research**, not the room’s 50/50 split. If one pattern is ~90% of libraries **and** apps, we can punt the mode.

Also: if range-oriented, click **between** thumbs should not silently pick a thumb (`preventDefault`-ish); click **outside** the interval could still move the closest thumb — needs to stay consistent with drag. Related: #1278.

Keyboard/focus for a “segment” control will be a **separate** issue. If the segment is draggable, it should be focussable

Next for me: survey common libraries vs in-app pickers and report back here. Removing the `agenda+` until that lands.
