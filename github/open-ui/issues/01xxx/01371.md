## @TrySound — 2026-02-13

I previously used [react-colorful](https://omgovich.github.io/react-colorful/), which is pretty much a standard Saturation × Value area + Hue slider.

<img width="267" height="261" alt="Image" src="https://github.com/user-attachments/assets/a39039e2-1ead-4c41-be1c-1b31d4456f21" />

Though Adam's color input is built as a web component and can be universally used with other frameworks (I use Svelte for another app).

He initially added only sliders and a static area for color preview.

<img width="356" height="420" alt="Image" src="https://github.com/user-attachments/assets/4ae354ff-b498-45e3-a201-07d64ab53b93" />

So my first implementation was just putting the area on top. I added a canvas-based Chroma × Lightness area to support OKLCH first, though it didn't work well with RGB, and I switched to Saturation × Value there as a more widely used solution.

Figma supports both RGB and HSL, but for HSL it does not use the same Saturation × Value area; instead, it supports the whole Saturation × Lightness area. This gave me the idea to support multiple areas for different color spaces.

Sliders for all channels are still in place, since SV is incompatible with any of the supported spaces, and more granular control still makes sense.

Then Adam suggested shrinking the preview and putting it at the bottom to keep all controls and make it similar to other color pickers.

## @aardrian — 2026-02-13

React Datepicker: https://reactdatepicker.com/

I recommend against following it given the last time I reviewed it I found the following [WCAG](https://www.w3.org/WAI/WCAG22/quickref/) violations (this despite its accessibility notes and guarantees):
* 1.3.1: Info and Relationships (A)
* 1.4.1: Use of Color (A)
* 1.4.11: Non-text Contrast (AA)
* 2.1.1: Keyboard (A)
* 3.3.2: Labels or Instructions (A)
* 4.1.2: Name, Role, Value (A)

Happy to offer more detail on those if needed.

## @travis-jeans — 2026-02-14

Hello, I found a link to this thread on Mastodon. Here are some pickers and what I like or don't like about them (focus on open source since that is what I'm using right now) but I'll include some ones I've used previously afterward.

<img width="455" height="283" alt="Colour Contrast picker example from GNOME with comparison between black and white" src="https://github.com/user-attachments/assets/5c45a986-235a-4ba9-800c-b485b64277f5" />

### Contrast picker by GNOME (Linux)

Not a picker in the sense of picking colours off the screen but lets you compares colours. Including for the "do nots" list and the simple interface.

#### Good:

- Comparison of two colours
- Allows quick comparison of colour pairs using copy-paste functionality of HEX codes
- Simple, easy to use interface
- Easy to interpret with A, AA, AAA bars and contrast ratio

#### Bad:

- Colour pick icon seems to be just an icon / reference to copy-pasting colours not a button to let you pick a colour off the screen nor does it open a colour pick dialog
- If you pick a bad colour combination it turns the interface invisible
- Can't select or copy the reported colour contrast ratio
- Not a colour picker, just a comparison tool

Bad colour combination examples:

<img width="451" height="279" alt="Comparing white and pink, the interface turns a light colour pink with 1.6:1 contrast ratio" src="https://github.com/user-attachments/assets/9795eb35-6b6f-4f15-97a2-888ec9e46750" />

Comparing white and white... is unusable. You need to close the app and restart. I'm going to report this to the devs after this, assuming it hasn't been done already. (Update: Made an [Issue on their GitLab page](https://gitlab.gnome.org/World/design/contrast/-/issues/37))

<img width="451" height="281" alt="Comparing white and white makes the interface invisible, the selected input has a highlight around it and the app logo is still visible but everything else is white" src="https://github.com/user-attachments/assets/708a316f-8759-421d-9b81-b324ac3bc7d5" />

### WebAIM Color Contrast Analyzer

Special mention to [WebAIM Color Contrast Analyzer.
](https://webaim.org/resources/contrastchecker/). Like Contrast its main goal is to compare a foreground and background swatch.

<img width="746" height="820" alt="Screenshot from WebAIM Color Contrast Analyser" src="https://github.com/user-attachments/assets/968936a3-d5f8-423e-9d93-712e4e486b44" />

#### Good:

- Example of "Large text", "Small text", and a UI box
- Big pass or fail text with additional colour decoration and easy to read text for A, AA, AAA success or failure
- Giant HEX Colour input box
- Color Swatch which will bring up the desktop default colour picker if pressed
- Colour swatch is separate to the HEX code
- Adjustment sliders

#### Bad

- Uses the desktop colour picker which will vary depending on your operating system
- Not specialised as a colour picker so sometimes I will need to go into Inkscape or whatever program tweak the colour using that colour picker, then paste back into WebAIM, rinse and repeat

### ColorPicker (Linux)

So apparently [ColorPicker (Linux)](https://github.com/keshavbhatt/ColorPicker) isn't maintained anymore but I haven't updated to the successor yet. It has some useful features though.

<img width="865" height="496" alt="ColorPicker for Linux screen" src="https://github.com/user-attachments/assets/68af9973-7175-4e12-97c7-f849ebc25bde" />

#### Good:

- Pick screen colour button which has text and icon label
- HSV picker with 360 colour bar and colour grid
- copy-able fields for HEX (they call HTML), HSV, RGB, alpha
- An area where you can visually compare two shades for text and background (Pick Bg Color)
- Add temporary swatch area

#### Bad:

- Almost too many features, some I don't use like Shade generator, Basic Colors, Temporary Swatch might be better as  optional toggle-able features
- Would be nice to have the ability to swap colour space from HSV to HVL or something else

### Just Color Picker (Windows)

Not my screenshot but borrowing it. There are more examples on the website [Just Color Picker](https://just-color-picker.en.lo4d.com/windows).

<img width="450" height="329" alt="Just Color Picker screenshot" src="https://github.com/user-attachments/assets/20975d7e-b5eb-4f4f-be1e-5e79480672ec" />

#### Good:

- Radio buttons to toggle RGB, HSV, HSL
- RGB code in textarea box has colour swatch behind the text (would be better if it was beside the text - similar possible issue as Contrast
- Ability to save multiple swatches
- Extra numbers not always very useful (coordinates under the swatch)
- Big Copy Value button
- Color sliders to adjust the selected value
- Will automatically save previously swatches in a list
- Maybe unrelated but the logo is really cute and memorable

<img width="128" height="128" alt="Just Color Picker logo is a cartoon chameleon with a curled tail" src="https://github.com/user-attachments/assets/664d7560-a05e-4174-aa12-b8c4750ee69c" />

#### Bad
- Down arrows to move between previously selected swatches should be beside the swatch selector box not the "copy value" button
- Can't choose to save a swatch temporarily it is automatic, maybe you pick several colours you don't like (a "temporary save area" and a "saved swatch area" can be different things
- The zoomed in preview area with the cross hair isn't always that useful, sometimes you can't remember what part of a picture you're looking at and your eyes don't have that level of resolution when picking anyway

### Overall

- The ability to select from different colour spaces is very helpful (RGB, HSV, HSL)
- Being able to see RGB colour values and HEX codes are as a designer, the ability to see HSV or HSL values is good as well especially if paired with a slider
- Visually a slider plus values is easier and quicker to interpret than either one alone (a colour gradient-filled slider with live swatch updating)
- Ability to easily copy a HEX code is a very valuable feature (a button is usually less clicks than selecting the text input box and manually copying (e.g. web design/ colour palette creation)
- Although I haven't seen it, the ability to quickly copy an RGB or other swatch value without having to click into an input field or highlight text would be helpful (web design reporting colour swatches) - the copy icon could be a useful button 
- Having a colour swatch preview of the colour in the app is helpful but only if it is beside the colour code (not behind it as a background colour since it affects accessibility / legibility)
- Color sliders and color grid / select area are useful for different reasons - both is ideal
- Integer (not float) values for colour values in the interface is less cluttering (I've heard arguments this is less accurate - I don't know the maths but an interface where integer values are used on the sliders like Inkscape is more legible than what's in Krita for instance, decimal values are longer to read)
- Accessibility comparison options are useful (but not mandatory since there are specialist apps for it), still would be very useful and help normalize accessibility testing colours if more widely available
- Swatch foreground and background comparison swatches are useful, the ability to see preview text with those colours with an easy to interpret accessibility bar would be amazing (but also probably very rare)
- If there is a save swatch area, I think it's best if there's a "recent swatches / swatch history" and "saved swatches" are separate since those fulfill different functions

Hey, we [discussed on bsky](https://bsky.app/profile/lukewarlow.dev/post/3mesmvsopnk2s) that you're also interested in what's holding us back from using the HTML input pickers.

I work for a website in the travel industry and date selection is important to us.

<img width="374" height="485" alt="Image" src="https://github.com/user-attachments/assets/5c6571b4-392d-4ea7-acf6-527a486f376d" />

<img width="550" height="714" alt="Image" src="https://github.com/user-attachments/assets/605cfad9-1807-43df-9521-0fca365ded55" />

To replace the above calendar pickers with HTML `<input type=date` pickers, we'd need:

1. to be able to show the `<input type=date` control in the expanded state, rather than as a field that pops-up when you click on it. That's because in the first screenshot we combine it with the specific-date/month toggle and because in the 2nd screenshot the calendar is a core part of the page's design.
2. to be able to disable particular days, because for example there aren't suitable flights available.
3. to be able to highlight a tail of following dates, approximately a week long to show the trip's duration
4. to theme with our brand colours and typography
6. to add extra text and symbols onto each day (eg the prices and cheapest price symbol in the second screenshot)

We don't offer a date range. It is quite usual in the travel industry to select both departure and return on the same calendar and possibly something we'd experiment with again.

We don't track but in our industry it might be important to have telemetry on what months people look at before making their decision or bouncing.

Hope this helps. I'm happy to provide more details if it is wanted.

EDIT:

Not useful for my website, but I imagine it would be very useful to be able to style the collapsed date input with CSS and [Intl.DateTimeFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/DateTimeFormat) properties.

## @Crissov — 2026-02-17

Do you really want to collect *all* kinds of pickers in a single topic? 

----

The main focus for now seems to be colors, although most people never ever need one that goes beyond choosing a **hue from a palette**. Speaking of which, I have very strong opinions about representing an angular value by vertical or horizontal sliders.

Other frequently occurring values are essential **cyclic** as well, but are rarely made selectable by a matching widget, calendar months for instance. Apple got that right in some places on iOS (but week-tabulated months sometimes slide horizontally and sometimes vertically). 
![iOS cyclic month picker](https://github.com/user-attachments/assets/f6ebae19-9a32-4776-884e-f4165e7972e5)

Linear sliders are also often used for (automatically determined min-max) ranges that have **neither a linear nor a normal bell-shaped distribution** of values, for instance many prices on the low end and two or three extreme outliers. 

There were some nuisances with it, but overall, old versions of MS Word (2007ish) had good input widgets for lengths that support **multiple units** with conversion to preferred ones. 

Good pickers will let users **paste a value** at any time and anywhere, then do their best to interpret it correctly, e.g. a locally formatted datetime in a date-only picker or a phone number with or without international prefix and separators. 

**Country and language** pickers are notoriously bad and difficult. Nobody wants to scroll through an alphabetic list of 200 or more entries, especially if they display native names but are sorted by code or by English names with an unfamiliar **collation** algorithm: will you find Austria after Australia, after American Samoa (`AS` < `AT`), before or after Oman (Oesterreich < Osterreich) or after Zimbabwe (Z < Ö)? Other localizable values are also difficult, e.g. fonts. 

A recent pet peeve of mine are versatile **clothing size pickers and filter selectors**. There are several sizing systems and subsystems which usually cannot be converted 1:1 correctly and often use overlapping designations, e.g. `36` could be a European shoe size or lady‘s dress size, or an underbust girth for bras  or a hip girth or leg length for jeans measured in inches, or the age of a toddler in months. Similarly, **filtering by spatial dimensions** of physical products is hard: does it matter which one is height, width, breadth or depth, is diameter, circumference or volume/capacity more intuitive, which unit is used or implied, do you match minimum, maximum or exact value?

**Date range** pickers always mess me up because I never assume correctly whether you need to click and drag or click once for both, start and end, or whether the inverse direction also works, or how you can adjust just one limit without the other. 

PS: I realize that this reply is a bit unstructured and partially off-topic.
