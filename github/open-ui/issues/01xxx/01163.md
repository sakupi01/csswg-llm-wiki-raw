## @andyearnshaw — 2026-04-24

I can see the last discussion on this resolved to use the `name` attribute, although there were some reservations about that. I share similar reservations because it means you have to "globalise" the `name` attribute—that is, you have to make it part of `HTMLElement.prototype` for the IDL. That's totally doable, but it creates a situation where there's a `name` property that works one way for almost everything and then a different way for the handful of elements for which `name` works differently. It also prevents exclusive visibility on things like `<iframe>`, `<form>` or `<slot>`, because their names are supposed to be unique, so those elements have limited/different functionality as openables.

Maybe it would make sense to break out exclusive visibility into its own attribute? That way, you have a generic attribute that is flexible and doesn't need to only apply for openables. This is actually [an idea I had](https://github.com/whatwg/html/issues/1809) about 5 minutes before a discovered the Openables API proposal. I named the attribute `visibilitygroup`, with the idea that all elements part of a visibility group have mutually exclusive visibility. Adapting my example for openables:

```html
<div class="tabs">
  <div class="tab-list" focusgroup="tablist">
    <button commandfor="tab1" command="open-openable">Tab 1</tab>
    <button commandfor="tab2" command="open-openable">Tab 2</tab>
    <button commandfor="tab3" command="open-openable">Tab 3</tab>
  </div>

  <div class="tab-content" visibilitygroup> <!-- all children are part of a visibility group -->
    <section id="tab1" role="tabpanel" openable="open">...</section>
    <section id="tab2" role="tabpanel" openable>...</section>
    <section id="tab3" role="tabpanel" openable>...</section>
  </div>
</div>
```

In fact, the spec for `<details>` could be updated to specify that the `name` attribute implicitly applies a visibility group to its non-`<summary>` content.

The idea is that the attribute used with no value applies exclusivity to all children, whereas providing a value applies the exclusivity to the element itself. It could even have multiple tokens to be part of multiple visibility groups. For example, if you wanted to show different sidebar content depending on which tab is open, but your sidebar is not part of your tab panel, you could use multiple visibility groups to do it, and it eliminates the use of JavaScript for it.

## @andyearnshaw — 2026-04-27

> And since it already has been adopted the `details` element for the same purpose I think using it for openable elements is the path of least resistance.

The difference with `details` is that the IDL only needs to apply on the `HTMLDetailsElement` interface. The current resolution to apply a `name` attribute to everything will require the IDL for `HTMLElement` to be updated, and this attribute will essentially be shadowed by the one on `details` (and `iframe`, and `slot`, and everything else). When you factor that in, I think it becomes the path of most resistance, although I'm not a committee member on any of the various standards where this will apply so I can't say for sure.

> In an ideal world we would introduce a group attribute and update multiple specs with it for absolute clarity. But this might be a tad unrealistic.

What do you think makes it unrealistic? Most, if not all, graduated proposals here target multiple specs (usually HTML and CSS). If anything, I think shadowing the `name` attribute is more unrealistic, as it usually only takes one committee member to block a proposal and it seems like a pretty obvious blocker.

> I would not be happy to see the need for a container wrapper be introduced. While of course many classical use cases are sharing a common ancestor. But it robs the behavior of a lot of flexibility

My suggestion was to allow both forms:

> The idea is that the attribute used with no value applies exclusivity to all children, whereas providing a value applies the exclusivity to the element itself. 

That means the following are equivalent:

```html
  <div class="tab-content" visibilitygroup>
    <section id="tab1" role="tabpanel" openable="open">...</section>
    <section id="tab2" role="tabpanel" openable>...</section>
    <section id="tab3" role="tabpanel" openable>...</section>
  </div>
```

```html
  <div class="tab-content">
    <section id="tab1" role="tabpanel" openable="open" visibilitygroup="my-tabs">...</section>
    <section id="tab2" role="tabpanel" openable visibilitygroup="my-tabs">...</section>
    <section id="tab3" role="tabpanel" openable visibilitygroup="my-tabs">...</section>
  </div>
```

The shorthand is just a convenience aspect that I don't particularly feel strongly about. I think it may be a new concept to HTML, so if it were a blocker to adoption then the explicit form would be enough.

> It introduces the need to traversing the tree up and down to find the group siblings of an element. Rather than to check for an common attribute.

This isn't particularly complex. It would only apply to all children of the parent, there's no "traversing the tree up and down".

> It adds a container, that needs to be considered when layouting for the sole purpose of controlling a child or descenders behavior.

Again, the container is optional (but likely there anyway in the majority of use cases). If you didn't want the container, you could use the attribute-name-with-value approach instead.

> It deviates from the existing behavior of input type="radio" and details conceptually. So if the goal is consistency, we would need to introduce the same group concept for those elements as well.

Things with the `name` attribute already deviate in behaviour. If it helps you understand it, you can look at it this way:

* `name` on `<input type="radio">` adds the element to a "value group" _and_ a "focus group"
* `name` on `<details>` adds the element's children (except the `<summary>`) to a "visibility group"
* `name` on everything else (where defined on the interface) doesn't create a "value group", "focus group" or a "visibility group", in fact in most places it doesn't create any kind of group

Creating a new definition of the `name` attribute for all other elements (add this element to a "visibility group") is just another deviation. My suggestion is actually trying to prevent this.

You could also consider the "focus group" behaviour of `<input type="radio">` to be superceded and extended upon by the `focusgroup` proposal that's part of this repository. Likewise, if visibility groups were to get their own proposal, they would supercede and extend upon the behaviour of the `<details name>` element's implicit "visibility group".
