## @mfreed7 — 2025-09-10

> Given that WebKit is explicitly opposed to interestfor in its current shape 

Nothing about their [objection](https://github.com/whatwg/html/issues/10309#issuecomment-3266951344) actually mentions the shape. It states that it is "premature" because "mobile does not provide a consistent and reliable way to get to tooltip-like information". Essentially they deny the existence of long-press on mobile as a de-facto standard for everything other than web browsers, despite [research](https://docs.google.com/spreadsheets/d/11Bt_FCAqu1hd5llGRGpzgwlgHaqLmOC4SJEMRtNQY-g/edit?gid=113109928#gid=113109928) to the contrary, and a [dedicated UIKit API for long press](https://developer.apple.com/documentation/uikit/handling-long-press-gestures). For this reason, I'm unconvinced there's any change that can be made to the shape of the API that will change their opinion. Or at least none that has been stated out loud.

> For better or for worse iOS one of the largest computing platforms does not pratically offer alternatives to WebKit (yet). So if they don't support it and and we'll always need a polyfill then this feature being in the platform doesn't actually provide much value.

The [polyfill](https://github.com/mfreed7/interestfor) is actually fairly functional. It doesn't provide touchscreen functionality, because (due to lack of `interestfor` in the platform) that is impossible to implement on the web today. But otherwise, I think it actually could be a very good path forward for sites that want to use this API even on WebKit browsers that don't natively support it.

## @tabatkins — 2025-09-11

I strongly agree with Mason in this regard. Apple's publicly stated objection is not to any specific aspect of this, but seemingly to the generic functionality in its entirety, despite phone touchscreens having been in incredibly common use for over a decade and this UX pattern, in particular, being incredibly common across the entire app ecosystem on every mobile OS. The public market has iterated substantially and a "long-press" has been the stable winner for this type of interaction on mobile for a long time now; similarly for "hover" as the winning interaction on mouse-driven devices. There are some new form factors (Anne mentions "spatial UIs", presumably referring to VR/AR devices) that do not yet have widely-established and proven interaction patterns, but the existence of new varieties of UI should not block the enshrinement of existing stable UI patterns.

The particular type of interaction represented by `interestfor`, in particular, is *incredibly* difficult to do correctly in all aspects for authors (and, to some extent, *literally impossible*, as mobile platforms don't necessarily offer websites the ability to intervene in some necessary ways). Despite that, it's also incredibly common. Continuing to leave this to authors to figure out on their own is doing a disservice to users, who will benefit greatly from a standardized, predictable, accessible UX interaction here. We've already improved some *aspects* of it substantially (such as with popover, anchor positioning, etc), but the complete package is still substantially difficult to put together correctly, as wide experience across the website ecosystem shows.

## @mfreed7 — 2025-09-16

> Can you explain how the polyfill can be used for browsers that don't support it while also not working on iOS at all? I know it can't replicate the exact touch screen behaviour but not supporting any doesn't feel right.

Well again, it's not possible (due to the `<a>` context menu) to polyfill this behavior for touchscreens. But importantly, due to that same restriction, production sites today also do *absolutely nothing* for touchscreens. So this will not be a loss of functionality, it'll just be the lack of a gain for touchscreen. On supported browsers, touchscreen will work (a gain). On unsupported browsers, the polyfill will handle all cases except touchscreen (no loss). This seems ok to me?

And all of this neglects the very significant **user benefit** of a standardized API: the interaction pattern on desktop, for hover and keyboard, will be standardized and functional across sites. That seems to always get lost in the debate over this API, for some reason.


> Is it possible that the webkit-touch-callout https://developer.mozilla.org/en-US/docs/Web/CSS/-webkit-touch-callout can be used to control whether we get the interestfor behaviour or the default?

This would allow disabling the context menu on links. That's precisely what `interestfor` is trying to avoid, because that's bad for users. So I'd be against trying to incorporate that into the polyfill, since it'll break things for users, and likely that means developers won't use it.

> If the polyfill can provide a compelling experience then I don't think it's vital to ship in chromium despite objections. If it can't provide a compelling experience well then it can't be used to cover the lack of WebKit support. Either way I don't personally think that shipping in chromium is a net positive for the web.

It's clear (to me at least) that the debate over the importance of this API will not be settled by further discussion, it'll only be settled by observing developer behavior and getting folks to use the new API. And again, the native feature will unlock touchscreen-based interest, which is a win as compared to a polyfill.

> I completely understand the frustration especially when as you say it's not actionable feedback. But at the same time if this potentially never even gets added to Firefox let alone Safari I don't think its good to ship. The API shape exists and is ready to go should Apple ever change their mind.

I'm hopeful that this gets shipped in Firefox. Mozilla is [supportive of stage 2](https://github.com/whatwg/html/issues/10309#issuecomment-3252590058) for this API. And in stark contrast to [WebKit's three-sentence objection](https://github.com/whatwg/html/issues/10309#issuecomment-3266951344), the [discussion on the Mozilla standards position has been quite detailed and actionable](https://github.com/mozilla/standards-positions/issues/1181). As far as I can tell, I've addressed most/all points of that feedback.

> To take from the chrome shipping process. What does success look like if this gets shipped? If people can't make this work on iOS they'll never use it at scale. If this ships but can't support 50% of touch devices the original goal of solving this pattern for touch devices isn't met?

Success looks like eventual standardization, once evidence becomes available that the API shape is indeed good. And in the interim, the polyfill.
