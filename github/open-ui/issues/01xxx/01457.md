# The Main Take <a name="main-take"></a>

In the current proposal for [Declarative Overscroll Actions](https://open-ui.org/components/overscroll-actions.explainer/) an HTML attribute on the container is used as the opt-in mechanism to enable overscroll areas.

> First, the container needs to be identified as supporting overscroll areas. This is done by specifying `overscrollcontainer` attribute on the container.

To cut to the chase, I think that using an attribute as an opt-in mechanism is wrong, and I believe that, instead, this opt-in should be done through CSS.

There is also the command button to toggle overscroll that is part of the proposal:

> Second, we introduce a new command value, `toggle-overscroll`, to bind a trigger button to both the container (the scroll port) and the content (the element hidden in the overscroll area).

In a previous iteration of the proposal, this button was also necessary to make something an overscroll area (see [this (outdated) code example](https://github.com/whatwg/html/issues/12273#issuecomment-4203450851)), but that — thankfully — is no longer the case: the command button is nowadays only concerned with scrolling an overscroll area into or out of view.

_(So to correct the [meeting minutes](https://github.com/whatwg/html/issues/12273#issuecomment-4261358292): devrel said that the button is awful **as the way to make something an overscroll area** ;))_

# But, why CSS then? <a name="why-css"></a>

In my perception, Overscroll Areas are very much layout dependent: depending on what screen size you are looking at something, an element might always be in view (e.g. on the big screen layout) or tucked away behind a button that can toggle it (e.g. on the small screen layout).

Furthermore some Overscroll Areas may be presented without a Command Button to overscroll that area being present at all.

Finally, a container might have multiple overscroll areas, each with their own [overlay mode](https://open-ui.org/components/overscroll-actions.explainer/#overlay-mode), so one single attribute on the container won’t cut it.

Let’s take a look at some examples to clarify this …

## Example 1: Navigation / Drawer Menu <a name="example-1"></a>

Let’s look at a navigation menu. On a large screen layout this would be a side-column that is typically placed next to the content. On a small screen layout this becomes a drawer menu that you either reveal by pressing a hamburger button somewhere or — and this is what overscroll areas try to achieve — by scrolling from the edge of the screen to reveal said menu.

# But what about Accessibility? <a name="a11y"></a>

Good, I thought you’d never ask 🙃

## Interfaces should already be accessible <a name="a11y-already"></a>

Interfaces that get augmented with overscroll gestures should already be accessible regardless of overscroll gestures being added to it or not.

### Applied to the Drawer Menu <a name="a11y-already-example1"></a>

In the case of the drawer menu example, a developer MUST already have a command button in place to show / hide that sidebar.

The current API proposal already has this in place, namely a command button that can send a `toggle-overscroll` command.

```html
<button commandfor="menu" command="toggle-overscroll" id=btn aria-label="Reveal Menu">☰</button>
```

This button is still very much necessary, as it makes the interface accessible: you can tab into it, activate it to reveal the drawer menu, etc.

As a reminder: unlike the current proposal, this button here is not used for the opt-in to create an overscroll region, but it is used only for scrolling that overscroll area into view.

### Applied to the E-mail Interface <a name="a11y-already-example2"></a>

As for the e-mail client interface: the actions that are exposed by the gestures should already be reachable through the regular UI.

Practically speaking, I would expect to be able to tab through the list of emails, and when at the e-mail detail view, I would expect that detail view to have buttons to archive the email and toggle its read state.

Therefore, I don’t think that this interface should have a command button with `toggle-overscroll`, because a user can already perform the actions that are tucked away through another mechanism or path.

(I think of this similar to adding keyboard shortcuts to an interface. While very handy, the actions that these shortcuts do can already be achieved through the interface)

## Use `aria-actions` when there is no command button to toggle an overscroll area <a name="aria-actions"></a>

To present these extra actions tucked away behind overscroll areas, `aria-actions` (See issue [w3c/aria#1440](https://github.com/w3c/aria/issues/1440) and accompanying (WIP) PR [w3c/aria#1805](https://github.com/w3c/aria/pull/1805/)) should be used to expose these in an accessible way.

In the drawer menu example this is not necessary, because there are already command buttons in the markup to either show or hide the menu.

In the e-mail interface using `aria-actions` is very much necessary because there are no command buttons.

By setting the `aria-actions` on the e-mail `div` to point to the already present buttons for archiving and toggling the read/unread state, this can be achieved:

```html
<div class=email aria-actions="toggleread,archive">
  <a href="detail.html">…</a>
  <button id="toggleread" aria-label="Mark as read"><icon … /></button>
  <button id="archive" aria-label="Archive E-mail"><icon … /></button>
</div>
```

The exact markup is dependent on what `aria-actions` will end up looking like, but you should get the idea here: you link up the existing buttons (the very same ones presented to users who use overscroll) through `aria-actions`.

# So, what would a CSS opt-in look like? <a name="prototype"></a>

_(Everything in this section is informational, but I did want to share it with you to give the full picture of how I think about Overscroll Areas.)_

I don’t want to hinge this discussion on the exact shape of what this should look like, I am mainly seeking an agreement on that, perhaps, Overscroll Areas should be a CSS opt-in instead of an HTML opt-in.

However, I did my homework and created a prototype which you find at https://major-butterfly-redfish.codepen.app/ for you to explore. I’ve checked basic tabbing behavior, and VoiceOver announcing things, but nothing more.

Here’s a quick write-up of how it behaves. There is a lot of overlap with how the feature currently behaves, so not that much should be new:

- Overscroll areas use scroll-snapping
- Non-visible areas of overscroll areas are inerted, so you can’t tab into them.
- The `toggle-overscroll` command only makes that overscroll area visible, it doesn’t activate anything inside the now visible overscroll area.
- After an overscroll area becomes visible, there is a lot of behavior similar to a modal dialog being shown:
  - the rest of the contents in the parent scroller are inerted
  - the first focusable element inside the overscroll area gets focused
    - If there is no such element, the entire area gets focused.
  - visible overscroll areas are light dismissable
  - there are styleable backdrops

Some other things worth nothing with this proposal:

- (NEW) Overscroll Areas can be toggled on and off with Media Queries (or other conditions)
- (NEW) The opt-in is coupled with a positioning scheme that is inspired by anchor positioning’s 9-box grid and/or grid areas.
- (NEW) An Overscroll Area is a size container by default. Content inside an overscroll area can use container query units.
- (NEW) It is possible to define multiple overscroll areas, each with their own [overlay mode](https://open-ui.org/components/overscroll-actions.explainer/#overlay-mode). For example, content on the left can be “overlay”, whereas content on the right can be “normal” or “underlay”.

Again, please note that the CSS syntax from that prototype is **not** the core of this issue and is something that — if there is agreement on putting this in CSS — would need to be discussed at the CSS Working Group. The core of this issue is to get an agreement on that, perhaps, Overscroll Areas should be a CSS opt-in instead of an HTML opt-in.

## @bramus — 2026-06-15

> I think the discoverability concern would mostly be non-screen reader users. Especially those using an input modality without clear patterns for these sorts of things.

Is this really a problem if the means to reaching a specific goal are available elsewhere in the UI?

In the e-mail example, the archive and toggle read actions that are tucked away behind overscroll areas are just an extra means of invoking those actions, in addition to buttons available elsewhere in the UI. This similar to keyboard shortcuts being available _(where the de facto standard is to hit `?` to reveal instructions — try it on GitHub, YouTube, Gmail, etc.)_

If authors really want, they could always inject some indicator based on the `aria-actions` attribute. However, I wouldn’t want the UA to do this automatically as it:

- Totally depends on the use-case. In the drawer menu example this would not be needed at all, as there are invoker buttons present in the UI.
- People, myself included, already have the natural tendency use gestures on interfaces they see and and use on both touch and non-touch devices. I’ve already caught myself multiple times trying to flick away a dialog, use click+drag to move a scroller, or just scroll on desktop to recreate a gesture I know from the touch-device interface.

> On touch you might say that swipe is clear enough, but on desktop (or maybe tablet?) with a keyboard it might not be obvious that there are these actions nor how to get to them.

One thing we could consider here is allow revealing the overscroll gestures by means of the arrow keys. As in: when you’ve focused the main area of an overscroller, pressing the arrows _could_ reveal (and focus) those overscroll areas.

_(However, I’m not convinced of the above yet. At one point I had this in my prototype and it didn’t entirely feel right. This would need some user study and/or exploration of how other platforms currently do it)_

Main point remains that I think people will naturally try these gestures. A parallel I like to draw is with the light dismissal of dialogs: people are naturally trying to click the backdrop or hit the ESC key to close the dialog, without that being expressed in text anywhere. Users who try (or know), find that it works. Users who don’t, just click the dialog close button that the UI provides.

## @vmpstr — 2026-06-25

Just to respond to a few points:

* For screen reader users, I think we have a solution in that we have an aria-action that opens the overscroll area
* For desktop, I think we have a solution in that the majority population (windows with mouse wheel for example) needs to access these areas, and there are convenient `command="toggle-overscroll"` things that the developer can set up in those cases
* For mobile users with mobility impairments, I presume that the user is doing focus navigation whether it's with voice or keyboard. In those cases, I propose we make the overscroll container a tab stop and have it respond to the scroll actions in the same way a scroller would respond to scroll actions. I don't know if there are special shortcuts that we can employ here, since scrolling into pull-to-refresh (or scrolling to swipe-to-dismiss) would be somewhat unexpected.

I do want to mention that so far we've talked only about patterns that already exist on the web. I think we can improve accessibility by default for these patterns, and provide easy tools for developers to make the patterns fully accessible.

## @smhigley — 2026-06-25

I think, summarizing from the discussion, the question I'd be interested in folks' thoughts on is: should overscroll be considered a touch-specific interaction with `aria-actions` broadening that slightly to screen reader users but intentionally not covering access for desktop mouse, voice control, mobility-impaired users, switch, keyboard, etc., or is the goal to automatically enable universal access across all modalities (or as many as possible) by default?

To break down pros/cons (please add any I'm forgetting or that weren't touched on):

## touch-specific utility defined in CSS
This (to me) feels similar to drag/drop events in that it's targeted to exposing one specific type of interaction to web authors.

Pros:
- When authors are doing this correctly and overscroll is just one extra affordance to perform otherwise accessible actions, it's easy and they don't need to manually hide or disable browser-added affordances like the additional button.
- It's lighter and more scoped to spec and implement (and therefore also for authors to understand & code for, with fewer side effects)
- It can be in CSS, which allows it to be enabled via media query

Cons:
- It's easy for authors to code only for overscroll + hover/mouse, leaving out keyboard, switch, voice control, etc. Think something similar to GMail's archive/delete/mark read actions that work with overscroll on mobile, and show on hover on desktop. A company that does less accessibility testing seems (in my cynical view) likely to leave it at hover/overscroll and forget the rest.

These weren't discussed in the call, but occurred to me afterward and are more specific to CSS vs. HTML and not related to touch-only vs. broadly accessible:
- If authors do want do wire up a button with a command to overscroll, having the overscroll element defined in CSS separates where the definition & button association happen, making it less convenient to author and maintain:
```html
<li id="message-item">
  <div class="primary-content">
    Sender: Hello world!
  </div>
  <menubar id="message-actions">
    <menuitem>Archive</menuitem>
    <menuitem>Delete</menuitem>
  </menubar>
  <button commandfor="message-item" command="toggle-overscroll">
</li>
```
```css
/* what happens if someone moves this style to a different selector? */
.message-list li {
  overscroll: light;
}
```
- There are a number of interactive behaviors (dismiss interactions, modal vs. non-modal) that are part of overscroll and relevant when authoring JS to handle the related events. These are much easier to query in JS if defined in HTML.

## broadly accessible feature defined in HTML

Pros:
- Most authors don't think about accessibility beyond the basics, especially not voice control / switch / mobility impairments affecting scroll interactions / etc., and those would be the ones particularly impacted by not having a separate button to invoke.
- Rendering a button out of the box in theory would get authors to at least question why it's there before hiding it, and force some amount of intentionality if they truly have a use case where they do not need the button (acknowledging this can be annoying though)
- Things that affect interactivity are just easier to debug when defined in HTML -- you can target them with a JS querySelector, find them in devtools faster, etc.

Cons:
- Harder to enable this feature based on screen size or touch support, whereas CSS allows this easily via media queries
- If the browser renders or forces you to define a button to make this work, it's an extra step to hide it when you genuinely don't need it. I'm not sure the balance of how many implementations need the button to be accessible vs. how many don't. Email is a good example of not needing it, since users can perform the same actions after opening the email.

## Other options

We could consider explicitly saying this is a touch specific utility, but still keep it defined in HTML, based on the other pros & cons specific to CSS.

I'm also curious what folks would think of keeping the HTML approach but adding an associated CSS property to disable the overscroll behavior. That would keep all the authoring benefits of HTML while also adding the ease of enabling it based on a media query.

## @vmpstr — 2026-07-08

Hey Sarah, thanks for the breakdown.

I discussed this with @bramus (he's on PTO), and I think we align on the following:

During the call and from your comment it became clear that we are discussing more than just the HTML vs CSS opt-in here:

1. Is the button mandatory
2. Default accessibility
3. Should this be done through HTML or CSS

(There was also a 4th question about the name of the feature, but I’m omitting that for now)

To answer your main question right away: I do not want this to be a touch-only solution. The goal is for this feature to be as general as possible. I completely agree with the goal of making it accessible to as many modalities as possible by default.

To respond to the specific points:

**1. Is a button mandatory?**

Currently, the design does not require a mandatory button. However, the button still has its uses for UIs that require it (e.g. the nav drawer case). Authors can easily add them in those cases using the proposed "toggle-overscroll" command.

**2. Default accessibility**

I feel we have a good path forward for most of the input modalities that were mentioned (touch, trackpad, mouse), but we don't have a perfect solution yet for keyboard and voice control on mobile devices.

I think there are improvements possible here. For example, perhaps we could make elements with overscroll regions a tab stop. Then, the overscroll area would become accessible by arrow keys.

**3. HTML or CSS?**

Lastly, how should authors set these areas up? As you mentioned, both HTML and CSS have their own unique pros and cons.

I believe that CSS provides the simplest and most consistent way for authors to be able to adapt their interface based on the device and user preferences of the device being used, which will make it easier for the developer to switch to the best choice for the user.

However, maybe we can settle on 1. and 2. before necessarily cementing the decision for 3.

## @vmpstr — 2026-07-30

The summary of the proposal is roughly the following shape (all names are subject to bikeshed of course):

* Declare a container for the side menu with a new `overscrollcontainer` HTML attribute
* Declare a side menu on some child element of the container with a new `overscrollarea` HTML attribute
* Declare an element with a new `command="toggle-overscroll"` and `commandfor` attribute targeting the overscroll area element

That is the minimal set of attributes to set this up. This creates two snap areas for opening and closing this within the overscroll container, but the position right now remains unchanged. This also, depending on the CSS mode below, takes the element out of flow. 

To control where the menu goes and how it behaves, we have the following:

* CSS positioning properties (e.g. `top`, `left`, etc) position this within the overscroll container's overscroll region
* A new CSS property `overscroll-region-mode` targeting the container (or maybe we want to target the menu, tbd) which selects the mode of the container: `none | overlay | push | flex` or something along those lines. This part hasn't been fleshed out as much yet.

There's a special consideration for inertness here: some modes like `push` and `overlay` likely want to inert the menu when it's closed and inert the other non-menu content when open.
