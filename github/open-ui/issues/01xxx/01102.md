In my mind, the big complication with doing appearance:base for select multiple is that there's not a clear and easy way to represent multiple selected options in the button.

If we follow what browsers already do by having an in-page listbox for select multiple, it would be really easy to go forward with multi selects.

Do most use cases for multi-select have a button? Is it important? If so, what should be in the button?

## @josepharhar — 2025-04-24

Here's my current best strategy for customizable select multiple with popups:
- Require size=1 as an opt-in for select multiple with a popup to solve the mobile vs desktop problem
  - html issue: https://github.com/whatwg/html/issues/8189
  - Here's a table to explain what I mean: https://docs.google.com/presentation/d/10AQxrFI8GIW5q-CYi4mSE4hFK8P3RDGDLWKOdHZb9_A/edit#slide=id.g340018d7cba_1_86
  - This would be a breaking change to `<select multiple>` on mobile, but hopefully it isn't used enough to matter. I'm adding a usecounter to test this theory: https://chromium-review.googlesource.com/c/chromium/src/+/6447294
- Make `<selectedcontent>` for `<select multiple>` clone the contents of all selected `<option>`s in tree order and put their contents next to each other.
  - @argyleink pointed out to me that this could be useful if each option had an icon, you could render all of the icons next to each other for example.
- Don't support putting interactive content inside of the author provided `<button>`, just like we do for single-select.
  - This just means that the author provided `<button>` will still be inert, just like it is for single-select.
  - This doesn't support use cases like the ones in libraries screenshotted earlier in this thread. I'm not sure if those are even considered accessible or not. If people really want to build those, perhaps they can build their own popover and use an in-page customizable select inside of it.
- Maybe add "OK" and "Cancel" buttons to the bottom of the picker in the UA shadowroot of the popover
  - In response to feedback here: https://github.com/openui/open-ui/issues/1192#issuecomment-2795360353
  - Not sure if this is a good idea or not.
  - We could expose them with pseudo-elements for styling purposes, which would also give authors the ability to display:none them and implement their own activation behavior by preventDefault()ing certain events.

> (as it allows us to fix listboxes too)

I am working on a prototype of appearance:base-select for in-page/listbox selects here, I'll post somewhere to ask for feedback on it when its ready: https://chromium-review.googlesource.com/c/chromium/src/+/5893011
