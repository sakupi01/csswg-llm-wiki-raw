## @lukewarlow — 2026-03-09

I'm assuming you're referring to the demos at: https://microsoftedge.github.io/Demos/focusgroup/tablist.html

To clarify, the only behaviour focusgroup itself provides is the arrow key navigation (and some aria role mapping), the activation behaviour of each tab is entirely up to the author to do. As mentioned in This is mention in https://microsoftedge.github.io/Demos/focusgroup/tablist.html#key-point-navigation-vs-selection.

So if you want selection to follow focus you can, if you want it to be a more concious activation choice you can also do that. The purpose of those *Microsoft* demos is to show the kinds of patterns where focusgroup fits rather than being a 100% perfect implementation of each pattern.

Like with other behaviour tokens (e.g. [toolbar](https://open-ui.org/components/toolbar.explainer/) or [menu](https://open-ui.org/components/menu.explainer/)) I imagine OpenUI will tackle tablist (and the tab pattern in general) at the HTML level with dedicated elements. These would be where stuff like this activation behaviour would be decided. I imaging we'd make it so selection *doesn't* follow focus by default perhaps with an opt-in where desirable. But that's out of scope for the focusgroup attribute itself.
