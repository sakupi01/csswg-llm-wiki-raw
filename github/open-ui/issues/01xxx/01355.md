I think this might be an interesting topic to discuss in the (near?) future.

I was wondering how a `<selectedcontent>` should behave when multiple select is set with a `size="1"`

```
<select multiple size="1">
  <button>
    <selectedcontent></selectedcontent>
  </button>
  <option>option</option>
  <option>option 2</option>
  <option>option 3</option>
</select>
```
I like the idea of it outputting every selected option right after each other instead of 2 selected, 3 selected when more than 1 item is selected.

I would not foresee any comma separation for this, as this can probably easily be customized with pseudo-elements.


```
<select multiple size="1">
  <button>
    <selectedcontent></selectedcontent>
  </button>
  <option><div class="wrapper">option</div></option>
  <option><div class="wrapper">option2</div></option>
  <option><div class="wrapper">option3</div></option>
</select>
```

```
selectedcontent .wrapper::after {
  content: ',';
}
```

I thought this was a good idea, but other suggestions are more than welcome. It should at least be looked into.

## @mkrause — 2026-02-02

A few more thoughts on this:

Having (the DOM state of) `<selectedcontent>` be 1:1 with what the browser displays by default seems to defeat the point of this element in the case of customizable multi-select, given that the user is opting to customize the display but now does not have the information available necessary to customize this beyond some browser default (and language-dependent) string.

I'm wondering whether the (default) _presentation_ of `<selectedcontent>` needs to match the DOM contents. I could imagine some kind of CSS opt out to display the contents of the DOM instead. This would have accessibility implications also though, I'm not sure whether this is a good idea. Also: the `appearance: base` essentially _is_ the opt-in to take control over the styling already, so adding another layer of opt in seems unnecessary (although: see the situation with the separate select `::picker` opt-in).

Lastly, I wonder if there is a way to just make the default styling work better. For example: would it make sense to not just concatenate the selected `<option>` contents, but instead wrap in each in some wrapper element out of the box. This would open up doors for UA styling to provide a better default (if needed even some kind of magic `content: -ua-default-selected-content` override to get the "N selected" string back).

Maybe:

```html
<select multiple size="1">
  <button>
    <selectedcontent> <!-- DOM state: -->
      <option>option 1</option>
      <option>option 3</option>
    </selectedcontent>
  </button>
  <option selected>option 1</option>
  <option>option2</option>
  <option selected>option3</option>
</select>
```

Using `<option>` here again is probably a bad idea (will existing parsers read these as an `<option>` of the `<select>`?), and this is now inconsistent with single-select. But just throwing it out there

EDIT: Yeah, using `<option>` for this wrapper won't work. Firefox (v147) for instance will parse the `<option>` from inside the `<selectedcontent>`.

## @sb3nder — 2026-02-11

the `wrap` keyword does not sound good to me. it already has an established meaning in html and css, and this feels slightly different. that might be confusing.

also, showing all the selected options feels like the more common use case to me.

instead of controlling this via `wrap`, I was thinking about a few alternative patterns:

1. remove the behavior of showing the number of selected options from `<selectedcontent>`.
2. make the "show number of selected options" behavior opt-in via an attribute.
3. expose something in CSS (like a variable or function) that gives the localized count text, for example `"2 items"`.

---

### elaborating more on (1)

if `<selectedcontent>` is associated with `<select multiple>`, it wraps each selected option's content in a `div` and concatenate them.

(even if they aren't wrapped, I can always add a wrapper if I need one.
Or, for example, if I only need a comma, I can place a hidden `<span class="break">,</span>` in `<option>` and show it when in `<selectedcontent>`.)

## showing all the selected options
a placeholder could be done like:
```css
selectedcontent:empty::before {
	content: 'placeholder';
}
```

I also note that some people will add multiple content versions inside `<option>` for different uses, for example:

```css
select selectedcontent .show-in-opt,
select option .show-in-button,
select .show-out {
	display: none;
}

#out .show-in-opt,
#out .show-in-button {
	display: none;
}
```
```html
<selectedcontent for="select" id="out"></selectedcontent>
<select id="select">
	<button>
		<selectedcontent></selectedcontent>
	</button>
	<option>
		<span class="show-in-opt"></span>
		<span class="show-in-button"></span>
		<div class="show-out" aria-="" tabindex=""></div>
	</option>
</select>
```

## showing the number of selected options
I believe that for `appearance: auto`, and `appearance: base` when `<button>` is not specified, the text is in the language of the UA and cannot be changed by developers.

if devs want to localize or change the wording, they could use `appearance: base` and then generate the count in CSS.

for example, using counters:
demo: https://codepen.io/sb3nder/pen/vEKMrze
```html
<button>
  <selectedcontent></selectedcontent> Selected
</button>
```
```css
selectedcontent {
  counter-reset: child-count 0;

  &::after {
    content: counter(child-count);
  }

  & > * {
    counter-increment: child-count 1;
    visibility: hidden;
    position: absolute;
  }
}
```
[EDIT] Realized that `counter()` alone does the job, no need for `sibling-count()` or `children-count()`.
