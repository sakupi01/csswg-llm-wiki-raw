A toolbar is a way to group related controls together and provide users quick access to commands. There is no dedicated `<toolbar>` element in HTML today; developers instead rely on generic containers like `<div>` with ARIA roles and JS to handle navigation. This proposal introduces a native `<toolbar>` element to give authors a semantic, accessible way to do this.

Toolbars are a common pattern across platforms. A standard element will make them easier to implement consistently on the web, while mapping directly to existing ARIA concepts. This helps assistive technology users understand relationships between grouped controls, and navigate between them more efficiently.  

**Use cases:**  
- The formatting toolbar in a document editor (bold, italic, underline, font family).
- The main command toolbar in a drawing or photo editing app.
- A simple toolbar with a search field and filter buttons in a catalogue.

### Proposed design  

At a high level, this proposal lets developers:  
1. Use `<toolbar>` to group a set of interactive controls.
2. Expose accessible grouping and navigation consistent with ARIA `toolbar` behaviour. 


See APG: https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/

## @lukewarlow — 2026-03-06

So firstly it's highly recommended that you only put key conflicting elements as the last element within the focusgroup, in which case the conflict isn't as bad.

But focusgroup does have handling for this. https://open-ui.org/components/scoped-focusgroup.explainer/#key-conflict-elements - specifically it gets special treatment, if you're focused on it pressing tab takes you to the next focusgroup item (or leaves the focusgroup if last) and pressing shift + tab* takes you to the previous focusgroup item.

* (currently it seems to take you back to the start of the focusgroup but I think that's a bug I need to report).

## @emilio — 2026-03-06

Ok that seems reasonable, I think, but maybe not ideal...

For a concrete example: Firefox's toolbar has the urlbar in it (plus potentially other items, and other textfields like e.g the searchbar). Right now the behavior when you tab around the browser UI is, I think, almost but not quite what you describe:

 * First you focus the first toolbar button. You can move between them with the arrow keys, but you can't "jump" to the text field with the arrow, you need another tab press.
 * When you're in the urlbar, arrows don't move focus around (good).
 * When you tab again, it goes to the next "group", which you can again move around with the arrow keys.

I think the key difference is that you can't focus the textfield with the arrow keys. I think that's a bit better because if pressing right arrow would take you to the textfield, you'd expect pressing left arrow to take you back to where you were (and vice versa). I think this way left / right arrows and tab / shift+tab are symmetric.

I think focusgroup should probably behave similarly? (or maybe it does and I misread your link... It seems the link you gave deals with escaping the `<input>` when it's already focused, but wouldn't deal with preventing focusing the input, right?)

Are there any examples that behave like focusgroup? Might be worth to do some research there to see if there's some common precedent across platforms... It's very common to have searchfields in headerbars / toolbars (Google Docs has one, the windows task manager too, I think Matlab as well, probably office though I haven't used it in ages...)
