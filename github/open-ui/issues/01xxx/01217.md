Multi-select popups have some variations for committing the chosen options and closing the picker:
1. "OK" and "Cancel" buttons are both included in the popup.
    - Activating an option does not commit it until the "OK" button is pressed.
    - Pressing "OK" closes the picker and commits the selected options.
    - Pressing "Cancel" does not commit anything, effectively reverting changes.
    - [This is how the native select multiple popup on android works](https://drive.google.com/file/d/1cyMWPK5YksrR2TZwDINuQDjQifM7gCH5/view?usp=sharing).
2. Only a close button is provided.
    - Activating an option commits it immediately.
    - Pressing the close button closes the picker, just like light dismiss by clicking/touching outside the picker.
    - [This is how the native select multiple popup on iOS works](https://drive.google.com/file/d/1dR0KWb8Q87aoNwjNHvIahaoTHV4zsxH3/view?usp=sharing).
3. No buttons provided.
   - Activating an option commits it immediately.
   - Picker can only be closed by light dismiss or clicking on the invoker button.
   - This is how the select multiple popup in issues.chromium.org works (see the "OS" label on any bug)

Not providing any buttons would be the easiest to implement and standardize.

If we provide buttons automatically in the UA shadowroot of the select's picker, should we make it configurable to switch between option 1 and option 2? This would require more work.

~~In my opinion, implementing option 2 would be the best since it's not too hard to implement and customize and provides good defaults/affordances.~~

In my opinion, option 3 is the best because it ensure that light dismiss commits options, raises less questions to me about how to implement the accessibility mapping of the popup element, doesn't require us to implement and standardize additional buttons, and should still make it possible for authors to implement their own buttons if they want them.

## @josepharhar — 2025-06-03

Some reasons to not provide ok/cancel buttons (option 3):
- Users may expect light dismiss to commit the options
  - If there is an "ok" button, then the user has to press it in order to commit the options, and light dismiss doesn't commit them.
  - I have ran into this issue with the time picker on android, it took me many attempts to learn.
- Developers can still add these buttons if they want them
  - It might be a little challenging to add an "ok" button which must be pressed in order to commit the options. It would probably be easiest to revert the changes if the picker is closed in other ways besides the "ok" button.
  - We could by default not fire a change event until the picker is closed anyway, but still fire input events every time the user clicks an option.

## @josepharhar — 2025-06-12

From the discussion with @keithamus in the joint meeting, it sounds like some authors will definitely want to have ok and cancel buttons, and customize light dismiss behavior to do things like prevent light dismiss entirely, make it cancel the changes, or make it commit the changes.

It sounded to me like we have 3 paths forward to address this:
- Build the buttons and behaviors into the browser, and add attributes to control the behaviors.
- Provide a way in the markup to put buttons before or after the listbox of options in the picker, so that the author can provide their own buttons and then hook up their own behaviors to those buttons.
- Don't work on select multiple with a picker for now and focus on shipping customizable select in-page (listbox mode) so that authors can build their own pickers and use customizable select in listbox mode inside their own picker.

Keith mentioned that sites will want to put lots of stuff in their pickers other than ok/cancel buttons, like a text input to filter, which is a reason not to build all the different modes/behaviors into the browser. Does all this sound right Keith?

## @josepharhar — 2025-12-16

Some questions:
- should the close button be keyboard focusable?
   - if it isn't then keyboard users will just have to know to press the escape or tab keys to close the picker, unless we add behavior to other keys
- should the picker have a dialog mapping since there is more content in there than just options?
- how should we style the close button? should it look like it comes before or after the options? can we use styles which make it easy for developers to move the close button around/before/after the options?
- what should be in the close button? text that says "ok" or "close" and is internationalized by the browser? an "x"? an emoji?
- can we make it easy for developers to replace the contents of the close button?
  - maybe we could use the content property?

Some suggestions:
- the close button should not be keyboard focusable in order to make the keyboard behavior better match single-select, and because it is a pseudo-element
- it would be easier to make the picker have a dialog mapping in order to account for the close button because we shouldn't have a button inside of a listbox, so im leaning that way, but maybe it should just be listbox in order to match single-select and the close button shouldn't be included in the a11y mappings to make it acceptable for it to be a listbox, but maybe that would make it weird to use with screen reader... I'm leaning dialog.
- the close button should come after the options to match what i think most pickers look like
- the close button should say "ok" and be translated by the browser. maybe a checkmark would be ok as an emoji, but i can't think of anything else
- if we use an emoji then it should be replaceable by the content property, otherwise not be replaceable since the content property doesn't work on elements which have text content

Since Luke's react-aria example has no button, and there are so many open questions and limitations about how the close button might work, I'm now convinced that we should move forward with no ok/cancel buttons at all.

With customizable listbox, it is easy to build your own picker with ok/cancel buttons like this: https://codepen.io/jarhar/pen/ZYOWzEy

Proposed resolution: Don't include any ok, cancel, or close buttons in customizable select multiple popup.
