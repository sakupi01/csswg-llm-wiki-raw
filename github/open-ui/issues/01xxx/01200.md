During yesterday's telecon, @domfarolino had a very interesting comment at the end concerning the discussion of how to handle menuitems that behaved as hyperlinks, overtly declaring he was opposed to allowing `href` on `menuitem` elements.  The brief details seemed related to parsing/security (please correct me if i misunderstood).   But that less than a minute mention gave a lot of context to why we kept having to retread the questions about why hyperlinks shouldn't be nested inside of menuitems.  That got me thinking...

- If `href` being an allowed attribute to `menuitem` is a no go...
- And nesting hyperlinks within `menuitem` elements is also a no go. (in case it wasn't clear - i'm very much opposed to that as well. it flys in the face of ARIA and HTML best practices - that is except for the summary element which is an example of HTML contradictions and i will stop myself before i rant... )
- That means both of those options are a waste of time to discuss further.


That got me wondering about how to allow instances of menuitems that do need to be able to act as a hyperlink, but shouldn't _need_ to have authors use JavaScript when there is already a native way to markup hyperlinks.

I assume it's not just href - but _any_ attribute that would for a URL as its value is a non-starter.  Additionally, it wouldn't even just need to be href, but other hyperlink attributes that would be needed for menuitem as well.  target, download, maybe others.  I understand the complexity this would add, for what did seem such a simple solution when not considering the bigger picture.

So what if we just allowed hyperlinks as children of menulists?  As we briefly touched on yesterday, that'd be quite odd - especially if a menu contained both menuitems and hyperlinks.  It'd be strange to introduce the new elements and then be like - oh but for this use case, use this very old element instead.... but that got me wondering more..


## skip all the preamble, here's the proposal

What if we drop the idea of adding menuitem elements in this proposal, and instead just use `<a href>` and `<button>` elements (which would default to `type=button` when a child of a `menulist/bar`.

The rational here being that this is not actually dissimilar to what some people are doing now to create custom ARIA menus.  

```
<div role=menu>
  <button role=menuitem ...>foo</button>
  <a href=lol.html role=menuitem ...>bar</a>
</div>
```

The key difference here would be that the browser would automatically handle the implicit roles of the `a` and `button` elements - converting them to `role=menuitem` in the accessibility tree.

While there should be some unification in the UA styling of these elements when used in this context, arguably they could have _some_ visual distinctions to help indicate one will perform an action (button) and one will likely navigate you somewhere (hyperlink).
These elements could then reuse their default high contrast styling - as they have coloring variations to help high contrast theme users know the difference - rather than needing to repeat or create new styles for `menuitem`.  

This doesn't necessarily solve for everything we we've been discussing.  But maybe it can help with the differentiation of when an item is really meant to be a hyperlink vs action.  It does also mean there's one less element to need to propose - particularly one that uniquely comes with interesting history and truly, would technically be performing redundant functions to the existing hyperlink and button elements...

looking forward to hear thoughts on this here or when we can talk about this during an upcoming meeting.

## @domfarolino — 2025-04-24

We talked about this internally, and we do like the proposal; specifically I think it solves the anchor/link discoverability problem for accessibility technology pretty neatly, which is nice. One tradeoff we lean towards is not allowing normal `<button>`s to be nested in `<menulist>`s, and instead stick with the new `<menuitem>` element and its `<fieldset>`/checkability machinery. Something _new_ feels easier to integrate with the menu-specific use case, instead of stripping down and overwriting certain parts of the existing button processing model in a way that feels a little magical just because it happens to appear inside a menu. There are further complexities with `<button>` and its default appearance, and overall I think a lot of the complexity can be side-stepped with the middle ground of indeed allowing anchors inside menulists, and allowing menuitems as well.

One remaining accessibility issue that is not immediately worked out by this proposal is what we discussed on the last telecom about "dual accessibility roles", right? My understanding is that if you're using accessibility technology in application mode, and you come across a `<menulist>` with anchor tags in it that's intended to be a navigation menubar, if we don't make the menu's role `"navigation"`, then AT may skip over the whole menu when looking for navigation-related components. So while this fixes the anchor tag discoverability issue, I think we still need to tread lightly and figure out how to ensure a menu with anchor links in it doesn't continue to have the wrong role. @scottaohara let me know if my understanding of this issue is sound.

reasons i dont like reusing `<button>`:
