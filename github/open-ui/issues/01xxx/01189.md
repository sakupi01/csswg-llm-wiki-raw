The explainer still has two alternative concepts in it:
1. `<menuitemcheckbox>` and `<menuitemradio>`
2. `<menuitem checkable>` with `<fieldset checkable=single|multiple>`.

I think that we are leaning towards option 2. Does anyone disagree?

Should `<menuitem>` need a `checkable` attribute or is being inside a `checkable` fieldset good enough? In other words, should we allow mixing checkable and non-checkable menuitems inside a `<fieldset checkable>`?

Should the default value of `<fieldset checkable>` be `checkable=single`?

## @scottaohara — 2025-04-10

>One thing is this would change the aria role based on its location in the DOM and the state of its parent. is there precedence for doing that?

oh is there.... there are a number of elements that have 'contextual roles'.  this is largely related to structural markup elements (or - you might think of them under the Sections and grouping content element categories).

but more to your point, this is taking that concept a bit further, but imo, in a way that could improve the authoring experience and reduce author error.

e.g., it's a lot simpler to just declare menuitem elements, and then when needed put them into a group with attributes that refine their behavior / change their role to match (but at least still in the same menuitem category).  A lot easier than having to both define the group to identify boundaries, and then add that attribute to each and every menuitem element (without forgetting one) OR introduce the other 2 variant menuitem elements.


Fwiw, i really like the idea of reusing the multiple attribute, rather than having to define values for checkable.

## @smaug---- — 2026-08-27

Are there concrete examples where devs have created menus (maybe using some JS libraries or native APIs) with some badly constructed radio groups?

Single checkbox-y things are common and fine, and they don't need grouping so fieldset around such is just overkill.

I would expect that by far the most common case when a radio group is needed, there is only a single group inside a submenu, in which case submenu itself could do the grouping (all the type=radio menuitems would be part of it).  If we want to prevent bad usage there, like non-radio menuitems between same-group radio menuitems, we can do that just by making the whole radio group disabled or  "being-in-invalid-state". No need to force everyone to create overly complicated HTML structures when a simple one works fine.

## @dbaron — 2026-09-08

@smaug---- (and others) What do you think about the following alternative solution (with naming choices tentative) for checkbox/radio menuitems, which at a high level moves *half* of the radio/checkbox decision from an attribute on `<fieldset>` to an attribute on `<menuitem>`:

1. Introduce the `checkable` attribute on `<menuitem>`.  By default this creates a menuitem with "checkbox" semantics, i.e., no interaction with other items.
2. Reduce the `checkable` attribute on `<fieldset>` to just `checkable=single`.  (Any other values of `checkable` are ignored.)  Inside of a `<fieldset checkable=single>`:
   1. Any `<menuitem checkable>` aquires "radio" semantics rather than "checkbox" semantics, with the `<fieldset>` being the grouping element.
   2. Any `<menuitem>` without the checkable attribute is an authoring conformance error, and becomes `disabled` as an error handling mechanism.
3. Optionally, we could also add `checkable=single` to `<menulist>` with the same semantics as `<fieldset>`.
