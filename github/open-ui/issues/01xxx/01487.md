To design interest invokers, we have currently invented a parallel set of attributes with `interestfor` instead of `commandfor`. But essentially, interest invokers are just command invokers with a different set of events for the trigger. But re-using the same set of attributes would mean they cannot be combined on the same element, a common need.

But we'll run into this again. E.g. more triggers have already been proposed: keyboard shortcuts, overscroll, value changes (#1359), etc. 

Instead of ad hoc copying the API for each case, which doesn't scale, what if we generalize it in a way that allows:
1. customizing the trigger
2. attaching multiple commands to the same element (this also allows multiple regular commands, for which there are use cases!)

I'd propose a `<command>` element:
- The invoker is implicitly the parent. Later, we can introduce an additional attribute to specify a different invoker (either on the `<command>` or the invoking element), allowing for declarative reusable commands.
- An attribute (`action`? `value`?), analogous to `command`. Possibly defaulting to `toggle-popover` to provide similar DX as today's interest invokers?
- A new attribute for the trigger, e.g. `type="click | interest"`. Singular value at first, later multiple values can provide multiple triggers if use cases emerge.
- `for` as an equivalent of `commandfor`. Later, we could expand the syntax to produce dynamic targets for multiple different invoking elements.

I think this provides a lot more flexibility and room to grow with only marginally additional verbosity (and existing syntax can remain as a shortcut):

<table>
<thead><tr><th>Today</th><th>With <code>&lt;command></code></th>
<tr>
<td>

```html
<p>Some text with a <a href="#" interestfor="mypopover">link</a>.</p>
<p id="mypopover" popover>A short preview with some quick info</p>
```

</td>
<td>

```html
<p>Some text with a <a href="#">link <command type=interest for=mypopover></command></a>.</p>
<p id="mypopover" popover>A short preview with some quick info</p>
```

</td>
</tr>
<tr>
<td>

```html
<button commandfor="mypopover" command="toggle-popover">
  Toggle the popover
</button>
<div id="mypopover" popover>
  <button commandfor="mypopover" command="hide-popover">Close</button>
  Popover content
</div>
```
</td>
<td>

```html
<button>
  <command for=mypopover></command>
  Toggle the popover
</button>
<div id="mypopover" popover>
  <button>Close <command action="hide-popover" for="mypopover"></command></button>
  Popover content
</div>
```

</td>
</tr>
</table>

I think this offers **a lot** of room to grow, for example:
- Additional triggers, or even **custom triggers**, analogously to custom commands!
- Conditional attributes ike `media`
- Many actions require additional parameters, it's trivial to expand to that
- `<command>` elements would be hidden by default per the UA stylesheet, but if visible, they can be used as click-targets, providing a way to create interest buttons, feeding two birds with one scone!


WDYT?

As you first think about it, `interestfor` and `commandfor` sound exactly analogous to each other. Indeed, [my initial proposal](https://github.com/openui/open-ui/issues/767#issue-1753136462) (from way back when) was to just add a `"hover"` value to `popovertargetaction`. It was renamed, and [that's the origin of "interest"](https://github.com/openui/open-ui/issues/767#issuecomment-1654177227). However, we subsequently removed that value, because it doesn't fit for a number of reasons. You mentioned one of them: a common use case is to want *both* of them on the same element. However, more importantly, there are a number of issues and footguns:
- `interestfor` doesn't have an equivalent of `command`. You can show interest in something, and you can lose it, but there's no way to change what action happens on that target element. That's [not an oversight](https://open-ui.org/components/interest-invokers.explainer/#why-no-interestaction-attribute).
-  `command` is only supported on buttons, because it is triggered by activation. `interestfor` is supported on more things, like links, because it can live alongside something that already has an activation behavior.
- There are [CSS-based delays](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/interest-delay) associated with `interestfor` that don't have any meaning for `commandfor`. We could generally add them and ignore them for "`commandfor`-like-`<command>`s" but likely (to generalize!) we'd call them "command-delay" or something, which would be more confusing.

I strongly suspect that when it comes time to make a general API work for keyboard shortcuts, overscroll, or any of the rest, you'd discover all kinds of similar asymmetries that you'd have to work around. E.g. the `shortcut` attribute for keyboard shortcuts only applies to "keyboard shortcut commands". In the end, you will have simply relocated and renamed the attributes, from the element itself to an ancestor `<command>` element.

> But we'll run into this again. I'd like to understand more about why it doesn't scale. There's no limit on the number of attributes an element can have. Generalizing sounds nice from a platform perspective, because "the one thing" is easier to find in documentation. But I think it might be harder to use and understand in practice. Separate attributes for separate behaviors feels (to me at least) easier to understand and use.

I'm reminded of the effort to "generalize" popover transitions. In my initial proposal, this was how you did that:

```html
<style>
  [popover] {
    opacity: 0;
    transition: opacity 0.5s;   /* <--- one line of CSS  */
  }
  :popover-open {
    opacity: 1;
  }
</style>
```

Now, instead, there's a [complicated set of four CSS APIs](https://open-ui.org/components/popover.research.explainer/#animation-of-popovers) that have to be used just-so, or you shoot yourself in the foot. Indeed, see [our huge blog post](https://developer.chrome.com/blog/entry-exit-animations) that tries to explain how to use these APIs. Personally, I think the snippet above is self-explanatory and wouldn't have needed a blog post at all. "But it's general!" Yes, it's now possible to transition `<dialog>` (but not fullscreen!) with that same complicated CSS blob, and that sounds like a benefit. But I think we likely could have instead just found a way to just make the above magic also work for `<dialog>` without all of the developer pain of the "general" solution we invented instead.
