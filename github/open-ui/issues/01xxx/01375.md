See this issue for context:

https://github.com/w3c/csswg-drafts/issues/13520

Apple strongly feels that the default roundedness needs to change, and they'd like to discuss this issue with more designers in OpenUI.

<!-- comment id=3928382337 author=fantasai created=2026-02-19T16:32:12Z url=https://github.com/openui/open-ui/issues/1375#issuecomment-3928382337 -->
## @fantasai — 2026-02-19

More specifically, Apple feels strongly that the default styling of `appearance: base` controls should be good enough to use in production for a basic website, and that the current styling of selects (where the button is rounded and the picker attached below it is square) is too weird to be usable without additional styling.

<img width="220" height="104" alt="Image" src="https://github.com/user-attachments/assets/2c6b1742-6b07-4732-ab73-dcf2c45f4a86" />

So the question for OpenUI is: would you use this in a production website as-is? If not, what about the default styling should we tweak to make it acceptable?

There are some ideas in the original issue, and we're also open to more ideas. But mostly we wanted to hear from designers what they think.

CC @thebabydino

## @thebabydino — 2026-02-20

Yes, that looks weird.

First change I would  make:  consistent `border-radius` for both. Whatever that `border-radius` is. But not one very rounded and one very square. My personal preference would be for both to get a smaller `border-radius`.

Second change I would make: unhide that `:focus` outline. Just do something so it's not under the picker. Add a tiny bit of space between the button and the picker. Place whichever of the button/ picker has focus on top. The old school approach of giving  the outline a negative `outline-offset` so it's contained within the `button`.

Considering the double border discussion though, place whichever has focus on top is out.

Also, how about also adding a `border-inline-start` of `3px` using the `accent-color` value on `option` elements on `:hover`? Might be a more obvious hover indicator that just the background.

## @sb3nder — 2026-02-26

Another thing I would like to hear your thoughts on is the `:focus-visible` outline.

[WCAG22 2.4.7 Focus Visible AA](https://www.w3.org/TR/wcag22/#focus-visible) says:
> Any keyboard operable user interface has a mode of operation where the keyboard focus indicator is visible.

But I wonder, how does one evaluate that it's actually visible?

Fwiw, there's a **AAA** criterion about this: [WCAG 2.2 2.4.13 Focus Appearance](https://www.w3.org/TR/wcag22/#focus-appearance), which says:
> When the keyboard focus indicator is visible, an area of the focus indicator meets all the following:
> - is at least as large as the area of a 2 CSS pixel thick perimeter of the unfocused component or sub-component, and
> - has a contrast ratio of at least 3:1 between the same pixels in the focused and unfocused states.

## @sb3nder — 2026-02-26

@lukewarlow As far as I remember, `outline-offset` behaves differently across user agents:

With `outline-offset: 0px` and `outline-style: auto` (the user agent outline):
- Chrome: `-1.5px` offset.
- Firefox: `0px` offset, except when it's hard-coded then it is fixed.
- WebKit: `2px` offset, except when it's hard-coded then it is fixed.

With `outline-offset: 0px` and `outline-style: solid` (or other explicit styles):
- Chrome: `0px` offset.
- Firefox: `0px` offset.
- WebKit: ~~`2px`~~ `0px` offset.

In an ideal world, ~~the offset would be part of the outline shorthand, and~~ each user agent would define its value explicitly.
That way, we could set something like `outline-offset: -2px` for `<option>` in the base styles and rely on consistent behavior... but perhaps that's just wishful thinking.
