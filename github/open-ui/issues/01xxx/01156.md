Currently the [openable explainer](https://open-ui.org/components/openable.explainer/) uses a defaultopen attribute.

This was based on the previous proposal for initially open popovers. Naming aside does it make sense to be a separate attribute here, or should an alternative approach be taken?

<!-- comment id=2660999953 author=lukewarlow created=2025-02-15T16:46:54Z url=https://github.com/openui/open-ui/issues/1156#issuecomment-2660999953 -->
## @lukewarlow — 2025-02-15

What if we want a way to define initially open openables and then in future we also want to do the same for popover, the two will conflict and we'll have to decide which one wins.

Perhaps it's good that they'd conflict because if we had a separate mechanisms and both were used we'd still ultimately have to define a winner (or perhaps both should lose?).

<!-- comment id=2721668821 author=sorvell created=2025-03-13T15:29:27Z url=https://github.com/openui/open-ui/issues/1156#issuecomment-2721668821 -->
## @sorvell — 2025-03-13

Some related points and questions:
* is this only for the initial state? Having a property based API is pretty nice for declarative frameworks which can more easily set properties than call methods.
* given `<dialog popover=... openable>`: my understanding is that popover provides extra functionality v. just `<dialog>` but does openable?
* given `<div popover=... openable>`: is popover basically a superset of openable and if so, should it win out?
* if the functionality is mostly duplicative perhaps with the most capable mode winning out, since `<dialog open>` exists, `open` could just be used in lieu of `defaultopen`; however, `<details open>` means "open contents" which is different from openable's open.
* if `open` could otherwise be used and `<details>` is the only outlier, perhaps it could/should not support `openable` and `open` could then be used instead of `defaultopen`?

<!-- comment id=2721753342 author=lukewarlow created=2025-03-13T15:54:09Z url=https://github.com/openui/open-ui/issues/1156#issuecomment-2721753342 -->
## @lukewarlow — 2025-03-13

It's only an attribute for initial state, we're definitely not doing state reflection to an attribute. That being said we can possibly have a *property* that can be used instead of methods. But I suspect it should be methods because it will probably do various things (such as maybe setup focus ordering and stuff).

<!-- comment id=2722091104 author=mfreed7 created=2025-03-13T17:25:18Z url=https://github.com/openui/open-ui/issues/1156#issuecomment-2722091104 -->
## @mfreed7 — 2025-03-13

Seems to me that a content attribute should be the way to go here, which specifies only the **initial** state (timing needs to be defined carefully) of the openable. And I do have somewhat strong views on the name, that it should be `initiallyopen`. The word "initially" concretely says what it does. The word "default" is somewhat close, but doesn't imply anything about timing.

Side note: content attributes usually always have to reflect to IDL, so it'll need a `div.initiallyOpen`. And that's why the timing needs to be carefully designed - does setting that on an element and then inserting it into the DOM cause it to be open?

<!-- comment id=2722125438 author=lukewarlow created=2025-03-13T17:33:58Z url=https://github.com/openui/open-ui/issues/1156#issuecomment-2722125438 -->
## @lukewarlow — 2025-03-13

I think yes we'd need an element insertion steps to account for setting it before inserting.

I also agree on the name fwiw. I was going for the bad name first change later approach.

I think my main concern is around clashing with popover.

I also think the reason initially makes more sense than default is because it's not "resettable" like the default value is on form elements.
