If the intention is to limit the behavior of `focusgroup` strictly to focus navigation, without any concept of activation or triggering commands on the child elements, I would strongly suggest removing the `"tablist"` behavior token.

Especially for beginners, this naming is confusing and frustrating.

Initially, attempting to use the [ARIA `tablist` role](https://developer.mozilla.org/de/docs/Web/Accessibility/ARIA/Reference/Roles/tablist_role) had no effect.

Then `focusgroup="tablist"` appeared promising, but it only implements a small part of the expected behavior.

In practice, it is technically just shorthand for `focusgroup="inline wrap"`

All remaining aspects of a tablist interaction still need to be implemented manually. 
Because of this, the `"tablist"` behavior token implies functionality that is not actually providedd.

The name `"tablist"` strongly implies behavior aligned with the [ARIA tablist pattern](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Reference/Roles/tablist_role)

Authors encountering `focusgroup="tablist"` may reasonably expect that it assists with:

* activating tabs
* managing the selected state
* coordinatin tab panels

Since none of this functionality is provided, the token name may lead developers toward incorrect assumptions.

## Proposal: Remove the `tablist` behavior token

If the intention of `focusgroup` is to remain strictly limited to focus navigation, I suggest to remove the `tablist` and actually most of the other behavior tokens. 

Ideally limit the set of tokens to directional cues, wraps and memory.

This would avoid implying support for a higher-level UI pattern that the feature does not actually implement.

## Alternative Integrate `focusgroup` with `invoker commands`

Integrate `focusgroup` with `invoker commands`

If `focusgroup` were able to trigger invoker commands when focus changes, it could enable a declarative tab pattern.

```html
<div focusgroup="inline invoke">
    <button focusgroupstart commandfor="tabpanel1" command="toggle">Tab 1</button>
    <button commandfor="tabpanel2" command="toggle-openable">Tab 2</button>
    <button commandfor="tabpanel3" command="toggle-openable">Tab 3</button>
</div>

<div id="tabpanel1" openable defaultopen name="tabs"></div>
<div id="tabpanel2" openable name="tabs"></div>
<div id="tabpanel3" openable name="tabs"></div>
```
In such a model:

- `invoke` would trigger commands when focus changes
- panels would be [`openable`](https://open-ui.org/components/openable.explainer/)
- a shared `name` could enforce mutual exclusivity in `openable` elements , similar to the `details` pattern (see https://github.com/openui/open-ui/issues/1163)
- styling could rely on yet to define pseudo-classes for invoker (see https://github.com/openui/open-ui/issues/622)

This would allow tabs to be expressed declaratively without JavaScript.

## @g12n — 2026-03-11

@lukewarlow This is why I suggested an `invoke` keyword for the `focusgroup` attribute. This is related to https://github.com/openui/open-ui/issues/1030 where @flackr used a similar keyword for the same behaviour. 

If you want to archive a tab-like behaviour with **manual activation** you would simply omit the keyword. 

So instead of `focusgroup="inline invoke"` you would write `focusgroup="inline"`

```html
<div focusgroup="inline">
    <button focusgroupstart commandfor="tabpanel1" command="toggle-openable">Tab 1</button>
    <button commandfor="tabpanel2" command="toggle-openable">Tab 2</button>
    <button commandfor="tabpanel3" command="toggle-openable">Tab 3</button>
</div>

<div id="tabpanel1" openable name="tabs" defaultopen></div>
<div id="tabpanel2" openable name="tabs"></div>
<div id="tabpanel3" openable name="tabs"></div>
```
This way you can opt in to the "automatic activation", the markup is really readable. 

And the main point remains: instead of `tablist` I would prefer `inline wrap invoke` to lower the expectation, especially of new developers, to the level that matches the real goals and behaviour of the property.

## @g12n — 2026-03-11

Automatic roles are plagued by the same shortcomings as aria roles themselves: without additional code they don't provide a meaningful behavior. 

That's why there is the saying ["No ARIA is better than bad ARIA."](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA#before_using_aria). The same rule that applies to JavaScript is true for the native attribute:

If is doesn't provide the correct behavior it should not set the role. 

If code is needed to provide the behavior this code can (and should be the only one to) set the role.

## @g12n — 2026-03-11

@janewman I understand the reasoning. And the impatience – trust me: I am waiting for that for ages as well. 

But communicating to the screen reader something can cause more trouble, if it's done before it is clear that the elements behaviour matches the users expectation.

For APGs that specify only the  the focus behaviour like the [toolbar](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/) there isn't much of a problem. 

But if the APG specifies *selection* and/or *activation* of child element, like the [listbox](https://www.w3.org/WAI/ARIA/apg/patterns/listbox/), the [radiogroup](https://www.w3.org/WAI/ARIA/apg/patterns/radio/) the [tablist](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) pattern, prematurely telling the screen reader role can cause the same harm as a prematurely placed ARIA-Role.

The gap between expected developer experience and real results is one of the reasons why a11y and especially ARIA is deemed so complicated by many developers.  

To complete the expected bahavior you have two promising Proposals in the queue:

1. the [Openable API](https://open-ui.org/components/openable.explainer/)
2. the future versions of [Invokers](https://open-ui.org/components/future-invokers.explainer/)
