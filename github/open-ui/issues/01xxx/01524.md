The prototype uses `::slider-thumb(n)`, `::slider-thumb(*)` and `::slider-segment(n)`. Segments are numbered by position; thumbs are undefined.

## Questions

- **Stability:** inserting a thumb renumbers the ones after it, so styles jump to another input. Acceptable?
- **State:** styling a disabled thumb today needs `rangegroup:has(input[name=x]:disabled)::slider-thumb(1)`. Should thumbs match their input's state directly (`::slider-thumb(*):disabled`, `:focus-visible`)?
- **Syntax:** is `(*)` needed, or does bare `::slider-thumb` mean all thumbs? Allow `An+B`?

## Suggestion
`n` = DOM order, segments stay positional, and thumbs match their input's pseudo-classes.

## @anaskim — 2026-10-26

Selecting one thumb by a positive integer should be straightforward to implement. The user agent already needs an ordered participant list to generate the thumbs, so `::slider-thumb(1)`, `::slider-thumb(2)`, and so on can match against that one-based index. Insertion, removal, or reordering would invalidate and renumber the affected generated pseudos.

A full `An+B` microsyntax also looks technically feasible, but it does add complexity. I don't currently see a strong enough authoring benefit to require that it in v1 because most examples can style every thumb with bare `::slider-thumb` and override a small number with integer indexes.

My preferred surface would be:

- bare `::slider-thumb` matches all thumbs;
- `::slider-thumb(<positive-integer>)` matches one thumb;
- omit `::slider-thumb(*)`, because it's a duplicate form;
- defer `An+B`, `odd`, and `even` until concrete use cases that it's important.
