Right now, elements with `popover` dismiss with the `Escape` key out of the box, but do not prevent that keyboard event from reaching the DOM, and propagating up through its ancestors. Functionally, that means that popovers nested within other controls like dialogs, sidepanes, etc. would in most cases also cause those wrapping controls to close when the popover is escape-dismissed.

This is different from the established behavior of browser escape handling in existing HTML elements with popups (`select`, color inputs, and date inputs), where using `Escape` to close them does not generate a keyboard event in the DOM. That's more a side effect of those being fully browser-rendered UI, but the end result is still the same -- they can be safely closed without causing wrapping controls to also close.

While interestingly it doesn't look like the native `<dialog>` element closes as a result of an inner popover escape-dismissing, any higher-level custom keyboard listener that handles escape would catch it and dismiss the dialog, e.g.: https://jsfiddle.net/Lrkce325/

Most open source control libraries rely on downstream controls stopping propagation to handle multiple levels of popups. Since `popover` doesn't currently do this, I'm not sure if it's possible to safely use it together with any library's custom dialog component. Referring to the [Open UI Dialog page](https://open-ui.org/components/dialog.research/), all the libraries linked in that page with live examples that I was able to test showed this exact issue.

The `popover` attribute is rather different from `select`, `input type=date`, and `input type=color`, so fully obscuring the event seems wrong here (even more so because `popover` could itself have nested controls that need to handle escape). My first thought was to allow the capture phase but stop propagation past the popover node (or past the trigger, if focus is there), but that's only an initial idea, I'm sure there are potential issues with that approach as well. I'm curious if other folks also see this as an important issue, and other thoughts on how to solve it.

I think the ultimate solution here is for sites to use the [close watcher API](https://developer.mozilla.org/en-US/docs/Web/API/CloseWatcher). That will handle this situation (and is I suspect why native dialog doesn't have the problem).

## @smhigley — 2025-02-03

@lukewarlow the event propagation issue would only be relevant to escape key events whose target is within the `popover` node, so I believe it would be technically possible at least to stop bubbling past that element.

The biggest current issue with the close watcher API is probably that it doesn't have enough support to use in production right now, and also that essentially no major component frameworks/libraries use it. So I think that would mean that it is impossible to use `popover` in any context where that UI might end up in a custom dialog (which I believe is unfortunately most at-scale contexts, since UI tends to be reusable in all cases but small custom-coded websites).

That issue could potentially be solved with time, but the other persistant problem is that the close watcher API is that it is not suitable for all popup content use cases. Not all dialogs/panels/etc. should be closeable with the back button on mobile, and it's possible to have multiple non-modal dialogs or panes open at a time, any of which may have nested popovers. Those non-modal dialogs would need to handle the escape key themselves, not respond to an escape press from anywhere on the page. If `popover` doesn't handle `stopPropagation` for escape presses with an inner event target, I'm not sure it'd be technically possible to code the correct escape handling behavior. Or at least not without some monster block of code that walks up the DOM tree from the event target, checking each node for the presence of a `popover` attribute.

The differentiation between escape event targets being inside or outside the popover matters, since I believe a reasonable user (particularly screen reader users, but also keyboard users) would assume that if their focus is inside the popover and they press escape, the popover alone should close. If the author has allowed focus to be outside the popover while it stays open, I believe the user assumption would be that the outer context should close, if one exists.

@lukewarlow one issue is that closing dialogs & other surfaces isn't the only common use of escape -- it's also widely used (in Microsoft at least) as a way to move up a level in static UI. ## @mfreed7 — 2026-06-11

I thought about this one quite a bit. Generally, I agree with @lukewarlow's comments above, that the `CloseWatcher` is the mechanism used by browsers (and the spec) here, and to do this correctly requires that the site also use CloseWatcher. This behavior is quite nuanced, to avoid abuse and to get the interaction model right. I'm not sure the best solution is to just stop propagating key events in these cases. (See [this part of the spec](https://html.spec.whatwg.org/multipage/interaction.html#the-closewatcher-interface:~:text=they%20are%20grouped%20together) for the details.)

For example, in the [repro in the OP](https://jsfiddle.net/Lrkce325/), in the case of a `popover` nested inside a `<dialog>`, by itself the `dialog` doesn't close when the user hits ESC once. That's because in that repro, there's a user interaction which creates a new close watcher group. The popover gets one, the dialog gets the other, and they close independently. In other cases (e.g. both dialog and popover showing up without a click, or multiple popovers showing up with a single click) the behavior is different (e.g. both close with a single ESC, or just the popover close, etc.).

I put together this repro with variations on the theme:

- https://jsbin.com/yakiyuk/edit?html,output

In my testing, that behavior seems quite interoperable - all browsers do the same thing(s).

In the repro in the OP, I think the right thing is to just replace the manual `keydown` listener with something like this:

```javascript
btn.addEventListener('click', () => {
	dialog.showModal();
	new CloseWatcher().onclose = () => dialog.close();
});
```
