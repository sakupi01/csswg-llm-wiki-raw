We can define `<menulist>` elements to be popover by default. This would be more natural for developers, but I am not sure if it breaks any semantic.  For example, there is no `popover=none`, so users wouldn't be able to opt out. Maybe we would need to add that as a valid value.

```HTML
<menubar>
  <menuitem menulist=more>More commands</menuitem>
</menubar>
<menulist id="more">
 ...
</menulist>

<!-- OR -->

<menubar>
  <menuitem commandfor="more" command="toggle-menulist">More commands</menuitem>
</menubar>
<menulist id="more">
 ...
</menulist>

```

The second option would be to let the developer add the popover attribute and trigger the popover by using command/commandfor. This gives more flexibility to add more commands in the future and allow developers to turn it on/off by removing the attributes.

```HTML
<menubar>
  <menuitem commandfor="more" command="toggle-popover">More commands</menuitem>
</menubar>
<menulist id="more" popover>
 ...
</menulist>
```

This is probably related to the openable issue (https://github.com/openui/open-ui/issues/1198). If we want to allow inline menulist, than going with command/commandfor would be better.

## @lukewarlow — 2025-05-29

Thinking on this more I'm not even sure that it's technically true to say this would be a "popover". I think more accurately it would be an element placed into the top layer, with light dismiss and an associated close watcher. Iirc it has differing behaviour to a standard popover (e.g. I think it should automatically get focus on open). I think it should be considered more akin to a sibling of `[popover]` much like `<dialog>` has similarities but also differing behaviour

For example commandfor=menulist would setup an aria-haspopup relationship which it wouldn't do for a standard popover. Obviously we can do that regardless but I think it makes more sense to explain that as a consequence of the element not as a consequence of popover on a specific element.

## @ITenthusiasm — 2026-08-08

One potential callout I'd have is that people may not want `<menulist>` in the top layer if they are trying to replicate the look/feel of `contextmenu`s in mobile apps.

> Disclaimer: I've seen [Open UI's Context Menu notice](https://open-ui.org/components/menu.explainer/#how-can-we-use-menu-elements-to-support-custom-right-click-context-menus). It makes sense. However, at this point in time, I'm not aware of a good alternative for people building "native-ish" PWAs/Electron Apps/Tauri Apps. In these cases, an ARIA `menu` seems to be our best shot at presenting `contextmenu`s with _app-specific_ actions to users.

For example, `contextmenu`s in Mobile Apps often apply a dimming/blurring effect to everything _except_ 1&rpar; the entity on which the user opened the `contextmenu` and 2&rpar; the `contextmenu` itself. If the menu is rendered in the top layer, then `::backdrop` cannot be used to apply the blurring/dimming effect because it would blur/dim the target entity as well. (I'm assuming that an `openable` would have a `::backdrop` which wouldn't have this issue.)

Admittedly, a hacky workaround could be

```css
menulist:popover-open {
  &::backdrop {
    background-color: transparent;
  }

  + .pseudo-backdrop {
    position: fixed;
    inset: 0;
    /* Other Styles */
  }
}
```

This would allow `.pseudo-backdrop` to apply blurring/dimming _beneath_ the target entity and _above_ everything else, assuming `z-index`es are set correctly. So `::backdrop` wouldn't be used at all. But the approach still feels a little weird.

Just a thought. Feel free to call me crazy, or to tell me this is a different problem.
