We've put together an explainer for a new feature, tentatively called "Declarative Overscroll Actions". I'd like to use this issue to introduce the concept, and hopefully start a discussion in OpenUI. Assuming the group is amenable to incubating the idea, we can branch off other issues as they come up.

A quick copy/paste of the first few sections of the explainer are below. Please see the full explainer here:

- https://open-ui.org/components/overscroll-actions.explainer/


## Introduction

The web platform allows for sophisticated scrolling experiences, but it currently lacks a semantic way to utilize "overscroll" space (the area beyond the scroll boundary).

Common UI patterns like **side-menus** (swiping past the edge to reveal a menu) or **swipe-to-action** (swiping a list item to reveal delete buttons) currently rely on complex nested scrollers or JavaScript gesture polyfills. These workarounds are difficult to implement, computationally expensive, and often fail to provide accessible alternatives for non-touch users.

## Proposal

We propose a set of HTML attributes that declaratively bind an element (the "overscroll content") to the scroll boundary of a container.

Crucially, this binding is defined on an **activatable element** (like a `<button>`). This ensures that every gesture-based action has a guaranteed, accessible fallback interaction (click/enter) without extra developer effort.

### Goals

* **No JavaScript:** Enable swipe-to-reveal and pull-to-refresh gesture-based interactions using only HTML and CSS.
* **Accessibility by Default:** Enforce the existence of a semantic button to toggle the view, ensuring keyboard and assistive technology support.
* **Performance:** Offload gesture physics and animation to the browser's compositor thread (via scroll timelines).

## The API

There are two parts to the API:

First, the container needs to be identified as supporting overscroll areas. This is done by specifying `overscrollcontainer` attribute on the container.

Second, we introduce a new `command` value, `toggle-overscroll`, to bind a trigger button to both the container (the scroll port) and the content (the element hidden in the overscroll area).

```html
<div id="container" overscrollcontainer>
    <menu id="menu">
        <li>Home</li>
        <li>Settings</li>
    </menu>
    Some content.
</div>

<button commandfor="menu" command="toggle-overscroll" id=btn>
  Toggle Menu
</button>
```

### Behavior

1.  **Positioning:** the `#menu` is effectively absolutely positioned within
    the "overscroll" area of the overscroll container.
2.  **Chaining:** When a user scrolls `#container` to its limit, the scroll
    chains to the `#menu`, pulling it into view.
3.  **Activation:** As an alternative to scroll gestures, activating the
    `<button>` will perform a `scrollIntoView`-like action on the `#menu`.
    Activating it again scrolls `#menu` back out of view.

[Here is a simple demo implementation on Github.io](https://flackr.github.io/web-demos/css-scroll-snap/menu2/). This demo does not require any browser features, though this feature is being prototyped in Chromium.

## @scottaohara — 2026-02-13

some thoughts / initial responses to the questions in the explainer 

- if the over scroll content is positioned off screen / invoked by a button or swipe gesture, then it needs to be completely hidden so that users can't tab to or discover the content. (effectively display none).  
- if this will support a backdrop / obscuring the content that is pushed off screen  - then when the overscroll content appears on screen, focus shouldn't remain in the obscured content area
  - seems that this _should_ be treated as modal. 
  - if there is no obscuring of the content that is pushed aside to make room for the overscroll content, and the main content is squished/reflowed rather than going off screen - then seems like _that_ would be a non-modal use case.
  - per the above, and the question about whether the button should have an aria-expanded state - if the overscroll content is styled in a way to make it appear that the primary content is inert (re: the example) then focus should move to the invoked slideout content, and then an aria-expanded state isn't that necessary.  BUT, if it's going to not be treated as modal / the primary content is not inert, then an expanded state is important / the moving of focus isn't as necessary.
- if this isnt goign to be treated as modal at all, then when focus leaves the overscroll content, it should dismiss like it does with the light dismiss click.   But if focus isn't managed / the focus order of the content doesn't make sense (like the demo - i have to shift + tab backwards to get to the overscroll content) - then this will set people up really easily to be fail wcag's focus order requirement.  that i unless some of popover's tabindex magic is brought into this to essentially "fix" the focus order

## @smhigley — 2026-02-19

I mentioned this on the meeting, but I'll drop a comment here to be more concise --

I think one open question/problem to add to the roadmap is how to make sure the overscroll area can be closed in an accessible way. That includes solving for the following two cases:
- if the overscroll area is modal, so the original button isn't in the a11y tree. This would affect screen reader and voice control software. (Desktop screen reader users could potentially use escape, but not touch SR users or VC users)
- whether or not it's not modal, if the scroll causes the orignal button to be outside the visible area. This would not affect screen readers, but would affect some switch users, voice control users, and some people not using any AT but with mobility disabilities that affect their ability to scroll.

(this does seem solvable, just something that should be added to the list of things to solve so we don't forget)
