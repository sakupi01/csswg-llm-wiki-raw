In the [menu elements explainer](https://open-ui.org/components/menu.explainer/), sub-menus are connected via the `commandfor` API:

```html
<button commandfor=parent command="show-menu">Menu</button>

<menulist id=parent>
  <menuitem>Item</menuitem>
  <menuitem commandfor=submenu command="show-menu">Submenu</menuitem>
  <menuitem>Item</menuitem>
</menulist>

<menulist id=submenu>
  <menuitem>Item</menuitem>
  <menuitem>Item</menuitem>
</menulist>
```

The [APG Menu Guidelines](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/) says this about submenus, though:

> If activating a [menuitem](https://w3c.github.io/aria/#menuitem) opens a submenu, the menuitem is known as a parent menuitem. A submenu's menu element is:
> - Contained inside the same menu element as its parent menuitem.
> - Is the sibling element immediately following its parent menuitem.

It also briefly mentions `aria-owns` at the bottom, for the type of menu structure (i.e. non-nested) envisioned by the menu elements explainer.

I wanted to open an issue to just double-check that this APG guidance is correct and is the right one to be following here.

Guidance for creating menus have never mentioned/required a details association. `aria-controls`... maybe... though i doubt it'd be needed with the proper focus management/keyboard navigation behaviors in place. but absolutely yes to `aria-haspopup=menu` for buttons that invoke a menulist, or menuitems that invoke a sub-menulist

Ok, thanks! What about `aria-owns`? We explicitly don't want to nest the menus directly, for a couple reasons:
1. It would be an a11y no-no explicitly: `<menuitem>` is an interactive element, so nesting a `<menulist>` inside that, which itself contains more `<menuitem>`s would be nested interactives. And nesting just the `<menulist>` within each other but outside the triggering `<menuitem>` also feels weird.
2. It's not a common pattern that we've seen in the wild, in design systems. Some do, but it seems like the majority do not.

So it sounds (from the APG) like we need to make them nested in the a11y tree, but not nested in the DOM tree, which sounds like `aria-owns`.

## @jcsteh — 2025-11-07

A few things to consider here if this comes up again:

1. One advantage of having proper ancestry for sub-menus is that a user can perceive the hierarchy semantically. Without that ancestry, they're relying purely on the series of steps they took (arrow keys, etc.) to perceive the hierarchy. I assume the hierarchy is visually apparent? If so, arguably, it should be semantically apparent, too.
2. Real world examples of how a user might perceive the hierarchy:
    - In NVDA, the braille display shows the context/breadcrumbs for the focus if the user scrolls back.
    - The NVDA review cursor can navigate hierarchically, as can VoiceOver ("stop interacting with").
3. That said, ARIA is inconsistent in whether hierarchy is exposed in the accessibility tree or not. For example, nested treeitems can either be nested or siblings with aria-level.
4. Various non-web GUI frameworks are also inconsistent:
    - Native Windows sub-menus and native sub-menus in Microsoft Edge do not expose hierarchy in the accessibility tree.
    - Gecko native sub-menus do expose hierarchy in the accessibility tree.
    - I'm not sure about MacOS native sub-menus, but it'd be interesting to find out.
