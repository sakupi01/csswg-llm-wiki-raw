If a menuitem is hooked up to open a submenu:
1. Should hovering or clicking invoke the submenu? Should it be developer controllable?
2. Should keyboard focus open the submenu, or should you have to focus and then press another keyboard button to open the submenu?
  - Where should keyboard focus go when the submenu is invoked?

Does interesttarget already have answers to all of these questions? If so, how could we ergonomically combine interesttarget with however we hook up the association between a menuitem and submenu?

>Should hovering or clicking invoke the submenu? Should it be developer controllable?

probably developer controllable.  the menuitems of menubars commonly require specific action for a user to invoke them - but menuitems that invoke submenus within a menu popup and often automatically show their related submenus on hover/focus or still require someone to invoke them via purposeful activation (click even).

so mabye click to open is the default, and then authors can change to open on hover/focus to match their current custom implementations.

>Should keyboard focus open the submenu, or should you have to focus and then press another keyboard button to open the submenu?

answered this above.  it could be either.

>Where should keyboard focus go when the submenu is invoked?

if opened via click, then auto-moving to the appropriate menuitem in the submenu can be reasonable.
but would not be desired if the submenu auto opened on focus/hover

## @Permik — 2025-06-11

FWIW, the submenu activation should follow what the platform defaults are with a pointer device. I.E. Open on hover.

This unfortunately can become cumbersome as with touch-inputs with split-submenu buttons and touch devices where you don't necessarily have the option to "hover".
(E: There could be a possibility to add an affordance to the split-submenu scenarios for touch screen devices to have an extra state for touch devices where you have to activate the sub-menu a second time when using a touch device)

And like with the new styleable select element, we should keep the platform functionality of drag-clicking to navigate the menu and invoke the selected option.

## @dbaron — 2026-01-21

So I think there are separate questions here about both (a) mouse and (b) keyboard behavior.  While we could come up with parallel answers for both, we don't necessarily need to (and there are some factors that might lead to wanting different answers, see below).

https://www.w3.org/WAI/ARIA/apg/patterns/menubar/ has a detailed description of desired keyboard behavior, but I don't see any description of desired mouse behavior.

In general, mouse behavior for menus does involve opening on hover.  In most cases it also seems to involve both, although sometimes just one of, (a) some sort of delay both for opening and closing and (b) a safe-triangle behavior (not necessarily a physical triangle but sometimes or often a function of gross direction of movement) that increases that delay when the user is moving towards an open submenu.

We have a proposed platform feature, [interest invokers](https://open-ui.org/components/interest-invokers.explainer/) that could explain the hover opening and probably (a), but (in its current form) not (b).  However, progress on the feature is currently stalled so it's probably unwise to depend on it.

It seems like we could reasonably allow the open-on-hover behavior to be implementation-defined to some degree, with a note in the spec describing some likely desirable behaviors.  This probably isn't compatible with fine-grained developer control of the behavior, although it probably still is compatible with a more coarse-grained control (for example, to disable opening on hover entirely).

So based on these thoughts and on the discussion above, I think my current preference is to:
* define keyboard behavior in line with APG pattern guidance (generally trying to resolve the "optional" things based on evidence of what is common)
* define click/pointer/touch-based opening of toplevel menus and submenus and activation of menuitems (including with dragging as discussed in https://github.com/openui/open-ui/issues/1312#issuecomment-3469585173)
* suggest that implementations support hover-based opening of submenus (and of different toplevel menus when one toplevel menu is already open) with both delay and safe triangle but allow the details to be implementation-defined
* probably define focus behavior that results from all of the above (probably including the hover-based opening)
* possibly define a mechanism to disable the hover-based opening (though I'm not quite sure what it should be)

(Though after writing that I wonder if I've perhaps more of it should be implementation-defined?)
