We resolved in the issue #74 to not allow interactive elements within an option. @levithomason asked if this would also be true of the top part, which currently is named <button> which behaves as a button and an expectation of being a native `<button>`. That said, the web platform, due to the same issues as the `<option>` additional interactive elements are not allowed within them. Levi brought up scenarios such as a multi-select that shows the selected options in an input at the top that are clickable to deselect the option.

This is to review whether the current anatomy design would limit this capability or not.

For reference here is the current [anatomy design](https://open-ui.org/components/select#anatomy):

![image](https://user-images.githubusercontent.com/865244/80245392-77308c80-861f-11ea-8532-b40d8d060b2b.png)

Related to https://github.com/WICG/open-ui/issues/73

## @mfreed7 — 2023-02-16

So we've discussed and resolved the issue of interactive elements within `<options>` (in https://github.com/openui/open-ui/issues/74) and within the listbox (in https://github.com/openui/open-ui/issues/540). This issue seems to be about interactive elements inside the **button**. My thoughts:

 - We obviously need to allow interactive elements to be slotted into the **button** part. It's a button after all.
 - Allowing interactive elements in the **marker** and **selected-value** slots feels broken/odd, since both of those parts are *inside* the button. Per-spec ([here](https://html.spec.whatwg.org/multipage/form-elements.html#the-button-element)), interactive content is not allowed within a button. I think we should not do anything special in these cases, however. We should just do whatever happens today when a developer does `<button><input></button>` for example.
