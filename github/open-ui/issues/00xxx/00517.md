We have been (esp big props to @jonathantneal) at work the last several weeks trying to put things into good order to have a pretty solid take in the `oui` branch of our [spicy-sections repository](https://github.com/tabvengers/spicy-sections/tree/oui).  As we demonstrated a few weeks ago, this involves a lot of changes

* Changes the name from `<spicy-sections>` to `<oui-panelset>`
* Moves *nearly* all of the attribute relationships into the shadow dom
* Provides well specified parts for the shadow dom 
* Changes the CSS property/value to be simple and intuitive/close to what we would probably propose
* Fixes a problem we had with testing setup
* Rewrites all of the tests to this model
* Creates some nice gh-pages hosted documentation 

Along the way, however, we struck upon a fairly significant [new open question/debate](https://github.com/tabvengers/spicy-sections/issues/65).  We have noted this directly in the readme itself with appropriate recommendations relating to use.  Despite that, we believe the best thing to do is to  move this work at this stage into the openui repo and work together to address them.

We're asking for : a) Consensus to do that - and b) specifics about how (we could transfer the repo, but then I suppose we have to merge into main first - or we can fresh commit that branch into a new repo here and put a note on the old repo - or ...?)

## @gregwhitworth — 2022-04-13

A) +1, very supportive of this
B) With regards to moving the spec/explainer and component over here are my initial thoughts and honestly these should probably be broken out into separate issues but it's generally the tenants on web component creation/transfer.

* **Separate Repo within OpenUI Organization or under OpenUI Repo**:  One of the key reasons I'd prefer a single repo is for issue discovery. Granted this has its own downsides but labelling enables filtering so I'm less concerned about this personally.
    * The Explainer should land on the site in the same way others have. With regards to documentation this may require some additions to the site (@captainbrosset was thinking about this too) but I'd prefer to not have numerous different areas where folks don't know where/how to discover the work.
    * The component: Currently we have a sub-branch called components that under the components folder actually has web components authored on top of Fast (@chrisdholt and others did work to enable transpilation down to native web components but simplify DX).
* **Framework/No Framework/Hybrid?:** Given what we discussed *very* early on, this group will define and build on top of standards. As such, if the group desires to leverage a framework for uniform authoring/improved DX, etc it needs to lean heavily into web components so that ultimately what we're providing to the community is effectively web components. If there is a desire to leverage a framework (I think there should be) we should have an issue solely on that and discuss the requirements and make a decision.
* **Testing:** What testing framework do we want to use? As I noted to folks years ago I'd really like if the tests can be easily ported into WPT since so much of this work has an expectation of graduating to WHATWG/CSS/ARIAWG, etc.
* **Issues:** The issues should get moved over to the repo and labeled with `panelset` (did we resolve on this name in Open UI??).
* **Archival/historical purposes:** The spicey sections repo should move to the Open UI org and will be put into an archived state. This will keep it in association with Open UI for later reference. This is important as well for informing future discussions around resolutions.

I'm sure there are more things to discuss but I'd really love for the spicey section team to inform aspects of the above as they begin moving through it.

Thanks for all of the effort on this folks!

## @jonathantneal — 2022-04-13

About testing:

I’d love to help further bridge the gap with proposals and WPT. I am enthusiastic about WPT, and I was even recently playing around with WPT to prototype a popup polyfill. However, I do also have three concerns about using WPT as it is today.

1. The WPT [local environment setup](https://web-platform-tests.org/running-tests/from-local-system.html) is bespoke to get going, which I think will limit contributions compared to other project environments.
2. The WPT [testing types](https://web-platform-tests.org/test-suite-design.html#test-types) don’t appear to include the same kinds or levels of visual testing or interaction testing that we are accomplishing in TestCafe. Switching to manual testing would feel like a real downgrade.
3. The WPT tests don’t factor in library code, understandably. I have been working on code coverage tests, which means those tests would need to exist parallel to the WPT (harness?) tests.

Those things are important to me. Do they seem reasonable to others? Are those issues already mitigated in WPT and I’m missing information?

Even with those issues, I have been thinking of ways we could bridge the gap. For instance, I am looking into running WPT tests from within TestCafe, to reduce the duplication of tests, and I’m looking at how I might capture data from a browser to populate test coverage, further reducing possible test code duplication.

I am also only one person. If my concerns seem legitimate to others and my proposed solutions seem helpful, then I would love to contribute them. I’m also open to other ideas. For instance, I’m not against duping certain tests into WPT style tests.

I just want to be sure that whatever I do is in alignment with you all, my fellow contributors.
