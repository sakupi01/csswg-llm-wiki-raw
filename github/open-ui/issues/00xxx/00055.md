I'm forking from the other issue as I think there were two seperate issues in one. This one and whether they should be referred to as glyphs/icons.

@levithomason I think this could be interesting, though I do wonder how semantics will play into this. Several teams across Microsoft use a pencil for "edit"; however, from a longevity standpoint, I think that might be a mistake to standardize on. Teams at MSFT who don't have edit states may also use that specific icon/glyph to signify "pencil" or something else. 

A better example may be that in Edge, a star signifies something like a "favorite". In the Store, that same glyph might be used to signify "rating". The icons are semantic for each team and their specific application. I'm curious how we could standardize considering how often this might happen. "Star" would convey the visual of the icons and could offer alignment for both teams, but it might not end up in the table we create simply because teams are naming the glyph for their semantic scenario.

Mind you, I don't have a great solution or alternative proposal - but I'm wondering how the matrix works with the above considered? Thoughts?

## @gregwhitworth — 2020-03-23

To put it succinctly, using @chrisdholt example - would you prefer for us to standardize on an icon being named: *star* or *favorite*?

I personally prefer to utilize the action or hint that is being conveyed as there are many paradigms and scenarios where the same icon may overlap and because we're desiring these to be blueprints for different platforms to build their controls/components from I don't think we should require that "edit" be represented by a "pencil" when they could prefer to solely use the word "Edit" or some other type of graphic.

**Proposed Resolution:** When creating a new control or component that has a part which may contain a graphic representation for an action or hint to the user, name it as the action or hint and not the assumed graphic representation.

I think this is the same issue as with colors, and there are two layers here. 

For colors, the base layer, has “blue”, “red“, “green”, etc. The second layer has “primary”, “error”, “success”, etc.

For icons, the base layer has “star”, “pencil”, “arrow right”, etc. The second layer has “favorite”, “edit”, “previous”, etc.

Then we have a mapping between the two on the design system level.

## @levithomason — 2020-04-10

**TL;DR**

Seems there is consensus on naming according to behavior/usage/intent opposed to literal name describing the shape itself.  Agreed here 👍 

**Longer story**

IMHO it would be ideal to name icon slots by their usage or intent.  This allows folks to use any icon they would like without invalidating the name.  Example, an "expand-icon" (hypothetical) will always "expand" the component (such as a tree).  The actual shape of the glyph or graphic in that slot could be a "chevron-right / chevron-down" or "plus-sign / minus-sign" (hypothetical) and still not violate the fact that it is the "icon representing the expansion of the tree item."

If we name these by their actual name ("chevron-down"), then I would think that would also necessitate disallowing changing them to another glyph.  I would also propose that they must be able to changed else folks will build their own.

This is also inline with one of Open UI's current naming principals:

>### Names should be void of design information
>
>**Why?** When designs change names should not become invalid. Names should stand the test of time. Usually, names based on intent or usage are more robust and stand this test. Consider a component that displays mock content while waiting for the actual content to load. It might be more ideally named Placeholder opposed to Shimmer, even though most implementations appears to flash or shimmer. When the design changes and these components no longer shimmer, the name will become invalid and not make sense.

We also faced this issue over the last couple years in Stardust / Fluent UI since we allowed the icon set to be swapped out as part of the "theme" definition.  However, some components internally rely on certain icons being available (i.e. a Menu Item's "indicator" icon which points in the direction of a submenu).
