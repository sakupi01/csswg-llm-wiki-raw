In https://open-ui.org/components/invokers.explainer/#what-does-this-mean-for-popovertarget we say the new attribute doesn't neccesarily mean the popover ones will go away.

I think it'd be good to get a concrete proposal on what happens to them (effectively I want whatever we write to not need "necessarily" in it).

I propose we deprecate `popovertarget` and `popovertargetaction` as they're completely superfluous once we have `invoketarget` and `invokeaction`, with the eventual goal of their removal in future.

## @keithamus — 2023-10-08

> A migration polyfill probably wouldn't even be necessary on the basis they'd be polyfilling invoketarget anyway?

 While the migration path is quite straightforward, for larger orgs (like GitHub) who have hundreds of references it'll take some time to migrate. We'd want a period of time where both are supported in some manner (be it via a singular polyfill, multiple polyfills, or by browsers supporting both for some time). Right now we polyfill popovertarget because Firefox doesn't support it, if Firefox shipped popover w/o popovertarget work would be need to done on https://github.com/oddbird/popover-polyfill which assumes `popovertarget` comes for free with `popover`. So there'd need to be not-insignificant coordination from all parties.

> Even just something like a warning in dev tools if you have popovertarget without a corresponding invoketarget would be a good start. At some point the usage of popover will probably drop to an acceptable level to remove but possibly not?

I think browsers should probably add a `console.warn` when using both `invoketarget`/`popovertarget` because `invoketarget` will silently prevent `popovertarget` from working, which could lead to confusion.

So if we were to _also_ warn when using `popovertarget` _without_ `invoketarget` we're effectively making it warn whenever `popovertarget` would be used - which is fine but we should make that the conscious choice.

An important take-away here is to ensure developers have all the necessary mechanics in place to be able to easily turn `popovertarget` into `invoketarget` without any incidental complexity - which IMO further talks to the point of there being a long enough window where browsers support both in order to let web developers to migrate.
