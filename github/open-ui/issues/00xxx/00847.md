I was reading this article on gregs website: https://www.gwhitworth.com/posts/2019/can-we-please-style-select/
This article points out why we need `<selectlist>`, but also says that the top frustration with `<select>` is "Not being able to create a good user experience for searching within the list." There is an example [in the demos](https://microsoftedge.github.io/Demos/selectlist/index.html) which adds a text input in the listbox to filter which addresses this top frustration, but based on what I've been hearing from accessibility experts, there should not be any interactive content inside the listbox element except for `<option>`s.

So my question for accessibility people is: what is the right pattern to create a select-like thing where you can filter the options? Is that just called a combobox, where instead of a button to open the listbox there is a text field?

I see in [this combobox in aria practices](https://www.w3.org/WAI/ARIA/apg/patterns/combobox/examples/combobox-autocomplete-list/) that the user can still sort of commit any text they want even if its not a valid option... what if you want to limit the possible choices to whats in the listbox like the one in the demos?

I think that this is only with the `listbox` role, but with the `<listbox>` element, the accessibility API mappings and content model could be different, to allow for this.

---

> where instead of a button to open the listbox there is a text field?

I feel that we shouldn't allow for the search input to replace the selectlist's button element.

Since then authors could use this element as more of a text autocomplete, than a `<select>` element.

But this then raises the question of how dynamic data would work. Since usually text autocompletes have loads of options which users can choose from, for example, a search engine's search bar. Where it'd be unpractical to have all these `<option>` elements.

The ability to search through the options would best work where data is static. For example, searching through countries to choose a location.

## @josepharhar — 2025-05-13

We should probably make the filtering work automatically without making authors implement their own script to filter options.

For putting a text filter inside the select element's popup, here are some options that I think we have:
1. Require the author to put an `<input>` inside the picker
    - We have to hope that the author puts the `<input>` before the `<option>`s. Is there any legitimate case for doing otherwise?
    - This also requires tracking which `<input>` is the first, whether it comes before `<option>`s or not, just additional bookkeeping to do in the browser which isn't ideal but is doable.
    - Should an attribute be set on the input element to say that its being used as a filter? Or should that be done automatically?
    - Should `<input type=search>` and `<input type=text>` be supported?
    - Requires more parser changes to allow `<input>` in `<select>`, which will likely require wrapping it with a `<div>` or some other unintuitive thing.
2. Add an HTML or CSS opt-in to display a filter input automatically
    - We could add an `<input>` to the UA shadowroot at the beginning of the picker before the slot element for the options and other nodes.
    - Strengthens guarantees that it comes before options and that it's easy for the browser to track it in the DOM.
    - This could be targeted with a part-like pseudo-element, like `select::text-filter`.
    - How would we get the current value of the text input from script? Expose a new script IDL on the select element? Is this even needed?
3. Variation on option 2, but only show the text input when the browser thinks there are too many options.
   - I think this is how the firefox experiment works.
   - Could make it not needed to opt in via html or css, but not sure if this would be liked by authors.

my vote would be that the input, regardless of where it is placed, becomes the first element of its closest parent group/listbox element, after any legend that might exist.

the most common reason to have an input in a popup like this is because you want to filter/search the available options. 

so:

```
<select>
  ...
  <option>foo</option>
  <input value="i'm second cause lol expectations">
   <option>bar</option>
</select>
```

would have the popup render as input, foo, bar

where as

```
<select>
  ...
  <option>foo</option>
  <optgroup>
     <legend>sub-group</legend>
      <option>bar</option>
      <input>
      <option>baz
  </optgroup>
</select>
```

would render in the order of: foo, sub-group, input, bar, baz


--- 

there can be a user case where someone wants to add a text field to create new options - but we're getting well into the territory of a more customized component that will need additional scripting and likely other controls like add/remove buttons.  that's not going to be what the majority of web authors will need.

## @josepharhar — 2025-10-10

I've been thinking more about the issues with putting an input inside a select, and I think that it would be better to support this use case by adding a way to associate an input element with a listbox select element without nesting, like this:
```html
<button commandfor=picker command=show-popover>
  <selectedcontent for=select></selectedcontent>
</button>
<dialog popover id=picker>
  <input list=select> <!-- NEW -->
  <select size=4 id=select>
    <option>one</option>
    ...
  </select>
</dialog>
```
We could also leverage improvements to the input element which would be needed for combobox, such as additional attributes to control filtering and primitives for focus handling.

## @josepharhar — 2025-10-16

> the issues with putting an input inside a select

To elaborate on the issues:
- a11y issues, see discussion [here](https://issues.chromium.org/issues/402429384)
- Allowing the parser to put `<input>` inside `<select>` would break websites: https://issues.chromium.org/issues/379612186
-  Parser changes make it harder to write polyfills
- There are several variations of this which each have cons, see [earlier comment](https://github.com/openui/open-ui/issues/847#issuecomment-2876984892)
  - I think that we would have to choose between limiting functionality with a pseudo-element which may or may not have some kind of opt in which might not be well received in HTML, or hoping that authors put the input element in the correct spot which could be easy to get wrong

some notes per the markup pattern and what i was mentioning in the call today:

```
<label for=trigger>Lable/name of trigger</label> <!-- 1 -->
<button id=trigger 
  commandfor=picker 
  command=show-popover>
  <selectedcontent for=select></selectedcontent>
</button> <!-- 2 -->
<dialog popover id=picker> <!-- 3 -->
  <input filter=select> <!-- 4-->
  <select size=4 id=select> <!-- 3 -->
    <option>one</option>
    ...
  </select>
</dialog>
```

1. authors would still generally need to provide a label for their picker trigger
2. while a button element, it'd need to follow the ARIA select-only combobox pattern.  role=combobox, aria-haspopup=dialog ... etc. 
3. the accName of the trigger could be automatically used to name the dialog or select (progably the select)
4. if we have a new `filter` attribute - arguably this could be automatically given an accName of "filter" - which would probably be a good thing to do, since as i mentioned during the call, these can commonly be added into these sorts of popups and lack labels/names

## @keithamus — 2025-10-29

Yes apologies I had meant to follow up on this. 

So I think the basic principle is that we should come up with some reasonable filtering API by default, so if a list of elements need to be filtered the UA can do some sort of substring matching (or something more fancy like character matching), but it should be cancelable so that developers can intercept to provide their own filtering. The justification for providing their own filtering is two fold: 1. because they might want to introduce new results (that might be async, from the server) and 2. because they might want to override the search functionality to be more context aware or so.

So I think the `<select>` could dispatch a `beforefilter` non-bubbling cancelable event. If it's not cancelled, it will perform the search. A `filter` event also feels like a good natural symmetry which would happen after the search has been completed- which would not be cancelable.

When the event is not cancelled, I'd suggest each `<option>` that matched would have a psuedo class. I think also we need to have a pseudo on the `<select>` itself to denote that it is currently being filtered, so e.g. `:filtered` (or similar) on the `<select>`, and maybe each `<option>` could have `:filter-match` (or similar). The UA sheet could have something simple such as `:filtered :not(:filter-matched) { display: none }`. These pseudos would provide styling hooks for developers so they could progressively build up more features. For example is a developer wants to grey out options instead of hiding them they can, or if they wanted to always show an item, even if it's not matched, they can. I think it's important we don't `disable` any options, as that might not be the developer's desire. Hiding is likely a sufficient default (though maybe someone can tell me why it's not).

For users overriding the search functionality, while we could provide APIs to set these pseudos, I think the MVP can be the cancelable event, and developers rolling their own search would just need to set a class on each `<option>`/`<select>` which isn't the worst. We can always add new APIs later to make scripting these more useful.

So by default if a user wants the built-in search, they set up the HTML with the `<input filter=my-select>` and everything "just works". They then have a set of progressive hooks:

 - Want to show more items? Override `:filter-matched`, e.g. `:filtered :not(:filter-matched).always-show { display: block }`. 
 - Want to show some items when there are no search results? `:filtered:not(:has(:filter-matched)) {}`
 - Need to fetch more results from the server? `.preventDefault()` on the `'beforefilter'` event and then just do your own thing, adding a `.filter` & `.filter-match` class to the DOM.

this wasn't explicitly mentioned in the markup example, but another a11y consideration likely need to be handled is if someone can type in a query to the input field which results in the listbox displaying no options.   

commonly authors render a "no results found" sort of message. As this would be considered a "status message", it really should be exposed in a way where it could be automatically announced by screen readers.

how exactly we want to handle this / _if_ a message is even displayed by default is something to consider.  but if a listbox could be filtered to return no options, and its left up to the author to render their own message, it might still be worth discussing if a default, localized, (maybe ARIA Notify) message is announced to users?
