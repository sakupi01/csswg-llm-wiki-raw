Should we support both `part="option"` and `<option>` or just update the [content model](https://html.spec.whatwg.org/multipage/form-elements.html#the-option-element:concept-element-content-model) for `<option>` to support arbitrary content when it is a descendant of `<select>`?

Note that supporting both `part="option"` and `<option>` could lead to inconsistency when reading / writing the IDL property (e.g. `selected=false`);

<!-- comment id=912052955 author=dandclark created=2021-09-02T21:00:32Z url=https://github.com/openui/open-ui/issues/396#issuecomment-912052955 -->
## @dandclark — 2021-09-02

My preference is to apply part behavior only for `<option>` (and update the `<option>` content model), for the reason you point out (inconsistency with the IDLs for `<div part="option">` vs `<option>`).

Supporting two ways to supply options seems like extra complexity without any concrete benefit.

There's also some precedent for this now since we only allow the listbox part to be a `<popup>`, i.e. `<div part="listbox">` doesn't work.

## @dandclark — 2021-09-03

Hmm, customElement options are a use case I hadn't thought of. Allowing that might be enough of a reason to support non-`<option>` option parts.

The reason we'd been considering not supporting them basically comes down to complications regarding differences in the IDL properties of options vs non-options. For example, consider the `disabled` IDL property of [HTMLOptionElement](https://developer.mozilla.org/en-US/docs/Web/API/HTMLOptionElement#properties), which is reflected with the "disabled" content attribute (see https://developer.mozilla.org/en-US/docs/Glossary/IDL#content_versus_idl_attributes).

Consider this case:

```html
<selectmenu>
    <option disabled>one</option>
    <div disabled part="option">two</div>
</selectmenu>
<script>
    const option = document.querySelector("option");
    const div = document.querySelector("div");
    console.log(option.disabled); // true
    console.log(div.disabled); // undefined
</script>
```

If controller code uses the IDL property to determine disabled status, then the option will be disabled but the div will not be, since the disabled content attribute is not reflected to the IDL property for divs. This could be confusing for authors.

Instead, the controller code could check the `disabled` content attribute to determine disabled status, but then authors who try to set disabled status in this way will run into problems:

```html
<selectmenu>
    <option>one</option>
    <div part="option">two</div>
</selectmenu>
<script>
    const option = document.querySelector("option");
    const div = document.querySelector("div");
    option.disabled = true;
    div.disabled = true;

    console.log(option.hasAttribute("disabled")); // true
    console.log(div.hasAttribute("disabled")); // false
</script>
```

So, there are some stumbling blocks for both implementers and developers here. Allowing only `<option>`s is the most straightforward way to resolve it. But, the use case of custom option elements might be important enough to make it worth handling these tricky cases in other ways, e.g. considering an option part to be disabled if *either* the IDL property or the content attribute are set.

Separately, using `role` instead of `part` seems like a potential improvement. I'll raise that over at https://github.com/openui/open-ui/issues/354.

I think the callout for something like disabled IDL and other variations is definitely something to be aware of. I do, however, think that not supporting custom elements here would be a miss. While less than ideal, I think that a little added logic could make it relatively easy to support everything here by hooking off `role`. If `role="option"` is present, we have pretty clear guidance as to what needs to be true/exist from an API standpoint in order for these states to be conveyed to AT. In this case we're likely making some assumptions, but we could also think of it as a contract :). We have clear guidance from ARIA regarding what an element with `role="option"` should support, so while it's a bit more code, I think we *could* likely check for a few things and set/act according to what's present there. I will note, that it is possible with custom elements to define a disabled attribute/idl so it *may* exist...but in this specific case could we not check for `disabled` OR `aria-disabled="true"`?
