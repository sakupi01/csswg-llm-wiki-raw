See https://github.com/keithamus/invoker-buttons-proposal/issues/14 for more details and that repo in general for full details.

TLDR: `interesttarget` attribute currently proposed to be supported on buttons and links. Could we add support to `<area>`, `<input>`, `<textarea>`, `<select>`, `<summary>`. (`selectlist` in future would be on this list) along with potentially other elements?

Are there extra elements we can/should add this too?

## @adactio — 2023-12-05

Could `interestTarget` be used to provide a declarative option for some JavaScript APIs? I'm thinking specifcally of JavaScript APIs that require a user interaction (and so most demos involve the creation of a button element anyway) and that don't currently have an equivalent HTML element.

For example:

* The Fullscreen API
* The Geolocation API
* The Web Share API

For that last one, the default behaviour could be sharing the current URL. I've been [collecting use cases](https://github.com/adactio/share-button-type/issues/1) to inform [a proposal for `button type="share"`](https://github.com/adactio/share-button-type/issues/1) but `button interestarget="share"` would achieve the same goal.

Likewise, `button interesttartget="requestfullscreen"` and `button interesttarget="exitfullscreen` could be directly equivalent to `document.requestfullscreen` and `document.exitfullscreen` but without the need to create a button with JavaScript (or write any JavaScript at all).

I'm not sure how the `button interesttarget="geolocation"` would work other than perhaps populating an `input` element using `invoketarget`.

I realise that this issue was asking specifically for HTML elements, not JavaScript APIs, so I apologize if this is off-topic.

## @SilentImp — 2024-12-16

Hi, 
I want to add additional problems and use cases to consider.
Invokers can be added to buttons/inputs—to interactive elements—to avoid the "pit of success." It makes sense. 

However, there is an issue related to that: inputs and buttons are replaceable elements. As a result, there is no way you can make them behave as normal text in the flow. Applying hyphens, flow through lines and all the rest. 

Yes, it's the presentational problem and it can be solved from the CSS side:
- [[css-forms] Allow making button element a real inline (or block/flex/etc)](https://github.com/w3c/csswg-drafts/issues/3226) _Feb 16, 2021_
- [[css-ui] appearance: base to enable interoperable styling of controls/components](https://github.com/w3c/csswg-drafts/issues/5998) _Oct 19, 2018_

At the same time maybe we can solve it from invokers side as well. Could it be faster, more efficient or better from any other point of view?

I see a lot of typography-related use cases for popovers/invokers. 
**For example:** you have a paragraph of text. In the word are abbreviations. You decide to move away from the `abbr` attribute `title` to have a fancy-looking and more accessible popover with full form. You have to write the abbreviation on the button ... and now it's not behaving the same way as before. Line height and baseline can give you a headache. 

But ok, abbreviations are not long. But what about reference text?
I have a paragraph of news text. There are references to some past events, which are not the subject of this article. I want to click on this event reference text and show the cut-in side notes to the left or right of the column. I wrapped reference text in a button, but now it doesn't properly flow into the next line. 

Of course, there can be UI workarounds: add a button info after text and make it `super`, or something. But it seems hacky without a reason. 

What are your thoughts on this matter?
