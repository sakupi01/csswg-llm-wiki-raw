Based on the needs from the tabs research, we believe that there is a common show-hide functionality which enables many tab components to be built. We have compiled a list of ways in which that content could be build from using existing primitives to inventing new ones at https://github.com/flackr/declarative-show-hide .

We would like to evaluate the options, whether we have missed any requirements or if any of the existing requirements are unnecessary and identify our best options moving forward for implementing tab components.

## @gregwhitworth — 2021-04-15

@flackr one thing that I didn't want to bring up on the call is that this visibility is trying to solve something as well in that we need a relationship between two items for some type of functionality. For example the `popup` proposal has a popup attribute to tie the event handlers for toggling the popup.

Likewise, while investigating the file input we identified that while a default anatomy of the input and button being siblings is fine there are many scenarios in which they are not siblings. So ultimately the containing element where you want to reflect the chosen files actually needs a relationship connection rather than an assumption that they will always be within the same host element.

I'll be honest that I don't think we need to super-generalize these associations, eg: we have `for` but I don't think I'd want `for` to be the solution for invoking a popup. I am however curious if we shouldn't define this association? For example we have the definition of a context attribute, should we possibly introduce a type of attribute that has an assumption of some form of relationship with tied behaviors? This would set the stage for those behaviors to be defined and researched on their own, eg: will show/hide solve `popup`,`tabs`, etc?
