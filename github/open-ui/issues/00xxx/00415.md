In some cases, it might make sense for blur (focus leaving the `<popup>`) to trigger light dismiss. For example, if the `<popup>` is the menulist for a `<selectmenu>`, when the list is opened, it is focused, and tabbing out feels like it should close. However, in most other cases, it seems like this behavior would likely be confusing. In particular, because the `<popup>` is not focused by default (without `autofocus` or `delegatesfocus`), it feels especially weird that tabbing over to `<popup>` and then leaving it should close it. But it came up in a discussion, so I thought I should raise it here. Perhaps it should be a light-dismiss trigger only if the `<popup>` is auto-focused?

Not wishing to detract from the semantic mapping discussion, I wanted to point to this piece of the initial explainer:

> An opened popup will have “light dismiss” behavior, meaning that it will be automatically hidden when:
> 
> The user hits the escape key,
> The layout of the popup or its anchor element is changed.
> **Focus moves outside of the popup (and its invoking and anchor elements, if applicable).**

The carveout for invoking/anchor elements was meant to solve for things like comboboxes, where you wouldn't want light dismissal of the popup when focus is in the text field. There's something attractive to your line of thinking on `autofocus`/`delegatesfocus`, but just wanted to add that there are cases where you wouldn't autofocus the popup but would expect it to dismiss on blur.

## @mfreed7 — 2022-03-18

I just wanted to summarize what I heard at the [discussion](https://github.com/openui/open-ui/issues/415#issuecomment-1071180773) yesterday:

- Generally, folks seem to think that "loss of focus" (see below) **should** cause a light dismissal of the popup. In particular, the AX folks on the call seemed to think that this was the most appropriate behavior.
- There were some good points raised about how to define "loss of focus":
   - The **popup** losing focus is what matters, and it is typically not focusable. So the `focusout` event is the more relevant one, rather than `blur`, since `focusout` bubbles.
   - Moving focus between elements within the popup will trigger `focusout` events. So we need to be careful in how we define "loss of focus" for a popup. It cannot be simply a `focusout` event bubbling to the popup element.
   - Similar to the above, clicking on a non-focusable element within the popup will cause focus to move to the `<body>` and stay there, and that should not constitute a "loss of focus". This will make the above bullet more difficult.
   - When the popup opens, focus might remain on the element that triggered it, and not move inside the popup. In that case, we would want to light dismiss when the **trigger** element loses focus, unless focus is moved directly to something within the popup. Essentially, the trigger element should be considered part of a group including the popup and any ancestor popups, and moving focus within this group should not light dismiss anything.
- We also discussed whether there was a difference between the element losing focus and the **window** losing focus (to another application window). The general consensus seemed to be that window blur should **not** trigger a light dismissal. However, after the meeting, @dandclark pointed out that we [already discussed this exact issue](https://github.com/openui/open-ui/issues/241),  and the resolution there was to have window blur trigger light dismiss. The rationale (see [the minutes](https://www.w3.org/2020/12/17-openui-minutes.html#ResolutionSummary)) was that most operating systems behave this way, and we shouldn't diverge without significant research. I have a hard time disagreeing with this logic, and prior resolution.
- To complete the summary, see the point raised/discussed just above. We need to think about the behavior when the triggering element is clicked or focused. Should that re-close the popup, or leave it open?

One more point, pulled from https://github.com/openui/open-ui/issues/319, is that we need to think about the correct behavior for focus moving between documents within a page. It would seem (to me at least) that this should fall into the same logic described in the comment above: when the focus leaves one popup, and moves to another element (including within a different embedded frame/document), the first popup should be light dismissed.

<!-- comment id=1093244861 author=mfreed7 created=2022-04-08T18:57:42Z url=https://github.com/openui/open-ui/issues/415#issuecomment-1093244861 -->
## @mfreed7 — 2022-04-08

I propose this as a behavior:

1. Add a `focusout` event listener to `Document`.
2. In this listener, iterate through each Popup in the Popup Stack, starting from the "top" of the stack:
   a. Inspect the `relatedTarget` for the event.
   b. If the related target is null, continue.
   c. If the related target is a flat tree descendent of the Popup, continue.
   d. If the related target is a flat tree descendent of the Triggering Element for Popup, continue.
   e. Light dismiss Popup.

I believe this will result in the following behavior:
 - Any change of focus **within** a popup will **not** light dismiss the popup.
 - Any change of focus **within or to/from the triggering element** of a popup will **not** light dismiss the popup.
 - A change of focus to another element on the page, including an `iframe`, **will** light dismiss the popup.
 - A **window blur** (i.e. moving to another application window) **will** light dismiss the popup.

Thoughts?

## @dandclark — 2022-04-08

I think that doesn't work for the following case:
1. Use clicks on focusable item in popup.
2. User clicks on nonfocusable item in popup (here we get `focusout` with `target` == the focusable item, and `relatedTarget` == null. No light dismiss; so far so good).
3. User clicks on nonfocusable item outside of popup (e.g. the `document.body`). Since no focusable item had focus prior to this click, we don't get another `focusout` event, and the popup does not light dismiss.

Because of scenarios like this I'm not sure that it's possible to define this behavior in a straightforward way in terms of the existing DOM events like `focusout`. We may unfortunately need some platform magic to make this work properly.

## @mfreed7 — 2022-04-19

Ok, slightly modified proposal, which I think takes care of the problem example above:

1. Add a `focusout` event listener to `Document`, which iterates through each Popup in the Popup Stack, starting from the "top" of the stack, and does:
   a. Inspect the `relatedTarget` for the event.
   b. If the related target is null, continue.
   c. If the related target is a flat tree descendent of the Popup, continue.
   d. If the related target is a flat tree descendent of the Triggering Element for Popup, continue.
   e. Light dismiss Popup.

{The above is exactly the same, and will handle all cases except **clicking** on a non-focusable child of the popup, then **tab-navigating out** of the popup to another control.}

2. Add a `focusin` event listener to `Document`, which iterates through each Popup in the Popup Stack, starting from the "top" of the stack, and does:
   c. If the target is a flat tree descendent of the Popup, continue.
   d. If the target is a flat tree descendent of the Triggering Element for Popup, continue.
   e. Light dismiss Popup.

{This should handle the problem case. The first click on the non-focusable child of the popup will cause the related target in the `focusout` handler to be null, so the popup will not close. The tab navigation out of the popup will then not cause any `focusout` events, but will cause a `focusin` on the new focus target. Since that will not be a descendent of the Popup or Triggering Element, the popup will close here.}


Thoughts?

## @mfreed7 — 2022-09-28

@aleventhal mentioned to me that this behavior (pop-up element blur causing a light-dismiss) might be very confusing for screen reader users, since it isn't obvious where the "end" of the pop-up is. It might be too easy to tab past the end of the pop-up, have the pop-up light-dismiss, and then be confused about where that content went, and what lies "behind" in tab order at this point. In fact, I think this is also a concern for sighted users, since it's not always obvious where the tab stops are within a pop-up, so it's easy to accidentally tab out of a pop-up.

I do think this behavior is expected and normal for a `<selectmenu>`, but I'm re-opening this issue to perhaps re-discuss whether we want this behavior for a general pop-up.

## @mfreed7 — 2022-10-06

Thanks for the discussion just now. At this point, it seems like there are really two options:

 1. `blur` is **not** a light dismiss trigger for pop-ups. If a developer wants `blur` to light dismiss, they can add focus catchers and call `hidePopUp()` from JS. Not declarative, but relatively straightforward. This will solve [#609](https://github.com/openui/open-ui/issues/609), but might cause user-confusion if they expect to tab out of a pop-up to get it to close. Users would need to learn to use ESC to escape out of pop-ups.
 2. Only light dismiss via `blur` **once focus has entered** the pop-up (or its triggering/anchor elements). This should solve [#609](https://github.com/openui/open-ui/issues/609). It does not solve the user-confusion problem where the user accidentally closes the pop-up via tabbing "too far". It is also potentially impossible for a developer to "disable" this behavior if they desire - `blur/focusout` are not cancelable.

Thoughts? Other ideas?
