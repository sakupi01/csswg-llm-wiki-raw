First, I'm a bit unclear on Open-UI vs. WhatWG HTML for this. This issue is about standardizing the pseudo element parts of the Web Platform `<input type=range>`. Does this belong here? Or in WHATWG? I do see that there is a [research page](https://open-ui.org/components/slider.research) for "slider" which is the Open UI concept implemented by `<input type=range>`.

## Problem
1. No healthy way to style the filled/progress amount of the slider
    1. CSS only solutions are bound to the size of the track based on the only cross browser solution possible 
        1. [example from native-ui](https://app.native-elements.dev/editor/elements/range) (about as beautiful as they get)
        1. [example](https://codepen.io/argyleink/pen/WNoxjLL): since this design called for the thumb to be larger than the track, CSS only can't show the "filled" amount
    1. current prefixed selectors stomp each other, so developers are forced to duplicate styles
        1. Josh Comeau sharing their learnings about this oddity: [tweet](https://twitter.com/JoshWComeau/status/1359213597331763200?s=20)
    1. Javascript solution runs on page load and watches for user input to update a custom property
        1. [example](https://codepen.io/argyleink/pen/OJbXOvY)
    1. Firefox has `::-moz-range-progress`
        1. [MDN](https://developer.mozilla.org/en-US/docs/Web/CSS/::-moz-range-progress)
    1. we've recently added support for `accent-color` which will tint this fill range state, but still can't target it with a selector and give it a gradient background
2. Partial support of <datalist> [ticks](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/range#A_range_control_with_hash_marks:~:text=A%20range%20control%20with%20hash%20marks,-This) and labels
    1. [vertical] completely unsupported with ticks
        1. vertical tucked behind a prefix `-webkit-appearance: slider-vertical;` why?
    1. labels missing
    1. missing selectors for styling ticks / labels

## Tasks:
1. Separate `track` from `progress` and enable `::-webkit-slider-progress-track` as a style target for CSS
2. Complete current ticks implementation to work with vertical
    1. unprefix the selectors
    1. support attribute
3. Add labels to our slider implementation
4. Help spec a way to style the labels and ticks

## Resources
- Range ticks/hashes/labels: https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/range#A_range_control_with_hash_marks 
- HTML 5.1 spec: https://www.w3.org/TR/html51/sec-forms.html#range-state-typerange

## @thebabydino — 2023-06-23

Just commenting to say that, in light of the data I collected from the [recent CodePen challenge](https://codepen.io/challenges/2023/june/2), I've changed my mind about the anatomy I had in mind prior to this. To exactly what, it's not even clear to me. Every solution comes with its own set of problems.

What I can say is this: if the progress or thumb are inside the track, they will be affected by filter effects, clipping, masking on the track.

For example, we may want to have a filter creating a 3D effect on the track. Let's say we want our track to look like below:

![screenshot of irregular shaped 3D track](https://github.com/openui/open-ui/assets/76854602/9f0d38c1-cec2-46cc-a563-d60ff3716d8e)

We can get this effect with an SVG filter (CodePen [live example](https://codepen.io/thebabydino/pen/RwjzEpm)), but this is also going to affect all descendants - this is why putting the progress and the thumb feels like a bad idea.

Another example would be the case where we want to have a mask on the track, but the thumb should be bigger and expand outside the area retained by the mask:

![screenshot of track with mask and  a bigger thumb](https://user-images.githubusercontent.com/76854602/160440002-19c2e135-5392-456b-831f-a64ad67ba919.png)

However, the track, the progress and the thumb are siblings in the current Firefox implementation and this comes with [major disadvantages](https://gist.github.com/thebabydino/17d690865685abea678791d5307513ab) too.

> From a quick glance it seems the main issue with the CSSWG resolved structure for range is that it doesn't support multiple thumbs. How big of a deal do we think that is?

I agree that this would be the item that I'd bring up. We don't have psuedo-element short-hands so we can't make `slider-thumb` a shorthand for `slider-thumb-one` and 'slide-thumb-two`.

I will note that I'm personally ok with `slider-thumb` being the name for `slider-thumb-two` (or whatever it's called) because most browsers don't implement this and so it would increase complexity. They could of course implement `slider-thumb-one` without `slider-thumb-two` but that would make it weird for devs to have a name that indicates there should be more than one and it not be available.
