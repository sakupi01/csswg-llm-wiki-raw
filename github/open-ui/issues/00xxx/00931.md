## @moniuch — 2025-01-11

_Issue marked as stale but let me add my comment_

- `includes` is probably the most typical scenario for searching, but it is also most typical for it to be case insensitive. Not sure if includes would imply sensitiveness (as [String.prototype.includes](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/String/includes) does). Maybe there should be a way to explicitly provide the sensitivity flag?

- `startswith` is perhaps less common, at least seems counter-intuitive from user PoV - but the same case sensitiveness comment would apply anyway

- `pattern` would be the easiest way to provide the case sensitivity flag, however in practice, the pattern would have to be reassigned with every keystroke - feels a bit of a costly operation for a quick keystroke succession. Feel free to correct me if I'm wrong.

## @josepharhar — 2025-10-31

here are some notes i took during [the meeting](https://github.com/openui/open-ui/issues/847#issuecomment-3469525886)

use cases:
- asynchronously fetching options from a server
- filtering including alt text and/or aria labels and/or a new attribute
- filtering excluding decorative text in the option like online status
- nice default with bailout (for server option fetching or DOM virtualization)
- styling filtered and shown options
- customize rendering of options based on filter, like highlighting text
- turn filtering on or off
    - could be with an attribute like the proposed search attribute, or the beforefilter event

solutions:
- [beforefilter js api](https://github.com/openui/open-ui/issues/847#issuecomment-3461203364)
- several attributes on the input element to control filtering like search and pattern
- attribute on option elements to indicate what its text exposed for filtering is
- provide a match function to return true or false for each option
- beforefilter event provides a promise which can be resolved with options to be filtered

I still don't understand why we need both the filter and search attributes.

I don't really like the idea of the browser taking a filtering function which it then runs on each option, I think that should be built on top of another primitive like the beforefilter event.

It sounds like there is interest in providing both basic filtering attributes like the currently proposed search attribute which has different values as well as a more powerful api like beforefilter. I hope that goes over well in standards discussions.

Making the browser provide a callback in the beforefilter event so script can provide the options which match sounds useful in order to make options match the filtering pseudo-classes, but also sounds tricky. What do you think @keithamus? @mfreed7 do you have any additional thoughts on how to describe this api?

## @josepharhar — 2025-11-05

Besides making the beforefilter event cancelable, it sounds like there are multiple ways we could provide script with a way of saying which options are filtered:
1. Make a way to provide the browser with a promise in the event handler. Script should resolve the promise with a lits of option elements which do (or don't) match the filter, and they match (or don't) the pseudo-class for filtered out options. I'm not sure what should happen if another beforefilter event needs to be fired before the first one has resolved from script. It could look like this:
```javascript
target.addEventListener('beforefilter', event => {
  event.preventDefault();
  event.optionsPromise = new Promise(async resolve => {
    // Fetch options from server and maniuplate the DOM
    // or just run something on existing options
    let validOptions = ...;
    resolve(validOptions);
  });
});
```
2. Don't provide any promise/async primitives in the event and let script take care of it. Add an IDL to option elements which indicates whether they are filtered out or not which can be set by the browser or by script which affects the pseudo-class. Example:
```javascript
let abortController = null;
target.addEventListener('beforefilter', event => {
  event.preventDefault();
  if (abortController) {
    abortController.abort();
  }
  abortController = new AbortController();
  // Fetch options from server **using abortController.signal** and manipulate the DOM
  // or just run something on existing options
  for (const option of target.querySelector('option')) {
    option.filtered = shouldFilterOption(option);
  }
});
```
I like option 2 because it clearly answers how multiple consecutive beforefilter events works (the browser can always just fire them immediately) and script can just do whatever kind of debouncing it wants. Instead if just adds the filtered IDL to option elements which I think is simple. What do yall think?
