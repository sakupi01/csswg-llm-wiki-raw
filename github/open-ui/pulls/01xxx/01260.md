A proposal for a more scoped version of focusgroup. This proposal differs from the [original explainer](https://open-ui.org/components/focusgroup.explainer/) in the following ways:
* Usage of the attribute is strictly limited to select aria roles.
* No CSS support
* Grid support is moved to be a future consideration.

Please see the "Alternative Scoping Mechanism" for another way to scope the scenarios where focus group can be used **without** breaking the norm of aria being a semantic-only set of attributes. If there is consensus that this approach is favored, I will flip the proposal to favor that approach instead.

## @janewman — 2025-08-21

**Update incoming**
After discussing this in today's Aria WG meeting, @smhigley had what I think is a great addition to the "Alternative Scoping Mechanism" that I will be updating this PR with shortly.

### Usage as previously explained in this proposal.
```html
<div id="one" role="radiogroup" focusgroup="wrap" aria-label="Text formatting">
  <div role="radio" aria-checked="false" tabindex="-1">Bold</div>
  <div role="radio" aria-checked="true" tabindex="0">Italic</div>
  <div role="radio" aria-checked="false" tabindex="-1">Underline</div>
</div>
```
In this approach, role is required to be present and match a supported role. **This breaks norms around aria being semantic-only.**
### Alternative scoping approach that keeps aria as semantic-only (preferred)
```html
<div id="two" focusgroup="radiogroup wrap" aria-label="Text formatting">
  <div role="radio" aria-checked="false" tabindex="-1">Bold</div>
  <div role="radio" aria-checked="true" tabindex="0">Italic</div>
  <div role="radio" aria-checked="false" tabindex="-1">Underline</div>
</div>
```
In this example, `focusgroup` will "implicit the specified role into the element", in this case, the element with id of "two" will have the role of `radiogroup`.
### Sarah's Addition to the alternative scoping approach
```html
<div id="two" focusgroup="radiogroup wrap" aria-label="Text formatting">
  <div aria-checked="false" tabindex="-1">Bold</div>
  <div aria-checked="true" tabindex="0">Italic</div>
  <div aria-checked="false" tabindex="-1">Underline</div>
</div>
```
With this addition, children whose focus is managed by `focusgroup` will also have their appropriate role set, ensuring:
1. Authors are guided into following accessible patterns.
2. Less attributes for authors to set explicitly.

## Upcoming changes
Before meeting today, I had intended on publishing an update that makes the second approach (alternative scoping mechanism) the default used in the document, but I think Sarah's suggestion is quite compelling, and will be moving forward with this approach, with the others listed in an "alternatives considered" section.

## @sorvell — 2025-09-04

> This was my initial approach (https://github.com/openui/open-ui/pull/1260#issuecomment-3211641378), but early feedback and Aria WG discussion raised the issue that aria needs to continue to be semantic-only, and this approach broke this behavior by tying behavior to the aria role.

If aria is semantic only then it should not impact behavior. The proposal here tries to side-step that by using aria roles outside of aria attributes and then inferring the attributes based on those settings. Although this is slightly similar to how some native elements have inferred roles, I would still say that it is giving aria non-semantic behavior and therefore still runes afoul of this criticism.
